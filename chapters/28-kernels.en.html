In the GLM recipe, swapping only the kernel that multiplies the “fat” prefill experts took the MoE layer at 7,168 tokens from 77–91 ms down to 31 ms, without changing a single weight. In the DeepSeek recipe, turning on an “optimized” decode path cost 15% in speed and was switched back off. The kernel is where the math meets the silicon. Here you will see it as a workshop with conveyor belts (tiles, stages, epilogues), learn which languages it is written in, understand why the same computation calls for different kernels in prefill and in decode, and read every kernel flag in the recipes knowing what it swaps underneath. At the end, the second version of the GLM recipe, on an engine called TensorFold, shows what changes when a kernel is forbidden to let the batch alter a single bit of a row.

What a kernel is and how it reaches the SM

When vLLM runs y = x @ W, the CPU multiplies nothing: it enqueues a launch (“run function K with this grid, these pointers and these sizes”). That function, compiled for the GPU, is a kernel. The request goes into a CUDA stream, a queue the GPU consumes in order, and the CPU moves on. A single decode step fires off hundreds of launches (the CPU cost of each one is the subject of the next chapter).

The grid is made of CTAs (thread blocks). Each CTA runs entirely on a single SM, in warps of 32 threads (Inside the GPU). How many CTAs fit on an SM at the same time, the occupancy, depends on the registers and shared memory each one asks for. If the grid has more CTAs than the GPU can run at once, they go in waves:

\[ n_{\text{waves}} = \left\lceil \frac{n_{\text{CTA}}}{n_{\text{SM}}\cdot o} \right\rceil \qquad\qquad \text{mean utilization} = \frac{n_{\text{CTA}}}{n_{\text{waves}}\; n_{\text{SM}}\; o} \]
  • \(n_{\text{CTA}}\): CTAs requested in the launch (the grid size)
  • \(n_{\text{SM}}\): the GPU's multiprocessors (GB10: 48; datacenter GB300: 160)
  • \(o\): occupancy, concurrent CTAs per SM

In the figure, each square is an SM and each little bar is a CTA at work. Change the grid and switch GPUs.

Notice the step: with 48 SMs and occupancy 1, 56 CTAs need two waves, and the second one runs with 40 SMs sitting idle. A grid built for the 160 SMs of a GB300 turns into several waves on a GB10. That is the argument behind the launch profiles of QSA, Qwen's sparse attention, in which a cheap indexer picks ~2,048 positions per query (Sparse attention; section 4).

Memory or math: who rules the clock

Every kernel reads bytes and does FLOPs, and the minimum time is the larger of the two ceilings:

\[ t \;\gtrsim\; \max\!\left(\frac{\text{bytes}}{B},\; \frac{\text{FLOPs}}{P}\right), \qquad I = \frac{\text{FLOPs}}{\text{bytes}}, \qquad I^{*} = \frac{P}{B} \]
  • \(B\): memory bandwidth (GB10: ~273 GB/s theoretical, ~230 GB/s effective in the reports)
  • \(P\): peak FLOPs (GB10: ~125 dense BF16 TFLOPS, an estimate from the GLM repository)
  • \(I\): arithmetic intensity; \(I^{*}\): the “ridge”, ~458 FLOP/B on the GB10 according to the GLM repository

Below the ridge, the kernel is memory-bound: the SMs wait for bytes. Above it, it is compute-bound. In a linear layer, what decides the side is M, the number of rows (tokens) that pass through it in the step.

Deep dive: where the ~112 FLOP/B of GLM's MoE comes from

A GEMM of \(M\times K\) by \(K\times N\) does \(2MKN\) FLOPs and, with small M, basically reads just the weights: \(KN\cdot b/8\) bytes. So \(I \approx 16M/b\): 4M FLOP/B with 4-bit weights. In a 1,024-token prefill chunk, top-8 spreads 8,192 pairs over 288 experts, ~28 rows per expert, and \(4\times 28 \approx 114\) FLOP/B: the GLM repository's “~112 FLOP/B, below the ridge of 458”. Even the MoE prefill is memory-bound. (Interpretation: the average-based arithmetic is ours.)

Why this matters

In decode, M = sequences × (1 + speculative tokens): 4 × 8 = 32 in GLM (DFlash2 with k=7), 7 per request in DeepSeek (DSpark, k=6), 4 per request in Qwen (MTP=3). In prefill, M ranges from 1,024 to 8,192 per chunk. Nearly every kernel flag in the recipes is a dispatch by M: one kernel for “few rows, lots of bytes”, another for “many rows, lots of math”.

Inside a GEMM: tiles, the mainloop and the kernel languages

Almost all of an LLM's time goes to GEMMs: \(C_{M\times N} = A_{M\times K}\,B_{K\times N}\), with A = activations and B = weights. A naive kernel would read each element of B once per row of A. Every serious kernel uses tiling: each CTA takes a \(B_M\times B_N\) block of C and walks along K in slices of \(B_K\), bringing the A slice and the B slice into shared memory (SMEM), where each number is reused \(B_N\) (or \(B_M\)) times:

\[ I_{\text{tile}} = \frac{2\,B_M B_N B_K}{\left(B_M B_K + B_K B_N\right)\cdot \text{bytes per element}} \]
  • \(B_M, B_N\): height and width of one CTA's output tile (e.g., 128 × 128 in GLM's E2 kernel)
  • \(B_K\): depth of the K slice per iteration (16 in E2, 32 in E3)

In the figure, the “tiles” view shows that walk and the roofline ruler; the “pipeline” view opens up the mainloop, the loop that fetches the next slice while computing the current one.

With M = 1, the C tile is almost empty: there is no reuse of B, and the kernel becomes a GEMV whose only mission is to read the weights at peak bandwidth. With M = 8,192, the same tile becomes a math machine. There is no such thing as “the good kernel”: there is the good kernel for a given M.

Anatomy of the mainloop

  1. cp.async (global → SMEM). An asynchronous copy that bypasses the registers: the thread fires it off and moves on.
  2. Stages (circular buffer). With S stages, S−1 slices stay in flight while the current one is consumed, hiding DRAM latency. GLM's E3 uses 4.
  3. ldmatrix (SMEM → registers). Loads fragments in the layout the tensor core expects.
  4. mma.sync. The per-warp matrix multiply on the tensor core (e.g., m16n8k16 FP16 → FP32). SM121 uses mma.sync, not the tcgen05 of datacenter Blackwell, which is why GLM reuses the ExLlamaV3 path.
  5. Epilogue. Once K is done, the FP32 accumulator is still in registers: it is the cheap moment to apply a scale, an activation, a rotation or a routing weight before writing C.
Analogy: the workshop with conveyor belts

The CTA is a workshop: DRAM is the faraway warehouse, SMEM is the workbench, the registers are the hands, the tensor core is the press. With 1 stage, the press stops every time the truck leaves to fetch the next box; with S stages, S−1 boxes are already on the conveyor, and cp.async is the delivery order nobody stands around waiting for. Swizzle arranges the workbench so 32 hands don't bump into each other. The epilogue is the packaging: the finishing touches are done before the part leaves, without shipping it to another building and back.

Two details separate correct from fast. Swizzle: SMEM has 32 banks of 4 bytes; if the threads of a warp touch the same bank at different addresses, the accesses are serialized, and XOR-ing the column with bits of the row spreads them out (the figure's toggle). Spills: when registers run out, the compiler dumps values into local memory (LDL/STL), which in practice is DRAM with a cache.

In the recipe: the trellis arrives early, in 16 B loads

In TensorFold's expert decode kernel (dec_kernel), each lane read the EXL3 trellis with 32-bit __ldg loads, one k step ahead, and only after a chain of dependent reads (count → item → the item's rows). With TF_GLM_EXL3_LOADS=nc, the recipe default, the trellis comes in 16 B non-coherent loads (ld.global.nc.L1::no_allocate.v4.u32), still one k step ahead (nc2 and nc4 go to 2 and 4): the read-only path, without filling L1 with data that is read once. The item comes with its count in a single round trip, and the first steps' words are requested before the item's rows reach SMEM, which shortens the chain. The words go through a 1 KB staging area in the warp's slice and are read back in the layout that decode_tile and the m16n8k16 mma expect. It is only data movement, so the bits do not change. On its own: prose 48.36 → 48.78 tok/s, code 59.54 → 60.42 (1 request). The patch is adapted from another community project, jayleaton/glm53-tensorfold-spark.

What language is a kernel written in

Every GEMM kernel goes through these steps. What changes from language to language is who writes each one: you, a template library or a compiler.

CUDA C++
You write the code for one thread (blockIdx, threadIdx) and do everything by hand: copies into SMEM, barriers (__syncthreads()), swizzle and the mma.sync in inline PTX. nvcc compiles it at build time (AOT) for an exact architecture and produces a .so extension. DeepGEMM is also CUDA C++, but JIT-compiled.
CUTLASS / CuTe
NVIDIA's C++ templates: tile, stages and epilogue become parameters, and the library assembles the “collective” mainloop and epilogue (carried out jointly by the CTA's threads). CuTe describes layouts as shape:stride, that is, which thread touches which element.
Triton
Python. You write a program, one instance of the kernel that becomes a CTA and operates on whole tiles (tl.load, tl.dot); tl.program_id(0) tells you which piece is yours. The compiler splits the tile among the num_warps warps and generates the copy pipeline (num_stages), the swizzle and the tensor core instructions. tl.constexpr arguments, such as BLOCK_N, are compile-time constants. JIT on the first call.
CuTeDSL
CuTe in Python, with JIT.
TileLang
A tile-level Python DSL (buffers, pipelined loop, T.gemm) that generates CUDA and JIT-compiles it.

In the recipes: CUDA C++ in GLM's exllamav3_ext (E2, E3, FAST), in the cooperative MoE, in FlashKDA and in Qwen's GDN decode; CUTLASS in Qwen's FlashInfer MoE and in CutlassFP8ScaledMMLinearKernel; Triton in QSA, in chunk_kda and in DSpark; CuTeDSL in b12x; TileLang in DeepSeek's mHC. That is why a Triton kernel is swapped by editing a .py in the container (the QSA and DSpark patches), while a CUDA C++ one requires recompiling the extension in the image build (the exllamav3_ext patches in GLM's Dockerfile).

In the recipe: fewer stages in registers, more in SMEM

The stock exl3_moe_kernel<4,256> (K4 = 4 bits per weight) spilled on SM121 (88 B frame, 39 LDL). patch_exl3_decode_pipeline.py creates glm53_exl3_moe_fast_kernel: 1 stage of fragments in registers and 8 in SMEM (stock: 3 and 3), plus one fewer rotation. Each EXL3 matrix carries two vectors: suh, which multiplies the input before the Hadamard rotation, and svh, which multiplies the output after it (Rotations, trellises and EXL3); if gate and up share the same suh, one input rotation serves both. Result: 127 registers, 0 LDL, serving +7.71% / +8.88% / +14.59% (structured / code / json), with GLM53_EXL3_MOE_FAST=1 (long-coding, TP2/SM121 only, fails closed without the patch). Numerics “INCONCLUSIVE”: the stock controls also fail the KL ≤ 0.01 gate.

Deep dive: the E2 kernel (CUDA C++) in one paragraph

exl3_fat_gemm multiplies by weights that stay compressed: each 16×16 block is a bitstream of a trellis (with K4, 64 16-bit words). The 256-thread CTA (8 warps) covers a 128×128 tile and advances along K 16 at a time. The input (FP16, already multiplied by suh and rotated) goes into SMEM with an XOR swizzle, and each warp decodes its trellis block straight into registers, in the mma m16n8k16 format, without rebuilding BF16 in DRAM. The epilogue does the 128-wide Hadamard of the output via lane exchanges and multiplies by svh. The _scatter version adds into out[token] without atomics; E3, with several experts writing to the same token, uses a 16 B vector atomicAdd (float4, sm_90+), hence EXL3_FAT_MOE_MIN_CAPABILITY=(9,0).

Deep dive: rewriting a Triton kernel in CUDA without changing a bit

In decode, the TensorFold recipe (patch 0019) replaced the Triton kernel _hc_partial (half of the hyper-connections' hc_pre: 24 mixing products and one sum of squares per row, over 16,384 columns) with a CUDA one that uses 48 blocks per row instead of 16. Since the recipe demands the same bits (section 9), the CUDA version copies what the Triton compiler had decided: the layout (sizePerThread [1, 8], threadsPerWarp [2, 16]), the in-order sum of 8 products per thread, the butterflies over 8, 4, 2 and 1 lanes and the (w0 + w2) + (w1 + w3) combination across warps, with __fmaf_rn, __fadd_rn and __shfl_xor_sync. The lesson holds in any language: in Triton you do not write the reduction tree, but it exists, and it is what sets the bits.

Fusion: the fastest byte is the one that never goes back to DRAM

If decode is bandwidth-bound, every intermediate that one kernel writes to DRAM for the next one to read is wasted bandwidth. Fusing means doing the next kernel's work while the data is still in registers or SMEM. The classic case is each expert's SwiGLU FFN (Transformer block), \(y = W_{\text{down}}\big(\mathrm{silu}(W_{\text{gate}}x)\odot W_{\text{up}}x\big)\):

\[ \underbrace{2I}_{\text{write } g,u} + \underbrace{2I}_{\text{read } g,u} + \underbrace{I}_{\text{write } a} + \underbrace{I}_{\text{read } a} \;\;\xrightarrow{\text{epilogue fusion}}\;\; \underbrace{I}_{\text{write } a} + \underbrace{I}_{\text{read } a} \]
  • activation elements moved through DRAM, per row (token)
  • \(I\): the expert's intermediate width (moe_intermediate_size 2048 in GLM and in DeepSeek)
  • \(a = \mathrm{silu}(g)\odot u\): the input to the down GEMM

Turn on the fusions in the figure and watch the trips to DRAM turn into on-chip traffic.

The weights are read the same way in every arrangement: fusion saves activations and launches, a little in decode and a lot in prefill. In the recipes, the epilogue of GLM's E3 does Hadamard + svh, the SwiGLU clamp (limit 10), the sigmoid and the rotation of the down input; DeepSeek's _dspark_markov_block_argmax_kernel finds the local top-1 of base_logits + markov_embed @ W2ᵀ in vocabulary blocks of 256 without materializing the 129,280 logits; and FlashAttention (next section) fuses QKᵀ, softmax and ·V.

Pitfalls: fusion isn't free

(1) It doesn't always speed things up. B12X_W4A16_TC_DECODE=1 (small-M decode, M ≤ 8, top-k sum fused into the FC2 epilogue) measured 46 vs 55 tok/s at c=1 (−15%) and was left at 0. (2) It changes the summation order. The fused finalize of the FlashInfer CUTLASS MoE sums the experts in a variable order; since floating-point addition is not associative (How the computer stores numbers), the greedy output changes between identical runs. (3) fast-math changes rounding. GLM's E3 is compiled without --use_fast_math, and the sigmoid uses exp in double precision and __fdiv_rn to reproduce torch.sigmoid.

DeterminismVLLM_FLASHINFER_MOE_FUSED_FINALIZE=0

Injected by start.sh when VLLM_MOE_DET_FINALIZE=1, with a separate autotune cache (…/flashinfer_autotune_cache_unfused); the overlay files/determinism/flashinfer_cutlass_moe.py makes the unfused finalize selectable. With QSA's top-k sorted as well, the logprob spread dropped from 0.25 nats (median) and 6.07 (max) to 0/0, and the greedy outputs went from 5/5 distinct to 1/5, at a cost of ~4% in decode and prefill. That is why it is opt-in, for bit-identical A/B runs.

In the recipe: fused epilogue, “last block” and copied rounding

In TensorFold's expert dec_kernel, the down projection (SK = 1) applies the 128-point Hadamard and svh to its own sums and writes Y: “no Z round trip, no epilogue launch”. In gate/up, with SK = 4, no block holds the whole sum; the TF_GLM_EXL3_FUSE=2 variant elects the last block to finish (a counter bumped with atomicAdd after __threadfence, the same pattern as the cooperative MoE in section 7), which reads the partials in split order and runs the epilogue. It stayed off: “measured slower”. On the numerical side, the Triton version of the chunked KDA (patch 0014, which reworked 0012's for the GB10 and for precision) ran with enable_fp_fusion=False, libdevice.exp and div_rn to round like kda.cu, which is compiled with --fmad=false: a bf16 tie rounded the other way moves a key by 2−8. The CUDA kernel that replaced it (section 9) inherited the rule: --fmad=false, expf and IEEE division. It is the discipline of the vLLM recipe's E3 (compiled without --use_fast_math), carried all the way to FMA contraction.

Attention in blocks: online softmax, FlashAttention and split-K

The attention of one query needs \(\mathrm{softmax}(qK^\top/\sqrt d)\,V\) (Attention). Materializing the row of scores (and, in prefill, the n×n matrix) would cost absurd amounts of memory and bandwidth. FlashAttention walks K and V in blocks and keeps only three things per row: the partial maximum \(m\), the normalizer \(\ell\) and the accumulator \(\mathbf o\). This is the online softmax:

\[ m' = \max\!\big(m,\ \max_{j\in\mathcal B} s_j\big),\qquad \ell' = e^{m-m'}\,\ell + \sum_{j\in\mathcal B} e^{s_j-m'},\qquad \mathbf o' = e^{m-m'}\,\mathbf o + \sum_{j\in\mathcal B} e^{s_j-m'}\,\mathbf v_j \]
  • \(s_j = q\cdot k_j\cdot\text{scale}\): score of key \(j\); \(\mathcal B\): the iteration's block of keys
  • \(e^{m-m'}\): the factor that rescales what has already been summed when a larger maximum shows up
  • at the end, the output is \(\mathbf o/\ell\), identical to the exact softmax

Follow along step by step with real numbers; steps 6 and 7 carry the rule over to prefill.

In prefill, each CTA takes a block of \(B_q\) queries and walks the blocks of \(B_k\) keys and values, bringing each one into SMEM once for all \(B_q\) queries, with one \((m,\ell,\mathbf o)\) state per row. Only one \(B_q\times B_k\) tile of scores exists at a time, and with a causal mask the blocks above the diagonal aren't even loaded.

Qwen's patches play two tricks on top of this flow: exp2 instead of exp (the last step of the figure) and “folded” scales. With FP8 KV (Quantizing the KV cache), \(q\cdot(s_k k) = s_k\,(q\cdot k)\): the kernel computes the product with the converted K and multiplies the scores by k_scale afterward; the V scale comes in at the end.

Decode: few rows, idle SMs, split-K

In decode there is 1 (or 1+k) query per sequence and per KV head: in Qwen at TP2 (1 kv-head per GPU), a request with MTP=3 produces 4 rows, and four CTAs on a 48-SM chip would leave 44 idle. Split-K (flash-decoding) divides the key axis into S partitions, gives one CTA to each (row, partition) pair and merges the partials via log-sum-exp:

\[ \mathrm{LSE}_p = m_p + \ln \ell_p,\qquad \mathrm{LSE} = \ln\sum_{p=1}^{S} e^{\mathrm{LSE}_p},\qquad \mathbf o = \sum_{p=1}^{S} e^{\mathrm{LSE}_p-\mathrm{LSE}}\;\frac{\mathbf o_p}{\ell_p} \]
  • \(p\): a partition of the key axis, computed by an independent CTA
  • \(m_p,\ \ell_p,\ \mathbf o_p\): the online softmax state at the end of the partition
  • \(\mathrm{LSE}_p\): the partition's “size” on a log scale (in the kernels: mid_lse, next to mid_out)

More partitions fill more SMs, but each one pays for a prologue and writes a partial that the merge has to read: the sweet spot depends on how many SMs the GPU has.

This is the Qwen repository's diagnosis: the stock table of _qsa_sparse_paged_gqa_splitk_kernel was “tuned on GB300”; on the GB10, the small-decode bucket (block_n = 16, 64 partitions, 4 warps) launches ~5× more CTAs than fit in one wave and then merges 64 partials. The gb10 profile cuts that to 16 partitions (“≈1.3 waves instead of ≈5”), but it is a non-benchmarked guess (“the GPU was busy”), and the default is still stock. In the table, block_n is the BLOCK_N of the Triton snippet in section 2 (keys per iteration), splits are the partitions and warps is num_warps; the bucket is derived from base_programs = rows × kv-heads.

In the recipe: when split-K is surplus

Split-K pays prologues and partials to fill idle SMs. In a 2,048-row prompt chunk there is no idle SM left, and TensorFold removed the partials from the prefill's sparse latent attention: _sparse_onepass (Triton) gives one program to each (row, group of 32 heads, latent slice), walks all the selected tokens in a single online softmax and writes BF16 directly, with no mid_out, no mid_lse and no merge. The fixed tile (32, 32, 1) makes a row's bits independent of the chunk (section 9). Quantized GEMM: Marlin, CUTLASS and the crossover by M

Quantizing weights (Why and how to quantize) only speeds things up if some kernel knows how to consume the small bits. There are two families:

Weight-only · W4A16 / W8A16

  • 4/8-bit weights; activations in BF16/FP16, no new error.
  • The kernel dequantizes in registers and feeds a 16-bit MMA.
  • Reads 2–4× fewer bytes: wins in decode; computes at the 16-bit rate: loses in prefill.
  • E.g.: Marlin, ExLlamaV3/EXL3, b12x W4A16.

Weights + activations · W4A4 / W8A8

  • Activations quantized on the fly.
  • Native FP8/FP4 tensor cores (on the GB10, FP4×FP8 at ~4× the BF16 rate, an estimate from the DeepSeek repository): wins in prefill.
  • Costs a quantization kernel and extra error: W8A8 on KDA's in_proj (GLM #182) gave a KL of 7.99× the null baseline and 23 flips.
  • E.g.: CUTLASS FP4/FP8, FlashInfer CUTLASS MoE.
Deep dive: why Marlin is fast at small M

At small M, winning means reading each weight exactly once, at peak bandwidth, and hiding everything else behind that read. Three ideas from Marlin's general design (not from the recipes): (1) Repacking at load time: the weights are reordered once into the tensor core's fragment layout, and each thread uses 16 B loads to read precisely the bits it will use. (2) Dequant via bit tricks: one lop3 slots the weight's bits into the mantissa of a “magic” FP16, and a subtraction removes the offset, work that fits in the shadow of the loads. (3) Stripes: the tiles are divided into stripes across the SMs, so every SM has work even with few tile columns. The price is shape rigidity: in GLM at TP3, with 22 KDA heads per rank, the pitch of f_b_proj/g_b_proj is not 8-aligned, Marlin won't take them, and they stay in BF16.

Notice the scissors. Marlin W8A16 reads half the bytes of BF16 and, according to the repository, does well at small M; but dequantizing and using a 16-bit MMA makes it 3.1–3.7× slower from M = 768 on (measured). The crossover itself was not measured, and didn't need to be: in the measurements, decode stayed at M ≤ 220 and prefill at M ≥ 768. MoE in kernels: fused MoE, grouped GEMM, thin and fat experts

At the kernel level, a MoE layer (Mixture-of-Experts) is a choreography:

  1. Routing. Router GEMM + top-k (GLM: 8 of 288; DeepSeek: 6 of 256; Qwen: 10 of 512).
  2. Permutation. Sort the (token, slot) pairs by expert, so each expert sees its rows contiguously.
  3. Expert GEMMs. gate/up → SwiGLU → down, with M = that expert's rows.
  4. Finalize. Undo the permutation, multiply by the routing weight and sum each token's k contributions.

A fused MoE does all this in a few launches; its heart is a grouped GEMM, a single kernel that runs dozens of GEMMs of different sizes, reading from a table on the device where each problem starts.

Analogy: the post office sorting room

Each token arrives with k envelopes, one per chosen expert. The permutation is the sorting: the envelopes are ordered by destination, and each expert receives one contiguous stack. The grouped GEMM is the single truck that covers every route in one trip without calling headquarters (the CPU): it carries a table on its dashboard, written on the GPU, with the address and size of each stack. The finalize is the delivery: each reply goes back to its token, weighted by the routing, and the k replies are added up.

The challenge is that the rows per expert change brutally between phases. Play with the figure:

In decode (32 rows, 256 pairs), almost every expert gets 0–3 rows: thin experts, where what matters is reading each weight once, fast. In prefill (a 1,024-token chunk), the hottest expert shows up in almost every token (max 1,024, mean of the max ≈ 920, measured in the GLM repository): fat experts, where math dominates. No single kernel serves both worlds.

The GLM ladder: from the Python loop to the grouped GEMM

The core idea is to trade questions to the CPU for a table on the GPU. In decode, exllamav3_ext.exl3_moe handles the layer in a single launch: at load time, build_exl3_fused_state writes the address of each expert's weights to the device, and the kernel finds, on its own, whatever expert the routing picks (EXL3_FUSED_MOE=1; 0 is a Python debugging loop, and FAST requires 1). The launch buffer only holds EXL3_TEMP_ROWS_FUSED rows per expert; the experts that exceed it become “fat”. Before, 91–98.6% of the prefill MoE layers had experts above the cap of 128, and they fell into a Python loop with BF16 reconstruction and .nonzero().tolist(): one host-device sync per layer (1.45 s of CPU in aten::nonzero in a 3-step capture). In the recipe: the same thin/fat problem, another design

TensorFold has no thin/fat boundary and no per-expert row cap. In prompts, the plan splits each expert's rows into items of up to 64 pairs (a hot expert becomes several items) and section 9's EXL3 prompt kernels run them; in decode, every window (up to 32 rows in the batch) goes to dec_kernel. The input rotation became per row too: the patch checks bit for bit (through view(int16), because “-0 is not +0”) that every expert in the checkpoint has the same gate and up suh. So the rotated input depends only on the row, and the 16 rotations per row of top-8 × 2 matrices become 1 (TF_GLM_EXL3_ROWROT in prompts, TF_GLM_EXL3_XROW in decode). It is the same observation that gave the vLLM recipe's FAST kernel one rotation less.

Completion counters elect the last block to arrive, which applies the rotations and the activation and, in B, sums the slots in a fixed order.

Tune, compile and launch: autotuning, JIT, PDL and streams

Autotuning: measure instead of guessing

A parameterized kernel (tile, splits, warps, stages) has several tactics, and the best one depends on the shape and the GPU. Autotuning measures the candidates at the real shape and stores the winner in a hash-keyed cache. Under TP there is an extra requirement: all ranks must run the same sequence of kernels, because each collective (the all-reduce, for example) only finishes when everyone arrives (Parallelism). Four risks showed up:

  • Boot stability. In GLM, FlashInfer's autotune of sparse-MLA and fused_moe (gemm1/gemm2) killed rank 0 on SM121, and the full autotune blew through unified memory (Unified memory): the recipe uses --no-enable-flashinfer-autotune and a patch to kernel_warmup.py that removes the sparse-MLA warmup and makes the autotuner return early (“Skipping FlashInfer autotune on SM121”).
  • Incomplete coverage. In DeepSeek's production lane (A), --enable-flashinfer-autotune stays on and the cache persists in vllm-cache/flashinfer_autotune_cache/<hash>/, but the stock sparse-MLA warmup only covers tokens=16: unseen shapes fall back to tactic=-1, and the first request after a restart can see a TTFT of 6–10 s.
  • Different ranks, different kernels. In Qwen (v0.30 lane), a persisted cache that differed between the nodes once hung TP2 in the autotune collective. The fix was VLLM_FLASHINFER_AUTOTUNE_CACHE_DIR=/tmp/fi_autotune, an ephemeral cache inside the container, so both nodes start from the same empty state. DeepSeek's Stage-C overlay (lane B) extends autotune to the SM120 sparse-MLA decode (including DSpark's k+1 shapes) and has rank 0 tune and broadcast the tactics (broadcast_object).
  • Autotune inside the capture. ExLlamaV3's autotune synchronizes the stream when it sees a new shape, which breaks CUDA graph capture; GLM warms up every shape × rows {1, 2, 4, 8, 16} beforehand (next chapter).

JIT, AOT and specialization

The languages from section 2 split into two ways of compiling (JIT vs AOT). AOT: GLM's exllamav3_ext (turboderp c5d9c657, with the aarch64, fat and decode patches) is compiled with TORCH_CUDA_ARCH_LIST=12.1a, and the build asserts that the symbols exist (exl3_moe, exl3_fat_gemm, exl3_fat_moe_*, glm53_fast_moe_version()==1). JIT: Triton, CuTeDSL, TileLang, DeepGEMM and FlashInfer compile when a shape shows up and need the toolchain in the container. DeepSeek exports PATH, CUDA_HOME and LD_LIBRARY_PATH pointing to /usr/local/cuda and pins DG_JIT_USE_NVRTC=0 + DG_JIT_NVCC_COMPILER=/usr/local/cuda/bin/nvcc (DeepGEMM compiles with nvcc, not NVRTC).

Specialization. Each value of a tl.constexpr produces a separate compiled variant, with the dead branches removed: that is why KV_QUANT_MODE=0 leaves QSA's BF16 code identical to the original. Triton also specializes pointers by 16-byte alignment: in DeepSeek, the mixed prefill sliced two scalar pointers at the same offset and produced 3 alignment states × 2 block sizes = 6 cache entries, with JIT in the middle of serving, which could make the other rank blow through the NCCL watchdog (600 s). Hotfix #133 marks them with do_not_specialize_on_alignment.

Names by compute capability. The vendored DeepGEMM generates sm121_* names on the GB10, but only ships sm120_* headers; production was living off old cubins, and any cache miss failed with Failed to open …/sm121_fp8_mqa_logits.cuh. hotfix-deepgemm-sm121-mqa-header-alias.sh (DSPARK_ENABLE_DEEPGEMM_SM121_ALIAS=1, mandatory with the indexer's MXFP4 cache) writes four headers (fp8/fp4, paged or not) into DEEP_GEMM_IMPLS_DIR with #include "sm120_X.cuh" and #define sm121_X sm120_X: SM120 and SM121 share the consumer Blackwell ISA. FLASHINFER_DISABLE_VERSION_CHECK=1, in turn, appears in both recipes: in DeepSeek because the cubin/JIT cache is 0.6.13 and the Python package is 0.6.15; in GLM, in the fixed environment (reason not documented).

In the recipe: measured tables, JIT with versioned names

TensorFold does not tune tactics at runtime: its tile tables were measured once on the GB10 and live in the code (DEC_TILES for the decode Q4; F8_PROMPT, “swept on GB10 at 2,048 rows; no choice changes a row's bits”). There is no tactic to diverge between ranks, and a shape missing from the table uses the default configuration without measuring anything at runtime; the price is measuring again on another GPU. The CUDA C++ extensions are not built AOT into the image: they compile JIT on the first start of each image (a few minutes), into a cache mounted per image hash (TORCH_EXTENSIONS_DIR=/cache/torch_extensions). Every patch that changes a .cu bumps the version in the module name (tensorfold_glm_exl3_v1 → … → v19; tensorfold_qmm_v3 → v4), so no cache ever loads an old .so. And the cold-JIT risk in TP shows up: since each rank compiles on its own, the two can “drift tens of seconds apart”; until the engine is built, every eager RoCE all-gather (outside a CUDA graph) waits for the other rank at an NCCL barrier (patch 0052).

Overlapping launches: PDL and streams

Between two kernels on the same stream there is a bubble: the second only starts when the first finishes. Programmatic Dependent Launch (Hopper onward) lets the next kernel run its prologue while the previous one finishes, and wait at an explicit point (griddepcontrol.wait) before reading what the previous one wrote. GLM recorded a race (“PDL lowering races KDA state kernels on SM12x”), and the patch changes the major >= 9 gate to major in (9, 10), turning PDL off on the GB10. (Interpretation: the repository only records the race; the typical PDL failure mode is a dependent kernel consuming data without a griddepcontrol.wait first.)

Analogy: the relay baton

Without PDL, the second runner only takes off once they have the baton: safe, but slow. With PDL, they start running inside the exchange zone (the prologue) and only reach back at the agreed point, the griddepcontrol.wait. If they close their hand before the baton arrives, they leave empty-handed: that is the race, and nobody raises a flag, because the race goes on, with the wrong result.

The other way to overlap is different streams. DeepSeek creates 3 auxiliary streams for independent attention-input GEMMs (the compressor's kv_score, indexer.weights_proj and the indexer compressor's kv_score), leaving fused_wqa_wkv on the default stream: small GEMMs, which on their own don't fill 48 SMs, share the chip. (GLM's E1 tier also uses a side stream, to copy counts to the host.)

In the recipe: a side stream that only reads

A TensorFold decode layer alternates DRAM-bound matmuls with phases that leave DRAM idle: the two all-gathers (the RoCE wait), the hyper-connection glue, router and top-k, the KDA recurrence and the latent attention core. With TF_GLM_L2PF=1, a small kernel on a side stream does an L2 prefetch of the weights the main stream will read next (cp.async.bulk.prefetch.L2, or prefetch.global.L2::evict_last, or ld.global.cg), up to 8 MiB at each of three points in the layer (TF_GLM_L2PF_SITES=afo). For a 4-bit matrix whose launch fits in one wave (≤ 192 programs = 4 CTAs/SM × 48 SMs, according to the code), it fetches the start of each slice early, to shorten the slowest program of the wave (section 1); and the shared expert now runs before the routed ones, so the routed experts' stream of more than ~100 MB does not evict it from L2. The stream is forked at the point and joined before the forward ends, so the branches of the CUDA graph meet again. No store, atomic or reduction: the bits do not change. Prose 48.36 → 49.46 tok/s, code 59.54 → 61.08 (1 request, two boots each); with section 2's nc loads and TF_ROCE_MAX_KB=512, +2.7% / +3.3%. It too is adapted from a jayleaton/glm53-tensorfold-spark patch.

Notice the two kinds of failure. A PDL race would corrupt things silently (in the figure, the step even gets shorter); cold JIT and divergent tactics hang in the collective. The hang shows up on day one; the corruption only shows up if you measure quality (Measuring the damage).

Update: kernels that preserve the bits, in TensorFold

The GLM recipe has a second version : the same EXL3 checkpoint served by another engine, TensorFold v0.6.0 with 53 patches, one rank per Spark (An exact engine; the full recipe is in Swapping the engine). For this chapter, the change is twofold. First, there are no pluggable backends: “each model family supplies its own kernels”, in Triton and CUDA C++, written for the exact shape of GLM-5.3-Flash (the expert decode path requires D = 4,096 and 1,024 expert columns per rank). Second, these kernels obey a rule that no kernel in the previous sections had to follow.

Why it matters: verifying a draft becomes an equality test

TensorFold samples each token with a key (the request's seed, or a hash of the prompt, plus the position and the token id), so the chosen token is a deterministic function of the logits. Verifying a draft means computing the logits at that position, sampling with the key and comparing. If a row's logits have exactly the bits they would have with the row alone, the drafted reply is the serial decoding, bit for bit, and 4 requests together give what each would give alone. Hence the contract: “Verify kernels keep each row's arithmetic independent of the other rows in the call.” That is a row-independent kernel. In vLLM, speculation preserves the distribution (rejection sampling), not the sequence, and the batch can change bits.

What the rule forbids and what it leaves free

Look again at the stock table of QSA (Qwen's sparse attention) in section 4: the number of split-K partitions comes from the bucket of rows (64 in small, 32 in lt32, 8 in le256). The same query, in a step with 4 rows or with 40, is summed in different slices, and since fp32 addition is not associative, the last bit changes. Dispatch by M (Marlin ↔ BF16 above 512 rows) and FlashInfer's fused finalize, which sums the experts in a variable order, do the same. In vLLM this is acceptable, and Qwen's deterministic mode is opt-in, at a cost of ~4%. TensorFold's verify kernels follow four rules:

  1. Split-K by the weight's shape, never by M. The 4-bit matmuls call split_k(n, k); in the EXL3 experts, gate/up (K = 4,096) uses SK = 4 and down (K = 1,024 per rank), SK = 1. The partials are added in split order.
  2. The tile may vary; each output's chain may not. For the decode Q4 (up to 16 rows), the DEC_TILES table picks per shape (n, k), “measured on GB10”, among configurations of columns, warps and stages, and “every choice gives the same bits”, because each output keeps the same summation order. In the indexer's scorer, on the other hand, swapping 4 warps for 8, or blocks of 64 pools for 32, would change the bits; the number of programs per row (ROW_SCORE_G = 128, grid-stride) is “speed only”.
  3. Atomics only on integers. A float atomicAdd sums in arrival order, like the E3's vector atomicAdd in the vLLM recipe (section 2); the histograms of the top-k selection use integer counters, which give the same result in any order.
  4. Whatever may switch algorithms with the batch size runs per stream. The drafter selector's F.linear (cuBLAS) and torch.topk run, in multi-stream mode, only on each stream's own rows.

In the figure, the row is a dot product of 4,096 terms computed for real in fp32, on synthetic data. Change the number of rows in the window and the kernel's rule, and compare the 32 bits of the result with those of the same row computed alone.

Notice that the “by shape” rule is not more accurate than the others: it is reproducible, and that is what turns into a test. In the v1.3 checks, “drafted == serial 6/6, concurrency 22/22”; in the README, 11 of 11 staggered replies and 11 of 11 sent in a burst came out identical to the same requests served one at a time.

Getting faster without touching a bit

With each row's arithmetic locked, what is left to optimize is where the bytes come from and when they arrive. Almost every comment in the kernel patches ends with “the same bits”:

  • Launch order (TF_GLM_EXL3_NFIRST). In the grouped expert kernel, the grid was (item, column block, …), with the item in blockIdx.x, the fastest-varying dimension. An item is up to 16 rows routed to the same expert (16 × 4,096 × 2 B = 128 KiB in fp16), and each column block of the item rereads those rows. With the item first, neighboring blocks in the launch order belong to different items, and in a chunk of thousands of rows an item's rows leave the L2 before they are reread. Swapping blockIdx.x ↔ blockIdx.y puts an item's blocks side by side: “the same kernel and arithmetic, 2.3-2.5x faster at 4,096 rows”. It applies to windows of 64 rows or more; decode keeps the old order. The number is the grouped kernel's: since patch 0004, the default prompt path runs on the \(Y^\top = W^\top X^\top\) kernels (below), which are born with this grid (column block in x, item in y), and the grouped kernel with NFIRST is left for TF_GLM_EXL3_PROMPT=0.
  • Interleaving bottlenecks (TF_GLM_EXL3_ORDER). In the prompt plan, an expert with a single item reads its weights from DRAM and does little math; an expert with several items shares its weights through L2 and is bound by the tensor core. In plan order, the two kinds arrive in batches, and DRAM and the tensor cores work “in turns”. A 1,024-thread kernel marks each item, numbers the heavy ones with a per-warp prefix sum (__shfl_up_sync) and interleaves the lists: the heavy item of rank r goes to the fractional position \((r+\tfrac12)/n_p\), and the light item of rank l, to \((l+\tfrac12)/n_l\). Only which block runs which item changes.
  • Summing the splits inside the program (TF_GLM_EXL3_SEQ; in the BF16/FP8 matmuls, from SEQ_ROWS = 256 rows up). Instead of writing SK fp32 partials and reducing them in another kernel, one program walks the splits in sequence and accumulates \(((0 + s_0) + s_1) + \dots\) in registers: the reducer's sum, without the partials' round trip through memory. In the BF16 prompt matmuls, 1.3–3.2× with N ≥ 512 and K ≤ 4,096, at 2,048 rows on the GB10; slower on narrow outputs (N from 32 to 288) and long K (6,144, 8,192).
  • Bytes that arrive early. Register prefetch of step k + 1 (TF_GLM_EXL3_PF), the trellis's non-coherent loads (section 2) and the L2 prefetch on a side stream (section 8) change only when the bytes arrive.
Analogy: the study desk

You have 10 books and need to read 8 chapters of each, but the desk only holds 4 open books; the rest go back to the shelf (the DRAM). Reading chapter 1 of every book, then chapter 2 of every book, forces you to fetch each book from the shelf 8 times. Reading all 8 chapters of one book before taking the next, only once. The sentences you read are the same, in the same order within each book: only the trips to the shelf change. That is NFIRST. ORDER is alternating dense books, which demand hours of thinking, with light ones, which only require hauling the stack from the shelf, so that you and the library cart are not left idle waiting for each other.

When the bits change on purpose

Exact does not mean “the bits of the checkpoint in BF16”. Three of the recipe's defaults are declared approximate: the 4-bit dense weights (DENSE=q4, section 6), the FP8 KV and the chunked KDA. And prefill has its own kernels, whose bits differ from decode's. The rule requires each path to be reproducible: a row's bits depend only on its own values, not on the batch or on where the prompt was split. Since draft and serial go through the same prefill, “drafted == serial” still holds.

EXL3 prompt: \(Y^\top = W^\top X^\top\)
The decode kernel decodes each trellis tile to feed just 2 mma (16 rows). In prompts, each expert receives dozens of tokens, and decoding the same tile again every 16 rows is waste. The trick is to compute the transpose: a decoded tile, reordered, is an A fragment of \(W^\top\) in the m16n8k16 format, and the tokens become the B fragments, coming from SMEM via ldmatrix. Each decoded tile feeds the 64 rows of a pass (PM = 64, 8 warps): 8 mma instead of 2. The mainloop has 3 cp.async stages (slices of 32 k values), SMEM rows with +16 B of padding so that ldmatrix lands on distinct banks, and a fused epilogue (128-point Hadamard in registers, svh, clamp, SiLU, the down's suh and another Hadamard). Each output is a single fp32 chain over ascending k, with no split-K and no partials: bits that differ from decode's, identical under any splitting. PM = 128 with 16 warps was “measured slower on real routing”.
Chunked KDA: one block per head
Where the vLLM recipe uses FLA's chunk_kda in Triton (or FlashKDA, opt-in on TP3), kda_chunk.cu gives one 256-thread block to each head, walks 32-row sub-chunks and keeps the 128 × 128 fp32 state in registers (64 floats per thread). There is no multi-stage pipeline in SMEM: the GB10's 99 KiB (101,376 B) per block had already limited the earlier Triton version to a single stage, because the pipelined loops would need up to 154 KiB. Instead, while it computes one sub-chunk, the kernel warms the next one's rows in L2 (prefetch.global.L2) and, at the start of each, copies its own into SMEM with 16 B cp.async. It is compiled with --fmad=false, CUDA's expf and IEEE division, like the serial kernel, and sums in a fixed order: deterministic, “close to the serial kernel, not its bits”. Prefill of 50k 29.3 → 26.4 s; 149k 91.1 → 84.5 s (one boot each; details in Linear attention).

Caveats

The per-patch gains were measured on intermediate builds, with one or two boots each, and do not add up linearly. There is no controlled A/B between the two recipes: TensorFold measured prose at 60.4 tok/s with 1 request and a prefill of ~1,950 tok/s up to 64k (sparkDash, temperature 0, GPU clocks capped at 2,200 MHz), against 36.1 tok/s and 1,411–1,511 tok/s for the vLLM recipe, on different dates, configurations and tools. And kernels written for one shape do not serve another: in v1.3.2, GLM's CUDA engine required exactly two ranks, with no TP3 or TP4; TP3 only arrived in v1.4, with patches 0066–0068 splitting heads, expert columns and vocabulary in whole units per rank.

In the recipes: the kernel map and how a patch swaps a kernel

Each recipe is a choice of kernel per layer and per phase. Pick a recipe and a phase: the “train” runs through the stations of one step. The GLM·TF lane shows the same model on an engine that writes almost every kernel on the hot path.

Five ways to swap a kernel

  1. Engine flag. --moe-backend, --linear-backend, --attention-backend: vLLM already has the options (DeepSeek: flashinfer_b12x).
  2. Env read by an overlay. The overlay decides the path at runtime: EXL3_FAT_GROUPED, GLM53_KDA_BF16_LARGE_M, VLLM_B12X_*, QSA_PROFILE.
  3. Replaced Python file. b12x_moe.py and nvidia/sm120.py (DeepSeek lane B), the qsa.py generated by apply_patch.py, a generated exl3.py (EXL3_OVERLAY_HOST). For Triton kernels, that is enough.
  4. Native extension at build time. For CUDA C++: patch_exl3_fat_kernel.py copies the fat kernels' .cu/.cuh into quant/ in exllamav3_ext and adds the m.def(...) entries to bindings.cpp, without touching the stock kernels; Dockerfile.e3-layer (experimental, MAX_JOBS=2) compiles E3 as an additive module, without --use_fast_math, without rebuilding the image.
  5. Source-exact hotfix. A script checks the target's text (or SHA-256), swaps a snippet and fails closed if it doesn't match, like the PDL gate:
old_pdl = ("            return False\n"
           "        return major >= 9\n")
if text.count(old_pdl) != 1:
    raise RuntimeError("expected one PDL capability gate")
platform.write_text(text.replace(old_pdl,
    "            return False\n"
    "        # PDL lowering races KDA state kernels on SM12x (GB10).\n"
    "        return major in (9, 10)\n"))
In the TensorFold recipe: the sixth way is the diff

The TensorFold lane does not swap kernels through an engine flag or a runtime overlay: the 53 patches are unified diffs against the site-packages of TensorFold v0.6.0, applied in name order with patch -p0 --forward during the image build (if one fails to apply, the build fails), and the image tag carries a hash of the patches themselves. Python, Triton and CUDA C++ all go in the same way; the CUDA compiles JIT on the first start (section 8). Each new kernel brings its own switch (TF_GLM_EXL3_NFIRST, _ORDER, _SEQ, TF_GLM_KDA_CHUNKED…), with the old path at hand as the reference. And the proof changes nature: on the exact paths, instead of “KL ≤ 0.01”, the question is whether the reply's hash changed; on the ones declared lossy, benchmarks such as GSM8K (98.0%) and HumanEval (97.6%) with FP8 KV and q4 dense weights.

Every swapped kernel needs proof. EXL3_SELFCHECK_GPU is 0 at build time (no GPU) and 1 at launch, running the EXL3 overlay tests on the GPU before serving. resolve_exl3_fat_tier and grouped_fat_eligibility degrade explicitly: no shared suh → sorted; E3 requested without the symbols → error at load; ineligible shape (not K4, mul1 codebook, hidden % 256, intermediate % 128 or capability < 9.0) → E2, with the reason. The line exl3 e2 diag … effective_tier=grouped is the boot check. kernel_lab/exl3 ships an oracle for K1–K8 (1 to 8 bits per weight; max error 1.08e-6) and a benchmark.py for sweeping tactics on SM121 (4 tile shapes; never run). TRITON_INTERPRET=1 runs Triton kernels on the CPU, testing the kpool seed without a GPU.

In short: GLM writes its own CUDA C++ kernels where the format is rare and turns off whatever destabilizes the GB10; Qwen sticks with the stock kernels plus surgical Triton patches; DeepSeek bets on b12x (CuTeDSL) and its own sparse-MLA, with heavy JIT; GLM's TensorFold lane writes its own kernels for every layer and forbids the batch from changing a bit of any row. All of them are launched hundreds of times per step.
