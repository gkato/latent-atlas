Before the first kernel, every recipe answers a mundane and treacherous question: are the bytes on disk exactly the bytes that were measured? A frontier checkpoint arrives as 11 to 206 files, from ~98.6 GiB to ~164 GiB, plus half a dozen JSONs that tell the engine how to interpret each byte. A corrupted shard doesn't bring vLLM down until ~33% into the load; a layer name that doesn't match makes the MTP come up unquantized and die ~7 minutes later; an invisible newline in a 40-character file blocks the offline boot. Let's take a checkpoint apart like a watch: the safetensors format byte by byte, the index that stitches the shards together, the loader that turns names into parameters sliced per GPU, the quantization_config that gives the bytes their meaning, and the discipline of cache, revisions and hashes that makes a served model reproducible.

Anatomy of a model repository

A model on the Hugging Face Hub is a git repository. JSONs and code live in regular git; the giant weights live in Git LFS, which stores in the repository only a pointer holding the content's SHA-256. “The checkpoint” is a commit: a fixed set of files that, together, describe the model.

Analogy: the assembly kit

The config.json is the blueprint; the .safetensors files are the boxes of parts, each labeled with its contents; the model.safetensors.index.json is the packing list (which part is in which box); the quantization_config is the fitting guide, without which a compressed part looks like junk; tokenizer and chat template are the user manual. One box missing, or a packing list that lies, and the assembly jams halfway through.

In the figure, each file of a real repository lights up the vLLM component that consumes it. The three repositories share the same skeleton, with quirks: a legacy quantization sidecar in Qwen, a Python encoder instead of Jinja in DeepSeek, a “text-only” template that the GLM recipe replaces.

Note that config.json has several readers: architectures picks the class in the model registry (Inside vLLM), the hyperparameters size every tensor, and quantization_config picks the quantization method. generation_config.json sets the default sampling when the client sends nothing (Qwen: temperature 1.0, top_p 0.95, top_k 20); DeepSeek ignores it with --generation-config vllm. And the chat template may not be usable: GLM's is text-only, so the recipe forces its own; DeepSeek ships a Python encoder (encoding/encoding_dsv4.py) instead of Jinja: the container entrypoint copies that file into vLLM, and --tokenizer-mode deepseek_v4 calls it. It is not loaded as remote code. --trust-remote-code is something else, a requirement of the V4 architecture (table below).

Pitfall: the config can “lie” without being wrong

The GLM checkpoint uses SGLang names (num_experts_per_tok, hc_mult…). Without aliases, vLLM couldn't find them and fell back to its own default: it routed 7 experts per token instead of the 8 it was trained with, with no error at all. The vision tower declares rms_norm_eps = 1e-5, but was trained with 1e-6; with the declared value, the image descriptions came out repetitive. Read the config together with the code that consumes it.

Safetensors, shards and the index

PyTorch's old weight format is pickle, which serializes Python objects: loading can execute code embedded in the file. For weights that is both a risk and a waste, because a tensor is just numbers with a type and a shape. safetensors is exactly that: 8 bytes (a little-endian u64 with the size \(N\) of the header), \(N\) bytes of JSON (for each tensor, dtype, shape and data_offsets, plus an optional __metadata__; Qwen's writer pads it with spaces up to a multiple of 8) and the blob with the raw bytes, in row-major order.

\[ \text{bytes}(t) \;=\; e_t - b_t \;=\; \beta(\text{dtype}_t)\,\prod_{k} s_{t,k} \qquad\qquad \text{file range} = [\,8 + N + b_t,\;\; 8 + N + e_t\,) \]
  • \(b_t, e_t\): data_offsets of tensor \(t\), counted from the start of the blob
  • \(\beta\): bytes per element (BF16 = 2, F32 = 4, F8_E4M3 = U8 = 1, I16 = 2); \(s_{t,k}\): the dimensions (scalar: shape [], product 1)

A real example: Qwen's model.language_model.layers.3.self_attn.q_proj.weight is BF16 [12288, 2560] (24 heads × 256 × 2; the extra half is the output gate), so \(12288 \times 2560 \times 2 = 62{,}914{,}560\) bytes, exactly 60 MiB, and element \((i, j)\) sits at byte \(8 + N + b + 2(i \cdot 2560 + j)\). Step through the figure.

Note step 4: there is no “FP4” dtype. An NVFP4 expert is U8 [640, 1280] with two values per byte (logical matrix 640 × 2560); GLM's EXL3 trellises are I16; DeepSeek's E8M0 scales arrive as float8_e8m0fnu. The file says “how many bytes, with what shape”; the meaning comes from quantization_config.

mmap, zero-copy and partial reads

Because the header locates each tensor, the loader can use mmap: the OS maps the file into virtual memory and reads only the pages that get touched, and the tensor becomes a view over them (zero-copy). Over the network, HTTP range reads fetch 8 bytes, then the header, then only the desired tensor. Qwen uses lazy loading (table below); build_ple_packed_table.py memmaps the 128 shards of the NVFP4 PLE and writes a [total_rows, 90] matrix (80 B of codes + 10 B of scales per row) in blocks of \(2^{19}\) rows; GLM's dense_overlay.py reads remote headers without downloading weights. The physical side (page cache in unified memory, 64 KiB pages, O_DIRECT) is left for Unified memory.

Sharding and the weight_map packing list

A single 160 GB file would make every retry, every hash and every rsync expensive, because the unit of failure would be the entire model. HTTP range requests can resume a giant file, but verifying, syncing and loading would still happen as one block. That's why the checkpoint is split into shards, which give you the granularity to download, verify and load piece by piece, and a JSON serves as the packing list: {"metadata": {"total_size": …}, "weight_map": {"tensor": "file", …}}. In Qwen's nvidia checkpoint, the weight_map lists 299,545 tensors across 11 files (the last one, model-fp8-mtp-ple.safetensors, is 53.7 GB), total_size 132,639,846,394 B. The index defines what a complete snapshot is: every file named in the values of the weight_map exists.

From name to parameter: the vLLM loader

Checkpoint names and shapes almost never match vLLM's parameters. The engine first builds the model's skeleton: for each layer, the quantization method calls create_weights, which registers empty parameters in the checkpoint's format, each with its own weight_loader. Then load_weights walks the (name, tensor) pairs from the shards and, for each one, renames, stacks and slices:

  1. Rename. A WeightsMapper translates names: in DeepSeek, layers. → model.layers., head.weight → lm_head.weight, .attn.compressor. → .attn.mla_attn.compressor., .ffn.gate.bias → e_score_correction_bias (the auxiliary-loss-free bias from Mixture-of-Experts).
  2. Stack. Matrices with the same input become one bigger GEMM: gate_proj + up_proj → gate_up_proj. A table of stacked params gives the destination and the shard_id (the slot).
  3. Slice. The weight_loader cuts out the part that belongs to the rank in tensor parallel: rows in a column-parallel layer, columns in a row-parallel one. With expert parallel, instead of cutting, it chooses which whole experts stay on the rank.
TP in 1 minute (and the naming paradox)

PyTorch stores each linear as \(W \in \mathbb{R}^{\text{out} \times \text{in}}\): each row is an output neuron, and the layer computes \(Y = XW^\top\). Megatron, which named the cuts, writes \(Y = XA\) with \(A = W^\top\). That's why column-parallel splits the columns of \(A\), which are the rows of \(W\): each rank computes a slice of the outputs, with no communication. Row-parallel splits the rows of \(A\), that is, the columns of \(W\) (the inputs): each rank multiplies its slice of the input, produces a partial sum, and an all-reduce adds up the partials. The classic FFN pair is gate/up column-parallel followed by down row-parallel, with a single all-reduce at the end.

\[ W = \begin{bmatrix} W^{(0)} \\ W^{(1)} \end{bmatrix} \;\Rightarrow\; Y = \big[\, X W^{(0)\top} \;\big|\; X W^{(1)\top} \,\big] \] \[ W = \big[\, W^{(0)} \;\big|\; W^{(1)} \,\big] \;\Rightarrow\; Y = X^{(0)} W^{(0)\top} + X^{(1)} W^{(1)\top} \]
  • 1st line, column-parallel: cuts the rows of \(W\); each rank produces a piece of \(Y\), with no communication
  • 2nd line, row-parallel: cuts the columns of \(W\); each rank produces a partial sum, and the all-reduce adds them up
  • \(W^{(r)}\): rank \(r\)'s slice; \(X^{(r)}\): the matching slice of the input (already distributed by the previous layer)

Expert parallel (EP) is a different idea: no expert is cut; each rank holds whole experts, and an expert_map translates the global index into the local one (E4 becomes expert 0 of rank 1). Qwen uses EP (--enable-expert-parallel, 256 of the 512 experts per GPU) and so does GLM TP3 (96 of 288); DeepSeek runs TP=2 without EP. Details and communication costs in Splitting the model.

In a stacked column-parallel layer, each rank doesn't hold “the top half” of the fused matrix, but its own slice of each slot:

\[ W^{(r)}_{\text{gate\_up}} \;=\; \begin{bmatrix} W_{\text{gate}}\big[\, r\tfrac{I}{P} : (r+1)\tfrac{I}{P},\; : \,\big] \\[4pt] W_{\text{up}}\big[\, r\tfrac{I}{P} : (r+1)\tfrac{I}{P},\; : \,\big] \end{bmatrix} \]
  • \(r\): rank; \(P\): TP size; \(I\): the FFN's intermediate dimension
  • this way \(\text{SiLU}(x W_\text{gate}^{(r)\top}) \odot x W_\text{up}^{(r)\top}\) multiplies matching rows with no communication

Example (computed from GLM's config, hidden 4096, moe_intermediate_size 2048): the shared expert fuses gate_proj [2048, 4096] and up_proj [2048, 4096] into gate_up_proj [4096, 4096]; in TP2 each rank holds [2048, 4096], 1024 rows of each. Cutting off the top half would leave rank 0 with only gate. GLM also fuses q_a_proj + kv_a_proj_with_mqa (fused_qkv_a_proj), wk + weights_proj and six linear-attention projections into in_proj_qkvbfg_a (6 launches → 1), replicating the small f_a/g_a; DeepSeek fuses w1/w3, attn.wq_a/attn.wkv and compressor.wkv/wgate.

The routed experts follow the same logic. In pure TP (DeepSeek), the FusedMoE weight_loader slices all experts across the ranks: w1/w3 along the intermediate dimension (column-parallel), w2 along the input (row-parallel). With moe_intermediate_size 2048, each rank holds all 256 experts at a width of 1024. With EP, the same loader first checks the expert_map: if the global expert doesn't belong to the rank, the tensor is skipped; if it does, it goes in whole at the local index. Step 5 of the figure compares the two.

Slicing quantized weights: the weight and its scales travel together

In BF16, slicing is a narrow() along one dimension. A quantized weight is made of two or more tensors (codes + scales, or trellis + signs), and each one must be cut at the same logical boundary as the weight, or replicated when it doesn't depend on the cut dimension. Three rules decide which TPs are viable (in the table, column-parallel cuts the outputs and row-parallel, the inputs):

  1. A per-block scale can only be cut at a block boundary. The local width after the split must be a multiple of the block. Otherwise, one scale would serve both ranks and would have to be split in half, which is not a thing.
  2. Packed formats cut in bytes. With 2 FP4 values per byte, the boundary must be even in logical values, and a multiple of 16 so as not to split an NVFP4 scale block.
  3. Whatever describes the uncut dimension is replicated. Global scales (weight_scale_2, input_scale), markers and the Hadamard signs on the side that wasn't split go whole to both ranks.

These rules explain a decision in the Qwen recipe. FP8-dense chose a per-channel scale rather than blocks of 128 for three reasons: it needs no calibration; the rank-320 projections of the hyper-connections and the sliced shared expert (320 rows per rank) aren't multiples of 128 (rule 1); and vLLM's ParallelLMHead sliced block scales incorrectly, cutting the scale tensor by the same vocabulary rows as the weight, when it has 128 times fewer rows. A per-channel scale has one row per weight row and is cut the same way. The EXL3 trellis cut lives in GLM's overlay (shard_exl3_col/shard_exl3_row), which rejects any dimension that doesn't divide by the TP; the TP3-with-EP bug was precisely this loader still trying to slice each expert by 3 (patch_exl3_ep_shard.py).

Pitfall: a substring is not a segment

DeepSeek's stacked mapping tests "w1" in name, and the DSpark drafter has a markov_w1, which would mistakenly land in slot 0 of gate_up_proj. The Stage-C overlay brings map_dspark_stacked_param_name, which compares name segments, ignores .experts. and is covered by test_dspark_stacked_mapping.py.

Embedded drafters live under their own prefix. The DeepSeek target skips everything that starts with mtp.; the drafter loads only mtp.<stage>.*, renaming it to model.layers.<num_hidden_layers + stage>.* (virtual layers 43–45), slices attn_sink by the rank's heads and maps .scale to .weight_scale (FP4 experts) or .weight_scale_inv (FP8), depending on expert_dtype.

Why an E8M0 scale can't be “converted”

An E8M0 scale is just an exponent: byte \(e\) is worth \(2^{e-127}\). The MoE parameter is uint8; a copy_() would perform a numeric conversion, and byte 120 (\(2^{-7} = 0.0078125\)) would become the integer 0. The loader does view(torch.uint8): it reinterprets the bits and stores 120.

Finally, process_weights_after_loading repacks everything into the kernel's layout (for example, that of Marlin, a GEMM kernel that multiplies 4- or 8-bit weights by dequantizing them in registers and requires the weights reordered into tiles; see Kernels), precomputes tables and sometimes dequantizes (GLM turns the MLA projections of an FP8 checkpoint into BF16).

quantization_config: the bytes' instruction manual

A U8 [640, 1280] tensor doesn't say whether it's packed FP4 or INT8. The quantization_config does. Its quant_method picks the QuantizationConfig class that owns the checkpoint (exl3 in GLM, modelopt in Qwen, fp8 in DeepSeek), which answers get_quant_method(layer, prefix) layer by layer: which method creates, loads and runs that weight.

DeepSeek is the leanest case, and it shows that quantization_config doesn't always tell the whole story. It declares quant_method: fp8, fmt: e4m3, weight_block_size: [128, 128], scale_fmt: ue8m0 (scales that are powers of 2) and activation_scheme: dynamic, which applies to the dense linears. The routed experts are something else, and the hint comes from a field outside it: expert_dtype: fp4, that is, MXFP4 (e2m1 with one E8M0 scale per 32 values). That field is what makes the mapper send experts.*.w[123].scale to weight_scale (the name that Mxfp4MoEMethod registers) and every other .scale to weight_scale_inv (the FP8 block scales).

Patching the config without touching the cache

Editing the cached config.json is tempting and wrong: it's a hash-addressed blob (next section), shared across revisions and copied to the worker; editing it breaks verification and makes it impossible to say what was served. That leaves two clean tools.

1. --hf-overrides: a JSON merged into the in-memory config (ModelConfig._apply_dict_overrides), which only descends into keys that are sub-configs. In a multimodal model, the parent wraps a text_config (the LLM) and a vision_config; in qwen4_exp the parent also exposes rope_parameters as a plain dictionary, so {"rope_parameters": …} at the root landed on the parent and never reached the text_config: every old “1M” run served unscaled RoPE. The fix is a single nested payload:

--hf-overrides '{"text_config": {"ple_embedding_dtype": "float8_e4m3fn",
                                 "rope_parameters": {"rope_type": "yarn", "factor": 4.0,
                                                     "original_max_position_embeddings": 262144}}}'
# rope_parameters only with YARN_ENABLE=true (current default: false, MAX_MODEL_LEN 262144)

The error is silent: the server comes up and answers; only a long-context test, or reading the effective value, reveals the problem (the recipe README still shows the buggy form in an old block). The same mechanism declares 66 heads in GLM's TP3 (TP=3 and TP=4) and turns on the YaRN described in Position.

2. Detect what's missing and mount corrected configs on top. Qwen's patched ple_layer.py chooses the PLE method from text_config.ple_embedding_dtype, which the nvidia checkpoint doesn't declare. detect_ple_dtype.py looks for the group whose targets contains ple_embedding.ngram_embedding and translates num_bits 8 → float8_e4m3fn, 4 → nvfp4; the result goes into the nested override. As for the MTP: vLLM builds it at an absolute index, continuing the stack (num_hidden_layers = 48 → mtp.layers.48), but the nvidia checkpoint writes metadata only for mtp.layers.0.*. patch_checkpoint_config.py writes config_patched.json and hf_quant_config_patched.json, which are bind-mounted over the snapshot inside the container, and has a preflight mode that fails in seconds.

Why the 128 block isn't guessed

FP8_BLOCK_SCALES only works because patch_modelopt_fp8_block_moe.py teaches the dispatcher to build an Fp8MoEMethod with weight_block_size = [g, g], reading g from group_size. It refuses to guess: a wrong block silently applies misaligned scales, and the symptom would be a near-random draft acceptance rate. With the right block: MTP=3 at 52.1 tok/s, acceptance rate 72.8% (89/74.5/60% by position).

The Hugging Face cache and offline mode

huggingface_hub stores downloads in a layout designed to deduplicate and pin revisions:

$HF_HOME/hub/models--nvidia--Qwen3.8-Flash-Next-NVFP4/
├── blobs/            actual content; name = hash (SHA-256 for LFS, git SHA-1 for small files)
├── refs/main         text: the commit "main" pointed to
└── snapshots/
    └── fc694b54…/    one directory per commit, with relative symlinks
        ├── config.json -> ../../blobs/…
        └── model-00001-of-00010.safetensors -> ../../blobs/…

Each blob stores the content once; each snapshot is a tree of symlinks that assembles the view of one commit; refs/main is a text file with the hash. A commit that changes only config.json gets a single new blob; the multi-GB shards stay in the same blobs (that's the figure's illustrative scenario, inspired by fc694b54, which renamed a label in the config). The folder name, models--<org>--<repo>, is what GLM exposes as MODEL_CACHE_NAME.

All three recipes serve with HF_HUB_OFFLINE=1 and TRANSFORMERS_OFFLINE=1: inside the container, nothing touches the network. That gives you reproducibility (what was verified is what runs), avoids surprises (in DeepSeek, a revision missing from the cache would turn into a silent ~157 GiB download at boot: ≈169 GB, although the warning in validate-dspark-config.sh still says ~155 GB, a figure from the 0731 lane) and lets you mount the cache read-only on the worker. Downloads happen beforehand, in scripts that force online mode.

In offline mode, asking for main means reading refs/main and opening snapshots/<hash>/. The trap: the huggingface_hub 1.28 in Qwen's day-0 image reads the file without .strip(). Writing echo $SHA > refs/main leaves a \n behind; the library looks for snapshots/<sha>\n and vLLM dies with a “repo not found” that never mentions the newline (issue #36). The recipe compares the actual bytes ($(cat …) would hide the newline) and rewrites with printf only if they differ. DeepSeek's prepare writes the ref with a newline, but serves with an explicit --revision on its own image: the behavior depends on the library version, so write without a newline and test the offline boot.

Hard-link the blob, not the symlink

A derivative that reuses shards doesn't copy them. But the snapshot's files are relative symlinks: a hard-link of the symlink, in another repository, would point to a path that doesn't exist there. The FP8-dense converter solves this with os.path.realpath and makes the hard-link to the blob: same inode, zero bytes (an absolute symlink is plan B). GLM, during rsync, repairs a dangling drafter link by copying with rsync -L.

In the recipe: when the blob itself is a link

The TensorFold version of the GLM recipe copies to the worker only what the revision uses: it reads where the symlinks in snapshots/<rev>/ point, transfers those blobs, and then recreates the snapshot links and refs/main, the same layout huggingface_hub keeps. Issue #15 found the hole in that plan: with the Xet backend, a blob in models--…/blobs/ can itself be a link into a blobs/ at the cache root, outside the copied folder, and those files never reached the worker. The cure is the one the vLLM lane uses for the drafter, following the links: rsync -a -L --partial copies the content each link points to and resumes if the copy drops. Two details close the offline mode. Downloading by commit hash writes no refs/main, so the script writes the pin there with printf %s (no newline), only when there is no other. And the server does not even consult refs/main: start.sh hands tensorfold serve the snapshot path, after checking that its config.json exists on both Sparks. The containers run with HF_HUB_OFFLINE=1 and no token goes into them.

Pinned revisions, mirrors and gated repositories

In git, main is a moving pointer; a commit hash (40 hex) is immutable. Pinning the revision means serving by hash. The recipes treat this as a rule: in DeepSeek, issue #19 introduced the pin (prepare and serve with --revision) so that a change on main, in the weights or in the encoder, never goes unnoticed; in GLM, the rationale for pinning the drafter is that “a mutable Hub main has already swapped the weights.” With --trust-remote-code, pinning is also a security measure, since following main would accept any new code (our interpretation, following from the same mechanism). A byte-identical mirror in a repository you own even protects you against the upstream disappearing.

The three recipes chose different strategies, and they're worth comparing. pins a commit and passes it to prepare and serve (--revision). goes further: a byte-identical mirror, pins for both target and drafter, and presets that lock every pin at once (in snapshot 94ae731; since 2026-10-04, commit 98cf18f, the default is the lab's own pack, Mia-AiLab/GLM-5.3-Flash-EXL3-4bpw-TensorFold, and the fallback points at the same repository). is the exception: it serves the refs/main snapshot, with no fixed hash, and compensates with two safety nets: completeness (resolve_snapshot.py) and the hash manifest saved with repository and revision (verify-weights.py --save-manifest). The cost of following main showed up for real: on 2026-09-05, nvidia's commit fc694b54 renamed the MTP experts' label from FP8_BLOCK_SCALES to FP8_PB_WO in config.json (but not in the sidecar), and the recipe had to learn the new label and patch both files. That's exactly the kind of change a pin turns from a surprise into a decision.

In DeepSeek, DSPARK_REVISION unset uses the pin, and set to empty follows the tip of main (the shell pattern ${VAR-default} × ${VAR:-default}): a conscious choice between reproducibility and freshness. The revision also explains the runtime: Vision-Exp has num_nextn_predict_layers = 3, which forces k = 6 in the draft (DFlash2 and DSpark); 0731 had 1 and used k = 5, with acceptance rates of 0.93/0.75/0.66/0.58/0.47 by position, and it was on 0731 that the ablation direction was captured. Presets lock all the pins of an option: GLM53_MODEL_PRESET=abliterated points to bullerwins/GLM-5.3-Flash-exl3-4bpw-ablit@14858211… (120 shards, 175,642,157,752 bytes) and forces ABLIT=0, because reapplying the edit at runtime “would produce a different model”; any divergence is fail-closed. Gated repositories require accepting terms and an HF_TOKEN (HTTP 403 = terms not accepted).

Integrity: size is not proof

A checkpoint can be wrong in four ways: a shard is missing, is truncated, has flipped bytes at a similar size, or a JSON was rewritten at the same size. Each detector only sees some of them. The case that motivated hashing in Qwen (issue #30): a shard corrupted mid-download, its size off by a few hundred MB in a multi-GB file, passed the old check, and the engine didn't die until ~33% into the load, with safe_open complaining about incomplete metadata, file not fully covered.

The definitive detector is the content hash. SHA-256 reduces any file to 256 bits with an avalanche effect: flipping one bit changes, on average, half of the output. The Hub publishes the expected hashes at /api/models/{repo}/tree/{rev}?recursive=true: the lfs.oid (SHA-256, for LFS files) and the oid (the git blob SHA-1, for small files):

\[ \text{oid}_{\text{git}}(c) = \mathrm{SHA1}\big(\,\texttt{blob}\;\Vert\;\text{space}\;\Vert\;|c|_{10}\;\Vert\;\text{NUL}\;\Vert\;c\,\big) \qquad\qquad \text{oid}_{\text{LFS}}(c) = \mathrm{SHA256}(c) \]
  • \(c\): the file's content; \(|c|_{10}\): its size in bytes, in decimal; \(\Vert\): concatenation; NUL: the zero byte

Qwen's verify-weights.py uses only the standard library (it runs on any node), streams in 1 MiB blocks with 8 threads and distinguishes three outcomes: 0 (matches), 1 (the weights have a problem) and 2 (the tool failed), because “corrupted weights” and “try again” call for different actions. Measured time: ~1 min for 135 GB at 2.4 GiB/s.

In the recipe: “the marker is a claim, not proof”

To avoid scanning 164 GiB at every boot, GLM writes .glm53-exl3-synced with the revision on the worker. The marker is only written after the probe passes (every file in the index must dereference to a regular file of exactly the head's size, via find -L … -printf '%s %p'), is only honored if the probe passes again, and is deleted before any rsync that changes files: an interrupted sync never becomes “complete.”

In the recipe: the engine reads first, the list checks afterwards

The TensorFold version verifies in two layers. Before copying anything, it runs tensorfold info on the head's snapshot, in a container of the image itself and offline: the worker only receives a checkpoint the engine can read (the recipe filters the EXL3 support is experimental warning out of the report, because it serves EXL3 on purpose). Then it compares head and worker through a path size list of every file in the snapshot, with links followed (find -L . -type f -printf '%P %s'): an identical list skips the copy; a list that still differs after the copy aborts the preparation. By the figure above, that list catches a missing file and a truncated one, but not bytes swapped at the same size, and the drafter in the previous section showed that “same size, other content” really happens. What covers that hole is only the transit: rsync checks every file it sends with a whole-file checksum, but a file already on the worker at the same size is skipped without being reread, by the list or by rsync's own quick check of size and modification time (our interpretation; the recipe does not compare SHA-256 against the Hub, as Qwen's verify-weights.py does).

The marker changes nature too. It is a line with model@revision, drafter@revision, the image on both Sparks, the patches hash, the worker and the weights mode, and start.sh redoes the preparation whenever the current line differs from the stored one. Interpretation from the code: it invalidates by configuration, not by content. With the same line, the boot only checks that the image and the snapshot's config.json exist on both sides, without repeating the size probe the vLLM lane runs before honoring its marker.

Derived checkpoints and the trip to the worker

Sometimes the right checkpoint for your hardware doesn't exist, and you build it. A derived checkpoint is born locally, deterministically, from pinned inputs, and is verified before serving. Golden rules: links instead of copies for whatever doesn't change, atomic writes, metadata that explains the origin, and a test of the quantization resolution before boot.

Qwen: the FP8-dense hybrid

At batch-1 decode, the BF16 dense layers (GDN, attention, hyper-connections, shared experts, lm_head) account for ~6.9 of the ~9.2 GiB read per step. The converter turns 591 linears into FP8 E4M3 with one scale per output channel, without calibration (the activation is quantized dynamically per token):

\[ s_i = \frac{\max_j |W_{ij}|}{448}\;(\geq 10^{-12}), \qquad q_{ij} = \mathrm{E4M3}\!\left(\mathrm{clamp}\!\left(\tfrac{W_{ij}}{s_i},\,-448,\,448\right)\right) \]
  • \(i\): row (output channel); \(448\): the largest finite E4M3 value; writes weight F8_E4M3 + weight_scale F32 [out]

Per channel rather than in blocks of 128 because of the cutting rules we saw in the loader (rank 320 of the hyper-connections, a shared expert with 320 rows per rank, block scales in ParallelLMHead). The converter is a safetensors lesson in itself: a custom writer writes the header first (the sizes are known) and seeks to each piece; it processes 16 MiB blocks of rows; it writes to .tmp, calls fsync and renames atomically. Result: 202 hard-linked shards, 4 rewritten (11.8 GB), ~2 min on CPU. The checks come before any GPU: relative RMSE 0.0240/0.0262/0.0268 (min/median/max), cosine ≥ 0.9996, alarm above 0.06 (Measuring the damage); 30/30 prefixes resolved to the expected method; and the expected log line Selected CutlassFP8ScaledMMLinearKernel for ModelOptFp8PcPtLinearMethod. The predicted gain (~5.7 GiB/step, ~85–90 tok/s) is analytical: it has never been measured on a GPU.

GLM: the dense overlay and the 6 bpw drafter

The dense-h3 preset rewrites nothing: dense_overlay.py creates a directory of relative symlinks to the entire TR3 pack (they resolve inside the container and survive rsync -a) and adds one safetensors file with the non-expert linears in EXL3, fetched via range reads from turboderp/GLM-5.3-Flash-exl3 (branch 4.05bpw, commit 2a30229e, ~5.3 GB), with a rewritten index and non_routed_exl3 in the config. It's a transplant: the donor stores q/k/v fused into qkv_proj (sliced by block), gate/up become slots of gate_up_proj, and in_proj_qkvbfg_a keeps slots 3–5 in BF16. The DFlash2 drafter is quantized to 6 bpw (fork exllamav3@63b32f0, no calibration, ~25 min on the GB10, K/V in BF16) and packaged with byte-identical copies of the BF16 tensors and relative prefixes that the runtime shifts to layers 45..49.

Metadata that configuresglm53_profile

The pack's config.json gains a glm53_profile (name=dense-exl3-h3-dflash2-6bpw, draft.model, a 40-hex draft.revision, draft.config_sha256), which binds target and drafter by hash and on its own selects GLM53_DENSE_EXL3=1, GLM53_DENSE_FP8=off, GLM53_DENSE_EXL3_PREFILL_BF16 (below), GLM53_KDA_BF16_LARGE_M=0, ABLIT=0, SPEC_METHOD=dflash, DFLASH_DRAFT_TP=2. Pins: TR3 config SHA-256 4f5341e0…, index 2f64d21c…, overlay 1a1b0793…, drafter local/GLM-5.3-Flash-DFlash2-EXL3-6bpw@27d19286…; a divergent build is refused. Opt-in, TP2 only, no A/B against the default. After 98cf18f, the preset's config and index pins are still TR3's: the base has to be that pack, and the preset refuses the new default checkpoint (docs/REFERENCE.md).

The chosen value is GLM53_DENSE_EXL3_PREFILL_BF16=kda_in,shared_down,mla_qkv_a,shared_gate_up,kda_o,mla_q_b: these six H3 groups keep a reconstructed BF16 copy of the EXL3 weight (Hadamards already applied) and, when the batch has more than 144 rows (prefill), run a plain BF16 GEMM instead of decoding the trellis on every call. It costs an extra 2 bytes per weight per rank.

In the recipe: derive at load time, not on disk

The TensorFold version tackles the same problem (the ~9.7 GiB per Spark of BF16 weights outside the routed experts, reread at every decode step) without creating any checkpoint. The GLM family's loader asks for each tensor by its checkpoint name and, with DENSE=q4 (the default), performs load-time quantization: affine groups of 64 values in 4 bits, with the range chosen among 16 clippings (from 1.0 down to 0.55 of the min/max) by the least squared error, and scale and bias in BF16, ~4.5 effective bits per weight (the research's calculation). The head goes to FP8, kv_b stays in BF16, and matrices whose input is not a multiple of 64 fall back to FP8. DENSE=fp8 uses one scale per row and 128-column block; DENSE=bf16 is, in the words of config.sh, the checkpoint as it is. Measured with DFlash2, one boot each, q4 against fp8: prose 38.9 → 44.4 tok/s, code 44.2 → 48.7, prefill ~1,090 → ~1,260 tok/s, with GSM8K 98.0% and HumanEval 95.1% on both (bf16: 97.2 / 96.3). This is an A/B from config.sh, taken during development: it does not compare with the recipe's headline numbers, measured with sparkDash and the GPU clocks capped at 2,200 MHz.

The trade-off against Qwen's FP8-dense is clear-cut. At load time there is no new file to build, pin, hash and copy: the worker receives the published checkpoint, and the transformation is versioned by the patch code (the image hash) plus one knob. In exchange, the served bytes do not exist on disk and no SHA-256 names them; the conversion is repeated at every boot and, without an equivalent of Qwen's offline verifier, quality only shows up by measuring the server (interpretation). Issue #18 is the example: with q4, short French coding prompts lose the end of turn and run until max_tokens in 12 of 48 replies (1 of 48 with bf16 or fp8), something GSM8K and HumanEval, in English, did not show.

The trip to the worker: rsync or NFS

rsync gives the worker a local copy (~126 GiB for Qwen, ~164 GiB for GLM): twice the disk, but decoupled nodes and a faster cold start. With NFS, the head exports the cache read-only and the worker mounts it: zero extra disk and easy checkpoint swaps, but the head has to stay up and every cold start rereads everything over the cable. “The cable” is the direct 200 Gb/s link of the ConnectX-7 (CX7), the network card that connects the two Sparks through the QSFP port, the same one NCCL goes through. The server is a privileged Alpine container running the kernel's nfsd, NFSv4 only; the worker mounts with nfsvers=4.2,ro,nconnect=8,rsize=wsize=1048576,hard,timeo=600 (“nconnect=8 is what makes the cold load actually use the cable”). The scripts refuse 10.0.0.* and 127.*: over the management network, 164 GiB becomes “an overnight job” (networking in NCCL and RDMA).

Weights on the workerWORKER_WEIGHTS=copy · nfs

With copy (the default), the worker gets its own copy, ~166 GiB, over the link between the Sparks: prepare.sh first checks the worker's free disk (the snapshot size plus 5 GB) and copies only the revision's blobs with rsync -a -L --partial. With nfs, nothing is copied: the head exports the cache read-only to the worker's CX7 address (once, with root on the head), and prepare.sh creates on the worker, without sudo, an NFS-type Docker volume with the same client options seen above and checks that the worker sees every file of both snapshots with the head's size. The recipe reports loading as fast as from the local disk (both ranks up in ~2.2 min); the price is that of any NFS, the head has to stay up. This lane's memory budget is in Unified memory; the engine, in An exact engine.

In the recipes: the weights checklist

The three recipes ride the same subway line, each with its own extra stations, and the TensorFold version of GLM (, built step by step in Swapping the engine) shows that changing the engine does not change the line: the same checkpoint goes through the same seven stations, with different answers at each one. Pick a recipe and follow the train: each station shows the real value in use.

The pattern repeats: everything that can fail late is checked early (completeness before rsync, hash before loading, the MTP preflight before 7 minutes of boot, headers before stopping a healthy pair), and nothing in the cache is edited (fixes go through overrides or configs mounted on top; derivatives live in their own local repositories; whatever is served always has a hash that names it).

  1. Read the repository the way the engine reads it: config.json with its sub-configs and quantization_config, sidecars, safetensors headers; note down the format of each part and the names of the scales.
  2. Pin everything by hash (target, drafter, auxiliaries), consider a mirror, and download outside the serving path, with generous timeouts. If you choose to follow main, as Qwen does, require completeness and save a manifest with repository and revision, so that a change like fc694b54 is detected, not inherited.
  3. Check that the TP you want cuts each format at a block boundary (16, 32, 128, 16-wide tiles); if it doesn't, use EP, replicate, or change the scale granularity.
  4. Serve offline and write refs with printf.
  5. Verify in layers: count, weight_map, dereferenced size, hash against the manifest.
  6. Find out what the loader doesn't know (absolute indices, aliases, undeclared dtypes, new labels) and fix it without touching the cache, with a preflight that fails in seconds.
  7. Derive with links and verify offline; choose rsync or NFS according to how you operate.
