To generate a single token with 850 thousand tokens of context, every attention layer has to consult what it stored about all of those 850 thousand tokens. If the 45 layers of GLM-5.3-Flash were classic multi-head attention in BF16, that would come to about 2.95 MB per token of context, some 2.5 TB for the whole conversation, almost ten times the combined memory of the two DGX Sparks. The GLM recipe stores about 7,579 bytes per token (our own math from the layout, 11 × 656 + 11 × 33 B, consistent with the README's ~7.1 GiB per million tokens); the version, which serves the same weights on the TensorFold engine instead of vLLM, stores about 6,204 (also our own math), and you will see where the difference comes from. Of that nearly 400× gap, this chapter explains the largest factor: about 57× comes from MLA (65,536 B → 1,152 B per layer, both in BF16). The rest comes from two places: the FP8 of the packed layout, about 1.7× (quantized KV, ch. 23), and the fact that only 11 of the 45 layers store KV, about 4×, because the 34 KDA layers have a fixed state (Linear attention, ch. 14). The MLA factor has three rungs: sharing keys across heads (MQA and GQA), storing a latent summary and rebuilding the heads only when it is time to compute (MLA), and the extreme case of DeepSeek-V4, in which the key is the value itself. Along the way you will understand why the GLM recipe fills 64 dimensions with zeros, why DeepSeek “un-rotates” the attention output, why the TP=3 patch creates a ninth group of ghost heads and why a certain weight is never quantized. And you will see what changes when the engine writes kernels for the model, instead of dressing the model up for the kernel.

The library that grows with every token

Recall what happens during decode (covered in Prefill, decode and the KV cache). In each layer, the new token produces one query per head and compares that query against the keys (K) of all previous tokens. The scores become weights through the softmax, and the weights mix the values (V) of those tokens. The past K and V never change, so the engine keeps them in the KV cache instead of recomputing them. The cost of this archive, per token of context, is a simple calculation:

\[ \text{bytes per token} \;=\; L \times n_{kv} \times (d_k + d_v) \times b \;\;\xrightarrow{\;d_k \,=\, d_v \,=\, d_h\;}\;\; L \times 2 \times n_{kv} \times d_h \times b \]
  • \(L\): layers that store KV
  • \(n_{kv}\): K/V heads per layer
  • \(d_k\), \(d_v\): key and value dimensions of each head
  • \(2\,d_h\): the common case in which key and value have the same size \(d_h\)
  • \(b\): bytes per number (2 in BF16, 1 in FP8)

The short form, with the factor of 2, only holds when \(d_k = d_v\). That is not always the case. In MiMo-V2.6-Flash, the model from the recipe-from-scratch tutorial, the key has head_dim = 192 and the value v_head_dim = 128. An MHA with DeepSeek-V3's dimensions would store \(128 \times (192 + 128) = 40{,}960\) numbers per token and layer, a number that \(2 \times n_{kv} \times d_h\) cannot produce. Anyone building a new recipe should start from the general form.

This number bills you twice. First in capacity: the memory reserved for the cache divided by the bytes per token tells you how many tokens fit, summed over all concurrent conversations. Then in bandwidth: in dense attention, every decode step rereads the sequence's entire KV. The model weights are read once per step and serve the whole batch, but the KV belongs to each individual conversation and grows with it. At long context, it is the KV that dominates the bytes read per generated token.

Analogy: the index-card library

Imagine that each attention head is a librarian with their own card file. For every word read, each librarian writes two cards (one for the “subject”, the key, and one for the “content”, the value) and files them away. To answer a new question, each of them flips through their entire card file. With 64 librarians and a book of a million words, the building cannot hold that much paper. This chapter offers three ways out: librarians who share card files (MQA/GQA), a single file of summaries from which each librarian works out their own cards (MLA), and summaries that already serve as subject and content at the same time (DeepSeek-V4).

In the figure below, each row is what one layer stores for one token. At every step, the beam sweeps all the rows (that is the decode read) and a new row is filed at the end. Switch the scheme and watch the row width shrink.

Notice two things. The row width multiplies everything: capacity, bytes read per step and, therefore, decode speed at long context. And MLA is not the narrowest row in the figure (MQA is). The beauty of it is that it gets close to MQA in bytes without giving up heads with their own keys and values, something we will unpack in the next sections.

Why this matters

There are four levers in the formula and a fifth outside it, and the recipes pull all of them. \(n_{kv}\) and what is stored per token (\(d_k + d_v\)) are the subject of this chapter. \(b\) is the quantized KV of Part IV. \(L\) shrinks in hybrid models, where only 1 in every 4 layers stores KV (linear attention). The fifth lever does not change capacity, only bandwidth: reading just part of the rows at each step, which is the sparse attention of the next chapter. Anyone building a recipe needs to know which lever each model pulled, because that is what determines the kernels, the --kv-cache-dtype and what happens to the cache under tensor parallel.

MHA, MQA and GQA: how many key drawers?

In the original multi-head attention, MHA, each of the \(H\) heads has its own query, key and value projections (the mechanics are in Attention):

\[ q^{h}_t = W_Q^{h} x_t,\qquad k^{h}_j = W_K^{h} x_j,\qquad v^{h}_j = W_V^{h} x_j,\qquad o^{h}_t=\sum_{j\le t}\operatorname{softmax}_j\!\Big(\tfrac{q^{h}_t\cdot k^{h}_j}{\sqrt{d_h}}\Big)\,v^{h}_j \]
  • \(x_t\): state of token \(t\) at the layer input
  • \(h\): head index, counted from zero: \(h = 0, \dots, H-1\)
  • \(W^{h}_Q, W^{h}_K, W^{h}_V\): projections of head \(h\), from \(d_{model}\) to \(d_h\)
  • \(o^{h}_t\): head output, later concatenated and projected by \(W_O\)

With MHA, \(n_{kv} = H\): each head stores its own key and its own value per token. In 2019, Noam Shazeer proposed MQA (multi-query attention): all heads keep their own queries, but share a single key and a single value per token. The cache shrinks by a factor of \(H\). The cost is quality: every head now consults the same catalog. In 2023, Ainslie and colleagues proposed the middle ground, GQA (grouped-query attention). The \(H\) heads form \(G\) groups, and heads in the same group share K and V.

\[ k^{h}_j = k^{\,g(h)}_j,\quad v^{h}_j = v^{\,g(h)}_j,\qquad g(h) = \Big\lfloor \frac{h}{H/G} \Big\rfloor,\qquad n_{kv} = G \]
  • \(G\): number of groups, that is, of K/V heads; with \(h\) counted from zero, \(g(h)\) runs from \(0\) to \(G-1\)
  • \(H/G\): queries per KV head (the group ratio)
  • \(G = H\): MHA; \(G = 1\): MQA

Sharing K and V does not make the heads look at the same place. Each head keeps its own query, and the product \(q^h\cdot k^{g}_j\) gives a different attention pattern for each one. What the group shares is the catalog of keys and the content on offer. There is also a hardware bonus: when the kernel loads a K/V row from memory, that row serves all \(H/G\) queries in the group. Since decode is limited by bandwidth (memory-bound), this reuse raises the arithmetic intensity almost for free.

In the figure, the dots at the top are the query heads and the ones at the bottom are the K/V heads. The pulses show a KV read traveling up and being used by several queries. Drag the number of KV heads and turn on tensor parallel.

Read the three panels at the bottom. The group ratio tells you how many queries each KV read feeds. The bytes per layer drop in proportion to \(n_{kv}\). And under tensor parallel the cache per GPU only shrinks as long as there are KV heads to hand out: with a single head, every GPU keeps its own full copy. This detail will come back with MLA, which behaves like an MQA during decode.

Pitfall: KV with fewer heads than GPUs

Tensor parallel splits the heads across GPUs, and each GPU only needs the KV of its own queries. If \(n_{kv} \ge\) TP and divisible by it, the KV splits. If \(n_{kv} <\) TP, the KV head is copied onto several GPUs, and in MQA (or MLA during decode, which is an MQA over the latent) every GPU stores the entire cache. That is why, in DeepSeek-V4, going from TP=2 to TP=3 does not divide the KV per rank: more memory is left over because each rank holds fewer weights (≈ 35 GiB of KV per rank, 5 M tokens), but prefill gets 22–23% slower at 128K–256K, because the attention and the indexer stay whole on every rank. Details in Parallelism.

The sparse-attention indexers, which you will meet in the next chapter, are pure MQA: GLM's has 32 query heads and one 128-dimensional key per token (indexer.wk [128, 4096]), and Qwen's has 4 queries and indexer_kv_heads = 1, a value the model code requires. When all you need is to rank candidates, a shared catalog is enough.

MLA: store the summary, not the cards

GQA saves cache by making heads identical in K and V within a group. Multi-head Latent Attention (MLA), introduced by DeepSeek-V2 in 2024, saves in a different way: each head keeps its own keys and values, but all of them are derived from the same small vector per token. The mathematical tool is low-rank factorization (reviewed in Tensors and linear algebra): a large matrix \(W \in \mathbb{R}^{m \times n}\) can be approximated, or built that way from the start, as the product of two skinny ones \(A \in \mathbb{R}^{m\times r}\) and \(B \in \mathbb{R}^{r\times n}\), with \(r\) much smaller than \(m\) and \(n\). The cost drops from \(m\,n\) to \(r\,(m+n)\) numbers, and everything that passes through \(W\) is squeezed through an \(r\)-dimensional bottleneck.

The lesson is that when the useful information lives in a few directions, a narrow bottleneck loses little. MLA applies this idea to K and V, and the crucial point is where the bottleneck sits: between the token and the cache. For each token \(t\), the layer computes a KV latent and stores it. Each head's keys and values are linear functions of this latent:

\[ c^{KV}_t = W^{DKV} x_t \in \mathbb{R}^{d_c},\qquad k^{C}_{t,h} = W^{UK}_h\, c^{KV}_t,\qquad v^{C}_{t,h} = W^{UV}_h\, c^{KV}_t \] \[ c^{Q}_t = W^{DQ} x_t \in \mathbb{R}^{d'_c},\qquad q^{C}_{t,h} = W^{UQ}_h\, c^{Q}_t \]
  • \(W^{DKV}\): down-projection (the “D”), from \(d_{model}\) to \(d_c\)
  • \(d_c\): rank of the latent, the kv_lora_rank
  • \(W^{UK}_h, W^{UV}_h\): up-projections (the “U”) of head \(h\), from \(d_c\) to \(d_h\)
  • \(d'_c\): rank of the query latent, the q_lora_rank
  • \(C\): “content” part, with no position

Only \(c^{KV}_t\) goes into the cache: \(d_c = 512\) numbers per token and per layer, versus \(H \times (d_k + d_v)\) for an MHA. The query also goes through a bottleneck (\(d'_c = 1536\) in GLM and DeepSeek-V3), but that one does not touch the cache. It saves parameters and weight bandwidth, because the query is never stored.

Note the difference from GQA. In an 8:1 GQA, the 8 heads of a group read exactly the same key. In MLA, GLM's 64 heads have different keys, but they all live in the same 512-dimensional subspace spanned by the latent. A good way to picture it is different heads with a common source.

It is not post-training compression

It is tempting to think of MLA as an SVD applied to an already-trained MHA. It is not: the bottleneck is part of the architecture from the very start of training, and the model learns to store in 512 dimensions whatever the heads will need. That is why kv_lora_rank is a checkpoint hyperparameter, not a recipe knob. Changing it would take a different model.

Weight absorption: why the cache is just the latent

There is a problem hidden in the previous section. If each head's keys are \(W^{UK}_h c_j\), then at every decode step we would need to rebuild K and V for all past tokens, head by head. Either we pay for that reconstruction at every step, or we store the rebuilt K and V and lose all the savings. The way out is the associativity of matrix multiplication, and it is the heart of MLA. Look at the product that gives the attention score:

\[ q_{t,h}^{\top}\,k_{j,h} \;=\; q_{t,h}^{\top}\,\big(W^{UK}_h c_j\big) \;=\; \big(W^{UK\top}_h\, q_{t,h}\big)^{\top} c_j \;=\; \tilde q_{t,h}^{\top}\, c_j \] \[ o_{t,h} \;=\; \sum_j a_{tj,h}\, W^{UV}_h c_j \;=\; W^{UV}_h \Big( \sum_j a_{tj,h}\, c_j \Big) \]
  • \(\tilde q_{t,h} = W^{UK\top}_h q_{t,h}\): “absorbed” query, already in latent space (\(d_c\) dimensions)
  • \(c_j\): stored latent of token \(j\) (in the cache)
  • \(a_{tj,h}\): attention weight of head \(h\) from token \(t\) to token \(j\)
  • \(W^{UV}_h\): applied once, after the sum, and not to each token

Read it slowly. Instead of carrying every latent in the cache up to the head's space, we carry the query down to latent space, just once per step. Attention then runs directly on the stored latents, and the V up-projection happens after the weighted sum, only once. This is weight absorption. The result is surprising: all \(H\) heads consult the same vectors \(c_j\), as key and as value. MLA during decode is, quite literally, an MQA over the latent, with \(d_{qk} = d_c\) (plus the RoPE part, as we will see) and \(d_v = d_c\).

The figure does the math with numbers. Both routes reach the same scores, but the work scales very differently with the size of the cache.

The counters show the price of each route. Rebuilding K and V for a 128K context at every step would cost teraflops per layer, just to redo what was already in the cache. Absorbing costs one small projection per head. But here is an honest caveat: with absorption, each score uses 512-dimensional vectors (576 with RoPE), versus 256 for the original head. Per query–key pair, absorbed MLA does more math than an MHA. It wins because in decode the bottleneck is the bytes read, and it reads 656 B per token in FP8 (1,152 B in BF16 with the RoPE padding, or 1,024 B for the 512-wide latent alone) instead of the 65,536 B of ready-made K and V in BF16.

Deep dive: prefill rebuilds, decode absorbs

In prefill the situation flips. There are thousands of queries at once, the work is limited by compute rather than bandwidth, and rebuilding K and V once for the whole chunk comes out cheaper than computing 576-dimensional scores. That is why MLA implementations have two paths: an “expanded” MHA for prefill (in vLLM, forward_mha) and an absorbed MQA for decode (forward_mqa). In GLM, the FLASHINFER_MLA_SPARSE_SM120 backend inherited a forward_mha that only raises NotImplementedError. The build patch declares supports_dense_mha_prefill = False, and prefill goes through the same top-k MQA kernel as decode, which matches the model's own sparse semantics (next chapter).

Another engine: the latent in prefill too

In the GLM·TF recipe, which serves the same weights on the TensorFold engine, the DSA layers stay on the latent path in both phases (TF_GLM_LATENT=1; with 0, the engine goes back to storing per-head K and V, a path kept for A/B comparison). What changes between prefill and decode is how the two small projections run: the query absorption and the expansion of the attended latent. In a prompt chunk, 2,048 rows by default, they become real GEMMs, and one of the recipe's patches moves them onto the tensor cores (TF_GLM_LATENT_MMA=1, fixed 64 × 128 × 64 tiles). In a decode window, with only a few rows, each program reads one block of a head's weights and does a separate FP32 sum for each row of the window. The fixed tiles follow this engine's central rule: a row's bits must not depend on the other rows of the chunk, so that any slicing of the prompt reaches the same state. Prompt rows don't have the bits of decode rows, but each one always comes out the same. Notice that neither recipe rebuilds per-head K and V in GLM's prefill. The engine from the inside is in Exact engine.

Absorption has a practical consequence for anyone who quantizes. The absorbed multiplications read the kv_b_proj weight tensor directly: the code slices \(W^{UK}\) and \(W^{UV}\) out of this tensor and uses them in its own math, instead of calling the linear layer. A format packed for a GEMM kernel (Marlin FP8 or EXL3, which rearrange the weight into the layout that their own kernel understands) does not serve this path. Our interpretation: there is also a numerical reason, because an error in \(W^{UK}\) contaminates the absorbed query of every head, in every score. And the weight is small. By our count, it is 16.8 M parameters per layer, about 0.4 GB in BF16 summing the 12 MLA layers of the GLM checkpoint (the 11 in the decoder plus 1 in the MTP layer).

The recipe's dense FP8 mode (W8A16 on Marlin: weights in FP8, activations in BF16, one scale per output channel) is organized in groups: shared, dense, kda and mla. The mla group converts the fused down-projection (q_a_proj + kv_a_proj_with_mqa become fused_qkv_a_proj), q_b_proj and o_proj. kv_b_proj is left out, in BF16, because absorption reads the weight directly. For the same reason, the dense EXL3 overlay (non_routed_exl3.layers) refuses kv_b_proj. Even the official FP8 checkpoint keeps it in BF16 (modules_to_not_convert). The FP8 details are in FP8, FP4 and microscaling.

VariableTF_GLM_KVB=bf16 (default) · fp8 · q4

In the GLM·TF recipe, the checkpoint's dense weights go to 4 bits (DENSE=q4), but kv_b_proj stays in BF16 (v1.3.2 corrected the docs, which said FP8). The reason is not vLLM's. TensorFold writes its own absorption and expansion kernels, and one of the recipe's patches (glm-decode-rounds) taught them to read kv_b in FP8, as e4m3 with one FP32 scale per row and per 128-column block of the latent (half the bytes), or in 4 bits, in groups of 64 with an MSE-searched range (about a quarter). Each program dequantizes its weight block once and does a single FP32 sum per row, whatever the number of rows in the window. vLLM's restriction came from the kernel, not from the math. The recipe keeps the BF16 default, and the code classifies the other options as lossy formats, like the rest of DENSE. The order of the absorbed computation also enables a trick. Since \(W^{UV}\) only comes in after the sum, a side stream brings into L2, while the attention core runs, the “value” half of kv_b, which expand_v reads next, and then the o_proj weights. It is one of the three per-layer prefetch sites of TF_GLM_L2PF=1, which together took prose from 48.36 to 49.46 tok/s with 1 request (two boots each).

Decoupled RoPE, and the GLM that did without position

Absorption has an enemy: RoPE. It rotates each token's key by an angle that depends on the position \(j\) (see Position: RoPE, NoPE, mRoPE and YaRN). If the rotation \(R_j\) sits between the latent and the key, the math becomes:

\[ q_{t,h}^{\top} \big(R_j\, W^{UK}_h c_j\big) = \big(W^{UK\top}_h R_j^{\top} q_{t,h}\big)^{\top} c_j \]
  • \(R_j\): RoPE rotation for position \(j\), different for each token in the cache
  • the absorbed query now depends on \(j\): you would need one \(\tilde q\) per context token

The matrix we wanted to absorb got stuck between two things that vary, and \(\tilde q\) can no longer be computed just once. DeepSeek-V2's solution was decoupled RoPE: splitting each head into two parts. The content part (NoPE) comes from the latent and can be absorbed. A small part, of \(d_r = 64\) dimensions, carries the position: a RoPE key \(k^R_j\) shared by all heads (a 64-dimensional MQA) and stored in the cache next to the latent, plus one RoPE query per head, derived from the query latent.

\[ s_{tj,h} = \frac{\tilde q^{\,C\top}_{t,h}\, c^{KV}_j \;+\; q^{R\top}_{t,h}\, k^{R}_j}{\sqrt{d_h + d_r}},\qquad k^{R}_j = \operatorname{RoPE}_j\!\big(W^{KR} x_j\big),\qquad q^{R}_{t,h} = \operatorname{RoPE}_t\!\big(W^{QR}_h c^{Q}_t\big) \]
  • \(c^{KV}_j\) (512) and \(k^R_j\) (64): the 576 dimensions stored per token
  • \(q^R_{t,h}\): positional part of the query, one per head
  • \(d_h + d_r\): 128 + 64 = 192 in DeepSeek-V3, the original head scale

Hence the magic number of MLA kernels: 576 = 512 + 64. It is the dimension of the “key” that the absorbed kernel sees, and it is the origin of the 656-byte record of the V3.2 family's fp8_ds_mla layout: 512 B of latent in FP8, 16 B of scales and 128 B with the 64 RoPE dimensions in BF16 (the bytes are unpacked in Quantizing the KV cache). Compare with Qwen, which is GQA: there, partial RoPE rotates 64 of the 256 dimensions directly in the stored key. With no latent there is no absorption to protect, and nothing needs to be decoupled.

GLM-5.3-Flash: MLA without position

GLM-5.3-Flash follows the Kimi Linear lineage: 3 KDA linear attention layers for every MLA layer, and the MLA is NoPE. In the config, qk_rope_head_dim: 0 and mla_use_nope: true. The head has 256 content dimensions and none for position, and the softmax scale is qk_head_dim**-0.5 = 1/16. Token order arrives through the KDA layers, with causal recurrence and a short convolution, and through a small positional embedding in the indexer's pools (Linear attention). Without RoPE, absorption is total and the cache could be just the 512-dimensional latent.

Except the hardware does not cooperate. In the GLM recipe's vLLM image, the only sparse MLA backend for GB10 (SM12x) is FLASHINFER_MLA_SPARSE_SM120, and it was written for the 576 geometry. The stock image loads the checkpoint and dies on the first forward, with two refusals. The first comes from concat_and_cache_mla: pe_dim must be 64 for fp8_ds_mla, because the 656 B record has a fixed slot for 64 RoPE dimensions. The second comes from FlashInfer's SM120 entry point, which requires kv_lora_rank = 512, qk_rope_head_dim = 64 and a 576-wide query. Worse: FlashInfer only instantiates three geometries. DSV3_2 and GLM_NSA have \(d_{qk}\) = 576, a 656 B record and top-k ∈ {128, 512, 1024, 2048}. DSV4 has 512 dimensions, a 584 B record (448 FP8 + 64 BF16 + 8 B footer) and top-k ∈ {128, 512, 1024}. GLM-5.3 would need \(d_{qk}\) = 512 with top-k 2048, a combination that does not exist, and its uniform 512-wide latent does not fit DSV4's 448/64 split.

The recipe's way out is elegant: dress GLM in the GLM_NSA geometry using zeros. The figure shows why this is exact.

Why the padding is exact

With \(q' = [\,\tilde q\,;\,0\,]\) and \(k' = [\,c\,;\,z\,]\), the score is \(q'\cdot k' = \tilde q\cdot c + 0\cdot z = \tilde q \cdot c\) for any \(z\). The softmax receives the same scores, and the value comes only from the 512-dimensional NoPE region (\(d_v = 512\)), so the output is mathematically identical; numerically, it can only differ by the accumulation order inside the kernel. Zeroing the query alone would be enough mathematically. Our interpretation: writing k_pe as zeros guards against garbage from uninitialized memory, because \(0 \times \text{NaN} = \text{NaN}\), and keeps the cache deterministic.

The price is space, and only space: 656 B per token per layer instead of the ~528 actually needed (512 + 16), about 24% more KV in the target's 11 DSA layers. No new kernel was written. MLAAttentionSpec.real_page_size_bytes already allocates block_size × 656 for fp8_ds_mla in models that are not deepseek_v4, so the allocation lines up with no further patches.

Build patchrope_pad = 64 when qk_rope_head_dim == 0

In the Dockerfile, a Python block edits flashinfer_mla_sparse_sm120.py inside the image with substitutions that require exactly one match (replace_once). If qk_rope_head_dim == 0, the impl sets self.rope_pad = 64 and kernel_qk_rope_head_dim = 0 + 64, and right before the kernel it does q = F.pad(q, (0, 64)). In do_kv_cache_update, the k_pe passed to the cache becomes new_zeros(…, 64). The guard is explicit: if kv_lora_rank != 512, the patch raises NotImplementedError, because the 576 geometry only adds up with 512 + 64. Lesson for your own recipe: if a new NoPE model has a different kv_lora_rank, this trick will not work and you will need another kernel.

VariableKV=fp8 → TF_GLM_KV=fp8

The GLM·TF recipe does not go through FlashInfer. TensorFold writes the attention kernels for GLM's family in Triton, and they take the latent width as a parameter, from the model's kv_lora_rank: \(d_{qk} = 512\), with no 576 geometry to dress up for, no rope_pad and no RoPE block in the cache. In BF16, the row is the bare latent, 1,024 B (the “1 KB a token and layer” of TensorFold's docs). With KV=fp8, the recipe's default, each row becomes 512 e4m3 codes, one FP32 power-of-two scale and 12 zero bytes of alignment: 528 B, the ~528 “actually needed” of the math above, 19.5% less than fp8_ds_mla's 656.

The kernel takes advantage of the fact that, in absorbed MLA, the latent is key and value at the same time. The same tile of codes enters both products, and the row's scale is folded into both: it multiplies the scores before the softmax and the probabilities before the weighted sum. Multiplying by a power of 2 rounds nothing, so the math is that of the BF16 kernel on the dequantized rows, up to the order of the FP32 sums. Adding the indexer's pooled key (144 B per pool of 4 tokens, 36 B per token), that makes 11 × 564 = 6,204 B per token and per rank, versus 7,579 in the vLLM recipe. This is our own math from the code, and the latent stays whole on both ranks, as in vLLM (our interpretation of the geometry code). FP8 is lossy: the recipe publishes GSM8K 98.0% and HumanEval 97.6% with FP8 KV and 4-bit dense weights, and KV=bf16 is the exact cache, with a window of 196,608 tokens (with DFlash2) instead of 1,048,576. The row byte by byte is in Quantizing the KV cache.

DeepSeek-V4: the key is the value itself

DeepSeek-V4-Flash takes absorption to the limit. In absorbed MLA, the latent \(c_j\) already plays the role of key and value at the same time, and the matrices \(W^{UK}\) and \(W^{UV}\) only survive inside the query and the output. V4 takes the next step and eliminates them. Each token produces a single 512-dimensional vector per layer, and that vector is, quite literally, the key and the value of all 64 heads (num_key_value_heads = 1).

\[ kv_j = \operatorname{RMSNorm}\big(W^{kv} x_j\big) \in \mathbb{R}^{512} = [\,\underbrace{kv^{\text{NoPE}}_j}_{448}\,;\,\underbrace{R_j\,u_j}_{64}\,],\qquad o_{i,h} = \sum_j a_{ij,h}\; kv_j \]
  • \(W^{kv}\): wkv, 4096 → 512 (2.10 M parameters)
  • 448 dimensions without position and 64 with RoPE, in the last positions, interleaved style (is_neox_style=False)
  • \(R_j u_j\): the positional part, rotated by the absolute position \(j\)
  • \(a_{ij,h}\): weights of head \(h\), with scale \(512^{-1/2}\) and one attention sink per head

In vLLM this shows up in a telling way: DeepSeek-V4's MLA wrapper is built with kv_lora_rank = head_dim and v_head_dim = head_dim, both 512. It is the absorbed form with nothing left to absorb, and whatever is specific to each head now lives only in the query (wq_b) and the output (wo_a). The query follows the low-rank pattern: wq_a (4096 → 1024, the q_lora_rank) → q_norm → wq_b (1024 → 64 × 512), followed by an RMSNorm with no weight on each head and by RoPE on the last 64 dimensions. The same 1024-dimensional query latent feeds the sparse indexer.

Notice where RoPE ended up: inside the shared vector, with nothing decoupled. In the previous section, the rotation broke absorption because it was stuck between the latent and \(W^{UK}\). In V4 there is no \(W^{UK}\) between the rotation and the dot product: \(q_{i,h}\cdot kv_j\) is already the final computation, and there is nothing to absorb. That is why RoPE can live in the last 64 dimensions of \(kv_j\) itself, with no need for a separate key. The price is that the value, being the same vector, also arrives rotated.

That is the problem that remains. In ordinary attention, RoPE only touches Q and K, because position needs to decide who receives attention, not the content being mixed. In V4, the value is the key, so every value arrives with 64 dimensions rotated by the absolute position of its token. The sum \(o_i\) mixes absolute rotations: the same stretch of text, placed further along in the document, would produce an output rotated a different way. The fix is inverse RoPE: rotating the last 64 dimensions of the output by the query's position \(-i\).

\[ R_{-i}\; o^{R}_{i} \;=\; \sum_j a_{ij}\, R_{-i}R_{j}\, u_j \;=\; \sum_j a_{ij}\, R_{\,j-i}\; u_j \]
  • \(R_{-i}\): rotation by the query position, with the sign flipped (the conjugate)
  • \(R_{-i}R_j = R_{j-i}\): rotations in the same plane add up
  • each contribution now depends only on the distance \(j - i\)

In the figure, each clock is a context token with the RoPE part of its value (one pair of dimensions, one frequency). The big arrow on the left is the raw output; the one on the right, the un-rotated output. Shift the whole stretch further along in the document and compare.

In the official reference, this is one line: apply_rotary_emb(o[..., -rd:], freqs_cis, True), where the True asks for the conjugate, the inverse rotation. In vLLM, the operation is fused into a kernel, fused_inv_rope_fp8_quant, which un-rotates the 64 dimensions and quantizes the output to FP8 on the spot for the grouped multiplication of wo_a. You can see it in the attention code of the DSpark drafter in the Stage-C overlay, which repeats the target's projection structure. (The DS recipe runs on three runtime lanes, that is, three versions of the vLLM code inside the container. Lane A, the default, uses the Anemll 0.1.1 image. Lane B, the historical one, uses the Stage-C image with an overlay that copies whole vLLM files: it is the one with readable code in the repository and the only one that registers the VLLM_DSV4_* and VLLM_USE_B12X_WO_PROJECTION variables. Lane C is an experiment on top of official vLLM main.) The kernel has an invariant (num_heads == n_groups × heads_per_group, per rank) that the TP=3 patch must preserve.

And the cache? Each V4 row has 584 bytes: 448 B with the NoPE dimensions in FP8 E4M3, in 7 blocks of 64 with a power-of-2 scale (UE8M0); 128 B with the 64 RoPE dimensions in BF16; and an 8 B footer (7 scales + 1 of padding). Within a page, all the data comes first (576 B × tokens) and then all the scales (8 B × tokens). The model was trained with those 448 dimensions simulated in FP8, in blocks of 64 (QAT), and the reference explains that the RoPE dimensions stay in BF16 “for positional precision”. Storing the KV in FP8 is therefore the training regime, not an extra approximation.

Parametershead_dim: 512 (448 NoPE + 64 RoPE) · kv_lora_rank = head_dim = 512

The 64 query heads have 512 dimensions, and the KV latent has the same size, because it is the key and the value. That is why the cache row is 584 B, and not 64 heads × something. And that is why the KV is replicated on every rank under tensor parallel: there is only one KV head, and nothing to slice. Without the per-layer compression of the next chapter, it would be 43 × 584 = 25,112 B per token. With it, ≈ 3,850 B. fused_wqa_wkv (wq_a and wkv fused together) is also replicated (disable_tp=True): they are small projections, and the KV latent is needed whole on every rank.

Parameterq_lora_rank: 1024

The query goes through wq_a (4096 → 1024, 4.19 M parameters) → q_norm → wq_b (1024 → 32,768, 33.55 M). A direct 4096 → 32,768 projection would have 134 M. The bottleneck cuts parameters and weight bandwidth at every decode step, and the 1024-wide latent is reused by the indexer. Along the lineage, V2 and V3 used 1536, and V4-Flash, with a smaller hidden_size (4096, versus 5120 in V2 and 7168 in V3/V3.2), uses 1024. Under TP, wq_b is column-parallel: 32 heads per rank at TP=2.

The two-step output: o_groups and o_lora_rank

V4's attention ends with a size problem. It has 64 heads × 512 dimensions = 32,768 output numbers per token, and a direct projection back to 4096 would have \(32768 \times 4096 \approx 134.2\) M parameters per layer. V4 applies low rank here too, in groups. The 64 heads form o_groups = 8 groups of 8 heads (4,096 dimensions each). Each group goes through its own projection wo_a[g]: 4096 → 1024, the o_lora_rank. The 8 results are concatenated (8,192) and go through wo_b: 8192 → 4096.

\[ y_t = W^{b}\,\big[\,W^{a}_{1}\, o_{t,G_1}\,;\;\dots\;;\,W^{a}_{8}\, o_{t,G_8}\,\big],\qquad W^{a}_g \in \mathbb{R}^{1024\times 4096},\quad W^{b} \in \mathbb{R}^{4096\times 8192} \]
  • \(o_{t,G_g}\): outputs of the 8 heads in group \(g\), concatenated (8 × 512 = 4,096)
  • \(W^a_g\): the group's wo_a, 8 × 4.19 M = 33.55 M in total
  • \(W^b\): wo_b, 33.55 M
  • total 67.1 M, half of the direct projection

In the implementation, wo_a is a batched matrix multiplication (BMM), an einsum ("bhr,hdr->bhd") in FP8. Each letter is an axis: \(b\) is the token, \(h\) the group, \(r\) the group's 4,096 inputs (\(8 \times 512\)) and \(d\) the 1,024 outputs (the o_lora_rank). The letter \(r\) is missing from the output, so it is summed over: for each group, a \(1024 \times 4096\) matrix multiplies that group's vector of 4,096 inputs. In vLLM, wo_a.is_bmm = True and bmm_batch_size is the number of local groups: 4 per rank at TP=2. wo_b is row-parallel: each rank multiplies its slice and an all-reduce sums the partials, one per layer and per step.

Switch the TP in the figure. At TP=3, see what the patch does and what it cannot do.

The shape contract decides everything. Eight groups do not divide evenly by 3. Stock vLLM either refuses to start (64 % 3 != 0) or, worse, silently goes ahead with 8 // 3 = 2 local groups and drops the rest, which produces fluent, meaningless text. The TP=3 patch (patches/tp3/apply_tp3_patch.py, only with TP_SIZE=3) raises the groups from 8 to 9 and keeps 8 heads per group: the heads go from 64 to 72, with 3 groups and 24 heads per rank. Group 9 has wo_a and wo_b zeroed and attn_sink = −∞. The sink must be \(-\infty\), not 0, because it adds \(e^{\text{sink}}\) to the softmax denominator: \(e^{-\infty} = 0\) changes nothing, whereas \(e^{0} = 1\) would shrink all of the head's weights. Padding heads inside the groups looks simpler, but it moves \(r\) away from 4096 and the einsum kernel refuses it. The expected boot log, on every rank, is DSv4 TP pad: heads 64 -> 72 for TP=3. The full story is in Beyond 2 nodes.

Parameterso_groups: 8 · o_lora_rank: 1024 · q_lora_rank / o_lora_rank: 1024 / 1024

All three numbers come from config.json and cannot be tuned. What the recipe controls is how they are distributed. At TP=2, n_local_groups = 8 // 2 = 4, and the wo_a BMM runs with 4 matrices per rank. At TP=3, the pad to 9 groups is mandatory. In lane B (Stage-C overlay), VLLM_USE_B12X_WO_PROJECTION=1 swaps the generic path for a b12x kernel that fuses wo_a and wo_b and preserves the checkpoint's UE8M0 scales (the code refuses to start without an FP8 weight_scale_inv). In lane A, the default (Anemll 0.1.1 image), this variable only produces the warning Unknown vLLM environment variable. More in Kernels.

What a token costs: the calculator

Now we can write down the math for each scheme. For the layers that store KV:

\[ \underbrace{2\,H\,d_h\,b}_{\text{MHA}} \quad\ge\quad \underbrace{2\,G\,d_h\,b}_{\text{GQA}} \quad\ge\quad \underbrace{2\,d_h\,b}_{\text{MQA}} \qquad\qquad \underbrace{d_c\,b + d_r\cdot 2 + \text{scales}}_{\text{MLA}} \qquad \underbrace{(d_h - d_r)\,b + d_r\cdot 2 + \text{scales}}_{\text{MLA with } K=V} \]
  • bytes per token and per layer; multiply by \(L\)
  • MHA, GQA and MQA written with \(d_k = d_v = d_h\); if they differ, replace \(2\,d_h\) with \(d_k + d_v\)
  • in MLA, the RoPE part (\(d_r\)) stays in BF16 (2 B) even with the latent in FP8
  • scales: 4 × FP32 per row in fp8_ds_mla (16 B), 8 B in the V4 layout

The calculator below does the math for any combination. The presets load each model's real dimensions and highlight the scheme it uses, with the bytes of the actual layout.

Play with the GLM preset. With the same 11 layers, an MHA in FP8 would store 360,448 B per token, while the packed MLA stores 7,216 B, 50 times less. Adding the indexer's 33 B per layer, you get 7,579 B per token. This is our own math from the layout (11 × 656 + 11 × 33), not a number the recipe prints, but it matches the README, which quotes ~7.1 GiB per million tokens: \(7{,}579 \times 10^6\) B = 7.06 GiB. In this chapter's convention (1M = \(2^{20}\) tokens), the same cost comes to ≈ 7.40 GiB at 1M. The GLM·TF preset sets \(d_r\) to zero: 528 B per layer and, with the indexer's pooled key at 36 B per layer, 6,204 B per token, 18% less. In the DeepSeek preset, the 584 B K = V row per layer, over 43 layers, would give 25,112 B per token and ≈ 24.5 GiB at 1M (26.3 GB), more than the entire KV pool (17.04 GiB per rank). That is why V4 also compresses its own KV along the time axis, the last missing piece and the subject of the next chapter.

The pure math is a floor

What the engine allocates is always a bit more than the formula. On Qwen with FP8 KV, boot reports 32.02 GiB for 3,652,200 tokens, 9,418 B per token per GPU, 41% above the 6,656 B of the pure main KV. The difference comes from QSA's indexer and compressor in BF16, the GDN state and page rounding. On DeepSeek, the “Maximum concurrency” line counts the four KV groups with the same page size and gives ≈ 7.8 KB per token, twice the physical cost. Use the formula to decide whether a model stands a chance of fitting, and the boot log to find out how much fits (PagedAttention and the KV budget).

In the recipes: the model, the kernel and the adaptation in between

The architecture says what needs to be computed. The kernel says in what format it agrees to compute it. MLA attention kernels are written for specific geometries: key dimension, row bytes, top-k and number of local heads become template parameters, fixed at compile time. DeepSeek's FlashMLA was built for datacenter Hopper and Blackwell and does not exist on GB10. There, what vLLM has is FlashInfer SM120, with its three geometries. A good part of a recipe's engineering is fitting the key (the model) to the lock (the kernel).

Notice that the adaptations follow a pattern. When the model asks for less than the kernel offers, the recipe pads with neutral values: zeros in GLM's RoPE, extra heads with a zero query in GLM's TP=3 (22 → 32 local heads), a ghost group with sink \(-\infty\) in DeepSeek's TP=3. When it asks for more, the recipe trims judiciously, like the 511 pools + tail of GLM's indexer, which fit into the template's 2,048 candidates (next chapter). In every case, the question is the same: is the padding a neutral element of the operation? Zero is neutral for the sum inside a dot product, \(-\infty\) is neutral for the denominator of a softmax. A wrong value here does not break the boot, it just ruins the answers.

The other way out: a made-to-measure lock

The GLM·TF recipe solves the fit from the other side. Instead of adapting the model to a generic kernel, it uses an engine, TensorFold, in which each model family brings its own kernels. GLM's DSA layers run on kernels built for its geometry: a 512-wide latent, 32 heads per rank and the indexer's whole selection, 512 pools plus the incomplete pool, up to 2,051 tokens, without the cut to the template's 2,048. There are no zeros to write and no pools to cut. The price goes elsewhere: kernels that only serve this family, 53 patches tied to one engine version (v0.6.0) and, in v1.3.2, a GLM CUDA engine that required exactly two ranks, with no TP=3 or TP=4. Since v1.4, patches 0066–0068 split the 64 heads unevenly over 3 ranks (22/21/21), with no padding (switch the TP with the TensorFold key in the figure); TP=4 lives on a branch. Whoever needs breadth, such as a model the engine does not implement yet, stays with the generic lock. Whoever has a single architecture can fight for every byte. The full recipe, with the other differences between the engines, is in GLM recipe · TensorFold.

Three more pieces of the kernel puzzle

The hotfix hotfix-dsv4-issue141-sparse-mla-decode-chunk.py (opt-in, DSPARK_ENABLE_ISSUE141_SPARSE_MLA_CHUNK=1) works around stochastic crashes in the “paged” decode path of FlashInfer SM120 above 64 rows. It slices the call into views of up to 64 rows, with no copies, cutting the six row-bound arguments together. It is a workaround, not the root cause. The overlay's B12X_MLA_SPARSE backend serves the V3.2 family (576 head, 656 B fp8_ds_mla, block of 64) and is not used by V4, but it is useful as a comparison between the layouts. And the issue #22 hotfix fixed a string comparison: nvfp4_ds_mla fell into the slow BF16 path (~1 tok/s at 600K) instead of the FP8 one (~17 tok/s), even though the bytes are identical. Details in Kernels and quantized KV.
