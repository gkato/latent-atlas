Open the NVFP4 checkpoint of Qwen3.8-Flash-Next and you find 299,545 tensors, with names like model.language_model.layers.17.mlp.experts.203.down_proj.weight. GLM-5.3-Flash and DeepSeek-V4-Flash have similar lists. It looks like a tangle, but behind it there is a single mold, repeated dozens of times: the Transformer block. Each block reads a fixed-width vector, performs two computations (attention, which you saw in the previous chapter, and a feed-forward network) and adds the result back into a vector that runs through the entire model, the residual stream. In this chapter you will assemble this block piece by piece: the decoder-only assembly line, the residual stream, pre-normalization with RMSNorm, the SwiGLU FFN and the swiglu_limit cap. Then comes the bookkeeping (parameters and FLOPs of each piece), the difference between a dense block and an MoE block, and how to read the tensor names of a checkpoint. By the end you will know why the recipes insist on hidden_size 4096, why GLM's EXL3 overlay repeats SWIGLU_LIMIT_DEFAULT = 10.0 and which piece of the block each patch touches.

From token to logit: the decoder-only assembly line

The three models in the recipes are decoder-only Transformers. The original 2017 Transformer had two halves: an encoder that read the entire source sentence and a decoder that wrote the translation. Modern LLMs kept only the second half. They receive a sequence of tokens and, at each position, predict the next one. The causal mask you saw in attention guarantees that position \(t\) only sees positions \(\le t\). That is why a single pass through the model trains every position at once and, at inference, generates one token at a time.

A token's journey has four stations, always the same:

  1. Embedding. The token id picks a row of the table \(E \in \mathbb R^{V\times d}\) (chapter Tokens and embeddings). Out comes a vector of \(d\) numbers.
  2. \(N\) blocks. Each block receives the matrix \([T \times d]\) (one vector per token) and returns another \([T \times d]\) matrix.
  3. Final norm. One last RMSNorm (the normalization you met in chapter 2) puts the vector on the scale the next piece expects.
  4. lm_head. The matrix \(W_U \in \mathbb R^{V\times d}\) turns the vector into \(V\) logits, one per vocabulary token. Sampling (chapter Generating text) picks the next token from them.
\[ \mathbf h^{(0)}_t = E[x_t] \qquad \mathbf h^{(\ell+1)} = \mathrm{Block}_\ell\big(\mathbf h^{(\ell)}\big) \qquad \mathbf z_t = W_U\,\mathrm{Norm}\big(\mathbf h^{(N)}_t\big) \]
  • \(x_t\): id of the token at position \(t\); \(E[x_t]\): row \(x_t\) of the embedding table
  • \(\mathbf h^{(\ell)}_t \in \mathbb R^{d}\): the state of token \(t\) at the input of block \(\ell\); \(d\) = hidden_size
  • \(N\) = num_hidden_layers: number of blocks
  • \(\mathbf z_t \in \mathbb R^{V}\): logits; \(V\) = vocab_size

Notice the property that holds everything up: every block receives and returns the same shape. This shape contract is what lets you stack 45 blocks in GLM, 48 in Qwen and 43 in DeepSeek. It also lets you read the state in the middle of the stack (the drafters do this) and even cut the stack short: the recipe-from-scratch tutorial uses --hf-overrides '{"num_hidden_layers":N}' to compare only the first \(N\) blocks against the reference. In the figure, pick a model and follow the token character along the conveyor belt.

The number that shows up most in the recipes is \(d\), the model width. Think of it as the gauge of a railroad. Every car (every sublayer) has to fit it, so it dictates the shape of almost every matrix: the embedding is \([V \times d]\), the input of every projection has \(d\) columns, the output of every sublayer has \(d\) rows.

Why the shape contract matters to recipe writers

Every speculative decoding drafter reads the target model's residual stream, and so it depends on \(d\). GLM's DFlash2 takes the output of 5 layers (5, 14, 24, 33 and 42) and compresses \(5 \times 4096 = 20{,}480\) numbers per token back down to 4096 with an fc matrix \([4096 \times 20480]\). DeepSeek's DSpark averages the 4 streams at layers 40, 41 and 42 and projects \(3 \times 4096 = 12{,}288 \to 4096\). Qwen's MTP combines the target's final state with the embedding of the next token. If the engine hands over the wrong state (in the middle of a computation, or with the 4 streams still separate), the draft gets bad and acceptance plummets, without any error message. These drafters are the subject of Part VII.

The residual stream: the bus everyone reads from and writes to

Inside each block, the token's vector goes through two sublayers. The first is the token mixer (attention, or a variant of it), which brings in information from other positions. The second is the FFN, which processes each token on its own. The decisive detail is how the result comes back. No sublayer replaces the vector. Each one reads a normalized copy and adds its contribution to the original vector:

\[ \mathbf h' = \mathbf h + \mathrm{Attn}\big(\mathrm{Norm}_1(\mathbf h)\big) \qquad\qquad \mathbf h'' = \mathbf h' + \mathrm{FFN}\big(\mathrm{Norm}_2(\mathbf h')\big) \]
  • \(\mathbf h\): the token's vector at the block input (a point on the residual stream)
  • \(\mathrm{Norm}_1, \mathrm{Norm}_2\): RMSNorms with their own gain (next section)
  • \(\mathrm{Attn}\): the attention sublayer, including the o_proj that brings the result back to width \(d\)
  • \(\mathrm{FFN}\): the feed-forward network, whose last matrix (down_proj) also returns width \(d\)

We call this “\(\mathbf h + \ldots\)” a residual connection, the same “gradient expressway” from chapter 2, now seen from inside a Transformer block. The vector \(\mathbf h\), which passes from block to block collecting sums, is the residual stream. The most useful picture is a bus (or a highway with \(d\) lanes). The sublayers are stations by the side of the road. Each station takes a snapshot of what goes by (the normalized read), computes something and drops a package on the road (the sum). Nobody erases what the others left. If you unroll the equations, the final vector is literally the sum of everything that was written:

\[ \mathbf h^{(N)} = \underbrace{\mathbf h^{(0)}}_{\text{embedding}} + \sum_{\ell=0}^{N-1} \Big( \underbrace{\mathbf a^{(\ell)}}_{\text{attention}} + \underbrace{\mathbf f^{(\ell)}}_{\text{FFN}} \Big) \]
  • \(\mathbf a^{(\ell)}\): what block \(\ell\)'s attention wrote (output of o_proj)
  • \(\mathbf f^{(\ell)}\): what block \(\ell\)'s FFN wrote (output of down_proj)

The figure shows this in slow motion. Each lane of the bus is a coordinate of the vector, and each color is a different writer. Use the steps to see the reads (copies that take nothing off the road) and the writes (packages that pile up).

Look at the last step: the vector that reaches the lm_head is a sum with one term per writer, and each term is still there, intact. Three consequences follow, and you will meet them again in the recipes.

Readers and writers

Every matrix in a block is one of two kinds. The readers receive the normalized copy: q_proj, k_proj, v_proj in attention and gate_proj, up_proj in the FFN. The writers produce what gets added: the embedding, the o_proj of each attention and the down_proj of each FFN. If you want to stop the model from writing a certain direction into the stream, edit the writers. That is exactly what abliteration does (chapter Directions in latent space). GLM edits the o_proj of layers 15 to 45. Qwen's abliterated checkpoint changes the o_proj of the 12 sparse attention layers. DeepSeek does the edit at runtime, right after the attention output: \(\mathbf x \leftarrow \mathbf x - \lambda(\mathbf x\cdot\mathbf v)\mathbf v\).

The inner width can be different

The bus has width \(d\), but the work inside a station can be much wider, or narrower. Qwen, with \(d = 2560\), does attention in 24 heads of 256 dimensions (6144 numbers). GLM, with \(d = 4096\), uses 64 heads of 256 in its MLA attention (16,384). DeepSeek uses 64 heads of 512 (32,768), eight times \(d\). The experts, on the contrary, get narrower: 2048 in GLM and DeepSeek, 640 in Qwen. What doesn't change is the interface. The sublayer reads \(d\) and returns \(d\), and that is why there is always an output matrix (o_proj, wo_b, down_proj) with \(d\) rows.

The gradient highway

Why add instead of replace? During training, the gradient has to travel back from the output to the first block. In a network without a residual it goes through each layer multiplied by that layer's derivative, and the product of dozens of factors tends to vanish or explode. With the residual, the derivative of a block with respect to its input is the identity plus something:

\[ \frac{\partial \mathbf h^{(\ell+1)}}{\partial \mathbf h^{(\ell)}} = I + \frac{\partial F_\ell\big(\mathrm{Norm}(\mathbf h^{(\ell)})\big)}{\partial \mathbf h^{(\ell)}} \]
  • \(I\): identity matrix, the “direct path” created by the sum
  • \(F_\ell\): the sublayer (attention or FFN) of block \(\ell\)

The \(I\) works like a direct line that crosses the whole network. Even if the sublayers are hard to get through, the signal arrives. The next figure does the actual computation on a toy network. It nudges the input a tiny bit and measures how much of that nudge is still felt at each layer, which mirrors the gradient that flows back during training. Compare three architectures while changing the weight gain and the depth: no residual, with residual, and residual plus small writers.

Without a residual, the message gets lost as in the telephone game. Each layer multiplies the nudge by a factor close to the gain \(g\), and the product of dozens of factors leaves the band in one direction or the other. With gain 0.3 and 64 layers, \(10^{-34}\) of the nudge is left. With gain 1.5 and 32 layers it becomes \(10^{6}\) times larger. Only gains close to 1 survive, and barely: gain 1.2 with 32 layers already gives \(10^{2.8}\). With a residual, the nudge never vanishes, because the identity path carries it intact. In the figure, the sensitivity never drops below ≈ 0.9. But with writers the same size as the readers, it grows layer by layer, and with high gain (from ≈ 2.1 on) and many layers it goes past \(10^{3}\). This growth is much slower than before: gain 3 with 64 layers gives \(10^{2.7}\) with a residual and \(10^{30}\) without. The third option divides the writers (\(W_2\)) by \(\sqrt{64} = 8\), the same idea as the “small writer initialization” used in practice (GPT-2, for example, divides the weights of the residual layers by \(\sqrt N\) at initialization). With it, the sensitivity stays between ≈ 0.8 and ≈ 8 for every gain and depth in the figure. Identity path plus restrained writers: that is what makes it possible to train stacks of 40 to 60 blocks.

Deep dive: how vLLM implements the sum

In vLLM's models the residual travels as a separate tensor and the sum happens inside the kernel of the next norm. This is the fused add + RMSNorm pattern, which saves one round trip to memory per sublayer. In the simplified form that almost every model follows:

# forward of a pre-norm block in vLLM (simplified)
if residual is None:                      # first block
    residual = hidden_states
    hidden_states = self.input_layernorm(hidden_states)
else:                                     # add what the previous block wrote + normalize
    hidden_states, residual = self.input_layernorm(hidden_states, residual)
hidden_states = self.self_attn(positions, hidden_states)       # writes a
hidden_states, residual = self.post_attention_layernorm(hidden_states, residual)
hidden_states = self.mlp(hidden_states)                        # writes f
return hidden_states, residual            # the sum of f is left to the next block

That is why “the state of the residual stream at layer \(\ell\)” is not a ready-made tensor sitting in memory. It is hidden_states + residual, and sometimes not even that. In GLM, with 4 streams (mHC), the block returns (hidden, residual, post, comb), with the last write deferred so it can be fused into the next layer. The patch_glm_eagle3.py patch has to materialize hc_post and then hc_contract (the average of the 4 streams) to hand DFlash2 a 4096-wide vector.

Preview: widening the bus

The three models in the recipes swap the single wire for 4 parallel streams. GLM and DeepSeek use mHC, with a \([4 \times 4096]\) state, or 16,384 numbers per token. Qwen uses the Gated Residual, with 4 branches of 2560. Each sublayer still reads a vector of \(d\) and writes \(d\), but the read and the write become learned mixtures of the 4 streams. That is why the table above says “of each of the 4 streams”. The full mechanism is in Hyper-connections. Qwen's N-gram table is also a writer to the residual. The code calls it PLE (in transformers, Per-Layer Embedding): it is a giant table of vectors (51.2 B parameters) in which bigrams and trigrams of the local context become indices via hashing, and at the layer with index 1 it adds its vector to the 4 branches (N-gram Memory).

In the recipe: every write becomes an all-reduce

In tensor parallel, the residual stream is replicated on every GPU, while the core of the sublayers is sliced. The reader matrices are cut along their output rows and run without communication. The writers are row-parallel: each GPU computes a share of the sum, and an all-reduce gathers the shares before adding them to the residual. Result: two collectives per block. In DeepSeek at TP=2 that is 43 wo_b all-reduces plus 43 from the MoE per decode step. The message size is \(d\) × 2 bytes per token: 8 KB with \(d = 4096\) in BF16. Details in Splitting the model.

Pre-normalization and RMSNorm: the volume control

Since the residual stream is a sum that only grows, the vector's magnitude changes a lot from block to block. If every sublayer read the raw vector, it would have to work with numbers of order 0.1 as well as of order 100. Normalization solves this. Before reading, the sublayer rescales the copy to a standard magnitude.

There are two places to put the norm. In the 2017 Transformer it sat after the sum, right on the road: \(\mathbf h' = \mathrm{Norm}(\mathbf h + F(\mathbf h))\). This is post-norm. It rescales the stream itself at every block and gets in the way of the gradient's direct line, and deep post-norm networks need a careful learning-rate warmup. Today's LLMs use pre-norm. The norm sits on the on-ramp, \(\mathbf h' = \mathbf h + F(\mathrm{Norm}(\mathbf h))\), and the road stays clean. The trade-off is that the stream grows unchecked along the stack. That is why there is a final norm before the lm_head.

The norm used by all three models is RMSNorm, a simplification of LayerNorm. Both were introduced in chapter 2; what matters here is their role as the block's on-ramp:

\[ \mathrm{RMSNorm}(\mathbf x) = \frac{\mathbf x}{\sqrt{\tfrac1d\sum_i x_i^2 + \varepsilon}} \odot \boldsymbol\gamma \qquad\qquad \mathrm{LayerNorm}(\mathbf x) = \frac{\mathbf x - \mu}{\sqrt{\sigma^2 + \varepsilon}} \odot \boldsymbol\gamma + \boldsymbol\beta \]
  • \(\sqrt{\tfrac1d\sum_i x_i^2}\): the RMS (root mean square), the “typical height” of a coordinate
  • \(\varepsilon\): a tiny number that prevents division by zero (rms_norm_eps)
  • \(\boldsymbol\gamma \in \mathbb R^d\): learned per-channel gain (the …norm.weight tensor)
  • \(\mu, \sigma^2\): mean and variance of the coordinates; \(\boldsymbol\beta\): learned bias (only LayerNorm has it)

RMSNorm neither subtracts the mean nor has a bias. It does less arithmetic and, in practice, works as well as LayerNorm. Its central property is scale invariance: if \(\varepsilon\) is negligible, \(\mathrm{RMSNorm}(\alpha\mathbf x) = \mathrm{RMSNorm}(\mathbf x)\) for any \(\alpha > 0\). The norm is an automatic volume control. Whether the signal arrives as a whisper or a shout, it always comes out at the same volume, and the gain \(\boldsymbol\gamma\) only equalizes channel by channel. Try it in the figure. Turn the input scale up and down, compare with LayerNorm and see when \(\varepsilon\) stops being negligible.

Notice that with the scale at 10⁻³ and ε = 10⁻², the output drops to near zero. The mean of the squares of the figure's vector at that scale is \(2.9\times10^{-6}\), so the denominator becomes \(\sqrt{2.9\times10^{-6} + 10^{-2}} \approx 0.1\) instead of \(\approx 1.7\times10^{-3}\), and the output shrinks about 58 times. Real values of ε are much smaller, so this only happens with nearly null vectors.

Pitfall: the name post_attention_layernorm

In a pre-norm model, post_attention_layernorm is not a post-norm. It is the norm that sits after attention and before the FFN, on the FFN's on-ramp. The name dates from the post-norm era and stuck. And if you port a model with a zero-centered gain (like Qwen) and forget the “1 +”, the norm multiplies everything by a \(\mathbf w\) close to zero. The model loads without errors and generates garbage.

In the recipe: norms stay in BF16

Qwen's experimental FP8-dense checkpoint converts the dense projections to FP8 (GDN, attention, Gated Residual, shared expert, lm_head). The EXCLUDE_MODULES list keeps in BF16, among others, the q_norm/k_norm, the linear_attn.norm and the hc_norms. Likewise, GLM's GLM53_DENSE_FP8 quantizes projections and never norms. Norms are tiny (in GLM, 8192 parameters per block), so there is nothing to save. And they are sensitive, because each gain multiplies an entire channel in every token.

The SwiGLU FFN: gate, up and down

Attention is the conversation between tokens. The FFN is individual reflection: it processes each token on its own, with the same matrices for every position, and mixes the vector's channels instead of mixing positions. The classic FFN is a two-layer MLP, \(W_2\,\phi(W_1\mathbf x)\), which opens the vector up to an intermediate width \(I\) (typically \(4d\)), applies a nonlinearity \(\phi\) and closes it back down to \(d\).

All three models use a variant with a multiplicative gate, from the GLU (gated linear unit) family, which you saw in the multiplicative gates of chapter 2: SwiGLU. Instead of one up projection, there are two. One of them goes through SiLU and becomes a gate that decides, neuron by neuron, how much of the other gets through:

\[ \mathrm{FFN}(\mathbf x) = W_{\text{down}}\Big(\mathrm{SiLU}\big(W_{\text{gate}}\,\mathbf x\big) \odot W_{\text{up}}\,\mathbf x\Big) \qquad \mathrm{SiLU}(z) = z\,\sigma(z) = \frac{z}{1+e^{-z}} \]
  • \(W_{\text{gate}}, W_{\text{up}} \in \mathbb R^{I\times d}\): the two up projections (gate_proj, up_proj)
  • \(W_{\text{down}} \in \mathbb R^{d\times I}\): the down projection (down_proj), the residual writer
  • \(I\) = intermediate_size (dense FFN) or moe_intermediate_size (each expert)
  • \(\odot\): element-wise product; \(\sigma\): sigmoid

That is three matrices instead of two, hence \(3\,d\,I\) parameters. To spend the same as a classic FFN with \(I = 4d\) (\(8d^2\)), a SwiGLU uses \(I \approx \tfrac83 d\). The models in the recipes choose other proportions. The dense FFN of GLM's layers 0–2 has \(I = 12{,}288 = 3d\): \(3 \times 4096 \times 12{,}288 = 150{,}994{,}944\) parameters per layer. Each GLM and DeepSeek expert is a SwiGLU \(4096 \to 2048 \to 4096\) (25,165,824 parameters). Each Qwen expert is \(2560 \to 640 \to 2560\) (4,915,200).

Analogy: the gatekeeper and the messenger

Each of the \(I\) intermediate neurons has a gatekeeper (the row of \(W_{\text{gate}}\)) and a messenger (the row of \(W_{\text{up}}\)). The gatekeeper looks at the token and decides whether to open the gate: SiLU gives almost 0 for negative scores and lets positive scores through almost whole. The messenger brings a signed value. What gets through is “message × gate opening”. Then the corresponding column of \(W_{\text{down}}\) says what to write into the residual stream when that neuron fires. A widely shared interpretation sees the FFN as a key–value memory: the up rows are the keys (patterns the neuron detects) and the down columns are the values (what it adds).

The figure does the math with numbers, on a toy FFN with \(d = 4\) and \(I = 6\). Follow the steps. Then turn on the split across two GPUs to see how tensor parallel cuts this computation.

Look at the gating step: neurons with a negative gate barely contribute, however large the up is. And look at the TP split. Cutting \(I\) in half requires no communication at all until the end, because each neuron depends only on its own gate and up rows. This is the column-parallel → row-parallel pair, with a single all-reduce, which you will see generalized in Splitting the model. In GLM at TP=2, each expert gets \(I_{\text{local}} = 1024\) per GPU. In Qwen, \(640/2 = 320\) is not a multiple of 128, the block size of the FP8 scales of the MTP experts. That is why the recipe uses expert parallel (whole experts per GPU) instead of cutting each expert.

How the engine runs SwiGLU

In the checkpoint, gate and up are two tensors. In vLLM they become one, the gate_up_proj, a MergedColumnParallelLinear layer with output \(2I\): one bigger GEMM instead of two small ones. The loader knows how to fill this two-slot tensor because each model declares a stacked parameters mapping. In DeepSeek, whose checkpoint calls gate/up/down w1/w3/w2:

stacked_params_mapping = [
    # (vLLM parameter, checkpoint name, slot)
    ("gate_up_proj", "w1", 0),   # gate
    ("gate_up_proj", "w3", 1),   # up
    ...
]
# forward: gate_up = x @ [W_gate; W_up]ᵀ  →  SiluAndMul (or SiluAndMulWithClamp)  →  down_proj

The SiluAndMul activation receives the \([2I]\) vector, cuts it in half and returns \(\mathrm{SiLU}(\text{half 1}) \odot \text{half 2}\). MoE kernels go further. GLM's E3 tier runs all of a layer's “fat” experts (the ones that get many tokens, typical of prefill) in three launches, while the thin experts go through the standard fused kernel (exl3_moe). The three launches are a gather of each expert's rows, the gate/up GEMM with SwiGLU applied in the epilogue (the result never goes back to memory before the gating) and the down GEMM with a scatter back to the tokens. This is kernel fusion, the subject of Kernels.

The limiter: swiglu_limit = 10

GLM and DeepSeek add a clamp to SwiGLU. Before the gating, the gate is capped from above and the up is clamped on both sides:

\[ \mathrm{act}(g, u) = \mathrm{SiLU}\big(\min(g,\,L)\big)\cdot \mathrm{clamp}(u,\,-L,\,L) \qquad\Longrightarrow\qquad |\mathrm{act}| \le \mathrm{SiLU}(L)\cdot L \approx 99.995 \text{ for } L = 10 \]
  • \(g = (W_{\text{gate}}\mathbf x)_i\), \(u = (W_{\text{up}}\mathbf x)_i\): the two scores of neuron \(i\)
  • \(L\) = swiglu_limit (10.0 in both models)
  • \(\mathrm{clamp}(u, -L, L) = \max(-L, \min(u, L))\)
  • \(\mathrm{SiLU}(10) = 10\,\sigma(10) \approx 9.9995\)

Why only from above on the gate? Because SiLU is already bounded from below: its minimum value is about −0.28 (near \(z \approx -1.28\)), and for very negative \(z\) it goes to zero. The danger is only on the positive side, where \(\mathrm{SiLU}(z) \approx z\) grows without bound. The up, on the other hand, enters the product linearly, so it needs clamping on both sides. With both clamps, each intermediate neuron returns at most ~100 in absolute value. Without them, a gate of 20 with an up of 20 would give 400, and nothing prevents larger values.

In the figure, the left panel shows the two paths with and without the clamp, and the right one shows the whole map of \(\mathrm{act}(g,u)\). The little dots are activations of a heavy-tailed neuron, and the ones that hit the clamp get pinned to the edge. Move \(L\).

Notice two things. For almost every sample the clamp does nothing, because they stay inside the frame. And when the clamp does act, the effect is large: it swaps 300 for 100. The limit is rare and decisive, and that is why you can't ignore it.

Why the limit exists and why the engine has to copy it

The main reason is that the limit is part of the model's math. The field is in the config.json of both checkpoints, and each one's reference implementation applies the limit. So whenever a neuron goes past 10, the “correct” model is the one with the clamp. An engine that forgets the limit produces different outputs precisely on the tokens where some activation is extreme. These tokens are few, but the error always repeats on them. A secondary reason is numerical. Bounded activations keep intermediate results in a safe range for kernels that compute in FP16 (maximum 65,504), which is the case of the EXL3 kernels, and for ~4-bit weights, whose rounding error can produce spikes. DeepSeek's reference computes the experts in FP32 “for stability”, and the quantization inventory reads the EXL3 limit as protection against FP16 overflow. That last point is the inventory authors' reading, not a claim made by the model itself.

The paths written in PyTorch in the overlay (the Python loop and the fat-expert tiers, exl3.py:855, 890 and 1056-1059) and E3, which does the clamp in the epilogue of the gate/up GEMM (exl3_fat_moe.cu:349-355), compute the reference formula, silu(gate.clamp(max=limit)) * up.clamp(min=-limit, max=limit). The kernels inherited from exllamav3 apply the limit to the already activated gate, \(\min(\mathrm{SiLU}(g), L)\cdot\mathrm{clamp}(u,\pm L)\): that is what the vendored copy hadamard_inner.cuh does, and the cooperative MoE declares that it follows the same semantics. The two forms coincide after rounding (the math is in the deep dive below). Why 10: it is the value the model was trained with, and the overlay needs it to keep numerical parity with the reference. Engineering consequence: the cooperative decode kernel for TP3 was specialized for this value. The runtime has ACTIVATION_LIMIT = 10.0, and any other limit comes back as activation_limit_unsupported and falls back to the standard EXL3 path. The contract test confirms this with a limit of 0.5, rejected by the eligibility screening.

The official reference does the same in FP32: up = clamp(up, -10, 10), gate = clamp(gate, max=10), silu(gate) * up. Why it matters: the recipe swaps the routed experts' backend for b12x (--moe-backend flashinfer_b12x), which reads this same value as gemm1_clamp_limit (b12x_moe.py:685, 749, 779), the limit applied to the output of the first GEMM (gate/up). If the two diverged, the numerics of the 256 experts would change without any visible error. And when the limit arrives as None, the code uses plain SiluAndMul, also silently.

Deep dive: “the same clamp” with two semantics

The clamp pattern (gate capped only from above, up on both sides) is the same as gpt-oss's. GLM's cooperative kernel even has a separate function for the gpt-oss variant (“gpt-oss clamped swiglu”), which also uses a 1.702 factor inside the sigmoid and a “+1” on the up path. GLM and DeepSeek use plain SiLU, without these extras, and GLM's cooperative kernel runs the generic path with a limit. More subtle: that path follows the semantics of exllamav3's activation kernels (its comment says so, and the vendored copy hadamard_inner.cuh confirms it), which applies the limit to the already activated gate, \(\min(\mathrm{SiLU}(g), L)\). The reference, the overlay's PyTorch paths and E3 do \(\mathrm{SiLU}(\min(g, L))\). The maximum difference between the two is \(L\,(1-\sigma(L)) \approx 4.5\times10^{-4}\) for \(L = 10\), below BF16's spacing near 10 (0.0625). In practice the two coincide after rounding. This is the kind of math worth doing every time a new kernel “implements the same thing”. The test that decides is numerical parity against the reference (chapter Measuring the damage).

Pitfall for overlay writers

Qwen3.8 has no swiglu_limit: the field doesn't exist in its config.json. One interpretation, which the sources don't confirm, is that the architecture's many sigmoid gates, in GDN, in attention, in the Gated Residual and in the shared expert, play a similar role of containing activations. Don't copy the clamp from one model to another. And when the model does have the limit, don't forget it in a custom kernel. It acts on few tokens, so smoke tests pass and only a KLD or parity measurement shows the problem.

A block's bookkeeping: parameters and FLOPs

With the pieces assembled, we can count. Suppose \(h\) query heads of dimension \(d_h\) and \(n_{kv}\) key/value heads. When \(n_{kv} < h\), the attention is a GQA (grouped-query attention): groups of \(h/n_{kv}\) query heads share the same K and the same V, which shrinks \(W_K\), \(W_V\) and the KV cache by the same proportion. Qwen's QSA uses 24 query heads for 2 KV heads. The MLA chapter goes deeper into this family of tricks. The count goes like this:

\[ P_{\text{attn}} = \underbrace{d\,h\,d_h}_{Q} + \underbrace{2\,d\,n_{kv}\,d_h}_{K,\,V} + \underbrace{h\,d_h\,d}_{O} \qquad P_{\text{FFN}} = 3\,d\,I \qquad P_{\text{block}} = P_{\text{attn}} + P_{\text{FFN}} + 2d \]
  • \(h, d_h, n_{kv}\): num_attention_heads, head_dim, num_key_value_heads
  • \(2d\): the gains of the two RMSNorms (negligible)
  • whole model: \(N\,P_{\text{block}} + V d\) (embedding) \(+\, V d\) (lm_head, if not tied) \(+\, d\)

In the classic Transformer (\(h\,d_h = d\), \(n_{kv} = h\), FFN with \(8d^2\)), attention has \(4d^2\) and the FFN \(8d^2\): two thirds of a block's parameters are in the FFN. That is why MoE, which swaps the FFN for experts, moves the total so much.

Where the FLOPs are

Each weight takes part in one multiplication and one addition per token: 2 FLOPs, the basis of FLOPs per token. So the weight matmuls cost \(\approx 2\,N_{\text{active}}\) FLOPs per token. Attention has an extra cost that doesn't come from weights. For a token that looks at \(n\) positions, \(QK^\top\) and the weighted sum of \(V\) cost \(2\,h\,d_h\,n\) each, or \(4\,h\,d_h\,n\) per layer. This term grows with the context, and the weight term doesn't:

\[ \text{FLOPs/token} \approx 2\,N_{\text{active}} + \sum_{\text{layers}} 4\,h\,d_h\,n \qquad\qquad n^\ast = \frac{P_{\text{block}}}{2\,h\,d_h} \;\overset{\text{classic}}{=}\; 6d \]
  • \(N_{\text{active}}\): active parameters per token (in MoE, only the chosen experts count)
  • \(n\): positions the token attends to (the context, in dense attention)
  • \(n^\ast\): context from which attention starts to cost more FLOPs than all of the block's weights

In a classic dense model with \(d = 4096\), attention starts to dominate at \(n^\ast = 6d \approx 24.6\) thousand tokens. At 1 million tokens it would cost ~40 times more than the weights. That is exactly why the attention layers of the three models are sparse, linear or compressed (Part III). The calculator below lets you build a block and see both kinds of bookkeeping. The scale compares attention and FFN in parameters, and the gauge underneath splits the FLOPs per token as the context grows.

Play with the Qwen preset. The scale tips almost entirely toward the FFN, because the 512 experts add up to 2.52 billion parameters in a layer whose attention has 49.8 million. But FLOPs per token count the active ones, and only 10 + 1 experts run. With a short context, projections and active experts dominate. Raise the context and the attention band swallows the rest already at around \(n^\ast \approx 8.6\) thousand tokens, well before the classic model, because the active part of the block (≈ 105 M) is small next to the attention width (24 × 256). Qwen's sparse attention exists to cut exactly that band (chapter Sparse attention).

In the recipe: the real split of GLM's FLOPs

The roofline analysis of the GLM recipe (docs/improve-prefill.md) estimates ≈ 19.5 B active parameters and ≈ 36 GFLOP per token, split like this: routed experts 16.9 GFLOP (47%), KDA layers 11.6 (33%), sparse MLA + indexer 3.3 (9%), shared expert 2.1 (6%), dense MLP 0.9 (2.5%) and lm_head 1.27 (3.5%). The exact count from the checkpoint's shapes gives ≈ 17.4 B active, with embedding and lm_head. The conventions differ, for example in how to count the cost of the KDA recurrence, which is not a weight matmul. In both counts, the routed experts are the largest slice, and that is why they are the ones that get 4 bits (EXL3). In prefill at 947 tok/s, the same table gives ≈ 34 TFLOPS summed over both nodes, ≈ 14% of the GB10's BF16 peak, which shows the wall is somewhere else (memory bandwidth to read the experts).

Why this matters: FLOPs × bytes

The same active-parameter bookkeeping gives the two quantities that rule inference. FLOPs per token ≈ 2 × active, and that limits prefill. Bytes read per step ≈ active × bits/8, and that limits decode, which reads every active weight to generate a single token (chapter Prefill, decode and the KV cache). Counting parameters per piece of the block is the first step of any recipe.

Dense or MoE: the same mold, different fillings

In an MoE, the block's FFN station becomes a hospital with triage. Instead of one big SwiGLU, there are \(E\) small SwiGLUs (the experts). A router picks \(k\) of them for each token, and a shared expert sees everyone. The block's interface doesn't change: the MoE FFN reads \(d\) and writes \(d\), and the rest of the block doesn't even notice the swap. The same goes for the token mixer. Full attention, sparse attention with an indexer, linear attention with a recurrent state, sliding window: they are different fillings for the same mold, which Part III takes apart.

The subway map below shows each model's real stack. Each station is a block: the color says the kind of mixer, the ring says the kind of FFN and the markers point to the layers that the recipes treat in a special way. Tap a station to see that block's parameters.

The map shows the mold repeating and the filling varying. Also notice the size asymmetry. In GLM, a dense layer (0–2) has ≈ 137.7 M of KDA attention + 151 M of FFN, almost half and half. An MoE layer with KDA has the same attention + 7.27 B of FFN: 98% of the block is experts, of which each token uses only ≈ 227.7 M (8 routed + 1 shared + router).

Initial dense layersintermediate_size: 12288 · first_k_dense_replace: 3

GLM's first three layers (0, 1, 2) use a dense SwiGLU FFN with \(I = 12{,}288\) instead of MoE. The other 42 in the trunk, plus the MTP layer, are MoE. A common reading, which here is interpretation, is that the first layers process general features, useful to every token, where routing helps little and destabilizes training. DeepSeek-V4 went another way: in layers 0–2 it kept MoE, but with fixed routing by token id (hash). In the GLM recipe, these three FFNs make up the dense group of GLM53_DENSE_FP8 (suffixes .mlp.gate_up_proj and .mlp.down_proj). They are in BF16 in the mirror, and the group quantizes them to per-channel FP8 at load time and runs them with Marlin W8A16. The deep dive is in Mixture-of-Experts.

Depthnum_hidden_layers: 45

There are 45 decoder blocks: 34 KDA and 11 sparse MLA, in the pattern KDA, KDA, KDA, MLA repeated 11 times, plus layer 44 (KDA). The MTP block takes index 45, outside this count. vLLM uses num_hidden_layers as the index of the first MTP layer, and DFlash2 numbers its layers starting at 45, which is why the dense FP8 group skips layers.N with N ≥ 45. Block 45 is used with SPEC_METHOD=mtp and is also edited by ABLIT. tools/pack_profile.py rejects a pack with hidden_size ≠ 4096 or num_hidden_layers ≠ 45.

Reading a checkpoint: tensor naming

Tensor names in a safetensors file are the module's path in the PyTorch tree, followed by .weight. With the block's mold in mind, the list stops being a tangle. The canonical naming of Hugging Face checkpoints, in the Llama/Qwen2 style, is this:

NameShapePiece of the block
model.embed_tokens.weight\([V, d]\)embedding
model.layers.{i}.input_layernorm.weight\([d]\)norm before attention
model.layers.{i}.self_attn.q_proj.weight\([h\,d_h,\ d]\)reader: queries
…self_attn.k_proj.weight / v_proj.weight\([n_{kv}\,d_h,\ d]\)readers: keys and values
…self_attn.o_proj.weight\([d,\ h\,d_h]\)attention writer
model.layers.{i}.post_attention_layernorm.weight\([d]\)norm before the FFN
…mlp.gate_proj.weight / up_proj.weight\([I,\ d]\)FFN readers
…mlp.down_proj.weight\([d,\ I]\)FFN writer
model.norm.weight\([d]\)final norm
lm_head.weight\([V, d]\)lm_head (absent if tied)
Pitfall: [output, input]

PyTorch's nn.Linear stores the weight as [out_features, in_features] and computes \(\mathbf y = \mathbf x W^\top\). That is why the down_proj of GLM's dense MLP shows up as [4096, 12288], and not \([12288, 4096]\). The first dimension is the side that receives the result, the second is the side that gets read. When a tensor's first dimension equals \(d\), it is a residual writer.

The three models in the recipes depart from this pattern, and each departure says something about the architecture. GLM and Qwen are multimodal, so the text tensors live under model.language_model.. GLM stores different projections in the KDA and MLA layers, and its EXL3 experts come in four tensors (trellis, suh, svh, mcg). Qwen has no input_layernorm, post_attention_layernorm or model.norm: the Gated Residual plays that role, and its q_proj is twice as tall because it carries the query and the output gate. DeepSeek uses short names in its reference's convention (embed, attn.wq_a, ffn.experts.E.w1, head), which vLLM renames at load time. Explore in the figure by choosing the model and the layer.

The engine needs to know all of this to load the weights. In DeepSeek, the overlay's mapper replaces layers. with model.layers., head.weight with lm_head.weight, embed.weight with embed_tokens.weight, .ffn.gate.bias with e_score_correction_bias and .shared_experts.w2 with .shared_experts.down_proj, and the stacked mapping joins w1/w3 into gate_up_proj. The recipes also use names as edit addresses: ABLIT picks the o_proj of specific layers, and Qwen's FP8-dense selects tensors by 19 name patterns and excludes others. The full story is in Checkpoints.

Pocket recipe: rebuilding the block of a new model

Before reading any code, list the per-layer suffixes. The model.safetensors.index.json index has the weight_map of every name, and grouping them reveals the mold and the variations (which layers have full attention, which are dense, where there are extras):

import json, re, collections
names = json.load(open("model.safetensors.index.json"))["weight_map"]
kinds = collections.defaultdict(set)
for n in names:
    m = re.search(r"layers\.(\d+)\.(.+)", n)
    if m:  # fold the experts into a single entry
        kinds[re.sub(r"experts\.\d+\.", "experts.E.", m.group(2))].add(int(m.group(1)))
for k, ls in sorted(kinds.items()):
    print(f"{k:64s} {len(ls):3d} layers  e.g.: {sorted(ls)[:4]}")

The shapes require reading each shard's header (a few KB, without downloading the weights). The recipe from scratch tutorial does this with byte-range reads.

Block checklist for a new model

Faced with an unfamiliar config.json, answer in this order. (1) \(d\), \(N\), \(V\) and whether the embedding is tied. (2) Pre-norm with RMSNorm? Which ε? Zero-centered gain? (3) Is the FFN a SwiGLU? Does it have swiglu_limit? What \(I\) in the dense layers and in the experts? (4) Which layers are dense and which are MoE? (5) Is the residual simple or widened (hc_mult, hc_count)? (6) Which tensor names does the engine expect, and which does the checkpoint bring? Every “different from the standard” answer is a patch candidate. The new-model tutorial does this exercise from start to finish.

There is one piece the block, on its own, barely has: the notion of order. The FFN processes each token in isolation. Without a mask, attention is permutation invariant: shuffle the tokens and each one gets exactly the same mixture, just in a different position. With the causal mask, the model starts to sense position, but only indirectly: the token at position \(t\) sees \(t+1\) tokens, the next one sees one more. Recurrent mixers, such as KDA, carry order by construction. The next chapter shows how models inject position explicitly (RoPE, partial RoPE and YaRN) and why these indirect signals are enough for GLM to live without RoPE in its MLA layers (NoPE).
