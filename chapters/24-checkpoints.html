Antes do primeiro kernel, toda receita responde a uma pergunta banal e traiçoeira: os bytes no disco são exatamente os bytes que foram medidos? Um checkpoint de fronteira chega como 11 a 206 arquivos, de ~98,6 GiB a ~164 GiB, mais meia dúzia de JSONs que dizem ao motor como interpretar cada byte. Um shard corrompido só derruba o vLLM a ~33% da carga; um nome de camada que não bate faz a MTP nascer sem quantização e morrer ~7 minutos depois; um newline invisível num arquivo de 40 caracteres impede o boot offline. Vamos desmontar um checkpoint como um relógio: o formato safetensors byte a byte, o índice que costura os shards, o carregador que transforma nomes em parâmetros fatiados por GPU, o quantization_config que dá significado aos bytes, e a disciplina de cache, revisões e hashes que torna um modelo servido reprodutível.

Anatomia de um repositório de modelo

Um modelo no Hugging Face Hub é um repositório git. JSONs e código ficam no git normal; os pesos gigantes ficam no Git LFS, que guarda no repositório só um ponteiro com o SHA-256 do conteúdo. “O checkpoint” é um commit: um conjunto fixo de arquivos que, juntos, descrevem o modelo.

Analogia: o kit de montagem

O config.json é a planta; os .safetensors são as caixas de peças, cada uma com etiqueta do conteúdo; o model.safetensors.index.json é o romaneio (qual peça está em qual caixa); o quantization_config é o manual de encaixe, sem o qual uma peça comprimida parece lixo; tokenizer e chat template são o manual de uso. Faltou uma caixa ou o romaneio mente, e a montagem trava no meio.

Na figura, cada arquivo de um repositório real acende o componente do vLLM que o consome. Os três repositórios têm o mesmo esqueleto, com peculiaridades: um sidecar de quantização legado no Qwen, um codificador Python no lugar do Jinja no DeepSeek, um template “só texto” que a receita GLM substitui.

Repare que o config.json tem vários leitores: architectures escolhe a classe no registro de modelos (Por dentro do vLLM), os hiperparâmetros dimensionam cada tensor e o quantization_config escolhe o método de quantização. O generation_config.json define a amostragem padrão quando o cliente não manda nada (Qwen: temperature 1.0, top_p 0.95, top_k 20); o DeepSeek o ignora com --generation-config vllm. E o chat template pode não servir: o do GLM é só texto, então a receita força o seu; o DeepSeek traz um codificador Python (encoding/encoding_dsv4.py) no lugar do Jinja: o entrypoint do container copia esse arquivo para dentro do vLLM, e o --tokenizer-mode deepseek_v4 o chama. Não é carregado como remote code. O --trust-remote-code é outra coisa, um requisito da arquitetura V4 (tabela abaixo).

O checkpoint do GLM usa nomes do SGLang (num_experts_per_tok, hc_mult…). Safetensors, shards e o índice

O formato antigo de pesos do PyTorch é o pickle, que serializa objetos Python: carregar pode executar código embutido no arquivo. Para pesos isso é risco e desperdício, porque um tensor é só números com tipo e forma. O safetensors é exatamente isso: 8 bytes (um u64 little-endian com o tamanho \(N\) do cabeçalho), \(N\) bytes de JSON (para cada tensor, dtype, shape e data_offsets, mais um __metadata__ opcional; o escritor do Qwen completa com espaços até múltiplo de 8) e o blob com os bytes crus, em ordem row-major.

\[ \text{bytes}(t) \;=\; e_t - b_t \;=\; \beta(\text{dtype}_t)\,\prod_{k} s_{t,k} \qquad\qquad \text{faixa no arquivo} = [\,8 + N + b_t,\;\; 8 + N + e_t\,) \]
  • \(b_t, e_t\): data_offsets do tensor \(t\), contados a partir do início do blob
  • \(\beta\): bytes por elemento (BF16 = 2, F32 = 4, F8_E4M3 = U8 = 1, I16 = 2); \(s_{t,k}\): as dimensões (escalar: shape [], produto 1)

Exemplo real: model.language_model.layers.3.self_attn.q_proj.weight do Qwen é BF16 [12288, 2560] (24 cabeças × 256 × 2, a metade extra é o gate de saída), logo \(12288 \times 2560 \times 2 = 62.914.560\) bytes, exatamente 60 MiB, e o elemento \((i, j)\) está no byte \(8 + N + b + 2(i \cdot 2560 + j)\). Percorra a figura.

Repare no passo 4: não existe dtype “FP4”. Um expert NVFP4 é U8 [640, 1280] com dois valores por byte (matriz lógica 640 × 2560); as treliças EXL3 do GLM são I16; as escalas E8M0 do DeepSeek chegam como float8_e8m0fnu. O arquivo diz “quantos bytes, com que forma”; o significado vem do quantization_config.

mmap, zero-copy e leituras parciais

Como o cabeçalho localiza cada tensor, o carregador pode fazer mmap: o SO mapeia o arquivo na memória virtual e só lê as páginas tocadas, e o tensor vira uma vista sobre elas (zero-copy). Pela rede, range reads HTTP buscam 8 bytes, depois o cabeçalho, depois só o tensor desejado. O Qwen usa carga lazy (tabela abaixo); build_ple_packed_table.py faz memmap dos 128 shards da PLE NVFP4 e grava uma matriz [total_rows, 90] (80 B de códigos + 10 B de escalas por linha) em blocos de \(2^{19}\) linhas; o dense_overlay.py do GLM lê cabeçalhos remotos sem baixar pesos. O lado físico (page cache em memória unificada, páginas de 64 KiB, O_DIRECT) fica para Memória unificada.

Sharding e o romaneio weight_map

Um arquivo único de 160 GB tornaria caro cada retry, cada hash e cada rsync, porque a unidade de falha seria o modelo inteiro. Range requests HTTP até retomam um arquivo gigante, mas verificar, sincronizar e carregar continuariam acontecendo em bloco. Por isso o checkpoint é dividido em shards, que dão granularidade para baixar, verificar e carregar por partes, e um JSON faz de romaneio: {"metadata": {"total_size": …}, "weight_map": {"tensor": "arquivo", …}}. No nvidia do Qwen, o weight_map lista 299.545 tensores em 11 arquivos (o último, model-fp8-mtp-ple.safetensors, tem 53,7 GB), total_size 132.639.846.394 B. O índice define o que é um snapshot completo: todo arquivo citado nos valores do weight_map existe.

Do nome ao parâmetro: o carregador do vLLM

Os nomes e formas do checkpoint quase nunca coincidem com os parâmetros do vLLM. O motor primeiro constrói o esqueleto do modelo: para cada camada, o método de quantização chama create_weights, que registra parâmetros vazios no formato do checkpoint, cada um com seu weight_loader. Depois, load_weights percorre os pares (nome, tensor) dos shards e, para cada um, renomeia, encaixa e fatia:

  1. Renomear. Um WeightsMapper traduz nomes: no DeepSeek, layers. → model.layers., head.weight → lm_head.weight, .attn.compressor. → .attn.mla_attn.compressor., .ffn.gate.bias → e_score_correction_bias (o viés sem perda auxiliar de Mixture-of-Experts).
  2. Encaixar. Matrizes com a mesma entrada viram um GEMM maior: gate_proj + up_proj → gate_up_proj. Uma tabela de stacked params diz o destino e o shard_id (a gaveta).
  3. Fatiar. O weight_loader recorta a parte do rank de tensor parallel: linhas numa camada column-parallel, colunas numa row-parallel. Com expert parallel, em vez de cortar, ele escolhe quais experts inteiros ficam no rank.
TP em 1 minuto (e o paradoxo do nome)

O PyTorch guarda cada linear como \(W \in \mathbb{R}^{\text{out} \times \text{in}}\): cada linha é um neurônio de saída, e a camada calcula \(Y = XW^\top\). O Megatron, que batizou os cortes, escreve \(Y = XA\) com \(A = W^\top\). Por isso column-parallel divide as colunas de \(A\), que são as linhas de \(W\): cada rank calcula uma fatia das saídas, sem comunicação. Row-parallel divide as linhas de \(A\), ou seja, as colunas de \(W\) (as entradas): cada rank multiplica a sua fatia da entrada, produz uma soma parcial, e um all-reduce soma as parciais. O par clássico da FFN é gate/up column-parallel seguido de down row-parallel, com um único all-reduce no fim.

\[ W = \begin{bmatrix} W^{(0)} \\ W^{(1)} \end{bmatrix} \;\Rightarrow\; Y = \big[\, X W^{(0)\top} \;\big|\; X W^{(1)\top} \,\big] \] \[ W = \big[\, W^{(0)} \;\big|\; W^{(1)} \,\big] \;\Rightarrow\; Y = X^{(0)} W^{(0)\top} + X^{(1)} W^{(1)\top} \]
  • 1ª linha, column-parallel: corta as linhas de \(W\); cada rank produz um pedaço de \(Y\), sem comunicação
  • 2ª linha, row-parallel: corta as colunas de \(W\); cada rank produz uma soma parcial, e o all-reduce soma
  • \(W^{(r)}\): a fatia do rank \(r\); \(X^{(r)}\): a fatia correspondente da entrada (já distribuída pela camada anterior)

Expert parallel (EP) é outra ideia: nenhum expert é cortado; cada rank guarda experts inteiros, e um expert_map traduz o índice global para o índice local (E4 vira o expert 0 do rank 1). O Qwen usa EP (--enable-expert-parallel, 256 dos 512 experts por GPU) e o GLM TP3 também (96 de 288); o DeepSeek roda TP=2 sem EP. Detalhes e custos de comunicação em Dividindo o modelo.

Numa camada empilhada column-parallel, cada rank não guarda “a metade de cima” da matriz fundida, e sim a sua fatia de cada gaveta:

\[ W^{(r)}_{\text{gate\_up}} \;=\; \begin{bmatrix} W_{\text{gate}}\big[\, r\tfrac{I}{P} : (r+1)\tfrac{I}{P},\; : \,\big] \\[4pt] W_{\text{up}}\big[\, r\tfrac{I}{P} : (r+1)\tfrac{I}{P},\; : \,\big] \end{bmatrix} \]
  • \(r\): rank; \(P\): tamanho do TP; \(I\): dimensão intermediária da FFN
  • assim \(\text{SiLU}(x W_\text{gate}^{(r)\top}) \odot x W_\text{up}^{(r)\top}\) multiplica linhas correspondentes sem comunicação

Exemplo (cálculo a partir do config do GLM, hidden 4096, moe_intermediate_size 2048): o shared expert funde gate_proj [2048, 4096] e up_proj [2048, 4096] em gate_up_proj [4096, 4096]; em TP2 cada rank guarda [2048, 4096], 1024 linhas de cada. Cortar a metade de cima deixaria o rank 0 só com gate. O GLM também funde q_a_proj + kv_a_proj_with_mqa (fused_qkv_a_proj), wk + weights_proj e seis projeções da atenção linear em in_proj_qkvbfg_a (6 lançamentos → 1), replicando as pequenas f_a/g_a; o DeepSeek funde w1/w3, attn.wq_a/attn.wkv e compressor.wkv/wgate.

Os experts roteados seguem a mesma lógica. Em TP puro (o DeepSeek), o weight_loader do FusedMoE fatia todos os experts entre os ranks: w1/w3 pela dimensão intermediária (column-parallel), w2 pela entrada (row-parallel). Com moe_intermediate_size 2048, cada rank guarda os 256 experts com 1024 de largura. Com EP, o mesmo loader primeiro consulta o expert_map: se o expert global não é do rank, o tensor é ignorado; se é, entra inteiro no índice local. O passo 5 da figura compara os dois.

Fatiar pesos quantizados: o peso e as escalas andam juntos

Em BF16, fatiar é um narrow() numa dimensão. Um peso quantizado é feito de dois ou mais tensores (códigos + escalas, ou treliça + sinais), e cada um precisa ser cortado na mesma fronteira lógica do peso, ou replicado quando não depende da dimensão cortada. Três regras decidem quais TPs são viáveis (na tabela, column-parallel corta as saídas e row-parallel, as entradas):

  1. Escala por bloco só se corta em fronteira de bloco. A largura local depois do split precisa ser múltipla do bloco. Senão, uma escala serviria aos dois ranks e teria de ser partida ao meio, o que não existe.
  2. Formato empacotado corta em bytes. Com 2 valores FP4 por byte, a fronteira precisa ser par em valores lógicos, e múltipla de 16 para não partir o bloco de escala do NVFP4.
  3. O que descreve a dimensão não cortada é replicado. Escalas globais (weight_scale_2, input_scale), marcadores e os sinais de Hadamard do lado que não foi dividido vão inteiros para os dois ranks.

Armadilha: substring não é segmento

O mapeamento empilhado do DeepSeek testa "w1" in name, e o drafter DSpark tem um markov_w1, que cairia por engano na gaveta 0 do gate_up_proj. O overlay Stage-C traz map_dspark_stacked_param_name, que compara segmentos do nome, ignora .experts. e é testado por test_dspark_stacked_mapping.py.

Drafters embutidos moram num prefixo próprio. O alvo DeepSeek pula tudo que começa com mtp.; o drafter carrega só mtp.<estágio>.*, renomeando para model.layers.<num_hidden_layers + estágio>.* (camadas virtuais 43–45), fatia o attn_sink pelas cabeças do rank e mapeia .scale para .weight_scale (experts FP4) ou .weight_scale_inv (FP8), conforme o expert_dtype.

Por que uma escala E8M0 não pode ser “convertida”

Uma escala E8M0 é só um expoente: o byte \(e\) vale \(2^{e-127}\). O parâmetro do MoE é uint8; um copy_() faria conversão numérica, e o byte 120 (\(2^{-7} = 0{,}0078125\)) viraria o inteiro 0. O carregador faz view(torch.uint8): reinterpreta os bits e guarda 120.

Por fim, process_weights_after_loading reempacota para o layout do kernel (por exemplo, o do Marlin, um kernel de GEMM que multiplica pesos de 4 ou 8 bits desquantizando-os em registradores e exige os pesos reordenados em tiles; ver Kernels), pré-calcula tabelas e às vezes desquantiza (o GLM passa projeções MLA de um checkpoint FP8 para BF16).

quantization_config: o manual de instruções dos bytes

Um tensor U8 [640, 1280] não diz se é FP4 empacotado ou INT8. Quem diz é o quantization_config. Seu quant_method escolhe a classe QuantizationConfig dona do checkpoint (exl3 no GLM, modelopt no Qwen, fp8 no DeepSeek), que responde camada a camada get_quant_method(layer, prefix): qual método cria, carrega e executa aquele peso.

O DeepSeek é o caso mais enxuto e mostra que o quantization_config nem sempre conta a história toda. Ele declara quant_method: fp8, fmt: e4m3, weight_block_size: [128, 128], scale_fmt: ue8m0 (escalas que são potências de 2) e activation_scheme: dynamic, o que vale para os lineares densos. Os experts roteados são outra coisa, e quem avisa é um campo fora dele: expert_dtype: fp4, ou seja, MXFP4 (e2m1 com uma escala E8M0 por 32 valores). É esse campo que faz o mapper mandar experts.*.w[123].scale para weight_scale (o nome que o Mxfp4MoEMethod registra) e todos os outros .scale para weight_scale_inv (as escalas de bloco do FP8).

Remendar a config sem tocar no cache

Editar o config.json do cache é tentador e errado: ele é um blob endereçado pelo hash (próxima seção), compartilhado entre revisões e copiado para o worker; editá-lo quebra a verificação e torna impossível dizer o que foi servido. Sobram duas ferramentas limpas.

1. --hf-overrides: um JSON mesclado no config em memória (ModelConfig._apply_dict_overrides), que só desce em chaves que são sub-configs. Num modelo multimodal, o pai embrulha um text_config (o LLM) e um vision_config; no qwen4_exp o pai também expõe rope_parameters como dicionário simples, então {"rope_parameters": …} na raiz caía no pai e nunca chegava ao text_config: todo run “1M” antigo serviu RoPE não escalado. A correção é um único payload aninhado:

--hf-overrides '{"text_config": {"ple_embedding_dtype": "float8_e4m3fn",
                                 "rope_parameters": {"rope_type": "yarn", "factor": 4.0,
                                                     "original_max_position_embeddings": 262144}}}'
# rope_parameters só com YARN_ENABLE=true (padrão atual: false, MAX_MODEL_LEN 262144)

O erro é silencioso: o servidor sobe e responde; só um teste de contexto longo, ou a leitura do valor efetivo, revela o problema (o README da receita ainda mostra a forma bugada num bloco antigo). O mesmo mecanismo declara 66 cabeças no TP3 do GLM (TP=3 e TP=4) e liga o YaRN de Posição.

2. Detectar o que falta e montar configs corrigidos por cima. O ple_layer.py corrigido do Qwen escolhe o método da PLE por text_config.ple_embedding_dtype, que o nvidia não declara. detect_ple_dtype.py procura o grupo cujo targets contém ple_embedding.ngram_embedding e traduz num_bits 8 → float8_e4m3fn, 4 → nvfp4; o resultado entra no override aninhado. Já a MTP: o vLLM a constrói em índice absoluto, continuando a pilha (num_hidden_layers = 48 → mtp.layers.48), mas o nvidia grava metadados só para mtp.layers.0.*. patch_checkpoint_config.py escreve config_patched.json e hf_quant_config_patched.json, montados por bind-mount sobre o snapshot dentro do container, e tem um modo preflight que falha em segundos.

Por que o bloco 128 não é adivinhado

FP8_BLOCK_SCALES só funciona porque patch_modelopt_fp8_block_moe.py ensina o despachante a construir um Fp8MoEMethod com weight_block_size = [g, g], lendo g do group_size. Ele recusa adivinhar: um bloco errado aplica escalas desalinhadas em silêncio, e o sintoma seria aceitação de rascunho quase aleatória. Com o bloco certo: MTP=3 a 52,1 tok/s, aceitação 72,8% (89/74,5/60% por posição).

O cache do Hugging Face e o modo offline

O huggingface_hub guarda downloads num layout feito para deduplicar e fixar revisões:

$HF_HOME/hub/models--nvidia--Qwen3.8-Flash-Next-NVFP4/
├── blobs/            conteúdo real; nome = hash (SHA-256 p/ LFS, SHA-1 git p/ pequenos)
├── refs/main         texto: o commit para onde "main" apontava
└── snapshots/
    └── fc694b54…/    um diretório por commit, com symlinks relativos
        ├── config.json -> ../../blobs/…
        └── model-00001-of-00010.safetensors -> ../../blobs/…

Cada blob guarda o conteúdo uma vez; cada snapshot é uma árvore de symlinks que monta a visão de um commit; refs/main é um texto com o hash. Um commit que troca só o config.json ganha um único blob novo; os shards de vários GB continuam nos mesmos blobs (é o cenário ilustrativo da figura, inspirado na fc694b54, que renomeou um rótulo no config). O nome da pasta, models--<org>--<repo>, é o que o GLM expõe como MODEL_CACHE_NAME.

As três receitas servem com HF_HUB_OFFLINE=1 e TRANSFORMERS_OFFLINE=1: no container nada toca a rede. Isso dá reprodutibilidade (o que foi verificado é o que roda), evita surpresas (no DeepSeek, uma revisão ausente do cache viraria um download silencioso de ~157 GiB (≈169 GB; o aviso do validate-dspark-config.sh ainda cita ~155 GB, número da lane 0731) no boot) e permite montar o cache somente leitura no worker. Os downloads acontecem antes, em scripts que forçam o modo online.

No modo offline, pedir main é ler refs/main e abrir snapshots/<hash>/. A armadilha: o huggingface_hub 1.28 da imagem day-0 do Qwen lê o arquivo sem .strip(). Quem grava echo $SHA > refs/main deixa um \n; a biblioteca procura snapshots/<sha>\n e o vLLM morre com um “repo not found” que não cita o newline (issue #36). A receita compara os bytes de verdade ($(cat …) esconderia o newline) e reescreve com printf só se diferirem. O prepare do DeepSeek grava o ref com newline, mas serve com --revision explícito na sua imagem: o comportamento depende da versão da biblioteca, então escreva sem newline e teste o boot offline.

Hard-link no blob, não no symlink

Um derivado que reaproveita shards não os copia. Mas os arquivos do snapshot são symlinks relativos: um hard-link do symlink, em outro repositório, apontaria para um caminho que não existe lá. O conversor FP8-dense resolve com os.path.realpath e faz o hard-link para o blob: mesmo inode, zero bytes (symlink absoluto como plano B). O GLM, no rsync, repara um link pendurado do drafter copiando com rsync -L.

Na receita: quando o próprio blob é um link

A versão TensorFold da receita GLM copia para o worker só o que a revisão usa: lê para onde apontam os symlinks de snapshots/<rev>/, transfere esses blobs e depois recria os links do snapshot e o refs/main, o mesmo layout que o huggingface_hub mantém. A issue #15 achou o furo dessa conta: com o backend Xet, um blob de models--…/blobs/ pode ser, ele mesmo, um link para um blobs/ na raiz do cache, fora da pasta copiada, e esses arquivos não chegavam ao worker. O remédio é o mesmo que a lane vLLM usa para o drafter, seguir os links: rsync -a -L --partial copia o conteúdo apontado por cada link e retoma se a cópia cair. Dois detalhes fecham o modo offline. Baixar por hash de commit não grava refs/main, então o script escreve o pin lá com printf %s (sem newline), só quando não há outro. E o servidor nem consulta o refs/main: o start.sh passa ao tensorfold serve o caminho do snapshot, depois de conferir que o config.json dele existe nos dois Sparks. Os containers rodam com HF_HUB_OFFLINE=1 e nenhum token entra neles.

Revisões fixas, espelhos e repositórios restritos

Em git, main é um ponteiro móvel; um hash de commit (40 hex) é imutável. Pinar a revisão é servir por hash. As receitas tratam isso como regra: no DeepSeek, a issue #19 introduziu o pin (prepare e serve com --revision) para que uma mudança em main, nos pesos ou no codificador, nunca passe despercebida; no GLM, a justificativa do pin do drafter é que “um main mutável do Hub já trocou os pesos”. Com --trust-remote-code, pinar também é segurança, pois seguir main aceitaria qualquer código novo (interpretação nossa, decorrente do mesmo mecanismo). Um espelho byte-idêntico num repositório seu protege até contra o upstream sumir.

As três receitas escolheram estratégias diferentes, e vale comparar. O pina um commit e o passa ao prepare e ao serve (--revision). O vai além: espelho byte-idêntico, pin do alvo e do drafter e presets que fecham todos os pins de uma vez (no retrato 94ae731; desde 2026-10-04, commit 98cf18f, o padrão é o pacote próprio do laboratório, Mia-AiLab/GLM-5.3-Flash-EXL3-4bpw-TensorFold, e o fallback aponta para o mesmo repositório). O é a exceção: serve o snapshot de refs/main, sem hash fixo, e compensa com duas redes de segurança, a completude (resolve_snapshot.py) e o manifest de hashes salvo com repositório e revisão (verify-weights.py --save-manifest). O custo de seguir main apareceu de verdade: em 2026-09-05 o commit fc694b54 da nvidia renomeou o rótulo dos experts da MTP de FP8_BLOCK_SCALES para FP8_PB_WO no config.json (mas não no sidecar), e a receita teve de aprender o rótulo novo e patchear os dois arquivos. É exatamente o tipo de mudança que um pin transforma de surpresa em decisão.

No DeepSeek, DSPARK_REVISION não definido usa o pin, e definido vazio segue o tip de main (o padrão de shell ${VAR-padrão} × ${VAR:-padrão}): uma escolha consciente entre reprodutibilidade e atualização. A revisão também explica o runtime: o Vision-Exp tem num_nextn_predict_layers = 3, o que força k = 6 no rascunho (DFlash2 e DSpark); o 0731 tinha 1 e usava k = 5, com aceitação 0,93/0,75/0,66/0,58/0,47 por posição, e foi nele que se capturou a direção de ablação. Integridade: tamanho não é prova

Um checkpoint pode estar errado de quatro jeitos: um shard falta, está truncado, tem bytes trocados com tamanho parecido, ou um JSON foi reescrito com o mesmo tamanho. Cada detector enxerga só alguns. O caso que motivou o hash no Qwen (issue #30): um shard corrompido no meio do download, com tamanho errado por algumas centenas de MB num arquivo de vários GB, passou pela checagem antiga, e o motor só morreu a ~33% da carga com safe_open acusando incomplete metadata, file not fully covered.

O detector definitivo é o hash de conteúdo. O SHA-256 reduz qualquer arquivo a 256 bits com efeito avalanche: trocar um bit muda, em média, metade da saída. O Hub publica os hashes esperados em /api/models/{repo}/tree/{rev}?recursive=true: o lfs.oid (SHA-256, arquivos LFS) e o oid (o SHA-1 de blob git, arquivos pequenos):

\[ \text{oid}_{\text{git}}(c) = \mathrm{SHA1}\big(\,\texttt{blob}\;\Vert\;\text{espaço}\;\Vert\;|c|_{10}\;\Vert\;\text{NUL}\;\Vert\;c\,\big) \qquad\qquad \text{oid}_{\text{LFS}}(c) = \mathrm{SHA256}(c) \]
  • \(c\): conteúdo do arquivo; \(|c|_{10}\): tamanho em bytes, em decimal; \(\Vert\): concatenação; NUL: o byte zero

O verify-weights.py do Qwen usa só a biblioteca padrão (roda em qualquer nó), faz streaming em blocos de 1 MiB com 8 threads e separa três respostas: 0 (confere), 1 (pesos com problema) e 2 (a ferramenta falhou), porque “pesos corrompidos” e “tente de novo” pedem ações diferentes. Tempo medido: ~1 min para 135 GB a 2,4 GiB/s.

Na receita: “o marcador é uma alegação, não uma prova”

Para não varrer 164 GiB a cada boot, o GLM grava no worker .glm53-exl3-synced com a revisão. O marcador só é escrito depois que a sonda passa (cada arquivo do índice precisa se desreferenciar num arquivo regular do tamanho exato do head, via find -L … -printf '%s %p'), só é honrado se a sonda passar de novo e é apagado antes de qualquer rsync que mude arquivos: um sync interrompido nunca vira “completo”.

Na receita: o motor lê antes, a lista confere depois

A versão TensorFold verifica em duas camadas. Antes de copiar qualquer coisa, roda tensorfold info sobre o snapshot do head, num container da própria imagem e offline: o worker só recebe um checkpoint que o motor consegue ler (a receita filtra do relatório o aviso EXL3 support is experimental, porque serve EXL3 de propósito). Depois compara head e worker por uma lista caminho tamanho de cada arquivo do snapshot, com links seguidos (find -L . -type f -printf '%P %s'): lista igual pula a cópia; lista diferente depois da cópia aborta o preparo. Pela figura acima, essa lista pega arquivo faltando e truncado, mas não bytes trocados com o mesmo tamanho, e o drafter da seção anterior mostrou que “mesmo tamanho, outro conteúdo” existe de verdade. O que cobre esse buraco é só o trânsito: o rsync confere cada arquivo que envia com um checksum do arquivo inteiro, mas um arquivo que já está no worker com o mesmo tamanho é pulado sem ser relido, pela lista ou pelo teste rápido de tamanho e data do próprio rsync (interpretação nossa; a receita não compara SHA-256 contra o Hub, como faz o verify-weights.py do Qwen).

O marcador também muda de natureza. É uma linha com modelo@revisão, drafter@revisão, a imagem nos dois Sparks, o hash dos patches, o worker e o modo dos pesos, e o start.sh refaz o preparo sempre que a linha atual difere da gravada. Interpretação a partir do código: ele invalida por configuração, não por conteúdo. Com a linha igual, o boot só confere que a imagem e o config.json do snapshot existem nos dois lados, sem repetir a sonda de tamanhos que a lane vLLM roda antes de honrar o seu marcador.

Checkpoints derivados e a viagem até o worker

Às vezes o checkpoint certo para o seu hardware não existe e você o constrói. Um checkpoint derivado nasce localmente, de forma determinística, de entradas pinadas, e é verificado antes de servir. Regras de ouro: link em vez de cópia para o que não muda, escrita atômica, metadados que expliquem a origem e teste da resolução de quantização antes do boot.

Qwen: o híbrido FP8-dense

Em decode batch 1, os densos BF16 (GDN, atenção, hyper-connections, shared experts, lm_head) são ~6,9 dos ~9,2 GiB lidos por passo. O conversor passa 591 lineares para FP8 E4M3 com escala por canal de saída, sem calibração (a ativação é quantizada dinamicamente por token):

\[ s_i = \frac{\max_j |W_{ij}|}{448}\;(\geq 10^{-12}), \qquad q_{ij} = \mathrm{E4M3}\!\left(\mathrm{clamp}\!\left(\tfrac{W_{ij}}{s_i},\,-448,\,448\right)\right) \]
  • \(i\): linha (canal de saída); \(448\): maior finito do E4M3; grava weight F8_E4M3 + weight_scale F32 [out]

Por canal e não em blocos de 128 pelas regras de corte que vimos no carregador (posto 320 das hyper-connections, shared expert com 320 linhas por rank, escalas de bloco no ParallelLMHead). O conversor é uma aula de safetensors: um escritor próprio grava o cabeçalho primeiro (tamanhos conhecidos) e faz seek para cada pedaço; processa blocos de 16 MiB de linhas; grava em .tmp, faz fsync e renomeia atomicamente. Resultado: 202 shards hard-linkados, 4 reescritos (11,8 GB), ~2 min em CPU. As verificações vêm antes de qualquer GPU: RMSE relativo 0,0240/0,0262/0,0268 (mín/mediana/máx), cosseno ≥ 0,9996, alarme acima de 0,06 (Medindo o estrago); 30/30 prefixos resolvidos para o método esperado; e o log esperado Selected CutlassFP8ScaledMMLinearKernel for ModelOptFp8PcPtLinearMethod. O ganho previsto (~5,7 GiB/passo, ~85–90 tok/s) é analítico: nunca foi medido em GPU.

GLM: o overlay denso e o drafter 6 bpw

O preset dense-h3 não reescreve nada: dense_overlay.py cria um diretório com symlinks relativos para todo o pack TR3 (resolvem dentro do container e sobrevivem a rsync -a) e acrescenta um safetensors com os lineares não-expert em EXL3, lidos por range reads de turboderp/GLM-5.3-Flash-exl3 (branch 4.05bpw, commit 2a30229e, ~5,3 GB), com índice reescrito e non_routed_exl3 no config. É um transplante: o doador guarda q/k/v fundidos em qkv_proj (fatiados por bloco), gate/up viram gavetas de gate_up_proj, e in_proj_qkvbfg_a mantém as gavetas 3–5 em BF16. O drafter DFlash2 é quantizado a 6 bpw (fork exllamav3@63b32f0, sem calibração, ~25 min no GB10, K/V em BF16) e empacotado com cópias byte-idênticas dos tensores BF16 e prefixos relativos que o runtime desloca para as camadas 45..49.

Pins: config TR3 SHA-256 4f5341e0…, índice 2f64d21c…, overlay 1a1b0793…, drafter local/GLM-5.3-Flash-DFlash2-EXL3-6bpw@27d19286…; build divergente é recusado. Opt-in, só TP2, sem A/B contra o padrão. O valor escolhido é GLM53_DENSE_EXL3_PREFILL_BF16=kda_in,shared_down,mla_qkv_a,shared_gate_up,kda_o,mla_q_b: esses seis grupos H3 guardam uma cópia BF16 reconstruída do peso EXL3 (Hadamards já aplicados) e, quando o lote tem mais de 144 linhas (prefill), rodam um GEMM BF16 comum em vez de decodificar a treliça a cada chamada. Custa 2 bytes por peso por rank a mais.

Na receita: derivar na carga, não no disco

A versão TensorFold ataca o mesmo problema (os ~9,7 GiB por Spark de pesos BF16 fora dos experts roteados, relidos a cada passo de decode) sem criar checkpoint nenhum. O carregador da família GLM pede cada tensor pelo nome do checkpoint e, com DENSE=q4 (o padrão), faz quantização na carga: grupos afins de 64 valores em 4 bits, com a faixa escolhida entre 16 recortes (de 1,0 a 0,55 do mín/máx) pelo menor erro quadrático e escala e bias em BF16, ~4,5 bits efetivos por peso (cálculo da pesquisa). A cabeça vai para FP8, o kv_b fica em BF16 e matrizes cuja entrada não é múltipla de 64 caem para FP8. DENSE=fp8 usa uma escala por linha e bloco de 128 colunas; DENSE=bf16 é, nas palavras do config.sh, the checkpoint as it is. Medido com DFlash2, um boot cada, q4 contra fp8: prosa 38,9 → 44,4 tok/s, código 44,2 → 48,7, prefill ~1.090 → ~1.260 tok/s, com GSM8K 98,0% e HumanEval 95,1% nos dois (bf16: 97,2 / 96,3). É um A/B do config.sh, feito durante o desenvolvimento: não se compara aos números de vitrine da receita, medidos com o sparkDash e os clocks da GPU limitados a 2.200 MHz.

O trade-off com o FP8-dense do Qwen é nítido. Na carga, não há arquivo novo para construir, pinar, hashear e copiar: o worker recebe o checkpoint publicado, e a transformação fica versionada pelo código dos patches (o hash da imagem) mais um knob. Em troca, os bytes servidos não existem em disco e nenhum SHA-256 os nomeia; a conversão se repete a cada boot e, sem o equivalente ao verificador offline do Qwen, a qualidade só aparece medindo o servidor (interpretação). A issue #18 é o exemplo: com q4, prompts curtos de código em francês perdem o fim de turno e correm até max_tokens em 12 de 48 respostas (1 de 48 com bf16 ou fp8), algo que GSM8K e HumanEval, em inglês, não mostravam.

A viagem até o worker: rsync ou NFS

rsync dá ao worker uma cópia local (~126 GiB no Qwen, ~164 GiB no GLM): disco em dobro, mas nós desacoplados e cold start mais rápido. Com NFS, o head exporta o cache somente leitura e o worker o monta: zero disco extra e troca fácil de checkpoint, mas o head precisa ficar de pé e cada cold start relê tudo pelo cabo. “O cabo” é o link direto de 200 Gb/s da ConnectX-7 (CX7), a placa de rede que liga os dois Sparks pela porta QSFP, a mesma por onde passa o NCCL. O servidor é um container Alpine privilegiado com o nfsd do kernel, só NFSv4; o worker monta com nfsvers=4.2,ro,nconnect=8,rsize=wsize=1048576,hard,timeo=600 (“nconnect=8 é o que faz a carga a frio usar o cabo”). Os scripts recusam 10.0.0.* e 127.*: pela rede de gerência, 164 GiB viram “um trabalho de madrugada” (rede em NCCL e RDMA).

Pesos no workerWORKER_WEIGHTS=copy · nfs

Com copy (o padrão), o worker ganha a própria cópia, ~166 GiB, pelo link entre os Sparks: o prepare.sh confere antes o disco livre do worker (o tamanho do snapshot mais 5 GB) e copia só os blobs da revisão com rsync -a -L --partial. Com nfs, nada é copiado: o head exporta o cache somente leitura para o endereço CX7 do worker (uma vez, com root no head), e o prepare.sh cria no worker, sem sudo, um volume Docker do tipo NFS com as mesmas opções de cliente vistas acima e confere que o worker enxerga cada arquivo dos dois snapshots com o tamanho do head. A receita relata carga tão rápida quanto do disco local (os dois ranks no ar em ~2,2 min); o preço é o de todo NFS, o head precisa ficar de pé. O orçamento de memória dessa lane está em Memória unificada; o motor, em Um motor exato.

Nas receitas: o checklist dos pesos

As três receitas percorrem a mesma linha de metrô, cada uma com suas estações extras, e a versão TensorFold da GLM (, montada passo a passo em Trocando o motor) mostra que trocar o motor não muda a linha: o mesmo checkpoint passa pelas mesmas sete estações, com outras respostas em cada uma. Escolha uma receita e acompanhe o trem: cada estação mostra o valor real usado.

O padrão se repete: tudo que pode falhar tarde é verificado cedo (completude antes do rsync, hash antes da carga, preflight da MTP antes de 7 minutos de boot, cabeçalhos antes de parar um par saudável), e nada no cache é editado (correções por override ou por configs montados por cima; derivados em repositórios locais próprios; o que é servido sempre tem um hash que o nomeia).

  1. Leia o repositório como o motor lê: config.json com sub-configs e quantization_config, sidecars, cabeçalhos safetensors; anote o formato de cada parte e os nomes das escalas.
  2. Pine tudo por hash (alvo, drafter, auxiliares), considere um espelho e baixe fora do serviço, com timeouts generosos. Se escolher seguir main, como o Qwen, exija completude e salve um manifest com repositório e revisão, para que uma mudança como a da fc694b54 seja detectada, não herdada.
  3. Confira se o TP que você quer corta cada formato numa fronteira de bloco (16, 32, 128, tiles de 16); se não cortar, use EP, replique ou troque a granularidade da escala.
  4. Sirva offline e escreva refs com printf.
  5. Verifique em camadas: contagem, weight_map, tamanho desreferenciado, hash contra o manifest.
  6. Descubra o que o loader não sabe (índices absolutos, aliases, dtypes não declarados, rótulos novos) e corrija sem tocar no cache, com um preflight que falhe em segundos.
  7. Derive com links e verifique offline; escolha rsync ou NFS pela sua operação.
