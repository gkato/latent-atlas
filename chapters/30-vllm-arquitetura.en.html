You type vllm serve on one node, the same line on the other, and a few minutes later two machines answer as if they were one, streaming, to several clients at once. Between the command and the first token lives a small operating system: processes that talk through shared memory, a scheduler that decides at every step who moves forward (≈ 50–110 ms per step in the recipes' decode: Qwen measures ≈ 52–61 ms with one client; the GLM and DeepSeek values are our own math, tok/s ÷ tokens per step), an executor that spreads the work across the GPUs, and several extension points where you plug in a quantization format, an attention backend or an entire model. When a recipe talks about an “overlay on gpu_model_runner.py”, the “gb10_hybrid_nvfp4 plugin” or “VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS=1800”, it is tinkering with one of these gears. Here we take the engine apart piece by piece, so you know where each tweak touches and why.

What an inference engine does

Mathematically, an LLM is a function: it takes a sequence of tokens and returns, for the last position, a distribution over the vocabulary (Generation and sampling). Twenty lines of PyTorch are enough to generate text: tokenize, run the prefill, sample, run a decode step and repeat until the end. That is a generation loop, not a service. An inference engine exists because that loop, once put in front of real users, hits five walls:

  1. The GPU sits idle. In decode, each step reads all the active weights to produce one token per sequence (Prefill, decode and KV). Putting \(B\) sequences in the same step divides that read by \(B\).
  2. Memory vanishes. The KV cache grows with every token, and reserving the maximum context per client wastes almost all of it. You have to allocate on demand (PagedAttention and KV).
  3. The CPU gets in the way. Tokenizing, detokenizing, applying templates and advancing grammars is CPU work in Python. In the same loop that feeds the GPU, the GPU waits.
  4. One GPU is not enough. The recipes' models require two nodes executing the same step in lockstep.
  5. Every model is its own case. Without extension points for formats, backends and architectures, every new model becomes a fork.

The first wall comes down to simple arithmetic. Model the time of a decode step as a fixed cost (reading the weights) plus a cost per sequence in the batch:

\[ t_{\text{step}}(B) \approx t_{\text{weights}} + B\,t_{\text{seq}} \qquad\qquad \text{throughput}(B) = \frac{B}{t_{\text{step}}(B)}\ \text{tokens/s} \]
  • \(B\): sequences in the same step (batch size)
  • \(t_{\text{weights}}\): time to read the active weights once (limited by memory bandwidth)
  • \(t_{\text{seq}}\): extra cost of each sequence (its own KV, activations, sampling)

As long as \(t_{\text{weights}} \gg B\,t_{\text{seq}}\), doubling the batch nearly doubles throughput. The figure shows this live. Token-clients arrive at the queue on the left, the GPU in the middle “reads the weight matrix” at every step (the sweep across the grid) and each seated passenger gets one token per step. Compare the naive loop, which serves one client to the end before taking the next, with an engine's continuous batching, which refills seats at every step.

Watch the “tokens per read” counter. In the naive loop it stays pinned at 1. In the engine it climbs to the number of seats, and the same sweep yields eight tokens. That is why every recipe chooses how many sequences fit per step (Scheduler and batching), and why speculative decoding works: it puts several tokens of one sequence into the same read.

Analogy: a restaurant with an industrial kitchen

The dining room (API server) takes orders, translates the menu (tokenizes) and serves in slices (streaming). The expediter (EngineCore) decides each round what goes on the griddle. The storeroom (KV manager) lends out shelves. The kitchen (one worker per GPU) cooks the same recipe in two units linked by intercom (NCCL, NVIDIA's library that sums and exchanges tensors between GPUs). If the head waiter also cooked, the griddle would cool down every time a customer walked in.

The five walls turn into six jobs, and each one has a vLLM component and chapters of its own in this trail:

Not every engine is vLLM

The five walls hold for any engine. So does the split into six tasks, but how each one is designed changes from engine to engine. The GLM recipe now has a second version that serves the same checkpoint, on the same two Sparks, with a different engine: TensorFold v0.6.0 plus 53 patches from the recipe (An exact engine, Swapping the engine). It is a per-family engine. It has no generic model registry, no quantization plugins and no paged KV manager, because each model family writes its own forward, its own cache and its own draft verification. The bet trades breadth for a tailored fit, and this recipe's numbers suggest it pays off: in prose, with one request (sparkDash, temperature 0), the vLLM recipe logged 36.1 tok/s and the TensorFold one measures 60.4 tok/s, the latter with the GPU clocks capped at 2,200 MHz. These are measurements from different dates and configurations, not a controlled A/B: read them as an order of magnitude. Throughout the chapter, the boxes with the badge show where this other design touches each of vLLM's gears.

vLLM V1 as processes: who lives where

vLLM's “V1 engine” tackles the third wall with an operating-systems idea: isolate in processes whatever competes for CPU. In Python, a thread busy with JSON holds the interpreter (the GIL), so the front end, the scheduling loop and each GPU get processes of their own. From the outside in:

API server
HTTP process (FastAPI) with the OpenAI endpoints. It renders the template and tokenizes; on the way back, the output processor detokenizes, applies stop strings and runs the reasoning and tool parsers.
AsyncLLM
The engine's asynchronous facade, inside the API process. Its EngineCoreClient sends EngineCoreRequest and receives EngineCoreOutputs over ZMQ.
EngineCore
Process that runs a busy loop schedule() → execute_model() → update_from_output(). It hosts the Scheduler, the KVCacheManager, the structured-output manager (xgrammar) and the Executor.
Executor
The one that knows where the GPUs are: uni (worker in the same process), mp (multiprocessing, one process per GPU, including on other nodes), ray or external_launcher.
Worker
One process per GPU: it initializes the device and the NCCL/Gloo groups, builds the model and loads its slice of the weights.
Model runner
Inside the worker, it turns the scheduler's plan into GPU tensors, chooses CUDA graph or eager execution, runs the forward, samples and, with speculation, verifies and proposes drafts.

How many processes does that add up to? The vLLM documentation counts \(A\) API servers (by default, equal to DP), one EngineCore per data replica and one worker per GPU:

\[ N_{\text{proc}} = A + DP + DP \cdot PP \cdot TP\ (+1 \text{ coordinator if } DP>1) \qquad \text{recipes: } 1 + 1 + 1\cdot 1\cdot 2 = 4 \]
  • \(A\): API server processes
  • \(DP\), \(PP\), \(TP\): degrees of data, pipeline and tensor parallelism (Parallelism)

In the recipes (DP = 1, PP = 1, TP = 2 across two nodes), the head hosts the API server, the EngineCore and the rank 0 worker, and the other node hosts only the rank 1 worker. The optimization docs ask for at least \(2 + N\) physical cores (with \(N\) GPUs), because “the EngineCore runs a busy loop and is particularly sensitive to CPU starvation”. The figure below follows a request through the process map, station by station.

Three details explain parameters in the recipes. The EngineCore does not run the model: it plans and dispatches, and rank 1 receives the plan over the network. All ranks execute the same plan and meet at the all-reduces; divergent configurations mismatch the collectives and hang the pair (CUDA graphs and warmup). And only rank 0 returns the output, identical to rank 1's by construction.

Multi-node with the mp executor

All three recipes, in their vLLM versions, launch the same command on both nodes, changing only the role. The head opens the rendezvous (--master-addr/--master-port) and the API. The worker joins with --node-rank 1 and --headless, with no API server and no scheduler:

# head (rank 0): API server + EngineCore + local worker
vllm serve <model> --tensor-parallel-size 2 --distributed-executor-backend mp \
  --nnodes 2 --node-rank 0 --master-addr <IP_HEAD> --master-port <PORT> --host 0.0.0.0 --port 8888 ...
# worker (rank 1): the worker only
vllm serve <model> --tensor-parallel-size 2 --distributed-executor-backend mp \
  --nnodes 2 --node-rank 1 --master-addr <IP_HEAD> --master-port <PORT> --headless ...

Automatic executor selection picks mp when there are several CUDA nodes, ray when a Ray cluster is active and uni when the world has a single GPU. Even so, the recipes pin the value instead of trusting the heuristic. The rendezvous ports are 25000 , 29521 and 50000 .

Parameter--distributed-executor-backend mp

All the vLLM recipes use mp; none uses Ray. GLM justifies it with simplicity: two nodes with one GPU each, one process per node, no Ray cluster to maintain inside containers. The worker joins headless and only runs the model.

Another design: one process per Spark

This map is a vLLM choice, not a law. The TensorFold version of the GLM recipe serves the same checkpoint with two processes, one per Spark. Each one runs tensorfold serve <snapshot> --tp 2 --rank R --master <head> --master-port 29551. Rank 1 starts first, over ssh, and then rank 0 starts; besides its half of the model, it opens the API on port 8888 and runs the scheduler in a thread. There is no EngineCore in a separate process, no executor and no shared-memory queue between processes. By the section's count, \(N_{\text{proc}} = 2\) instead of 4. Since the two ranks still execute the same step in lockstep, someone still has to decide and the other has to follow. The difference is in what crosses the cable:

vLLM V1 (GLM, Qwen, DeepSeek recipes)

  • Rendezvous via --master-addr/--master-port, with NCCL and Gloo groups from torch.distributed.
  • The leader (EngineCore) does not run the model. Every step, it sends the SchedulerOutput serialized with pickle: how many tokens each request processes and in which blocks.
  • The workers execute that plan and meet at every layer's all-reduces.
  • A configuration that differs between ranks mismatches the collectives and hangs the pair in the middle of serving.

TensorFold (GLM·TF)

  • Rendezvous via a TCPStore on rank 0, which publishes the ncclUniqueId. NCCL is loaded through ctypes, and the all-gather takes the all-reduce's place: each rank receives the other's partial and adds the two in rank order, so both arrive at the same bits.
  • The leader (rank 0) also runs the model. Every iteration, it sends one message: an int32 vector of operations (ADMIT, EVICT, MOVE, GROW, FILL, MFILL, ROUND, FINISH, IDLE, plus SLOT when TF_GLM_MULTI_LONE=1), sent in two all-gathers, the length and then the values.
  • Rank 1 applies the same operations, in the same order and through the same code. Drafts do not travel: it derives them on its own and only checks the depths.
  • At startup, each rank packs its settings into a list of integers, all-gathers it and refuses to start if the lists differ.

Why is replicating only the decisions enough? (Interpretation.) TensorFold promises equal bits on both ranks: the same operation on the same state gives the same result on both sides. So only what can differ between two machines needs to travel, such as the clock, clients arriving and dropping, and the pool's allocation. Everything else is recomputed locally. It is an SPMD with a leader, and the startup check turns into a boot error what in vLLM would be a hang while serving. That is why start.sh passes every TENSORFOLD_*, TF_GLM_* and TF_ROCE_* variable to both containers. What is lost is the isolation this section opened with: API, scheduler and sampler (which runs on the host, in float64) share rank 0's process, where vLLM separates the front end from the loop that feeds the GPU. We found no measurement of that cost in this recipe. The protocol, with a figure, is in An exact engine.

How the processes talk: queues, busy-waiting and deadlines

There are two transports between the processes. Between the API server and the EngineCore run ZMQ sockets carrying msgpack-serialized messages. From the EngineCore to the workers, each step's plan travels through a MessageQueue (vllm/distributed/device_communicators/shm_broadcast.py), a ring buffer of slots in shared memory. The writer serializes the SchedulerOutput with pickle, copies the bytes into a slot, marks it “written” and fires a ZMQ notification (cheap, but not free) for whoever is asleep. Each local reader reads the slot and marks it “read”. Remote readers, like the worker on the other node, receive the same pickle bytes through a ZMQ socket.

The way back uses the same mechanism. In the upstream MultiprocExecutor, each worker creates a response queue (worker_response_mq) in shared memory, and the EngineCore is its reader: that is how rank 0's ModelRunnerOutput arrives at the end of every step. So there are readers waiting on both sides: the workers wait for the next plan and the EngineCore waits for the step's response. This is our reading of the upstream code; check vllm/v1/executor/multiproc_executor.py in your image.

The delicate part is how the reader waits for the next message. There are two extremes:

  • Busy-waiting (busy-wait): polling the flag in a loop. The reaction is nearly instantaneous, but a CPU core spins flat out.
  • Sleeping on a notification socket: the CPU is free, but when the message arrives the operating system has to wake the thread, which costs latency on every wakeup.

The SpinCondition class is a hybrid. After each message, the reader spins for a busy_loop_s window and, if nothing arrives, sleeps until notified. In stock vLLM, that window is 1 second. Call the window \(W\) and the interval between messages \(\Delta\). The back-of-the-napkin math goes like this:

\[ \text{CPU spinning} \approx \frac{\min(W, \Delta)}{\Delta} \qquad\qquad \text{wakeups per message} = \begin{cases} 0 & \Delta \le W \\ 1 & \Delta > W \end{cases} \]
  • \(W\): busy-wait window (busy_loop_s)
  • \(\Delta\): interval until the next message (in decode, on the order of the step duration)

In decode, the intervals between steps always stay below 1 s. With the stock window the reader never sleeps: each reader takes a whole core, all the time, whether it is a worker waiting for the plan or the EngineCore waiting for the response. On an ordinary server that is just waste. On the GB10, CPU and GPU share the same SoC, with the same power and thermal budget. DeepSeek observed 3–4 Grace P-cores spinning at max clock (issue #79), which matches one reader spinning at each end of the queues (interpretation). The figure simulates a reader in slow motion. Move the window and see what happens to the CPU and to the number of wakeups.

With \(\Delta \approx 100\) ms (the order of GLM's step, by our math: tok/s ÷ tokens per step) and \(W = 16\) ms, the formula predicts the CPU spinning ≈ 16% of the time (≈ 24% in the figure, because the bursts are covered too), a drop close to the −85.3% measured on the EngineCore. It makes sense that the CPU of whoever dispatches the plan drops: the EngineCore is also a reader, of the response queue, and spins waiting for the result of each step. The closeness of the numbers is our interpretation. Decode even rose 0.95%, probably because the idle CPU leaves power budget for the GPU (interpretation). At 2 ms it lost 1.68% (interpretation: the reader starts sleeping between closely spaced messages and pays for the wakeup on the critical path). 32 and 64 ms lost ~1.8%, and the repository doesn't explain the non-monotonicity. Treat the curve as a measurement, not a law: your hardware may have a different sweet spot.

In the TensorFold lane: spin while working, sleep while idle

With no queues between processes, TensorFold faces the same dilemma somewhere else. A rank 1 with no work would wait for rank 0's next message inside an all-gather, holding the GPU. Instead, it waits on a doorbell, a tf_glm_request_<n> key in the rendezvous's own TCPStore. While serving, the thread that moves the all-gathers over RoCE spins as long as there are operations, because the gaps between collectives inside a CUDA graph stay under a millisecond. Only after a run of spins with no signal does it start asking for short nanosleeps. The stated result is that an idle server holds no GPU and no CPU core. It is the same hybrid as SpinCondition with a different criterion (interpretation): instead of a time window \(W\) after each message, the engine spins while there is work and sleeps when there is none. The doorbell started as a patch in Mia's recipe and was merged into TensorFold v0.6.0.

The step deadline

Dispatching the plan is half the conversation. The other half is waiting for the workers' response, and that wait has a deadline. In the mp executor, each step is a remote call (an RPC, execute_model/sample_tokens) with a limit of VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS, 300 s by default. If a worker doesn't answer in time, the EngineCore concludes it has hung and dies, taking the service down with it. Three other clocks live alongside this one:

The compose file sums up the trade-off: 1800 s “survives a worst-case compile; a real hang only shows up later”. It doesn't fix the XGrammar hang (#136), nor does it extend the 600 s watchdog. GLM uses the same value for the same reason. The timeline of the three clocks is in CUDA graphs and warmup.

Pitfall

Raising a deadline trades a loud error for a silent wait. The real cure for JIT in the middle of serving is persistent caches and shape warmup at boot. The long deadline is only the seat belt for when those fail.

In the TensorFold lane: the clock lives on the wire

With no RPC between processes, there is no step deadline. The clock that matters sits in the communication: TF_ROCE_WAIT_S (20 s by default in the patch and in v1.3.2, from 1 to 3,600; since v1.6 the recipe uses 300 s, because in the issue #54 reports the peer was late on long prompts, not lost: a late peer costs one slow round, and a rank that is really gone is noticed after 300 s) caps how long a GPU waits for the peer's shard in an all-gather over RoCE before declaring the runtime poisoned. The villain is the same as in the DeepSeek card above, JIT compilation, only at a different time. On the first start of each image, each rank compiles its CUDA extensions on its own, and the two can drift tens of seconds apart, more than a RoCE wait tolerates. The fix (patch 0052) makes every RoCE all-gather run outside a graph wait for the peer at an NCCL barrier until the engine is built. The ones captured in a CUDA graph never do this. When something really fails, the engine assumes the two ranks can no longer agree: a broken flag latches and every later call fails until both restart. With FOREGROUND=1, start.sh takes one rank down when the other dies, because a lone rank would wait for its peer forever. For diagnosis, TF_GLM_MULTI_WATCHDOG_S (300 s) dumps the Python stacks of a stuck iteration.

A step inside the worker: the model runner

The scheduler speaks in requests (“A advances 1 token, B prefills 5, C advances 1”); the GPU only understands dense tensors. The model runner translates one into the other at every step: it flattens the tokens into a single queue (a “ragged” batch) and builds the tensors that tell attention who is who:

\[ \texttt{qsl}_{r} = \sum_{r' < r} s_{r'} \qquad\qquad \texttt{slot}(t) = \texttt{BT}\!\left[r_t,\ \left\lfloor p_t / b \right\rfloor\right]\cdot b + (p_t \bmod b) \]
  • \(s_r\): tokens scheduled for request \(r\) in this step
  • \(\texttt{qsl}\): query_start_loc, where each request starts in the flattened queue
  • \(\texttt{BT}\): block table (row = request, column = logical block, value = physical block)
  • \(p_t\), \(r_t\): position of token \(t\) and its request; \(b\): tokens per block
  • \(\texttt{slot}(t)\): the slot mapping, the physical address where the token's K/V is written

The figure builds these spreadsheets for a small batch (illustrative numbers). Follow the vectors as they fill up, the slot-mapping arrows landing on physical blocks and the sampling happening only at the positions that matter.

Notice: the model sees only 7 rows, and it is the metadata that says which rows see which keys. Logits come out only at the sampling positions (\([0, 5, 6]\)), because the LM head over a vocabulary of ≈ 130–250 thousand tokens is expensive (DeepSeek 129,280, GLM 154,880, Qwen 248,320). And this step is mixed, so it doesn't fit a uniform-decode graph (CUDA graphs).

After the forward comes the sampler: temperature, top-k/top-p, penalties, grammar masks. DeepSeek turns on the FlashInfer sampler (VLLM_USE_FLASHINFER_SAMPLER=1). With speculative decoding, the runner also runs the rejection sampler, which compares the drafts against the model's probabilities, and the proposer, which generates the drafts for the next step (Speculation).

In the TensorFold lane: rows of a window, contiguous addresses

TensorFold has no generic model runner. The GLM family's engine builds the step itself, and the spreadsheets change shape. The rows of a decode round are verification windows: each stream's pending token followed by its drafts, up to 16 rows per stream and 32 in the batch (in v1.3.2; since v1.5, 64 in the batch by default with PARALLEL above 4, TF_GLM_MULTI_WINDOW). Each stream owns an extent, a contiguous range of rows in the cache pool, and a token's address no longer goes through a block table. In essence, it is the extent's base plus the position, \(\texttt{base}_{r_t} + p_t\) (our reading of the code). Each row's position, base, slot and parity live in device tables, which is why one CUDA graph per row count (from 1 to 32) covers any mix of streams. A prompt chunk never shares a forward with decode rows, so there is no mixed step that leaves the graph. In place of the rejection sampler comes verification by equality: each row is sampled with the target's keyed sampling, and a draft is accepted as long as it equals that sample. As a result, the reply with drafts comes out identical to serial generation, token by token. The price comes in two parts: the segmented code has a fixed ceiling on concurrent requests, 4 in v1.3.2 and 8 since v1.5 (patch 0069; in vLLM, GLM's 4 slots are just the value chosen for --max-num-seqs), and every so often it has to move and compact extents, work that vLLM's block table avoids (next chapter).

V1 and V2: two model runners

There are two implementations of the runner, and the recipes use both:

Model Runner V1

  • vllm/v1/worker/gpu_model_runner.py, a single file with thousands of lines.
  • A persistent InputBatch mirrored in CPU arrays, prepared at every step and copied to the GPU.
  • Deprecated since v0.29, with removal planned for v0.32.

Model Runner V2

  • vllm/v1/worker/gpu/…, the default since v0.29.
  • Persistent state on the GPU, inputs prepared by Triton kernels, a Triton sampler.
  • No CPU-GPU synchronization in the main loop, designed for asynchronous scheduling.

For a recipe, the difference is concrete: different files. A patch against V1's gpu_model_runner.py doesn't fit V2, and vice versa. That is what separates DeepSeek's lanes: A (Anemll, production) uses V2, B (Stage-C overlay) uses V1. Qwen's day-0 image combines engine V1 with runner V2.

The way back, even when there is no token

At the end of the step, update_from_output() in the EngineCore records each request's accepted tokens, frees the blocks of whoever finished, advances the grammars and sends EngineCoreOutputs to the API server. There is an edge case that shows why this contract has to be explicit: steps in which a request only runs the multimodal encoder and samples nothing.

Hotfixhotfix-vllm-empty-encoder-output.py (always on)

The pinned image made up token 0 when an encoder-only producer sampled nothing, and the scheduler had no branch to finish those requests. Token 0 is a real id, so the “nothing” became a spurious token. The vLLM backport 7ca49fbe returns an empty list per request, marks is_mm_encoder_only and finishes with FINISHED_STOPPED once the prompt has been consumed, pre-validating both target files before writing. The lesson: “there is no output” is represented as empty, never with a sentinel that is also a valid value.

From config.json to the Python class: the model registry

How does vLLM know which code runs a checkpoint? Through two chained lookups into config.json (The three models, Checkpoints):

  1. model_type → config class. It says how to read the fields: a Transformers class or one of vLLM's own classes in vllm/transformers_utils/configs/. That is where names, defaults and aliases get resolved.
  2. architectures → model class. The model registry (vllm/model_executor/models/registry.py) merges dictionaries such as _TEXT_GENERATION_MODELS, _MULTIMODAL_MODELS and _SPECULATIVE_DECODING_MODELS into _VLLM_MODELS: architecture name → (module, class).
  3. Lazy import. Each entry becomes a _LazyRegisteredModel(module, class). The module is only imported when needed, because importing model code can initialize CUDA, and CUDA initialized before the workers' fork gives “Cannot re-initialize CUDA in forked subprocess” (lazy registration).
  4. Instantiate and load. The class is built with the VllmConfig and receives the weights through load_weights, with a weight_loader per parameter that cuts out the rank's slice.

Recent versions adopted a hardware-isolated layout: an entry can point outside model_executor/models, as in "DeepseekV4ForCausalLM": ("vllm.models.deepseek_v4", …), with the implementation in vllm/models/deepseek_v4/nvidia/. Drafters are registered architectures too, and their config can be the target's own, rewritten. DeepSeek's DSpark drafter shows that this rewrite changes per lane. In the Stage-C overlay (lane B), SpeculativeConfig.hf_config_override takes a DeepSeek-V4 with dspark_block_size and rewrites the same config to model_type: deepseek_v4_dspark, architectures: ["DeepSeekV4DSparkModel"] and n_predict = dspark_block_size. Lane A's Anemll image does something else: it maps deepseek_v4 → deepseek_mtp with n_predict = num_nextn_predict_layers (3 in Vision-Exp) and then switches the architecture to DSparkDraftModel. It looks like a plumbing detail, but it decides the number of drafts, as the card below shows. Pick a model in the figure and follow the lookup; the two DSpark drafters appear side by side.

The router panel is the most treacherous case. GLM's checkpoint uses SGLang names (num_experts_per_tok, hc_mult, hc_sinkhorn_iters, mla_use_nope, linear_attn_config), and Glm5NextTextConfig reads them with .get, keeping both names (config aliases). The code comment records what used to happen: “without this, our default (num_experts_per_token=7) was used, routing 7 experts per token instead of the trained 8”. Nothing broke; the model just got worse, silently.

Parametermodel_type: qwen4_exp (text: qwen4_exp_text)

How a new model gets into vLLM

When the registry doesn't have your architecture (the “challenge” in the MiMo tutorial), you write the class. The anatomy of an implementation is always the same:

  1. Config. If the model_type is unknown, create the config class and resolve the field aliases. This is where you avoid the 7-experts bug.
  2. Modules built from vLLM's parallel layers. Assemble the model with QKVParallelLinear, MergedColumnParallelLinear, RowParallelLinear, VocabParallelEmbedding/ParallelLMHead, the fused MoE layer and the Attention layer, which picks the backend. Pass each of them the quant_config and the prefix (the module's full name): that is how quantization decides layer by layer (next section).
  3. forward(input_ids, positions, …). Model code doesn't manage the KV cache: the attention layer reads the step's metadata (block table, slot mapping) from the forward context built by the runner.
  4. load_weights. Map checkpoint names to vLLM parameters (hf_to_vllm_mapper, fusions like gate_proj+up_proj → gate_up_proj) and let each parameter's weight_loader cut out the rank's slice (Checkpoints).
  5. Interfaces. Declare capabilities by inheriting marker classes, like IsHybrid and HasInnerState (GLM's wrapper) or SupportsEagle3. In MiMo, the omni class lacking the SupportsEagle3 marker kept DFlash from starting.
  6. Register. In the in-tree registry, or through a plugin, with no fork: ModelRegistry.register_model("Arch", "package.module:Class").
  7. Prove it. Truncated parity: --hf-overrides '{"num_hidden_layers": 2}' --enforce-eager against the HF model with the same layers, comparing logprobs (top-20 KLD). Then TP2 against TP1: if they diverge, the problem is in the sharding, not the kernel (Recipe from scratch).

Building for free: the meta device

Sometimes you need the structure of the whole model (names, shapes, module order), but only a tiny fraction of the weights. PyTorch has a device for exactly that: the meta device. A tensor on meta has a shape and a dtype, but not a single byte of memory. Building a 133 GB model inside with torch.device("meta"): costs almost nothing. Afterwards, you selectively materialize only the subtree you care about.

vLLM uses exactly this in Qwen's PLE offload process, the 51.2 B-parameter N-gram table (≈ 51 GB in FP8) that can be computed on the CPU (Unified memory, N-gram and MTP). The docstring of _load_weights in ple_offload/worker.py describes four steps, and the figure animates them:

Step 4 matters as much as step 1: process_weights_after_loading runs only on the PLE subtrees, because “the rest of the model is still on meta and cannot be visited”. And loading is fail-loud: a materialized parameter without a weight raises RuntimeError instead of serving garbage. The process brings up an isolated TP1 Gloo world, computes the PLE once per DP rank and spreads it to each TP rank via CUDA IPC. Hence the dependency on the mp executor.

Pluggable quantization: the three-hook contract

Every quantization format (FP8, NVFP4, EXL3, mixed ModelOpt…) answers the same questions: which tensors the layer stores, how they arrive from the checkpoint, what preparation they get after loading and which kernel does the math. vLLM turned those questions into a contract. On the configuration side, a QuantizationConfig (vllm/model_executor/layers/quantization/base_config.py) is built from the checkpoint's quantization_config or from --quantization:

  • get_name(): the name that --quantization accepts.
  • from_config(dict): reads bits, codebook, groups, excluded modules.
  • get_min_capability(): the lowest supported compute capability (EXL3: 80; the GB10 is SM121).
  • override_quantization_method(): automatically claims a checkpoint.
  • get_quant_method(layer, prefix): the heart of it. For each layer, it returns the method object that will create, load and execute those weights (or None = native).

On the layer side, the method implements three hooks, identical for linears (LinearMethodBase: QKV, gate/up, down, o_proj, lm_head) and experts (FusedMoEMethodBase). The starting point is UnquantizedLinearMethod:

class MyMethod(LinearMethodBase):
    def create_weights(self, layer, ...):          # at model construction
        # registers Parameters with the CHECKPOINT's shapes/dtypes
        # and attaches a weight_loader that knows how to cut each TP rank's slice
    def process_weights_after_loading(self, layer): # once, after loading
        # repack to the kernel's layout, scales, auxiliary copies; free the sources
    def apply(self, layer, x, bias=None):          # on every forward (maybe inside a CUDA graph)
        # the GEMM: no allocation, no CPU sync

Each hook runs at a moment with its own rules: create_weights before any weight exists; process_weights_after_loading once, where expensive work fits; apply millions of times, maybe inside a captured graph, where allocating or calling .item() is forbidden (CUDA graphs). Pick one of the recipes' methods and walk through the five moments.

Three lessons. The decision is per layer, and the prefix carries the name: one string mistake and the layer is born unquantized, silently (Checkpoints). The checkpoint's layout is almost never the kernel's, and hook 4 converts it once. And the kernel can change with \(M\): memory rules in decode, compute in prefill, and a method can dispatch each regime to its own kernel (Kernels).

Registering the name and winning the fight for the checkpoint

The @register_quantization_config("name") decorator (out-of-tree since PR #11969) makes --quantization name valid; the built-in methods live in the QuantizationMethods Literal and in get_quantization_config(). Registering is not enough. To reconcile the checkpoint's quant_method with --quantization, ModelConfig walks an ordered list of methods asking, via override_quantization_method, who claims the checkpoint. A method that isn't on the list is never consulted.

Build modificationsregistration of exl3 + patch_model_overrides.py

vLLM doesn't know EXL3. The Dockerfile (lines 387-416) edits quantization/__init__.py by anchor (each one exactly once, otherwise the build aborts): it adds "exl3" to the Literal and lazily imports Exl3Config in get_quantization_config. overlay/exl3.py (3,248 lines) carries @register_quantization_config("exl3") on line 1705. Extension pointExl3Config.get_quant_method (exl3.py:1853)

Decides each module's precision: RoutedExperts → Exl3MoEMethod (int16 trellis + suh/svh + mcg marker, never expanded to BF16); ParallelLMHead → Exl3LinearMethod only if the pack declares it, otherwise None; LinearBase → Exl3LinearMethod, Glm53DenseFp8Method (GLM53_DENSE_FP8 groups, FP8 via Marlin) or UnquantizedLinearMethod. Propagating the quant_config: the layer nobody asks about

A QuantizationConfig only decides for the layers that receive the quant_config. If a constructor passes a hard-coded quant_config=None, get_quant_method is never called there and the layer stays BF16 whatever the checkpoint says (quant_config propagation). GLM ran into this in KDA and MLA (patch_dense_fp8.py keeps the quant_config when it is exl3); Qwen, in the hyper-connections.

Plugin: quantization without touching vLLM

The clean alternative to editing the image is a plugin: a Python package with an entry point in the vllm.general_plugins group. Pluggable kernels: modular MoE, workspaces and attention backends

Quantization decides which weights exist; backends decide who does the math. For MoE, vLLM has a modular interface in three pieces: an oracle picks the backend from --moe-backend and the weight format; a prepare/finalize stage does the tokens' dispatch and combine; and an experts class does the GEMMs and declares its scratch in workspace_shapes.

Backend--moe-backend flashinfer_b12x → B12xExperts

In the MXFP4 oracle (fused_moe/oracle/mxfp4.py), the patch official-main-b12x-nvfp4-python.patch adds the B12X_MXFP4 enum and the map "flashinfer_b12x": [Mxfp4MoeBackend.B12X_MXFP4]; backend_to_kernel_cls returns [B12xExperts], with hidden and intermediate rounded up to 128. B12xExperts(mk.FusedMoEExpertsModular) accepts only MXFP4 (fp4_e8m0_k32, w31 layout), prepares the W4A16 format and frees the source weights so as not to pay for the memory twice. Its workspace_shapes returns ((0,), (scratch,), (M, K)): only a workspace2, sized by plan_tp_moe_scratch. The boot confirms “Using 'B12X_MXFP4' Mxfp4 MoE backend”. GLM doesn't pass --moe-backend (the MoE belongs to EXL3); Qwen stays on auto.

The shared workspace: reserve up front, lock, never grow during capture

Sparse-attention and MoE kernels need scratch space: indices, partial logits, split-K sums. Allocating on every call costs time, and during a CUDA graph capture it is forbidden: the graph records addresses. vLLM uses one workspace manager per device. A kernel asks for several buffers at once (current_workspace_manager().get_simultaneous(...)) from a single region; in the dummy run, at worst-case shapes, the region grows to the peak; lock_workspace() freezes the size, and asking for more becomes an error. That scratch comes out of the KV budget (PagedAttention and KV).

Backport and backend#50298 (top-k + SWA indices, FlashMLA path) and the SM120 split-K scratch

In the FlashMLA sparse prefill path (models/deepseek_v4/nvidia/flashmla.py), on every prefill chunk, combine_topk_swa_indices() allocated a (num_tokens, combined_topk) int32 tensor and filled it with −1. The backport passes out=(indices, lens), reuses the buffers and skips the fill; the dummy/capture path (forward_mqa) reserves both buffers together with the BF16 workspace via get_simultaneous. With combined_topk = round_up(top_k + window, 128) = 640, at 8192 tokens that is 20 MiB of indices alone (our math, from the patch's formula). Upstream measured 1.88× on that kernel. Caveat: FlashMLA is the Hopper/SM10x backend. On the GB10 the model code picks DeepseekV4SM120SparseImpl (that is what the Stage-C overlay shows), which has its own _forward_prefill and doesn't call combine_topk_swa_indices(); the backport is applied, but may sit inert there. It serves here as an example of the contract. What runs on the GB10 is the SM120 split-K scratch (mid_out, mid_lse), requested through the same get_simultaneous and reserved in the dummy run (sm120.py:102, :276-286 in the Stage-C overlay). VLLM_DEBUG_WORKSPACE=1 logs every resize.

There is a vLLM feature that collides head-on with the shared scratch: dual batch overlap (--enable-dbo, micro-batching). It splits the batch into two micro-batches to hide one's communication under the other's computation, which requires kernels that can run interleaved. The figure shows the MoE pipeline, the workspace over the course of boot and the two ways to break the contract.

ForbiddenVLLM_UBATCH* · VLLM_DUAL_BATCH* · VLLM_ENABLE_DBO · --enable-dbo

GLM's cooperative decode MoE uses scratch and per-device completion counters: stage A zeroes B's counters and vice versa, so the calls must be ordered, with no overlap. The adapter (extensions/cooperative_moe/runtime.py) refuses any configuration that interleaves launches. No recipe uses DBO.

Attention backends: an enum, a priority list and inheritance

Attention follows the same pattern (table of GB10 backends in Kernels). The AttentionBackendEnum enum (vllm/v1/attention/backends/registry.py) maps names like FLASH_ATTN, FLASHINFER_MLA_SPARSE or CUSTOM to the class path. The platform walks a priority list and keeps the first backend compatible with the capability, head size, KV dtype, MLA/sparse, sliding window, non-causality and CUDA graph support. To force one, use --attention-backend or --attention-config '{"backend": …}'.

Parameter (lane B)VLLM_ATTENTION_BACKEND=B12X_MLA_SPARSE

Not set by default. In the Stage-C overlay's enum, B12X_MLA_SPARSE is an opt-in b12x backend, outside auto-selection, chosen explicitly through this variable. It serves the V3.2 family (head 576, 656 B/token, block 64), not DeepSeek-V4, whose model picks its own backend (DSV4_SPARSE_MLA_SM120, via _select_v4_sparse_impl()). In v0.30 the variable no longer exists; use --attention-backend.

Backends are classes, and classes inherit, including their refusals (backend inheritance). Qwen shows this clearly. QSA sparse attention runs its own Triton kernels, but the implementation class inherits from FlashAttentionImpl (in v0.30, Qwen4ExpQSAFlashAttentionImpl). The inherited __init__ refuses quantized KV, because FlashAttention can't read it.

ModificationFlashAttentionImpl.__init__ receives 'auto' (patch_qsa_fp8_kv.py)

The QSA backend passes "auto" to FlashAttentionImpl.__init__ and restores the real dtype right afterwards, relaxes the other two guards and adds fp8/fp8_e4m3 to supported_kv_cache_dtypes. It is safe because the only entry point is forward_qsa, with Triton kernels that apply k_scale/v_scale after the product: FlashAttention is only the nominal base class. Result: 2,131,159 → 3,652,200 KV tokens (×1.70; not ×2 because the indexer and the GDN state stay in BF16). In the v0.30 lane, the equivalent is the backport of vLLM #55557 (Quantized KV cache).

Configuring the engine: flags, variables and images

There are three layers of configuration, and mixing them up is a classic way to lose hours.

1. Flags. vllm serve turns the arguments into a VllmConfig, with typed sub-configs (ModelConfig, CacheConfig, ParallelConfig, SchedulerConfig, CompilationConfig, SpeculativeConfig, AttentionConfig…) that travel to every process; each piece reads its own part. JSON flags (--speculative-config, --compilation-config, --hf-overrides) carry entire sub-configs. The last figure shows who consumes each of the recipes' flags.

2. VLLM_* variables. They are registered in a single file, vllm/envs.py, with defaults and lazy reading. vLLM checks the environment keys that start with VLLM_. Unknown ones produce only a warning, “Unknown vLLM environment variable detected: VLLM_…”, and are ignored: the server starts normally, without the change you asked for.

Overlay (lane B)recipe/overlay/vllm/envs.py

The Stage-C overlay's envs.py registers VLLM_DSPARK_*, VLLM_DSV4_*, VLLM_USE_B12X_WO_PROJECTION and friends. In lane A (Anemll), they only produce the “Unknown” warning and do nothing (2026-07-29 audit comparing vllm.envs.environment_variables in the container against the overlay). The symmetric caveat from docs/ENVS.md: an unregistered variable doesn't mean the feature is missing, because the logic may come built in without the switch. Look for the variable in the envs.py of the image, or for the warning in the log.

3. Variables owned by others. NCCL_*, TORCH_*, PYTORCH_CUDA_ALLOC_CONF and the recipes' own (GLM53_*, EXL3_*, DSPARK_*) are read by other libraries or by the patches themselves, with no central validation. A typo there slips through without any warning at all. The recipes defend themselves by validating the values in the launcher and again inside the container, like patch_spinwait.py does.

The image is part of the recipe

The model code, the backends and the defaults live inside the image. None of the three recipes runs “latest” vLLM. Of the images used, only Qwen's v0.30 lane corresponds to a release. The others are development builds or forks, snapshots of main with patches. The version string tells that story, in setuptools-scm format: in 0.25.2.dev0+g752a3a504.d20260714, 0.25.2.dev0 is the development version on its way to 0.25.2, +g752a3a504 is the commit and .d20260714 indicates a modified tree on that date. In setuptools-scm's default scheme (guess-next-dev; the reading is ours), devN counts the N commits after the last tag, and the version number is already “bumped” to the next one. A .dev0 accompanied by .d<date> means: built from the tag's own commit (zero commits after), with uncommitted modifications. That is what shows up when someone applies patches and builds. In 0.1.dev20051+g487ecf187, 0.1.devN is what setuptools-scm writes when the build can't see any tags: N commits, no reference tag. Use the upstream docs for concepts and the boot log of your image for defaults.

Overlay or patch: replace the file or edit the snippet

Every recipe ends up touching the code inside the image, in one of two ways (just the concept here; the full engineering is in Recipe engineering):

  • File overlay: replaces the whole file, via COPY (DeepSeek's lane B, 17 files) or a bind-mount :ro (mounting a host file over the image's file, at the same path, read-only). Readable and complete, but it freezes the file at one version: if the base changes, it silently reverts new fixes or mixes versions (“files from different versions mixed together break imports in subtle ways”, the tutorial warns).
  • Targeted patch: edits only the snippet it needs, with a unique anchor, diff hunks or a file hash. When the image changes, the anchor doesn't match and the boot aborts (fail-closed); a good patch also recognizes when the fix is already upstream and exits without doing anything.

The recipes combine both. Qwen extracts the .orig from the image itself, applies the patch by anchor and mounts the result: an overlay derived from the right file. DeepSeek's lane A edits the files at boot, with a pinned SHA-256 and an atomic os.replace. GLM does patches at build time and overlays at start, and its TensorFold version moves everything into the build, with 53 diffs applied to an engine that is not vLLM. Patches at build timepatch -p0 --forward × 53 · tag = hash of the patches

The TensorFold version of the GLM recipe takes the targeted patch to the extreme and moves it out of the boot. The Dockerfile starts from nvcr.io/nvidia/pytorch:26.07-py3, installs TensorFold from the git tag v0.6.0 and applies the 53 unified diffs to site-packages, in name order, with patch -p0 --forward. A diff that doesn't apply breaks the build, not the boot, and the build ends by importing the engine's main modules as a test. The image tag is the hash of the content: the first 12 hex digits of the SHA-256 of patches/*.patch plus the pip extras, which gives v0.6.0-ae8d1c789b47. As long as the patches are the release's, prepare.sh pulls the published image by digest (“a tag can be moved, a digest cannot”) and only accepts it if its tf.patches label matches the hash. JIT-compiled kernels live in one folder per image hash, so that one image never loads another's build. The cost shows up when the version changes: moving from TensorFold v0.5.0 to v0.6.0 meant redoing the series, and three patches that had gone upstream (the idle rank's doorbell, the memory reserve and the MTP head switch) left it. The TENSORFOLD_*, TF_GLM_* and TF_ROCE_* variables go with -e to both containers, and the startup settings comparison guarantees the two ranks read the same values. A comparison of values does not catch a misspelled variable name, which is simply never read (interpretation). Extra command-line arguments get a finer net: start.sh validates them with TensorFold's own parser, in a throwaway container, and a typo there fails before the running server is stopped.

In the recipes: the engine dashboard

Putting the pieces together, each recipe is a choice of where to touch the engine:

GLM · plugging in a format and kernels

  • Registers an entire quantization method (exl3) and wins the fight for the checkpoint.
  • Offers to shorten the IPC busy-loop (optional 16 ms, used in the long-coding profile; stock by default) and raises the engine's deadlines.
  • Forbids DBO: the cooperative MoE uses per-device scratch.

Qwen · fixing via bind-mount

  • Untouched day-0 image, with files from the image itself patched and mounted.
  • The model paths depend on the lane (qwen3_8_flash_next × qwen4_exp).
  • Backend inheritance worked around to get FP8 KV in the QSA kernels.

DeepSeek · three runtime lanes

  • Production on an external image (runner V2) with source-exact hotfixes.
  • Stage-C overlay (runner V1) as a readable reference implementation.
  • Quantization plugin as a template for extending without a fork.

GLM·TF · swap the engine

  • Two processes, one per Spark: rank 0 serves the API and decides, rank 1 applies the operations it receives.
  • No registry, plugins or PagedAttention: the glm5_next family brings its own kernels, cache and verification.
  • 53 diffs at build time, an image identified by the patches' hash and pulled by digest.

Checklist: the engine side of a new recipe

  1. Is the model in the image's registry? python3 -c "import vllm.model_executor.models.registry as r; print({k: v for k, v in r._VLLM_MODELS.items() if 'MyModel' in k})" inside the container. If it isn't, the choice is between an implementation, a plugin or another image.
  2. Which lane? Release, dev build or fork. Write down the version string and the digest, and read the defaults in the boot log (non-default args).
  3. Read the config the way vLLM reads it. architectures, model_type, alternative field names. Compare the effective value against the trained one (the 7 × 8 experts case).
  4. Who owns each layer? Is the quant_method native, does it need a patch or does it fit in a plugin? Does the quant_config reach every module?
  5. Which backends came up? Look in the log for the attention backend and MoE lines (e.g., “Using 'B12X_MXFP4' Mxfp4 MoE backend”).
  6. Processes and IPC. mp executor, --ipc host, the same arguments and the same patch bytes on every rank.
  7. Variables. Look for “Unknown vLLM environment variable” in the log. Each warning is a tweak that didn't happen.
  8. Clocks. RPC deadline above the worst legitimate JIT, without forgetting the 600 s watchdog.
  9. Patches that fail loudly. Unique anchor, “already upstream” detection, a log marker and a CPU test for each one.
