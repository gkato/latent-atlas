The DeepSeek-V4-Flash checkpoint is about 157 GiB, and a DGX Spark sees 121.69 GiB. It doesn't fit on one machine. And even if it did, every decode token would be limited by the bandwidth of a single memory bus. Splitting the model across two nodes solves both problems, but every cut charges a toll on the network. In this chapter you'll learn the possible cuts: by columns and by rows (TP), by experts (EP), by layers (PP), by requests (DP), and by tokens (DCP and SP). You'll also learn to predict how many messages each cut sends over the cable per token, which is what lets you pick the topology for a new recipe without trial and error.

Why split a model

There are two reasons, and they pull in slightly different directions. The first is capacity: the weights have to fit in memory. All three recipes start with checkpoints larger than one node: GLM-5.3-Flash in EXL3 is 163.6 GiB, Qwen3.8-Flash-Next NVFP4 is 133 GB, and DeepSeek-V4-Flash is 155–157 GiB. Once the model is split in two, each rank holds 79.65 GiB (GLM), 64.46 GiB (Qwen, measured), and 79.17 GiB (DeepSeek). Whatever is left of the ~121 GiB becomes KV cache, activations, and headroom for the operating system.

The second reason is bandwidth. In decode, generating one token requires reading every active weight from memory, and the GB10 delivers ~273 GB/s in theory (235–245 GB/s in practice, per the Qwen recipe audit's estimate). With two nodes there are two buses, but they only help if they work at the same time on the same token. That distinction decides almost everything in this chapter: some cuts have both buses reading in parallel, and others make them take turns.

\[ t_{\text{step}} \;\approx\; \frac{B_{\text{sliced}}/p \;+\; B_{\text{replicated}}}{\text{bandwidth per node}} \;+\; N_{\text{col}}\Big(\alpha + \frac{n}{\beta}\Big) \]
  • \(B_{\text{sliced}}\): bytes read per step in tensors split across the ranks
  • \(p\): number of ranks (GPUs) splitting those tensors
  • \(B_{\text{replicated}}\): bytes of tensors that each rank stores whole and reads whole
  • \(N_{\text{col}}\): number of collectives (synchronized exchanges between ranks) per step
  • \(\alpha\): fixed latency of each collective; \(n\): message bytes; \(\beta\): cable bandwidth

Read the equation as a budget. Cutting well shrinks the first term, because each rank reads only its own part. Whatever can't be cut (or isn't worth cutting) stays in the second term and is read by everyone. The third term is the network bill. It barely exists inside a box with NVLink, but it weighs heavily between two Sparks connected by a 200 Gb/s cable. There are five classic ways to cut, and each one moves these terms in its own way.

Notice what changes between the modes. In TP everything shows up half and half, because each node stores half of every matrix and both work together on every token. In EP attention stays half and half, but each expert lives whole on one node. In PP the top layers stay on one node and the bottom ones on the other, and the token crosses the boundary once. In DP each node has the whole model and serves its own requests. In DCP the KV is split by tokens. In vLLM, the number of GPU processes in each engine replica (the world size) is \(\text{TP}\times\text{PP}\), times the prefill context-parallel size when that is enabled. DP multiplies whole replicas, each with its own processes: in total there are \(\text{DP}\times\text{PP}\times\text{TP}\) workers. EP and DCP reuse ranks that already exist, without adding processes.

Analogy: two kitchens and one order

A gigantic order arrives at two kitchens connected by a pass-through window. In TP, each kitchen chops half of every ingredient, and the pots are combined through the window at every stage. In EP, one kitchen has the pastry chef and the other the sushi chef, and each dish goes to whoever knows how to make it. In PP, one kitchen makes the appetizer and passes the plate to the other to finish. In DP, the two kitchens are identical and each serves its own tables, which only works if each one has room for the whole recipe. The window is the network. The more times you use it per dish, the longer the waiter on the other side waits.

Tensor parallel: cutting columns, cutting rows

Every linear layer is \(Y = XW\), with \(X\) of shape \([T\times d]\) (\(T\) tokens, width \(d\)) and \(W\) of shape \([d\times n]\). Tensor parallel (TP) cuts \(W\), and there are two possible cuts, popularized by Megatron-LM (Shoeybi et al., 2019).

In the column-parallel cut, each rank stores a block of columns of \(W\), that is, a piece of the outputs. Since each column of \(Y\) depends only on the corresponding column of \(W\), each rank computes its slice of \(Y\) on its own, without talking to anyone. In the row-parallel cut, each rank stores a block of rows, that is, a piece of the inputs, and receives the corresponding slice of \(X\). Each rank then produces a whole \(Y\), but a partial one: the true result is the sum of the partials from all ranks, and that sum is an all-reduce.

\[ \underbrace{XW = X\,[\,W_0 \mid W_1\,] = [\,XW_0 \mid XW_1\,]}_{\text{column-parallel: nothing to add}} \qquad \underbrace{HW' = [\,H_0 \mid H_1\,]\begin{bmatrix} W'_0\\ W'_1\end{bmatrix} = H_0W'_0 + H_1W'_1}_{\text{row-parallel: sum = all-reduce}} \] \[ Z \;=\; f(XW)\,W' \;=\; \sum_{r=0}^{p-1} f(XW_r)\,W'_r \]
  • \(X\): input \([T\times d]\), identical (replicated) on every rank
  • \(W_r\): column block of rank \(r\), shape \([d\times n/p]\); \(W'_r\): row block, shape \([n/p\times d]\)
  • \(f\): elementwise function (ReLU, SiLU, SwiGLU…), applied locally
  • \(p\): TP degree; the sum \(\sum_r\) is the only communication, an all-reduce

The second line is the central trick, the Megatron pair. Take a column-parallel layer, follow it with an elementwise function, then a row-parallel one. The sliced output of the first is already in the format the second expects, and \(f\) acts on each slice independently. The whole pair costs one all-reduce. Follow along in the figure, with real numbers.

The figure's last step is the reason the order is column → row, and not the other way around. If the first layer were row-parallel, each rank would have a partial sum \(P_r\), and \(f(P_0) + f(P_1) \neq f(P_0 + P_1)\) whenever some coordinate changes sign. You would have to add before \(f\) (one all-reduce) and again at the end: two collectives instead of one.

Where the pair shows up in a Transformer

The pair fits twice in each block. In attention, heads are natural columns: the Q, K, and V projections of one head occupy a contiguous block of columns, and one head's attention only looks at its own Q, K, and V. So QKV is column-parallel by heads, attention runs locally on each rank, and o_proj, which mixes the heads, is row-parallel. In the SwiGLU FFN, gate and up are column-parallel with the same cut of the intermediate dimension, \(\text{SiLU}(\text{gate})\odot\text{up}\) is elementwise, and down is row-parallel. Result: two all-reduces per block, one after attention and one after the FFN (or the MoE).

Deep dive: a useful consequence of row-parallel

In a row-parallel layer, the output dimension stays whole on every rank, and only the input is split. An edit that acts on the output space, like the abliteration projection \(W' = W - \alpha\, r\,(r^\top W)/\lVert r\rVert^2\), is identical on each rank and needs no collective at all. That's what GLM's ablit_runtime.py does on the o_proj of layers 15–45 (chapter 19). On TP3, the transplant donor gets padding at the end of the input dimension to match the 66 heads.

Pitfall: only split what is divisible

Every cut axis has to be a multiple of \(p\): number of heads, intermediate dimension, vocabulary. With \(p=2\) almost everything divides (64 heads in GLM and DeepSeek, 24 in Qwen, intermediates of 2048 and 640). With \(p=3\) almost nothing divides, and the recipes need padding or another kind of parallelism. This is divisibility, which section 4 revisits for quantized tensors and chapter 40 takes all the way to TP=3 and TP=4.

A whole block under TP: where the collectives live

Apply the pair to a whole model and you get a map. The vocab-parallel embedding splits the table into id ranges: each rank looks up only the ids in its range, returns zeros for the others, and an all-reduce assembles the vector. In each layer, the token mixer (attention, GDN, KDA) and the FFN/MoE each end with an all-reduce. At the end, the vocab-parallel lm_head produces logits sliced by id range, and an all-gather joins them for the sampler. Everything too small to be worth cutting, or that can't be cut, stays replicated: norms, the MoE router, hyper-connections, indexers, and the latent projection of MLA.

The subway line shows something the equation in the first section hid: the number of meetings per step is fixed and large. The Qwen recipe audit counted ~106 collectives per decode step with MTP=3: 36 all-reduces from the out_proj of the GDN layers, 12 from the o_proj of the attention layers, 48 from the MoE, 1 logits all-gather, and 9 from the drafter's three passes. Each message is 5 to 20 KB. In DeepSeek there are ~108: 43 + 43 all-reduces (wo_b and MoE in each of the 43 layers), 6 from the draft, 2 from the embedding, 2 logits all-gathers, and 12 from the Markov head loop. At 20–50 µs each, that comes to 2–3 ms per step in Qwen (6–8% of the step) and 3–5 ms in DeepSeek, and this floor doesn't shrink with the batch.

Why this matters

Replicas cost no communication, but they cost bandwidth: each rank reads the whole replica on every step. In Qwen, the hyper-connections (1.19 GiB in BF16, with disable_tp=True and quant_config=None hardcoded) are 13% of the ~9.2 GiB each GPU reads per decode step. When you do the back-of-the-envelope math for a new recipe, add the replicas without dividing by \(p\). That's the \(B_{\text{replicated}}\) term of the first equation.

Closing the pair without an all-reduce: the TensorFold version of the GLM recipe

The whole map above assumes the pair ends in an all-reduce. The GLM recipe now has a second version : the same checkpoint, on the same two DGX Sparks, served by the TensorFold v0.6.0 engine with 53 patches instead of vLLM (An exact engine explains the engine, and Swapping the engine, the recipe). The weight cuts are those of a TP2: heads divided across the ranks, each expert cut in half (1,024 of the 2,048-wide intermediate per rank), and ~80 GiB of weights on each Spark. What changes is how the pair is closed. An all-reduce is a reduce-scatter followed by an all-gather, and the communication library does the sum. TensorFold takes the sum away from the library. Each rank finishes the attention block and the FFN block (MoE, or a dense MLP in the first 3 layers) with a partial \(P^{(r)}\) of shape \([R, 4096]\) in fp32, does an all-gather of the partials, and adds the two in its own kernel, always rank 0 first (the rank-order sum). The result is rounded to BF16 a single time.

\[ y_{\text{vLLM}} = \mathrm{bf16}\big(\mathrm{bf16}(P^{(0)}) + \mathrm{bf16}(P^{(1)})\big) \qquad\qquad y_{\text{TF}} = \mathrm{bf16}\big(P^{(0)} \oplus P^{(1)}\big) \]
  • \(P^{(r)}\): rank \(r\)'s partial, shape \([R \times 4096]\) in fp32; \(R\) = rows in the step
  • \(y_{\text{vLLM}}\): in our reading of vLLM's default path, each rank hands over its partial in BF16 and the all-reduce sums BF16 activations. That's two roundings in sequence (the partial's and the sum's), and \(4096 \times 2\) B = 8 KiB per row on the wire
  • \(y_{\text{TF}}\): \(\oplus\) is the fp32 sum done by the engine's kernel, rank 0 first. That's one rounding, and \(4096 \times 4\) B = 16 KiB per row on the wire

Why do it this way? TensorFold's contract is exactness: a drafted reply must be bit-for-bit equal to serial decoding, and each rank samples the token on its own, without exchanging the result with its peer. For that, all the arithmetic that defines a token has to belong to the engine, in a fixed order. With two terms the order wouldn't even matter, because the sum of two numbers is commutative. The rank-order rule is what would keep the guarantee with more ranks. The gain that already holds with two is a different one: sum in fp32, round once, and let the library only move bytes. With that, choosing the transport stops being a numerical decision. Small messages go over a hand-written one-shot RDMA all-gather, and large ones over NCCL, “with the same output layout (rank order), the same bits”. The price is on the wire. With two ranks, the ring all-reduce and the all-gather send the same number of bytes per rank for the same tensor, so the difference is the element size: 16 KiB per row instead of 8.

In decode that doubling barely matters. A verification window has up to 16 rows per stream and up to 32 in the 4-stream batch, that is, 16 to 512 KiB per all-gather: to the left of the \(\alpha\beta\) knee of section 9, or close to it in the widest batch. The fixed latency is what counts, and that's what the RDMA transport goes after. A 16 KiB all-gather takes 11 µs, versus 45 µs on NCCL, and decode gains 6% (prose from 44.2 to 46.9 tok/s, code from 48.7 to 51.6, measured by the recipe on an intermediate build, before other gains). In prefill the bytes count. A 2,048-row chunk sends 32 MiB per exchange point, and that all-gather takes 1.9 ms on both rails of the cable and 3.5 ms on one. The collective count is the subway's: 2 exchange points per layer, 90 per forward pass across the 45 layers. On top of those come the exchanges of the DFlash2 drafter, which also splits its projections across the ranks, two small messages per iteration, with which rank 0 tells rank 1 what to do, and the sampler's candidate exchange (section 8).

Commandtensorfold serve … --tp 2 --rank R

One process per Spark. start.sh brings up rank 1 on the worker, over ssh, and then rank 0 on the head, which also opens the API. In recipe v1.3.2 (TensorFold v0.6.0 + 53 patches) there was no equivalent of the vLLM recipe's start-tp3.sh: TensorFold's CUDA engine for GLM required exactly two ranks, and the decode kernels the recipe adds were written for the TP2 geometry (the experts' fast path requires \(D = 4096\) and 1,024 expert columns per rank). That limit is gone: since v1.4 (2026-10-03), patches 0066–0068 run the engine on three ranks through ./start-tp3.sh (experimental), splitting heads, expert columns, vocabulary and drafter KV groups in whole units with the remainder on the lowest ranks (64 heads → 22/21/21, no padding), and four Sparks run on a separate branch. Chapter 40 compares that uneven split with vLLM's padding, and the what-changed section lists the rest. The ranks also can't diverge in anything. At startup, each one packs its settings into a list of integers, the two exchange it by all-gather, and they refuse to start if the lists differ. That's why every TF_GLM_* variable goes to both containers. In service the leader and follower rule applies: rank 0 decides everything that depends on time, clients, or placement and sends one message per iteration, and rank 1 applies it through the same code. It's the same rule as the DeepSeek recipe in section 10 (the same engine args on both ranks), taken to the extreme. The engine's documentation adds a caveat: exactness holds for the same engine, weights, and settings, and doesn't promise the same bits across different rank counts.

vLLM × TensorFold: who sums, and at what precision

Both versions of the GLM recipe cut the same weights the same way; what changes is who sums. vLLM sends half the bytes (BF16 activations), leaves the reduction to the library, and scales to three and four Sparks. TensorFold sends twice as much, sums in fp32 in a fixed order, and rounds once. With two ranks, both paths already give identical bits on both nodes (adding two terms gives the same bits in either order); what TensorFold gains is the sum inside the engine's own code. The bits stop depending on the library and the transport, which brings freedom to swap the transport and an objective test for every optimization (did the reply's hash change?). In exchange, in v1.3.2 it was stuck at two ranks. Since v1.4 it also runs on three (experimental), still with all-gathers, and that's where the bill shows: with \(N\) ranks, the all-gather makes each rank receive \(N-1\) whole partials (two at TP=3), while the ring all-reduce always receives fewer than two (our own arithmetic): the choice that comes cheap on two nodes gets more expensive with more.

Cutting quantized tensors without breaking blocks

A quantized weight isn't just a matrix of small numbers. It comes with structure: blocks that share a scale, tiles that can only be decoded whole, rotations that mix dozens of columns. The TP cut has to respect that structure, otherwise one rank ends up with half of a block whose scale lives on the other. The general rule has two parts. (1) Along the cut axis, the local slice has to be a multiple of the block size. (2) Metadata that runs along the cut axis (scales, sign vectors) is cut along with it, and metadata that runs along the other axis is replicated.

  • NVFP4 (chapter 21): blocks of 16 values along K (the input), each with an E4M3 scale. A cut in N (column-parallel) splits no block at all. A cut in K (row-parallel) needs slices that are multiples of 16.
  • MXFP4: blocks of 32 along K, with an E8M0 scale. Same logic, with 32-alignment.
  • FP8 in 128×128 blocks: the scale covers a square, so any cut, in N or in K, has to land on multiples of 128.
  • EXL3 (chapter 22): 16×16 trellis tiles and the equivalent matrix \(W = \operatorname{diag}(\text{suh})\,H\,\hat W\,H\,\operatorname{diag}(\text{svh})\), with block-diagonal Hadamards of 128. suh has the size of the input and svh the size of the output.

The recipes' real cases are all in the figure. It's worth going through them one by one, because each explains a topology choice:

  • Qwen's MTP experts (FP8 in 128×128 blocks, intermediate 640): in pure TP each rank would get 320, and 320/128 = 2.5. NVIDIA's card asks for EP “so that the width of the MTP experts stays compatible with the 128×128 FP8 blocks”. In our reading (interpretation), that's what's behind the comment ENABLE_EXPERT_PARALLEL=true # Required for NVFP4 in .env.sample.
  • Qwen's vision MLP (4304): NVFP4 kernels require an input that is a multiple of 16, and 4304/2 = 2152 isn't. With weights the tower gets sliced and breaks at load time, so the recipe uses --mm-encoder-tp-mode data (section 6).
  • GLM's EXL3 experts (2048): on TP2, 1024 per rank respects tiles and Hadamards. On TP3, 2048/3 isn't an integer, and the trellis is already packed at a width of 2048. The solution is EP: 96 of the 288 experts per rank.
  • DeepSeek's MXFP4 experts (2048): on TP2 the down gets 1024 = 32 blocks of 32. On TP3 the patch pads to 2112 (704 per rank).
  • Qwen's FP8-dense checkpoint: Mia chose FP8 scales per output channel instead of blocks of 128. One reason is that vLLM's ParallelLMHead loader slices block scales wrong (it narrows along the vocabulary rows, not along the scale blocks). Per-channel scales slice exactly like the weight.
Modificationshard_exl3_col / shard_exl3_row (_load_exl3)

The overlay's EXL3 loader (exl3.py:661-676, 3072-3120) applies the rule to the letter. gate/up are column-parallel: it cuts the trellis on dim 1 (output tiles) and svh on dim 0, and replicates suh. down is row-parallel: it cuts the trellis on dim 0 (input tiles) and suh, and replicates svh. Before cutting, the loader translates the expert's global id to the local one and skips the load if the expert doesn't live on this rank. If the dimension doesn't divide by \(p\), it raises an error instead of rounding. The replicated vectors cost little, but they do cost something: a whole [4096×2048] expert has 4.0117 effective bits per weight, and the TP2 slice of gate/up [4096→1024] goes up to 4.0196, because it carries the whole suh. After down, the MoE runner does one all-reduce per layer to add up the halves.

Tip: check the shape after the cut

Kernel constraints apply to the local shape, not to the checkpoint's. Qwen's MXFP8 patch checks the post-TP \((N, K)\) before choosing the kernel: in_proj_a/b ends up [48, 2560], and mm_mxfp8 requires \(N \ge 128\). Those layers fall back to BF16 emulation, dequantized once at load time. When you put together a recipe, make a table of the local shapes for each TP you plan to use, before downloading 150 GB.

Expert parallel: whole experts

In an MoE, TP cuts each expert in half, and the two ranks compute half of each chosen expert. Expert parallel (EP) does the opposite: it distributes whole experts. In vLLM, --enable-expert-parallel makes the MoE layers use EP instead of TP, with EP group size = TP × DP, while attention stays in TP. Each rank keeps an expert map that translates an expert's global id to the local index, or marks it as “doesn't live here”.

What EP does to communication depends on one question: do the ranks have the same tokens? With DP=1, which is the case for all three recipes, yes: TP replicates the activations on every rank. There's nothing to dispatch. For every token in the batch, each rank runs only the chosen experts that live on it, treats the others as a zero contribution, and adds everything up in the same all-reduce TP would already do. With DP>1, each data replica has different tokens, and each token needs to travel to the owner of each chosen expert and back. This round trip is dispatch and combine, done by an all-to-all or by an all-gather followed by a reduce-scatter.

Three lessons from the figure. First: in “EP, DP=1” mode no arrows cross between the GPUs. EP only changed which weights each GPU stores, and the collective is still TP's all-reduce. Second: with few tokens per step, EP gets unbalanced. With one token and top-2, both experts can land on the same GPU, and the other one sits idle. The new-recipe tutorial (MiMo, no shared expert) notes that, in decode at batch 1, one rank can get 6 of the 8 experts. TP inside the expert is perfectly balanced by construction. Third: with DP>1, all-to-all traffic grows with tokens × top-k × width, and it leaves the latency regime for the bandwidth regime.

Deep dive: EPLB and redundant experts

In large clusters with wide EP, the figure's imbalance becomes a production problem: a popular expert overloads its rank. vLLM has --enable-eplb, which measures the load over a window (window_size), rebalances periodically (step_interval), and can keep extra copies of the most used experts (num_redundant_experts). No recipe uses it, and none has measured it. In our reading (interpretation), with DP=1 the imbalance only shows up at small batch, where each step draws different experts, and that's exactly where periodic rebalancing doesn't help. DeepSeek doesn't even have EP.

Pipeline and data parallel: the alternatives the recipes turn down

Pipeline parallel (PP) cuts the model in the other direction: layers 0 through \(L/2-1\) on one node and the rest on the other. Communication is minimal, because only each token's activation crosses the boundary between stages, point to point, once per step. The price is taking turns. While stage 2 works on one batch, stage 1 needs another batch so it isn't sitting idle. With \(p\) stages and \(m\) microbatches in flight, the idle fraction (the bubble) is:

\[ \text{bubble} \;=\; \frac{p-1}{m+p-1} \qquad\qquad t_{\text{1 token}}^{\text{PP}} \approx p\cdot\frac{T}{p} = T \qquad t_{\text{1 token}}^{\text{TP}} \approx \frac{T}{p} + t_{\text{net}} \]
  • \(p\): number of stages (nodes); \(m\): microbatches in flight
  • \(T\): time to read all active weights with a single bus
  • \(t_{\text{net}}\): cost of TP's collectives in the step

The last two expressions explain why decode doesn't want PP. In PP, a token goes through stage 1 (which reads half the weights) and then through stage 2 (the other half): the buses take turns, and the per-token latency is that of a single node. In TP, both nodes read their halves at the same time. The new-recipe tutorial sums it up: PP stays out “because it doubles decode latency at small batch”, and support for spec decode under PP is recent (#50514, in v0.30), one more risk.

Note that PP isn't useless: with many microbatches and a slow network, its aggregate throughput ties TP's or even beats it. That's why PP shows up in large training clusters and in high-throughput services. But a two-node recipe optimized for single-user latency picks TP.

Parameter--pipeline-parallel-size 1

The DeepSeek compose file passes the value explicitly, so every rank holds all of the model's layers, partitioned only by TP. It's the recipe's documented choice: PP=1, no EP, no DCP. There's a code detail that shows why PP would need extra care: the _mtp_hidden_buffer buffer, which stores states for the drafter, only exists on the last PP rank (model.py:1772-1780). With stages, the features the drafter reads would live on only one node. In vLLM, the split of layers per stage can be forced with VLLM_PP_LAYER_PARTITION.

Data parallel: replicas of the whole engine

Data parallel (DP) is the simplest parallelism: two copies of the model, each serving its own requests, with no communication at all in the forward pass. In vLLM, --data-parallel-size creates engine replicas (one EngineCore per replica, with a coordinator). DP requires the whole model to fit in each replica, and none of the three recipes fits in one Spark. In large MoE clusters, DP shows up in combination: attention runs in DP (each replica stores the KV only for its own requests) and the experts run in EP across all GPUs. That's where the previous section's all-to-all really gets to work.

ParameterMM_ENCODER_TP_MODE → --mm-encoder-tp-mode data

There's one place where the recipes do use DP: the vision tower. In weights (the default, MM_ENCODER_TP_MODE empty on GLM TP2) the ViT is sliced by TP like everything else. In data, each rank stores the whole encoder and the batch of images is split across the ranks. It's a local DP that avoids collectives inside the ViT and sidesteps divisibility (chapter 17). GLM turns on data only on TP3 (start-tp3.sh:426), because the tower's dimensions don't divide by 3. Qwen always turns it on, because 4304/2 = 2152 isn't a multiple of 16. Replicating costs little: Qwen's ViT is 0.84 GiB and isn't even touched in text decode.

In the GLM·TF recipe: neither slice nor replicate the tower

vLLM's two modes put both GPUs to work on vision, either slicing the ViT (weights) or splitting the images (data). The TensorFold version of the GLM recipe picks a third way out: only rank 0 loads the tower, with 1.05 GiB of BF16 weights and 0.75 GiB of workspace (~1.8 GiB). When a prefill chunk reaches the rows of an image, rank 0 hands rank 1 only the rows of that chunk, through an all-gather (rank 1 contributes zeros), and neither of them keeps a second copy. There's no divisibility to respect and no collective inside the ViT. The price is a memory asymmetry: rank 0 pays for the tower alone, and VISION=0 gives that space back to the cache. The details are in chapter 17.

Other acronyms you'll run into

PCP (--prefill-context-parallel-size) splits the prefill of a long prompt across ranks (partial query, ring attention) and increases the world size. DBO (--enable-dbo, dual batch overlap) splits the batch into two microbatches to overlap communication and computation. No recipe uses them, and GLM's cooperative MoE extension explicitly refuses --enable-dbo.

KV under TP: split heads, replicate the latent, or split tokens

So far we've only talked about weights. The KV cache also gets split, and the rule comes from attention: under TP, each rank computes its own query heads, and needs the K and V those heads look up. The result depends on how many KV heads the model has.

  • GQA with at least \(p\) KV heads: each rank stores the KV heads of its own groups. In Qwen, the 2 KV heads of the QSA layers become 1 per GPU. The main FP8 KV is 13,312 B/token in total and 6,656 B/token per GPU. The measured pool comes to 9,418 B/token/GPU because the state of the GDN layers and the state of the QSA indexer/compressor stay in BF16 and share the same pool (the README adds that the page size is rounded up to match the GDN page).
  • MLA or MQA, a single latent head: there's nothing to split. All query heads on all ranks read the same latent vector, so it stays replicated. In GLM, the 11 MLA layers write 656 B/token/layer on each rank (~7,579 B/token/rank, adding up everything that grows with the context). In DeepSeek, the compressed KV and the indexer cache (~3.85 KB/token physical, plus ~3.4 MB per sequence for the SWA windows) stay whole on both ranks. The 17.04 GiB pool holds 2,331,430 tokens.

With MLA, then, the second node doesn't bring KV capacity by splitting: it brings free memory, because it takes half of the weights off each rank. That's why DeepSeek's TP3 gives ~35 GiB of KV per rank (5.0 M tokens, 16 slots): each rank holds only 60.69 GiB of weights. The price shows up in long prefill, with TTFT +22–23% at 128K–256K, because the latent KV and the indexer are still replicated and computed on every rank, and a three-node all-reduce costs more.

Decode context parallel (DCP) attacks that duplication. Instead of replicating, it splits the KV's tokens across the TP ranks, interleaved (in vLLM, --decode-context-parallel-size, with granularity cp_kv_cache_interleave_size), without increasing the world size. In attention, each rank computes a partial attention over only its own tokens. The partials are combined exactly with the log-sum-exp trick, the same one FlashAttention uses:

\[ m_r = \max_{j\in\mathcal{T}_r} s_j,\quad \ell_r = \sum_{j\in\mathcal{T}_r} e^{s_j - m_r},\quad o_r = \frac{1}{\ell_r}\sum_{j\in\mathcal{T}_r} e^{s_j-m_r}\, v_j \qquad\Longrightarrow\qquad o = \frac{\sum_r e^{m_r-m}\,\ell_r\, o_r}{\sum_r e^{m_r-m}\,\ell_r},\ \ m = \max_r m_r \]
  • \(\mathcal{T}_r\): KV tokens stored by rank \(r\); \(s_j = q\cdot k_j/\sqrt{d}\) is the score of token \(j\)
  • \(m_r\), \(\ell_r\): local max and normalizer (the pair that forms the LSE, \(m_r + \ln \ell_r\))
  • \(o_r\): partial output of rank \(r\); \(o\): exact output, identical to attention over all tokens

Look at the counter: with replicated MLA, the joint pool of the two GPUs stores the same number of tokens that one GPU alone would store with the same free space. DCP=2 doubles that number. The cost is extra collectives in each attention layer, to merge the partials at every step (in DeepSeek, the audit estimates ~43 more per step).

The DCP degree also has a ceiling: \(\text{DCP} \le \text{TP}/H_{kv}\), with \(H_{kv}\) the number of KV heads. DCP only reuses the duplication that exists when TP has more ranks than KV heads. With MLA (\(H_{kv}=1\)) and TP=2, DCP=2 is the maximum. In Qwen's GQA (2 KV heads, TP=2) the math gives \(2/2 = 1\): each rank already stores only its own head, and there's no duplication left to eliminate. It makes sense, then, that DCP shows up in the DeepSeek and GLM recipe documents and not in Qwen's.

In the recipe: DCP is the “zero numerical risk” alternative that isn't turned on

The DeepSeek audit records that DCP isn't wired into DSV4's sparse backends in this image (grep -r dcp models/deepseek_v4/ comes back empty). With TP, the whole KV stays replicated on both ranks. A DCP=2 would double the capacity and halve the attention bytes per rank at long context, at the price of ~43 more collectives per step. In the FP4 KV study (item 8), it appears as option D: keep the 584 B row and split tokens, with zero numerical risk, because the merge is exact. The indexer operator already has the DCP path (_merge_dcp_topk_global), and the next section's SP indexer reuses exactly that kernel.

In the recipe: the TP2/EP2/DCP2 card is from another image

GLM's README warns that the Hub card from brandonmusic (TP2/EP2/DCP2 + calibrated NVFP4 MLA KV) describes the SM120 B12X image (verdictai/glm53-flash-exl3-k4:…-v84-dflash2), not this overlay. Here the KV stays in fp8_ds_mla, replicated, and the recipe's KV capacity log refuses to estimate when DCP or PCP > 1, because the block sizes change. vLLM's sliding-window KV spec requires DCP == 1. Reading a model card takes this kind of care: the topology it describes holds for the stack of whoever wrote it.

In the GLM·TF recipe: the latent is still replicated

Switching engines doesn't change the MLA rule. In TensorFold, the latent cache's sizing doesn't even divide by the number of ranks: each Spark keeps the whole latent of every token, and there's no DCP either. What changes is the row. With no 576 geometry of vLLM's kernel to pad to, it's the 512-wide latent in FP8 e4m3 with one power-of-2 scale: 528 B per token and layer, versus the 656 B of fp8_ds_mla (chapter 23). And the pool isn't a fixed number: it comes from the memory the system reports as free at startup, minus a reserve, up to a cap the recipe sets. In the recipe's measured startup, it held 2,922,496 tokens, versus the 1,233,779 of the vLLM recipe's fixed 11 GiB pool, under different settings. This section's lesson still holds: with a single latent head, the second node brings capacity by freeing weights, and a shorter row fits more tokens in the same space.

Shard the KV by owner

DCP splits every conversation's tokens across the ranks and merges partials in every layer. Mia's later TensorFold recipes try a coarser cut that needs no merge: each conversation lives on one Spark, its owner. GLM's patch 0129 (by Robert Wojciechowski, TF_GLM_KV_SHARD=1, opt-in, unreleased after v1.10) starts from this section's observation: TP splits the heads, but every head reads the whole MLA latent, so each Spark held a full copy, 11 DSA layers × (528 B of FP8 latent + 36 B of pooled keys) = 6,204 B per token per Spark. Sharded, only the owner keeps a conversation's latents (the pooled keys stay on every Spark): 3,300 B per token at two Sparks, so the same memory holds 1.87× the tokens (2.66× computed at three, untested there). In decode, the queries are all-gathered and the owner computes all 64 heads over its latents, sending the other Spark its heads' outputs (64 heads at once give the same bits as 32 + 32). In a prompt, the other Spark keeps its own heads and the owner sends only the history rows the chunk's sparse attention selects (90% of the history under 50k tokens, ~43% at 250k). Measured on two Sparks at 8 streams, every reply byte-equal to the unsharded engine's: pool 1,505,280–1,531,904 → 2,813,952–2,842,624 tokens, decode 103.1 → 102.4 tok/s, a 205k-token prompt 113.4 → 113.7 s when it borrows free rows. The price is placement: a part can fill while the other has room, so a conversation is sometimes “carried” to the other Spark (~5.8 KB per token over the link). DeepSeek-V4.1's two-Spark TensorFold recipe ported the idea (KV_SHARD=1, off by default): at 2,101,248 positions, 1,062 MiB per rank against 1,783 MiB replicated, for 1–4% of decode. The full GLM-5.3 on three Sparks takes the DCP road instead: context parallelism (CP=1, patches 0112–0113, after drowzeys' scheme) keeps every third token's caches on each Spark, which lets the default window reach 499,712 tokens (163,840 without it, with an FP8 instead of an FP4 KV), with decode as fast as without it and prefill around 590–610 tok/s at 4k–32k.

How it transfers. On a cluster you get the same menu. DCP (--decode-context-parallel-size in vLLM) and context parallelism for long prefills split tokens evenly and pay a log-sum-exp merge per layer. Owner placement is closer to DP attention in large MoE deployments (each data-parallel attention rank keeps only its own requests' KV) and to KV-aware routing, which sends a conversation back to the replica that already holds its cache. Even splits balance load by construction; owners pay nothing per layer but must be balanced by placement, eviction and the occasional move.

Sequence parallel and the exact distributed top-k

One axis is left to cut: the tokens (or, in sparse attention, the keys). That's sequence parallel (SP), and around the recipes it shows up in four different forms. In the vLLM recipes, only the second and the third actually run; the fourth runs in the TensorFold version of the GLM recipe .

1. Residual SP (the Megatron idea) and vLLM's MoE SP

An all-reduce can be written as a reduce-scatter followed by an all-gather. In between, each rank has the complete sum for a slice of the tokens. Megatron's SP takes advantage of that interval: norms and residual adds run only over the local slice of tokens, saving memory and work, and the all-gather only happens before the next column-parallel layer. The linears are still sliced by TP; what changes is that, between them, each rank stores only its own slice of the activations. In vLLM this idea lives in a compilation pass that fuses the collectives (pass_config.enable_sp; the model runner pads the number of tokens up to a multiple of TP for it to work). No recipe passes this option.

The is_sequence_parallel that shows up in the code of vLLM's MoE models is something else, despite the name: it's sequence-parallel MoE (parallel_config.use_sequence_parallel_moe). In our reading of the vLLM code, it only turns on with EP, DP>1, and TP>1, the arrangement from section 5 in which the all-to-all really works. Inside each DP replica, TP has replicated the tokens on all ranks. If every rank dispatched the same tokens to the experts, each token would be sent and computed TP times. So the tokens are sliced (sp_shard) before the layers, and each TP rank dispatches and computes only 1/TP of them. The shared expert, which doesn't go through dispatch, stays replicated: the model builds it with disable_tp=is_sequence_parallel (GLM's TP3 patch, patch_tp3_glm.py:219-234, starts from exactly this line). DeepSeek's model.py in the overlay says the same thing in a comment: in this mode, input and output are sliced by tokens, the weights stay replicated, and there's no collective. With DP=1, which is the case for all three recipes, the mode stays off.

This explains a line in patch_glm_eagle3.py, which exposes auxiliary states to the DFlash2 drafter. When the mode is active, it does sp_all_gather(value)[:full_num_tokens]. In our reading, it's a safeguard: without it, with the mode on, the drafter would receive only the rank's slice of tokens. The final slicing removes the padding that made the number of tokens divisible by \(p\). In the recipes, with DP=1, this branch never runs.

2. Indexer SP: split the keys and merge the finalists

DeepSeek's lightning indexer (chapter 13) is replicated: each rank scores all compressed keys against all queries, an \(O(\text{queries}\times\text{keys})\) cost that dominates prefill from 128K on (≈80 TFLOP per 1024-token chunk at 900K, done twice, once on each GPU). The hotfix hotfix-dsv4-sp-indexer-prefill.py splits each request's compressed keys into \(p\) contiguous, page-aligned slices. Each rank scores only its own slice with the same kernel (fp8_fp4_mqa_logits + per-row top-k), packs the (score, global id) pairs of its local top-k, does an all-gather of those candidates (\(p \times 512 \times 8\) B per query), and merges everything, in a distributed top-k, with DCP's stable selector (stable_topk_from_gathered_candidates_cutedsl). The figure shows why this gives exactly the same result.

\[ \operatorname{top}_k(s) \;=\; \operatorname{top}_k\Big(\,\bigcup_{r=0}^{p-1} \operatorname{top}_k\big(s^{(r)}\big)\Big) \]
  • \(s\): the whole row of scores; \(s^{(r)}\): the slice of scores stored by rank \(r\)
  • proof: if \(x\) is in the global top-\(k\), at most \(k-1\) elements of the whole row beat it; therefore at most \(k-1\) elements of its own slice beat it, and \(x\) is in its owner's local top-\(k\)
  • ties require a stable order (by id), otherwise different ranks would pick different finalists: hence the “stable” selector
ParameterDSPARK_ENABLE_SP_INDEXER=1 · DSPARK_SP_INDEXER_MIN_KEYS=8192

Opt-in (default 0 = stock bytes). Only chunks with at least 8,192 compressed keys (32K tokens of context, at a ratio of 4) use the SP path. Decode, short chunks, DCP>1, and TP=1 stay byte-for-byte identical to stock. The decision uses CPU metadata that is identical on all ranks, so the control flow is symmetric and the collective doesn't get out of sync. Measured: TTFT at 128K of 76.0 s (74.4 s warm) versus 79.0/81.2 s, about −4 to −6%. At 8K and 32K nothing changes, and RULER-lite scored 8/8. The gain fell far short of the 1.5–1.8× estimate and costs ~1 GB of MemAvailable. Even so, because it's exact, the A/B on 2026-09-02 returned an ON verdict, and the following baseline measurements ran with it on. The default in .env.dspark.example is still 0. Exactness is tested against brute force: tests/test_sp_indexer_prefill.py (splitting and bounds on TP 2/3/4) and scripts/test-sp-indexer-gpu.py (equivalence with the real kernels).

3. Split vocabulary and argmax by pairs

The vocab-parallel lm_head is the same idea with \(k=1\). Each rank has a contiguous range of ids (on Qwen TP2, 0–124,159 and 124,160–248,319) and computes the logits only for its own range. The default path does an all-gather of the whole logits (in Qwen's verify, 4 × 124,160 × fp32 ≈ 2 MB). To choose the draft token, it's enough for each rank to send the pair (max value, global id): \(O(2\cdot p)\) numbers instead of \(O(V)\). That's the distributed argmax that chapter 36 uses in Qwen's reduced vocabulary (use_local_argmax_reduction, get_top_tokens) and that DeepSeek uses in the draft (VLLM_DSPARK_LOCAL_ARGMAX). The _dspark_markov_block_argmax_kernel kernel goes further: it computes the local top-1 of base_logits + markov_embed @ W2ᵀ in blocks of 256 ids without materializing the Markov logits, and only each rank's winner takes part in the global top-1.

Splitting by id ranges has a pitfall: the work can end up uneven. Frequent BPE ids are low, so Qwen's 47,149-id draft vocabulary lands almost entirely on rank 0 (45,734 versus 1,415). Rank 0 reads 0.22 GiB per draft and rank 1 ~0.01 GiB. Since the two meet in a collective, the step waits for the slowest rank, and the --balance-shards flag of build_draft_vocab.py exists to balance the ranges. For the same divisibility reason, Qwen's N-gram table (PLE) is rounded up to a multiple of 128 rows (make_ngram_vocab_size_divisible_by: 320,001,446 → 320,001,536) and sliced by rows, ~160 M rows and ~23.8 GiB per GPU.

In the GLM·TF recipe: candidates instead of logits, even with top-p

GLM's lm_head in TensorFold is vocab-parallel too, and argmax by pairs becomes the \(k=1\) case of a more general rule. To sample, each rank sends its top_k + 8 largest candidates or, with top-k off (top_k ≤ 0 in the request; the server default is top_k=20, i.e. 28 candidates), up to 1,024 per row, and the final choice runs on the host, in float64. Top-p is the hard case, because the nucleus depends on the mass of the whole vocabulary. The engine stores each candidate's mass as a fixed-point integer with 40 fractional bits, so the sums of the pieces are exact and the ranks agree bit for bit. The default test is conservative: each rank's share has to end inside the candidates it sent, and if any row fails, the ranks send their whole pieces of the vocabulary again. The opt-in TENSORFOLD_NUCLEUS_UNION=1 uses a coverage argument similar to the proof of the distributed top-k: it walks the candidates of both ranks together until it reaches the requested mass. If the value where it stopped is larger than the last candidate of every rank that didn't send its whole piece, no token left behind can enter the nucleus, and the draw is the same, with fewer whole-piece reads. Sampling in full is in chapter 9.

4. The hyper-connection glue split by rows

The fourth form is the Megatron idea applied to a single piece. In GLM, between two sublayers sits the glue of the hyper-connections: the post of the sublayer that just finished plus the pre of the next one, with 24 dot products over 16,384 columns, Sinkhorn, and RMSNorm on every row. Its weights are too small to be worth the TP cut, so it stays replicated, and after each exchange point both ranks run the same glue on the same \(R\) rows. In decode, with at most 16 rows per stream, that costs little. In a 2,048-row prompt chunk, it's double the work at the 90 exchange points of every forward pass.

The glue doesn't mix tokens: a row's coefficients depend only on that row. So it can run on each rank's slice of rows, exactly like the norms in Megatron's SP. With SPLIT=1, the TensorFold version of the recipe makes rank \(r\) the owner of rows \([rH, rH+H)\), with \(H = R/2\). At each exchange point, each rank (1) sends its peer only the fp32 partial of the peer's rows, via ncclSend/ncclRecv, (2) sums the two partials of its own rows, rank 0 first, (3) runs the glue only on them, and (4) sends its normalized rows back to the peer, in BF16. Steps (1) and (2) play the role of the reduce-scatter, and (4) plays the role of the all-gather, only with already-normalized rows instead of raw sums. The figure puts the three closings side by side.

Per row and per exchange point, each rank now sends \(\tfrac12 \cdot 16 + \tfrac12 \cdot 8 = 12\) KiB instead of the all-gather's 16 KiB, and does half the glue (our own arithmetic). The recipe's numbers come with conditions. The prefill of a 50-thousand-token prompt went from ~1,270 to ~1,730 tok/s, measured together with two prompt-kernel patches (0009 and 0020), so it isn't the isolated effect of the split. The exchanges also run on a second stream, overlapped with the work on the rank's own rows (TF_GLM_PREFILL_OVERLAP=2); the final step of that overlap took a 149-thousand-token prompt from 92.8 to 90.7 s (two boots on each side). Chunks with fewer than 64 rows don't split, and decode rounds pay ~1.5%. The bits don't change, because every glue kernel is row-independent and the order of the partial sum is the same. Chapter 15 details the two overlap levels and shows the timeline.

Trade-off: split only where there are rows to spare

The GLM recipe on vLLM keeps the glue replicated: no extra exchange, and the doubled work is the price. The TensorFold version splits the glue in prefill and pays with a second exchange per point, an extra stream with events to order everything, and a 64-row threshold. In decode the split wouldn't pay off (our interpretation): with at most 16 rows per stream, the message is small, and the fixed latency of one more exchange would cost more than the half glue it saves. It's the same math as DeepSeek's SP indexer: splitting work by tokens only pays when there are tokens to spare.

What the network costs: latency, bandwidth, and what to replicate

Every parallelism choice ends in a network bill, and the most useful model for it is the α-β model (chapter 39): each collective pays a fixed latency \(\alpha\), plus the time to push \(n\) bytes at \(\beta\) bytes per second. For a ring all-reduce with \(p\) ranks:

\[ T_{\text{AR}}(n) \;\approx\; \alpha \;+\; 2\,\frac{p-1}{p}\,\frac{n}{\beta}, \qquad n = \text{step rows} \times d \times 2\ \text{B (BF16)} \]
  • \(\alpha\): latency per collective, 20–30 µs in the Qwen audit and 30–50 µs in the DeepSeek one (RoCE without GPUDirect)
  • \(\beta\): useful link bandwidth. With one HCA (the default for all three recipes at TP=2), ≈11–13 GB/s: one PCIe Gen5 ×4 PF gives ≈15.7 GB/s raw, the DS audit estimates ~11 GB/s effective, and GLM's boot measures all-gather at 12.6 GB/s per rank. The 25 GB/s (200 Gb/s) only comes with both PFs.
  • \(d\): residual width (2560 in Qwen, 4096 in GLM and DeepSeek)
  • step rows: sequences × (1 + drafted tokens) in decode; the whole chunk in prefill

The “knee” of the curve sits at \(n^\star \approx \alpha\beta\), on the order of hundreds of KB. Below it, the time is practically \(\alpha\) and the collective is latency-bound. Above it, the time grows linearly with the bytes and becomes bandwidth-bound. Decode lives to the left of the knee: a Qwen verify has 4 rows × 2560 × 2 B = 20 KB per all-reduce. Prefill lives to the right: a 1024-token DeepSeek chunk sends 1024 × 4096 × 2 B = 8 MB per all-reduce, 86 times (≈690 MB per chunk per rank). An 8192-token Qwen chunk sends 42 MB, 96 times, ~150–180 ms of communication per chunk on a 200 GbE link (Qwen audit estimate, which assumes the full 200 Gb/s; with one PF it would be close to double).

Three practical consequences. First: in decode, increasing the batch barely changes the network cost, because the message stays to the left of the knee. That's why the Qwen audit says the 2–3 ms per step “don't shrink with the batch”. Second: in prefill, larger chunks don't save all-reduce bytes. The same audit notes that --max-num-batched-tokens 8192 is reasonable and that increasing the chunk doesn't reduce the traffic. Third: the physical link matters. Each PCI function of the Spark's ConnectX-7 is PCIe Gen5 x4 (~126 Gb/s), so the 200 Gb/s only shows up when using both (socket-direct). Between nodes, the only all-reduce path that works is PyNCCL: vLLM's custom all-reduce requires P2P on the same node.

Replicate or slice: measure before deciding

If each collective costs ~30 µs, replicating a small matrix to eliminate collectives always looks like a good deal. The DeepSeek recipe tested this, and the result is instructive. DSpark's Markov head (markov_w1 and markov_w2, 129,280 × 256 × 2 B ≈ 66 MB each) is sliced by vocabulary, and the sequential 6-position loop does 12 serialized collectives per step. The hotfix hotfix-dsv4-replicate-markov-head.py (DSPARK_ENABLE_REPLICATE_MARKOV=1) swaps VocabParallelEmbedding + ParallelLMHead for local nn.Embedding + ReplicatedLinear. Measured: acceptance unchanged (correct), no gain at c=1, aggregate throughput at c=6 of 122 versus 148 tok/s (worse), and −0.44 GiB of KV on the head node. Verdict: off. The likely reading (interpretation): the 12 collectives were cheap compared with the time to read the whole W2 (66 MB, instead of half) at each of the loop's 6 positions, which adds ~200 MB per step and per rank. W1 barely weighs in, because as an nn.Embedding it's only looked up, a few rows per step. And the extra memory came out of the KV pool (−0.44 GiB). The Stage-C variant (VLLM_DSPARK_REPLICATE_MARKOV_W1) replicates only markov_w1, as a local embedding.

The mirror-image case is in Qwen. The hyper-connections are replicated because the model code hardcodes disable_tp=True (and quant_config=None), and they cost 13% of the step's bytes. The way out Mia took wasn't slicing, but quantizing: the FP8-dense checkpoint takes HC, GDN, attention, and lm_head to FP8 per channel. Per channel, and not in blocks of 128, because the HC's rank-320 projections aren't multiples of 128 (section 4 gives the other reason, the ParallelLMHead one). The estimated analytical gain is +40–60% at batch 1, not yet measured on GPU.

The drafter's TP

The drafter model in speculative decoding (chapter 37 for DFlash2 and DSpark) can have its own TP degree (draft TP, draft_tensor_parallel_size in --speculative-config). With TP equal to the target's, each draft splits the weight reads but pays collectives on every forward. With TP=1, one rank does everything and the others wait, but without talking. There's no universal answer. In GLM, DFlash2 (~2.3 GiB) at DFLASH_DRAFT_TP=2 was kept on TP2: in the “C4 keep” run on 2026-08-30 (C4 is the experiment label, not concurrency 4), decode hit 65.1 tok/s on structured text and 27.1 on prose, versus 61.7/26.9 from an earlier measurement with TP=1. The gain is clear on structured text and within noise on prose (0.2 tok/s). Prefill in the same run was 938/972/997 tok/s at 8K/16K/100K. On TP3, the drafter's 32 query heads and 8 KV heads don't divide by 3. The drafter runs with TP=1 on rank 0 (with GQA padded to 36/9), which the README calls “the divisibility tax”. On TP4, 32/8 divide by 4, and draft TP goes back to 4.

Roadmap: choosing the topology for a new model

  1. Add up the bytes per component and mark each one as sliceable (heads, intermediate, vocabulary), only distributable (experts), or replicated (latents, indexers, routers, low-rank blocks). Estimate weights per rank = sliced/\(p\) + replicated.
  2. Build the divisibility table of the local shapes for each candidate \(p\), including quantization blocks and kernel constraints (multiples of 16, 32, 128; \(N \ge 128\)).
  3. Decide on EP when cutting the expert breaks blocks or kernels. With DP=1 it doesn't change the network, but it gets unbalanced at batch 1.
  4. Count the collectives per step (2 per layer + embedding + logits + drafter) and multiply by \(\alpha\). Compare with the weight-read time per step.
  5. Look at the KV: if there's a single latent head (MLA/MQA), the KV is replicated. Capacity comes from smaller weights per rank, or from DCP, if the backend supports it.
  6. Leave PP and DP out on 2 nodes, unless the goal is aggregate throughput and the model fits.
  7. Measure every replica or cut with A/B/A: the replicated Markov head and the draft TP show that intuition about collectives can be wrong in both directions.

Every cut in this chapter ends in an all-reduce, an all-gather, or an all-to-all, and their cost was treated as a given \(\alpha\) and \(\beta\).
