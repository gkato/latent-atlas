O método: onze passos, um critério de saída em cada

Nos capítulos anteriores você desmontou três receitas prontas (GLM, Qwen e DeepSeek) e aprendeu a medir o que elas entregam. Agora o problema se inverte: o modelo saiu ontem, ninguém escreveu a receita, e as instruções oficiais foram pensadas para H200 e B200, nunca para um GB10. Por onde começar?

A resposta é um método. São onze passos com a mesma forma: objetivo → conceito → como fazer → aplicado ao modelo → critério de saída. O critério de saída é a parte que mais importa. É um artefato verificável (uma tabela, uma linha de log, um teste verde), e sem ele você não avança. É isso que separa uma receita reproduzível de um “funcionou na minha máquina”.

Na figura abaixo, cada passo é uma estação de metrô. Avance com o stepper e observe duas coisas: a cor da linha e as setas de volta.

Repare que quatro passos inteiros acontecem antes de qualquer docker run. Não é burocracia: o download tem ~175 GB e um boot frio leva uns 11 minutos [medido: tonyd2wild]. Descobrir no papel que algo não cabe, ou que um kernel não existe para o seu hardware, é ordens de grandeza mais barato do que descobrir no log.

Três selos para cada número

As receitas do laboratório seguem uma regra dura: todo número publicado é uma medição, não um palpite. O tutorial em que este capítulo se baseia marca cada valor com um de três selos, e você deve fazer o mesmo no seu README:

[estimativa]

[a medir]
ninguém publicou ainda: é trabalho seu.

Por que este modelo é um bom caso de ensino

O alvo são dois GB10 (sm_121, 128 GB de LPDDR5X unificada por nó a ~273 GB/s), dos quais o CUDA enxerga 121,69 GiB [medido: README Qwen3.8 do laboratório], ligados por ConnectX-7 com RoCE de 200 Gb/s. Na prática cabem ~160–170 GiB de pesos no par. Entre os lançamentos de agosto e setembro de 2026, o MiMo-V2.6-Flash-MOPD foi escolhido por cinco motivos:

🧮

Cabe apertado

São ~161 GiB de pesos para 2 × 121,7 GiB. Sobram ~15–20 GiB de KV por rank, e isso obriga a fazer a conta de memória direito. Um Spark sozinho não roda o formato nativo.

🧩

Quebra suposições

Day-0 com bugs silenciosos

--kv-cache-dtype fp8 ignorado sem aviso; QKV zerado com certos carregadores; verify especulativo num kernel lento em contexto longo. Todos com PR aberto.

🔁

MOPD, não RL

MOPD e RL são duas variantes de pós-treino do mesmo modelo base. O RL saiu do aprendizado por reforço; o MOPD é esse mesmo checkpoint com uma etapa a mais de destilação on-policy a partir de vários professores especializados (o card descreve a versão nova como Multi-Prefix Multi-Teacher On-Policy Distillation). Arquitetura, config.json (idêntico byte a byte) e drafter são os mesmos; só os pesos mudam. A etapa extra foi feita para mitigar a repetição de tool calls, o defeito que mais aparece com agentes.

Passo 0 — Triagem: ler o modelo antes de baixá-lo

Objetivo. Antes de baixar 170 GB, descobrir o que o modelo tem de diferente e onde o motor vai quebrar.

Conceito. Um checkpoint se descreve em três camadas. (1) O card traz a intenção e os comandos oficiais. (2) O config.json traz a geometria, que determina memória, paralelismo e kernels. (3) Os cabeçalhos safetensors trazem os dtypes e shapes reais, que às vezes contradizem o config. No MiMo, por exemplo, quant_method: fp8 convive com experts em MXFP4.

O truque que torna a triagem barata é o formato do arquivo (visto em Checkpoints). Um .safetensors começa com 8 bytes que formam um inteiro sem sinal de 64 bits, little-endian, com o tamanho \(N\) do cabeçalho. Em seguida vêm \(N\) bytes de JSON com, para cada tensor, dtype, shape e data_offsets. Só depois vêm os dados. Uma range request HTTP pede apenas um trecho do arquivo, e com duas delas você lê o “sumário” de um shard de ~1,3 GB sem baixá-lo.

#!/usr/bin/env python3
"""Triagem de um checkpoint no Hub sem baixar os pesos: config, índice e cabeçalhos por range request."""
import collections, json, re, struct, sys, urllib.request
REPO = sys.argv[1]; REV = sys.argv[2] if len(sys.argv) > 2 else "main"
BASE = f"https://huggingface.co/{REPO}/resolve/{REV}"

def get(url, rng=None):
    req = urllib.request.Request(url, headers={"Range": f"bytes={rng}"} if rng else {})
    with urllib.request.urlopen(req, timeout=120) as r:
        return r.read()

def header(fname):
    n = struct.unpack("<Q", get(f"{BASE}/{fname}", "0-7"))[0]      # 8 bytes: tamanho N do JSON
    return json.loads(get(f"{BASE}/{fname}", f"8-{8 + n - 1}"))      # N bytes: o sumário do shard

cfg = json.loads(get(f"{BASE}/config.json"))
idx = json.loads(get(f"{BASE}/model.safetensors.index.json")); wm = idx["weight_map"]
print("arch:", cfg["architectures"], "| índice:", idx.get("metadata"), "| tensores:", len(wm))
pat = cfg.get("hybrid_layer_pattern") or []
print("globais:", [i for i, x in enumerate(pat) if x == 0], "| SWA:", pat.count(1))
q = cfg.get("quantization_config", {})
print("quant:", {k: v for k, v in q.items() if k != "ignored_layers"},
      collections.Counter(re.sub(r"\.\d+\.", ".N.", x) for x in q.get("ignored_layers", [])))
wanted = ["model.layers.0.self_attn.qkv_proj.weight", "model.layers.1.self_attn.qkv_proj.weight",
          "model.layers.1.mlp.experts.0.gate_proj.weight", "model.mtp.layers.0.self_attn.qkv_proj.weight"]
for f in dict.fromkeys(wm[t] for t in wanted if t in wm):          # cada shard uma vez só
    for k, v in header(f).items():
        m = re.match(r"model\.(layers\.[01]|mtp\.layers\.0)\.", k)
        if k != "__metadata__" and m and (".experts." not in k or ".experts.0." in k):
            print(f"  {k:66s} {v['dtype']:8s} {v['shape']}")
  • get() envia o cabeçalho HTTP Range: bytes=a-b; o Hub responde só com aquele trecho.
  • header() faz a leitura em dois tempos: struct.unpack("<Q") decodifica os 8 primeiros bytes como uint64 little-endian (< = little-endian, Q = 64 bits sem sinal), e a segunda requisição traz exatamente o JSON.
  • O weight_map do índice diz em que arquivo mora cada tensor. Quatro tensores-sonda bastam: a camada 0 (global, MLP densa), a camada 1 (SWA + MoE), um expert e o MTP.
  • O Counter com a regex \.\d+\. → .N. resume os 49 ignored_layers em dois padrões, em vez de imprimir 49 linhas.

Passo 1 — A matemática da memória

Objetivo. Saber, antes de lançar, quanto sobra para KV e, com isso, quanto contexto e quantas requisições simultâneas cabem.

Conceito. No GB10 a memória é unificada (Memória unificada): o sistema operacional, o page cache, o Docker e o vLLM disputam os mesmos 128 GB. O --gpu-memory-utilization (GMU) é uma fração dos 121,69 GiB que o CUDA enxerga, e o vLLM divide esse orçamento assim (PagedAttention & KV):

\[ \underbrace{\mathrm{GMU}\cdot M_{\text{vis}}}_{\text{orçamento}} \;=\; W_{\text{rank}} \;+\; O \;+\; P_{\text{KV}} \]
  • \(M_{\text{vis}}\): memória visível ao CUDA por nó (121,69 GiB no GB10)
  • \(W_{\text{rank}}\): pesos carregados por rank
  • \(O\): ativações de pico + memória “non-torch” + CUDA graphs
  • \(P_{\text{KV}}\): o pool de KV, que é o que sobra, compartilhado por todas as requisições

KV: o que cresce e o que é fixo

Um modelo híbrido tem dois tipos de custo de KV (Prefill, decode & KV, Atenção esparsa). As 9 camadas globais guardam K e V de todo o contexto; as 39 SWA guardam só a janela. Por rank, com \(s\) bytes por elemento:

\[ b_{\text{GA}} = L_{\text{GA}}\cdot\tfrac{H^{\text{GA}}_{kv}}{TP}\cdot(d_k+d_v)\cdot s = 9\cdot 2\cdot 320\cdot s \qquad b_{\text{SWA}} = 39\cdot 4\cdot 320\cdot s \] \[ \text{req}(L) \;=\; L\cdot b_{\text{GA}}\cdot\rho \;+\; b_{\text{SWA}}\cdot B\!\left(\left\lceil \tfrac{W+k}{B}\right\rceil+1\right) \;+\; b_{\text{draft}}\cdot B\!\left(\left\lceil \tfrac{W_d+k}{B}\right\rceil+1\right), \qquad \rho=\frac{\lceil L_{\text{GA}}/g\rceil\,g}{L_{\text{GA}}} \]
  • \(b_{\text{GA}}\): bytes/token/rank que crescem com o contexto: 11.520 B em BF16, 5.760 B em FP8
  • \(b_{\text{SWA}}\): 99.840 B/token (BF16) ou 49.920 B (FP8), mas só para a janela
  • \(b_{\text{draft}}\): o KV do drafter DFlash, 5 camadas SWA com 8 KV heads (4 por rank) de 128 + 128: \(5\cdot 4\cdot 256\cdot 2 = 10.240\) B/token em BF16, com janela \(W_d = 1024\)
  • \(L\): tokens da requisição; \(W = 128\): janela; \(k\): tokens especulativos; \(B = 64\): tokens por bloco
  • o \(+1\) cobre o bloco parcial: uma janela de \(W+k\) tokens que desliza raramente começa numa fronteira de bloco, então pode tocar \(\lceil (W+k)/B\rceil + 1\) blocos ao mesmo tempo
  • \(\rho\): enchimento do alocador híbrido; grupos de \(g=5\) camadas → 9 globais ocupam 10 “slots”: \(\rho = 10/9\), +11%

Com k = 7, a parte SWA custa \(49.920 \times 64 \times (\lceil 135/64\rceil + 1) = 49.920 \times 256\) ≈ 12,8 MB por requisição em FP8, fixos. O drafter soma outro custo fixo: \(10.240 \times 64 \times (\lceil 1031/64\rceil + 1) = 10.240 \times 1152\) ≈ 11,8 MB [estimativa], em BF16, como o tutorial-fonte assume para o GB10 (se o seu build puser o KV do drafter em FP8, é a metade; confira no log). Juntos, ~24,6 MB fixos por requisição: o drafter quase dobra o custo fixo. A parte global custa 6.400 B por token (5.760 × 10/9). Duas consequências: o custo que cresce com o contexto é pequeno (para comparar, 13,3 KB/token no Qwen3.8 em TP2 BF16, e 656 B por camada MLA no GLM), e o alocador desperdiça ~11% das páginas globais. O PR #58175 mediu +10,57% de capacidade ao passar para grupos de 3 (1.606.781 → 1.776.588 tokens, MiMo BF16 TP2).

ap.add_argument("--ctx", type=int, nargs="*", default=[32768, 131072, 262144, 1048576])
a = ap.parse_args(); c = json.load(open(a.config)); b = 2 if a.kv == "bf16" else 1
blocks = lambda win: (math.ceil((win + a.spec_k) / a.block) + 1) * a.block   # janela + k, com o bloco parcial
pat = c["hybrid_layer_pattern"]; n_ga, n_swa = pat.count(0), pat.count(1)
ga_tok = n_ga * (c["num_key_value_heads"] // a.tp) * (c["head_dim"] + c["v_head_dim"]) * b
swa_tok = n_swa * (c["swa_num_key_value_heads"] // a.tp) * (c["swa_head_dim"] + c["swa_v_head_dim"]) * b
swa_req = swa_tok * blocks(c["sliding_window"]); draft_req = 0
if a.draft:
    d = json.load(open(a.draft)); bd = 2 if a.draft_kv == "bf16" else 1
    d_tok = d["num_hidden_layers"] * (d["num_key_value_heads"] // a.tp) * (d["head_dim"] + d.get("v_head_dim", d["head_dim"])) * bd
    draft_req = d_tok * blocks(d.get("sliding_window") or 1024)
pad = math.ceil(n_ga / a.group_size) * a.group_size / n_ga
kv_gib = a.visible_gib * a.gmu - a.weights_gib - a.overhead_gib

      f" + drafter {draft_req/1e6:.1f} MB | pool {kv_gib:.2f} GiB")
cap = kv_gib * 2**30 / (ga_tok * pad); print(f"capacidade ~{cap/1e6:.2f} M tokens")
for L in a.ctx:
    print(f"  ctx {L:>8}: {kv_gib*2**30/(L*ga_tok*pad + swa_req + draft_req):6.2f} requisições cheias")

Leia o script como a equação de cima escrita em Python: ga_tok é \(b_{\text{GA}}\), blocks() é o \(B(\lceil (W+k)/B\rceil+1)\), swa_req e draft_req são os dois termos fixos, pad é \(\rho\) e kv_gib é \(P_{\text{KV}}\). O --draft lê o triage/dflash/config.json do Passo 0 (por isso o caminho precisava ser preservado); como o drafter é um qwen3 com um só head_dim (128 para K e V), sem v_head_dim, o script reusa o head_dim para o V. Três regras de ouro do GB10

1. O log manda. Leia Available KV cache memory e GPU KV cache size e recalibre o --overhead-gib.

2. Deixe folga no host. O processo da API, o processor multimodal (o cache padrão é de 4 GiB de RAM; use --mm-processor-cache-gb 1), o page cache e o SO usam a mesma memória. Mantenha MemAvailable ≥ 4–6 GiB no pico e libere o page cache do checkpoint com posix_fadvise(DONTNEED) antes do boot.

Quantizar você mesmo, e medir

Se o arquivo não é o oficial (ou se você gerou um, com llm-compressor, nvidia-modelopt, exllamav3 ou llama-quantize), você deve uma medição de KLD. O detalhe crucial: a referência precisa rodar no mesmo motor. Não existe BF16 público do MiMo e o HF não roda 173 GB num Spark, então sirva o oficial no vLLM e compare o candidato contra ele pelas prompt logprobs (Medindo qualidade):

\[ D_{\mathrm{KL}}(P\,\|\,Q) \;=\; \sum_{t\in \mathcal{T}_k} \tilde P(t)\,\big(\log \tilde P(t) - \log Q(t)\big), \qquad \tilde P(t) = \frac{P(t)}{\sum_{u\in\mathcal{T}_k} P(u)} \]
  • \(P\): distribuição do próximo token na referência (oficial)
  • \(Q\): a do candidato, na mesma posição do mesmo texto
  • \(\mathcal{T}_k\): os top-\(k\) tokens da referência (\(k=20\))
  • \(\tilde P\): \(P\) renormalizada nesse suporte; tokens ausentes em \(Q\) recebem um piso
# kld_topk.py — KLD aproximada (suporte top-k) entre dois servidores vLLM com o mesmo tokenizer
import json, math, sys, requests
REF, CAND, MODEL_REF, MODEL_CAND, K = sys.argv[1], sys.argv[2], sys.argv[3], sys.argv[4], 20
docs = [json.loads(l)["text"] for l in open("kld_corpus.jsonl")]   # ex.: 64 janelas de 2048 tokens

def plp(url, model, text):
    r = requests.post(f"{url}/v1/completions", json={"model": model, "prompt": text, "max_tokens": 1,
                      "temperature": 0, "prompt_logprobs": K}, timeout=600).json()
    return r["choices"][0]["prompt_logprobs"][1:]            # posição 0 não tem distribuição

tot, n, top1 = 0.0, 0, 0
for d in docs:
    for p, q in zip(plp(REF, MODEL_REF, d), plp(CAND, MODEL_CAND, d)):
        P = {t: v["logprob"] for t, v in p.items()}; Q = {t: v["logprob"] for t, v in q.items()}
        zP = math.log(sum(math.exp(v) for v in P.values()))   # renormaliza no suporte top-k
        kl = sum(math.exp(lp - zP) * ((lp - zP) - Q.get(t, min(Q.values()) - 2.0)) for t, lp in P.items())
        tot += kl; n += 1; top1 += max(P, key=P.get) == max(Q, key=Q.get)
print(f"KLD média ≈ {tot/n:.4f} nats | concordância top-1 {top1/n:.3%} | {n} posições")

O truque é o prompt_logprobs: com max_tokens: 1, o vLLM devolve, para cada posição do prompt, as \(k\) maiores log-probabilidades. Cada documento do corpus vira milhares de amostras de distribuição. A linha do kl é a equação de cima; o piso min(Q) − 2 evita \(\log 0\) quando o candidato não tem aquele token no seu top-k. Limites: a KLD top-k subestima a real, a chave do token depende da versão (ID ou string), e o corpus precisa ser exatamente o mesmo dos dois lados.

A escala de referência

O painel de KLD da receita GLM mediu o EXL3 de 4 bpw servido a 0,0246 nats, praticamente igual ao FP8 oficial daquele stack (0,0246), com 54% dos bytes; o NVFP4 ficou em 0,061. Heurística razoável: < 0,03 ótimo, 0,03–0,06 aceitável, > 0,1 aparece em uso. Confirme sempre com evals de tarefa (GSM8K, HumanEval+, needle).

Passo 3 — Topologia (TP, EP, PP)

Objetivo. Decidir como dividir o modelo entre os dois GB10 (Paralelismos, NCCL & RDMA).

  • TP corta cada matriz. Exige 2 all-reduces por camada (atenção e MoE), cada um sensível à latência do link (8 KB por token no decode), e pede divisibilidade: heads % TP, KV heads % TP (ou replicação), moe_intermediate/TP múltiplo do bloco de quantização.
  • EP põe experts inteiros em cada rank e troca tokens por all-to-all ou allgather/reduce-scatter. Sem expert compartilhado, a carga depende do roteamento: com poucos tokens (decode, batch 1), um rank pode receber 6 dos 8 experts.
  • PP corta as camadas em fatias (24/24). Passa só ativações, mas com batch 1 um nó fica ocioso enquanto o outro trabalha. Serve para throughput com muitos streams, não para latência.

Tudo divide. O único “quase ✘” é o pré-sharding: o checkpoint foi salvo fatiado para TP=4, e você vai rodar TP=2. A figura mostra o que isso significa, linha a linha, no QKV.

Repare nos blocos âmbar das camadas globais. Cada chunk tem 3072 + 192 + 128 = 3392 linhas, que não é múltiplo de 128: o bloco de escala 25 cobre as últimas 64 linhas de K e as primeiras 64 de V, e o bloco 26 é meio vazio. Um bloco de 128 linhas tem um único fator F32, então, quando o layout [Q | K | V] do rank junta linhas de blocos de origem diferentes, não existe escala do checkpoint que sirva. O loader stock resolve isso da forma cara: desquantiza e requantiza as linhas de QKV de cada rank. Neste checkpoint, em TP2, isso muda 18% dos pesos de Q, ~51% dos de K e 73–81% dos de V nas camadas globais, com erro relativo L2 de 1,3–2,5% [medido: diffbot]. Até o Q, que alinha, muda. A explicação provável: requantizar recalcula a escala de cada bloco a partir dos valores desquantizados, e ela não precisa coincidir com a que foi gravada [interpretação].

O caminho exato (PR #59053, VLLM_MIMO_EXACT_QKV=1) evita a conta. Nas camadas globais, ele mantém o K e o V de cada chunk nas escalas do checkpoint, num layout com padding zero [Q… | K V pad | …]: 192 + 128 + 64 = 384 linhas, três blocos exatos, que reaproveitam os blocos 24, 25 e 26 originais. O forward separa K e V desse layout. Nas SWA o carregamento é uma permutação pura de blocos. Os pesos ficam idênticos bit a bit aos do checkpoint, e o preço é ~12K tokens a menos no pool de KV por causa do padding [medido: diffbot]. Nas SWA há ainda outro problema, de lógica e não de escala: cada chunk carrega 2 KV heads, e a suposição “1 chunk por KV head” quebrava o sharding (#57508).

Decisão: TP=2 (uma GPU por nó, --nnodes 2), com EP como variável de A/B no Passo 9. O tonyd2wild roda TP2 sem EP, a diffbot usa EP desligado como padrão e o Smilehyu (SGLang) roda TP2/EP2. PP fica fora porque dobra a latência de decode com batch pequeno, e o suporte a spec decode sob PP é novo (#50514 no v0.30).

Custo de comunicação [estimativa]: são 96 all-reduces por passo de decode (48 camadas × 2), cada um de ~15–30 µs em RoCE. Isso dá 1,5–3 ms num passo de ~25 ms (~10%). Se o NCCL_DEBUG=INFO mostrar NET/Socket em vez de NET/IB, o RoCE não está sendo usado e esse custo explode; corrija NCCL_IB_HCA e NCCL_IB_GID_INDEX como na receita Qwen.

Três mecanismos por trás da tabela

Por que DiffKV significa Triton (G1, G7). O vLLM tem dois backends para K e V de tamanhos diferentes. O FLASH_ATTN_DIFFKV precisa de FlashAttention 3/4, que não existe no sm_121, então toda a atenção do alvo cai no TRITON_ATTN_DIFFKV. É por isso que os dois patches de atenção são arquivos Triton.

Por que o verify fica lento (G7). Em contexto longo, a atenção de decode é dividida ao longo do KV (split-KV): vários blocos de threads (CTAs) leem pedaços diferentes do contexto em paralelo e depois juntam os resultados. O kernel stock desliga o split-KV quando max_seqlen_q > 1, e um verify de 8 tokens (1 + 7 rascunhos) rodava em só 18 CTAs, com quase toda a GPU ociosa. O patch da diffbot mantém o split-KV no verify e cobre o verify inteiro num programa (BLOCK_M = q_len × 16): decode de 87–94 para 156–175 tok/s a 46K [medido: diffbot, SM120].

Por que o DFlash precisa de um marcador (G4). O DFlash não rascunha só a partir de tokens: ele consome os hidden states de 5 camadas do alvo (target_layer_ids [0, 11, 23, 35, 47]), e o vLLM entrega esses estados auxiliares pela interface do EAGLE3. O marcador SupportsEagle3 declara que a classe sabe expô-los. Na classe omni os ganchos já delegavam ao modelo de linguagem interno; faltava só o marcador [medido: tonyd2wild, patch 02].

O gerador é fail-closed (aborta se a âncora não bate), idempotente e capaz de detectar quando a correção já chegou ao upstream:

#!/usr/bin/env python3
import re, sys
src, dst = sys.argv[1], sys.argv[2]
s = open(src).read()
MARK = "# [mimo-recipe] cache_config per layer"
if MARK in s:                                                   # idempotente
    open(dst, "w").write(s); print("[overlay] já aplicado"); sys.exit(0)
if re.search(r"cache_config\s*=\s*layer_cache_config", s):     # a imagem nova já corrigiu
    open(dst, "w").write(s); print("[overlay] already upstream"); sys.exit(0)
# Âncora 1: início do __init__ do MiMoV2FlashDecoderLayer
a1 = "        quant_config = vllm_config.quant_config\n        layer_id = extract_layer_index(prefix)\n"
if s.count(a1) != 1:
    sys.exit("[overlay] âncora 1 não encontrada exatamente 1x — a imagem mudou; revise o patch")
s = s.replace(a1, a1 + f"        {MARK}\n        import copy\n"
    "        layer_cache_config = copy.copy(vllm_config.cache_config)\n"
    "        if layer_cache_config is not None:\n"
    "            layer_cache_config.sliding_window = None  # globais continuam globais\n")
# Âncora 2: as duas construções de MiMoV2Attention recebem cache_config

if n != 2:
    sys.exit(f"[overlay] esperava 2 construções de MiMoV2Attention, achei {n}")

              "                quant_config=quant_config,\n                cache_config=layer_cache_config,\n"
              "                partial_rotary_factor=")
open(dst, "w").write(s); print("[overlay] cache_config encaminhado (2 camadas-tipo)")

Leia as defesas uma a uma. O MARK torna o script idempotente: rodar duas vezes não aplica duas vezes. A regex de “already upstream” faz o patch se aposentar sozinho quando a imagem nova trouxer a correção. As âncoras são strings exatas com contagem exigida (1 e 2): se a imagem mudou, o script morre com uma mensagem clara em vez de gerar um arquivo meio patchado. E a correção em si é sutil: encaminhar o cache_config compartilhado ativaria o FP8, mas levaria junto o sliding_window: 128 do nível do modelo para as camadas globais. Por isso o patch usa uma cópia com sliding_window=None. A figura mostra os quatro estados possíveis.

Na correção ingênua, o FP8 funciona e as camadas globais passam a enxergar só 128 tokens: o needle falha, e nada no log avisa. Com o overlay 1 sozinho, o boot falha, porque o backend DiffKV Triton ainda rejeita FP8. Esse é o comportamento certo: falhar alto. Só com o overlay 2 (o porte do #58128 para triton_attn_diffkv.py e triton_unified_attention_diffkv.py) você chega ao estado bom. Para portá-lo, baixe o diff (curl -L https://github.com/vllm-project/vllm/pull/58128.diff), rode patch --dry-run contra os arquivos extraídos da imagem e, se não aplicar limpo (o PR é contra o main, a imagem é o dev449), refaça à mão com âncoras. Nunca copie arquivos do main para dentro da imagem: versões misturadas quebram imports de forma sutil.

4.4 Paridade truncada contra o HF

Rodar o modelo inteiro no HF é impossível num Spark. A técnica é a paridade truncada: comparar um modelo com as mesmas \(N\) primeiras camadas nos dois lados.

  1. Escolha N = 2. A camada 0 é global com MLP densa e a camada 1 é SWA com MoE: as duas cobrem todos os tipos de bloco. Em BF16 isso ocupa ~13 GB no HF (são 256 experts desquantizados de uma camada).
  2. vLLM: --hf-overrides '{"num_hidden_layers": 2}' --enforce-eager, sem speculator; TP=1 num nó e depois TP=2 entre os nós, porque é no TP=2 que vivem G2 e G3. Precisa do guard do #58184 (ou de um overlay equivalente) para ignorar o QKV das camadas 2–47. O texto gerado é lixo, e isso é esperado: o que se compara são as logprobs.
  3. HF: AutoModelForCausalLM.from_config(cfg_truncado, trust_remote_code=True, torch_dtype=bfloat16) com attn_implementation="eager" (o HF cai para eager quando há sinks) e um state dict desquantizado das camadas 0–1, com as fórmulas abaixo.
  4. Métrica: 32 prompts de 512 tokens, KLD top-20 por posição e concordância top-1. Referência [heurística]: KLD média < 1e-3 e top-1 > 99% em TP1; em TP2, o mesmo valor que em TP1. Se o TP2 diverge do TP1, o problema está no sharding (G2/G3), não no kernel.
  5. Testes de kernel da imagem, com o overlay montado: pytest tests/kernels/attention/test_triton_unified_attention_diffkv.py (os casos que exigem FA3/FA4 aparecem como skipped no GB10).
\[ W_{\text{FP8}}[i,j] = q[i,j]\cdot s_{\lfloor i/128\rfloor,\,\lfloor j/128\rfloor} \qquad\qquad W_{\text{MXFP4}}[i,j] = \mathrm{E2M1}\big(n[i,j]\big)\cdot 2^{\,e_{i,\lfloor j/32\rfloor}-127} \]
  • \(q\): valor E4M3 armazenado; \(s\): weight_scale_inv F32 do bloco 128×128 (respeitando os 4 chunks do QKV, 27 blocos de linha na GA e 29 na SWA)
  • \(n\): nibble de 4 bits; E2M1 mapeia 0…15 em [0, .5, 1, 1.5, 2, 3, 4, 6, −0, −.5, …, −6]
  • \(e\): byte E8M0 da escala, um a cada 32 valores
  • A convenção “nibble baixo = elemento par” (OCP/gpt-oss) precisa ser confirmada contra o GEMM do kernel
Critério de saída

Os overlays passam nos testes de CPU; paridade truncada TP1 = TP2 ≈ HF dentro do limiar; o boot completo loga todos os marcadores; o G1 é provado pelo pool 2× e o G2 pela soma não nula do QKV.

Passo 6 — Decodificação especulativa

Objetivo. Escolher o speculator e o k que maximizam os tok/s na sua carga, medindo a aceitação (Especulação: fundamentos, DFlash & DSpark).

Conceito. O drafter propõe k tokens e o alvo verifica todos numa passada. Cada passo emite os rascunhos aceitos mais um token do próprio alvo (a correção, ou o bônus quando tudo passa), e o ganho é

\[ \text{tok/s} \;=\; \frac{1 + \bar a(k)}{t_{\text{passo}}(k)}, \qquad \bar a(k) = \sum_{i=1}^{k} \alpha^{i} \;\;\text{(aceitação geométrica, modelo simplificado)} \]
  • \(\bar a(k)\): rascunhos aceitos por passo, em média
  • \(\alpha\): probabilidade de aceitar cada posição, se as posições fossem independentes
  • \(t_{\text{passo}}(k)\): custo do passo. Tem uma parte que sobe com k (verify maior, capture sizes maiores) e, com DFlash, uma parte quase fixa: o drafter rascunha o bloco inteiro de 8 numa passada, qualquer que seja o k usado

A aceitação depende do tipo de texto: altíssima em JSON, contagem e código, baixa em prosa; temperatura 1,0 a reduz em relação a 0. No MiMo há duas opções embutidas: DFlash (k de 1 a 7; o bloco de 8 é o do treino) e MTP (k de 1 a 3). O ngram é experimental. Meça com os contadores Prometheus do vLLM V1, lidos por diferença antes e depois de cada braço:

m() { curl -s http://$HEAD_IP:8888/metrics | grep -E "^vllm:spec_decode_num_(drafts|draft_tokens|accepted_tokens)_total" ; }
m > before.txt; python3 bench/run_category.py --category code --n 20; m > after.txt
# tokens aceitos por passo = Δaccepted / Δdrafts ; taxa por token = Δaccepted / Δdraft_tokens
curl -s http://$HEAD_IP:8888/metrics | grep accepted_tokens_per_pos    # curva por posição (decai com a posição)

O gabarito publicado [medido: tonyd2wild, vLLM TP2, DFlash k=7, FP8 KV, temperatura 0, C=1] dá, em tokens aceitos por passo (de 7): estruturado 6,85, código 5,23, matemática 5,00, JSON 4,00, raciocínio 2,62, prosa 1,23; e, em tok/s por stream, código 70,5, prosa 25,9, média 53,3. O simulador abaixo usa esses pontos para calibrar um modelo simples e perguntar: e se k fosse outro?

Mude a categoria e observe o k ótimo andar. Em código e texto estruturado o modelo prefere k = 7: quase tudo é aceito, e cada passo caro rende 6 a 8 tokens. A medição concorda na maior parte: no TP4 do tonyd2wild, k = 4 foi pior que k = 7 em matemática (82 contra 95 tok/s), texto estruturado (78 contra 115) e contagem (84 contra 136), e empatou em código dentro do ruído (86 contra 83) [medido: tonyd2wild]. Em prosa, com \(c_d = 0\), o modelo diz outra coisa: prevê ganho com k pequeno (ótimo em k ≈ 2). A medição não viu esse ganho: no mesmo TP4, k = 4 não melhorou a prosa (28 contra 35 tok/s em k = 7). É sinal de que o custo do passo tem uma parte fixa que o modelo linear ignora, porque o DFlash rascunha o bloco de 8 de uma vez. Suba o \(c_d\) e veja o ganho de k pequeno em prosa encolher até sumir. Trate “k ≈ 2 em prosa” como hipótese [a medir], não como recomendação. A comparação MTP × DFlash do SGLang (o MTP ganhou em prosa, 35,0 contra 25,8 tok/s, e perdeu em código, 46,0 contra 69,8 [medido: MiaAI-Lab]) usa outro drafter e não valida o efeito de k; ela só mostra que, em prosa, o drafter importa mais que o k. A interpretação provável da parte que cresce com k: num MoE, verificar k + 1 tokens acorda mais experts distintos por camada do que verificar 1.

Repare também na faixa de capture sizes. A lista 8 16 … 64 é perfeita para k = 7 e ruim para qualquer outro k: com k = 3, um batch de 3 sequências tem 12 tokens e é “padded” para 16. A caiu na versão pior desse erro: com 6 sequências × 7 tokens = 42, o teto padrão truncou a grade em 40 e o passo de 42 tokens rodava eager (−12% no agregado de c=6), até arredondar o teto para 48.

Protocolo: linha de base sem spec por categoria (código, JSON, prosa, raciocínio, resumo) com C=1; DFlash k ∈ {3, 5, 7} e MTP k ∈ {1, 2, 3} com o mesmo prompt set, em temperatura 0 e 1,0; repetir em 32K e 128K (o custo do verify em contexto longo depende do G7); escolher pela média ponderada da sua carga. Um laboratório que atende agentes de código pesa código e JSON.

Passo 8 — Benchmark

Objetivo. Números reproduzíveis de TTFT e TPOT, e tok/s na escada de concorrência e no prefill, com o método publicado (Benchmarking). Antes de medir, calcule onde você deveria chegar: o prefill é limitado por compute, e o decode sem spec é limitado por banda (GPU por dentro). Cada passo de decode lê, por rank, os experts ativos e tudo o que é denso:

\[ \text{bytes/passo/rank} \approx \underbrace{2{,}51}_{\text{8 experts}\times 47,\ \div 2} + \underbrace{1{,}44}_{\text{qkv FP8}} + \underbrace{1{,}61}_{o\_proj\ \text{BF16}} + \underbrace{0{,}63}_{lm\_head} + \underbrace{0{,}2}_{\text{router, MLP densa}} \approx 6{,}4\ \text{GB} \;\Rightarrow\; \text{tok/s} \le \frac{273\ \text{GB/s}}{6{,}4\ \text{GB}} \approx 43 \]
  • Tudo [estimativa] a partir dos shapes; o TP divide quase tudo por 2
  • Com o_proj em FP8 (#59083) o total cai para ~5,6 GB e o teto sobe para ~49 tok/s
  • Na prática espere 50–65% do teto, e depois multiplique pelo efeito do spec

A figura transforma essa conta numa esteira: os bytes de um passo passam do LPDDR5X para a GPU na velocidade da banda, e o tempo que a esteira leva é o tempo mínimo do passo.

Repare no que a régua revela: o decode sem spec deveria ficar em ~21–28 tok/s [estimativa]. Os 70,5 tok/s medidos em código só são possíveis porque cada passo emite ~6 tokens. E os 25,9 de prosa ficam dentro da faixa sem spec: é a mesma conclusão do simulador, agora por outro caminho.

Passo 9 — Tuning iterativo

Objetivo. Melhorar um alvo declarado sem quebrar o resto, com uma regra de decisão escrita antes do experimento (Benchmarking). A regra, declarada em docs/ antes de medir:

  1. Uma variável por vez, no desenho A/B/A (baseline → mudança → baseline, no mesmo boot ou em boots pareados), com ≥ 3 execuções por braço e a mediana.
  2. Aceite se o alvo melhora ≥ 3% nos dois lados do A/B/A, nenhuma métrica secundária piora mais de 2%, o canário de qualidade fica dentro do ruído (GSM8K-200 ± 3 questões; needle 100%; suíte de tools 100%) e não há OOM no pior caso.
  3. Rejeite e registre o resultado negativo no CHANGELOG, como o tonyd2wild fez com k=4 e com MNBT 8192.

Armadilhas do .env

Um .env é sourced pelo shell: aspas somem, e um JSON como {"image":8} chega quebrado. Por isso a aceita image=N e monta o JSON dentro do container, e o start.sh acima monta o --speculative-config a partir de SPEC_K. A também normaliza BOM e CRLF numa cópia 0600 antes de ler. Documente a precedência, porque cada receita decide de um jeito. Na o .env vence o ambiente (KV_CACHE_DTYPE=fp8 ./start.sh é ignorado se o .env define a chave), com exceção de ABLIT e HF_TOKEN, e as lanes start-fp8.sh e start-v030.sh usam variáveis OVERRIDE_* lidas depois do .env. Na é o contrário: o que o chamador exporta, inclusive vazio, vence o .env, exceto ABLIT, que é forçado a 0 depois do .env. Escolha uma regra, escreva-a no README e faça o resumo do launch imprimir o valor efetivo de cada chave.

O start.sh faz, nesta ordem: (1) doctor: ssh ao worker, a imagem nos dois nós com o digest igual, RoCE ativo, GPU ociosa, MemAvailable, disco, earlyoom desligado; (2) download + verify no head e sync (rsync ou NFS read-only); (3) extrai os arquivos da imagem, confere o sha256 e gera os overlays, abortando se uma âncora falhar; (4) recusa combinações proibidas antes de subir (KV_CACHE_DTYPE=fp8 sem overlay, SPEC_K > 7 com DFlash ou > 3 com MTP, capture sizes que não são múltiplos de k+1, flags inexistentes); (5) libera o page cache, sobe o worker, sobe o head e espera o /health com timeout de ~20 min (o boot frio leva ~11 min com mmap [medido: tonyd2wild]); (6) imprime as linhas de KV do log e roda o smoke.sh.

Além do MiMo: o desafio, o Mac e o checklist final

Desafio: Naive-N0.5-Flash, um modelo que o vLLM ainda não conhece

O Naive-N0.5-Flash (2026-09-27, MIT) tem 309B parâmetros e 15,5B ativos e deriva da base do MiMo-V2.5: mesma espinha dorsal (48 camadas, hidden 4096, 256 experts top-8, 4 KV heads, vocabulário 152.576). Mas troca as camadas globais por DeepSeek Sparse Attention (DSA) num layout ~5:1 SWA:DSA, sem nenhuma atenção densa global. Os pesos são BF16 (617,8 GB) e FP8 (~310 GB), com um Naive-N0.5-Flash-FP8-Draft. É o exercício “nível 2”: o Passo 4 deixa de ser overlay e vira implementação completa.

  • Passo 0: NaiveN05FlashForCausalLM, model_type: naive_n05_flash, remote code em modeling_naive_n05_flash.py, e nenhuma entrada no registry do vLLM.
  • Passo 1: não há mais camada global densa. O DSA ainda guarda KV e uma chave pequena do indexador para todo token (o armazenamento cresce com o contexto), mas cada query lê só o top-k (Atenção esparsa). Refaça a fórmula por camada DSA a partir do config: KV heads × dims × bytes + a chave do indexador.
  • Passo 2: nem o FP8 cabe em 2 Sparks. Quantize os experts (NVFP4 com llm-compressor ou ModelOpt, calibrado) e meça a KLD contra o FP8 oficial rodando em ≥ 3 nós, ou contra a referência HF truncada.
  • Passo 4: escreva o modelo como plugin out-of-tree, que registra a arquitetura sem fork. Reaproveite mimo_v2.py (MoE, SWA com sinks, loader do QKV) e troque as globais por um bloco DSA. O DSA do vLLM existe para MLA (DeepSeek-V3.2 e V4); DSA com GQA é trabalho novo, e no sm_121 os backends de sparse-MLA também não servem direto. Valide com paridade truncada N = 6, para incluir ao menos uma camada DSA.
  • Passo 6: confira se o FP8-Draft segue um formato que o vLLM já conhece (EAGLE3/DFlash) ou se também precisa de registro.

A troca central é de mecanismo, não de formato, e vale ver de perto. Numa camada global do MiMo, cada query lê o K e o V de todos os tokens anteriores. Numa camada DSA, um indexador barato dá uma nota a cada token passado, usando chaves pequenas guardadas à parte, e a atenção de verdade lê só os top-k.

Repare no que não muda: o armazenamento. A DSA ainda guarda o KV de todo token, porque qualquer um deles pode ser escolhido amanhã, e ainda soma a chave do indexador. O que ela corta é a leitura por query, de L para k (mais a varredura das chaves pequenas). É por isso que a conta do Passo 1 precisa ser refeita, e não apagada.

# naive_plugin/__init__.py — instalado com pip install -e . ; entry point "vllm.general_plugins"
def register():
    from vllm import ModelRegistry
    ModelRegistry.register_model("NaiveN05FlashForCausalLM",
