A coding agent talks to the model dozens of times per task, and on every call it resends everything: the system prompt with the house rules, the schema of every tool, the entire history of commands and outputs. Since the server remembers nothing between calls, the engine would redo the prefill of those same thousands of tokens every single time. Prefix caching starts from a simple idea: don't compute again what has already been computed. In the GLM recipe, a ~8K-token continuation turn drops from 8.53 s to 1.30 s of TTFT; in the Qwen recipe, a repeated 600K-token prompt drops from 336 s to 2.87–8.82 s. You will see why reuse is mathematically correct, how vLLM finds the reusable piece, and why hybrid models with drafters turned this idea into a minefield that the three recipes crossed with patches, flags and measurements. At the end comes an update: the second version of the GLM recipe, on the TensorFold engine, replaces block hashing with a few whole kept prompt states, and an identical 64K-token prompt comes back in under 0.07 s.

The same beginning, computed again

Recall prefill (chapter 10): for every prompt token and every layer, the model computes K and V (or the MLA latent, or the recurrent state) and stores them in the KV cache. The cost grows at least linearly with the number of tokens, and the full-attention part grows quadratically. Until prefill finishes, no response token comes out: that time is the TTFT.

Now look at real traffic. The OpenAI-compatible API is stateless: the server doesn't keep the conversation, and the client resends the full history on every turn. That scatters repeated prefixes everywhere:

Without the cache, the total cost grows with the square of the number of turns, because each turn reprocesses all the previous ones; with the cache, it grows linearly. And granularity matters: with 16-token blocks the leftover is negligible, but with the hybrids' 3,584 (section 4) a short conversation can lose almost everything. The GLM recipe measures ~940 to ~1,600 tokens/s of cold prefill, depending on the kernel version: without the cache, a 100K-token history would cost one to almost two minutes of TTFT on every turn.

The response goes into the cache too

A general vLLM mechanism: the full blocks of the assistant's response, filled during decode, also get hashed. If the client resends the previous response tokenized exactly the same way, it hits on the next turn. If the chat template strips the reasoning (<think>) from old messages or re-renders the response, the tokens change there and reuse stops at its beginning.

In the recipe: the server gives back the reasoning the client threw away

The GLM-5.3 template renders the reasoning of every assistant step that comes after the last user message (interleaved thinking). In a tool loop, a client that doesn't resend a step's reasoning_content makes the template write <think></think> there. That is a context the model never wrote, and the prompt stops matching the previous one at that point, so everything from there on goes through prefill again. In the TensorFold version of the GLM recipe, the server keeps the reasoning of replies that made tool calls (an LRU of up to 1,024 replies and 32 MiB of text, in TF_GLM_KEEP_REASONING and TF_GLM_KEEP_REASONING_MB), keyed by the call ids and by a SHA-256 of the conversation before them, and puts it back before rendering. A reply only goes back into the conversation it was written for. The rebuilt prompt is once again what the model generated, and the prefix matches again.

Why reuse is allowed: the causal mask

Reuse only makes sense if the KV of a prefix is the same in any request that starts with it. In a decoder this holds exactly, because of the causal mask (chapter 6): at layer \(\ell\), the state of token \(i\) depends only on tokens \(0\ldots i\).

\[ h_i^{(\ell)} = F^{(\ell)}\!\left(x_0, x_1, \ldots, x_i\right) \quad\Longrightarrow\quad k_i^{(\ell)} = W_K^{(\ell)}\, h_i^{(\ell-1)},\;\; v_i^{(\ell)} = W_V^{(\ell)}\, h_i^{(\ell-1)} \]
  • \(x_j\): the token at position \(j\) (vocabulary ID)
  • \(h_i^{(\ell)}\): the residual stream vector of token \(i\) after layer \(\ell\)
  • \(F^{(\ell)}\): the composition of the first \(\ell\) layers, with masked attention (\(j \le i\))
  • \(k_i, v_i\): the K and V rows that token \(i\) writes to that layer's cache; \(W_K, W_V\) are fixed weights

If two prompts share the same first \(p\) tokens, the first \(p\) rows of K and V are identical in every layer, no matter what comes after. The figure shows this with a one-layer toy model: two prompts, A and B, with their K matrices actually computed.

The equality depends on neither luck nor approximation: it is structural. That is why prefix caching is a lossless optimization from a mathematical standpoint. It only exists in causal models, and it only works for prefixes: an identical stretch in the middle of the prompt, preceded by something different, has a different KV.

Deep dive: bit-identical?

Mathematically, yes. Numerically, KV recomputed in a different batch can differ in the last bits, because the order of the sums inside the kernels changes (chapter 4); the GLM recipe saw greedy outputs differ even within the same arm of an A/B. Before blaming the cache for differences between cold and warm, measure the server's own variation.

What is stored and what isn't

The cache stores the KV of every layer: the MLA latent, the indexer's K cache and the recurrent state at checkpoint positions. Logits are not stored. To generate the first token the model must run at least the last position, which is why vLLM caps the hit at \(n-1\) tokens: even an identical prompt recomputes one token. In section 5 the cap becomes \(n-1-W\).

In the recipe: kept logits and equal bits

The TensorFold version of the GLM recipe answers the two boxes above differently. Along with the state at the end of a prompt, the engine keeps the head's logits row, and an identical prompt samples its first token straight from it, with no prefill at all: 64K tokens sent again take under 0.07 s, against 34 s the first time. And the bits become a contract: four requests served together give the same replies as each one alone (the batch doesn't touch the last bits), and “resumed = fresh” is an engine rule, not a hope. A state is only resumed at points of a 64-token grid, where the KDA prefill kernel lines up exactly as in a prefill from scratch, and keyed sampling draws the same token from the same logits. Section 9 shows the mechanism.

The hash chain: how vLLM recognizes a prefix

vLLM stores KV in blocks of block_size tokens (the paging from chapter 31). Prefix caching reuses these same blocks, and for that it needs a key that answers: “does this physical block contain the KV of exactly this prefix?”. Looking only at the block's own tokens isn't enough, because the KV of block \(j\) depends on all previous tokens. The solution is a chained hash:

\[ H_j = \operatorname{hash}\!\big(H_{j-1},\; (t_{jB},\, t_{jB+1},\, \ldots,\, t_{jB+B-1}),\; \text{extras}\big), \qquad H_{-1} = \texttt{NONE\_HASH} \]
  • \(H_j\): the key of block \(j\), which summarizes the whole prefix up to the end of that block
  • \(B\): the group's block size (16 by default; 256 in DeepSeek; 3,584 in GLM's MLA manager)
  • \(t_i\): the token IDs (not the text: what counts is the tokenization)
  • extras: additional keys, such as cache_salt (block 0 only), a LoRA ID and image hashes (multimodal)
  • NONE_HASH: the seed of the first block

Chaining gives, at O(1) cost per block, a key that identifies the entire prefix. In the classic form, only full blocks get a hash, because the contents of a partial block are still going to change. vLLM v0.28+ gained fine-grained hits that can end in the middle of a block, and section 4 shows why hybrids almost never get to use them. The algorithm is set by --prefix-caching-hash-algo: sha256 (default), sha256_cbor, xxhash or xxhash_cbor. None of the recipes changes the default.

In the figure, each block is a railcar, and each car's hash is computed from the previous car's hash (the coupling). The locomotive carries the NONE_HASH. The top train is the request that is already in cache, and the bottom one is the new request.

Notice the domino effect: a difference at position \(p\) invalidates every block from \(\lfloor p/B \rfloor\) on. Hence the most important hygiene rule of prefix caching: what is stable goes first (rules, tools, document) and what varies goes last (the question, the date, the user ID).

In the recipe: the effort directive that zeroed the cache (#144)

The DeepSeek checkpoint's encoder inserts the reasoning_effort directive right after the BOS, before the system prompt: BOS + directive add up to 93 tokens at max/xhigh, 80 at high and 0 at low/off/medium. With 256-token blocks, the hashes already diverge at block 0, and the cache splits into three “buckets”: 0 hits across buckets, 96–98% within each one. The hotfix hotfix-dsv4-issue144-effort-align.py (opt-in, DSPARK_ENABLE_ISSUE144_EFFORT_ALIGN=1) renders BOS + system + directive + rest: on a 4,646-token agent prompt, it goes from 0 to 18/18 shared blocks, at the cost of 1 token in the BPE merge at the seam; low, chat mode and conversations without a system prompt stay byte-identical to stock. The default is 0: the TTFT gain (2.3–2.7×, according to the report) is “to be validated” and the quality gate is still pending. Only chat_template_kwargs.reasoning_effort reaches the encoder, and DSPARK_I144_TOKENIZER_JSON (unset) points the test to a real tokenizer.json so it measures the true BPE merge instead of fixtures.

In the recipe: don't change the effort mid-conversation

In the GLM template, the effort word lands at character 39 of the prompt: switching reasoning_effort between turns causes a total miss in a conversation that was warm. Turning thinking on or off also changes the prefix, because the Reasoning Effort: line is only rendered with thinking. The same reasoning explains the tool_choice: "none" patch: it keeps the tools block in the prompt and forbids opening a tool call via bad_words, instead of removing the tools (which --exclude-tools-when-tool-choice-none would do), because removing them would change the shared prefix.

Classic trap

A system prompt that starts with “Current date and time: …” (an illustrative example) changes block 0 on every request and silently disables prefix caching. Put any variable field at the end.

Inside the BlockPool: table, reference counting and LRU

Finding the key is half the job. The other half is deciding which blocks stay in memory. In vLLM V1 everything lives in the BlockPool, which has three pieces:

KVCacheBlock
each physical block: block_id, ref_cnt (how many live requests use it) and block_hash (empty if the block is not cached). ID 0 is the null block, a placeholder that holds no data.
hash → block table
the index that answers “is there already a block with this \(H_j\)?”.
free queue
the doubly linked list of blocks with ref_cnt = 0. Allocations come off the head, and a block can be pulled out of the middle in O(1) when a hit “touches” it.

The life cycle has four verbs. Look up: get_computed_blocks walks the hashes from left to right and stops at the first miss, capped at \(n-1\) tokens. Touch: each hit increments the reference count and takes the block out of the free queue; two live requests can point to the same physical block, because full blocks never change again. Allocate: a new block comes off the head of the queue and, if it still had a hash, the hash leaves the table. This is lazy eviction: a free block stays useful until someone needs the space. Free: when the request finishes, ref_cnt drops and the blocks return to the queue in reverse order, so that the deepest one, whose hash covers the most tokens, is evicted first. Upstream, according to the documentation, they all go to the tail (LRU, evicted last). In the GLM recipe's image, according to its README, only the ones with a hash go to the tail; the ones without a hash go to the front (LIFO, recycled right away), and that is the rule the figures follow.

Analogy: the library shelf

A book on loan (ref > 0) doesn't leave the building. A returned book goes to the end of the returns shelf, with its label (hash), still available to whoever asks for the same title. When space runs out, the librarian recycles the book at the start of the shelf, the one returned longest ago. The first volume of a popular series (the system prompt) is requested by almost everyone; the tenth (the end of a long conversation) only serves whoever is in exactly that conversation, and that is why it goes first.

Hit rate, TTFT and how to see the cache at work

\[ \rho = \frac{\Delta\,\texttt{vllm:prefix\_cache\_hits}}{\Delta\,\texttt{vllm:prefix\_cache\_queries}}, \qquad \text{TTFT} \approx t_0 + \frac{n - h}{R_{\text{prefill}}} \]
  • \(\rho\): hit rate; the two Prometheus counters (at /metrics) count queried and hit tokens, and the rate comes from the before/after difference
  • \(n\): prompt tokens; \(h\): tokens hit (a multiple of the granularity, \(h \le n-1\))
  • \(R_{\text{prefill}}\): cold prefill speed (tokens/s); \(t_0\): fixed cost (scheduling, first decode step)

Check it against GLM: an 8,004-token follow-up hits \(h = 7{,}168\) and recomputes 836, and the TTFT drops from 8.53 s (cold) to 1.30 s. To see hits per request without opening Prometheus, the recipes use --enable-prompt-tokens-details, which adds usage.prompt_tokens_details.cached_tokens to the response. When streaming, the client must request "stream_options": {"include_usage": true} to receive the usage in the last chunk.

Flag--enable-prompt-tokens-details

Always on in Qwen (#63); docs/cache-reporting.md insists it is metadata only: it neither turns on nor tunes prefix caching, retention or the pool, and the /metrics counters exist without it. DeepSeek also always turns it on (the cold smoke test records cached_tokens: 0); GLM does so, since 2026-09-30 (#206, commit ecd1af6), in every launcher (start.sh, start-tp3.sh, start-tp4.sh); in snapshot 94ae731, only in the tp2-long-coding profile.

The cache is whatever is left of the pool

There is no separate memory for the prefix cache: it is the set of free blocks that still have a hash. GLM's boot line GPU KV cache size: 1,553,140 tokens is max_concurrency × max_model_len; that pool had 643 IDs and could hold only ~57K tokens of conversation in cache (section 6). Under load, the cache shrinks: in GLM's concurrency ladder with 50K tokens per lane, ×1 to ×4 kept a hit rate of 0.999–1.0 (TTFT ≤ 1.4 s); ×8 collapsed to 0.25–0.875 (p95 TTFT of 99–454 s) and ×16 to 0.189. Idle conversations have no reservation.

Hybrid models: the state that can't go back

So far, “the KV of a prefix” was a list of rows, one per token, which could be cut at any block. The three recipes serve models where this no longer holds. GLM-5.3 has 34 KDA linear-attention layers, and Qwen3.8 has 36 Gated DeltaNet layers (chapter 14). These layers keep a fixed-size recurrent state, updated at every token:

\[ S_t = \alpha_t\, S_{t-1}\,\big(I - \beta_t\, k_t k_t^{\top}\big) + \beta_t\, v_t k_t^{\top} \qquad(\text{delta rule with forgetting, schematic form}) \]
  • \(S_t\): the state matrix after token \(t\) (in GLM, \([32 \text{ heads}, 128, 128]\) in FP32 per layer and per rank)
  • \(\alpha_t, \beta_t\): forget and write gates, token-dependent (in KDA, forgetting is per channel)
  • \(k_t, v_t\): key and value of token \(t\)

The state is a snapshot, not a movie: from \(S_{10000}\) you cannot “subtract” the last 2,000 tokens and get \(S_{8000}\). To resume at position \(p\), you must have saved \(S_p\) exactly there. Saving at every token is out of the question: GLM's KDA state is 2,342,912 bytes per layer and per rank (2,097,152 of recurrent state + 245,760 of convolution state), versus 656 bytes per token of MLA KV. That is why vLLM saves states only at checkpoints, with mamba_cache_mode = align: at scheduler step boundaries aligned to blocks. The all mode is deprecated in v0.30, and in Qwen the model forces align (all raises an error).

Analogy: the video game without free saves

With full attention you can rewind to any frame of the movie. With a recurrent state it is like an old game that only saves at the map's checkpoints: if the new request diverges from the previous one in the middle of a level, you go back to the last checkpoint and play again from there.

Why the blocks get huge

All KV groups share a single pool with pages of the same size in bytes (chapter 31). Since the recurrent-state page is huge, vLLM increases the attention block size until an attention page can hold the state. In GLM, 2,342,912 ÷ 656 = 3,571.5 tokens, rounded up to the next multiple of 256 (an indexer requirement): 3,584 tokens, with mla_page = 3584 × 656 = 2,351,104 B, the value the boot log prints. In Qwen, the README cites a 1,600-token attention block, and the block drop patch cites 1,664 with MTP 3; the exact number depends on the KV and state dtypes (--mamba-ssm-cache-dtype) and on the TP. Consequence: hits only stop at multiples of 3,584 (GLM) or ~1,600/1,664 (Qwen). The 7,168, 10,752 and 14,336 tokens hit in GLM's 8k, 12k and 16k follow-ups are 2, 3 and 4 full pages.

Recall (chapters 14 and 31): a logical block is not a kernel page

The 3,584 is the manager's block: the unit of hashing, allocation and checkpointing. GLM's MLA kernel reads the KV in 64-token pages (56 per block), and shared checkpoints align to the LCM of the block sizes (the scheduler block). Splitting is only safe without padding: in a stretched page, like the drafter's in slot-share mode, the physical stride applies once per manager block, and splitting it would lead to out-of-bounds (OOB) access, which is why the worker refuses. Two overlays take care of the state in this regime: patch_mamba_align_chunking.py makes the prefill chunk stop at the page boundary (including smaller private Mamba pages), so that the checkpoint exists; patch_mamba_align_state_free.py frees superseded states that, under async scheduling, stayed stuck until the end of the request.

Another engine, another grain: 64 instead of 3,584

The 3,584 grain comes from a vLLM choice: all groups share a pool of pages with the same size in bytes, and the state's page rules. The TensorFold version of the GLM recipe has no such single page. Each request's KDA state lives in its own slot, outside the per-token cache pool, and the engine photographs whole states at a few points of a 64-token prompt grid. The grain drops to 64 for a different reason: with KDA_CHUNKED=1, the KDA prefill kernel works in 32-row sub-chunks at absolute positions, and only by resuming on the grid does the alignment match that of a prefill from scratch (chapter 14). The grid must be a multiple of 32, and the recipe keeps the default, 64. The price moves elsewhere. In vLLM, any page boundary still in the cache can serve as a hit; in TensorFold, only the few points where a photo was taken can (section 9).

The coordinator: the hit is the minimum across groups

With several groups, each one has its own answer to “how much of the prefix do I have?”. The hybrid coordinator (find_longest_cache_hit) looks for the longest full-attention hit (scanning left to right), then looks, within it, for the longest hit of the other groups (right to left) and keeps the smallest value:

\[ h = \operatorname{align}_{\,\operatorname{lcm}(B_g)}\Big(\min_{g \in \text{participants}} h_g\Big), \qquad h \le n-1 \]
  • \(h_g\): the longest prefix that group \(g\) can rebuild (attention: full blocks; state: last checkpoint; SWA: needs the last \(W\) tokens before the point)
  • \(\operatorname{lcm}(B_g)\): the “scheduler block”, the least common multiple of the groups' block sizes (3,584 in GLM; 256 in DeepSeek)
  • participants: groups that take part in prefix caching; GLM's KpoolTail (the indexer's circular scratch buffer) is left out

The minimum is a correctness requirement: if a group doesn't have the prefix, resuming there would mean running that layer with missing memory. In the figure, each lane is a KV group of one recipe, with its checkpoints and windows; the vertical line with the scissors marks the final hit.

Drag the control and notice the sawtooth: the hit rises in steps the size of the granularity, never continuously. In DeepSeek, with MLA in 256-token blocks, the step that matters is set by the SWA tails retained every 4,096 tokens (section 6); in an exact continuation, the previous request's boundary also works. Hence the line in hotfix #26's docstring: “a 21k prefix may cache ~20k instead of 21k; this is correct”.

In the recipe: the day SWA zeroed the cache (#26, #36)

DeepSeek-V4-Flash with DSpark runs four groups: 1× MLAAttentionSpec (block 256, --block-size 256) and 3× SlidingWindowMLASpec (128-token window, blocks of 64/4/8 with the same page size in bytes). The original fix combined v1 of the hotfix, which ignored SWA in the minimum, with tail retention VLLM_PREFIX_CACHE_RETENTION_INTERVAL=4096. That combination is what the 2026-08-13 CHANGELOG measured: x8 with ~22.8K, ~44.7K and ~88.4K warm 8/8 (ratios 0.9986, 0.9973 and 0.9996) and, at 32K, ~9 s warm versus ~421 s. But v1's lie cost dearly: on a ~21K Hermes prefix, MLA reported a 100% hit without the SWA tail, the engine skipped the prefill and filled the SWA KV with nulls, and the output turned into a “word salad” of </｜DSML｜parameter>, Chinese and loops (#36). v2 (hotfix-dsv4-issue26-hybrid-swa-min.py, always on; CI forbids v1) restores the minimum, reverts v1's injection and keeps the retention, but did not republish those numbers: the docstring and the CHANGELOG only state that hits remain large thanks to retention and stop at the last SWA tail.

The golden rule

“Skipping a Mamba miss is a correctness hole,” writes the GLM README. Never make a group lie about its own hit: if the hit is low, retain more checkpoints or align the prompt better, and only take a group out of the minimum with proof that it doesn't need the prefix (that is the proof GLM provides for the drafter in the next section). Raising --max-num-batched-tokens doesn't “fix” APC either, the README warns: the hit is bounded by the 3,584 checkpoint grid, and the recorded hit counts don't change with the chunk. Larger chunks only change costs, such as the activation reservation, which shrinks the pool, and a coarser interleaving with decode.

ParameterPREFIX_MATCH_UNIT → --prefix-match-unit

The smallest granularity at which a hit can end. Empty by default (vLLM resolves it); 64 is supported in the tested geometry (TP2/TP3/TP4) and 512 is invalid (“512 is illegal on this hybrid stack (KDA align block is 64)”). The conceptual point: a smaller granularity doesn't create state checkpoints that don't exist, and hits remain limited to points with saved state and a rebuildable drafter window. An overlay prevents the non-participating KpoolTail from vetoing fine hits; the participating groups still need to support the granularity.

Parameter--mamba-cache-mode align (forced)

Qwen doesn't pass the flag: the model forces align, and prefix caching is enabled by vLLM's default (also for Mamba models since v0.28). Besides GDN, PLE's short-conv is per-sequence state, treated as a Mamba-type layer, in the same align mode. Measured: a repeated 600K-token prompt drops from 336 s cold to 2.87–8.82 s (~40–110×). The cost is the ~1,600/1,664 granularity, which the state dtype also affects: a BF16 state shrinks the GDN page and allows a smaller attention block (1,664 instead of 3,200 with FP8 KV).

The drafter has a memory too

All three recipes use speculative decoding (chapter 35): a drafter proposes tokens and the target model verifies them. The drafter's context comes from the target: MTP and EAGLE use the target's hidden states; GLM's DFlash2 keeps its own KV with a 2,048-token sliding window; DeepSeek's DSpark stores features from the target layers in a 128-token window. When the target skips the prefill of a cached prefix, the drafter is left without that context, and sometimes the way out is the window replay: deliberately recomputing the end of the prefix. Each recipe ran into a different problem.

1. EAGLE's “lookahead” block (Qwen)

In an EAGLE-style drafter, the input at position \(p\) combines the target's hidden state at \(p\) with the next token. So the drafter's input at the last block of the prefix depends on a token that may not be shared by every request with that prefix (a didactic interpretation of the mechanism). As a precaution, vLLM drops the last matched block whenever there is an EAGLE-like proposer, MTP included: this is the EAGLE block drop. In Qwen this costs a whole block of 1,664 tokens of extra prefill per turn, and with bug #62 the second turn lost the entire cache.

3. The DSpark window that never filled up (DeepSeek)

In DeepSeek, DSpark's 128-token window is fed by the hidden states the target computes. On a hit, the target skips the prefix and only the suffix feeds the drafter. When an identical prompt is resent (retries, tool call prefixes, agent loops), the recomputed suffix can be shorter than 128 tokens: with 256-token blocks and the \(n-1\) cap, it ends up between 1 and 256. The window is incomplete and the response degenerates, for example into ["json followed by stop, deterministically at temperature 0. The fix caps the hit so that the target always recomputes a whole window:

\[ h_{\max} = \max\big(n - 1 - W,\; 0\big) \qquad (W = 128 \text{ in DSpark}) \]

In the recipe: the drafter's window goes into the photo

The window replay exists because, in vLLM, the DFlash2 KV is just another group of blocks, which may have been evicted or not retained. In the TensorFold version of the GLM recipe, a prompt's kept state carries the DFlash2 context window along (the rows of the 2,048-token sliding window that precede the point), and a request with DFlash2 only resumes from a state that brought the window. Since that context lives in a 2,176-row ring, the photo copies the ring's rows instead of slicing a flat buffer. Once resumed, the drafter is ready: the hit doesn't need to back off to rebuild the window. The cost goes into the memory of each kept state (section 9).

Retention: who deserves to stay in the cache

In a hybrid model, keeping a stretch of conversation costs a block in each participating group, and IDs are global and expensive: in GLM, each pool ID costs a whole page (11 MLA pages + 11 indexer pages, ≈25.9 MiB). The recipe's capacity-log overlay (GLM53_KV_CAPACITY_LOG=1) does the math that stock vLLM doesn't print, for an aligned 3,584-token segment with dense retention:

\[ \underbrace{1}_{\text{MLA}} + \underbrace{4}_{\text{4 Mamba groups}} + \underbrace{33}_{\text{drafter: } \lceil 2047/64\rceil + 1} = 38 \text{ IDs}, \qquad \Big\lfloor \tfrac{642}{38} \Big\rfloor \times 3584 = 57{,}344 \text{ tokens} \]
  • 642: usable IDs from a boot with 643 (ID 0 is the null block)
  • 33: the drafter's 64-token blocks covering the 2,048 window plus the EAGLE lookahead block
  • 57,344 tokens (16 segments): the ceiling of cached conversation with nothing running

That is 87% of the IDs spent on a group exempt from the minimum, which doesn't increase the hit. Worse: the drafter's final window is freed last and sits in the most protected position of the queue, while the MLA/Mamba blocks that actually provide the hit are evicted earlier. It is a priority inversion. The solution is sparse retention: saving checkpoints only every \(R\) tokens. With both retentions at \(R\), the cost per segment becomes \(1 + 37 \cdot 3584/R\): 10.25 IDs with \(R = 14{,}336\), 19.5 with 7,168 and 5.625 with 28,672. The price is that a late edit or branch falls back to the previous checkpoint, which can be very far away.

The model matches the recipe's two qualifications. With 0/0 and 390 blocks, four ~210K histories cost about \(4 \times (58 + 37) = 380\) IDs and fit: they were revisited in ~2.5 s, with 207,872 tokens hit each. With the dense grid, the same budget holds about 10 segments, and a 128K history would need ~1,330 IDs. During its own prime, the in-flight request holds the MLA pages; the Mamba checkpoints and drafter windows left behind return to the free queue with their hash and are evicted by the same prime's subsequent allocations (an interpretation based on the mechanism in section 3; the document records the result, not the cause). Measured: edits at 10% and 50% gave 0 hits in the dense runtime too. At 90% (an LCP of 114,666 tokens), dense hit 31 pages, 111,104 tokens, in 14.70 s; with 0/0 reuse was zero, and the operation took 112.49 s. The branch at 90% went from 3.35 to 99.89 s, and pure append was a tie (125,440 tokens, 2.80 s).

Upstream: from environment variable to argument

The VLLM_PREFIX_CACHE_RETENTION_INTERVAL variable belongs to the fork used in the pinned images. v0.29 brought --prefix-cache-retention-interval: the default of 0 keeps only semantic checkpoints, and dense retention is restored automatically for hybrid/EAGLE/MTP models. v0.30 removed the variable: anyone migrating the DS or GLM recipe needs to replace it with the argument, or the configuration silently disappears.

In the TensorFold version of the GLM recipe, the question “who stays?” changes units. Per-request control: namespaces, no-store and reset

The cache is shared by every request on the server, and sometimes you want a request to stay out of it. There are four levers, with very different effects:

cache_salt

A namespace. The salt enters the hash of block 0, and from there the entire chain: only requests with the same salt share blocks. The request keeps writing. Useful for isolating tenants and for honest cold benchmarks.

skip_reading_prefix_cache

Stock vLLM, read side: the request doesn't use the cache, but still writes its blocks.

skip_writing_prefix_cache

The no-store, a GLM overlay, write side: the request reads freely, inserts no hash at all, and its blocks go back to the front of the free queue.

/reset_prefix_cache

Empties the entire cache. Useful in benchmarks; dangerous if exposed.

Why did GLM have to invent no-store? In the free queue, hashed blocks go to the tail (section 3). A one-off batch request parks its blocks behind the server owner's idle 80K conversation, and the owner's blocks become the next ones evicted: the job reorders the LRU in its own favor. The salt doesn't solve it (it isolates, but still writes), and neither does skip_reading (it only acts on reads). In the figure, the conveyor belt is the free queue, with the head on the left.

Reset routes and the Bearer guard

/reset_prefix_cache is a development route; VLLM_SERVER_DEV_MODE=1 mounts the whole package (/sleep, /rlhf, /rpc…). GLM's overlay no. 24, patch_cache_reset.py, with GLM53_EXPOSE_CACHE_RESET=1 mounts only /reset_prefix_cache, /reset_mm_cache and /reset_encoder_cache, which reply {"success": bool} (false while any blocks are still held). The concern is security: the API-key middleware only protects /v1, /v2, /inference and /cohere, so routes at the root answer without the key even with VLLM_API_KEY set. That is why the default is 0, only the TP2 launcher applies it, and kits with untrusted clients should leave it off.

Deep dive: why isolate tenants

A cache hit is observable: the TTFT drops. On a server shared by clients who don't trust each other, this opens a timing side channel, in which one client could test whether another sent a certain prefix by measuring its own latency (an interpretation; it is the usual reason for per-tenant salts). cache_salt solves this without turning APC off, because each tenant only hits its own blocks.

Beyond the GPU: LMCache and KV connectors

Update: kept prompt states in TensorFold

The GLM recipe gained a second version, . The checkpoint is the same (GLM-5.3-Flash with the routed experts in 4-bit EXL3), on the same two DGX Sparks, but the engine is no longer vLLM: it is TensorFold v0.6.0 with 53 patches (the overview is in An exact engine, and the full recipe in Swapping the engine). Up to this section, “GLM recipe” meant the vLLM version. The new one has no BlockPool, no hash chain and no APC. The problem stays the same, because the client still resends the history every turn, but the answer is different. Instead of giving every block a hash so that any aligned prefix can be reused, TensorFold keeps a few whole states, at hand-picked points. And it promises something APC doesn't: a prompt resumed from a kept state gives the same bits as the prompt computed from scratch.

What goes into the photo

Section 4 called the recurrent state a snapshot, a photograph and not a movie: from \(S_{10000}\) you can't go back to \(S_{8000}\). TensorFold takes the metaphor literally. A kept prompt state gathers everything a request needs to continue from that point as if it had done the whole prefill:

per-token rows
the latents of the 11 DSA layers and the indexer keys, in FP8. They are not copied: they stay in the conversation's extent, a contiguous range of rows in the shared pool (chapter 48), and the kept state points to it.
fixed-size state
the recurrent states of the 34 KDA layers, the convolution windows and the tail of the indexer rings. This is the part that doesn't grow with the prompt.
drafter window
the rows of the DFlash2 ring that precede the point. A request with DFlash2 only resumes from a state that brought the window along (section 5). Together with the fixed-size state, it makes up the reservation each entry sets aside at startup: ~45 MiB per the v1.3.2 CHANGELOG, ~91 MiB measured on two Sparks in v1.10 (patch 0097).
logits row (end only)
when the point is the end of the prompt, the head's logits row, so that an identical resend samples the first token without running anything.

Only drafted requests without images keep states. To resume, the engine looks for the longest kept state whose ids are, token for token, a prefix of the new prompt (and whose DFlash2 window came along). There is no hash: the comparison runs directly on the ids, against a few dozen candidates at most.

Where to take the photos: grid, system, divergence and end

Each photo costs fixed memory, so the engine picks a few points, each for a reason:

  1. At the prompt's last multiple of 64 With a prompt grid \(G\), every prompt chunk starts on a multiple of \(G\), and the prompt's own state sits at \(B = G\lfloor n/G \rfloor\). If the prompt doesn't end on the grid, the request prefills up to \(B\) as a prompt of that length would, takes the photo and continues from there to \(n\). So “any prompt extending prompt[:B] passes through the same state there, fresh or resumed”. In the recipe, \(G = 64\), implied by KDA_CHUNKED=1.
  2. At the end of the system block With SHARED_PREFIX=1, the first occurrence of <|user|> marks where the system prompt ends. A photo there serves any new conversation with the same system prompt, even though none of them extends another conversation's whole prompt token for token.
  3. At the divergence point Also with SHARED_PREFIX=1: where the new prompt stops matching some kept prompt, as in a branch or a subagent. This is the shared prefix. These two extra points fall on the grid, only count if they add ≥ 256 tokens past the resume point (and past the other point), and there are at most 2 per request.
  4. At the end, with the logits row When \(n\) falls on the grid, the end photo also carries the logits row. This is the replay, the topic of the next subsection.

An agent request keeps 1 to 3 states: its own and up to two shared-prefix ones. Measured in the recipe (README: the two Sparks at the default configuration, with GPU clocks capped at 2,200 MHz): a new conversation with the same 7.9K-token system prompt prefills in 0.13 s instead of 4.24 s, with the same replies. Compare with section 4. In vLLM, the 3,584 grain comes from the size of the state's page, and any page boundary still in the cache can serve as a hit. In TensorFold, the 64 grain comes from the KDA prefill kernel (chapter 14). It is 56 times finer, but the points are few: only a boundary where a photo was taken can serve as a hit.

Three different replays

The word shows up with three meanings in this atlas. The window replay of section 5 deliberately recomputes the end of a prefix to rebuild the drafter's window. The recurrent-state replay (chapter 14) redoes the recurrence with the accepted drafts only. And TensorFold's prompt replay is the opposite of both: it recomputes nothing.

The full hit: keeping the logits row too

Go back to the box “What is stored and what isn't”, in section 1: logits don't go into the cache, and that is why vLLM caps the hit at \(n-1\) tokens. Even an identical prompt has to run the last position to get the first token's distribution. A kept state alone has the same problem: it holds caches and KDA states, but it doesn't say what the reply's first token is. The recipe's replay patch solves this by keeping, along with the state at the end of a prompt, the head's logits row: each rank's slice of the vocabulary, before any grammar mask. A resend with exactly those ids resumes there and samples the first token from that row, “prefilling nothing”.

Why does the reply come out equal, and not just similar? Because TensorFold's sampling is keyed (chapter 9): the Gumbel noise that decides each token is a pure function of the key (the request's seed or a hash of the prompt), the position and the token id. Same logits and same key give the same token. The count of what is redone on an identical resend goes like this:

\[ r_{\text{TF}}(n) = \begin{cases} 0, & n \bmod 64 = 0 \;\;(\text{replay}) \\ n - 64\lfloor n/64 \rfloor \le 63, & \text{otherwise} \end{cases} \qquad r_{\text{vLLM}}(n) \approx n - 3584\Big\lfloor \tfrac{n-1}{3584} \Big\rfloor \ge 1 \]
  • \(r(n)\): tokens that go back through prefill when an \(n\)-token prompt is resent identical
  • \(n \bmod 64 = 0\): only then is the prompt's own point its end, and the photo carries the logits row; off the grid, the engine resumes at \(B\) and redoes the tail
  • \(r_{\text{vLLM}}\): a simplified version of GLM's hybrid APC (3,584-token pages and the \(n-1\) cap); the DFlash2 window replay (section 5) may back off one more page

Measured in the recipe: an identical 64K-token prompt takes 34 s the first time and under 0.07 s the next, with the same reply. On the vLLM side, the GLM recipe recorded a resend of 814,571 tokens in 2.748 s, with 813,568 tokens coming from the cache: the 1,003 redone are exactly the \(r_{\text{vLLM}}\) of the simplified formula (227 pages of 3,584). And the ~8K follow-up drops from 8.53 to 1.30 s (sections 3 and 5). A third party, the jayleaton project (TensorFold 0.3.4, another checkpoint and other patches), measured that on this model a replay in vLLM recomputes ~8.2K, 5.7K and 11.1K tokens at 8K, 32K and 64K, far more than the simplified formula. None of this is a controlled A/B: engine, dates, workloads, configurations and conditions differ (the TensorFold numbers were taken with GPU clocks capped at 2,200 MHz).

An album with 32 slots

How many photos fit? Here the unit is neither a block nor a pool ID: it is the count of states. TF_GLM_CACHE_ENTRIES caps how many states are kept (8 in TensorFold, 32 in the recipe), and, in v1.3.2, the oldest goes when the count passes the cap, “however much of the pool is free”. The order is LRU: resuming from a state makes it the most recent (the policy changed later: section 10). The states also live inside the cache pool and are the first to give way when a live request needs room. With 8 slots and 1 to 3 states per agent request, three or four alternating conversations were already pushing each other out (issue #17). The recipe raised it to 32: each entry reserves ~45 MiB at startup by the v1.3.2 math, ~1 GiB more in total (v1.10 measured ~91 MiB per entry).

In the figure, each polaroid is a kept state, colored by conversation. The conversations take turns, and each request looks for the longest photo that is a prefix of its prompt, prefills the rest and pins up new photos.

Turn on LONE=1 in the figure and the album loses the other conversations' photos at every change. This is the lesson of TF_GLM_MULTI_LONE. The single-stream CUDA graphs recorded the addresses of slot 0 and of the pool's first rows, the “home” (chapter 29). With 1, a request decoding alone moves there to use those graphs, and evicts the kept prompts of the other conversations that lived in those rows. The gain was 0.6 to 0.9% of speed with one stream. The price showed up in interactive sessions: with three conversations taking turns (~4.5K tokens each, 6 warm turns), 0% of the prompts came from the cache with 1, against 98.1% with 0, and each conversation re-read its whole history every turn. The recipe has pinned 0 since v1.3.1. The moral holds for any engine: a speed optimization in another subsystem can zero the hit rate without a single error in the log, so measure the cache along with the tokens per second.

vLLM × TensorFold: two bets on the same problem

vLLM's APC (GLM recipe)

  • Chained hash of full blocks; reuse at any aligned prefix still in the cache
  • 3,584 grain in the hybrid (the state's page) and the \(n-1\) cap
  • Many cheap prefixes, evicted block by block (LRU, ref_cnt)
  • Full decode blocks get a hash too: the previous reply can hit
  • Drafter: replay of the 2,048-token window after the hit
  • Cold and warm may differ in the last bits

Kept states (GLM·TF)

  • Whole photos at a few points: grid, end of system, divergence and end of prompt
  • 64 grain (KDA kernel); replay with the logits row redoes 0 tokens
  • At most 32 states, ~45 MiB fixed each (~91 measured in v1.10), LRU by count in v1.3.2; later, superseded first, fork points kept and NVMe (section 10)
  • From reading the code, the reply gets no photo: the next turn resumes from the previous prompt and redoes reply + new message
  • DFlash2 window saved in the photo: no replay needed
  • Resumed = fresh, bit for bit (an engine contract)

Neither bet dominates. TensorFold wins where agent traffic weighs the most: resending the conversation, opening new conversations with the same system prompt and repeating an identical prompt, with exact, near-instant reuse. It loses on arbitrary reuse: a prefix that matches up to the middle of a kept prompt, with no photo there, doesn't serve, and, in v1.3.2, more than 32 states don't fit, however much free memory there is (since v1.10 the count can follow a share of the pool, and states that leave can go to NVMe: section 10). vLLM's APC reuses any aligned boundary of thousands of prefixes at once, but pays the hybrid's 3,584 grain, the \(n-1\) cap and the drafter window replay (interpretation from the two recipes).

Beyond memory: prompt states on NVMe

Section 9's album lived only in memory. A state that left it, through the count cap or because the pool needed room, and every one of them after a restart, cost a full prefill on the next turn: ~2 minutes at 200 thousand tokens. After v1.3.2, the GLM·TF recipe gained a third floor, each Spark's local NVMe. That is the spill tier: patch 0088 (by Robert Wojciechowski, in v1.9) and, with PARALLEL above 1, patch 0128's block store, which brings in the NVMe tier of BadAd84's PR #118. It is section 8's LMCache idea, only inside the engine and under the same contract: a prompt resumed from disk gives the same reply as a prefill from scratch. It ships off (SPILL_GIB=64 and a SPILL_DIR at the same absolute path on every Spark turn it on) and applies to states of 8,192 tokens or more (SPILL_MIN_TOKENS).

Three floors: pool, pinned memory and disk

A kept state has two parts of very different sizes (section 9). The per-token rows grow with the prompt: on disk, ~6.2 MB per 1,000 tokens, per Spark. The small part, with the recurrent state and the DFlash2 window, is ~91 MB per Spark at any length. Between the pool and the disk sits a pass-through floor, pinned memory: a 256 MiB write ring (TF_GLM_SPILL_STAGE_MIB) and 16 read slots of one block each (TF_GLM_SPILL_READ_BLOCKS). On the GB10 that memory also comes out of the same LPDDR5X, and the pool pays for the slots (~14 thousand tokens at PARALLEL=4). For the same reason, files are written with O_DIRECT: the page cache would share memory with the pool.

  1. Blocks that later turns share. Rows go to disk in 2,048-token blocks, each named by a hash chained over the token ids and the state's lineage (the computation it belongs to). It is section 2's hash chain put to another use: there it finds blocks in memory; here it names files. A conversation's next turn, or a branch that resumed from it, names the blocks its earlier turns wrote and writes only the new ones, and a block whose bytes equal one already on disk becomes a link. Measured: a turn that added 10.4 thousand tokens to a 40-thousand-token conversation wrote 68 MiB (6 new blocks), not the whole state.
  2. Written when kept, not when evicted. When a state is kept, only the small part and the block the prompt's end cuts leave the GPU right away; the other rows go to disk a little at a time, 4 blocks between rounds, through the pinned ring. That is why a conversation survives an eviction, a clean restart, a kill -9 or a watchdog restart. Measured: a 40-thousand-token conversation kept 3 s before a kill -9 of every rank came back from disk after the restart in 1.4 s (21.8 s from scratch), with the same reply.
  3. Read ahead and checked. A restore reads the blocks on 8 threads into the pinned slots and checks each one against its CRC-32. The engine copies the blocks read into the pool between rounds, at most 40 ms per gap (TF_GLM_SPILL_LOAD_MS, one budget for every restore in flight), so the other streams keep decoding. Before reading, rank 0 asks every Spark whether it holds the state; a file that fails on any of them is dropped on all, and the prompt goes through prefill.
  4. Leaves when room runs out, in a fixed order. Each conversation keeps the 4 newest states on its path (SPILL_TURNS) and trims the older ones as soon as a new one is written; they free only their small part, because the newest turn still names every block. The disk has a cap (SPILL_GIB per Spark) and a free-space floor (SPILL_MIN_FREE_GIB, 50 GiB). When room runs out, states go in this order: old turns (with SPILL_TURNS=0), abandoned branches (an edited or retried message), whole conversations, least recently used first, and shared prefixes last, such as the system prompt other conversations start from. SPILL_QUOTA caps one conversation's share: in issue #122, a single conversation's per-turn states filled 128 GiB in 30 minutes and pushed the others out.

Why does the disk beat the prefill, and by how much? A restore grows with the bytes; prefill grows faster than the prompt, because each new token's attention reads an ever longer history.

\[ t_{\text{restore}}(n) \approx t_0 + \frac{b\,n}{B_{\text{eff}}} \qquad\qquad t_{\text{recompute}}(n) = \frac{n}{r_p(n)} \]
  • \(n\): tokens in the state; \(b\): ~6.2 KB per token and per Spark on disk (README)
  • \(B_{\text{eff}}\): a restore's effective bandwidth; from the points measured at 260 thousand tokens (~1.6 GB per Spark), ~3.5–4.0 GB/s idle and ~2.6–3.0 GB/s beside a decoding stream (our math)
  • \(t_0\): fixed cost (asking the ranks, opening the files, the small part)
  • \(r_p(n)\): prefill speed, which drops with length: 1,952 tok/s at 8 thousand tokens, 1,642 at 262 thousand, 1,015 at 982 thousand (GLM-5.3-Flash, two Sparks, GPU clocks at 2,200 MHz)

A system prompt prefilled only once

There is a waste no cache fixes: several agents that start at the same instant on a system prompt the server hasn't kept yet (a cold start, a new harness, a changed tool list). Each would prefill the same prefix, side by side. With PREFIX_WAIT=1 (patch 0128, off by default because it changes admission), a request whose prompt starts at a point another request is still prefilling waits for that state, outside the queue, and resumes from it. This is the prefix wait, the single-flight pattern: one computation in flight per key, and whoever arrives later waits for its result instead of repeating it. Measured with six agents at once on a fresh 12-thousand-token system prompt (two Sparks, PARALLEL=8, every reply equal to its own run alone): all answered in 14.7–15.0 s, against 45.7–47.0 s; the slowest first token at 13.5–13.8 s, against 45.0–46.2 s; and 60,160 system-prompt tokens no longer recomputed. TensorFold's native engine does the same by default since 1.1.6 (TENSORFOLD_PREFIX_WAIT_MS, 60 s): with eight requests on a fresh 28-thousand-token system prompt on a GB10, the last first token came at 31 s instead of 201 s with Qwen3.8-27B.

Beyond the Spark: the same floor in a cluster

A GPU → host memory → local SSD hierarchy for the KV is what LMCache (section 8) and NVIDIA Dynamo's KV block manager (KVBM) do on H200 clusters, and what vLLM's KV connectors expose. Three things change scale (our interpretation). On a discrete GPU, host memory is a real floor, larger and slower than HBM, on the other side of PCIe; on the GB10 it is the same LPDDR5X and only a pass-through. With many nodes, a block's name must hold across the whole cluster (a chained hash does that), and a cache-aware router sends the conversation to where its blocks are. And the figure's math still holds: keeping only pays off when restoring is cheaper than recomputing, which depends on the length, on the disk or network bandwidth and on each machine's prefill speed.

Measuring and configuring: prefix caching in the three recipes

Measuring prefix caching calls for a counterintuitive precaution: the cache contaminates its own benchmarks. If you run the same “cold” prompt twice, the second run is already warm. A comment in GLM's benchmark records a case: reruns reused the previous session's text, and the “cold” TTFT dropped from 10.3 to 1.9 s. The recipes' protocol has five rules:

  1. Cold/warm pairs with unique content GLM's tests/bench_prefix_cache.py (--runs 3, or --concurrent 4 for isolated chats) sends a cold turn (system + document + question) and a warm one (same history + a follow-up question), with a session salt in the content on each invocation. Qwen's bench/longctx.py puts a UUID at the start of the prompt, and DeepSeek's 2026-08-14 results record unique cold prefixes.
  2. Reset between cold runs, when available The bench POSTs to /reset_prefix_cache if GLM53_EXPOSE_CACHE_RESET=1; the salt guarantees honest cold runs even with the route off.
  3. Rate from the counters Read vllm:prefix_cache_{hits,queries} before and after each turn and use the differences; the response's cached_tokens confirms it request by request.
  4. Compare with the page model In GLM the maximum hit is \(\lfloor n/3584 \rfloor \times 3584\): a 6.8k conversation reuses one page (~53%), and a 7.7k one reuses two (~93%). The bench reports hit_efficiency = measured hit ÷ full-page expectation; 1.0 means the page model was met.
  5. Cold prefill only with a unique salt Prefill tok/s = prompt tokens ÷ TTFT. Without a salt, APC “cheats” and the number is worthless (chapter 45).
In the recipe: measuring reuse without APC counters

The TensorFold version has no vllm:prefix_cache_*. /health shows how many prompts are kept (kept_prompts) and how much of the pool is free (pool_tokens, pool_free_tokens), and the README measures reuse as “first time” against “next time” of the same request. The salt rule still holds in another outfit: a cold run is only cold if no kept state is a prefix of it. And the LONE case (section 9) shows why you measure the hit rate along with the tokens per second.

Recipe from scratch: prefix caching for a new model

  1. Classify the layers Only full, causal attention? APC works out of the box, and the granularity is the block size. Recurrent state, SWA or an indexer? Expect a large granularity and a hit bounded by the minimum across groups.
  2. Read the boot log Write down the groups, the block sizes and the scheduler block. Remember that “GPU KV cache size” is concurrency, not cache size.
  3. Look at the drafter EAGLE/MTP loses the last block (there is an option to keep it); drafters with a window need replay after the hit.
  4. Arrange the prompt Stable first, variable last. Don't vary effort or thinking mid-conversation.
  5. Turn on observability and measure Use --enable-prompt-tokens-details, the counters and cold/warm pairs with a salt, and compare with the page model.
  6. Only then tune Retention if the traffic is append-only, no-store for batches, salt for tenants. KV offload only with a plan for when it fails.
