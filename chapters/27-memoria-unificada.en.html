On a datacenter GPU, VRAM is a vault all its own: the operating system and the file cache live in a different memory, on the other side of a bus. On the DGX Spark that wall doesn't exist. The GB10's CPU and GPU share 128 GB (nominal) of LPDDR5X, and everything Linux keeps around (processes, page cache, driver buffers) comes out of the same place as the weights and the KV cache. This chapter explains why the vLLM recipes use --gpu-memory-utilization between 0.75 and 0.87 instead of the upstream 0.92, why an rsync can block the boot, why a host that runs out of memory hangs instead of throwing an OOM, and how to build a node's budget, line item by line item. At the end, the new variant of the GLM recipe shows another way to budget: no GMU, just the MemAvailable at startup minus a reserve, refusing before loading anything that doesn't fit.

One RAM, two tenants

There are three common ways to wire the CPU and GPU to memory, and each one changes what “GPU memory” means.

  1. Discrete GPU (PCIe) The GPU has its own memory (HBM or GDDR), and the CPU has the host RAM. Every weight is copied over PCIe, and there are two independent budgets: filling the host's file cache doesn't take a single byte away from VRAM.
  2. Coherent superchip (Grace + Hopper/Blackwell) Two physical memories linked by NVLink-C2C, in a single address space. Each side can read the other's memory, but “far” is slower than “near”, as in a NUMA system.
  3. Unified memory (UMA) A single physical pool for both processors: the GB10 (20 ARM cores and a Blackwell sm_121 GPU on the same SoC) and the Apple M chips. There's no copy over PCIe, but the CPU and GPU compete for capacity and bandwidth (~273 GB/s theoretical; see Inside the GPU).

How much of the 128 GB CUDA sees depends on the kit and the kernel: 121.69 GiB per node on the Qwen pair (the number used in our math) and 123.72 GiB in a log from the GLM kit, which runs its own kernel. Don't copy anyone else's number: read MemTotal and the Free memory on device boot line on your own machine.

In unified mode, the disk → RAM → GPU path crosses no bus, but the same file can occupy RAM twice during loading: as page cache (the copy of the file that Linux keeps) and as a CUDA allocation (the tensor the GPU uses). On a discrete GPU, the first copy doesn't weigh on VRAM; on the GB10, both come out of the same pool.

Analogy: the shared-apartment fridge

A discrete GPU is every roommate having their own fridge: to use an ingredient, someone crosses the street (PCIe) carrying a grocery bag. Unified memory is one fridge for two: nobody carries bags, but if one roommate crams the door with containers “I might use later” (page cache), the other one can't find room for the KV cache. This chapter is about who throws the containers out, when, and who sounds the alarm before the fridge bursts.

Apple Silicon faces the same dilemma: mlx_lm.server calls mx.set_wired_limit(max_recommended_working_set_size) (19.07 GB, ~74% of the RAM on a 24 GB M4; sudo sysctl iogpu.wired_limit_mb=N raises the ceiling until the next reboot), and the vllm-metal examples use a --gpu-memory-utilization of 0.5 to 0.7. On a unified machine, the fraction you give the GPU is taken from the operating system.

Pitfall: every tool measures something different

On the GB10, nvidia-smi shows [N/A] for memory. Measure with vLLM's Free memory on device … boot line and with MemAvailable from /proc/meminfo (the available column of free), not with the free column, which ignores reclaimable cache.

The Linux memory census: MemFree is not MemAvailable

To Linux, RAM is a set of pages, fixed-size blocks: 4 KiB on x86 and on most ARM kernels. The GLM kit runs a custom kernel (6.17.13-rocket64k) with 64 KiB pages. Check yours with getconf PAGESIZE, because it will matter when the weights are loaded. Every page falls into a category, and each category reacts differently when memory gets tight:

anonymous memory
Process heaps and stacks (Python's anonymous RSS). With no file behind it, the only way out of RAM is to swap.
page cache
Chunks of files that were read or written. Clean pages can be dropped at any moment; dirty ones must be written to disk first.
kernel / slab
Kernel structures (inodes, dentries, network buffers), partly reclaimable.
free
Pages with no owner: the MemFree.

A healthy Linux system has almost no free memory, because it uses idle RAM as disk cache. That's why /proc/meminfo publishes two numbers. MemFree counts the pages with no owner. MemAvailable estimates how much a new program could allocate without swapping, adding in the droppable cache and slab (it's the math in si_mem_available()):

\[ \begin{aligned} \text{MemAvailable} \approx\; & (\text{MemFree} - R) \\ & + \big(C - \min(\tfrac{C}{2},\, W_{\text{low}})\big) \\ & + \big(S_{\text{rec}} - \min(\tfrac{S_{\text{rec}}}{2},\, W_{\text{low}})\big) \end{aligned} \]
  • \(R\): totalreserve_pages, the sum of each zone's “high” watermarks plus the zone reserves (lowmem_reserve)
  • \(C\): file page cache (active + inactive lists)
  • \(W_{\text{low}}\): sum of the “low” marks; the kernel assumes part of the cache and slab has to stay
  • \(S_{\text{rec}}\): reclaimable slab, with the same discount

On the GB10 this difference decides whether the model boots. torch.cuda.mem_get_info() returns the host's MemFree, and page cache counts as “used”, even though it's droppable. The vLLM boot check on an integrated GPU, on the other hand, reads MemAvailable. The two numbers disagree all the time.

Click “vLLM allocates”: the kernel drops clean cache on demand, and the allocation fits. GLM's problem was never a lack of memory, it was a program measuring the wrong thing. After the rsync to the worker, the log recorded buffer_size (1268776960 B) exceeds device memory budget (1255964672 B): 0.5 × MemFree ≈ 1.17 GiB for a ~1.18 GiB buffer, with more than 100 GiB of reclaimable memory right next to it. When it didn't abort, io_depth shrank from 512 to a few dozen.

Deep dive: why the container can't fix it on its own

The obvious remedy is sync; echo 1 > /proc/sys/vm/drop_caches (echo 3 also drops dentries and inodes). But inside a container /proc/sys is read-only without CAP_SYS_ADMIN. That's why GLM clears the cache on the host, before docker run, and the patch inside the container sizes the loader by MemAvailable, which is correct even without the cleanup.

In TensorFold

The engine behind the GLM recipe's new variant wrote this lesson into its own code. The function that recognizes the GB10 (CUDA flags it as is_integrated) warns that the “free” figure of a GPU living in host memory is MemFree, which counts the page cache as used. So, on an integrated GPU, the startup budget is MemAvailable minus a reserve, with the reclaimable page cache counted as available. On a discrete GPU, it takes the smaller of the GPU's free memory and the host's. An rsync right before startup doesn't shrink that budget (details in Update: the memory budget in TensorFold).

Going deeper: what even MemAvailable can't see

MemAvailable leaves memory out too, and two pieces of it showed up in the GLM·TF recipe after v1.3.2. The first is parked pages: on kernel 6.7 or newer, a bulk free leaves GiBs of free pages on the per-CPU lists (the count: lines under pagesets in /proc/zoneinfo), in neither MemFree nor MemAvailable, and they only come back slowly, at ~0.05–0.1 GiB/s over 1–2 minutes. Copying the image to the worker (docker save / docker load) parked 5–9 GiB there, and the first start of a new image compiles a kernel in the container ~1 s before the budget is read, which parks 2.4 GiB more. Since TensorFold reads MemAvailable only once, at startup, the first start budgeted 89.44 GiB on rank 0, against 94.86 GiB for a warm restart of the same image, and kept 2 prompt states instead of 32. Patch 0122 adds to MemAvailable the excess on those lists above their resting level (high_min), read once and logged: the first start now budgets 94.58 GiB (rank 1: 95.20). TensorFold's native engine got the same fix in 1.1.6.

The second is the display reservation: the GB10 firmware keeps ~2 GiB for a monitor, which a headless Spark never uses and MemAvailable never counts. With DISPLAY_KV_MIB (patch 0072, off by default), part of it joins each rank's KV pool without taking host memory: 1,792 MiB add ~277 thousand tokens at PARALLEL=8, with the same replies (0087 does the same through kindling spark-os's dispramd: 2,032 MiB, +317,440 tokens on three Sparks). Headless Sparks only, because a monitor's framebuffer lives in that reservation; the recipe refuses the setting while an output is connected. The lesson transfers partly: on a discrete GPU such as an H200, the budget comes from the GPU's own free memory and the host page cache doesn't enter the math, but the habit of checking where the engine gets its “free” from, and of not reading that number right after the machine freed a lot of memory, applies on any node.

gpu_memory_utilization when the OS lives next door

--gpu-memory-utilization (GMU, \(u\)) is the fraction of the device's total memory that vLLM is allowed to budget: weights, peak activations, the process's “non-torch” allocations and the KV cache. CUDA graphs (kernels recorded once and replayed with no launch cost; see CUDA graphs and warmup) are in or out depending on a knob. In the boot profile run, vLLM measures what's occupied and hands the rest to the KV (the full math is in PagedAttention and the KV budget). What matters here is what's left outside:

\[ B_{\text{vLLM}} = u \cdot M,\qquad \text{KV} \approx B_{\text{vLLM}} - W - A - O - \chi\,G,\qquad H = M\,(1-u) - E - S \]
  • \(M\): total visible memory (121.69 GiB per node on the Qwen pair)
  • \(W, A, O\): weights, peak activation and non-torch allocations
  • \(G\): CUDA graph estimate; \(\chi = 1\) with VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=1, otherwise 0
  • \(H\): headroom the host sees (≈ MemAvailable under load)
  • \(E\): what the GPU holds outside the budget: CUDA context, driver and NCCL buffers, unprofiled workspaces and, with \(\chi = 0\), the graphs themselves
  • \(S\): OS, services and host processes

On a discrete GPU, \(1-u\) is left over only for the CUDA context, which is why the upstream default is high (0.92 in v0.30.0). On the GB10, \(1-u\) is everything the system has left: \(0.01 \times 121.69 \approx 1.2\) GiB per hundredth or, in the words of the GLM README, each 0.01 is 1.2 GiB of host headroom.

Are the CUDA graphs inside or outside the budget?

With VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=1 (the upstream default; CG_ESTIMATE=1 in GLM), vLLM does a dry-run capture of the largest graphs and subtracts the estimate from the KV: the graphs stay inside the GMU, and an overestimate steals KV. In GLM, the estimate is 2.43 GiB while the captured graphs actually consume -0.19 GiB, so ~2.6 GiB of KV is reserved and never used. With 0 (DeepSeek's choice), nothing is subtracted: the graphs are captured after the KV pool and live outside the GMU, inside \(E\).

The Qwen boot falls in the second regime (the kit doesn't set the variable, but the math gives it away): 101.61 − 68.52 (weights + non-torch) − 1.07 (activation) = 32.02 GiB of KV, without subtracting the 0.54 GiB of graphs. The log confirms it: --kv-cache-memory=33651431445 (31.34 GiB) to fit into requested memory … Current kv cache memory in use is 32.02 GiB. The real pool overshot what fit in the budget by ~0.7 GiB, about the size of the graphs captured outside it (our interpretation). On UMA, every GiB outside the GMU comes straight out of the host.

In Qwen at 0.835, the budget was 101.6 GiB, but the CHANGELOG measured the driver holding 114.5 GiB per node: some 13 GiB of \(E\) (our math). Add a ~6 GiB OS floor and almost nothing is left: in a 6-worker soak, both nodes ran with MemAvailable between 0.3 and 0.9 GiB. That's why Qwen dropped to 0.80 on 2026-09-26: ~4 GiB less KV per node, same decode speed, and on the v0.30 lane (BF16 KV) a one-hour soak kept 4.5 GiB (head) and 7.8 GiB (worker) free. With 64.46 GiB of weights per GPU, the README sums it up: Weights, not KV, are what eats this box.

Why it matters: things that live outside the budget

The GMU only limits what vLLM profiles. In chunked prefill, a long prompt is sliced into pieces of up to N tokens per step so the decodes don't stall (Scheduler and chunked prefill). In DeepSeek, raising that N (--long-prefill-token-threshold) from 1024 to 2048 dropped the head's MemAvailable from 2.55 to 0.99 GB; the adaptive chunk (1024 with active decodes, otherwise the whole step) left 2.36/2.28 GB, versus 3.8–5.2 at baseline. These are workspaces allocated outside the GMU. In GLM, the multimodal cache is held at 1 GiB (MM_PROCESSOR_CACHE_GB=1, instead of 4) and compilation uses a restrained MAX_JOBS: keep the compile light on a UMA host.

What if the engine has no GMU?

The GMU is a vLLM design choice, not a law of the GB10. The variant of the GLM recipe runs on an engine that budgets by the MemAvailable at startup minus a reserve written in GiB (14.5) and refuses, before loading a single weight, any configuration that doesn't fit. The host headroom that here gets tuned in hundredths of \(u\) is, there, a number you write down directly. The comparison is in Update: the memory budget in TensorFold.

Inside the budget: weights, activations, KV and the allocator

Inside \(B_{\text{vLLM}}\), the order is fixed: weights, a profile run with the largest single-step batch (max_num_batched_tokens, the scheduler's per-step token ceiling, counting both decodes and prefill chunks), graphs (if estimated) and the rest for the KV. On UMA this measurement wobbles with whatever the host is doing. Hence the second tool: pinning the KV in bytes with --kv-cache-memory-bytes, which makes vLLM ignore the GMU for the KV.

GLM · KV pinned at 11 GiB

With InstantTensor, at 850k/0.85 only ~12.4–12.5 GiB of KV was left (versus ~17–18 without it), less than the 13.56 GiB of an 850k request, and the boot failed after the weights. The README simply notes: Model loading took 79.65 GiB is identical either way; the difference shows up only in Available KV cache memory. The cause wasn't measured (our hypothesis: the 4 GiB pinned ring counts as used in the profile run). The recipe pins --kv-cache-memory-bytes 11811160064 (11 GiB; previously 14): 1,233,779 tokens with the drafter's compact pages.

Qwen · the log suggests bytes

At 0.835 the log suggests 38.52 GiB of KV to fully utilize gpu memory, a calculation based on the free memory at boot (108.79 GiB). On UMA, free memory is the host's headroom, and it was at 0.835 that the host dropped to 0.3–0.9 GiB. Use the byte suggestion only to pin the pool (the 31.34 GiB fit in the requested budget), never to grow it. The TP1 lane accepts KV_CACHE_MEMORY as a pin.

DeepSeek · pure GMU

No pin: at 0.835 the boot shows 17.04 GiB = 2,331,430 tokens (2.22× of 1M). Boot-to-boot variation reaches ±0.6 GiB on the head, and the pool is sized by the poorest rank.

GLM·TF · an estimate, no profile run

TensorFold doesn't measure: it estimates from the weights' headers and a bytes-per-token formula, before allocating. The KV is neither a pin nor whatever the GMU leaves over: it's a single pool shared by the 4 requests, holding one full 1,048,576-token window (the most one request can use) plus whatever is left of MemAvailable − 14.5 GiB, up to 12.5 GiB (2,922,496 tokens at the measured startup). The decision is deterministic, but whatever the formula doesn't count has to fit in the reserve.

The PyTorch allocator and fragmentation

Between vLLM and the driver there's one more layer: PyTorch's caching allocator. Since cudaMalloc is expensive, it asks the driver for large segments and slices them into blocks. When a tensor dies, its block stays in the cache, “reserved but not allocated”. The problem is fragmentation: blocks from different segments don't merge, and a request larger than any hole creates yet another segment, even when the free space adds up to more than enough.

With PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True, each stream gets a segment that grows: the allocator reserves a large range of virtual addresses and maps physical pages at the end as needed (CUDA's virtual memory API). A large request reuses the free tail and extends only by the difference.

At the step with the request for 9, the top lane has 20 free units in total (three holes of 6 and two leftovers of 1), but no hole of 9, so a new segment is born. On UMA, that “reserved but idle” memory is missing from the host.

Loading 164 GiB: mmap, page cache and O_DIRECT

Before serving, the checkpoint has to travel from the NVMe to the GPU allocations. There are three paths, and on UMA the choice changes how much RAM is occupied during loading.

mmap: the file becomes memory

mmap maps a file onto a range of the address space. Reading the tensor is reading a pointer: the first time, a page fault brings the page from disk into the page cache. It's the standard safetensors path (zero-copy and lazy; Checkpoints covers the format). The pages are file-backed: the kernel can drop them and reread them whenever it likes, which is great for the host, but the GPU is copying from pages that can vanish mid-copy.

Pinned memory, H2D and the page size

A host→device (H2D) copy is done by a DMA engine, which needs pages that stay put: pinned memory. If the source is regular memory, the driver copies it into an internal pinned buffer or pins the pages temporarily. On the GLM kit's 64 KiB page kernel, cuMemcpyHtoDAsync hangs when the source is a file-backed mmap mapping. The fix is clone(): copy each tensor from the mmap into anonymous memory before it reaches the GPU. This was observed on that kernel, not on every GB10: Qwen and DeepSeek load through vLLM's stock mmap, with no clone (Qwen with --load-format safetensors --safetensors-load-strategy lazy), and the GLM patch stays inert on 4 KiB. Run getconf PAGESIZE before copying the fix.

O_DIRECT: skipping the page cache

With O_DIRECT, the disk writes straight into a process buffer, bypassing the page cache. InstantTensor (--load-format instanttensor) uses a ring of pinned buffers with many reads in flight (io_depth) to keep the NVMe queue full. The host doesn't “bloat” during loading, but the loader needs a budget for the ring, and that budget was the one being taken from MemFree.

In GLM (issue #204, before the new staging), InstantTensor loaded 164 GiB in ~65–70 s cold, versus ~290–300 s for auto without staging. With the cold-load patch and a full cache: 164 GiB in 36 s at 4.82 GB/s and /health at 230 s, close to the 4.9 GB/s ceiling of a single O_DIRECT reader on that NVMe (dd bs=16M iflag=direct). With a clean cache, the patch speeds nothing up (35–36 s in both cases): what it does is allow the boot after an rsync.

Tip: drop_caches or posix_fadvise?

Qwen uses the tweezers and keeps the sledgehammer (sync && echo 3 | sudo tee /proc/sys/vm/drop_caches) for when something else has filled up the cache.

Swap and the silent UVM livelock

Swap is anonymous memory's escape valve: when RAM runs out, the kernel writes process pages to disk and brings them back when they're touched. vm.swappiness (0–200) says how much it prefers swapping over dropping page cache. With 0, swap is not forbidden, just postponed until pressure gets severe, and Qwen's HANDOFF notes that the Spark already ships configured that way.

On the GB10, GPU allocations go through the UVM driver (nvidia-uvm), the same one that shows up when a cgroup blows its limit (UVM GPU1 BH invoked oom-killer …). GLM documented that, if the kernel sends vLLM pages to swap (or brings them back) under pressure, the driver can fall into a livelock: it spins without making progress.

The most treacherous symptom is /health returning 200: in V1, it only reads an error flag and never probes the workers. VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS doesn't fire, and in the worst case the node drops off SSH (sshd can't fork). Detection looks at progress: poll /metrics every 60 s and alert when, for N consecutive ticks (N = 10 is calm), num_requests_running + num_requests_waiting > 0 and prompt_tokens_total + generation_tokens_total don't change.

On UMA, running out of memory means no OOM: the host hangs

On a discrete GPU, blowing past VRAM produces a readable CUDA out of memory. On the GB10, exhausting the pool happens inside the driver's context: the kernel hangs with no OOM, and not a single journal line survives. The Qwen HANDOFF session took the host down three times. The next section exists to turn “hung host” into “dead container” or “readable error”.

GLM's recovery took 18 minutes, without anyone setting foot in the server room: logs first, a straight docker kill (graceful stop hangs), cycle the swap, and a trivial CUDA probe (a@a at 2048×2048) before concluding the driver is lost. nvidia-smi may keep showing 96% after the kill; that's cosmetic.

Fences: watermarks, cgroups and watchdogs

The kernel defends memory in layers. The main thresholds are each zone's watermarks, computed from two parameters:

\[ W_{\min} = \texttt{min\_free\_kbytes},\qquad \delta = \max\!\Big(\tfrac{W_{\min}}{4},\; M\cdot\tfrac{\texttt{watermark\_scale\_factor}}{10{,}000}\Big),\qquad W_{\text{low}} = W_{\min}+\delta,\quad W_{\text{high}} = W_{\min}+2\delta \]
  • \(W_{\min}\): minimum reserve; below it, whoever is allocating does direct reclaim (stops and reclaims memory on its own)
  • \(W_{\text{low}}\): below this, kswapd wakes up and reclaims pages in the background
  • \(W_{\text{high}}\): kswapd stops once free memory is back at this level
  • \(M\): managed memory (≈ 121.69 GiB); simplified single-zone model

With the Spark defaults (HANDOFF), min_free_kbytes=45167 (44 MB) and watermark_scale_factor=10, you get \(\delta \approx 0.12\) GiB: kswapd only wakes up with ~0.16 GiB free (~0.1% of RAM). Against a UVM allocating GiB per second, there's no floor, no warning and no valve. The package the HANDOFF measured during the single-Spark exploration raises the floor to 4 GiB and the scale to 300: \(\delta \approx 3.65\) GiB (3% of RAM), so kswapd wakes up with ~7.65 GiB free (~6%) and stops at \(W_{\text{high}} \approx 11.3\) GiB. Another measurement matches the formula: with the 4 GiB floor, MemFree was 112 GiB and CUDA saw 100.68 GiB (112 − 11.3 ≈ 100.7). Interpretation: CUDA sees MemFree minus the reserve up to the “high” mark.

With a 1 s interval and moderate allocation, the watchdog catches it. At 3 s (the poller that failed in the HANDOFF) and with a GiB/s collapse, memory crosses from “above 6” to “zero” between two readings: in the real incident, it went from 7.7 GiB to a hang in 25 s. That's why memwatch.sh calls itself the second line of defense: a userspace poller cannot catch a GiB/s collapse alone.

cgroups: per-container fences

A memory cgroup (docker --memory X --memory-swap X, equal values so there's no extra swap) limits the container, and above the limit the OOM killer acts only inside it. Do GPU allocations count? The HANDOFF contradicts itself: §1 records an EngineCore OOM-kill at 14.7 GiB with --memory 16g; the correction in §0 says GPU parameters are not charged (72 GiB of weights showing as “used” on the host, container at 10 GiB). In practice, the cap limits the host side and the GMU limits the GPU side; to know for sure, measure it on your own machine.

What TensorFold documents

The documentation of the new variant's engine confirms the correction in the HANDOFF's §0: on the GB10, the server's allocations come out of host RAM but are not charged to a container's memory limit (docker run --memory, memory.max). The limit neither holds back the weights and cache nor keeps them from squeezing the rest of the machine. To leave room for other containers, the engine recommends asking for a smaller --context or --parallel, and the recipe says to raise the reserve (MEMORY_RESERVE_GIB) when other work shares the Sparks. Neither relies on a cgroup cap.

Offloading to the CPU on a machine with no separate CPU: Qwen's PLE

On a discrete GPU, CPU offload moves a rarely used tensor to host RAM and frees up VRAM. Qwen3.8-Flash-Next has the perfect candidate: the N-gram PLE table (~320M rows × 160; see N-gram & MTP), addressed by hash and read only at layer 1, so its rows can be looked up on the CPU (VLLM_PLE_CPU_OFFLOAD=1).

On UMA, “CPU RAM” is the same pool: offloading doesn't free physical memory, it needs ~51 GB free, and the log showed Available RAM: 44.92 GiB (OOM/thrash). Hence PLE_OFFLOAD=false in dual. But the HANDOFF records two real wins: less UVM pressure at load time (71.78 GiB through UVM instead of 98.66) and, with the table in mmap, evictable page cache instead of anonymous RAM. The non-evictable footprint drops from ~104 GiB + KV to ~77 GiB + KV, and that's what let Qwen fit on a single Spark (TP1).

How the offload works (and where the GB10 broke it)

A separate process (PleOffloadWorker) builds the model on the meta device (tensors with a shape but no memory) and materializes only the PLE on the CPU. Each step's inputs (input_ids, query_start_loc, ngram_context) live in shared, pinned CPU buffers (cuMemHostRegister); the result goes to each TP rank's GPU buffer via CUDA IPC; requests travel over ZMQ PUSH/PULL with msgpack. Synchronization used stream memory ops: cuStreamWaitValue32 makes the stream wait until an integer in memory reaches a value, something that can be captured in a CUDA graph.

The GB10 reports CU_DEVICE_ATTRIBUTE_CAN_USE_STREAM_MEM_OPS = 0. Even so, the wait “returns success”, the next kernel blocks the host thread, and inside the graph nothing waits: after capture, the worker spun forever in ple_offload_wait. The patch replaces that semaphore with a host-side handshake using a sequence number.

Why a sequence number and not a “ready” flag? The flag would have to be reset every step, and resetting opens up a race. A monotonic counter needs no reset: the GPU waits for flag ≥ seq, and a stale value can never pass for a new one. The wait spins 2000 times and then sleeps 50 µs per iteration, so it doesn't burn a core; since the PLE layer sits at layer 1, the lost CPU/GPU overlap is negligible. On graph replay, the batch is rounded up to the captured size, and the padding rows (no request behind them) use NULL_BLOCK_ID and are masked in the PLE's short-conv, so they don't corrupt anyone's state.

The general lesson of the IPC bugs

In a buffer shared between processes, anything that silently changes the buffer (wrong dtype, a resize on an out=, a skipped constructor) turns into a GPU waiting forever or fluent gibberish, no error. The only symptom of the worst bug was a UserWarning: An output with one or more elements was resized. Treat that warning as fatal on an IPC path, and validate the buffer's dtype, shape and bytes at boot.

NFS: one checkpoint, two nodes

With TP=2, each node reads the checkpoint at boot. With rsync, the worker keeps a second copy (164 GiB in GLM, ~126 GiB in Qwen, ~157 GiB in DeepSeek; ~330 GiB duplicated in GLM's TP3). With NFS, the head exports the Hugging Face cache read-only and the worker mounts it as if it were local. The cache's structure is covered in Checkpoints; what matters here is the transport.

Why several connections? A TCP connection is usually processed by one core on each side and rarely fills a 200 Gb/s link. With nconnect=8, the client opens eight connections and spreads the requests across them. In a simplified model (our interpretation), \(T \approx \min(n \cdot t_{\text{conn}},\ B_{\text{link}},\ B_{\text{head}})\), where \(B_{\text{head}}\) is how much the head can serve. Don't confuse this ceiling with GLM's 4.9 GB/s: that one is for local O_DIRECT reads, nfsd reads through the head's page cache, and the real NFS throughput was never measured in the repository. As a counterpoint, Qwen's lazy load over NFS took 458 s for ~126 GiB, well below what the cable can do. GLM's .env.tp3.example sums up the intent: nconnect=8 is what makes a cold load use the cable.

Update: the memory budget in TensorFold

The GLM recipe now has a second version : the same EXL3 checkpoint, the same two Sparks, but a different inference engine, TensorFold v0.6.0 with 53 patches (the engine is the subject of TensorFold's exact engine; the recipe, of the GLM recipe on TensorFold). Everything this chapter said about --gpu-memory-utilization applies to vLLM. TensorFold has no such knob, because it asks a different question. vLLM asks “what fraction of the total is mine?”. TensorFold asks “how much does Linux say is available right now, and how much do I leave untouched?”.

The starting point is the lesson from the swap section, which the recipe's README puts like this: on the Spark's unified memory, running out tends to freeze the machine rather than fail an allocation. If running out of memory hangs the host instead of raising an error, the only safe moment to find out that a configuration doesn't fit is before allocating anything. Hence the startup sequence:

  1. Read what is really available. On an integrated GPU like the GB10, the budget starts from the MemAvailable in /proc/meminfo, and the reclaimable page cache counts as available. CUDA's free figure, which on the GB10 is MemFree, is left out: that's the rsync trap from the second section. On a discrete GPU, it takes the smaller of the GPU's free memory and the host's.
  2. Set the reserve aside. The reserve \(R\) is what startup leaves free: by default \(\max(4\ \text{GiB},\ \text{MemTotal}/10)\), ~12.2 GiB on a Spark. The variable TENSORFOLD_MEMORY_RESERVE_GIB replaces it (minimum of 2). The recipe uses 14.5.
  3. Estimate without loading. The startup estimate reads only the safetensors headers (name, shape and dtype of every tensor) and adds up the resident weights. For loading, it adds a staging peak of three times the largest layer, because CPU expert lists/stack, GPU uploads and tiled outputs can coexist during one layer load. The caches come from a bytes-per-window-token formula. There is no profile run.
  4. Search for the largest window that fits. A binary search finds the largest \(L\) with weights + caches(\(L\)) ≤ budget. The two ranks exchange their results through an all-gather and keep the smaller one, so the window is the same on both Sparks.
  5. Refuse before loading. If the requested window doesn't fit, startup fails, reporting the largest one that does and warning that no model weights or KV caches have been loaded. The recipe's start.sh reads the line largest fitting prompt-plus-reply window: N tokens and restarts once with --context N.
  6. What's left becomes pool. The up to 4 requests (4 in v1.3.2, PARALLEL=4; up to 8 since v1.5, patch 0069: what changed) don't each get a window: they share one pool of per-token caches that holds one full window plus whatever is left of the budget, up to KV_POOL_GIB = 12.5 GiB per Spark (the engine's default is 3). Any request can grow to the full window, and kept prompts and several long conversations at once live in that pool (PagedAttention and the KV budget compares it with vLLM's paging).
\[ \begin{aligned} B &= A_0 - R, & L^{*} &= \max\{\,L \le L_{\text{nat}} : E(L) \le B\,\}, \\ P &= \min\big(P_{\max},\ B - E(L^{*})\big), & \text{free}_{\min} &\approx R - \Delta_{\text{peak}} \end{aligned} \]
  • \(A_0\): MemAvailable at startup (start.sh warns if either Spark has less than ~110 GiB)
  • \(R\): reserve (14.5 GiB in the recipe); \(B\): budget
  • \(E(L)\): header-based estimate for a window of \(L\) tokens (88.09 GiB on rank 0, with \(L\) = 1,048,576)
  • \(L_{\text{nat}}\): the model's native window, 1,048,576 tokens
  • \(P\), \(P_{\max}\): the pool beyond the window and its ceiling (KV_POOL_GIB = 12.5 GiB per Spark)
  • \(\Delta_{\text{peak}}\): what the server uses beyond its own estimate, ~10 GiB at the peak (a 1M prompt). The last formula holds when the pool fills the whole budget (our interpretation)

At the startup the recipe measured, rank 0's estimate was 88.09 GiB and the pool hit its ceiling: 2,922,496 tokens (between ~2.1 and 2.9 million, depending on free memory at startup). MemAvailable sat at 7.0 GiB (rank 0) and 10.5 GiB (rank 1) at idle and, at the worst moment, with a 1M prompt, at 5.6 / 9.5 GiB. The README's arithmetic closes the loop: the server goes ~10 GiB past its own estimate at the peak, so the reserve also sets the lowest free memory, and 14.5 leaves ~4.5–5 GiB on the head. The measured minimum (5.6) sits a little higher because the pool hit its ceiling before using the whole budget, and that leftover stays free too (our interpretation). It's the same floor of a few GiB that the vLLM recipes chase by tuning the GMU in hundredths, only written directly in GiB. Rank 1 has more to spare, partly because the vision tower (1.05 GiB of weights + 0.75 GiB of workspace) lives only on rank 0 (interpretation).

Who absorbs the variation: the host's headroom or the pool?

Both engines obey the same physics: one RAM, one ceiling and a host that freezes if the ceiling is hit. What changes is who pays when the machine isn't empty at startup. In the GLM recipe on vLLM, the KV is fixed in bytes (11 GiB, 1,233,779 tokens), so the engine's demand doesn't depend on what else lives on the machine; the GMU only enters the startup checks. Another process holding memory doesn't change the capacity: either the preflight refuses (MemAvailable below GMU × total + 2 GiB) or, if startup gets through, the host's headroom under load shrinks by the same amount. In TensorFold, the reserve fixes the headroom, and what shrinks is the capacity: first the pool, then the window (the restart with the largest one that fits) and, finally, startup refuses.

Neither one is free. TensorFold's budget is safe on UMA, but the capacity depends on the state of the machine at startup: the same command yields anywhere from ~2.1 to 2.9 million pool tokens, and the budget is read once, so memory freed later only becomes pool on a new startup (interpretation based on the code). vLLM with a fixed KV gives the same capacity on every boot, but pushes the variation onto the host's headroom. That's why this chapter spent so many lines on hundredths of GMU, watchdogs and fences.

There's a second difference: measuring or estimating. vLLM's profile run measures the real activation peak, but it wobbles with whatever the host is doing at boot (hence GLM's byte pin). TensorFold's estimate is a formula: deterministic and done before allocating, but only as good as what it models. And it can be wrong in both directions: whatever it overcounts becomes lost KV (with no profile run, nothing corrects it later), and whatever stays outside (CUDA context, NCCL, graphs, transient peaks) has to fit in the reserve.

What the estimate gets wrong: passing peaks

In a unified pool, a peak lasting a few seconds is as dangerous as a permanent allocation, because the host has no idea it's temporary. The recipe's patches go after both of the estimate's errors: they flatten peaks that no startup estimate captures well, and they take out of the math what it used to overcount. Overcounted scratch

The opposite error: the estimate counted split-K and attention partials that the prompt kernels in use don't even allocate (patch 0028). With no profile run, every overestimated byte turns into a lost KV token.

📌

RDMA pinned memory

The RoCE all-gather registers a pinned host region with the network cards (hence --cap-add IPC_LOCK and --ulimit memlock=-1 in docker run). A pinned page is never swapped out or dropped, and on the GB10 “host” and “device” are the same LPDDR5X: it comes out of the same pool (our inference). Here it's tiny, ~3 MiB per Spark with TF_ROCE_MAX_KB=512 (2 sources × 2 slots × 512 KiB of receive + 2 × 512 KiB of send, our arithmetic), against InstantTensor's 4 GiB pinned ring in the vLLM recipe. The transport is covered in NCCL and RDMA.

Tip: the idea works outside TensorFold too

Even on an engine with a GMU, you can copy the design: read MemAvailable at startup, subtract a reserve that covers the peak outside the budget and refuse before loading, reporting what would fit. GLM's preflight on vLLM (MemAvailable ≥ GMU × total + 2 GiB, before stopping healthy containers) is a cousin of that idea. The difference is that it only checks startup; TensorFold's reserve is chosen by looking at the measured peak (14.5 − ~10 ≈ 4.5 GiB free at the worst moment).

In the recipes: a node's complete budget

A node's budget is a sum with a constraint. Inside the GMU: weights, extra copies, activations, non-torch, KV and, with the estimate turned on, the graphs. Outside: driver, unprofiled workspaces, non-estimated graphs, OS, services and page cache. And the total must never touch the 121.69 GiB.   • \(O\): overhead (OVERHEAD_GIB=5.6; measured 3.37 non-torch + 1.92 activation + 0.12 graphs = 5.41)
  • \(M_{\text{MTP}}\): MTP drafter (MTP_GIB=1.49; off by default on TP1, because every GiB counts)
  • \(\text{KV}_{\text{need}} = L \times 29{,}482\) B: KV for one sequence of \(L\) tokens (BF16, 28.8 KiB/token measured)
  • \(\text{KV}_{\text{target}}\): KV_TARGET_GIB (8 in the script, 20 in tp1/.env.sample; the HANDOFF cites 12, a discrepancy)
  • \(S_{\text{host}}\), \(R_{\text{OS}}\): HOST_SLACK_GIB and OS_RESERVE_GIB=16

Two details about the calculator. With KV_TARGET_GIB=20, MTP on and 10 GiB of slack, the cap goes past the ceiling (121.69 − 16) and the launcher refuses; tp1/.env.sample uses a slack of 5 in that regime (our interpretation). And the script predicts ~728k tokens for 20 GiB, more than the real boot delivered: 685,825 tokens at GMU 0.813 with a 98.9 GiB budget. The script estimates, vLLM decides. That boot kept a minimum MemAvailable of 13.1 GiB, almost all of it page cache holding the PLE table; below ~10 GiB, the PLE lookups would start hitting the disk.

Checklist for your recipe

(1) Add up the weights per node + the minimum KV for your max_model_len + ~5–6 GiB of overhead and compare with \(u \times M\), using your machine's \(M\). (2) Find out whether the graphs are inside or outside the GMU (VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS); if outside, subtract them from the headroom. (3) Start at GMU 0.80 and go up 0.01 at a time (≈ 1.2 GiB) only while the MemAvailable of both nodes, watched under real load, stays above ~5–6 GiB. (4) If the profile run is unstable, pin the KV in bytes, without growing beyond the budget. (5) Clear the checkpoint's page cache, distrust loaders that measure MemFree and check getconf PAGESIZE. (6) Swap kept on and cycled, earlyoom off, host without a desktop. (7) Watch NV_ERR_NO_MEMORY and progress in /metrics, not /health. (8) Weights over the CX7 with nconnect=8, or copy them once. (9) If your engine allows it, budget the TensorFold way: MemAvailable at startup minus a reserve that covers the peak outside the estimate, and refuse before loading anything that doesn't fit.
