An LLM has never read a single letter. When you send "hello world" to the GLM-5.3-Flash server, what reaches the neural network is two integers, 14978 and 1879 (the recipe README shows this response from the /tokenize endpoint). Everything the model knows about language starts at a table that swaps each integer for a vector and ends at another table that swaps a vector for a score for every possible integer. In this chapter you will see how text becomes integers (BPE tokenization), what lives in the vocabulary (including the special tokens that mark who is speaking, when to think and where an image goes), how a conversation becomes a prompt (chat templates, and the case where the template is a Python program), and how much the two ends of the network cost in memory and bandwidth: the embedding and the lm_head.

From text to integers

A neural network only does arithmetic: it multiplies matrices, adds vectors, applies functions. Text is not a number. Before any layer, you need a dictionary that swaps pieces of text for integers, and integers back for text. That dictionary is the tokenizer. Each piece is a token, and the set of all possible pieces is the vocabulary, of size \(V\).

The engineering question is: how big should the pieces be? There are three obvious answers, and each one breaks in a different way.

🔤

Letters or bytes

A tiny vocabulary (256 bytes cover any text), but huge sequences. Every letter costs one decode step, and attention pays the square of the length.

📚

Whole words

Short sequences, but the vocabulary explodes: cat, cats, kitten, kitty, proper names, code identifiers, typos. A word never seen before becomes “unknown”.

🧩

Subwords

The compromise that won. Frequent words become a single token, rare ones are assembled from pieces, and the bytes stay in reserve for anything left over.

One detail seems trivial but isn't: UTF-8. The computer stores text as bytes (see How computers store numbers), and only ASCII fits in 1 byte per character. The Portuguese “ç” takes 2 bytes (C3 A7), and so does “ã” (C3 A3); a Chinese ideogram takes 3, an emoji 4. That is why modern tokenizers start from bytes rather than characters: with 256 base symbols, any sequence has a representation and there is no “unknown” token. That is the “byte-level” in the byte-level BPE that the three recipe models use.

In the figure below, a toy BPE tokenizer was trained live, in your browser, on a small corpus in Portuguese, English and Python. Pick a sentence and drag the number of merges. The top strip shows the raw bytes, the middle one the tokenized sentence, and the bottom one the limit BPE can reach.

Notice three things. With zero merges, the Portuguese word “não” costs 4 tokens (n, C3, A3, o): the accent alone takes two. The first merges learned join precisely the byte pairs that always travel together, then syllables, and then whole words. The curve drops fast at first and then flattens, because each new merge finds less repetition to exploit. And it never breaks through the dashed floor: BPE does not join pieces that pre-tokenization separated (we will see why shortly).

\[ \varphi = \frac{n_{\text{tokens}}}{n_{\text{words}}}, \qquad \text{decode cost} \;\propto\; n_{\text{tokens}}, \qquad \text{prefill attention cost} \;\propto\; n_{\text{tokens}}^{2} \]
  • \(\varphi\): the tokenizer's fertility, in tokens per word; it depends on the language, the domain (prose, code, numbers) and the vocabulary
  • \(n_{\text{tokens}}\): the sequence length; on the server, maximum context, KV cache and speed are all counted in tokens
  • the quadratic cost of attention is the subject of Attention; here it is enough to know that a longer sequence costs more than proportionally
Trap: counting words instead of tokens

On an English filler text, the DeepSeek recipe measured 340,787 words → 533,110 tokens, or 1.564 tokens per word. An old heuristic got this ratio wrong: a stress test requested as “524,288 tokens” actually sent about 815k, and a 700k one would go past the 1M context ceiling, which showed up as a false “GARBLE DETECTED” (scripts/context-garble-sweep.py). The lesson became a design note in the recipe: measure lengths with the server's /tokenize, never with word counts.

Why this matters

--max-model-len, the size of the KV cache, speed in tok/s and the price of each decode step are all measured in tokens. A tokenizer that spends 20% fewer tokens on your language fits 25% more text into the same --max-model-len (1/0.8 = 1.25), and the same answer comes out in 20% fewer decode steps: at the same tok/s, that is 25% more words per second. It is not a preprocessing detail. It is performance.

BPE: the merge factory

The dominant algorithm is called BPE (Byte-Pair Encoding). It was born as a data compression technique and was adapted for text. The idea fits in one sentence: repeatedly join the most frequent neighboring pair.

Training: learning the merge list

  1. Start from the base alphabet. In byte-level BPE, that is the 256 byte values (ids 0 to 255). The whole training corpus is written in this alphabet.
  2. Count the neighboring pairs. In each word of the corpus, count every pair of adjacent symbols, weighted by the word's frequency.
  3. Merge the champion. The most frequent pair becomes a new symbol, with the next free id, and the rule “a + b → ab” goes to the end of the merge list.
  4. Repeat until the vocabulary reaches the desired size.
\[ (a^{*}, b^{*}) = \arg\max_{(a,b)} \sum_{w\,\in\,\text{corpus}} \text{freq}(w)\cdot \#_{(a,b)}(w), \qquad \mathcal{V}_{k+1} = \mathcal{V}_{k} \cup \{a^{*}b^{*}\}, \qquad |\mathcal{V}_K| = 256 + K \]
  • \(\text{freq}(w)\): how many times the word (pre-tokenized piece) \(w\) appears in the corpus
  • \(\#_{(a,b)}(w)\): how many times the symbol pair \(a\) followed by \(b\) appears inside \(w\) in the current segmentation
  • \(\mathcal{V}_k\): the vocabulary after \(k\) merges; \(K\): the total number of merges learned

Encoding: applying the merges in order of arrival

To tokenize new text, BPE starts from the bytes and applies the oldest merge available between two neighbors (the one with the lowest position in the list), repeating until none is left that applies. The process is deterministic: the same text always gives the same ids. Follow the step-by-step in the figure, with six words (Portuguese ones, as it happens) from a toy corpus.

Two facts come out of the figure and come back later on the trail. First, the id tells the story of training. Merges learned early are the most frequent pairs and get low ids, so in a byte-level BPE vocabulary a low id tends to mean a common token. The Qwen recipe uses this: when the available corpus is small, the script that builds the reduced vocabulary for the drafter (a small model that proposes tokens for the big model to verify; it comes back in the lm_head section and in Speculative decoding) fills the list with the lowest ids not yet seen (--fill-to-size), and the script itself warns that this is “a proxy, not a measurement”. Second, tokenizing is not concatenating. tok(A + B) is not always tok(A) followed by tok(B), because a merge can cross the seam. A patch in the DeepSeek recipe ran into this when it moved a piece of text inside the prompt: the BPE merge at the junction cost a 1-token difference (hotfix #144, further below).

Before BPE: pre-tokenization

Real tokenizers do not hand raw text to BPE. A regular expression first cuts the text into pieces (words with their leading space attached, numbers, punctuation, line breaks), and merges never cross those cuts. This is pre-tokenization. GLM uses a GPT-4-style regex that groups digits up to 3 at a time: “1048576” becomes “104”, “857”, “6” before any merge. This keeps the vocabulary from spending thousands of entries on whole numbers and makes the way numbers are written more regular for the model.

The attached leading space explains a useful subtlety: " hello" and "hello" are different tokens. GLM's warmup script builds prompts hello hello hello… with S repetitions and checks with /tokenize that the server counted exactly S tokens before firing the request that warms up that tensor shape (why warmup exists is covered in CUDA graphs and warmup). If the count does not match, that rung is skipped and the log says so.

EndpointPOST /tokenize

Mounted at the server root (/v1/tokenize gives 404). It accepts prompt (raw text) or messages (chat format, which goes through the chat template). Example from the README: {"prompt": "hello world"} → {"count": 2, "tokens": [14978, 1879]}.

Why the recipe uses it: the warmup needs prompts with an exact count (prefill rungs of 3,584, 7,168, 14,336 and 65,536 tokens) and asks the tokenizer itself instead of guessing. Careful: it is an unauthenticated route even with VLLM_API_KEY, because the middleware only protects /v1 and similar paths.

Looking at the real numbers, GLM-5.3-Flash's tokenizer.json carries 154,820 BPE tokens and 321,649 merge rules. More rules than tokens seems to contradict \(|\mathcal V| = 256 + K\), but a token can be reached by different paths (“ab”+“c” and “a”+“bc”); our interpretation is that the file stores redundant rules.

Deep dive: Zipf and the long tail

Token frequency roughly follows Zipf's law, \(f(r) \propto r^{-s}\) with \(s \approx 1\), where \(r\) is the token's rank from most common to rarest. A few tokens account for most of the text, and most tokens are rare. Two consequences show up in the recipes: a small subset of the vocabulary covers almost all the text of a domain (which is why drafting over 47k of the 248k tokens works, as we will see), and rare tokens get little training (the next section shows the side effect).

The id is also an address

In two of the three models the id is not only used to fetch the embedding. Qwen3.8 uses the ids of the previous tokens as a hash key into an N-gram table of 51.2 B parameters (the PLE, in N-gram and MTP) and treats <|endoftext|> (248044) as a document separator in that table. DeepSeek-V4 is an MoE: each layer has 256 sub-networks, the experts, and each token goes through only 6 of them (Mixture-of-Experts). In the first 3 layers, it picks the experts through a fixed table indexed by the id (hash routing, tid2eid [129280, 6]). Since the image placeholder 129264 is an id like any other, every image token went to the same 6 experts until a hotfix handled them separately. Moral: the tokenizer is welded to the weights. Changing the tokenizer means changing the model.

Special tokens: the protocol's punctuation

Besides the tokens BPE learned, the tokenizer carries a list of added tokens (added_tokens in tokenizer.json): reserved strings that it recognizes whole, before BPE, and maps to a fixed id. Some of them also carry the special: true flag, and those are the special tokens in the strict sense. The flag does not change encoding. It decides the way back: when ids are converted to text with skip_special_tokens (the vLLM default), specials vanish from the response and added tokens without the flag stay. Together, specials and added tokens are the punctuation of a protocol the model learned in training, and they fall into six families:

🚧

Boundaries

Start and end of sequence (BOS, EOS) and padding (PAD). DeepSeek: <｜begin▁of▁sentence｜> = 0 and <｜end▁of▁sentence｜> = 1.

🎭

Roles

Who is speaking. GLM: <|system|>, <|user|>, <|assistant|>. Qwen: <|im_start|> 248045 and <|im_end|> 248046 wrapped around the role name. DeepSeek: <｜User｜>, <｜Assistant｜>.

💭

Reasoning

<think> and </think> delimit the thinking. GLM: 154841 and 154842, plus /nothink 154851.

🛠️

Tools

GLM: <tool_call> 154843 and the result turn <|observation|>. Qwen: <tool_call>/</tool_call> 248058/248059. DeepSeek: the DSML markup.

🖼️

Modalities

One placeholder per image, which the processor expands into N vision tokens. GLM <|image|> 154854; Qwen <|image_pad|> 248056 between vision_start/end 248053/248054; DeepSeek <｜deepseek_image｜> 129264.

🫥

Mask and noise

Ids used as a “blank position” by block drafters, which propose several tokens at once (DFlash2 and DSpark). GLM's DFlash2: mask 154856. DeepSeek's DSpark: noise 128799, also used to pad CUDA graphs.

Note GLM's trick: its eos_token_id is a list, [154820, 154827, 154829], that is, <|endoftext|>, <|user|> and <|observation|>. The natural end of the assistant's turn is the moment it would “write” the marker of the next turn: the user's, or the observation that answers a tool call. Stopping at these ids ends the response at exactly the right point. Qwen does something similar: generation_config.json lists [248046, 248044] (<|im_end|> and <|endoftext|>), while the config declares BOS = EOS = 248044.

Why does each marker need to be one token? Because parsers, masks and budgets work with ids. Before testing tool_choice: none, the GLM recipe checks that <tool_call> becomes a single id (154843), the id the patch blocks in the logits. DeepSeek's thinking budget (hotfix #31) requires <think> to be a single token so it can count and force the closing tag.

And the special flag matters when separating thinking from answer. In GLM, ids 154820–154837 ([gMASK], <sop>, roles, media delimiters) are special, but 154838–154855 (<think> 154841, </think> 154842, <tool_call> 154843, /nothink, <|image|>, <|video|>) are added without the flag. That is why <think> does not vanish on detokenization: it arrives intact in the text, and what removes it from the answer and moves it to the reasoning field is the reasoning parser. The MiMo from the new-recipe tutorial is in the same situation: <think> and </think> are not flagged as special and show up in the text if the parser does not split them out. When you put a recipe together, open added_tokens and write down, token by token, which ones are special.

In the figure, each model's id space becomes a subway line. On the left, the whole vocabulary at real scale; on the right, the stations in order (the spacing there is not proportional to the id). Hover over or tap a station to read each token's role.

Notice that the specials sit right at the end of the id range in GLM and Qwen: they were added after BPE training. In DeepSeek, BOS and EOS take ids 0 and 1. Turn on TP=3 to see the extra padding.

Padding and the rows that never trained

vocab_size is usually rounded up. GLM uses 154,856 real ids and declares 154,880 (a multiple of 128); the tutorial's MiMo uses ids up to 151,674 and declares 152,576. There are two reasons: kernels like dimensions that are multiples of 64 or 128 (aligned tiles), and tensor parallelism splits the rows into equal slices across GPUs. vLLM rounds the vocabulary to a multiple of 64. With TP=3, 64 is not enough, and the recipes' patches use \(\text{lcm}(64, 3) = 192\) (in the code, padding_size = lcm(64, tp), where lcm stands for least common multiple): GLM goes to 154,944 and DeepSeek to 129,408 (129,280 is not divisible by 3), a form of vocabulary padding made of inert rows. GLM's lm_head in EXL3 (the recipe's quantization format, with Hadamard rotation and a trellis; Rotations, trellises and EXL3) also requires a vocabulary that is a multiple of 64, and 154,880 is one.

These extra rows, and the extremely rare tokens, reveal a beautiful asymmetry in training. The input embedding only receives gradient on the rows of tokens that appear in the batch. The output matrix receives gradient on every row at every step, because the softmax spreads probability over the whole vocabulary.

\[ \frac{\partial \mathcal L}{\partial E[v]} = \sum_{t\,:\,x_t = v} \frac{\partial \mathcal L}{\partial \mathbf{x}_t} \qquad\qquad \frac{\partial \mathcal L}{\partial z_v} = p_v - \mathbb{1}[v = y] \]
  • \(E[v]\): row \(v\) of the embedding; the sum is empty (zero gradient) if token \(v\) does not appear in the batch
  • \(\mathbf{x}_t\): the input vector at position \(t\); \(x_t\): the token id at that position
  • \(z_v\), \(p_v\): the logit and probability of token \(v\) at the output; \(y\): the correct token

The result: the output row of a never-seen token learns to be “never predicted” (its logit is pushed down at every step), while its input row stays near its initialization. A token like that is harmless at the output and unpredictable at the input, one of the roots of the so-called glitch tokens. The DFlash2 mask (154856) lives precisely in the padding range of the target's embedding. Our reading (interpretation) is that this does no harm: the drafter was trained always receiving that same vector as a “blank position”, and what matters is that it is fixed and distinct.

Where to read all this: the tokenizer files

Every number in this section comes from four JSON files in the checkpoint. Anyone about to write a recipe needs to know what to look for in each one. In tokenizer.json, four keys:

model
The type (BPE), the vocab (string → id) and the merges list, in priority order. GLM: 154,820 entries and 321,649 merges.
pre_tokenizer
The pre-tokenization regex and the byte-level mapping. In GLM, the GPT-4-style regex that groups digits 3 at a time.
added_tokens
Every added token, with its id and flags, among them special. This is where you find out that GLM's <think> (154841) is added without the flag.
decoder
How ids go back to text; in byte-level BPE, it undoes the byte mapping.

And in the three configuration files, which may disagree with each other:

tokenizer_config
chat_template (when present), bos_token, eos_token, pad_token, padding_side, model_max_length. GLM: padding_side: left (in a batch, padding goes on the left so that every sequence ends aligned and generation continues from the end of each one) and model_max_length: 1048576. In Qwen, eos_token is <|im_end|> 248046.
config
vocab_size (the rows of the matrices), bos_token_id, eos_token_id, pad_token_id. GLM: EOS [154820, 154827, 154829] and pad 154820 (<|endoftext|>). Qwen: BOS = EOS = 248044, which differs from the tokenizer's EOS.
generation_config
The sampling defaults and the eos_token_id values that stop generation. Qwen: [248046, 248044], both at once, which resolves the divergence.

Whatever else lives in a checkpoint (weights, indexes, quantization configs) is covered in Checkpoints.

Chat templates: the conversation becomes tokens

The API receives a list of messages in JSON. The model was trained on running text full of markers. The chat template translates one into the other. It is usually a Jinja program stored in the checkpoint, in the chat_template field of tokenizer_config.json or in a chat_template.jinja file (what each file in the repository holds is covered in Checkpoints). In vLLM, the API server runs it, before tokenizing and sending the ids to the engine (Inside vLLM).

What a template decides

Roles
How to mark system, user, assistant and tool, and in what order.
Generation prompt
With add_generation_prompt, the template ends the prompt with the header of the assistant's next turn, the generation prompt: <|assistant|> in GLM, <|im_start|>assistant in Qwen, <｜Assistant｜> in DeepSeek. The model carries on from there.
Reasoning
Thinking on: the prompt ends in <think> and the model goes on thinking. Thinking off: the template closes an empty block, <think></think> (GLM, Qwen), or just </think> (DeepSeek's chat mode). In GLM, clear_thinking replaces the reasoning of old turns with empty blocks.
Tools
The tool schema goes into the system region, and the template pins down the format the model learned to emit. GLM: XML, <tool_call>name<arg_key>k</arg_key><arg_value>v</arg_value></tool_call> (parser glm47). Qwen: <tool_call> blocks (parser qwen3_coder). DeepSeek: DSML (parser deepseek_v4). Results come back as <|observation|><tool_response>… in GLM and as <tool_result>… inside a user turn in DeepSeek.
Media
One placeholder per image or video; the multimodal processor expands it into N vision tokens (Vision).
Variables
The client's chat_template_kwargs (enable_thinking, reasoning_effort…) become template variables; each family's values are listed in The API.
Validation
What happens to an unexpected value is also template logic (or logic in the code around it), and each family decides differently. Qwen: reasoning_effort accepts low, medium and xhigh (default xhigh); high and max are rejected with HTTP 400 (Unexpected reasoning effort…) before they reach the engine. But the check lives inside the reasoning branch: with enable_thinking: false, an invalid value is silently ignored. And thinking_budget is not even honored by this build. GLM: nothing is rejected; anything that is not low or high becomes Max. DeepSeek: the encoder only reads chat_template_kwargs.reasoning_effort, and the top-level reasoning_effort field of the OpenAI API is ignored. Moral: test every kwarg in both branches, reasoning on and off, and look at the rendered prompt.

In the figure, the same conversation (a short system message and a question) goes through each model's template machine. Toggle reasoning, tools and the image, and compare what comes out the other side.

Notice that the prompt is almost all protocol. The human text (“What is 3+3?”) is an island in a sea of markers, and the prompt always ends with the generation prompt. Turning reasoning off only changes the tail in Qwen and DeepSeek. In GLM it also changes the head: the line <|system|>Reasoning Effort: Max only exists with reasoning on.

That has a price. Prefix caching reuses the KV cache of prompts that start the same way, comparing blocks of tokens chained by hash (Prefix caching). Any difference at the start invalidates everything after it. In GLM's template, two requests with different efforts share only the first 40 characters, [gMASK]<sop><|system|>Reasoning Effort: (the test tests/test_chat_template.py pins this down; the README says “char 39”). Changing the effort mid-conversation causes a total cache miss, which is why the recipe recommends fixing the effort per route.

Parameter--chat-template /opt/glm53/chat_template.jinja

Value: CHAT_TEMPLATE_HOST=files/chat_template.jinja is mounted into the container as CHAT_TEMPLATE=/opt/glm53/chat_template.jinja (start.sh:245-246). Why: in the README's words, “the checkpoint's Jinja is language-only”. The recipe's template builds [gMASK]<sop><|system|>…<|user|>…<|assistant|><think>, adds image, video and audio, the XML tool-call format and reasoning control: reasoning_effort low or high, and any other value becomes Max.

Validation: before restarting the service, the launcher parses the template with Jinja2 and the loopcontrols extension (the template uses {% break %}), that is, a syntax check that renders nothing (start.sh:966). The rendering itself is covered by the tests, in tests/test_chat_template.py. GLM53_VALIDATE_PYTHON pins which interpreter runs the check. Since it runs before the restart stops the old service, a broken template is rejected without taking anything down.

A wrong template raises no error

If the template does not match the training format, nothing breaks: the model just gets strangely worse. The test from the new-recipe tutorial: /tokenize with messages and add_generation_prompt must give ids identical to the reference apply_chat_template. The GLM recipe carries the scar: emitting the effort line together with the empty <think></think> block (to stabilize the cache) made the model reason in the answer channel, and the code score dropped from 98 to 60 on the recipe's benchmark.

When the template is a program: the DeepSeek encoder

The DeepSeek-V4 checkpoint ships no Jinja template. The conversation, reasoning and tool format lives in a Python program, encoding/encoding_dsv4.py, with functions such as encode_messages() and render_message(). A chat encoder like this is more expressive than Jinja (it validates messages, folds tool results into the user turn, writes DSML), but the engine needs to know how to call it. That is what --tokenizer-mode deepseek_v4 does: the tokenizer mode swaps vLLM's rendering path for a wrapper that calls the encoder. The available modes are auto, cohere, deepseek_v32, deepseek_v4, hf, inkling, kimi_k3, mistral, slow.

The format is lean: BOS, the effort directive (only at high and max), the system message with no marker, <｜User｜> and the question, and the generation prompt <｜Assistant｜><think> (or </think> in chat mode). Every past assistant turn ends in EOS. Walk through the assembly line in the figure.

Notice the cascade effect. With the directive right after BOS, the first block changes, and since each hash depends on the previous one, every block changes: 0 of 18 shared. With #144 on, the directive moves to the end of the system region, and all 18 full blocks match again, with the 4,630-token common prefix measured by the recipe. Now turn on “last turn = assistant”: the prompt ends in an EOS and there is no generation prompt.

Why is this so bad, in terms of tokens? In training, what came after <｜end▁of▁sentence｜> was a new role marker, never the assistant carrying on talking. Asking the model to generate from there puts it outside the training distribution: the recipe recorded 1-to-2-token responses ending in stop and, worse, hallucinated tool markup, which feeds on itself because the harness resends the history. The hotfix keeps the previous turn closed and appends a fresh header, <｜Assistant｜><think>. In the recipe's causal A/B, the open turn produced 183 coherent tokens and the EOS-closed one produced 400 tokens of raw <|DSML|tool_calls> as text.

In the recipe: the effort directive and the cache (#144)

The encoder inserts the directive right after BOS. BOS + directive add up to 93 tokens at max/xhigh and 80 at high; at low there is no directive. Different levels diverge at block 0 and share zero cache blocks (measured: 0% across levels, 96–98% within the same level). The opt-in patch DSPARK_ENABLE_ISSUE144_EFFORT_ALIGN=1 moves the directive to the end of the system region and leaves low byte-identical to stock; before it becomes the default, the recipe still asks for a quality gate at high/max, since the directive changes place. Only chat_template_kwargs.reasoning_effort reaches the encoder; the top-level OpenAI reasoning_effort field is ignored. max effort costs about 3× the latency of low. The hash mechanics are in Prefix caching, and reasoning effort is in Generating text.

Embedding: each id pulls a row

With the prompt converted into ids, the network begins. The first layer is the simplest of all: a table. The embedding is a matrix \(E \in \mathbb{R}^{V\times d}\), with a row of \(d\) numbers for each token in the vocabulary. For the token with id \(i\), the input vector is simply row \(i\).

\[ \mathbf{x}_t \;=\; E[\,i_t,\,:\,] \;=\; \mathbf{e}_{i_t}^{\top} E, \qquad \mathbf{e}_{i} = (0,\dots,0,\underbrace{1}_{i},0,\dots,0) \in \{0,1\}^{V}, \qquad \underbrace{[B,\,T]}_{\text{ids (int)}} \;\longrightarrow\; \underbrace{[B,\,T,\,d]}_{\text{vectors (BF16)}} \]
  • \(i_t\): the id of the token at position \(t\); \(\mathbf{x}_t \in \mathbb{R}^d\): its input vector
  • \(\mathbf{e}_i\): a one-hot vector, with a single 1 at position \(i\)
  • \(B\): sequences in the batch; \(T\): tokens per sequence; \(d\): the model width (4096 in GLM and DeepSeek, 2560 in Qwen)

The one-hot form is the math; the direct lookup is the implementation. Multiplying a one-hot by \(E\) would take \(V \times d\) multiplications, almost all of them by zero. The real kernel does a gather: it reads only the requested row, \(d\) numbers of 2 bytes each. Watch the vector bookshelf at work.

Notice that the same id always pulls the same row: “ cat” at the start or at the end of the sentence gets the same vector. The embedding does not know where the token is or what surrounds it. Position and context come in later, through the layers (Position and RoPE and Attention). The vector \(\mathbf x_t\) is the first state of the residual stream, the “bus” that each layer will read and rewrite (The Transformer block).

The rows of \(E\) are ordinary parameters, learned by backpropagation like any other weight (What learning is). The real sizes:

GLM-5.3-Flash

  • embed_tokens [154880 × 4096]
  • 634,388,480 parameters, BF16, 1.27 GB (1.18 GiB)
  • one row = 8 KiB read per token
  • the MTP and DFlash2 drafters reuse the target's embedding

Qwen3.8-Flash-Next

  • embed_tokens [248320 × 2560]
  • 635,699,200 parameters, BF16, 1.27 GB (1.18 GiB)
  • one row = 5 KiB read per token
  • MTP reuses the embedding (mtp_use_dedicated_embeddings: false)

DeepSeek-V4-Flash

  • embed [129280 × 4096]
  • 529,530,880 parameters, BF16, 1.06 GB (0.99 GiB)
  • one row = 8 KiB read per token
  • DSpark shares the embedding and lm_head with the target

In all three checkpoints the embedding stays in BF16, even with the experts in 4 bits. That makes sense: each token reads a single row, so compressing the table saves no bandwidth in the decode step, and it stays on the list of sensitive layers the recipes preserve (Quantization fundamentals). The exception proves the rule: Qwen's N-gram table is also an embedding, but it has 320 million rows and 51 GB, and there quantizing it pays off (FP8 or NVFP4), with a method that dequantizes only the rows fetched.

With two GPUs

In tensor parallel, the embedding becomes a vocab-parallel embedding: each GPU holds a contiguous range of ids. In Qwen with TP=2, rank 0 gets ids 0–124,159 and rank 1 gets 124,160–248,319. For an id outside its range, a rank returns a vector of zeros, and an all-reduce adds the two halves. The Parallelism chapter covers these collectives.

The geometry of embedding space

Each row of the table is a point in a \(d\)-dimensional space. Training knows nothing about dictionaries. It just pushes the rows around to reduce prediction error, and tokens used in similar contexts end up with similar vectors (the distributional hypothesis). The ruler for “similar” is cosine similarity, which measures the angle and ignores the length (Tensors and linear algebra):

\[ \cos(\mathbf a, \mathbf b) = \frac{\langle \mathbf a, \mathbf b\rangle}{\lVert \mathbf a\rVert\,\lVert \mathbf b\rVert} \in [-1, 1], \qquad \text{for random } \mathbf a, \mathbf b \text{ in } \mathbb{R}^d:\quad \mathbb{E}[\cos] = 0,\quad \sigma(\cos) \approx \frac{1}{\sqrt d} \]
  • \(\langle \mathbf a, \mathbf b\rangle\): the dot product; \(\lVert\cdot\rVert\): the L2 norm
  • \(\sigma\): the standard deviation of the cosine between two randomly drawn directions: 0.0156 with \(d = 4096\) and 0.0198 with \(d = 2560\)

The second half of the equation is the most counterintuitive fact about high dimensions, concentration of measure: two vectors drawn at random are almost perpendicular. In the plane, two random clock hands form any angle. In 4096 dimensions, nearly every pair lands within a few hundredths of 90°. The space has room for an enormous number of nearly independent directions, and the model uses this to store many concepts without them getting in each other's way. It is this same idea of “concept = direction” that abliteration exploits (Directions in latent space).

Notice the contrast between the two panels. In the 2D toy, similar directions are rare and precious, and clusters bump into each other. With \(d = 2560\) or \(4096\), the curve on the right becomes a needle: a similarity of 0.2, which would be nothing in the plane, is an extremely strong signal in high dimension, many standard deviations above chance.

A caveat about what the input embedding knows: above all, “which token is this” (case and spacing variants, synonyms, close translations). Meaning in context, whether “bank” is the side of a river or a place that holds your money, is built by the layers. Analogies like the king one are sharper in classic word embeddings and in the inner layers of an LLM than in the input table (an interpretation backed by the literature; we did not measure this in the three models).

Not every input vector comes from the table

In the end, a “token” for the network is a vector of \(d\) numbers, wherever it comes from. For image tokens, the placeholder is replaced by the vectors the vision tower produces, already projected to the text width (masked_scatter in Qwen; Vision). In Qwen, the N-gram memory injects a vector assembled from 16 rows of 160 numbers into layer 2 (index 1), across all four residual branches (ple_embed_dim = 16 × 160 = 2560, the same hidden_size width as each branch). They all live in the same space and are added or substituted like ordinary vectors.

lm_head: back to the vocabulary, and the price of V

After the last layer and the final normalization, each position carries a vector \(\mathbf h \in \mathbb R^d\). To turn it into per-token scores, the network's last matrix steps in: the lm_head (or unembedding) \(W_U \in \mathbb R^{V\times d}\), with one row per token.

\[ \mathbf z = W_U\,\mathbf h \quad\Longleftrightarrow\quad z_v = \langle W_U[v],\, \mathbf h\rangle, \qquad \text{bytes per read} = V\cdot d\cdot 2, \qquad \text{FLOPs per token} = 2\,V d \]
  • \(\mathbf z \in \mathbb R^V\): the logits, one raw score per token; the softmax turns them into probabilities (Generating text)
  • \(W_U[v]\): the row of token \(v\), its “output vector”; the factor 2 is the size of a BF16 in bytes
  • in GLM, the \(2Vd\) come to 1.27 GFLOP per token, against ~36 GFLOP/token for the whole model

Here lies an asymmetry that shapes recipes. The embedding reads one row per token. The lm_head needs all \(V\) rows at every decode step, because the sampler needs the score of the whole vocabulary (or, at the very least, has to find the largest one). In decode with a single sequence, this is a bandwidth-bound matrix-vector product: the entire matrix crosses memory to generate one token. The figure puts the two ends side by side.

Notice the distance between the bars: from 5 or 8 KiB to more than 1 GB, a ratio of \(V\), or 130,000 to 250,000 times. Tying the matrices halves the memory, but changes nothing about the per-step read, because the embedding was never the problem. Turning on the drafter multiplies the read. In a batch, the math improves: a single read of the matrix serves every sequence in the step, which is why the lm_head's per-token cost falls with concurrency (Prefill, decode and the KV cache).

To tie or not to tie

Tied embeddings (tie_word_embeddings: true) use the same matrix at both ends, \(W_U = E\), and save \(V\cdot d\) parameters. This is common in small models, where the vocabulary is a large slice of the total. The three recipe models do not tie (tie_word_embeddings: false), and pay 634 M extra parameters in GLM, 0.64 B in Qwen and 0.53 B in DeepSeek, a small fraction of models with hundreds of billions.

There is also a quality argument. The input row answers “which token is this?”; the output row answers “when should this token come next?”. Those are different questions. With tied matrices, a model with no layers would give the next token \(v\) the score \(\langle E[v], E[u]\rangle\), which is symmetric, and at \(v = u\) that score equals \(\lVert E[u]\rVert^2\). By the Cauchy-Schwarz inequality, \(\langle E[v], E[u]\rangle \le \lVert E[v]\rVert\,\lVert E[u]\rVert\), so, when the row norms are similar, \(u\) itself tends to get the highest score (a token with a much larger norm could still beat it): a built-in tendency to repeat the current token, which the layers have to undo. Untying the matrices undoes that knot (a didactic interpretation of a well-known argument; none of the recipes measures this).

A zero-layer model is a bigram model

Remove every layer and you are left with \(\mathbf z = W_U\,E[x_t]\): the next-token scores depend only on the current token. That is a bigram model, a \(V \times V\) transition table written as the product of two thin matrices, and therefore of rank at most \(d\). The embedding + unembedding pair reappears, in a low-rank version, inside the drafters. DSpark's Markov head adds a bias \(W_2\,W_1[\text{previous token}]\) to the logits, with \(W_1: V\times 256\) and \(W_2: 256\times V\), so that the positions of the parallel draft stay coherent with each other. GLM's DFlash2 selector does something similar with two “codebooks” \([V \times \text{rank}]\), a bigram conditioned on the hidden state.

A large vocabulary makes drafting expensive

In speculative decoding, a cheap drafter proposes a few tokens and the big model verifies them all at once (Speculative decoding). But every drafted token also has to choose among \(V\) candidates, and that is where the lm_head presents its bill again. In Qwen, MTP runs 3 times per step (num_speculative_tokens=3), and each round ends in the drafter's own head: since tie_word_embeddings is false, vLLM creates a ParallelLMHead with the full vocabulary for MTP (the checkpoint does not ship a separate mtp.lm_head), at 248,320 × 2560 × 2 B = 1.18 GiB, or 0.59 GiB per GPU at TP=2. Adding the target's verification, in its own lm_head, that makes 4 reads per step, 2.37 GiB per GPU (4 × 0.592), about 26% of the ~9.2 GiB each GPU moves in a step at batch 1: the largest item in the recipe's accounting, ahead of the experts.

The way out is to draft in a smaller vocabulary (FR-Spec). In the recipe, the variable MTP_DRAFT_VOCAB=files/draft_vocab_en_code_47k.txt (the default since 2026-09-10) points to a file of 47,149 ids, 19% of the vocabulary. start.sh mounts the file into the container, applies patch_mtp_draft_vocab.py and turns on use_local_argmax_reduction in the speculative config. On each GPU, the patch cuts out the rows of the drafter's head that are on the list and rewrites only get_top_tokens, the function that picks the drafted token. Each rank multiplies \(\mathbf h\) by its reduced slice, finds the local argmax and sends the others only the (value, global id) pair. An all-gather of \(2\cdot\text{TP}\) numbers per token replaces the one of \(V\) logits, and the largest pair wins (a rank with no ids on the list sends \(-\infty\)). The target's compute_logits, which produces the verification scores, keeps the full vocabulary. It is safe because the draft is greedy and verified: a token that is not on the list just becomes a rejected draft; it costs acceptance, never correctness. The slice read per draft round drops from 0.59 to 0.22 GiB on the most loaded rank, and decode gained 9.6% on average (2026-09-11), with the same tokens accepted per step. The figure shows where those 47k ids live, with real data from the file.

Notice two things. The low ids are nearly all there: of the first thousand, 971 made it, and occupancy drops bin after bin, the order of the BPE merges showing up as frequency. Near id 98k occupancy drops to almost nothing (our interpretation: the high ranges come from vocabulary extensions for other languages and scripts, rare in an English-and-code corpus). And the TP=2 boundary cuts the list brutally: 45,734 ids on rank 0 and 1,415 on rank 1. Rank 1 reads almost nothing, but the step waits for the slowest rank. Rank 0 still reads 0.22 GiB per round, twice the ~0.11 GiB of a perfectly balanced list (23,575 ids per rank). By our math, the default list captures about 78% of the possible savings: 0.59 → 0.22 GiB, against 0.59 → 0.11 GiB in the best case.

So why not balance it? The generator build_draft_vocab.py has --balance-shards, which spreads the filler evenly across the TP ranges, and the recipe measured the price on 2026-09-05. That round's corpus had only 8,305 distinct ids, and the 65,536-id list was completed with filler. With the filler taken from the lowest ids (65,392 of them on rank 0), the head came to 0.31 GiB per rank and acceptance to 53.2%. With --balance-shards 2 (32,768 per rank), the head fell to 0.16 GiB, but acceptance plunged to 47.8%, against 56.5% for the full vocabulary. Our reading of the mechanism: to give 32,768 ids to rank 1, the filler trades low, common ids for high ids that almost never appear in English and code. Bandwidth and acceptance pull in opposite directions, hence the advice the script itself gives: tune for coverage, not for size. The 47k list is unbalanced and still delivered +9.6% (2026-09-11) and +8.4% in an independent rerun (2026-09-16). A warning: it was tuned on English code and documentation (99.58% coverage on a separate held-out text), so it may draft worse in other languages, especially Chinese. For a different kind of traffic, generate the list from the model's own output, counting ids with the tokenizer given in --model/DRAFT_VOCAB_MODEL. The full workshop is in MTP, EAGLE and cheap drafts.

In the recipe: 129,280 logits, several times per step

In DeepSeek, the 129,280 × 4096 = 1.06 GB BF16 lm_head is read at every step, for the target's logits and for the base of the DSpark draft, which shares the matrix with the target. With the vocabulary sliced between the two GPUs, the sampler has to gather everything: an all-gather of 7 × 129,280 logits per sequence (the 7 positions the target verifies: the last accepted token and the 6 drafted ones), about 10.9 MB with 6 sequences. The Markov head (129,280 × 256 at each end, 2 × 66 MB) was at one point replicated on both GPUs to eliminate 12 serial collectives per step (DSPARK_ENABLE_REPLICATE_MARKOV). In the 2026-09-02 A/B the replication came out correct, with the same acceptance, but gained nothing with one sequence (c=1), and with six sequences (c=6) the aggregate fell from 148 to 122 tok/s; the KV cache also lost 0.44 GiB. The option stayed off. Replicating trades communication for memory and bandwidth, and here the trade did not pay off. At TP=3, 129,280 is not divisible by 3, and the vocabulary is padded to 129,408.

What about the head's precision?

All three checkpoints keep the lm_head in BF16. An error in the logits moves the argmax and the probabilities directly, which is why it stays on the list of sensitive layers. The exceptions are deliberate. Qwen's FP8-dense hybrid converts the lm_head to FP8 with a per-channel scale; the build checks the relative error and cosine of dequantized samples, on the CPU, but the effect on the GPU was never measured, and the recipe itself warns: if MTP acceptance drops, rebuild with the lm_head in BF16. In GLM, an EXL3 package can explicitly quantize the lm_head without padding, which requires a vocabulary that is a multiple of 64.

Checklist for your model

  1. Read the tokenizer. In tokenizer.json, tokenizer_config.json, config.json and generation_config.json (the map is in the vocabulary section): the type (byte-level BPE?), the config's vocab_size versus the ids actually used, the list of added_tokens and which ones have the special flag, multiple EOS ids and EOS disagreements between the files.
  2. Find the template. Is there Jinja in the checkpoint? Does it cover images, tools and reasoning, or is it “language-only”, as in GLM? Or does the format live in a Python encoder that requires its own --tokenizer-mode, as in DeepSeek?
  3. Prove the rendering. /tokenize with messages and add_generation_prompt must give ids identical to the reference apply_chat_template, with and without reasoning, with tools and with an image.
  4. Check the structural markers. <think>, </think> and the tool-call opener must be single tokens, because parsers, masks and thinking budgets work with ids. Also note whether they carry the special flag: without it, they show up in the text and depend on the reasoning parser.
  5. Stabilize the start of the prompt. Anything that varies per request (effort, date, session id) should come as late as possible, or the prefix cache dies at block 0.
  6. Do the lm_head math. \(V\cdot d\cdot 2\) bytes per read, times the reads per step (every draft round counts, whether the drafter has its own head, like Qwen's MTP, or shares the target's, like DSpark), divided by the TP. If that is a large slice of the step, consider a reduced vocabulary for the draft, chosen by coverage and with an eye on the most loaded rank.
  7. Check divisibility. \(V' = \lceil V / \text{lcm}(64, \text{TP})\rceil \cdot \text{lcm}(64, \text{TP})\). With TP=3 there is almost always padding (TP=3 and TP=4).
  8. Measure in tokens, never in words. Test contexts, warmup rungs and benchmark prompts: count them with the server's own tokenizer.

So far, each token has become a vector of \(d\) numbers, alone in its position, with no idea who came before it. The model only gets interesting when these vectors start exchanging information. That is the subject of the next chapter: Attention, the mechanism through which tokens talk to each other.
