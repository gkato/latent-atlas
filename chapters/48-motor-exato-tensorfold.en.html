Take the same checkpoint (GLM-5.3-Flash with routed experts in 4-bit EXL3, ~176 GB), the same two DGX Sparks and the same cable between them. Swap only the inference engine. The Mia's AI Lab recipe that traded vLLM for TensorFold v0.6.0 (by Ash Hart, Apache-2.0 license) plus 53 patches measured 60.4 tok/s on prose with a single request, where the vLLM recipe logged 36.1. It accepts the full native window of 1,048,576 tokens for four requests that share a pool of 2,922,496 tokens, and it answers an identical 64k prompt in under 0.07 s, versus 34 s the first time. (These numbers don't come from a controlled A/B, and we'll come back to that.) More intriguing than the numbers is the promise behind them. With drafts, the answer is bit for bit the same one you'd get generating one token at a time. Four requests served together receive the same bits they would receive alone. A prompt resumed from a kept state gives the same bits as the same prompt computed from scratch. This chapter is about the design ideas that make this possible and what they cost. The recipe, parameter by parameter, is the subject of the next chapter.

Two engines for the same model

In chapter 30 we took an engine apart into its pieces: API server, scheduler, KV manager, executor, model runner, kernels, sampler and communication between GPUs. vLLM assembles these pieces as a generic platform. It has a model registry, attention backends chosen by hardware and dtype, PagedAttention for any sequence, quantization plugins and CUDA graphs captured per batch size. The bet is on infrastructure that serves hundreds of architectures, with each model plugging into the sockets the engine offers.

TensorFold makes the opposite bet. In the words of the project's README, each model family brings its own kernels and its own draft verification. It is a per-family engine. In the Python line, up to 0.6.x, it has two backends: MLX, for Apple Silicon, and CUDA, for GPUs with compute capability ≥ 8.9, which includes Ada, Hopper and Blackwell, GB10 among them (NVFP4 and FP8 require ≥ 9.0). In v0.6.0 the families are Nemotron 3.5 Lightning, Qwen3.8-27B, Qwen3.8 Flash Next, GLM-5.3-Flash, Gemma 4, DeepSeek-V4-Flash (MLX only), Qwen3.6-35B-A3B and Ternary Bonsai 2. GLM-5.3-Flash runs on MLX on a 256 GB Mac or on CUDA with exactly two ranks, one per Spark (in v0.6.0; the recipe added a third rank with its patches 0066–0068).

Why does this weigh so much on this model in particular? Recall the anatomy from chapters 11 through 15. There are 45 layers: 34 of KDA (linear attention with a 128×128 recurrent state per head, chapter 14) and 11 of DSA, which is MLA (chapter 12) without RoPE, made sparse (chapter 13), with an indexer that picks pools of 4 tokens. On top of that come a 288-expert MoE with top-8 and 4-stream hyper-connections. It's a mosaic. In a generic engine every piece needs an adapter, and in the vLLM recipe those adapters show up as concrete costs:

  • the only sparse MLA kernel for SM12x requires the fp8_ds_mla record of 656 B per token and layer, which includes 128 B of zero-filled RoPE in a model that has no RoPE. That's ~24% more KV bytes in the DSA layers;
  • the KDA state goes in as a MambaSpec, and prefix caching only restores at points aligned to 3,584 tokens;
  • FULL CUDA graphs only apply to uniform batches, and mixed prefill and decode steps fall out of the graph;
  • it took writing a custom “fair” scheduler plus 25 Python overlays, reapplied on every docker run.

In the per-family engine, the forward is written layer by layer for this model. The cache stores exactly the 512-column latent, with no RoPE to pad. The KDA state is kept wherever the engine needs it, and CUDA graphs are captured by verification window width, not by batch size. Toggle between the two engines in the figure and watch the same cache row (one token, one DSA layer) in both layouts.

\[ B_{\text{tok}} = L_{\text{DSA}}\,\big(b_{\text{lat}} + b_{\text{idx}}\big):\qquad \text{vLLM: } 11\,(656 + 33) = 7{,}579\ \text{B} \qquad \text{TensorFold: } 11\,(528 + 36) = 6{,}204\ \text{B} \]
  • \(B_{\text{tok}}\): cache bytes per token, per rank (the latent is replicated on both ranks)
  • \(L_{\text{DSA}}\): layers with a per-token cache (11; the 34 KDA layers have fixed-size state)
  • \(b_{\text{lat}}\): latent bytes per token and layer (656 in fp8_ds_mla; 528 = 512 + 16 in kv8)
  • \(b_{\text{idx}}\): indexer bytes per token and layer (33 in vLLM; 144 B per 4-token pool = 36 in TensorFold)

At 1,048,576 tokens, that comes to ~7.40 GiB versus ~6.06 GiB per rank, 18% less. Whoever writes the engine for the family doesn't pay for another family's geometry.

Analogy: department store × tailor

vLLM is a department store with fitting rooms for every body type. Most of the time the clothes fit very well, and when they don't, you hem the trousers and add a pin (overlays, padding). TensorFold is a tailor who only takes a handful of clients but measures each one. The suit fits better. In exchange, every new client needs a new pattern, and in v0.6.0 anyone with 3 or 4 Sparks to connect wouldn't find their size (the GLM CUDA engine required two ranks; the recipe has since cut a three-Spark size, patches 0066–0068).

From Python 0.6 to the native engine 1.x

This chapter describes TensorFold v0.6.0, the Python engine that the GLM recipe pins. On 2026-10-07, TensorFold 1.0.0 replaced it with a native Zig binary: it loads checkpoints, tokenizes, renders chat templates and serves HTTP on its own, and runs Metal or CUDA kernels directly, with no Python or MLX installed. The Python line is frozen at 0.6.6 (tag v0.6.6, branch python-0.6); the native line reached 1.1.9 on 2026-10-29. The exactness contract survives the rewrite: a draft must equal the "draft": false token, resumed must equal fresh, concurrent must equal solo, for the same checkpoint, backend, settings and runtime. For GLM-5.3-Flash, the native engine serves CUDA ranks placed with TF_GLM_RANK and TF_GLM_WORLD (two ranks; a third runs since 1.1.2 with 22/21/21 heads, device qualification pending) and two M5 Ultra Macs on Metal. The GLM recipe still pins v0.6.0 plus its own patches, so the mechanisms below are v0.6.0's; where the native engine or the recipe changed one, the text says so.

Exactness as an invariant, not a goal

TensorFold's most radical design decision isn't about speed. It's a contract the documentation calls exact decoding, and almost every optimization among the 53 patches ends with a comment about it (“the same bits”, or the reason why not). There are four clauses, loosely paraphrased:

  1. A draft only gets in if it's equal. A draft is accepted only when it equals the token the same engine would produce serially.
  2. The draw has an address. Sampling depends on the prompt (or an explicit seed), the absolute position and the token id, and on nothing else.
  3. Rows don't see each other. The verification kernels keep each row's arithmetic independent of the other rows in the same call.
  4. Exactness has a scope. The guarantee holds against the same engine, with the same weights, runtime and settings. It does not imply identical output between MLX and CUDA, between different quantizations or between different rank counts.

From these clauses come four equalities, all verifiable by comparing response hashes:

✍️

Drafted = serial

The same answer as "draft": false, one token at a time (6/6 published cases).

👥

Concurrent = solo

Four together = each one alone: 11/11 staggered and 11/11 in a burst.

⏯️

Resumed = fresh

Resuming from a kept state ends in the same state as a prefill from scratch.

🪞

Rank 0 = rank 1

Identical bits in everything that is replicated: each Spark samples the same token without exchanging it.

None of this comes for free, because floating-point addition isn't associative (chapter 4). Every addition rounds, and the order of the roundings changes the result:

\[ (a \oplus b) \oplus c \;\ne\; a \oplus (b \oplus c), \qquad \text{e.g. fp32: } (2^{24} \oplus 1) \oplus 1 = 16{,}777{,}216 \quad\text{but}\quad 2^{24} \oplus (1 \oplus 1) = 16{,}777{,}218 \]
  • \(\oplus\): fp32 addition, i.e. exact addition followed by rounding to the nearest fp32 (ties go to even)
  • \(2^{24}\): from here on fp32 only represents even integers; \(2^{24}+1\) falls exactly halfway and rounds to \(2^{24}\)

In a typical engine, the order of the additions in a row depends on things that have nothing to do with it. A GEMM picks the reduction partitioning (split-K) and the tiles based on the number of rows in the batch. A selector like cuBLAS's switches algorithm depending on the shape. Float atomics add in the order the threads arrive. torch.topk switches code paths with size. All it takes is for your request's row to share a call with seven others and your logits change in the last bits, and in a near-tie that flips the chosen token. From then on, the answer diverges. That's what the figure shows, with real fp32 numbers.

TensorFold deals with these sources case by case, and the pattern is described in the concurrency patches. “Per-row” kernels (4-bit matmuls, norms, the hyper-connection glue, the experts) use a fixed partition based on the weight shape and fixed tiles, and therefore give the same bits for any slice of rows: these are the row-independent kernels. Whatever depends on each stream's state (the KDA recurrence, DSA attention, the context of DFlash2, the drafter from chapter 37) runs with per-row tables that exactly reproduce the loop, the tiles and the head blocks of the single-stream kernel. Whatever could choose a kernel by row count (the F.linear selector, DFlash2's torch.topk) runs per stream, only on that stream's rows. Reductions with atomics are restricted to integers, like the histograms of the top-k selection, which give the same result in any order. The name for the whole set is batch invariance.

The payoff shows up in three places. First, hash tests: every response carries a token_sha, and a correct optimization cannot change it. That's why the recipe states that COMM=roce, SPLIT=1, TF_GLM_L2PF and TF_GLM_EXL3_LOADS “move the same bits”. Second, freedom to optimize drafting, since no draft policy can change an answer. Third, safe recomputation: you can throw away a request's work and redo it knowing that the tokens already sent will come out the same.

Exact against the engine ≠ faithful to the checkpoint

The recipe leaves on three defaults that are not exact against the bf16 checkpoint, in exchange for speed and the 1M window. DENSE=q4 and KV=fp8 lose information, and KDA_CHUNKED=1 stays “close to the serial kernel, not on its bits”. The FP8 format's docstring sums up the philosophy: lossy (the owner's call), never inexact. In other words, the four equalities still hold, because each row's bytes depend only on that row. If you want the checkpoint as it is, use DENSE=bf16 KV=bf16 KDA_CHUNKED=0 and accept a smaller window (196,608 tokens).

What about vLLM?

In chapter 35 we saw that vLLM's speculation is “lossless” in distribution: rejection sampling preserves \(p\), but the batch, the graph and speculation itself change bits, and the greedy guarantee holds “up to numerical precision”. That isn't a flaw, it's a different choice. Requiring batch invariance constrains the kernels (no adaptive split-K, no float atomics), and those kernels tend to be the fastest for large batches. The GLM recipe could pay that price because it served at most 4 requests in v1.3.2 (8 since v1.5), not hundreds. The native engine runs more under the same contract: on CUDA, --parallel auto asks for up to 8 streams, GLM fits --parallel 16 at a 40,960-token window (1.1.0), and on Metal the Qwen3.8-27B's shared rounds take up to 128 streams. That is still a small batch next to a cloud deployment (interpretation).

Keyed sampling: a draw you can redo

Recall the sampler from chapter 9: divide the logits by the temperature, cut with top-k, top-p and min-p, renormalize and draw. The draw uses a stateful random number generator. The value that comes out at position \(p\) depends on how many numbers were pulled before, and that depends on the batch, on how many drafts were verified and on how many resamples rejection triggered. Even with a fixed seed, changing the speculation setup changes the answer.

TensorFold takes the state out of the generator. In keyed sampling, the random number that decides token \(i\) at position \(p\) is a pure function of three things: the seed, the absolute position and the token id. The seed is the request's seed or, if none is given, the SHA-256 of the prompt ids (8 bytes, 63 bits). That's why, as the README puts it, “the same request gives the same answer”. (That is v0.6.0's rule, which the GLM recipe still runs. In the native engine, since 1.1.1, a sampled request without a seed draws a fresh random one and logs it for replay; --prompt-seed restores the prompt-derived key, and greedy decoding is unchanged.) The mixing uses three rounds of splitmix64 and returns a double in \((0,1)\). The draw itself is the Gumbel-max trick:

\[ u_{p,i} = H(s,\,p,\,i), \qquad g_{p,i} = -\ln\!\big(-\ln u_{p,i}\big), \qquad x_p = \arg\max_{i\,\in\,\mathcal{C}_p}\Big(\frac{z_{p,i}}{T} + g_{p,i}\Big) \] \[ g_{p,i} \overset{\text{iid}}{\sim} \mathrm{Gumbel}(0,1) \;\Longrightarrow\; \Pr[x_p = j] = \frac{e^{z_{p,j}/T}}{\sum_{i \in \mathcal{C}_p} e^{z_{p,i}/T}} \]
  • \(s\): the seed (the request's seed or the SHA-256 of the prompt ids)
  • \(p\): absolute position of the token in the sequence; \(i\): token id in the vocabulary
  • \(H\): keyed hash (three rounds of splitmix64) that maps \((s,p,i)\) to a uniform in \((0,1)\), with no state
  • \(z_{p,i}\): logit of token \(i\) at position \(p\); \(T\): temperature
  • \(\mathcal{C}_p\): candidates left after the cuts (top-k, top-p and min-p, with min-p applied after top-p, “as SGLang does”; vLLM applies min-p before it)
  • \(g_{p,i}\): Gumbel noise. The second line is the theorem guaranteeing that the noisy argmax has the softmax distribution

Why does the theorem hold? With \(g = -\ln(-\ln u)\), the quantity \(E = e^{-g} = -\ln u\) is an exponential with rate 1. So \(\arg\max_i (z_i/T + g_i) = \arg\min_i E_i\, e^{-z_i/T}\), and each \(E_i\, e^{-z_i/T}\) is an exponential with rate \(e^{z_i/T}\). The draw turns into a race between independent exponential clocks, and in a race like that candidate \(j\) arrives first with probability \(e^{z_j/T} / \sum_i e^{z_i/T}\): exactly the softmax.

Candidates are sorted by decreasing value, with ties broken by increasing id, and the final choice is made on the host, in float64 (numpy). The token at position \(p\) becomes a deterministic function of the logits and the key. Now see what this does to speculation. In a round, the target computes the logits for every position in the window and samples each one with its key. Verifying a draft becomes comparing two integers:

\[ a = \max\{\, j \le k \;:\; d_i = x_{p+i}\ \ \forall\, i \le j \,\}, \qquad \text{emitted: } x_{p+1}, \dots, x_{p+a+1} \]
  • \(d_1,\dots,d_k\): drafts proposed for positions \(p+1,\dots,p+k\)
  • \(x_{p+i}\): the target's keyed sample at position \(p+i\), with the logits computed during verification
  • \(a\): accepted drafts, up to the first disagreement; token \(x_{p+a+1}\) is always emitted (the correction, or the bonus when all of them pass)

Since \(x_{p+i}\) doesn't depend on who proposed the draft, the output is the serial decoding whatever the drafter or the stopping policy. A bad drafter only makes the round shorter. This is verification by equality, and the figure lets you compare it with rejection sampling.

Look at the drafter in “verify” mode. Since the target's noise is known before verification (it's a function of the key), the drafter can use it to predict which token the target will draw. TensorFold's DFlash2 does this in its selector (weight NOISE = 0.7), and the recipe's stopping policy, fnc7:0.3, measures the chain's confidence under that noise, with \(\mathrm{softmax}((\text{score}+g)/\beta)\) and \(\beta = 2.0\) tuned on 9 dumps. The measured gain over the previous policy was 47.2 → 50.6 tok/s on prose and 51.7 → 55.5 on code. With rejection sampling, this would be impossible: the target's draw doesn't exist yet when the draft is made.

Exact top-p with the vocabulary split in two

There's also a detail that comes from distribution. The head (lm_head) is split by vocabulary, and each rank holds logits \([R,\ V/2]\). For top-k, each rank sends its k best candidates plus a margin of 8. With top-k off (top_k ≤ 0 in the request), only the top-p nucleus is left: each rank sends up to 1,024 candidates (the server default is \(T = 1.0\), top_k 20 and top_p 0.95, so, by the v0.6.0 code, a request without these fields takes the top-k path, with 28 candidates per rank; note that the recipe’s issue #91, in October, measured default requests on the top-k-off nucleus path at ~15 tok/s against greedy’s ~58 and describes the checkpoint’s defaults as top_k 0, which is why NUCLEUS_UNION=1 became the default in v1.9 — check which path your build takes before trusting a sampling benchmark), and if a row's nucleus goes beyond those 1,024, the whole shard is read. The probability masses become fixed-point integers, so that the cumulative sum is exact and doesn't depend on which rank adds what:

\[ m_i = \Big\lfloor e^{\,\tilde z_i - \tilde z_{\max}} \cdot 2^{40} \Big\rfloor, \qquad \text{need} = \Big\lceil \text{top\_p} \cdot \textstyle\sum_i m_i \Big\rceil \]
  • \(\tilde z_i\): the candidate's logit, already scaled by temperature; \(\tilde z_{\max}\): the largest of them
  • \(m_i\): fixed-point mass (64-bit integer, scale \(2^{40}\))
  • \(\text{need}\): integer mass the nucleus must cover; integer sums are exact in any order, so “one GPU = two GPUs”

What do you lose with all this, in the v0.6.0 engine the recipe runs? The API rejects logprobs, top_logprobs and any n other than 1 with HTTP 400 (“this engine returns no token probabilities”), and it accepts but ignores logit_bias and the presence, frequency and repetition penalties (chapter 9). Our own reading (this is interpretation): the sampler only sees the candidates that crossed the wire, not the full softmax, and any adjustment that depends on the generated history would have to go into the keyed function without breaking equality with the serial path. There's also a host cost. Third-party measurements on a similar TensorFold engine estimate ~2.3 ms per round for the float64 choice with 4 streams. The native engine shows that the missing probabilities were a gap, not a law of keyed sampling: on CUDA it returns logprobs (Nemotron since 1.0.5, streamed and on /v1/completions since 1.0.8), read on the GPU from the verified target logits, so drafted, concurrent and resumed requests give the same rows; GLM on CUDA returns prompt_logprobs since 1.1.1. It also takes an API key (--api-key, --api-key-file) and serves Anthropic Messages.

Tensor parallel without all-reduce: fp32 partials summed in rank order

In chapter 38 we saw the classic tensor-parallel pair: one projection split by columns, another by rows, and an all-reduce at the end to add up the partial contributions. For GLM on two Sparks, this happens twice per layer, after the attention block and after the MoE/MLP block. Each rank ends up with a partial \(P^{(r)}\) of shape \([R,\ D]\) in fp32, where \(R\) is the number of rows in the window and \(D = 4{,}096\). One partial row takes up \(4{,}096 \times 4 = 16\) KiB.

TensorFold doesn't call all-reduce. Each rank does an all-gather of the fp32 partials and performs a rank-order sum, rank 0 first. In the code's own words: “NCCL all-gather on the current stream, so CUDA graphs capture it; a rank-ordered sum after it keeps the ranks bitwise identical”.

\[ \Delta = \mathrm{bf16}\big(P^{(0)} \oplus P^{(1)}\big) \quad (\text{rank 0 first, rounds once}), \qquad P^{(r)} \in \mathbb{R}^{R \times 4096}\ (\text{fp32}) \] \[ X'_s = \mathrm{bf16}\Big(\text{post}_s\,\Delta + \big(((c_{0s}x_0 + c_{1s}x_1) + c_{2s}x_2) + c_{3s}x_3\big)\Big), \qquad s = 0,\dots,3 \]
  • \(P^{(r)}\): the partial computed by rank \(r\) with its half of the weights
  • \(\oplus\): element-wise fp32 addition. With two operands it is commutative: \(P^{(0)} \oplus P^{(1)} = P^{(1)} \oplus P^{(0)}\) bit for bit
  • \(\mathrm{bf16}(\cdot)\): rounding to bf16 (round-to-nearest-even); the branch \(\Delta\) is rounded only once
  • \(x_0,\dots,x_3\): the 4 residual streams of the hyper-connections (stored in bf16, read in fp32); \(c_{ks}\) and \(\text{post}_s\): glue coefficients, per row
  • \(X'_s\): stream \(s\) after the layer, rounded to bf16. In the MTP block, which has a plain residual, the rule is \(h' = \mathrm{bf16}(h + \Delta)\) (_residual_add in glue.py)

Notice what does not enter the fp32 chain: the residual. The two partials are summed on their own, rank 0 first, rounded once to bf16, and only then is the branch \(\Delta\) mixed into the 4 streams in a fixed order (the _hc_post kernel in glue.py). With exactly two partials, the order wouldn't even make a difference: \(a \oplus b = b \oplus a\) bit for bit, so the two ranks would agree summing in any order. Rank order is the engine's general rule. It starts to matter with 3 or more ranks, where \((P^{(0)} \oplus P^{(1)}) \oplus P^{(2)}\) can differ from \(P^{(0)} \oplus (P^{(1)} \oplus P^{(2)})\) (the \(2^{24}\) example from the section on exactness), and it takes the order out of the library's hands. As one of the engine's docstrings puts it, “an NCCL all-reduce leaves the order to NCCL”.

The numerical gain that already applies with two ranks is a different one: summing in fp32 and rounding once. In vLLM, each rank finishes its half of the projection with a bf16 output, and the all-reduce adds those bf16 activations. The result is \(\mathrm{bf16}\big(\mathrm{bf16}(P^{(0)}) + \mathrm{bf16}(P^{(1)})\big)\), with two roundings along the way. A test in TensorFold itself checks that the streams receive \(\mathrm{bf16}(P^{(0)} + P^{(1)})\), rank 0 first, “exactly like a plain branch” would. Compare the two paths in the figure, and flip the order of the sum to see that, with two operands, not a single bit changes.

There's an engineering gain too. In an all-reduce, the arithmetic happens inside the library, which picks the algorithm, protocol and number of channels based on message size. With an all-gather plus its own sum, the library only moves bytes. That's why TensorFold can send small messages over a hand-built RDMA transport (RDMA and NCCL are covered in chapter 39) and large ones over NCCL, “with the same output layout (rank order) and the same bits”. Switching transports stops being a numerical decision.

And the cost? With two ranks, all-reduce and all-gather move the same number of bytes for the same tensor of \(S\) bytes: a ring all-reduce sends \(2(N-1)/N \cdot S = S\) per rank, and the all-gather sends \(S\). But the two recipes don't move the same tensor. TensorFold sends fp32 partials (16 KiB per row), whereas vLLM reduces bf16 activations (8 KiB per row): that's ~2× the bytes on the wire. In decode this barely matters, because the messages are so small that what dominates is the fixed latency α of the α-β model, the topic of the second-to-last section. With \(N\) ranks the all-gather would get even worse, because each rank receives \((N-1)\,S\) (our own math; the v0.6.0 GLM CUDA engine used exactly two, and the recipe has run three since v1.4). The native engine attacks that cost: its rank_scatter (1.0.12) sums the fp32 partial rows in rank order over NCCL send and receive, each rank receiving only its own rows, and ends with the bits an all-gather plus a rank-order sum would give.

Other splits between the two ranks

Head split by vocabulary: each rank holds half the logits and exchanges only candidates. Replicated latent cache: each Spark stores the full latent of every token (the cache geometry doesn't divide by the number of ranks; an interpretation consistent with the code). That is still the default; the recipe's patch 0129 (TF_GLM_KV_SHARD=1, opt-in) can store each conversation's latent once, on its owner Spark: 6,204 → 3,300 B per token per Spark, 1.87× the pool on two Sparks. Hyper-connection glue split by rows during prefill (SPLIT=1): each rank owns half the rows of the chunk, receives from its peer only the partial for those rows, sums “rank 0 first” and sends back the normalized rows in bf16. Since the glue is row-independent, the bits are those of the unsplit path. The 50k prefill went from ~1,270 to ~1,730 tok/s (together with two prompt-kernel patches), and decode pays ~1.5%.

One rank per Spark: rank 0 decides, rank 1 applies

Each Spark runs a container with tensorfold serve <snapshot> --tp 2 --rank R --master <head> --master-port 29551. Rank 1 (the worker) comes up first, over ssh, and then rank 0 (the head), which also opens the API on port 8888. There's no EngineCore in a separate process and no worker pool: just two processes, one per machine.

Rendezvous. Rank 0 creates a PyTorch TCPStore at master:29551 (600 s timeout), generates the ncclUniqueId and publishes it to the store under the key tf_nccl_uid. Rank 1 reads the key and both call ncclCommInitRank. NCCL is loaded through ctypes (libnccl.so.2), without torch.distributed process groups, and the only collective is ncclAllGather on the current stream, which makes it capturable in a CUDA graph.

Same settings or nothing. At startup, each rank packs its relevant settings into a list of integers (context, prompt grid, copy drafts, split, MAX_ROWS, wide graphs, nucleus union…), does an all-gather and refuses to start if the lists diverge (“the two ranks were started with different settings”). It's a fail-closed design, and every patch that adds a knob adds it to this list. That's why start.sh forwards every TENSORFOLD_*, TF_GLM_* and TF_ROCE_* variable to both containers.

Leader and follower. The concurrency core is an SPMD with a leader, and the docstring sums up the rule like this: “rank 0 decides everything that depends on time, clients or allocation; rank 1 applies”. On every iteration rank 0 sends one message, an int32 vector sent through two all-gathers (first the length, then the values), with a list of operations: ADMIT, EVICT, MOVE, GROW, FILL, ROUND, FINISH, IDLE (plus SLOT and MFILL in later patches). Both ranks apply these operations in the same order and through the same code. An ADMIT carries the stream id, the slot, the base and size of the extent, the kept prompt to resume from and the sampling settings packed into 10 int32 (the seed in three words of 31/31/2 bits; temperature, top_p and min_p as fp64 in two words each; top_k in one), along with the shared-prefix points, the policy, the prompt, the grammar and the image positions. Drafts don't travel: rank 1 derives them on its own (the same prompt and the same tokens give the same proposals) and only checks the depths rank 0 sent.

Why centralize like this? (Interpretation.) What can diverge between two machines is the clock, the arrival of clients, disconnections and memory allocation, and all of that stays on rank 0. Everything else is a deterministic function of shared state, and exactness guarantees the same bits on both sides. vLLM also has a leader (the EngineCore sends the scheduler output to the workers). Here, however, the message is a short list of operations, and the heavy data is recomputed locally.

At rest. An idle rank 1 doesn't wait inside an all-gather, where it would keep the GPU spinning. It waits on a doorbell, a key tf_glm_request_<n> in the TCPStore itself. The result is that an idle server ties up neither the GPU nor a CPU core. This patch originated in Mia's recipe and was merged into TensorFold v0.6.0.

Failures. “After an error, the two ranks can no longer be trusted to agree”: a broken flag latches and every subsequent call fails until both restart. With FOREGROUND=1, start.sh takes one rank down if the other dies (“a lone rank would wait for its peer forever”), and a watchdog (TF_GLM_MULTI_WATCHDOG_S, 300 s) dumps the Python stacks of a stuck iteration. The patch 0040 deadlock teaches the general SPMD rule: every decision that leads to a collective must be a function of something identical on both ranks. Memory addresses aren't. The number of bytes is.

Memory: what the system says is there, minus a reserve

On GB10, CPU and GPU share the same 128 GB of LPDDR5X (chapter 27). That changes the physics of “running out of memory”. TensorFold's documentation warns that the server's allocations come out of host RAM but aren't charged against the container's memory limit (docker run --memory, cgroup memory.max), and that exhausting the memory of a unified GPU can freeze the host. The recipe is blunter: on the Spark, running out of memory tends to freeze the machine rather than make an allocation fail. There's no polite CUDA out of memory to catch.

TensorFold's rule starts from what the operating system says is available right now:

\[ B = \texttt{MemAvailable}_{\text{startup}} - R, \qquad R = \max\!\big(4\ \text{GiB},\ \tfrac{\text{RAM}}{10}\big)\ \ \text{or}\ \ \texttt{TENSORFOLD\_MEMORY\_RESERVE\_GIB} \] \[ E > B \Rightarrow \text{refuse before loading weights}, \qquad \text{extra pool} \approx \min\!\big(\texttt{KV\_POOL\_GIB},\ B - E\big) \]
  • \(\texttt{MemAvailable}\): a field of /proc/meminfo. On an integrated GPU, reclaimable page cache counts as available (“a single pool on a unified GPU”); on a discrete GPU the minimum of the GPU's free memory and the host's is used
  • \(R\): reserve. TensorFold's default is a tenth of RAM (~12.2 GiB); the recipe uses 14.5 GiB. It also covers the CUDA context, NCCL and workspaces the estimate doesn't count (3.5 to 4.8 GiB measured in the GLM document)
  • \(E\): the engine's startup estimate for the requested configuration (88.09 GiB on the recipe's rank 0, with ~80 GiB of weights)
  • extra pool: whatever is left becomes a pool of caches beyond the window, up to KV_POOL_GIB (12.5 GiB per Spark in the recipe). This is our reading of the README, which doesn't exactly reconcile the 2,922,496 tokens

If the configuration doesn't fit, the engine refuses before loading a single weight and reports the largest window that would fit. start.sh reads that line from the log and restarts once with --context N. There's one more important operational detail: at the worst moment (a 1M prompt), the server uses ~10 GiB beyond its own estimate. So the reserve also sets the minimum free memory, which ends up around \(R - 10\). With 14.5 GiB, ~4.5 to 5 GiB remain free on the head at the tightest moment. The recipe's measurement: idle MemAvailable of 7.0 GiB (rank 0) and 10.5 GiB (rank 1), a minimum of 5.6 and 9.5 GiB under a 1M prompt, and a warning from start.sh if any Spark has less than ~110 GiB free at startup. These numbers suggest that most of the ~10 GiB is already taken with the server idle: between idle and the minimum under 1M, the difference is only ~1.4 GiB on rank 0 and ~1.0 GiB on rank 1 (our interpretation).

In vLLM, gpu_memory_utilization times total memory defines a fixed ceiling, and a profile run measures what's left for KV, ignoring the page cache and other processes. The GLM vLLM recipe had to pin --kv-cache-memory-bytes (11 GiB, 1,233,779 tokens at 850k), tune the fraction in hundredths and live with crashes from a zeroed MemAvailable. The price of TensorFold's rule is a pool that depends on the machine at startup: ~2.1 to 2.9M tokens, and 2,922,496 in the measured startup, already at the 12.5 GiB cap.

One pool, four conversations: extents instead of pages

The GLM CUDA engine in TensorFold v0.6.0 “serves one request at a time”, with window-sized tensors. The recipe's concurrency core (patch 0030) needs to serve up to 4 requests (PARALLEL from 1 to 4 in v1.3.2; 1 to 8 since v1.5) without reserving 4 windows of 1M. The solution starts by separating what grows with context from what doesn't:

per token
Caches: the latents of each DSA layer, the indexer's grouped keys (one row per 4-token pool, with 2 pad rows because selection reads up to 2 pools past the window) and those of the MTP layer, as planes of a shared arena.
per stream
Slots: the KDA states [count, 2, layers, H, 128, 128] fp32 (with two parities, so verification doesn't destroy the committed state), the convolution windows, the window scratch and the DFlash2 context. On the host live the copy-draft index, the sampler and the grammar. An extra slot costs ~177 MiB per rank (our research's estimate, based on the code).

Each live stream (or kept prompt) owns an extent \([\text{base},\ \text{base}+\text{size})\) of contiguous arena rows, with base and size multiples of ALIGN = 2048 tokens. The single-stream code (prefill, decode windows, snapshots) runs over views of that extent “exactly as over its own tensors”. The bookkeeping is done on the host and is deterministic: first fit by lowest base, growth in place, relocation (MOVE, with a safe copy even when source and destination overlap) and compaction. Since the same operations happen in the same order on both ranks (previous section), the pools stay identical without any map having to be exchanged. A request is only admitted if there's room:

\[ L + K \;\ge\; \mathrm{align}_{2048}\!\big(n + 16\big) + 2048 \cdot D \]
  • \(L\): free rows in the pool; \(K\): rows of extents that only hold prompts (they can be evicted)
  • \(n\): prompt tokens; \(16\): MAX_ROWS, the widest verification window of a stream
  • \(D\): streams decoding; each one gets a slack block of 2,048 to grow into

If it doesn't fit, the request waits at the front of the queue, in FIFO order (NoRoom). A prompt larger than the whole pool fails. To make room, the v1.3.2 engine evicts kept prompts (LRU, never the protected ones), compacts, and grows in place or relocates; since v1.6 the recipe compacts before it evicts, and the order in which kept states go is no longer plain LRU (chapter 49, update). If a stream can't grow into the next window, it is paused. If all of them are paused and none is prefilling, the newest one without a grammar or images goes back to the queue and is redone later, and the tokens that had already been sent “are owed, not resent”. This preemption by recomputation is only safe because sampling is keyed.

The contrast with chapter 31 is direct. PagedAttention pages the KV into small blocks with one table per sequence: near-zero fragmentation, but kernels that gather through the table and, in a hybrid, giant pages (3,584 tokens in GLM) to align the recurrent state. Extents pay for fragmentation with occasional compaction and, in exchange, the kernels read contiguous rows, and the multi-stream batch carries only a small table per segment (SegRows). With few streams and huge windows the trade is a good one; with hundreds of short sequences, paging would win by a wide margin. The native engine went the paging way for GLM: since 1.1.6, GLM-5.3-Flash on CUDA takes its KV pages from a core pool by default from two ranks up (at TP=2 with the NVFP4 checkpoint, identical tokens and two streams 14% faster). By the README's rule, “a request can grow up to the full window and the four share the pool”: one 1M conversation next to another 1M one, or next to three of ~640k. /health shows pool_tokens, pool_free_tokens and the streams that are decoding, prefilling and paused.

Reuse without APC: kept states, a grid of 64 and replay

In an attention-only model, reusing a prefix means reusing KV rows, and the APC from chapter 33 does this with chained hashes of full blocks. In a hybrid, the “prompt state” also includes the recurrent state of each KDA layer (128×128 matrices per head), the convolution windows, the DFlash2 window and the tails of the indexer rings. That state exists at one point of the prompt and can't be sliced. vLLM handles this by storing block-aligned checkpoints, which in the GLM recipe fall every 3,584 tokens. The hit is rounded down to a whole block and the tail is recomputed.

TensorFold keeps a few whole prompt states, at hand-picked points:

  1. At the prompt grid point. With prompt grid \(G\), every prompt chunk starts at a multiple of \(G\), and the kept state sits at the last multiple of \(G\) inside the prompt. If the prompt doesn't end on the grid, the request prefills up to that point, keeps the state and resumes from it to the end. That way, “any prompt that extends prompt[:B] goes through the same state there, fresh or resumed”.
  2. At the end of the system block and at the divergence point (SHARED_PREFIX=1). A text-only request with drafts also keeps states where the prompt stops sharing with a kept prompt and at the end of the system block (the first occurrence of <|user|>). Each one lands on the grid, only if it adds ≥ 256 tokens, and at most 2 per request. This is the shared prefix.
  3. With the logits row, at the end (replay). A state alone isn't enough for an identical prompt, because the first token of the answer needs the logits of the last position. When the end of the prompt falls on the grid, the snapshot also keeps the head's logits row, before any grammar mask. An identical resubmission resumes there and samples the first token from that row “without prefilling anything”. This is replay.
\[ B(n) = G\,\lfloor n/G \rfloor, \qquad \text{replay (logits row kept)} \iff n \bmod G = 0, \qquad G = 64 \] \[ h_{\text{APC}}(n) \approx 3584\,\Big\lfloor \frac{n-1}{3584} \Big\rfloor \]
  • \(B(n)\): where the kept state of an \(n\)-token prompt sits (the code's grid_point). When \(n\) is a multiple of \(G\), \(B(n) = n\) and the snapshot also carries the logits row, which enables replay; otherwise, \(n - B(n) < G\) tokens are left to prefill
  • \(G\): the grid. With KDA_CHUNKED=1 it's 64, because the chunked KDA kernel works in sub-chunks of 32 rows at absolute positions, and a row's bits are only reproducible if the chunks start at multiples of 32
  • \(h_{\text{APC}}\): the APC hit on an identical resubmission, in a simplified version (blocks of 3,584, with the last position always recomputed to get the logits)

On an identical resubmission, then, TensorFold redoes zero tokens if \(n\) is a multiple of 64, and at most 63 otherwise. The simplified APC redoes up to 3,584. The numbers measured by the recipe: an identical 64k prompt in 34 s → under 0.07 s, and a new conversation with the same 7.9k system prompt in 4.24 → 0.13 s. On the vLLM side, the GLM recipe logged a ~8k follow-up at 8.53 → 1.30 s and the resubmission of 814,571 tokens in 2.748 s. A third party (the jayleaton project, with a different setup) measured that, on this model, a replay in vLLM recomputes ~8.2k, 5.7k and 11.1k tokens at 8K, 32K and 64K.

Look at the follow-up, because there TensorFold doesn't always win. The kept state sits at the point of the previous prompt, so the answer the model generated and the new message get prefilled again. APC, on the other hand, also keeps full blocks generated during decode. It's a design trade-off. TensorFold bets on exact, instant reuse for typical agent patterns (resending the conversation, sharing the system prompt) and gives up arbitrary reuse in the middle of any prefix.

Two operational limits complete the picture. The number of states is TF_GLM_CACHE_ENTRIES (8 in TensorFold, 32 in the recipe; ~45 MiB fixed per entry by the v1.3.2 estimate, ~91 MiB measured later with patch 0097): an agent request keeps 1 to 3 states, and with 8 entries three or four alternating conversations kept evicting one another. Prompts with images and requests with a grammar don't get replay. And the lesson of TF_GLM_MULTI_LONE: moving a lone stream onto the single-stream graphs yielded 0.6 to 0.9%, but it moved the stream to the start of the pool and evicted the other conversations' prompts. With three conversations alternating, 0% of prompts came from the cache with the mode on, versus 98.1% with it off. The recipe has kept it off since v1.3.1.

Rounds, windows and the wire between the Sparks

In TensorFold, the unit of time for decode is the round. It has five steps: propose drafts, run one verification forward over [pending token, drafts…] (the verification window), sample each row with its key, accept up to the first disagreement and commit the accepted rows (KV, KDA state, conv and drafter context). In one stream, the window goes up to MAX_ROWS = 16 rows: the pending token plus up to 15 drafts. This exists for the copy drafts, which look up the last 8 tokens in the prompt and in the answer and propose whatever came next, up to 15 per round (answers to editing tasks went from 84 to 119 tok/s). DFlash2 proposes up to 7, stopping by the fnc7:0.3 policy. With several streams, the combined window has at most MAX_WINDOW = 32 rows. If it goes over, the engine trims one draft at a time from the longest window.

\[ R = \sum_{s=1}^{S} \big(1 + k_s\big) \le 32, \qquad \text{bytes per all-gather} = R \cdot 4096 \cdot 4 = R \cdot 16\ \text{KiB} \le 512\ \text{KiB} \]
  • \(S\): streams decoding (up to 4 in v1.3.2; 8 since v1.5, with a 64-row window past 4 streams); \(k_s\): drafts of stream \(s\) in this round
  • \(R\): rows in the batched window. Each layer does two all-gathers of \([R, 4096]\) fp32 partials
  • 512 KiB: the recipe's TF_ROCE_MAX_KB, which fits exactly the full batched window of 4 streams

One graph per width. Instead of capturing CUDA graphs per batch size, like vLLM (chapter 29), TensorFold captures them per number of rows in the window: 1 to 8 (plus 16 with COPY_CODE=1) for one stream, and a graph for each count from 1 to 32 in the multi-stream batch. The trick that makes this possible is that positions, extents, slots and parities live in tables on the device, filled by an asynchronous copy before the replay. That way “one graph per row count covers any mix” of streams. The graphs are captured on slot 0, in the first rows of the pool, before any admission. The KDA state has two parities: the window writes to the other one, and on commit it's enough to flip the parity, or to rebuild the state from the accepted rows only. Decode always stays inside a graph. In an old cost measurement, verifying 8 rows took 66.0 ms versus 29.2 ms for one, ~2.3× more (the VERIFY_MS table from the policy simulator, from before the later decode optimizations). That slack is what speculation exploits.

The one-shot all-gather

Each layer does two all-gathers per round, and there are 45 layers. With a typical window, the message is tens of KiB. In the α-β model from chapter 39, \(t(n) \approx \alpha + n/\beta\), messages of that size are dominated by α, and the code itself notes that NCCL spends most of each one on fixed latency (~30 to 50 µs). On the DGX Spark there's an aggravating factor: there is no GPUDirect RDMA in the stack, so NCCL routes the data through the host.

Patch 0006 uses the “RoCEnante” transport from the b12x project and exploits a property of GB10: since the GPU is integrated and memory is unified, pinned host memory is directly addressable by GPU kernels, at full bandwidth, and the network card can register it with a simple ibv_reg_mr. The one-shot all-gather becomes a single kernel call in five beats. (1) Each block copies its part of the local shard into a pinned send slot. (2) The last block publishes the size and rings a doorbell after a system fence; a proxy thread in C (libibverbs) does an RDMA WRITE of the payload to the peer, in stripes split between the two HCAs, each stripe followed by a 4-byte write with the sequence number on the same reliable QP, so the flag never becomes visible before the data. (3) One thread per (peer, HCA) waits for the flag with system-scope acquire loads, with a timeout: running past it “poisons” the runtime. (4) Each block copies the shards in rank order. (5) The last block advances a device epoch, so a CUDA graph can replay the exchange without the host. Two slots, used ping-pong style, are enough.

\[ \Delta t_{\text{round}} \approx N_{\text{ag}}\,\big(t_{\text{NCCL}} - t_{\text{RoCE}}\big) = 90 \times (45 - 11)\ \mu\text{s} \approx 3.1\ \text{ms} \]
  • \(N_{\text{ag}}\): all-gathers per round (2 per layer × 45 layers)
  • \(t_{\text{NCCL}}, t_{\text{RoCE}}\): 45 µs and 11 µs per 16 KiB all-gather (README)
  • with rounds on the order of 50 ms, that's a few percent, consistent with the +6% measured (our own back-of-the-envelope math, which ignores the actual size of each window)

What goes over RoCE is decided only by the number of bytes: up to TF_ROCE_MAX_KB (256 in TensorFold, 512 in the recipe) goes over RDMA, and the rest over NCCL, with the same layout and the same bits. Raising it to 512 KiB put the 17-to-32-row windows on the fast transport (+1.4% on code at 4 streams). RoCE itself (COMM=roce against nccl, patch 0006, measured on an intermediate build and separately from the 512 KiB raise) gave +6% decode (prose 44.2 → 46.9, code 48.7 → 51.6 tok/s). The large prefill gathers stay on NCCL, on both rails (the QSFP port shows up as two PCIe Gen5 x4 functions; 32 MB drops from 3.5 to 1.9 ms) and with a correct RoCE v2 GID (a v1 or zeroed entry brings NCCL down “about a minute later”). And a custom transport brings its own failures: on first startup, each rank compiles its CUDA extensions on its own, and the two can drift further apart than the RoCE wait tolerates (~20 s in v1.3.2, TF_ROCE_WAIT_S; 300 s since v1.6). That's why patch 0052 makes each gather wait for the peer at an NCCL barrier until the engine is ready.

When to choose which engine

In v1.3.2, TensorFold was worth it when you had exactly two Sparks, up to 4 requests, agent workloads that resend the history, a priority on single-user decode and on the 1M context, and an interest in reproducibility (without a seed, the same request gives the same answer; "draft": false gives the serial reference). Since 2026-10-04, Mia's own vLLM recipe tells everyone to use the TensorFold one, which now runs three Sparks and eight requests. Stay on vLLM if you need logprobs, n>1, penalties, authentication on the server itself, four Sparks (its main branch has an experimental launcher) or a faster boot, or if you don't want to maintain a patch stack against a single engine version (53 patches then, 123 now). Watch out for the license: DFlash2 is CC BY-NC-ND (non-commercial) in both recipes. In TensorFold, DRAFTER=mtp avoids the problem at the cost of PARALLEL=1.

You now know how the engine thinks: exactness as a contract, a draw with an address, ranks that agree without talking, memory measured before it's promised, extents, kept states and an 11 µs wire.
