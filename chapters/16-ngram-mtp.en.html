Two architecture tricks look like magic the first time you see them in a config.json. The first is a table of 51.2 billion parameters in Qwen3.8-Flash-Next from which each token reads only 16 rows, at a practically zero cost in FLOPs: a hash-addressed N-gram memory that the vLLM code calls PLE. The second is an extra layer, trained to predict not the next token but the one after it, which at serving time becomes a free drafter: Multi-Token Prediction. In this chapter you will open both boxes. We will compute the hash by hand, understand why the tables have prime sizes, follow the retrieved row all the way to the residual stream, discover what state this layer carries between steps and see why loading a 51 GB table took an entire patch. On the MTP side, we will assemble the module piece by piece in the three models and understand where Qwen's mtp.layers.48 and DeepSeek's k=6 come from.

Capacity without FLOPs: the third axis

So far you have seen two ways of giving a model more "knowledge". In a dense model, every parameter works on every token: doubling the parameters doubles the FLOPs. In Mixture-of-Experts, the model stores many experts and each token wakes up only a few. Qwen3.8 has 512 experts per layer and uses 10, which gives 120.8 B parameters stored in the routed experts and only 2.36 B working per token. This is conditional computation: capacity grows faster than cost.

The N-gram memory takes the idea to the extreme. Instead of a network that computes, it is a lookup table: 320,001,536 rows of 160 numbers. For each token, 16 addresses are computed from the neighboring tokens, 16 rows are copied and concatenated into a 2,560-dimensional vector, and that's it. Copying a row multiplies nothing by anything. The work the design builds on (DeepSeek's Engram, cited by the Qwen technical report) calls this conditional memory, "a new axis of sparsity".

\[ \text{FLOPs/token} \approx 2\,N_{\text{active}} \qquad\qquad \text{table bytes read/token} = H \cdot d_h \cdot b \;=\; 16 \times 160 \times 1\ \text{B} = 2{,}560\ \text{B (FP8)} \]
  • \(N_{\text{active}}\): parameters that take part in multiplications for that token
  • \(H\): hash heads (16 in Qwen: 8 bigram + 8 trigram)
  • \(d_h\): width of each row (160)
  • \(b\): bytes per stored value (1 in FP8, 0.5625 in NVFP4 with scales)

Put the numbers side by side (our arithmetic, from the checkpoint shapes). The table holds 51.2 B of the 180 B parameters stored in the checkpoint, about 28%. Even so, the module's only heavy multiplications are in two small projections, 2,560 → 10,240 and 2,560 → 2,560 (32.8 M parameters), about 65.5 MFLOP per token. The gate and the short conv we will see later also multiply, but they cost a negligible fraction of that. That is 0.5% of the ~12 GFLOP that the model's ~6 B active parameters cost per token. The figure compares the three ways of storing capacity.

Look at the bottom number of the third panel. With 320 M rows, each parameter read per token "carries" 20 million stored parameters. In the MoE that ratio is 51. That is why the table shows up in the recipe's memory accounting (47.7 GiB in FP8, about 24 GiB per GPU with TP=2) and almost vanishes from the speed accounting: in the recipe's bytes-per-decode-step model, the router, the shared expert and the PLE projections add up to 0.40 GiB together, 4% of the traffic.

The figure's second mode shows a property as important as the first. The address of a row depends only on the token ids, and not on any hidden state. It is known before the first layer even runs. The MoE router is the opposite: it only knows which experts it will need when the hidden state arrives at the layer. This deterministic addressing is what makes it possible to fetch the rows from the CPU, an SSD or a memory-mapped file while the GPU computes layer 0. It belongs to the same family of ideas as the hash routing in DeepSeek's layers 0–2, which picks experts through a table indexed by the token id.

Three names for the same piece

In Qwen's card and technical report the module is called N-gram Embedding. In the config and the code it is ple_*. The vLLM docstring expands the acronym as "position-learning enhancement", transformers as "Per-Layer Embedding", and the LMSYS blog as "Per-Layer Embeddings". The acronym matches Gemma 3n's per-layer embeddings, small per-layer embeddings that can stay off the accelerator, and it was probably inherited from there. The idea of "cheap, offloadable capacity" is the same, but Qwen's mechanism is different: gated N-gram hashing, Engram-style. When you read PLE in Qwen's code, think "N-gram table".

Is it worth it?

The Qwen technical report includes two ablations that answer the question. First, where to place the table. Without N-grams, the loss was 1.585 and the benchmark average was 45.44. With the table in the 2nd layer, the loss dropped to 1.541 and the average rose to 47.94, the best position. Placing it in several layers did not help. Then, the size. With tables of 20×, 50×, 100× and 200× (the report's relative scale), the loss was 1.553, 1.541, 1.534 and 1.526. It keeps falling, but with diminishing returns, and the benchmarks saturate sooner. The gain was consistent in Chinese (one possible explanation, ours: multi-token words are very common there).

Analogy: the phrasebook

An experienced translator does not work out "New York", "on the other hand" or def __init__(self from scratch every time. They recognize the expression and pull its meaning from memory. The first layers of a Transformer spend attention and FFN rebuilding exactly this kind of local meaning. The N-gram table is a little phrasebook indexed by the last two or three words, which hands over that meaning ready-made right at the start of the stack and leaves the following layers free for everything else. That is the authors' motivation; the analogy is our interpretation of it.

From phrase to address: bigram and trigram hashing

An N-gram is a sequence of N consecutive tokens. For the token at position \(t\), the bigram is \((x_{t-1}, x_t)\) and the trigram is \((x_{t-2}, x_{t-1}, x_t)\). Qwen uses both: ngram_size = 3 means "up to trigrams", and the orders used are 2 and 3.

Why not store one row per N-gram? Do the math. With the 248,320-token vocabulary there are \(248{,}320^2 \approx 6.2 \times 10^{10}\) possible bigrams and \(\approx 1.5 \times 10^{16}\) trigrams. No memory holds that. The way out is the same as for every data structure that has to fit: hashing. Each N-gram is squeezed into a 64-bit number, and that number picks a row in a fixed-size table. Rows will be shared by different N-grams (collisions), and the next section deals with that.

Qwen's hash is multiplicative with XOR. Each relative position \(i\) (0 = the token itself, 1 = the previous one, 2 = the one before that) has an odd multiplier \(m_i\). Each id is multiplied by its multiplier and everything is combined with bitwise exclusive-or:

\[ h_2(t) = (x_t\, m_0) \oplus (x_{t-1}\, m_1) \qquad h_3(t) = h_2(t) \oplus (x_{t-2}\, m_2) \] \[ \mathrm{idx}_{n,k}(t) = \mathrm{off}_{n,k} + \big(h_n(t) \bmod p_{n,k}\big) \qquad\quad \mathbf e_t = \big[\, E[\mathrm{idx}_{2,1}] \,;\, \dots \,;\, E[\mathrm{idx}_{2,8}] \,;\, E[\mathrm{idx}_{3,1}] \,;\, \dots \,;\, E[\mathrm{idx}_{3,8}] \,\big] \in \mathbb R^{2560} \]
  • \(x_t\): id of the token at position \(t\) (0 to 248,319)
  • \(m_i\): odd 64-bit multiplier for relative position \(i\)
  • \(\oplus\): bitwise exclusive-or (XOR)
  • \(n \in \{2, 3\}\): N-gram order; \(k = 1..8\): hash head
  • \(p_{n,k}\): the head's own prime (≈ 20 million)
  • \(\mathrm{off}_{n,k}\): where the head's slice starts in the single table
  • \(E\): the table, \(320{,}001{,}536 \times 160\)
  • \(\mathbf e_t\): the 16 rows of 160, concatenated

The 16 heads (heads_per_ngram = 8 per order × 2 orders) live in a single table, each in its own contiguous slice. Heads of the same order share the same \(h_n\) and differ only in the prime used as modulus. Hold on to this detail, because it is the key to the next section. In the figure below, the machine runs the real code, with the checkpoint's multipliers and primes, over illustrative token ids.

Three things to notice. (1) Changing a single neighboring token changes all 16 addresses, because the whole \(h_n\) changes. (2) The bigram and trigram of the same token land in unrelated places, because the term \(x_{t-2} m_2\) scrambles the bits of \(h_2\). (3) With the wrong seed, the same tokens point to completely different rows. The table was trained with one specific addressing, and any divergence (seed, constant, multiplier, prime) makes the model read garbage without any error at all.

Where the multipliers come from

The three multipliers are not written anywhere in the config. They are generated by a classic pseudorandom function, SplitMix64, from a seed:

\[ s_{\text{base}} = \texttt{seed} + 10007 \cdot \ell_{\text{PLE}} \qquad m_i = 2\cdot\big(\mathrm{SplitMix64}(s_{\text{base}} + \gamma\,(i+1)) \bmod B\big) + 1 \qquad B = \Big\lfloor \tfrac{\lfloor (2^{63}-1)/V \rfloor}{2} \Big\rfloor \]
  • \(\texttt{seed}\): 1234 (the code's default; the nvidia config repeats the value)
  • \(10007\): _PLE_LAYER_PRIME, keeps the seeds of different PLE layers apart
  • \(\ell_{\text{PLE}}\): index of the PLE layer among the PLE layers (0 in Qwen, which has only one)
  • \(\gamma\): _SPLITMIX_GAMMA = 0x9E3779B97F4A7C15 (\(2^{64}/\varphi\))
  • \(V\): vocabulary size (248,320)
  • \(B\): bound that keeps \(x \cdot m\) from overflowing an int64

With \(V = 248{,}320\), the multiplier stays below \(\lfloor(2^{63}-1)/V\rfloor = 37{,}143{,}089{,}710{,}272\) (at most \(2B-1 = 37{,}143{,}089{,}710{,}271\)). So any id times any multiplier fits in a signed 64-bit integer, which is the type PyTorch uses. The \(2\cdot(\cdot)+1\) forces the multiplier to be odd. An odd number is invertible modulo \(2^{64}\), so the multiplication discards no information from the low bits. We recomputed the function and got exactly the values in the checkpoint's buffer: \(m_0 = 23{,}703{,}573{,}157{,}769\), \(m_1 = 20{,}109{,}073{,}645{,}365\) and \(m_2 = 8{,}052{,}911{,}324{,}071\).

Going deeper: what SplitMix64 does

SplitMix64 adds the constant \(\gamma\), applies two rounds of "xorshift and multiply", \(v \leftarrow (v \oplus (v \gg 30))\cdot M_1\) and \(v \leftarrow (v \oplus (v \gg 27))\cdot M_2\), and finishes with an xorshift without multiplication, \(v \leftarrow v \oplus (v \gg 31)\), with \(M_1\) = 0xBF58476D1CE4E5B9 and \(M_2\) = 0x94D049BB133111EB (_SPLITMIX_M1/M2). Each xorshift folds the high bits onto the low ones, and each multiplication spreads the low ones upward (the avalanche effect), so neighboring seeds give multipliers with no apparent relationship. It is the generator behind Java's SplittableRandom: fast, deterministic and easy to reimplement byte for byte. That last property is the one that matters here.

Defense in depthlayer_multipliers [3] · ngram_heads_vocab_sizes [16] · ngram_heads_offsets [16]

The checkpoint does not rely on the seed alone. It stores the three multipliers, the 16 primes and the 16 offsets as persistent buffers (int64). The load_weights rewritten by the recipe's patch copies these buffers over the computed values and checks the shape of each one. If your code's seed diverges from the training one, the checkpoint buffer wins. When you write support for a similar model, do the same: load the hash from the checkpoint, compare it with what the code computes and fail loudly if they differ. The loader also deliberately ignores auxiliary tensors that a training checkpoint might carry (hashstats_*, token_lookup).

Collisions, primes and heads: the hash as a sketch

The table has 160 M rows for bigrams and 160 M for trigrams, far fewer than the \(6.2\times10^{10}\) possible bigrams. By the pigeonhole principle, each row is shared by many N-grams. The design works anyway, for two reasons. The first is Zipf's law: a few N-grams are very frequent, and they are the ones that shape each row during training. The second is multi-head hashing. A rare N-gram may share head 1's row with a famous N-gram, but it is unlikely to share all eight rows with the same neighbor. The 16 concatenated rows form a practically unique "signature". Structures such as the count-min sketch and the Bloom filter use the same trick.

\[ P\big[\text{collision in head } k\big] \approx \frac{1}{p_k} \qquad\qquad P\big[\text{collision in all 8}\big] \approx \prod_{k=1}^{8}\frac{1}{p_k} \approx \big(5\times10^{-8}\big)^{8} \]
  • \(p_k\): prime of head \(k\) (≈ \(2\times10^{7}\))
  • holds for two distinct N-grams and a hash that behaves like a random one

This calculation assumes the heads are independent. But they use the same \(h_n\) and differ only in the modulus. This is where the primes come in, for two reasons:

  1. Primes use all the bits. Taking \(h \bmod 2^{b}\) means looking only at the \(b\) lowest bits of \(h\). And, in multiplicative hashing, the low bits of \(x \cdot m\) depend only on the low bits of \(x\). Tokens whose ids share their low bits would collide en masse. Reducing modulo a prime mixes all 64 bits into the result.
  2. Distinct primes make the heads independent. With the same modulus in every head, the 8 would be clones: whatever collides in one collides in all. With different primes, the remainders of \(h\) modulo each prime are "independent" (Chinese Remainder Theorem), and each head spreads the same \(h\) in a different way.

The figure below uses a toy version (primes 17, 19, 23 and 29) with the real multipliers. Compare "distinct primes" with "16 in all heads" and turn on the structured ids, in which the token ids are multiples of 16, like families of tokens with the same low bits.

At real scale the protection is even stronger, and it can be proven. The product of any three primes in the table (≈ \(8\times10^{21}\)) is larger than any difference between two 64-bit hashes (\(< 2^{63} \approx 9.2\times10^{18}\)). If two N-grams with hashes \(h \neq h'\) collided in three heads, all three primes would divide \(h - h'\), which is impossible. Conclusion (our arithmetic): two N-grams of the same order with different hashes share at most 2 of their 8 rows. A total collision only happens if the 64-bit hash itself collides.

Why this matters to whoever serves the model

Every number in this construction has to be reproduced bit for bit at inference: the order of the positions, the multipliers, the primes, the offsets and the integer type (int64, with the same remainder semantics). An "optimized" kernel that computes the hash in 32 bits, or an implementation that swaps XOR for addition, loads without error and produces a subtly worse model. It is a textbook case for parity tests against the reference (Part IV).

Sizes, padding and shards

The size of each head comes from ngram_vocab_size_base = 20,000,000: global head \(g\) uses the \((g+1)\)-th prime after 19,999,999. The 16 primes run from 20,000,003 to 20,000,171 and add up to 320,001,446 rows. make_ngram_vocab_size_divisible_by = 128 rounds the total up to 320,001,536, a multiple of 128, which lets the table split evenly across the tensor parallel ranks (the table is a VocabParallelEmbedding, sliced by row ranges). In the checkpoint, the table is stored in split_ngram_parts = 128 shards of exactly 2,500,012 rows. With TP=2, each GPU gets 160,000,768 rows, that is, 64 whole shards (our arithmetic).

From row to residual: context gate and dilated convolution

The vector \(\mathbf e_t\) that comes out of the table is noisy by nature. It mixes in the collisions and knows nothing about context: the bigram "the bank" is the same in a sentence about rivers and in a sentence about interest rates. Adding it raw to the residual stream would force the memory on the model. Instead, the module asks the current state whether that memory fits the context, and only then writes.

Recall from the previous chapter that Qwen3.8 uses a Gated Residual with hc_count = 4 branches of 2560, that is, each token's residual is \(R_t \in \mathbb R^{4\times2560}\). The PLE talks to each branch separately:

\[ \mathbf k_t = W_K\,\mathbf e_t \in \mathbb R^{4\times2560} \qquad \mathbf v_t = W_V\,\mathbf e_t \in \mathbb R^{2560} \qquad \hat{\mathbf k}_{t,i} = \mathrm{RMSNorm}_i(\mathbf k_{t,i}) \qquad \hat{\mathbf q}_{t,i} = \mathrm{RMSNorm}_i(R_{t,i}) \] \[ z_{t,i} = \frac{\langle \hat{\mathbf k}_{t,i},\, \hat{\mathbf q}_{t,i}\rangle}{\sqrt{2560}} \qquad g_{t,i} = \sigma\!\big(\mathrm{sign}(z_{t,i})\,\sqrt{|z_{t,i}|}\big) \qquad \mathbf u_{t,i} = g_{t,i}\,\mathbf v_t \] \[ \Delta_t = \mathbf u_t + \mathrm{SiLU}\big(\mathrm{Conv1d}_{k=4,\;\mathrm{dil}=3}(\mathrm{RMSNorm}(\mathbf u))_t\big) \qquad\qquad R_t \leftarrow R_t + \Delta_t \]
  • \(W_K\): key_proj, 2560 → 10240 (one key per branch)
  • \(W_V\): value_proj, 2560 → 2560 (one shared value)
  • \(i = 1..4\): residual branch
  • \(\mathrm{RMSNorm}_i\): RMSNorm per group of 2560 with gain \(1+w\)
  • \(z\): scaled key–query similarity
  • \(g\): scalar gate per branch, in (0, 1)
  • \(\sigma\): sigmoid; SiLU: \(x\,\sigma(x)\)
  • \(\Delta_t\): what gets added to the 4 branches

The query is the residual itself, what the model has already understood by layer 1. The key is a projection of the memory. When the two agree, \(z\) is large and the gate opens. When they disagree, the gate closes and that branch receives almost nothing. There are 4 keys, one per branch, so that each branch decides on its own. There is a single value, to save parameters. Follow the complete path step by step in the figure.

Two numerical details deserve a note. The PLE's RMSNorm is grouped: it normalizes each block of 2560 (each branch) separately, with gain \(1+w\). Since \(w\) is initialized to zero, the gain starts at 1. The \(\varepsilon\) is the config's rms_norm_eps = 1e-6, and the three norms (key, query and conv) use the same class. The \(\mathrm{sign}(z)\sqrt{|z|}\), in turn, is a "signed square root": it compresses large similarities before the sigmoid, so the gate saturates more slowly than with \(\sigma(z)\). The code also clamps \(|z| \ge 10^{-6}\) so the root doesn't misbehave at zero. This is our reading of the formula; the report does not justify the choice.

The short dilated convolution

The last ingredient is a dilated causal convolution, depthwise: each of the 10,240 channels has its own 4 weights and looks only at its own past. With ple_conv_kernel_size = 4 and dilation 3 (the ngram_size itself), the output at \(t\) combines \(\mathbf u\) at positions \(t, t-3, t-6, t-9\). That gives a receptive field of \((4-1)\cdot 3 + 1 = 10\) positions. In the vLLM code this conv's weights are initialized to zero, and the checkpoint brings the trained values, with shape [10240, 1, 4].

With \(d = 3\), the 4 taps cover 4 neighboring trigrams, from \(t-11\) to \(t\): 12 raw tokens of lexical context without any overlap. With \(d = 2\) the windows would overlap, and with \(d = 4\) there would be gaps. That is our interpretation of why the dilation was tied to ngram_size. The code only sets dilation = ngram_size, without a comment.

Where the PLE livesple_layer_ids: [2] → layers.1.ple

The config says layer 2, but that count starts at 1. vLLM exposes the module as model.language_model.layers.1.ple.*, and the LMSYS blog confirms it: "configured layer ID 2, corresponding to zero-based index 1". This difference matters when you write quantization patterns, exclusion lists and tests that look up tensors by name. The transformers implementation also requires the PLE layer to be of type linear_attention (GDN). \(\Delta_t\) is added to the 4 branches before that layer's Gated Residual read, so layer 1's GDN already receives the memory. The position has two advantages. It is early enough for the following layers to benefit from the memory, and late enough for (a) the residual to already carry some context for the gate to compare against (our interpretation, no source) and (b) there to be time to fetch the rows during layer 0, which is the technical report's argument.

The state the PLE carries: EOS, chunks and drafts

An ordinary embedding keeps no state: token \(t\) is enough. The PLE needs two memories of the past of each request. The first is the 2 previous ids, to build bigrams and trigrams: the N-gram context. The second is the conv's 9 previous inputs, \((4-1)\times3\): the convolution state. That is why the PLE behaves like a linear attention layer, and why the nvidia config declares number_of_conv_states = 3: [0] the GDN conv, [1] the PLE conv and [2] the N-gram context.

Three situations exercise this state. See each one in the figure; the text then goes into the details.

EOS segmentation

N-grams do not cross document boundaries. For each position, the code computes how many tokens have gone by since the last <|endoftext|> (id 248044). A neighbor at distance \(s\) only counts if it is inside the same segment. Otherwise, it is replaced by the EOS id itself, which also fills the positions that have no past. In practice, the first token after an EOS sees the trigram (EOS, EOS, \(x\)) instead of mixing in the end of the previous document. Without this, two documents concatenated in a training batch would "leak" into each other. The segmentation has to be reproduced exactly at inference.

Chunked prefill

With --max-num-batched-tokens 8192 in the Qwen recipe, a 30,000-token prompt is processed in 4 chunks (chunked prefill). The first token of the second chunk needs the last two ids of the first one, which are not in the current batch. forward_impl solves this by concatenating the saved ngram_context (2 ids per request) in front of the new tokens. The conv does the same with its 9-column state. The PLE's working buffers are sized from the scheduler settings: positions_buffer has max_num_batched_tokens positions and padded_buffer has max_num_seqs × max_num_batched_tokens int64 ids, that is, 8 × 8192 × 8 B = 512 KiB in the recipe (our arithmetic). A batch larger than that is rejected with an explicit error.

Speculative decode and rollback

First, a sneak preview. In speculative decoding, a cheap drafter proposes \(k\) tokens and the large model (the target) verifies all of them in a single forward, accepting the longest prefix it would have generated itself. The rest is discarded. Where the drafter comes from is covered in the MTP section and in In the recipes, further down, and the full theory is in Part VII. For the PLE, all you need to know is this: it processes tokens that may later be thrown away.

In the Qwen recipe the drafter is MTP with 3 drafts (MTP=3). The target verifies 4 tokens per request at each step (the last accepted one + 3 drafts). The PLE runs over all 4, but only some of them will be accepted. The conv state keeps \(9 + \texttt{num\_speculative\_tokens} = 12\) columns. After verification, the window "rolls back" to the last accepted token, shifting by num_accepted_tokens − 1. It is the same rollback that the convs in the GDN layers perform. The code has three paths for the conv: decode, batched prefill and speculative. The padding rows of the CUDA graphs use NULL_BLOCK_ID and are masked, so they don't corrupt anyone's state.

Integration with vLLMMambaBase · SHORT_CONV · qwen3_8_flash_next_ple_short_conv

To vLLM's KV manager, the PLE is a "Mamba-like" layer. It inherits from MambaBase with the SHORT_CONV backend and declares a constant-size state per request. The hybrid allocator reserves this state next to the GDN states, and it costs ~240 KiB per request: 10,240 channels × 12 columns × 2 B (our arithmetic). The state is replicated on both GPUs (is_kv_cache_tp_replicated = True), because the PLE projections are ReplicatedLinear: only the table is sliced by row ranges, while the projections, gate and conv run in full on each GPU. The conv is registered as an opaque custom op, torch.ops.vllm.qwen3_8_flash_next_ple_short_conv, with a fake impl. That way torch.compile and CUDA graph capture (cudagraph_mode: FULL_DECODE_ONLY in the recipe) treat the conv as a black box, and it can consult the step metadata in Python (CUDA graphs chapter).

Serving a 51 GB table: formats, the patch and offload

The table is Qwen3.8's largest tensor, and the format it is stored in decides whether it fits. In BF16 it is 102.4 GB (95.4 GiB), more than a 128 GB GPU can hold next to everything else. The way out is to quantize the table. This chapter comes before the quantization part, so here is just the bare minimum to follow along.

The quantization minimum for this chapter

To quantize is to store each number with few bits. Instead of the value, you store a small code and a scale, and the value is reconstructed as \(\text{value} \approx \text{code} \times \text{scale}\). That reconstruction is dequantization. Here the codes are tiny floating-point numbers. E4M3 uses 8 bits: 1 sign bit, 4 exponent bits and 3 mantissa bits, with a maximum of 448. E2M1 uses 4 bits: 1 sign bit, 2 exponent bits and 1 mantissa bit, and it can only represent 0, 0.5, 1, 1.5, 2, 3, 4 and 6, with a sign. The scale can apply to the whole tensor (per tensor: a single scale, dirt cheap, but a single extreme value "flattens" all the others) or to each block of 16 values (per block: more bytes of scales and much less error). NVFP4 combines both ideas, with one E4M3 scale per block of 16 and a global FP32 scale on top. Finally, ModelOpt is NVIDIA's quantization tool, and the nvidia checkpoint used in the recipe comes out of it. It writes into config.json a quantization_config that says, layer by layer (quantized_layers, config_groups), which format each tensor is in. The figure further down shows the code × scale arithmetic on one row of the table. The rest (why 448, microscaling, measuring the error) is left for Quantization fundamentals and FP8, FP4 and microscaling.

The recipe's checkpoints use two formats for the table:

  • Per-tensor FP8 E4M3 (nvidia/…-NVFP4, RadixArk/…-NVFP4 and the official FP8): 1 byte per value and a single BF16 scale (weight_scale) for the whole table. That is 47.7 GiB in total, about 23.8 GiB per GPU with TP=2. According to the nvidia card, the PLE and the MTP are byte-for-byte identical to those of Qwen/Qwen3.8-Flash-Next-FP8.
  • Packed NVFP4 (local-inference-lab/…-NVFP4): each row of 160 values becomes 80 bytes of E2M1 codes (two per byte), plus 10 bytes of FP8 E4M3 scales (one per block of 16), plus one global FP32 scale for the table. That is 90 B per row, 4.5 bits per parameter and 26.8 GiB in total. The format details are in FP8, FP4 and microscaling.

In any format, only the 16 rows fetched per token are dequantized, and the table stays compact in memory. In the figure, choose the format and hover over a value in the row.

Why vLLM needed a patch

For each layer, vLLM has a quantization method that decides how to create the tensors and how to read the bytes. The nvidia checkpoint is ModelOpt MIXED_PRECISION. In it, the experts are NVFP4, the MTP experts are block FP8, the PLE is per-tensor FP8 and the rest is BF16. The recipe's day-0 image only chose the FP8 method for the PLE when the entire checkpoint was an Fp8Config. Since this one isn't, the PLE was left without a method, vLLM created a ≈102 GB BF16 embedding and loading died. To make matters worse, nvidia declares the PLE's format only inside quantization_config.config_groups (a group with num_bits: 8 whose target is …ple.ple_embedding.ngram_embedding), and not in the text_config.ple_embedding_dtype field that the new code checks. The recipe solves it with a three-link chain:

  1. Detect. files/detect_ple_dtype.py reads the snapshot's config.json. If ple_embedding_dtype is already declared, it prints nothing. If not, it looks for the group whose target is the table and maps num_bits 8 → float8_e4m3fn and 4 → nvfp4. The PLE_EMBEDDING_DTYPE variable in .env (empty by default) skips detection in favor of a manual override.
  2. Inject. start.sh builds a single --hf-overrides nested under text_config: '{"text_config":{"ple_embedding_dtype":"float8_e4m3fn"}}', which also carries rope_parameters when YaRN is enabled. The nesting is mandatory. A top-level override is written to the parent config and never reaches text_config, and that is exactly how YaRN was once a silent no-op in this recipe.
  3. Dispatch. ple_layer_patched.py (generated by files/patch_ple_layer.py from the image's file, porting the logic of vLLM PR #53899 and mounted :ro through a bind-mount) rewrites _get_ple_embedding_quant_method. The decision order is: (a) ple_embedding_dtype ∈ {nvfp4, fp4, w4a16_nvfp4} → new NVFP4 method; (b) ∈ {float8_e4m3fn, fp8} → FP8 method; (c) serialized Fp8Config → FP8; (d) ModelOptNvFp4Config with the PLE not excluded → NVFP4; (e) otherwise, nothing (BF16).

The patch does more than dispatch. It creates Qwen3_8FlashNextPLENVFp4EmbeddingMethod, which keeps the table packed and whose lookup returns cat(codes, scales) = 90 B per head. It rewrites load_weights, which joins codes and scales shard by shard, trims each shard to the TP rank's row range and checks the shapes. It implements _dequantize_embeddings: two-level scaling in NVFP4, and emb.to(bf16) * weight_scale in FP8. And it fixes three bugs in the offload path, which we will see next. SKIP_PLE_PATCH=true skips all of that. That is what start-fp8.sh does with the official FP8 checkpoint, and the vLLM 0.30 lane also loads the PLE natively and clears PLE_EMBEDDING_DTYPE.

Outdated documentation: PLE_QUANT_OVERRIDE

The README and a report in the recipe describe an old shim in which start.sh exported PLE_QUANT_OVERRIDE=fp8 and ple_layer.py read it. A grep over the current code finds this variable nowhere outside the documentation. The mechanism in force is detect_ple_dtype.py → --hf-overrides text_config.ple_embedding_dtype → dispatch. When recreating the recipe, trust the code, not the README. This is a general rule for living recipes.

Deterministic addressing in practice: offload and mmap

Since the addresses depend only on the ids, the table doesn't need to be on the GPU. With PLE_OFFLOAD=true, the recipe exports VLLM_PLE_CPU_OFFLOAD=1. A separate process builds the model on the meta device (no memory), materializes only the PLE on the CPU, receives input_ids and ngram_context, performs the lookup and delivers the packed rows into a buffer shared with the GPU. The original design synchronizes CPU and GPU with stream memory operations (cuStreamWaitValue32). The GB10 reports CAN_USE_STREAM_MEM_OPS = 0 and, inside a CUDA graph, the wait doesn't wait. patch_ple_offload.py replaces this with a host-side handshake using a sequence number in a shared-memory flag. build_ple_packed_table.py writes the NVFP4 table to a single [rows, 90] file of 26.8 GiB, which the offload process maps with mmap (VLLM_PLE_PACKED_TABLE_DIR): file pages, evictable by the OS.

There are two outcomes, and they show that "offload" depends on the hardware. On a GPU with its own VRAM, offload frees VRAM. On the GB10's unified memory, "CPU RAM" is the same LPDDR5X, so moving the table saves no physical memory. What changes is the load-time pressure and, with mmap, the table becomes evictable page cache. In the TP1 profile (a single Spark), non-evictable memory dropped from ~104 to ~77 GiB, and start-tp1.sh subtracts PLE_GIB=26.82 from the GPU budget. In the two-Spark kit, offload stays off: it would need ~51 GB of free RAM, and the log showed ~45 GiB available.

"Fluent gibberish, no error"

In NVFP4 offload, the GPU placeholder didn't know the table was NVFP4 (the _offload_quant_method attribute was read but never written). The dequantization branch became dead code, and the packed rows were read as if they were values. The model did not crash: it started generating fluent, meaningless text. The other two bugs fixed were the get_offload_output_dtype function, deleted by mistake (the IPC buffer must be uint8 or float8_e4m3fn), and an index_select(out=…) that silently resized the buffer. Moral: packed formats fail quietly. Every new loading path needs a numerical test against the reference, and not just "it came up and answered".

Multi-Token Prediction: training to see two tokens ahead

Now for the second box. An ordinary LLM is trained on a single task: given the prefix \(x_{\le t}\), predict \(x_{t+1}\). Multi-Token Prediction adds, during training, modules that predict tokens further out. There are two schools. The first puts several output heads in parallel on top of the same trunk, each one predicting \(t+1, t+2, \dots\). The second, DeepSeek-V3's, adopted by GLM, by Qwen and by the DeepSeek-V4 preview's MTP-1, uses sequential modules, which preserve the causal chain. Module \(k\) receives the representation from the previous level and the embedding of the following token, which is known during training, and predicts one step further:

\[ \mathbf h'^{(k)}_t = W^{(k)}_{\text{proj}} \big[\, \mathrm{RMSNorm}\big(\mathrm{Emb}(x_{t+k})\big) \,;\, \mathrm{RMSNorm}\big(\mathbf h^{(k-1)}_t\big) \,\big] \qquad \mathbf h^{(k)} = \mathrm{Block}_k\big(\mathbf h'^{(k)}\big) \qquad P^{(k)}_{t+k+1} = \mathrm{softmax}\big(W_{\text{out}}\,\mathrm{Norm}(\mathbf h^{(k)}_t)\big) \] \[ \mathcal L = \mathcal L_{\text{main}} + \frac{\lambda}{D} \sum_{k=1}^{D} \mathcal L^{(k)}_{\text{MTP}} \qquad\quad \mathcal L^{(k)}_{\text{MTP}} = -\frac{1}{T}\sum_t \log P^{(k)}_{t+k+1}\big(x_{t+k+1}\big) \]
  • \(\mathbf h^{(0)}_t\): state that comes out of the trunk at position \(t\)
  • \(\mathrm{Emb}\): the main model's embedding (shared)
  • \(W_{\text{proj}}\): \(d \times 2d\) projection (eh_proj in GLM)
  • \(\mathrm{Block}_k\): a complete Transformer block (attention + FFN/MoE)
  • \(W_{\text{out}}\): the main model's lm_head (shared)
  • \(D\): number of modules (num_nextn_predict_layers)
  • \(\lambda\): small weight of the auxiliary loss

What is it for? In training, each position now produces more than one error signal, and the authors argue that the trunk learns representations that "plan" a little ahead. At inference, the model can simply drop the modules, or use them as a drafter for speculative decoding. In that role the module is nearly ideal. It reads the target's own hidden state, uses the same embedding and the same output head, and costs a single layer. In the figure, build the module step by step and compare the three models.

Notice what each module reads from the trunk. GLM reads a 4096-dimensional vector, already contracted from the mHC's 4 streams. Qwen reads the full 4 branches (10,240) and normalizes them together. DeepSeek's classic MTP reads the 4 streams (16,384). For anyone writing support for a model, this is the first question to ask about an MTP: which state does it consume? The answer defines the buffer the engine has to keep between the target's forward and the draft's. In DeepSeek that buffer is 256 MiB, and the recipe frees it with hotfix #50312 because DSpark doesn't use it.

Names and metadatanum_hidden_layers: 48 → mtp.layers.48

In the checkpoint the layer is called mtp.layers.0.*. vLLM builds it at the absolute index that continues the stack, num_hidden_layers + i = 48, and ModelOpt matches quantized_layers prefixes by exact string. Without a fix, the MTP's MoE was built without quantization and loading died ~7 min later with Layer mtp.layers.48.mlp.experts has no parameter 'w2_weight_scale_inv'. files/patch_checkpoint_config.py adds .0. → .48. aliases in quantized_layers and config_groups.targets, and normalizes the FP8_PB_WO label (group_size 128) to FP8_BLOCK_SCALES. It does this both in config.json and in the legacy hf_quant_config.json, both mounted over the snapshot. patch_modelopt_fp8_block_moe.py adds the missing branch for block FP8 in the MoE, with the block size read from the checkpoint, because a wrong block size would apply misaligned scales without any error. And expert parallel is mandatory: under pure TP, the experts' intermediate size of 640 would become 320 per GPU, which is not a multiple of 128. With EP, each GPU holds whole experts and the 128×128 blocks stay aligned.

In the recipes: from the config to --speculative-config

At inference, the MTP becomes a drafter like this. The target generates \(x_{t+1}\) and hands over \(\mathbf h_t\). The module proposes \(\tilde x_{t+2}\), feeds itself its own output and the embedding of \(\tilde x_{t+2}\), proposes \(\tilde x_{t+3}\), and so on, up to \(k\) drafts. The target then verifies the \(k+1\) tokens in a single forward and accepts the longest correct prefix. The theory of verification (rejection sampling, bonus token, choosing \(k\)) is left for Part VII. What matters here is what the architecture imposes on \(k\).

vLLM calls the number of distinct MTP modules in the checkpoint n_predict (num_nextn_predict_layers). If \(k \le\) n_predict, each position uses its own module. If \(k >\) n_predict, the modules are reapplied in a cycle, and vLLM requires \(k\) to be a multiple of n_predict ("Ensure divisibility for MTP module reuse"). With n_predict = 1 (GLM and Qwen), any \(k\) works. The same layer runs \(k\) times, and vLLM warns that this "may result in lower acceptance rate". The reason is a mismatch between training and inference. In step 1 the module reads the trunk's \(\mathbf h_t\), just as in training. In the following steps it reads its own output state, a signal with a different distribution, and each wrong draft contaminates the next ones. (The rate at position \(i\) already includes the requirement that the previous ones were accepted.) That is why acceptance drops by position, from 89% to 74.5% and 60% in Qwen, and that is why Qwen trains its layer "with multi-steps": it learns, already during training, to consume its own output. With n_predict = 3, only 1, 2, 3, 6, 9 and so on are valid. That is the reuse rule, and it explains one of the strangest numbers in the recipes.

Read the DeepSeek case alongside the figure. DSpark was trained with a block of 5, and the launcher requires \(k \ge 5\). But the default lane (Anemll 0.1.1 image) validates the method as if it were MTP, with n_predict = num_nextn_predict_layers = 3 in Vision-Exp. The smallest \(k\) that satisfies both rules is 6. (9, 12… also pass, but they drift even further from the trained block of 5, and each extra position yields less.) Note that the rule is only a config validation: nothing runs in a cycle. DSpark keeps drafting the whole block in a single forward, with the anchor plus \(k-1\) noise positions. With \(k = 6\), one of these positions falls beyond the trained block, and acceptance there is low (0.15 in bench_quick). In 0731 (n_predict = 1), \(k = 5\) passed validation and booted. The rule exists for classic MTP, which re-runs modules, and makes no sense for DSpark, whose stages are stacked and solve the whole block at once. The opt-in hotfix DSPARK_ENABLE_DSPARK_BLOCK_K=1 exempts method=dspark from the rule and allows MTP_NUM_TOKENS=5. With it, the measured per-position acceptance is the same (0.88 / 0.74 / 0.53 / 0.36 / 0.24), the step gets cheaper and the gain is +2–10% in single-stream.

Checklist for your recipe

When a new model brings an N-gram memory or MTP: (1) read the ple_*/ngram_* and num_nextn_predict_layers/mtp_* fields in the config; (2) compute the table size in each format and per GPU; (3) find out where the checkpoint declares the table's format and whether the engine's loader reads that place; (4) check that the hash (seed, primes, offsets, EOS segmentation) is reproduced bit for bit and that the state survives chunked prefill and speculative rollback; (5) for MTP, ask which state it consumes, how the engine numbers the layer (and whether the quantization metadata follows that numbering), which \(k\) the reuse rule allows, and how much memory and KV it costs when enabled.
