Nenhuma das três receitas roda o vLLM “de fábrica”. O GLM reaplica 25 overlays a cada boot sobre um fork (487ecf187); desde 2026-09-30 são 26, com o patch_indexer_warmup_range.py (#203). O DeepSeek executa uma cadeia de ~21 etapas de hotfixes antes do exec vllm serve. O Qwen monta cerca de dez arquivos patcheados por cima de uma imagem que nunca é reconstruída. E tudo isso duas vezes, uma por nó, porque basta um rank rodar bytes diferentes do outro para o NCCL poder travar sem mensagem de erro. Este capítulo trata da engenharia que torna isso sustentável: imagens identificadas pelo conteúdo, patches que preferem recusar a errar, ordem e paridade entre ranks, um .env que não te trai, launchers que checam antes de agir e canários que desconfiam do /health. As próximas receitas usam esse ofício em cada linha. A nova versão da receita GLM, que troca o vLLM pelo TensorFold, pratica o mesmo ofício com outras respostas: diffs assados na imagem, imagem nomeada pelo hash dos patches e um motor que confere sozinho se os dois ranks receberam as mesmas configurações.

Uma receita é software que remenda software

Você não é dono do motor. A imagem do vLLM foi construída por outra pessoa, o suporte ao modelo chegou no “dia zero”, os kernels foram escritos para GPUs de datacenter e não para o GB10 (sm_121), e bugs aparecem sob carga real, com número de issue: #22, #27, #141, #249… Sobram três caminhos. Você pode esperar o upstream (semanas). Pode manter um fork (e herdar a manutenção). Ou pode remendar o motor com disciplina de engenharia. As três receitas escolheram o terceiro, e a disciplina se resume a quatro princípios:

📌

Fixar pelo conteúdo

O ideal é imagem por digest, vLLM e ExLlamaV3 por commit, pesos por revisão. Nomes móveis (tags, main) mudam sem avisar, e onde a receita ainda usa uma tag, outra trava precisa cobrir o buraco.

⛔

Falhar fechado

Se a fonte não é a esperada, o patch recusa e o boot aborta (fail-closed). Um serviço que não sobe é melhor que um serviço que sobe errado.

🧪

Provar antes

Testes em CPU contra cópias dos arquivos originais, CI, verificação no build, canário depois do boot. GPU é cara e rara, CPU é barata.

⚖️

Mesmos bytes nos dois ranks

Mesma imagem, mesmos patches na mesma ordem, mesmos argumentos. Tensor parallel é um programa só rodando em duas máquinas.

Analogia: a rede de restaurantes

Imagine duas filiais que servem o mesmo prato, cozinhando metade cada uma. A receita exige a marca e o lote exatos de cada ingrediente (digest), e não “o fornecedor de sempre” (tag). Um fiscal devolve qualquer caixa com lote diferente, em vez de improvisar (fail-closed). As duas cozinhas seguem os passos na mesma ordem (paridade). E alguém prova o prato antes de abrir a porta (canário), porque “o fogão está ligado” (/health 200) não quer dizer que a comida está boa.

A figura percorre o caminho do git clone até o primeiro token. Em cada estação, olhe três coisas: o que está fixado (cadeado), o que é verificado (lupa) e o que acontece se a verificação falhar (placa de pare).

Imagens: camadas, tags, digests e a mesma imagem nos dois nós

Camadas e endereçamento por conteúdo

Uma imagem Docker (OCI) não é um arquivo único. É uma pilha ordenada de camadas, em que cada uma é um tar com as diferenças de sistema de arquivos que uma instrução do Dockerfile produziu. Por cima vem uma config (variáveis de ambiente, entrypoint, labels e a lista rootfs.diff_ids) e um manifesto que lista os blobs das camadas e da config. Cada peça é identificada pelo SHA-256 dos próprios bytes: é o endereçamento por conteúdo. Na hora de rodar, o driver overlay2 empilha as camadas somente-leitura e põe uma camada gravável por cima. É dela que falaremos adiante, em “Onde mora uma mudança”.

\[ \text{DiffID}_i = H(\text{tar}_i), \qquad \text{ChainID}_1 = \text{DiffID}_1, \qquad \text{ChainID}_i = H\big(\text{ChainID}_{i-1} \,\|\, \text{“ ”} \,\|\, \text{DiffID}_i\big) \]
  • \(H\): SHA-256; \(\|\) é concatenação de texto
  • \(\text{tar}_i\): conteúdo descomprimido da camada \(i\) (a lista RootFS.Layers é justamente \(\text{DiffID}_1,\dots,\text{DiffID}_n\))
  • \(\text{ChainID}_i\): identidade da pilha até a camada \(i\). Mudar um byte na camada \(k\) muda todos os ChainIDs de \(k\) para cima, e com eles a config e o manifesto

A consequência prática é poderosa: o digest do manifesto é uma impressão digital da imagem inteira. Se dois nós rodam a mesma imagem por digest, eles têm os mesmos bytes, garantido pela matemática e não pela boa vontade de ninguém.

Tag é apelido, digest é identidade

Uma tag (:0.1.1, :latest) é um ponteiro mutável no registry, como um branch do git. Qualquer um com permissão pode republicá-la apontando para outra imagem. O digest (@sha256:…) é como um hash de commit: imutável. Nas três receitas, só duas imagens são fixadas por digest. Uma é a base do GLM (ARG BASE=vllm/vllm-openai:glm53-flash-arm64-cu130@sha256:905c0293…, Dockerfile:88). A outra é a imagem da lane A do DeepSeek, que o .env.dspark.example fixa como ghcr.io/anemll/dspark-vllm-gx10:0.1.1@sha256:a83948492cf1…. Os hotfixes do DeepSeek são source-exact contra essa build, então outra imagem com o mesmo nome faria todos recusarem.

As outras imagens usam tags e dependem de outra trava. A imagem de serving do GLM é a tag :exl3-instanttensor, protegida pelo recipe stamp (adiante): um pull só é adotado se o label bater com o repositório. O Qwen usa as tags vllm/vllm-openai:qwen38-flash-next e …:v0.30.0 (lane 0.30). O README registra o digest da primeira (sha256:d464f3b4…, ~20,6 GB), mas o .env.sample não o fixa. Se essa tag fosse republicada, as âncoras exatas dos patches pegariam a mudança, ou, pior, ela passaria despercebida, porque o .orig extraído da imagem fica em cache (start.sh:568-575; veja o aviso na seção sobre onde mora uma mudança). A lane B do DeepSeek também parte de uma tag (unholy-fusion-prod-ready).

Multi-arch e a viagem até o worker

Um nome de imagem pode apontar para um índice multi-arch: um manifesto de manifestos, um por plataforma. O GB10 é linux/arm64 (CPU Grace). Quando o worker não consegue fazer pull (sem internet ou com rate limit do GHCR), as receitas transportam a imagem por SSH: docker save --platform linux/arm64 | ssh worker docker load. O --platform importa: sem ele, o load de um índice multi-arch quebra (o launcher do GLM descobre a plataforma por inspect e cai em linux/arm64).

Aí surge uma pergunta que parece trivial: o worker tem a mesma imagem que o head? Nenhum campo óbvio responde. O .Id difere entre os stores overlay2 e containerd (um usa o digest da config, o outro o do índice). E o docker save | load perde os RepoDigests, então uma imagem transportada nunca “bate” com a tag de origem, e o launcher antigo reenviava a imagem inteira a cada start. O GLM resolveu com uma image key, um hash curto de RootFS.Layers (os DiffIDs). Esses DiffIDs são idênticos dos dois lados em todos os caminhos, porque descrevem o conteúdo descomprimido e não o registry.

A mesma pergunta, com mais campos

A versão TensorFold da receita GLM tropeçou no mesmo buraco (issue #8): o prepare.sh comparava o .Id das imagens e falhava em todo run quando um Spark usava o store containerd e o outro o overlay2. A correção compara por conteúdo, como a image key, mas o SHA-256 cobre RootFS.Layers e a configuração de execução da imagem (Env, Entrypoint, Cmd, WorkingDir). Interpretação: duas imagens com as mesmas camadas e outro ENV (os caminhos de cache de JIT moram ali) rodariam diferente, e essa identidade também as separa.

Cache de build: a ordem das camadas é uma decisão de engenharia

O cache de build reaproveita uma camada enquanto a instrução, os arquivos copiados e todas as camadas abaixo forem iguais. Mude algo na camada \(k\) e tudo de \(k\) para cima é refeito. Por isso o Dockerfile do GLM compila a extensão CUDA do ExLlamaV3 antes de copiar o overlay/exl3.py. O comentário do arquivo diz que o overlay Python vem depois da compilação “para que edições não recompilem o exllamav3_ext”. E o LABEL glm53.recipe.stamp fica na última linha, para que um rebuild só de carimbo saia barato. LABEL nem cria camada de arquivos: é metadado da config.

Na figura, escolha o que mudou no repositório e a ordem do Dockerfile. Repare em quantas camadas são refeitas e em quais identidades mudam. Depois republique a tag e veja quem é enganado.

Na ordem “ingênua”, editar uma linha do exl3.py recompila a extensão CUDA inteira; na da receita, só as camadas leves de cima. E a tag republicada só engana quem a usa pelo nome sem outra checagem. No GLM, o carimbo do pull deixa de bater e a imagem nova não é adotada. Um pin por digest nem chega a ver os bytes novos.

O carimbo da receita

O launcher do GLM calcula um recipe stamp: o SHA-256 da lista ordenada de hashes de tudo que o Dockerfile copia (Dockerfile, overlay/, files/, tests/, ablit/, excluindo o transplante e o servidor NFS). Depois compara com o label da imagem local. Um git pull que muda um overlay produz carimbo divergente e rebuild automático (SKIP_BUILD=1 impede). Uma imagem puxada do GHCR só é adotada se o carimbo publicado também bater. Caso contrário, o launcher restaura a tag local, para não servir uma imagem sem os artefatos que o repositório espera.

Build: compilar para a máquina certa e testar antes de sair da fábrica

Extensões nativas: duas arquiteturas ao mesmo tempo

Parte do código que as receitas rodam não é Python: é uma extensão nativa, uma biblioteca .so em C++/CUDA que o Python importa. O exllamav3_ext do GLM executa o MoE quantizado em EXL3 (ver treliças e EXL3). Compilar uma extensão dessas é mirar duas arquiteturas de uma vez: a da CPU do host (aarch64 no GB10) para a parte C++, e a da GPU para os kernels. Errar qualquer uma quebra o build ou, pior, o primeiro request.

O stub honesto: patch_exl3_ext_aarch64.py

O ExLlamaV3 traz alvos de CPU com intrínsecos AVX2/AVX-512, instruções vetoriais que só existem em x86. Num Grace (ARM), o compilador recusa esses arquivos. A receita não tenta portá-los. Ela os substitui por stubs: is_avx2_supported() e is_avx512_supported() devolvem false, enable_fast_fp*() vira no-op e o all-reduce de CPU (perform_cpu_reduce*) chama std::abort(). O stub é honesto: diz “não suportado” onde a biblioteca pergunta e, nos caminhos de all-reduce, explode em alto e bom som se alguém chegar a um trecho que a receita nunca usa (o all-reduce aqui é do NCCL, na GPU). Nem todo stub aborta, porém. O bf16_add_inplace_avx512 vira um no-op silencioso, e isso só é seguro porque is_avx512_supported() devolve false e impede que alguém chegue até ele. Um stub silencioso depende desse portão. O Dockerfile avisa que esse patch “precisa ficar nesta camada”, a mesma do RUN que compila.

Compilando para sm_121a

Kernels CUDA viram cubins, binários para uma compute capability específica. O GB10 é 12.1. Com TORCH_CUDA_ARCH_LIST=12.1a, o nvcc gera cubins nativos sm_121a no build da extensão. FLASHINFER_CUDA_ARCH_LIST=12.1a e, no DeepSeek, CUTE_DSL_ARCH=sm_121a fazem o mesmo papel para outro momento: os kernels que o FlashInfer e o CuTeDSL compilam por JIT em runtime, já com o motor rodando. Sem eles, o JIT pode escolher um caminho mais lento. O compose do DeepSeek registra que, sem CUTE_DSL_ARCH, o b12x/CuTeDSL podia compilar no meio da inferência um MoE W4A16 mais lento, em vez dos kernels nativos do GB10. O sufixo a habilita instruções específicas daquela arquitetura, que não são portáveis: um cubin sm_121a só roda em 12.1. Cubins sm_120 sem o a rodam no 12.1 por compatibilidade binária dentro da família (o Qwen executa assim alguns kernels da imagem). Cubins sm_100, de datacenter, não rodam num 12.x. O capítulo GPU por dentro explica capabilities e PTX em detalhe. Aqui basta a regra: compile para a máquina que vai executar.

Buildexllamav3_ext · EXLLAMAV3_COMMIT=c5d9c657… · TORCH_CUDA_ARCH_LIST=12.1a

Numa única camada (Dockerfile:421-437), o build baixa o tarball do commit c5d9c657 (ExLlamaV3 0.0.43), aplica os stubs aarch64, acrescenta os fat kernels E2/E3 (kernels de MoE para os experts “fat”, que recebem muitas linhas por passo; ver kernels) e o pipeline FAST (kernels aditivos: os originais ficam intactos, e a receita pode cair de volta neles), aponta CPATH para os headers CUDA que a imagem guarda em nvidia/cu13/include e compila com MAX_JOBS=8. O Dockerfile.e3-layer, que compila uma única unidade de tradução, usa MAX_JOBS=2 para “manter a compilação leve num host UMA” (de memória unificada). Por fim, confere os símbolos: exl3_moe, exl3_fat_gemm, exl3_fat_gemm_scatter, exl3_fat_moe_{gateup,down,gather} e glm53_fast_moe_version() == 1. Um m.def esquecido no bindings.cpp derruba o build aqui, e não no primeiro request. No launch, SKIP_OVERLAY_VERIFY=0 ainda roda test_exl3_overlay.py com EXL3_SELFCHECK_GPU=1, um auto-teste real dos cubins na GPU.

Dependências que atropelam dependências

Um pip install inocente pode trocar uma biblioteca crítica por baixo de você. O GLM instala instanttensor==0.2.0 com --no-deps porque a instalação normal puxa nvidia-nccl-cu13==2.29.7 por cima do NCCL 2.30.7 da imagem. É o mesmo cuidado de USE_HOST_NCCL (padrão 0): com 1, a receita faz LD_PRELOAD de um NCCL do host. Dois NCCLs diferentes nos dois ranks é pedir para as coletivas divergirem (NCCL e RDMA).

Saber onde mora a mudança também explica as lanes do DeepSeek. Na lane A (Anemll, padrão), os hotfixes editam o vLLM instalado dentro do container, no boot. Na lane B (Stage-C), arquivos inteiros vêm na imagem. Na lane C (official-main), o main oficial recebe um patch Python com teste de sanidade. As variáveis VLLM_DSPARK_* e VLLM_DSV4_* só estão registradas no envs.py da lane B. Na lane A, elas geram o aviso Unknown vLLM environment variable e não fazem nada. O mesmo knob muda de significado conforme a lane.

Reiniciar não é recriar

Um container é uma imagem somente-leitura com uma camada gravável por cima, mais uma configuração fixada na criação: variáveis de ambiente, mounts e comando. docker restart (ou docker compose restart) reinicia o mesmo container, com a mesma camada gravável e o mesmo ambiente da criação. Um hotfix aplicado no boot anterior continua lá, byte por byte, e um gate alterado no .env nem chega ao container. Só recriar (./stop + ./start: remover e criar de novo) começa de uma camada gravável limpa, com os bytes stock da imagem e o ambiente novo. Por isso o CHANGELOG do DeepSeek repete, correção após correção: “Recreate both containers after pull (./stop then ./start); restart keeps the old overlay bytes.”

Com “hotfix no boot”: suba, desligue o gate e dê docker restart. O arquivo continua patcheado. Recrie e ele volta ao stock. Troque a imagem base e o patcher aborta diante do SHA-256 desconhecido, como deveria.

O outro lado: o que precisa sobreviver à recriação

Recriar joga fora a camada gravável inteira, inclusive os caches de JIT. O DeepSeek move TRITON_CACHE_DIR, TILELANG_CACHE_DIR e B12X_CUTE_COMPILE_CACHE_DIR para o volume do cache do HF. O motivo, documentado: o cache dentro da imagem “morre na recriação”, as formas conhecidas voltam a compilar no meio do serviço, e um rank compilando pode segurar o par além do watchdog de 600 s do NCCL (CUDA graphs e warmup). A regra: código patcheado vive na camada gravável e é refeito a cada criação; estado caro de reconstruir vai para volume.

O contrato do patch: source-exact, fail-closed, idempotente e atômico

Um patcher é um programa que edita outro programa já instalado. Para ser seguro, ele precisa cumprir quatro promessas ao mesmo tempo. Source-exact: só mexe em bytes que conhece exatamente. Fail-closed: diante do desconhecido, recusa. Idempotente: rodar duas vezes tem o mesmo efeito que rodar uma. Atômico: quem lê o arquivo vê a versão velha inteira ou a nova inteira, nunca metade. O hotfix-vllm-rope-swa-fix.py do DeepSeek (port do upstream vllm#54815) cumpre as quatro de forma didática.

Antes do mecanismo, o que ele corrige no modelo. O DeepSeek V4 mistura camadas com compressor de KV (CSA/HCA) e camadas de atenção esparsa com janela deslizante (SWA, 128 tokens no checkpoint servido). A RoPE codifica a posição girando pares de dimensões, e a YaRN estica essas rotações para contextos longos. Pela implementação de referência, esse esticamento pertence só às camadas compressoras, que olham o contexto longo por meio do KV comprimido. A build pinada promovia o tipo de RoPE para deepseek_yarn em todas as camadas, então as camadas SWA (0, 1 e as três do drafter DSpark) recebiam YaRN de fator 16 sobre uma janela de 128 tokens. O patch só promove a YaRN quando compress_ratio > 1 e dá às outras camadas factor=1.0, a escala identidade: RoPE simples no mesmo kernel. As camadas compressoras ficam, byte a byte, com os parâmetros de antes. Na receita, esse hotfix é opt-in: um gate do compose o roda antes do vllm serve. A mudança é pequena, mas altera a geometria das posições que a atenção vê, e por isso merece o contrato completo:

  1. Versão. Exige vllm == 0.25.2.dev0+g752a3a504.d20260714. Qualquer outra versão já é recusa.
  2. Tipo. O alvo precisa ser arquivo regular (lstat), nunca symlink.
  3. Identidade. Lê os bytes e calcula SHA-256 e tamanho. Aceita dois estados: stock 0074271a… (1.242 B) ou patched 6452ce2e… (2.111 B). Se já está patcheado, sai 0 com already-patched: essa é a idempotência.
  4. Transformação em memória. A região antiga precisa aparecer exatamente uma vez e o marcador # [dspark-rope-swa] não pode existir. Troca a região e roda compile() na pós-imagem.
  5. Pós-imagem pinada. O resultado precisa ter o SHA-256 e o tamanho patched esperados. O patch prova o que vai escrever antes de escrever.
  6. Publicação atômica. Arquivo temporário no mesmo diretório, write, flush, fsync, chmod igual ao original e os.replace(tmp, alvo). Em exceção, apaga o temporário.
  7. Reverificação. Relê o alvo, que precisa estar no estado patched. Qualquer falha imprime FAIL-CLOSED: … e sai 1. --check e --status só inspecionam, sem escrever.
\[ P(x) = \begin{cases} p & \text{se } H(x) = h_s \\ p & \text{se } H(x) = h_p \\ \bot & \text{caso contrário} \end{cases} \qquad\Rightarrow\qquad P(P(s)) = P(s) = p \]
  • \(x\): bytes atuais do arquivo-alvo; \(s\) e \(p\): as versões stock e patched conhecidas
  • \(h_s = H(s)\), \(h_p = H(p)\): os dois SHA-256 pinados no patcher
  • \(\bot\): recusa (exit 1). O patch é uma função parcial: fora de \(\{s, p\}\) não existe resposta, e “não existe” vira “não sobe”
  • A chance de um arquivo diferente ter, por acaso, o SHA-256 de um pin é da ordem de \(2^{-256}\): na prática, zero

Por que tanto cuidado na escrita? Porque open(alvo, "w") trunca o arquivo antes de escrever. Se o processo morrer no meio (OOM, queda de energia, docker kill), sobra um .py pela metade, e o vLLM não importa mais. Já os.replace é um rename POSIX: atômico, desde que origem e destino estejam no mesmo sistema de arquivos. Daí o temporário no mesmo diretório. O fsync antes do rename garante que os bytes chegaram ao disco antes de o nome passar a apontar para eles (publicação atômica). Na figura, tente os cinco estados do alvo e simule a queda de energia nos dois modos de escrita.

Três lições saem da figura. Rodar duas vezes é inofensivo. Um arquivo de outra versão é recusado antes de qualquer escrita. E a queda de energia é o teste definitivo: na escrita atômica, o arquivo continua stock e o próximo boot aplica normalmente; na ingênua, sobra um arquivo corrompido que o patcher recusa (ainda bem), mas que também impede o vLLM de importar.

Hash do arquivo inteiro ou âncora?

Há dois jeitos de garantir que se está editando o arquivo certo, e as receitas usam os dois:

Pin de SHA-256 do arquivo inteiro

  • Estrito: qualquer byte diferente em qualquer lugar vira recusa.
  • Exige re-portar e re-pinar a cada imagem nova. Casa com uma imagem pinada por digest.
  • Lane A do DeepSeek: todos os patchers modernos, com fixtures da fonte 752a3a504.
  • Também no GLM, nos patches de geometria crítica: o opt-in patch_sparse_mla_slice.py do TP=4 pina pré-imagem e resultado por SHA-256.

Âncora exata (1 ocorrência)

  • Tolera mudanças em outras partes do arquivo.
  • Risco: a semântica pode ter mudado fora da âncora. Mitigação: ast.parse/compile, testes com fixtures, marcadores de idempotência.
  • Qwen e a maioria dos patches do GLM: cada âncora exatamente 1×; se não casa, aborta sem escrever nada.

Hunks de diff do upstream

  • Embute o diff do PR e aplica hunk a hunk.
  • Detecta “já aplicado” e grava atomicamente.
  • Qwen patch_qsa_fp8_kv_v030.py (backport do vllm#55557): parse_diff / find / apply + os.replace.

Diff unificado aplicado pelo patch

  • A âncora é o contexto do trecho mais as linhas que ele remove.
  • Tolerante: aceita o trecho algumas linhas deslocado e, por padrão, ignora até 2 linhas de contexto que não batem em cada ponta (fuzz).
  • --forward recusa um trecho que pareça já aplicado; || exit 1 transforma qualquer recusa em build falho.
  • TensorFold: 53 diffs no build, sempre sobre a versão que o pip acabou de instalar.

Quando a correção toca vários arquivos, a atomicidade precisa virar transação. Os backports .sh do DeepSeek validam todos os alvos e âncoras antes de escrever qualquer um, e em falha fazem rollback byte-exato de tudo o que já publicaram (scripts/test-hotfix-atomic-transaction.py testa isso). O patch_block_drop.py do Qwen segue a mesma lógica: “Patch all files before writing any, so a failed anchor leaves no partial set.” O GLM acrescenta um guarda do lado do launcher. Cada overlay montado precisa conter sua string de identidade, terminar na última linha esperada e passar no parse do Python, o que pega uma cópia truncada ou trocada antes do boot.

Ordem e paridade: compondo patches nos dois ranks

Com um patch só, basta o contrato. Com 25, entra a álgebra: o arquivo que o vLLM executa é a composição de todos os patches, na ordem em que rodam.

\[ F = P_n \circ \cdots \circ P_2 \circ P_1(\text{stock}), \qquad P_a \circ P_b = P_b \circ P_a \ \ \text{se}\ \ R_a \cap \big(R_b \cup A_b\big) = \varnothing \ \ \text{e}\ \ R_b \cap \big(R_a \cup A_a\big) = \varnothing \]
  • \(P_i\): o i-ésimo patch (uma função parcial, como na seção anterior)
  • \(R_i\): a região de bytes que \(P_i\) reescreve; \(A_i\): o trecho que a âncora de \(P_i\) precisa encontrar intacto
  • A condição é suficiente: se nenhum dos dois reescreve o que o outro lê (a âncora) ou escreve (a região), eles comutam e a ordem não importa. Duas âncoras que só se sobrepõem na leitura (\(A_a \cap A_b \neq \varnothing\)) não atrapalham, porque cada patch encontra o trecho intacto na pós-imagem do outro
  • Se um reescreve a região ou a âncora do outro, a ordem vira parte da receita

É exatamente o que os comentários do start.sh do GLM, junto da GLM53_OVERLAY_ORDER, registram. O patch_hybrid_prefix_hit.py vem antes do patch_apc_per_group_retention.py “porque compartilham o ponto de inserção do helper do coordenador”. O patch_apc_no_store.py vem depois da retenção, mas só edita sampling_params.py, request.py e block_pool.py, sem âncoras em comum com os overlays do coordenador. O patch_kv_capacity_log.py segue o patch_glm5_drafter_group.py, o outro que edita kv_cache_utils.py. No TP=3, o comentário do script interno de start-tp3.sh registra que o patch_exl3_ep_shard.py precisa vir depois do patch_dense_fp8.py, que reinstala o exl3.py inteiro e apagaria a edição anterior. No DeepSeek, a ordem é a própria cadeia do command: do compose. O scripts/test-python-hotfix-failclosed.py confere a ordem e o || exit 1 de cada patcher Python, e o backport do #136 foi provado nas duas ordens contra o #44993: as regiões são disjuntas, e a âncora de cada um continua intacta na pós-imagem do outro.

Idempotência e ordem fixa juntas permitem um truque do GLM: aplicar os overlays no build (a imagem já sai coerente e os testes rodam sobre o código patcheado) e de novo no start, a partir dos arquivos montados em /opt/glm53/*.py:ro. Assim, corrigir um patch não exige rebuild. Na reaplicação, cada patch reconhece o próprio marcador e vira no-op.

Paridade: um programa, duas máquinas

Tensor parallel é SPMD: o mesmo programa roda em cada rank, e cada coletiva (all-reduce, all-gather) só termina quando todos os ranks chegam nela (paralelismos). Se um rank executa código diferente, ele pode lançar outra sequência de coletivas, e o outro espera para sempre, ou até o watchdog matar o processo. As receitas mediram isso: ranks com FP8, adaptive-k ou capture sizes diferentes travam o NCCL depois da captura PIECEWISE (CUDA graphs gravados por trecho, com a atenção rodando fora deles; ver CUDA graphs e warmup), e caches de autotune divergentes já travaram o TP2 do Qwen. Daí a paridade como regra. O GLM gera o bloco de overlays por uma função (emit_overlay_block), “mesmos bytes para os dois ranks”, e repassa exatamente os mesmos knobs GLM53_*/EXL3_* a cada container. O DeepSeek limpa com env -u os knobs que variam por rank (MASTER_ADDR/MASTER_PORT, NODE_RANK, HEADLESS). Na linha do compose do worker, injeta só o que precisa diferir (NODE_RANK=1, HEADLESS=1, VLLM_HOST_IP) e repete os demais valores já resolvidos (GPU_MEMORY_UTILIZATION, DSPARK_MODEL, DSPARK_REVISION, o cache do HF…), tirados do mesmo snapshot normalizado do .env. O Qwen monta os argumentos do vllm serve uma vez (VLLM_ARGS) e os compartilha entre os scripts do head e do worker.

Três desfechos para guardar. A ordem da receita e a ordem com C movido dão o mesmo hash, porque C comuta: ele nem abre o arquivo de A e B. Inverter A e B faz a âncora de um sumir, e o boot aborta nos dois ranks: seguro. O caso do TP=3 é o traiçoeiro. A reinstalação apaga a edição sem erro na hora do patch, e o sintoma só aparece na carga dos pesos (dim 0 size 2048 is not divisible by tp=3). E um worker com um patch a menos produz hashes diferentes nos dois ranks: o grupo sobe, mas pode travar na primeira coletiva que divergir.

No TensorFold, o próprio motor confere a paridade

As receitas vLLM garantem a paridade por fora: o launcher gera os mesmos bytes e os mesmos knobs para os dois ranks, e uma divergência que escape vira trava na primeira coletiva. O motor GLM do TensorFold acrescenta uma conferência por dentro. Na partida, cada rank empacota numa lista de inteiros as configurações que mudam a sequência de chamadas (drafter, capacidade, linhas por chunk, grade de prompt, copy drafts, divisão das hyper-connections, concorrência, larguras de janela…), os dois fazem um all-gather dessas listas e, se elas diferem, o motor se recusa a subir com the two ranks were started with different settings, imprimindo as duas. A trava silenciosa vira um erro com endereço. A seção de atualização mostra a conferência funcionando, e também que a ordem dos 53 patches importa pelo mesmo motivo desta seção: vários reescrevem a mesma linha.

.env, precedência e as armadilhas do shell

A configuração de uma receita vem de várias fontes: default no script, arquivo .env, variável exportada por quem chama, wrappers (start-fp8.sh), flags de linha de comando. A precedência é a regra que escolhe entre elas quando discordam:

\[ v = s_{k^*}, \qquad k^* = \min\{\,k : s_k \text{ está definido}\,\} \]
  • \(s_1, s_2, \dots\): as fontes, da mais forte para a mais fraca
  • \(k^*\): a primeira fonte que define a chave; ela vence e todas abaixo são ignoradas
  • “Definido” tem nuance: X= (vazio) é definido. O GLM trata um export vazio como override, e o DeepSeek faz unset das variáveis NCCL vazias, porque um NCCL_IB_GID_INDEX="" vira índice 0 e mascara o /etc/nccl.conf

A fórmula é a mesma nas três receitas, mas a ordem das fontes não é:

GLM: quem chama vence

  • O launcher tira um snapshot de todas as variáveis exportadas (inclusive vazias) antes do source .env e as reexporta depois.
  • Variáveis de identidade (HF_HOME MODEL MODEL_REVISION IMAGE PORT TP NNODES) avisam quando sobrescritas.
  • ABLIT é zerado depois do .env: só ABLIT=1 ./start.sh liga.

Qwen: o .env vence

  • source .env depois de ler o ambiente: KV_CACHE_DTYPE=auto ./start.sh é ignorado se o .env define a chave (um gotcha que custou um ciclo inteiro de launch).
  • Exceções: ABLIT e HF_TOKEN (_CLI_ABLIT, _CLI_HF_TOKEN).
  • OVERRIDE_* são lidos depois do .env. É assim que start-fp8.sh e start-v030.sh reaproveitam o mesmo start.sh.

DeepSeek: .env normalizado + CLI

  • --host/--port na linha de comando vencem o .env.dspark.
  • O .env vence o ambiente, com exceção dos knobs de ablação, que são preservados.
  • DSPARK_API_KEYS no ambiente diferente do .env não é resolvido pela precedência: é erro (exit 2).

Repare no Qwen com “você exporta”: o valor que você digitou só vale se o .env não tiver a chave. E no GLM com ABLIT: o .env nunca vence, por decisão explícita de segurança. Toda receita precisa escolher uma regra, documentá-la e fazer o launcher imprimir o valor efetivo (o Qwen manda conferir a linha KV dtype: no resumo do launch).

O .env é código de shell

Nas três receitas, o .env é lido com source: o bash o executa linha a linha. No GLM e no DeepSeek, o source fica entre set -a e set +a, que exporta tudo para os processos filhos. No Qwen, sem set -a, as variáveis ficam só no shell do launcher, que as usa para montar o comando do container. Isso traz armadilhas que um parser de configuração não teria:

  • Aspas somem. SPEC={"method":"dspark"} vira {method:dspark}, e o JSON morre.
  • CRLF. Um arquivo salvo no Windows termina as linhas em \r\n. O bash guarda o \r dentro do valor ($'fp8\r'), invisível no log.
  • BOM. Alguns editores gravam EF BB BF no começo. A primeira linha deixa de ser uma atribuição e vira um comando inexistente, e a variável fica vazia.
  • Octal e overflow. Em $(( )), 08 é erro (“value too great for base”) e 010 vale 8. Um número gigante dá a volta nos 64 bits: 18446744073709551622 vira 6 e passa em qualquer checagem de faixa.

O DeepSeek se defende em camadas. Primeiro, normaliza uma cópia privada (0600) do .env com sed (tira BOM e CRLF) e dá source nela; o arquivo do operador fica byte-idêntico. Depois, dspark_validate_numeric_knobs rejeita não-inteiros e valores com mais de 10 dígitos antes de qualquer aritmética, só pelo comprimento, sem avaliar o número. É um limite conservador (os máximos reais têm no máximo 7 dígitos) que nunca deixa um número gigante chegar à conta de 64 bits. Em seguida, normaliza com 10# (sempre decimal) e confere as faixas (MAX_NUM_SEQS 1–4096, MTP_NUM_TOKENS 0–64, MAX_NUM_BATCHED_TOKENS 1–8.388.608). Por fim, reescreve o snapshot para que o worker, que recebe o arquivo via docker compose --env-file, veja o mesmo decimal que o head. Os números importam porque são encaminhados à aritmética do próprio container: --max-cudagraph-capture-size $(( (6·(6+1)+7)/8·8 )) = 48. O GLM valida os knobs numéricos antes de parar o par saudável (MAX_MODEL_LEN ≤ 10⁶, MAX_NUM_SEQS ≤ 4096, MAX_NUM_BATCHED_TOKENS ≤ 8.388.608): um erro de digitação não derruba o serviço que estava bom.

Um .env lido, nunca executado

A versão TensorFold da receita GLM corta o problema pela raiz: o config.sh dela não dá source no .env. Ele lê o arquivo linha a linha e só aceita o formato CHAVE=valor (com export opcional na frente), conferido por expressão regular. Um valor entre aspas simples ou duplas perde as aspas e o comentário depois delas; um valor sem aspas perde o que vem depois do # e o espaço em branco do fim. A precedência é ambiente > scripts/local.sh (este, sim, lido com source, porque é código do operador) > .env > defaults, e o .env nunca sobrescreve uma chave já definida. Conferimos o parser num bash: o \r de um arquivo CRLF cai junto com o espaço do fim; {"method":"dspark"} chega com as aspas; $(touch PWNED) vira texto, sem executar nada. O BOM continua traiçoeiro de outro jeito: a primeira linha deixa de casar com o padrão e é ignorada em silêncio, e a chave fica no default. Os números ainda passam por expressões regulares no start.sh (PARALLEL de 1 a 4, COPY_MAX de 1 a 15) e, depois, pelo parser do próprio motor.

Montar o JSON dentro do container

A lição do caso “JSON no .env” vira padrão de projeto: no .env, só átomos simples (palavras e números validados). Estruturas complexas são montadas onde a sintaxe é controlada. O compose do DeepSeek também tem duas fases de interpolação: ${VLLM_PORT:-8888} é resolvido pelo Compose no host, enquanto uma referência escrita com o cifrão dobrado (dois $ seguidos antes de HEADLESS) chega ao container como $HEADLESS e só é avaliada pelo shell dele, em runtime. O próprio arquivo avisa para não adiar assim o VLLM_HOST: essa variável só existe para o Compose e não está no ambiente do container.

Entrypointmontagem do --speculative-config (docker-compose.dspark.yml:475-479)

O .env guarda só MTP_NUM_TOKENS=6 e DRAFT_SAMPLE_METHOD=probabilistic. Dentro do container, um case aceita apenas probabilistic|greedy (qualquer outro valor: mensagem e exit 2), e só então o JSON é montado com aspas escapadas:

# como o shell do container vê (no arquivo do compose, cada $ do shell aparece dobrado)
case "${DRAFT_SAMPLE_METHOD:-probabilistic}" in
  probabilistic|greedy) DRAFT_SAMPLE_METHOD="${DRAFT_SAMPLE_METHOD:-probabilistic}" ;;
  *) echo "DRAFT_SAMPLE_METHOD must be one of: probabilistic, greedy" >&2; exit 2 ;;
esac;
SPECULATIVE_CONFIG="{\"method\":\"dspark\",\"num_speculative_tokens\":${MTP_NUM_TOKENS:-6},\"draft_sample_method\":\"${DRAFT_SAMPLE_METHOD}\"}";
# → {"method":"dspark","num_speculative_tokens":6,"draft_sample_method":"probabilistic"}

Por quê: o valor cru do .env perderia as aspas no source e poderia injetar JSON arbitrário (um valor com " e , acrescentaria chaves). Com a lista branca, a string só pode ter formas conhecidas. O mesmo padrão aparece em DEFAULT_THINKING (off|low|high|max → DEFAULT_CHAT_TEMPLATE_KWARGS) e em LIMIT_MM_PER_PROMPT: a forma amigável image=8 é validada como inteiro e convertida para {"image":8}, porque o argparse da imagem Anemll faz json.loads e rejeitava image=8 cru. Os detalhes do DSpark estão em DFlash2 e DSpark.

Segredos e superfície exposta

Um launcher mexe com chaves de API, tokens do HF e endereços de rede, e cada canal por onde um valor passa é um lugar onde ele pode vazar. As receitas fecham esses canais um a um. O GLM passa -e VLLM_API_KEY sem valor na linha do docker run: a chave não aparece no argv nem vai para o worker. O DeepSeek aplica hotfix-vllm-redact-api-key-log.sh, que troca a chave por <redacted:N value(s)> na linha non-default args do log. Ele também avisa se a API faz bind em 0.0.0.0 sem chave ou se o .env com segredos é legível por grupo ou outros, e copia o env para o worker como arquivo temporário 0600 + mv -f (atômico). O Qwen grava o comando renderizado em .last_head_launch.sh com modo 0600 (ele pode conter --api-key) e manda o script do worker por stdin (ssh "bash -s" < script): nenhum arquivo fica num caminho fixo para vazar. E lembre que GLM e Qwen servem em --host 0.0.0.0 por padrão, aberto na rede. Mesmo com chave, /health, /metrics e /tokenize ficam sem guarda (API e ferramentas).

O launcher e a supervisão: do start.sh ao canário

Um launcher como o start.sh é um pequeno programa distribuído: coordena duas máquinas por SSH, e cada passo pode falhar de um jeito diferente. As três receitas convergem para a mesma espinha dorsal: um portão em cada passo até o READY e, depois dele, um jeito conhecido de observar o par:

  1. Trava e configuração. O GLM serializa start, restart e stop com flock em logs/cluster.lock. Em seguida vem o .env normalizado com seus números validados. Configuração inválida: exit 2, antes de tocar em qualquer container.
  2. Preflight. HEAD_IP precisa estar atribuído localmente, e o SSH roda em BatchMode com ConnectTimeout=10. Os GIDs RoCEv2 são conferidos por HCA (um GID errado mata o rank com errno 61 em ~60 s). A memória precisa passar em MemAvailable ≥ util × total + 2 GiB. O Qwen ainda exige GPUs ociosas (REQUIRE_IDLE_GPU), e o GLM limpa o page cache (drop_caches) nos dois nós (memória unificada).
  3. Imagem nos dois nós. pull ou save | ssh load, com a image key comparada entre head e worker.
  4. Pesos. Download no head, verificação de shards e tamanhos, e cópia ao worker por rsync ou NFS (nconnect=8 sobre a CX7; montar pela rede de gerência é recusado). Detalhes em checkpoints.
  5. Sincronizar artefatos. Compose, .env (0600, atômico), patchers e proposer vão para o worker. No DeepSeek, o preflight --check de cada patcher sensível roda no worker e depois no head, via docker compose run --rm --no-deps --entrypoint python3 … --check, antes de subir qualquer rank.
  6. Worker primeiro, head depois. O worker (rank 1, headless) sobe e espera o rendezvous, o encontro inicial em que os ranks trocam endereços. O head (rank 0) sobe com o TCPStore (o armazém chave-valor que hospeda esse encontro), o scheduler e a API. Quando a API aparece, o grupo inteiro já existe (NCCL e RDMA).
  7. Esperar com prazo. O launcher consulta /health ou /v1/models (DeepSeek: WAIT_ATTEMPTS=100 × WAIT_SECONDS=15 ≈ 25 min). O GLM faz fail-fast: se o container do worker morrer (3 checagens seguidas, ~30 s), aborta a espera em vez de esperar o timeout inteiro.
  8. Aquecer e provar. Warmup das formas que o tráfego vai usar, depois o canário. Só então vem o banner READY.
  9. Observar. Depois do READY, o operador precisa saber onde olhar. O GLM grava tudo em logs/ ($LOGDIR): build-sm121.log do build, overlay-verify.log do self-check na GPU e, quando o canário ou a espera falham, head.log e worker.log (este puxado por SSH) antes de encerrar. Com TAIL=1, o launcher segue o log do head depois do banner (Ctrl-C só desanexa; o servidor continua). O DeepSeek separa a observação em scripts próprios. O status-deepseek-v4-flash-dspark.sh conta as sondas que falham e devolve isso no exit code, para um supervisor poder confiar nele. O logs-deepseek-v4-flash-dspark.sh junta os logs do head e de cada worker (por SSH, 160 linhas por padrão, TAIL). O Qwen segue docker logs -f vllm-fn enquanto espera o /health, imprime um resumo com a linha KV dtype: (o valor efetivo) e guarda o comando renderizado em .last_head_launch.sh (no TP1, .last_launch.sh).

O Qwen deixa as etapas escolhíveis (DO_DOWNLOAD, DO_SYNC, DO_LAUNCH; --no-download, --launch, --nfs). O validate-dspark-config.sh do DeepSeek imprime a linha renderizada sem subir nada. Na parada, o GLM mata os dois containers direto e em paralelo (kill-first, ~15 s mais rápido; não há estado a descarregar). O DeepSeek usa stop_grace_period de 10 s. Medidas do boot: o ./start.sh restart do GLM caiu de 259 para 122 s (/health em 99 s, 2026-09-19), e o cold start do Qwen leva ≈ 10 min 55 s.

Supervisão: quem reinicia o quê

A política de restart divide as receitas. O DeepSeek usa unless-stopped (issues #38/#39: trazer de volta um worker que caiu, e restaurar os ranks após um reboot). O Qwen deixa --restart de fora de propósito: um rank reiniciado sozinho pode travar no init do NCCL (interpretação: o parceiro continua preso ao grupo antigo e não faz um novo rendezvous). O próprio CHANGELOG do DeepSeek admite o risco: reinícios independentes do Docker podem separar o par TP=2, e a saída é DSPARK_RESTART_POLICY=no com ./stop/./start juntos.

Supervisão também exige um contrato de códigos de saída. No DeepSeek: 0 ok, 1 falha, 2 configuração inválida, 3 já rodando. Depois de um reboot, o dockerd restaura os ranks e um ./start disparado pelo systemd encontra tudo no ar. Sair 1 causaria uma tempestade de retries; sair 3 com SuccessExitStatus=3 no unit resolve. Uma sonda remota distingue “o rank existe” (sentinela 42) de “o SSH falhou” (255). A documentação (docs/ENVS.md) ressalva que exit 3 não prova que o grupo está saudável, porque um reboot só do head pode deixar um worker velho. No GLM, o mesmo número 3 significa outra coisa: DEGENERATE ENGINE, vindo do canário. Códigos de saída são contratos locais, então documente os seus.

Launcher./start.sh em 5 passos · FOREGROUND=1

O start.sh da versão TensorFold segue a mesma espinha dorsal (setup, checagens, lançamento worker → head, carga, teste de fumaça) e traz quatro ideias que valem copiar. 1. Validar com o parser do próprio motor. Antes de parar qualquer coisa, os argumentos passam por build_parser().parse_args(...) do tensorfold.cli, num container descartável e sem GPU. Um erro de digitação falha ali, com o servidor antigo ainda no ar, e o launcher não precisa manter uma segunda cópia das regras do motor. 2. Marcador de preparo. Uma linha com modelo@revisão, drafter@revisão, os ids da imagem nos dois Sparks, o hash dos patches, o worker e o modo dos pesos; o prepare.sh roda de novo sempre que a linha atual difere da gravada. 3. Uma segunda chance medida. Se o rank 0 sai dizendo qual é a maior janela que cabe na memória daquela partida, o launcher sobe de novo uma vez, com --context igual a ela, e avisa. 4. O par como unidade. Não há política de restart do Docker. Com FOREGROUND=1, o script fica preso ao log do rank 0 e sai com o código dele, para um unit do systemd com Restart=on-failure, e um vigia para o rank 0 se o rank 1 terminar, porque um rank sozinho esperaria o parceiro para sempre. Nesse modo não há retry de janela nem teste de fumaça. No modo normal, o teste de fumaça é o mesmo “Reply with OK.” do GLM (temperatura 0, sem raciocínio, 32 tokens), mas só exige texto na resposta: a exatidão dos rascunhos é provada por outros testes (receita GLM em TensorFold).

Atualização: diffs assados e imagem por hash, no TensorFold

Tudo até aqui remenda o vLLM. A receita GLM agora tem uma segunda versão , que serve o mesmo checkpoint EXL3 nos mesmos dois Sparks com outro motor: o TensorFold v0.6.0 mais 53 patches. O TensorFold é escrito por família de modelo e chega como pacote Python, instalado pelo pip a partir de uma tag do git, com kernels próprios que compilam por JIT na primeira partida. O desenho do motor está no capítulo do motor exato, e a receita inteira, passo a passo, na receita GLM em TensorFold. Aqui interessa a engenharia de receita. O problema é o mesmo deste capítulo: você não é dono do motor, precisa dos mesmos bytes nos dois nós e prefere não subir a subir errado. As respostas mudam em três pontos: onde a mudança mora, como a imagem é identificada e quem confere a paridade.

Diffs unificados contra o site-packages, assados no build

Os 53 patches são diffs unificados, o formato que diff -u e git diff produzem, escritos contra os arquivos do TensorFold v0.6.0 instalados no site-packages do container. Nada é aplicado no boot. O prepare.sh monta a imagem com um Dockerfile embutido no próprio script, em cinco passos:

  1. Base. FROM nvcr.io/nvidia/pytorch:26.07-py3, o container PyTorch da NVIDIA, com CUDA, PyTorch, Triton e o compilador de extensões.
  2. Motor. pip install git+https://github.com/ashhart/TensorFold.git@v0.6.0, mais os extras av==18.1.0 (vídeo) e xgrammar>=0.2.8,<0.3 (saídas estruturadas), e um tensorfold --version.
  3. Patches. COPY da pasta patches/ e, no diretório que contém o pacote tensorfold, um laço que aplica cada *.patch em ordem de nome: patch -p0 --forward < "$p" || exit 1.
  4. Prova. Um python -c "import …" dos módulos patcheados (o servidor CUDA, o engine da família GLM, a visão) e dos extras. Um módulo que deixou de importar derruba o build.
  5. Carimbo. LABEL tf.patches=<hash> e um ENV que aponta os caches de JIT (TORCH_EXTENSIONS_DIR, TRITON_CACHE_DIR) para /cache, montado de fora pelo launcher.

Um diff unificado é um patch por âncora com outro sotaque. Cada trecho (hunk) traz as linhas que remove (-), as que acrescenta (+) e algumas linhas de contexto em volta, e o patch procura no arquivo o contexto mais as linhas removidas. Há duas diferenças em relação às âncoras exatas da receita vLLM. A primeira é a tolerância: o patch do GNU aceita o trecho algumas linhas acima ou abaixo do esperado e, por padrão, ignora até 2 linhas de contexto que não batem em cada ponta do trecho (fuzz); as linhas removidas, essas, precisam bater. A segunda é o --forward, que faz o patch recusar um trecho que pareça já aplicado em vez de oferecer desfazê-lo. Com o || exit 1, qualquer trecho recusado derruba o build. Interpretação: a tolerância seria um risco num alvo móvel, mas aqui o alvo é sempre o mesmo código, a tag v0.6.0 para a qual os diffs foram escritos e que o pip acabou de instalar. O que o contexto deixar passar, o import de prova e os testes de exatidão da receita (resposta com rascunhos igual à decodificação serial, quatro requisições juntas iguais a cada uma sozinha) pegam depois.

Isso muda a resposta da seção sobre onde mora uma mudança. Ela mora numa camada da imagem, sempre. Não há camada gravável patcheada no boot nem bind-mount: o código que o container roda é o da imagem, e um docker restart não tem como preservar um hotfix que nunca existiu. Mudar um patch custa um rebuild, mas barato. A camada do pip install vem antes do COPY patches e continua no cache de build, e o comentário do prepare.sh diz que o rebuild leva segundos. É a regra da ordem das camadas outra vez: o que muda pouco (o motor) embaixo, o que muda muito (os patches) em cima, o carimbo por último.

Ordem: cada patch é escrito sobre o anterior

Os patches entram em ordem de nome de arquivo, e o número na frente do nome (0001 … 0053) é a ordem. Nada garante que comutam, e muitos não comutam, porque vários reescrevem a mesma linha. O melhor exemplo é a lista de configurações que o motor confere na partida (adiante): mine = [...], no engine.py da família GLM. No v0.6.0 ela tem 8 itens. O patch 0007 acrescenta os parâmetros das copy drafts; o 0008, a grade de prompt; o 0010, a divisão das hyper-connections; e assim por diante até o 0035: nove patches reescrevem essa mesma lista, que sai do 0035 com 35 inteiros na configuração da receita. (O 0040 ainda acrescenta um, de dentro da função que gera o trecho da política multi-stream, sem tocar nessa linha: a imagem final confere 36.) Cada um traz no seu diff, como linhas removidas, a versão da lista que o anterior deixou. Na linguagem da seção sobre ordem e paridade, a região que \(P_k\) escreve é a âncora de \(P_{k+1}\), e a ordem faz parte da receita.

Na figura, a lista é uma fileira de fichas e cada patch é um carimbo que traz o seu trecho. Escolha o conjunto de patches e veja o que o prepare.sh faz com ele: o hash, de onde vem a imagem e onde o build para.

Três lições. Trocar dois vizinhos já quebra: o 0011 foi escrito contra a lista que o 0010 deixou. Apagar um patch do meio é a mesma coisa vista de outro ângulo. E as duas falhas acontecem no build, dentro do prepare.sh, que o start.sh roda antes de parar o servidor que está no ar: um conjunto de patches quebrado nunca derruba um serviço saudável. Foi esse o trabalho da v1.3 ao passar para o TensorFold v0.6.0: rebasear cada diff, apagar os que o upstream absorveu e renumerar o resto.

O nome da imagem é o hash das entradas

A imagem tem uma tag que vem do hash do que a define:

\[ h = \operatorname{SHA256}\big(P_{0001} \,\|\, P_{0002} \,\|\, \cdots \,\|\, P_{0053} \,\|\, E\big)_{[1..12]}, \qquad \text{tag} = \texttt{v0.6.0-}h \]
  • \(P_i\): os bytes de cada arquivo patches/*.patch, concatenados em ordem de nome (é o cat patches/*.patch do config.sh); \(\|\) é concatenação
  • \(E\): a linha IMAGE_EXTRAS (av==18.1.0 xgrammar>=0.2.8,<0.3). Mudar um pacote extra muda a imagem como mudar um patch
  • \([1..12]\): os 12 primeiros dígitos hexadecimais, 48 bits. Pelo paradoxo do aniversário, uma colisão por acaso só fica provável perto de \(2^{24} \approx 1{,}7 \times 10^{7}\) conjuntos de patches diferentes
  • Na release v1.3.2, \(h = \texttt{ae8d1c789b47}\) e a tag é v0.6.0-ae8d1c789b47

O prepare.sh calcula \(h\) e decide de onde vem a imagem. Se a imagem local já tem tf.patches igual a \(h\), não há nada a fazer. Se \(h\) é o hash da release, ele puxa a imagem publicada por digest (…@sha256:22789f0c…), porque uma tag pode ser movida e um digest não. Se \(h\) é outro (você mexeu num patch), ele tenta a tag v0.6.0-\(h\) no registry e, se ela não existe, ou com PULL=0, constrói, gravando \(h\) no label. Uma imagem puxada só é adotada se o label tf.patches dela for igual ao \(h\) calculado, e a do worker só passa se a identidade de conteúdo bater com a do head. É o carimbo da receita vLLM com uma diferença: lá a tag é fixa (:exl3-instanttensor) e o carimbo decide; aqui cada conjunto de patches tem a sua tag, com o hash no próprio nome.

Por que fixar o digest se o nome já é um hash? Porque o hash cobre as entradas, não o resultado. A base é uma tag (26.07-py3), o motor vem de uma tag do git e o xgrammar é uma faixa de versões, então dois builds com o mesmo \(h\), em dias diferentes, podem dar bytes diferentes (interpretação). O label diz “construída a partir destes patches”; só o digest diz “estes bytes”. A publicação também tem seus cuidados. O publish-image.sh confere que o label sobreviveu à reetiquetagem com os labels OCI (com eles, o pacote no GHCR herda a visibilidade do repositório), faz login com um DOCKER_CONFIG temporário, apagado no fim, para que nenhuma credencial fique em ~/.docker, envia :v0.6.0-\(h\) e :latest e imprime o par IMAGE_TAG/IMAGE_DIGEST para fixar no config.sh. Os pesos seguem a mesma lógica: MODEL_REVISION e DFLASH2_REVISION são commits do Hugging Face, os containers rodam com HF_HUB_OFFLINE=1, e um commit novo no Hub não muda nada até o pin mudar.

Paridade conferida pelo próprio motor

Falta garantir que os dois ranks rodam com as mesmas configurações. Isso começa no launcher. Toda variável TENSORFOLD_*, TF_GLM_* e TF_ROCE_* presente no ambiente vai com -e para os dois containers, porque o comando do rank 1 roda por ssh, aonde o ambiente do head não chega (nenhuma delas é segredo). Os argumentos extras de ./start.sh restart … entram nos dois ranks depois dos defaults, e o argparse fica com o último valor. E continua no motor, com a conferência de configurações. Na partida, cada rank monta a lista mine (36 inteiros na configuração da receita), acrescenta no fim quanta memória sobra para os prompts guardados, em MiB, e os dois fazem um all-gather. As listas precisam ser idênticas; a memória sobrando pode diferir, e os dois adotam a menor. Se algo difere, os dois param com uma mensagem que mostra as duas listas e pede o mesmo drafter e as mesmas flags nos dois ranks.

Na figura, mude um knob, desligue o repasse para o worker, como faria um launcher ingênuo, e depois desligue a conferência para ver o que ela evita.

O ganho está na classe do erro. Sem a conferência, uma configuração divergente vira o pior tipo de falha deste capítulo: o grupo sobe, responde e trava na primeira coletiva que sair de passo. Com ela, a mesma divergência vira uma recusa na partida, nos dois ranks, com as duas listas impressas. É o fail-closed aplicado à paridade. A conferência não substitui o repasse do launcher, que continua sendo o que faz as listas baterem; ela só garante que, quando não baterem, ninguém sirva.

Por que dá para assar tudo no build

Interpretação nossa. A receita vLLM reaplica os overlays a cada start porque a imagem dela é cara de reconstruir: a extensão EXL3 compila no build, e um git pull que muda um overlay não deveria custar uma recompilação. No TensorFold, a camada cara (o motor) é estável e os kernels nem moram na imagem, compilam no GB10 na primeira partida. O rebuild por patch sai em segundos, e assar tudo vira o caminho mais simples. O preço aparece em outros lugares: cada conjunto de patches é uma imagem nova a mandar ao worker (só as camadas que mudaram), a primeira partida de cada imagem compila de novo, e 53 diffs presos a uma versão do motor precisam de rebase a cada versão nova do upstream.

Nas receitas: provar em CPU, versionar e aposentar hacks

Testes em CPU com fixtures do upstream

O par de Sparks é caro e está quase sempre servindo. Runners de CI não têm GPU. A saída é testar os patches como transformações de texto, em CPU, contra fixtures: cópias congeladas dos arquivos exatos da imagem pinada. No GLM ficam em tests/fixtures/*-487ecf187.py.txt; no DeepSeek, em scripts/fixtures/*/…-752a3a504-stock.py (dez famílias). Um bom teste de patch prova seis coisas: as identidades pinadas batem, a transformação é a esperada, aplicar duas vezes é no-op, drift é recusado, o rollback é byte-exato, e o patch está ligado no compose ou launcher. Quando é preciso executar o código, entram stubs. O test_draft_vocab.py do Qwen roda as funções patcheadas com um lm_head vocab-parallel falso e o coletivo stubado, e compara com o argmax do vocabulário cheio. Há até simuladores: o test_issue43_scheduler_sim.py do DeepSeek mostra que nenhum decode ativo é pulado nas seis células frias (32K/62K × 2/4/8). No GLM, TRITON_INTERPRET=1 roda kernels Triton no interpretador de CPU.

CI: o portão antes do merge

O CI do DeepSeek (.github/workflows/validate.yml → scripts/ci-validate.sh, ubuntu-24.04, timeout de 10 min) é todo em CPU. Roda bash -n em todos os scripts, py_compile nos patches, ~60 testes unitários contra as fixtures e guardas de regressão. O patch retirado do #31, que varria tokens na CPU, não pode voltar a existir. O patch de GPU do #31 não pode conter .cpu(, .tolist( nem .detach( (sincronizações no caminho quente). O #26 aplicado precisa ser a v2. O script de build precisa passar no autoteste do #173. Velocidade (tok/s) continua exigindo o par de verdade: o CI prova que o patch está certo, não que está rápido. Depois dos retratos, as duas lanes do GLM foram pelo mesmo caminho. A receita TensorFold ganhou um workflow em CPU (2026-10-10, bbf7e4b) que aplica cada patch ao fonte fixado do v0.6.0, confere se a tag da imagem é o hash do conjunto de patches e roda os testes das ferramentas. Na lane vLLM, correções como a 4709bc5 (o esforço de raciocínio no launcher de TP4) vêm com um teste que comprovadamente falha no código anterior à correção (14 falhas no launcher antigo): uma forma barata de teste de mutação, em que o mutante é o código velho (interpretação nossa). E o decode-floor v7 (b94fdfd, #283) leva o contrato ao instalador: instalações pristine, v1, v2, v5 e v5+priority migram para os bytes de uma instalação nova da v7, e v3/v4, versões com drift, duplicadas, só com marcador ou sem marcador são recusadas sem escrita, uma migração versionada e fail-closed. Numa frota de imagens com patches, num cluster de H200 inclusive, são esses três hábitos (gate em CPU, teste que falha sem a correção, migração que recusa o que não reconhece) que impedem o drift.

CHANGELOG e versões

O CHANGELOG é o diário de bordo operacional. O Qwen segue Keep a Changelog por data. O GLM rotulou retroativamente o histórico com SemVer (1.0.0–1.5.0; a 1.6.0, de 2026-09-17, é o corte atual). O DeepSeek organiza por data. Nos três, as entradas carregam o que um operador precisa: o número medido, a issue e a instrução prática (“recrie os dois containers depois do pull”). O CHANGELOG também registra o que foi retirado, e por quê, para ninguém reintroduzir.

Aposentar hacks e os limites do backport

Todo patch é uma dívida: um dia o upstream corrige, e o patch precisa sair de cena. As receitas mostram cinco maneiras de aposentar bem:

  • Detectar e virar no-op. O patch_block_drop.py do Qwen (backport do vllm#53388) procura disable_eagle_block_drop na fonte da imagem. Se já existe, apaga as saídas antigas e não monta nada. O patch_determinism.py faz o mesmo com use_fused_finalize (monta o arquivo stock).
  • Nota de morte no próprio arquivo. O patch_qsa_fp8_kv_v030.py diz: apague este arquivo, seu teste e seu overlay quando a imagem for vLLM 0.31 ou posterior, que traz o #55557 nativo.
  • Recusar meia correção. O patch_kpool_tail_seed_stride.py do GLM (backport do vLLM #57477) só considera o arquivo corrigido pelo upstream se toda chamada do seed passar os strides reais. Um arquivo meio corrigido falha o boot.
  • Seguir o revert. O DeepSeek removeu o backport do #50004 em 2026-08-22, quando o upstream o reverteu (#51318: corrupção intermitente sob graphs FULL). O upstream depois reintroduziu uma versão segura para captura (#52823), mas a base pinada é anterior ao #50004 e não há variante segura para portar sobre ela.
  • Proibir a volta. O caminho de CPU do thinking_token_budget (#31/#34) custava um penhasco de ~4,7× no decode e saiu. O CI garante que ele não volte.
Uma sexta maneira: entregar ao upstream

A versão TensorFold mostra o fim mais feliz para um patch. Na v1.3 da receita, que trocou o TensorFold v0.5.0 pelo v0.6.0, três patches da Mia passaram a fazer parte do próprio motor e foram apagados: o doorbell em que o rank 1 ocioso espera sem girar, a reserva de memória TENSORFOLD_MEMORY_RESERVE_GIB e o TF_GLM_MTP. Os outros foram rebaseados sobre a versão nova e renumerados (0024 → 0023 … 0053 → 0050), três novos entraram, e o total continuou 53. Dois hábitos completam o ciclo. Muitos patches entram desligados, com o comportamento do upstream como padrão (TF_GLM_COPY_DRAFTS=0, TF_GLM_HC_SPLIT=0, TF_GLM_COMM=nccl…), e é o config.sh da receita que liga cada um, com o efeito medido escrito ao lado: cada ganho vira um interruptor que dá para medir sozinho. E um padrão que não paga é revertido com medição. A stream lateral que sobrepõe as trocas do prefill nasceu com prioridade alta (0010); o 0017 transformou a prioridade num knob, ainda alta por padrão, e o 0022 mudou o padrão para normal quando dois boots com cada prioridade mostraram o prefill igual e, com a alta, rodadas de decode ~0,5–1% mais lentas depois de um prompt.

E há o que não dá para backportar por patch Python sobre uma imagem fixada. O documento docs/vllm-027-new-patches.md do DeepSeek lista os PRs de desempenho do vLLM 0.27 que ficaram de fora e diz por quê:

Checklist para a sua receita

1. Fixe a base por digest e o motor por commit, e guarde os digests no .env de exemplo. É a boa prática, mas das três receitas só o DeepSeek (lane A) faz isso no .env; se usar tag, ponha outra trava na frente, como o carimbo do GLM. 2. No Dockerfile, ponha o que muda pouco embaixo (compilação) e o que muda muito em cima (Python, label). 3. Escreva cada patch como função parcial: pin de fonte, pós-imagem verificada, os.replace, --check. 4. Declare a ordem dos patches num único lugar e gere os mesmos bytes para todos os ranks. 5. No .env, só átomos; valide números, normalize BOM/CRLF, monte JSON no container. 6. Launcher: trava, valida antes de parar, preflight, worker → head, espera com prazo, fail-fast, canário, e logs dos dois nós num lugar conhecido. 7. Documente códigos de saída e política de restart. 8. Teste em CPU contra fixtures, rode no CI, registre no CHANGELOG com a instrução “recriar”. 9. Dê a cada hack um jeito de morrer: detecção de upstream ou nota de remoção.
