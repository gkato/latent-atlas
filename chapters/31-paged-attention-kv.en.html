When the DeepSeek recipe boots, the log says GPU KV cache size: 2,331,430 tokens and Maximum concurrency for 1,048,576 tokens per request: 2.22x. Even so, the recipe accepts six simultaneous conversations with a ceiling of 1 million tokens each. On GLM, the log announces 1,553,140 tokens, but doing the math by hand shows that only about 57 thousand tokens of stored conversation fit. Both things are true. To understand why, this chapter opens up vLLM's memory manager: PagedAttention, the block tables, the profile run that decides how much is left for the KV, and the hybrid allocator that puts attention, sliding window, recurrent state and drafter in the same pool. By the end you will know how to read those lines, predict the effect of each knob and size the KV for a new recipe. You will also see the counterpoint: the new version of the GLM recipe runs on another engine, TensorFold, which, in the v0.6.0 the recipe pins, solves the same problems without pages or a profile run.

Memory that grows without warning

Recall the chapter on prefill, decode and the KV cache. For every token processed, each attention layer stores one row of K and one of V (or a latent vector, in MLA). This KV cache gains one row per layer at every decode step, and the engine doesn't know when generation will stop: the answer may be 20 tokens long or 20 thousand. And a server handles dozens of conversations at the same time, each one growing at its own pace.

The naive solution, used by the first servers, is to reserve for each request a contiguous range of memory as large as the maximum it can reach: the prompt plus the maximum number of tokens requested, capped by max_model_len. That wastes memory in three ways (illustrative numbers):

  1. Reserved. The places for the tokens the request has yet to generate are taken from admission onward. At step 10 of an answer that will end up with 900 tokens, 890 places are already locked and empty, and no other request can use them in the meantime.
  2. Internal fragmentation. The part of the maximum-size reservation that will never be used, because generation stopped before the ceiling. The request reserved room for 32 thousand tokens and stopped at 900: the remaining 31,100 places stayed blocked until it finished, without ever storing anything.
  3. External fragmentation. Reservations come in different sizes and end in random order, so free memory turns into holes between live reservations. There may be plenty of free space, all added up, and still no hole big enough for the next request.

The paper that introduced vLLM (Kwon et al., SOSP 2023) measured that, in the systems of the time, only 20.4% to 38.2% of KV memory held actual token states. The rest was reservation and fragmentation. In the figure below, the same sequence of requests arrives at two allocators. Each little square is the place for one token. The final length of each request is random, and neither allocator knows it in advance.

Look at the queue in the top panel. Requests wait even with dozens of free places, because no contiguous hole is as large as the reservation, and most of what was reserved stays hatched (idle). In the bottom panel, any free block works for any request, and the waste boils down to the end of each request's last block. Increase B and that waste grows. When memory runs out in the middle of a generation, the paged allocator evicts the newest request, returns its blocks and puts it back in the queue. This is called preemption, and the next chapter covers it in detail.

Analogy: the movie theater that only sold whole rows

The contiguous allocator is a movie theater that only sells whole rows. A party of three takes up a row of twenty, and a party of twelve can't get in if no row is empty, even with half the room free. The paged one sells blocks of four seats anywhere in the room and hands out a ticket saying where each of the party's blocks is. The party ends up scattered, but everyone gets in. The ticket is the block table.

The counterpoint: contiguous, but without reserving the ceiling

The TensorFold version of the GLM recipe goes back to contiguous memory and tackles the three kinds of waste another way. It doesn't reserve the ceiling: each request gets a range the size of its prompt, rounded up to units of 2,048 tokens, and the range grows as the reply advances. All that sits idle is the end of the last unit. External fragmentation comes back, and it is undone by moving and compacting the ranges. The price is copying rows now and then and, as we read it, the math works because there are few requests at a time (at most 4 in v1.3.2; 8 since v1.5). The “Update” section, near the end of the chapter, shows the mechanism.

PagedAttention: pages, block table and slots

The idea comes from operating systems. A process sees contiguous virtual addresses, and the operating system maps them to physical pages scattered across RAM through a page table. PagedAttention applies the same trick to the KV:

block
a fixed-size page that holds the KV of block_size consecutive tokens of a request, across all layers of a group. Each block has an ID in the BlockPool, the owner of every physical block.
block table
each request's block table, which lists the physical IDs in logical order. Tokens 0…B−1 live in the ID at position 0, tokens B…2B−1 in the ID at position 1, and so on.
slot
the physical address of a token: ID × block_size + offset. At every step vLLM computes the slot mapping of the tokens about to be written.
null block
ID 0, reserved as a marker (null block). It never holds data. Unused table positions, and blocks that have already left a sliding window, point to it.
\[ n_{\text{blocks}}(L) = \left\lceil \frac{L}{B} \right\rceil \] \[ \text{slot}(r, t) = T[r,\ \lfloor t/B \rfloor]\cdot B + (t \bmod B) \] \[ \text{leftover}(L) = B\left\lceil \frac{L}{B} \right\rceil - L \le B - 1 \]
  • \(L\): tokens the request currently has (grows at every step)
  • \(B\): block_size, tokens per block
  • \(T[r, j]\): the physical ID stored at position \(j\) of request \(r\)'s table
  • \(t\): logical position of the token within the request
  • leftover: empty places in the last block, the only fragmentation that remains (per request and per group)

A step has two halves. In the write, a kernel (reshape_and_cache for regular attention, concat_and_cache_mla for MLA) takes the freshly computed K and V and stores them in the slots of the slot mapping. In the read, the paged attention kernel walks the request's table, block by block, and loads the KV of each ID. The request never needs contiguous memory.

Blocks are created on demand. When a request's last block fills up, the next token asks the free queue for a new block (allocate_slots). When the request finishes, its blocks go back to the pool. Follow the cycle step by step with two requests and 4-token blocks.

Three details of the figure come back throughout the chapter. A's blocks (1, 2 and 5) are not neighbors, and that costs attention nothing, because the kernel just follows the table. A's waste is only the end of block 5. And two tables can point to the same block: that's how prefix caching shares the KV of a common prompt, with a reference count on each block.

Why the indirection is cheap

For each block, the kernel does one extra read (the ID in the table) and then reads B contiguous tokens inside the page. With MLA at 656 B per token, a 16-token block already has 10,496 contiguous bytes (our math), enough for coalesced reads. With blocks that are too small, the table lookups start to add up. That's why kernels fix a page size: GLM's sparse-MLA kernels on SM12x were compiled for 64 tokens per page (kernels chapter).

No block table, a segment table instead

In TensorFold, a request's kernels read the KV as if it were a tensor of its own: a contiguous view of its range in the pool, with no per-block lookup. When several requests are verified in the same forward, each kernel gets a small table on the device (SegRows). Per row, it holds the position, the range's base, the segment and whether the row is dense or sparse. Per segment, it holds the start, the number of rows, the pooled keys' base (base/4) and how many pools the last row sees. That's one entry per request, not per block. Because the table lives on the device, a single CUDA graph per window width serves any mix of requests (CUDA graphs chapter).

What “one row” means in each recipe

What a slot holds depends on the model and on the KV dtype (quantized KV chapter). In GLM, one token of one MLA layer takes 656 B (fp8_ds_mla). In DeepSeek, the row is 584 B and the compressed layers store one row every 4 or 128 tokens. In Qwen, each TP2 GPU stores K and V for one 256-dimension head per layer: 1,024 B in BF16 and 512 B in FP8. Paging is the same in all three cases. What changes is what fits in each page.

Translating indices without falling off the map

Every paged read starts with a translation: which physical slot holds the token at logical position t of this request? In dense attention, the kernel itself does the math. In sparse attention, the indexer returns a list of chosen local positions (the top-k), and someone has to convert them into global slots before the read. The conversion is tiny and runs millions of times per second. An out-of-bounds index there turns into a read or a write in another request's memory.

\[ \text{addr}(T[r, j]) = r\cdot S + j \] \[ j \ge S \;\Rightarrow\; \text{addr} = (r+1)\cdot S + (j - S) \]
  • \(S\): width of a table row (block_table_stride), the maximum number of blocks per request in that group
  • \(r\cdot S + j\): a batch's table is a matrix stored row after row (row-major)
  • if \(j\) runs past the end of the row, there is no error: the address lands in request \(r+1\)'s row

DeepSeek: the conversion with guards

DeepSeek's C4A layers read the indices chosen by the indexer and need to convert them into slots. Before looking at the code, a word about where it comes from. The DeepSeek repository has three runtime lanes, that is, three ways of assembling the vLLM that serves the model. Lane A, the default, uses the Anemll image dspark-vllm-gx10:0.1.1 and applies hotfixes when the container boots; its sparse-MLA code is not in the repo. Lane B, the Stage-C overlay, copies whole files into another image and is historical/optional, but it is the only one with the complete code in the repo, so it serves as the reading reference. Lane C is an experiment on vLLM main. What follows is the Stage-C overlay code (lane B). In lane A, #133 comes in through patches/hotfix-dsv4-issue133-triton-specialization.py and #50298 through the v0.27 hotfix train. The inventory records that lane A incorporated logic equivalent to the overlay's, organized differently, but that code is not in the repo.

The Stage-C overlay ships compute_global_topk_indices_and_lens (cache_utils.py:391-499), a Triton kernel that fuses three operations: the table lookup (local index → global slot), counting the valid entries per token, and zeroing the length of padding tokens. Before reading, it runs three bounds checks:

  1. Valid token. Padding tokens (is_valid_token = 0) leave stale entries in the persistent top-k buffer, and those entries must not drive the read.
  2. Inside the row. block_indices < block_table_stride: a stale index may point past the request's row.
  3. Inside the pool. 0 ≤ block_numbers < num_blocks: an old or unallocated entry may point to a block that doesn't exist.

An entry that fails becomes −1 and is dropped, instead of turning into an out-of-bounds gather (IMA, illegal memory access). The overlay also fixes how Triton specializes this kernel (#133; see the CUDA graphs and warmup chapter). And where do stale entries come from? From reused buffers. The top-k buffer and the tables have fixed shapes so they fit in the CUDA graphs, and the positions the current step doesn't use keep whatever the previous step left there.

GLM: the one-block ring

GLM's indexer works with pools of 4 tokens (index_kpool=4). Until 4 tokens complete a pool, the last 1 to 3 sit in a tail that is not compressed yet. GLM's vLLM keeps that tail in a KV group of its own, the KpoolTail: a single block of 4 positions per request, used as a ring. The request's row in that group has width 1. The generic slot-mapping kernel computed block_table[req, pos // block_size] without clamping the index. For pos ≥ 4, it read past the only entry, and the kpool seed and update kernels wrote through a wrong ID. In generations of about 2,000 tokens, this crashed the process or, worse, silently corrupted the indexer of another layer.

patch_kpool_tail_slotmap.py changes a single line: block_indices = tl.minimum(block_indices, block_table_stride - 1). In the KpoolTail, with width 1, the slot becomes block_table[req, 0] × 4 + pos mod 4, the intended ring. In the other groups the clamp changes nothing, because a request never needs more blocks than its row can hold.

In DeepSeek mode, drag to logical block 2: the stale entry 14 doesn't exist in a pool of 12 blocks, and guard 3 drops the index. Further right, guard 2 prevents reading the neighboring row. In GLM mode, turn off the clamp and watch position 4 write into another request's block.

Finishing cleanly proves nothing

The KpoolTail patch documentation warns: a request that finished normally does not prove that its writes stayed within bounds. Most overflows land inside the shared pool and corrupt another request's KV without any error at all. The sibling bug, fixed by patch_kpool_tail_seed_stride.py (a backport of vLLM #57477), was a stride bug: the tail is an as_strided view of the indexer page (118,272 B between blocks, with the 3,584-token block), and the seed kernel treated it as a dense 2,048 B array. Every prefill wrote the tail into another request's indexer blocks. When a cache is a view, pass the real strides.

The tail is also a special case for prefix caching. It is scratch space for a single request and can never be reused: KpoolTailManager.cache_blocks returns immediately, without storing any hash. When a request hits a cached prefix, the ring starts empty, and reseeding it with less than a full pool would change which blocks sparse attention picks. That's why patch_hybrid_prefix_hit.py backs the hit off until at least 4 fresh tokens are left (the KpoolTail's block_size), which are recomputed and rebuild the tail before decode (marker [glm53-kpool-replay-floor-v1]).

The block size: the grain of everything

block_size looks like an implementation detail, but it is the grain of four things at once:

🧩

Waste

On average \((B-1)/2\) places are left over in each request's last block, in each group. Big block, big leftover.

📒

Tables

Each request may need \(\lceil L_{\max}/B \rceil\) entries. For Qwen at 1M, with the default block of 1,664, that's 601 entries (625 with the 1,600-token blocks of the BF16 KV).

⚙️

Kernel

Bigger pages mean fewer table lookups, but the kernel only runs with the page sizes it was compiled for.

♻️

Prefix cache

The hash is computed per full block. A hit can only stop at a block boundary, and the last token is always recomputed.

\[ \overline{\text{leftover}} \approx \frac{B-1}{2}, \qquad E = \left\lceil \frac{L_{\max}}{B} \right\rceil \] \[ h(n) = B\left\lfloor \frac{n-1}{B} \right\rfloor \]
  • \(\overline{\text{leftover}}\): expected empty places in the last block (assuming lengths that are “random” with respect to \(B\))
  • \(E\): table entries of a request at the ceiling \(L_{\max}\) = max_model_len
  • \(h(n)\): tokens reused when an \(n\)-token prompt with the same prefix comes back; the \(n-1\) is there because the last token has to be recomputed to produce the logits

vLLM's default is 16 tokens when the backend doesn't impose another value. All three recipes depart from it, each for its own reason. In the figure, pick a block size and a request length and compare the four consequences.

With 16 tokens the leftover is negligible, but the table of a 1M request has 62,500 entries. With 3,584 the table shrinks to 280 entries, and a resent 8,004-token prompt only reuses 7,168. That is exactly the number GLM measures in its follow-ups (prefix caching chapter).

Manager block × kernel block

There are two block sizes in play. The manager's is the allocation grain: how many tokens one block ID covers. The kernel's is the page size the attention kernel was compiled with. They can differ. The worker splits each manager block into several “virtual” kernel blocks (in the code, BLOCKS_PER_KV_BLOCK) and recomputes the addresses.

In GLM the difference is huge. All of FlashInfer's GLM_NSA/DSV3_2 sparse-MLA kernels on SM12x are instantiated with a 64-token page (PAGE_BLOCK_SIZE=64). The MLA manager uses 3,584-token blocks (the next section shows where that number comes from), so each ID covers 56 kernel pages. To make that math work on SM12x, the recipe's Dockerfile edits platforms/cuda.py and get_supported_kernel_block_sizes:

  • DeepGEMM paged-MQA, used by the indexer, only accepts block_kv 64 on sm_120, but vLLM assumed (32, 64). The indexer's storage block is block_size ÷ index_kpool. With an alignment of 4 × 32 = 128, the hybrid block landed on 1,664 tokens, or 416 entries, which is not a multiple of 64: the page became 32 and DeepGEMM aborted on an assert. With an alignment of index_kpool × 64 = 256, the block goes up to 1,792 (448 entries, divisible by 64).
  • The backend declared kernel sizes [64, 256]. The selector walks that list in descending order and, with a 1,792 block, would pick 256, which no GLM_NSA kernel implements. With capability.major == 12, the backend now declares only [64].

The values 1,664 and 1,792 come from the alignment chain described in the Dockerfile comment. In the current geometry, the KDA state pushes the block to 3,584, which is also a multiple of 256.

Don't split a padded page

When a group uses a padded page (page_size_padded larger than B × bytes per token, like GLM's drafter further on), the physical stride between blocks applies once per manager block. The virtual split assumes dense kernel blocks inside the page and would compute addresses beyond it. The guard that patch_glm5_drafter_group.py adds to v1/worker/utils.py forbids splitting padded pages, so the backend has to support the whole block (FLASH_ATTN declares multiples of 16).

The scheduler block: the LCM of the groups

When there are groups with different block sizes, the coordinator aligns cache hits and state checkpoints to the least common multiple of the block sizes, the so-called scheduler block. In GLM, the LCM of 3,584, 4, 3,584 and 64 is 3,584. In DeepSeek, the LCM of 256, 64, 4 and 8 is 256. That's why GLM's hits come in multiples of 3,584 (7,168, 10,752 and 14,336 tokens are 2, 3 and 4 pages) and why DeepSeek's --block-size 256 is also the grain of the prefix hash: in case #144, a 4,646-token prompt had 18 shareable blocks.

Another engine, another ruler

TensorFold has no LCM of groups, because there is no uniform page to align. The allocation grain is the 2,048-token ALIGN of the pool's ranges. Prompt reuse uses a third ruler: prompt states sit on a 64-token grid (at the prompt's last multiple of 64 and, for an identical resend, also at its exact end), not on 3,584-token boundaries (prefix caching chapter).

One pool, many layer types: the hybrid KV

All three recipes serve models that mix layer types (sparse attention and linear attention). Each type spends memory in its own way:

Each group has its own manager (SingleTypeKVCacheManager), its own allocation and caching rules, and its own block table per request. A coordinator (KVCacheCoordinator) orchestrates the managers, and they all take IDs from a single BlockPool, with globally unique IDs. This whole setup is the hybrid KV allocator.

The uniform page rule

For an ID freed by one group to serve any other, every group needs pages of the same size in bytes. And memory is organized in shared tensors: each KV tensor is shared by one layer from each group, and ID b of a group occupies page b in the tensors of that group's layers. An ID costs the same, whichever group holds it.

The problem shows up when the types have very different natural sizes. The state of a KDA or GDN layer is an entire matrix per request, millions of bytes. A 16-token attention page is a few KB. vLLM solves this by increasing the attention block size until the attention page catches up with the state, and pads the state up to the page size:

\[ B_{\text{att}} = \operatorname{align}_{a}\!\left(\left\lceil \frac{S_{\text{state}}}{b_{\text{tok}}} \right\rceil\right) \] \[ P = B_{\text{att}}\cdot b_{\text{tok}} \ge S_{\text{state}} \] \[ c_{\text{ID}} = \sum_{t\,\in\,\text{tensors}} P_t, \qquad M_{KV} = N\cdot c_{\text{ID}} \]
  • \(S_{\text{state}}\): bytes of one layer's recurrent state, per request and per rank (state + conv)
  • \(b_{\text{tok}}\): bytes of attention KV per token, per layer and per rank
  • \(a\): alignment required by the kernels (256 in GLM because of the indexer; 16 in Qwen, judging by the math)
  • \(P\): the page shared by all groups
  • \(P_t\): the page of KV tensor \(t\) (equal to \(P\) in the tensors the groups share; tensors that belong to a single group, like GLM's indexer ones, may have their own page)
  • \(c_{\text{ID}}\): bytes of one ID, the sum of the pages of all tensors; the pool charges this whichever group holds the ID. \(N\): number of IDs in the pool

In the figure, pick a model and watch the attention block grow until the page catches up with the state.

GLM shows the mechanism most clearly. The KDA state per layer and per rank at TP2 is 2,342,912 B: 2,097,152 of recurrent state [32 heads, 128, 128] in FP32 plus 245,760 of conv state in BF16. Dividing by 656 B per token gives 3,571.5 tokens, and the next multiple of 256 is 3,584. The page comes out to 3,584 × 656 = 2,351,104 B, the mla_page=2351104 that the boot log prints.

In Qwen, the KV dtype and the state dtype change the block. Per GPU at TP2, the GDN page has 1,572,864 B of recurrent state (24 × 128 × 128 in FP32) plus 61,440 B of conv state (5,120 × 6 in BF16), 1,634,304 B in total. With a BF16 KV (1,024 B/token), ⌈1,634,304 ÷ 1,024⌉ = 1,596, aligned to 16: a 1,600-token block, the README's value (:380-381). With the FP8 KV, which is the default (512 B/token), the same math gives 3,200. The README still says 1,600 in the FP8 boot paragraph, so check your own boot log. With MAMBA_SSM_CACHE_DTYPE=bfloat16 (the .env.sample default, which start.sh passes as --mamba-ssm-cache-dtype; without it the state stays in the checkpoint's FP32), the recurrent state drops to 786,432 B, the GDN page to 847,872 B and, with an FP8 KV, the block goes to 1,664. That is the value in patch_block_drop.py (:7-8), and .env.sample:74 records the same change, “3,200 → 1,664”, in the single-node recipe. With a BF16 KV and BF16 state it would be 832 tokens (our math). The state dtype also shows up in capacity: in the Sep 16 re-run, with FP8 KV and BF16 state, the boot showed 4,378,829 tokens, 16.70× at 262k (docs/bench/rerun-20260916.md), versus the 3,652,200 of the boot with FP32 state and a gpu_memory_utilization (GMU, the fraction of memory vLLM may budget; next section) of 0.835. The re-run doesn't record the GMU, so don't attribute the whole difference to the state.

In DeepSeek the constraint comes from elsewhere. The sliding-window page (64 tokens × 584 B = 37,376 B) is fixed by the C++ op that writes those rows. The C4 group, with one row every 4 tokens, needs 64 rows to fill the same page, and 64 × 4 = 256: hence the --block-size 256. The drafter's SWA groups use 4- and 8-token blocks with the same page in bytes. The repository doesn't document which group the C128A layers go into.

Now look inside GLM's pool. It has 22 KV tensors. Eleven have 2,351,104 B MLA pages, one per MLA layer, and are shared: the Mamba groups and the drafter store their pages in them. The other eleven belong to the indexer, one per MLA layer, with pages of 896 entries × 132 B = 118,272 B (~5% of the MLA page). vLLM's group 0 is a UniformTypeKVCacheSpecs with the 11 MLA layers and the 11 indexer layers, so one pool ID reserves both. In the figure below, each thick floor of the building is an MLA tensor, the thin floors at the top are the indexer tensors, and each column is a block ID. An ID runs through the whole building: the group that holds it uses one page in each tensor of its layers and pays for the rest.

That's why the cost of one ID, in GLM, is \(c_{\text{ID}} = 11 \times 2{,}351{,}104 + 11 \times 118{,}272 = 27{,}163{,}136\) B ≈ 25.9 MiB, and not just the 11 MLA pages. Sanity check: 643 IDs × 25.9 MiB ≈ 16.3 GiB, close to the 16.4–17.09 GiB of Available KV cache memory that the boots of that night printed (the number of IDs isn't logged, and the recipe's design doc doesn't account for the exact gap). If you forget the indexer, you divide 16.75 GiB by the MLA pages alone and get ~695 IDs, the physical ceiling that the design doc itself uses as an upper bound.

The tenant drafter: padded slot-share

GLM's DFlash2 drafter (DFlash2 and DSpark chapter) has 5 sliding-window layers with a BF16 KV, 2,048 B per token and per layer at TP2, and a 2,048-token window. The MLA page holds exactly 2,351,104 ÷ 2,048 = 1,148 draft tokens, but exact-fit mode demands two more things from that block: being a multiple of 64, so it splits cleanly into the 16-, 32- or 64-token kernel blocks that the SWA backends register, and being compatible with the 3,584 MLA block (one dividing the other), so the scheduler's LCM doesn't blow up. 1,148 fails both, and patch_glm5_drafter_group.py (:114-128) falls back to plan B: it creates an extra SlidingWindowSpec group, appended last, in padded slot-share mode: block_size=64, page_size_padded = mla_page, and drafter layer i co-owns MLA tensor i on disjoint IDs, just like the Mamba groups do. The boot confirms it: padded slot-share block=64 mla_page=2351104.

Slot-share doesn't add a single byte to the pool, but it charges one ID (priced as a full MLA page) for every 64 draft tokens. The tenant pays apartment rent to store a suitcase. Before it, inheriting the MLA manager's block (1,152 and later 3,584 tokens) made each of the 5 layers cost tens of MiB per block. With slot-share, a ~36k-token prompt took up ~16% of the pool, versus 44.6% in the compact-64 variant without slot-share, where each of the 5 layers had its own set of IDs.

The next step is compact pages (GLM53_DRAFT_KV_COMPACT=1, the default with SPEC_METHOD=dflash). The function _glm53_draft_block_size picks as the drafter block the largest multiple of 64 that divides the MLA block and fits in the physical page. At TP2: 896 × 2,048 = 1,835,008 B ≤ 2,351,104 B, and 896 divides 3,584. At TP3, with a 1,679,360 B page, a 2,560 MLA block and 1,536 B per token, it comes out to 640. Before switching on, the patch checks that every SWA layer belongs to the DFlash drafter. The effect is purely an accounting one. The drafter's admission quota drops from 65 to 6 IDs per request. The math is \(\lceil (W - 1 + \text{in flight}) / B \rceil + 1\), where W is the window and “in flight” are the tokens the scheduler has already dispatched and whose step hasn't finished yet. The allocator's CPU test uses 2,048 in flight: \(\lceil 4{,}095/64 \rceil + 1 = 65\) and \(\lceil 4{,}095/896 \rceil + 1 = 6\). And the IDs reserved per maximum-length request dropped from 180 to 121 (−32.78%) in qualification. Repeating a 28,672-token prefix with a 64-token tail went from 2.623 s to 0.302 s of TTFT. The repository itself stresses that this is not a measured VRAM reduction.

Why it matters: IDs are the currency

In a hybrid model, the bottleneck is usually the number of block IDs, not the bytes per token. Each ID costs one page in every tensor, even when the group holding it fills 6% of it. That's why GLM warns: don't lower MAX_MODEL_LEN to 256k hoping to “free up slots”. The ID demand of Mamba and of the drafter's window barely depends on length, and the hybrid ID overhead shrinks the pool.

The other way to pay for the state: slots

TensorFold separates the two kinds of memory that vLLM forces to share a page. What grows with the context (the latent of the 11 DSA layers and the indexer's pooled keys) lives in a pool of per-token rows. What is fixed per stream lives in a slot, allocated at startup: the KDA state [slots, 2, layers, H, 128, 128] in FP32, with two parities, the convolution windows and the verify window's scratch. The DFlash2 drafter's context sits in a ring of 2,176 rows, 21 MiB per rank whatever the window. Nobody pays an apartment's rent to store a suitcase. In exchange, the number of slots is fixed: the recipe uses 4 (PARALLEL=4), and each extra slot costs ≈177 MiB per rank (the research's math from engine.slot_bytes).

How much is left for the KV: profile run, workspaces and the byte pin

Before creating the pool, vLLM needs to know how many bytes it can give it. The answer comes from the profile run, a fixed sequence of measurements when each worker boots:

  1. Load the weights. The log prints Model loading took X GiB.
  2. Dummy pass. A fake forward with the largest possible batch (max_num_batched_tokens, which the recipes abbreviate as MNBT: the maximum number of tokens one scheduler step processes) measures PyTorch's activation peak and the memory outside PyTorch (CUDA context, NCCL buffers and the like).
  3. Workspaces. Kernel scratch buffers grow to the largest size requested during the dummy pass. Then the workspace manager is locked (lock_workspace()): no new buffer can be created, and allocating during CUDA graph capture is forbidden.
  4. CUDA graph estimate. With VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=1 (the default since v0.21), a rehearsal capture estimates the graphs' memory and subtracts it.
  5. The rest becomes KV. The pool is split into IDs and allocated, and only then are the real graphs captured.
\[ M_{KV} = u\cdot M_{\text{total}} - W - M_{\text{non-torch}} - A_{\text{peak}} - G_{\text{est}} \] \[ N = \left\lfloor \frac{M_{KV}}{c_{\text{ID}}} \right\rfloor = \left\lfloor \frac{M_{KV}}{\sum_t P_t} \right\rfloor, \qquad N_{\text{usable}} = N - 1 \]
  • \(u\): --gpu-memory-utilization; \(M_{\text{total}}\): the memory CUDA sees (≈121.7 GiB per Spark, in unified memory)
  • \(W\): weights; \(A_{\text{peak}}\): peak of the dummy pass, workspaces included; \(G_{\text{est}}\): graph estimate (zero if disabled)
  • \(c_{\text{ID}} = \sum_t P_t\): bytes of one ID, adding up the pages of all tensors (in GLM, 11 MLA + 11 indexer ≈ 25.9 MiB); the \(-1\) is the null block

With --kv-cache-memory-bytes the first equation goes away: \(M_{KV}\) is the number you passed (a fixed pool), and gpu_memory_utilization no longer applies to the KV. With TP, each rank measures its own. Interpretation of the mechanism: since every rank needs the same number of blocks, vLLM unifies the workers' configs using the smallest number of blocks, so the tightest rank sets the limit. There is also a check at the end: if the pool can't hold even one request of max_model_len tokens, the boot fails. In GLM, that happens after 5 to 9 minutes, with the weights already loaded.

Qwen publishes the budget of one node at a GMU (gpu_memory_utilization, the \(u\) in the equation) of 0.835 (the gpu_worker.py table): 121.69 GiB visible, 108.79 free at the start, 101.61 budgeted, 64.46 GiB of weights (68.52 with the memory outside PyTorch), an activation peak of 1.07 GiB, 0.54 GiB of CUDA graphs and 32.02 GiB of KV. The math closes like this: 101.61 − 68.52 − 1.07 = 32.02. In this boot the graphs show up in the table but are not part of the deduction (our observation, from the numbers). Build your own budget in the figure.

The Model loading took 79.65 GiB is identical in both cases, and the difference only shows up in Available KV cache memory. Workspaces: memory the KV never sees

Every buffer that exists during the dummy pass comes out of the KV, so an oversized workspace is context thrown away. Four cases show up in the recipes, and the sparse attention chapter details the indexer ones.

  • GLM's indexer workspace. The stock code sizes the prefill gather as max_model_len × 40 entries of 132 B: 5,036.40 MiB locked at 1M, a value measured with VLLM_DEBUG_WORKSPACE=1. The rightsize mode computes min(max_num_seqs, MNBT) × cdiv(max_model_len + k, compress_ratio): 125.9 MiB with 4 sequences, which gives back ~26–28% of KV.
  • E3 scratch. The grouped EXL3 kernel (EXL3_FAT_GROUPED=1) keeps a 560 MiB scratch that the profile run charges to the KV. With it, at 1M and util 0.87, the pool can no longer hold a 1M request, which needs 14.52 GiB with MNBT 7168.
  • FlashKDA buffers. At TP3, with HAREM_KDA_FLASHKDA=1 (patch_flashkda_tp3.py), the fused KDA prefill kernel preallocates its buffers in the workspace manager, with capacity guards, so it can run inside CUDA graphs. They come out of the KV like all the others.
  • Graph estimate. In GLM the estimate comes to 2.43 GiB, while the captured graphs consume −0.19 GiB. With CG_ESTIMATE=0 (which becomes VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=0) ~2.6 GiB go back to the KV with graphs still on, and patch_skip_cudagraph_profile.py also skips the rehearsal capture (11 s of boot). The recipe's default stays at 1, the upstream value. DeepSeek turns the estimate off (VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=0). Reading the inventory, this avoids undersizing the KV because of a conservative estimate.

DeepSeek shows the other side of the workspace manager contract. In the Stage-C overlay (lane B, the readable code), the SM120 backend (sm120.py) borrows the split-K scratch (mid_out, mid_lse) from the shared workspace and reserves it in the dummy path, so the buffer grows before lock_workspace(). The #50298 backport, which the default lane applies at boot with the v0.27 hotfix train, requests the combined index buffers (top-k + window) via get_simultaneous for the same reason, and the workspace now includes max_num_batched_tokens × combined_topk × 4 B. A buffer that only showed up after the lock would break graph capture.

Reading the boot: capacity, concurrency and ceilings

Once the profile run is done, vLLM prints three numbers. Available KV cache memory is \(M_{KV}\) in GiB. The other two lines come from a single calculation, done in kv_cache_utils.py:

\[ c_{\max} = \frac{N}{\displaystyle\sum_{g} \left\lceil \frac{\text{mem}_g(L_{\max})}{P} \right\rceil} \] \[ \texttt{GPU KV cache size} = \big\lfloor c_{\max}\cdot L_{\max} \big\rfloor \]
  • \(c_{\max}\): the maximum concurrency, printed as Maximum concurrency … X x
  • \(\text{mem}_g(L_{\max})\): the max_memory_usage_bytes of group \(g\), the memory a request of \(L_{\max}\) = max_model_len tokens takes in it at peak; divided by the page, it becomes IDs, and the denominator adds up the IDs of all groups
  • in a single-group model, the token line is ≈ \(N\cdot B\), the size of the pool; in a hybrid, it is concurrency in token units

In DeepSeek and Qwen, the token line reads almost like the pool size, with the caveat from the quantized KV chapter: it is allocator accounting, not physical cost. In DeepSeek, 17.04 GiB ÷ 2,331,430 tokens gives 7.8 KB per token, versus ~3.85 KB of physical cost. In Qwen FP8, 32.02 GiB ÷ 3,652,200 tokens gives 9,418 B per token and per GPU, 41% above the 6,656 B of pure attention (13 layers × 512 B): the GDN state and the QSA index (in BF16) don't shrink with the FP8 KV, and page rounding adds to it (README :376). That is also why the FP8 pool grows 1.70× in tokens, not 2×. In GLM the line is genuinely misleading. Follow the math of the Aug 31 boot.

Where the 9 and the 97 come from

Mamba in align mode: 2 + k pages. The manager keeps the current state, the previous state (which a step still in flight may be copying to its successor) and one state per speculative token, so it can roll back to the point where verification stops accepting drafts. With DFlash2's k = 7 speculative tokens, that's 2 + 7 = 9 pages per group (kv_cache_interface.py:818-819). patch_mamba_align_state_free.py, which came after this boot, now reserves 1 + max_concurrent_batches + k (10 with async scheduling), because a replaced state can only be freed after the step that reads it finishes. Your boot may show a different total.

In-flight tokens. These are the tokens the scheduler has already dispatched and whose step hasn't finished yet. With async scheduling, vLLM keeps up to max_concurrent_batches = 2 batches in flight, each with up to MNBT tokens: 2 × 2,048 = 4,096 in the Aug 31 boot. The drafter's window has to cover the previous 2,047 tokens plus those 4,096: ⌈6,143/64⌉ + 1 = 97 (the +1 covers a window that doesn't start on a block boundary).

Peak × admission. The 97 is the peak the boot uses (max_memory_usage_bytes, with two batches in flight). The 65 → 6 from the previous section is the admission quota that the allocator's CPU test computes with a single batch (2,048 in flight). Same formula, different inputs. By the same formula, at 1M with MNBT 7168 the drafter asks for ⌈(2,047 + 2 × 7,168)/64⌉ + 1 = 257 IDs (our math), a number that comes back in the section on ceilings.

The lesson of step 5 is that the 643-ID pool holds about 57 thousand tokens of conversation with nothing running, not 1.5 million. Two independent reviewers read the line as 1.5M of prefix cache before anyone redid the math. That's why the recipe includes patch_kv_capacity_log.py (overlay #12, applied after patch_glm5_drafter_group.py), controlled by GLM53_KV_CAPACITY_LOG=1 (default; 0 turns it off, any other value is rejected). It leaves the stock line byte-for-byte identical and adds one line per group (type, block size, page, IDs per request, whether it takes part in the prefix cache) plus a summary: usable IDs (num_blocks − 1), IDs per segment and conversation capacity. It is logging only and changes no allocation at all. Stock vLLM logs neither num_blocks nor the IDs per request (open request in vllm#54662). The numbers change from boot to boot. In the current boot, with the rightsize workspace, it's 820 IDs, 1.98× and ~75,264 tokens (21 segments). Read your own boot's summary, not a number from a README.

Ceilings, not reservations

--max-model-len and --max-num-seqs are ceilings. vLLM doesn't reserve 6 × 1M for six slots. It allocates blocks on demand, admits a request if there are blocks for the tokens it is about to process and, when the pool runs out, queues or preempts. The constraint that actually holds is

\[ \sum_{r\ \in\ \text{live}} L_r \;\lesssim\; C_{\text{pool}} \] \[ \#\{\text{live}\} \le \texttt{max\_num\_seqs}, \qquad L_r \le \texttt{max\_model\_len} \]
  • \(L_r\): the tokens request \(r\) has right now (prompt already processed + output)
  • \(C_{\text{pool}}\): the pool in tokens (2,331,430 in DeepSeek; 3,652,200 in Qwen FP8 at 0.835)
  • the “≲” is a reminder that the pool is counted in blocks and that hybrid models pay fixed IDs per request

The examples from DeepSeek's README are on the buttons: 6 × 50k = 300k fit with room to spare; 6 × 200k = 1.2M fit; 6 × 500k = 3.0M sit near or above the pool; 6 × 1M = 6.0M is impossible, and the extra ones wait. The “2.22×” only says that about two whole 1M requests fit at the same time. Switch to Qwen: with 13.93× at 262,144 tokens and MAX_NUM_SEQS=8, the limit is the turnstile, not the tank. With MAX_MODEL_LEN=1000000 × MAX_NUM_SEQS=8 the old .env asked a smaller pool for 8M tokens: vLLM doesn't OOM, but only ~2 requests of 1M stay resident, and from the third one on they get preempted and redo the prefill. Hence the README's profile table: deep-context sequential (1M, 2 sequences), 1M with concurrency (42.38 GiB pin, 3 sequences), throughput/agentic (262,144, 8) and middle ground (512,000, 4).

GLM was left out of the figure on purpose. There, each request pays fixed IDs (4 Mamba groups × 9, the KpoolTail ring, the drafter's window) that don't depend on \(L\), so the sum of tokens doesn't describe occupancy. For short requests, the fixed cost dominates.

What the ceiling still costs

Being a ceiling doesn't mean being free. max_model_len has three costs even when every prompt is short:

  1. The boot demands one whole request. The pool must hold at least one request of max_model_len. In GLM, 1M asks for 14.52 GiB of KV with MNBT 7168 (~7.4 GiB fixed + 7.1 GiB per 1M), and 500k asks for 10.98 GiB. Update: extents and free memory in TensorFold

Everything so far is vLLM. The GLM recipe now has a second version , which serves the same EXL3 checkpoint on the same two Sparks with another engine: TensorFold v0.6.0 plus 53 patches. TensorFold is written per model family, and GLM gets its own two-rank CUDA engine, one rank per Spark, with kernels, cache and verification built for it (exact engine chapter). The whole recipe is in the GLM on TensorFold recipe chapter. This engine has no PagedAttention, no block table and no profile run. It answers this chapter's two questions differently, where to keep a KV that grows without warning and how many bytes to give it, and it starts from other conditions: at most 4 requests at a time in v1.3.2 (1 to 8 since v1.5, patch 0069), each with a window of up to 1,048,576 tokens.

Per-token planes, per-stream slots

The first step is to separate what grows with the context from what doesn't. In vLLM, the KDA state, the MLA latent and the drafter's window draw IDs from the same pool, and the uniform page rule takes the block to 3,584 tokens. In TensorFold, everything that grows with the context becomes a plane of a shared arena: a tensor with one row per token (the latent of each DSA layer) or one row every 4 tokens (the indexer's pooled keys). What has a fixed size per stream stays outside the arena, in a slot: the KDA recurrent state in two parities, the convolution windows and the verify window's scratch. Since the state never shares a page with the latent, there is no uniform page to respect, and the pool's grain depends only on what the attention kernels need.

What goes in each row shrank too. With KV=fp8, a token's latent in one DSA layer takes 528 B (512 e4m3 codes, a 4 B power-of-two scale and 12 B of alignment), and the indexer's pooled keys take 144 B per pool of 4 tokens. Per layer that's ≈564 B per token, against 656 + 33 = 689 B in vLLM, and across the 11 DSA layers it comes to ≈6.2 KB per token per rank (the research's math from the code; the quantized KV chapter explains the scale). The latent is not split between ranks: each Spark keeps every token's whole latent.

Extents: ranges that grow, move and get compacted

The arena is cut into extents, contiguous ranges [base, base + size) of rows whose base and size are multiples of ALIGN = 2048 tokens. Each live stream owns an extent. Kept prompts live in extents too, and one extent can hold several kept prompts that are prefixes of one another. Single-stream code (prefill, decode window, snapshots) runs on views of its extent “exactly as on tensors of its own”: the kernels read contiguous rows and consult no table at all. The code justifies the alignment by the pooled keys, which start at base/4. An extent's view of that plane reaches 2 rows past its end, because token selection reads up to 2 pools past a window (the whole plane gets 2 extra rows at the end). Those 2 rows are the first rows of the next extent, so they are only ever read and masked, never written.

\[ \text{need}(p) = 2048\left\lceil \frac{p + 16}{2048} \right\rceil \] \[ \text{admit}(p) \iff F + K \ge \text{need}(p) + 2048\cdot n_{\text{dec}} \]
  • \(p\): prompt tokens; the 16 is a stream's widest verify window (MAX_ROWS: the pending token and up to 15 drafts)
  • \(F\): the pool's free rows; \(K\): rows of extents that only hold kept prompts and can be evicted
  • \(n_{\text{dec}}\): decoding streams; each gets a 2,048 block of headroom to grow into

Whoever fails the test waits, in arrival order. Once admitted, the stream gets a slot and an extent, and rank 0 follows a fixed sequence of rules whenever it needs room:

  1. Place. Lowest-base first fit: the first hole, from the start of the pool, where the extent fits.
  2. Grow. Every decode round, each stream's extent must cover the current position plus the widest window. If the rows right after it are free, it grows in place (GROW).
  3. Move. Otherwise, the whole extent goes to a hole where it fits (MOVE). Only the used rows are copied, in pieces that never read a row already overwritten when source and destination overlap.
  4. Evict. Out of room? Kept prompts give way first, least recently used first (LRU), and never the ones the operation protects.
  5. Compact. If there are enough free rows in total but no hole fits, every extent slides down and the free space becomes a single range, through a series of MOVEs. That's compaction.
  6. Pause and give back. If it still doesn't fit, the stream is paused for that round. If every decoding stream is paused and nobody is filling a prompt, the youngest one without a grammar or images gives back its slot and extent and returns to the queue. Later it redoes its prompt, and the tokens already sent “are owed, not sent again”. It's preemption by recomputation, safe because keyed sampling reproduces the same tokens (next chapter). If every stream has a grammar or images, the youngest fails with NoRoom.

That is the v1.3.2 order. Since v1.6 (patch 0074), steps 4 and 5 swap places: when the free rows add up to the request, the pool compacts first (each extent moves at most once) and evicts only while they fall short. Before, two agents taking turns on a nearly full pool evicted each other's only kept state and re-read 150–210 thousand tokens of history (2–3 minutes) on every turn. With the patch, in the tools/pool_pressure.py test (two Sparks, PARALLEL=8, a deliberately small pool), the other conversation's next turn went from 0% resumed (15.8 s) to 100% (0.6 s). A move is a copy on the GPU; an eviction costs the evicted conversation's whole prefill. Who leaves when the count cap on states overflows has also changed since v1.3.2 (prefix caching chapter).

In the figure the pool is a toy, but the rules are the code's. Let the simulation run, pile up conversations, click a kept prompt to continue that conversation and turn compaction off (ask for a long conversation and wait a little).

Without compaction, sooner or later the queue gets stuck, or a stream pauses, with plenty of free rows, only chopped up: it's the first section's external fragmentation, back again. With it on, evicting kept prompts is usually enough, and compaction only shows up now and then. When it does, a stream changes address without anyone noticing, because the kernels only see the view. Also look at the message column. The pool's bookkeeping runs only on the host and is deterministic. Rank 0 decides everything that depends on time, clients or placement and sends one message per iteration with the operations (ADMIT, EVICT, MOVE, GROW, FILL, ROUND, FINISH…). Rank 1 applies the same calls in the same order, and both pools stay equal without any memory map crossing the cable.

Why it works here, and not in a chat server

Our interpretation. The three kinds of waste from the first section come back at another size. The reserved waste disappears, because the extent starts at the prompt's size and grows round by round. Internal fragmentation stays below one 2,048-token unit per extent, 0.2% of a 1M window. External fragmentation comes back, and it is paid for with copies. With at most 4 streams (8 since v1.5) and a few dozen kept prompts, the extent list is short and compaction copies little, now and then. With hundreds of short requests coming and going, which is the scenario PagedAttention was designed for, the holes and the copies would be constant. In exchange, a stream's kernel is the same single-stream kernel, reading contiguous rows, and the recurrent state doesn't force 3,584-token pages.

After v0.6.0: the native engine went back to pages

Everything in this section is TensorFold v0.6.0, which the GLM·TF recipe still pins. TensorFold was rewritten as a native binary (v1.0.0, 2026-10-07), and there GLM-5.3-Flash on CUDA takes its KV from pages of the core pool by default since 1.1.6, already from two ranks (before, only from three; #1322). Measured by the project at TP=2, two GB10s with the NVFP4 checkpoint: the same tokens, +14% tokens/s with two streams for chat and code, prefill flat to 17% faster. Our interpretation: extents paid off with few streams and an engine for a single family; with more streams and several families sharing a core pool, the page table is worth its cost again, the same math that led vLLM to PagedAttention. On an H200 or a cluster the lesson is the same: the KV grain is an engineering choice that changes with the load, not a dogma.

Budget: free memory minus a reserve, no profile run

The unified memory chapter follows TensorFold's startup phase by phase. What matters here is what it does to the KV pool. TensorFold doesn't measure memory with a dummy pass either: it computes what it will allocate with formulas of the model's geometry (mla_geometry, bytes_at(capacity)) and compares the result with what the operating system says is available at startup. On an integrated GPU like the GB10, the available amount is MemAvailable from /proc/meminfo minus a reserve, because CPU and GPU share a single pool and reclaimable page cache counts as free. On a discrete GPU, it's the smaller of the GPU's and the host's free memory. The default reserve is the larger of 4 GiB and a tenth of RAM, and the recipe uses MEMORY_RESERVE_GIB=14.5. It also covers what the estimate doesn't count: CUDA context, NCCL and workspaces (TensorFold's GLM documentation measured 3.5–4.8 GiB of that, with another checkpoint and a 262,144 window).

\[ B = \texttt{MemAvailable}_{\text{start}} - R \] \[ N_{\text{pool}} = 2048\left\lfloor \frac{C + \max(0,\ G - E\cdot s)/b}{2048} \right\rfloor \]
  • \(B\): a Spark's budget; \(R\): the reserve (TENSORFOLD_MEMORY_RESERVE_GIB, 14.5 GiB in the recipe)
  • \(C\): the window (1,048,576 tokens); \(N_{\text{pool}}\): the pool's rows, a multiple of 2,048; the window is capped at \(N_{\text{pool}} - 16\)
  • \(G\): bytes of pool beyond the window, up to KV_POOL_GIB (the TF_GLM_CACHE_GIB: 12.5 GiB per Spark in the recipe, 3 in TensorFold), cut to what the budget leaves
  • \(E\cdot s\): the fixed reservation for kept prompt states; \(E\) = TF_GLM_CACHE_ENTRIES (32 in the recipe, 8 in TensorFold), ~45 MiB each according to the v1.3.2 CHANGELOG (~91 MiB measured on two Sparks in v1.10, patch 0097)
  • \(b\): bytes per token, taken from the geometry itself (how much the estimate grows over 65,536 tokens, divided by 65,536)

Two consequences for operations follow. The first: a setting that doesn't fit is refused before any weights load, with the largest window that would fit, and start.sh restarts once with it (--context N). The README gives the reason: on the Spark's unified memory, running out tends to freeze the machine rather than fail an allocation. Compare with GLM's vLLM without the byte pin, which only found out that the pool couldn't hold one max_model_len request after 5 to 9 minutes, with the weights loaded. The second: the pool depends on the startup. At the measured start, rank 0's estimate was 88.09 GiB and the pool came out at 2,922,496 tokens, at the 12.5 GiB cap. That's 1,427 extents of 2,048, of which 512 make up a 1M window (our math). Depending on free memory, the README speaks of ~2.1–2.9M tokens. With TensorFold's defaults (a reserve of a tenth of RAM and a 3 GiB cap), the pool is 1,411,072. The vLLM recipe pins 11 GiB and gets 1,233,779 tokens, for 850k windows. The two numbers don't use the same ruler: vLLM's is the stock line, the hybrid allocator's accounting (the “Reading the boot” section shows why it misleads on GLM), and TensorFold's counts physical rows of the pool. Also, the two recipes' measurements come from different dates and configurations, not from a controlled A/B.

The server also uses about 10 GiB beyond its own estimate at its peak, during a 1M prompt. That's why the reserve has a second role: it sets the floor of free memory. With 14.5 GiB, ~4.5–5 GiB are left on the head at the worst moment, according to the README, and the measurement gave 5.6 GiB on rank 0 and 9.5 GiB on rank 1 (7.0 and 10.5 GiB with the server idle). In the figure, put another load on the Spark and see who pays the bill in each engine.

These are two opposite contracts. In vLLM with a pin, the pool is constant and the host's headroom absorbs any variation, down to zero. vLLM's boot check compares MemAvailable with util × MemTotal, not with what the pin will actually allocate (unified memory chapter). In TensorFold, the reserve fixes the headroom's floor and the pool absorbs the variation, until the window no longer fits, and then the boot is refused before the weights. That contract only holds for what was already taken at startup. A load that arrives later comes out of the headroom in both engines, which is why the README asks for a bigger reserve when other work shares the Sparks.

Pool and reserveKV_POOL_GIB=12.5 · MEMORY_RESERVE_GIB=14.5

KV_POOL_GIB becomes TF_GLM_CACHE_GIB, the cap on the pool beyond the window, per Spark (3 GiB in TensorFold). The recipe's v1.2 raised the cap from 11 to 12.5 GiB, and the pool went from 2,684,928 to 2,852,864 tokens. MEMORY_RESERVE_GIB becomes TENSORFOLD_MEMORY_RESERVE_GIB: what the budget leaves free and, as a consequence, the floor of free memory under the worst prompt. Raise the reserve if other work shares the Sparks. TF_GLM_CACHE_ENTRIES=32 (8 in TensorFold) caps the kept prompts: each one reserves ~45 MiB at startup according to the v1.3.2 CHANGELOG (~91 MiB measured in v1.10), and with 8 entries three or four alternating agent conversations kept evicting each other (issue #17). With CONTEXT=0, the window becomes the largest the memory allows, and nothing is left to keep other conversations' prompts. Read your own boot's pool in /health, not the README's.

A recipe for your recipe

After any change to max_model_len, KV dtype, state dtype, number of speculative tokens or workspaces, restart and reread three things: Available KV cache memory, GPU KV cache size / Maximum concurrency and, if present, the per-group summary. Under load, watch kv_cache_usage and preemptions in /metrics, plus the host's MemAvailable. The pool is the pantry.
