Step 0 · Same weights, different engine

What does not change: the checkpoint Mia-AiLab/GLM-5.3-Flash-EXL3-TR3-4bpw (routed experts in EXL3 at 4 bits per weight, the rest in BF16, ~176 GB, pinned at revision 9eaebb7c…; since v1.3.3 the default is Mia-AiLab/GLM-5.3-Flash-EXL3-4bpw-TensorFold, Mia's own quantization in the same format and size), two 128 GB GB10s linked through their ConnectX-7 ports, and the DFlash2 drafter. The model is the hybrid from chapter 18: 45 layers (34 of KDA linear attention and 11 of RoPE-free MLA with a DSA indexer), an MoE with 288 experts (top-8 + 1 shared) and four mHC residual streams.

What changes is the engine. vLLM is generic, and serving an exotic model on it took workarounds: padding the latent from 512 to 576 columns to match the fp8_ds_mla kernel, treating the KDA state like Mamba with prefix caching in 3,584-token pages, writing a “fair” scheduler for mixed steps. TensorFold is a per-family engine: each family brings its own kernels and its own draft verification. Without patches, upstream v0.6.0 serves GLM on CUDA with two ranks, a default window of 2,051 tokens and one request at a time. The patches add four requests in a shared pool (eight since v1.5), FP8 KV with 1M context, copy drafts, new stopping policies, all-gather over RDMA, 4-bit dense weights, faster prefill, vision, robust tool calling and metrics.

The contract: three equalities

Almost every comment in the patches ends in “the same bits”, or explains why not. This is the engine's exactness contract, which has three clauses:

  • Drafted = serial: a reply produced with drafts is, bit for bit, the one-token-at-a-time decode ("draft": false returns that reference).
  • Concurrent = solo: four requests served together receive the same tokens they would receive alone.
  • Resumed = fresh: a prompt resumed from a kept state gives the same result as a prompt computed from scratch.

Three things hold this up. Keyed sampling (chapter 9) makes the token at each position a function of the logits and a key. Row-independent kernels give the same bits to a row alone or in a batch. And sums are done in a fixed order, including across the Sparks, because in floating point the order of the sums changes the rounding (chapter 4). The contract holds against the same engine, weights, runtime and settings. It does not promise equality between MLX and CUDA, between different quantizations, or between different numbers of ranks.

Try it. In Figure 49.1, follow the dashed boxes: the drafts advance 3, 1, 4… tokens per round, the batch 2 or 3, the resume skips the beginning, and still the four token_sha come out equal. Switch to “lossless”: the fifth belt, which diverged (≠), now matches the others.

The fifth belt clears up the most common confusion. Three defaults are not exact against the BF16 checkpoint: DENSE=q4 and KV=fp8 lose information on purpose, and KDA_CHUNKED=1 stays “close to the serial kernel, not its bits”. The three equalities still hold because they compare the engine with itself. To serve the checkpoint as it is, use DENSE=bf16 KV=bf16 KDA_CHUNKED=0 and accept a smaller window.

Analogy: the pre-printed scratch card

In ordinary sampling, each token is a die rolled on the spot. In keyed sampling, the “die” for each position is already printed on a scratch card whose serial number comes from the prompt. It does not matter who scratches it (the serial decode, the draft verifier or a batch of four): the same card reveals the same number, and a draft is accepted only when it matches what is printed.

Step 1 · Hardware, network and the path of an all-gather

  1. Two DGX Sparks with no other large GPU load, each with ~110 GiB free at startup (start.sh warns below that). The budget starts from the real MemAvailable (Step 3).
  2. A direct ConnectX-7 link: a QSFP cable and an IPv4 address on each end, on the same private subnet (192.0.2.1/24 and 192.0.2.2/24 in the README), ping working and a RoCE v2 GID (chapter 39), the entry that contains the node's IPv4 (::ffff:a.b.c.d): “an all-zero or v1 entry makes NCCL fail about a minute in”. With both ports cabled and addressed, both are used.
  3. Key-based ssh from the head to the worker: ssh-keygen -t ed25519, ssh-copy-id user@<worker> and the test ssh -o BatchMode=yes user@<worker> true. The worker does not even need the repository.
  4. Docker with the NVIDIA runtime, the user in the docker group, and rsync, on both. ~205 GB of disk per Spark (~176 GB of checkpoint, ~2.3 GB of DFlash2, ~25 GB of image). With NFS, the worker only needs the image.

The topology is one rank per Spark. start.sh brings up rank 1 on the worker over ssh and then rank 0 on the head, which opens the API on port 8888. They meet through a TCPStore on port 29551: rank 0 publishes the ncclUniqueId there, and both initialize an NCCL loaded through ctypes. At startup, the ranks exchange their settings and refuse to come up if they differ. That is why every TENSORFOLD_*, TF_GLM_* and TF_ROCE_* variable goes to both containers. In service, the leader and follower rule applies: “Rank 0 decides everything that depends on time, clients or placement; rank 1 applies it.” On every iteration, rank 0 sends an operations message (ADMIT, EVICT, MOVE, GROW, FILL, ROUND…). When idle, rank 1 waits on a TCPStore doorbell, without spinning. None of this is authenticated, so keep everything on the private link.

Why all-gather, and not all-reduce

In classic tensor parallelism (chapter 38), each rank computes partials after attention and after the MoE, and an all-reduce adds them up. But floating-point addition is not associative (non-associativity, chapter 4): in float64, \((0.1 + 0.2) + 0.3\) gives 0.6000000000000001 and \(0.1 + (0.2 + 0.3)\) gives 0.6. And NCCL does not guarantee the order. The ranks can end up with different bits and sample different tokens. TensorFold does an all-gather of the fp32 partials and each rank sums “rank 0 first” (the rank-order sum):

\[ y \;=\; \mathrm{fl}\big(P^{(0)} + P^{(1)}\big)\ \text{on both ranks}, \qquad B_{\text{row}} = D \times 4\ \text{B} = 16\ \text{KiB}, \qquad B_{\text{window}} = R \cdot 16\ \text{KiB} \]
  • \(P^{(r)}\): fp32 partial of shape \([R, D]\) from rank \(r\); \(\mathrm{fl}\): sum rounded in fp32 (same order, same bits)
  • \(D = 4096\): width of the GLM residual stream
  • \(R\): rows in the window (pending token + drafts; up to 32 with 4 streams, that is, 512 KiB)
Analogy: two cashiers, the same tally

Two cashiers get the same two receipts and must close out to the same cent. If each one adds them in the order the receipts arrive, a rounding can fall on different sides, and each cashier “draws” a different amount of change. TensorFold's rule: both receive both receipts in full (all-gather) and always add rank 0's first. It costs more paper, but the tally comes out the same, and each cashier draws the next token on its own.

Messages this small are dominated by NCCL's fixed latency (“~30–50 µs”). On the GB10, pinned host memory is addressable by the GPU at full bandwidth, and the NIC registers it with an ordinary ibv_reg_mr. Without GPUDirect RDMA, NCCL goes through the host anyway. Patch 0006 adopts the b12x transport, a one-shot all-gather: a kernel copies the shard to the pinned region and rings a doorbell. A proxy thread does the RDMA WRITE to the peer (the NIC writes straight into the other Spark's memory, without waking its CPU), with a 4-byte flag on the same reliable QP after the data (the queue pair is the NIC's send queue, which delivers in order: when the flag arrives, the data has already arrived). The GPU on the other side waits for the flag, copies the shards in rank order and advances an epoch on the device, so that the CUDA graph can replay the exchange. Result: 11 µs per 16 KiB all-gather versus 45 µs for NCCL, and +6% decode (prose 44.2 → 46.9 tok/s, code 48.7 → 51.6).

Try it. In Figure 49.2, at “decode · 16 KiB”, switch COMM to nccl: NCCL's staging and proxy come in, and the time goes from 11 to 45 µs. At “prompt chunk · 32 MiB”, the transport becomes NCCL on its own (it is over 512 KiB); turn off one rail and the time goes from 1.9 to 3.5 ms.

Above 512 KiB NCCL takes over, with the same layout and the same bits. That is the case for a prompt chunk: 2,048 rows × 16 KiB = 32 MiB. Each QSFP port shows up as two PCIe Gen5 x4 functions, and nodes.sh hands both to NCCL as rails: 1.9 ms versus 3.5 ms on one. With 4 channels, a decode-sized all-gather drops from 80 to 32 µs. The repository does not reconcile the README's 45 µs with these 32 µs, which probably come from different sizes and tuning. The head is split by vocabulary: each rank sends its best candidates (up to 1,024 for top-p, with masses in 40-bit fixed point so the sums are exact) and the choice happens on the host, in float64.

prepare.sh: idempotent setup

start.sh runs prepare.sh when the setup marker changes (model@revision, drafter@revision, image on both sides, patch hash, worker, weights mode). Each stage skips what has already been done:

  1. Preflight: Docker, GPU, rsync, ssh, link detection (route → interface → HCA → RoCE v2 GID index) and disk (MIN_FREE_GB=180, IMAGE_FREE_GB=35).
  2. Image on the head: as long as the patch hash is the release one (ae8d1c789b47), it pulls from GHCR by digest sha256:22789f0c…bb969 (“a tag can be moved, a digest cannot”). With modified patches, it looks for the tag of the new hash. Without it (or with PULL=0), it builds: FROM nvcr.io/nvidia/pytorch:26.07-py3, TensorFold v0.6.0 via pip with av and xgrammar, each patch with patch -p0 --forward in name order (one failure breaks the build), a verification import and the label tf.patches=<hash>, which a pulled image must also carry.
  3. Image on the worker: pulled or sent via docker save | ssh docker load, and compared by content. The .Id differs between containerd and overlay2, so it would never match (issue #8).
  4. Weights at the pinned revisions: download validated with tensorfold info, and the script writes the refs/main that a download by sha does not write. The copy to the worker uses rsync -a -L --partial (-L follows the xet backend's links, issue #15) and is checked file by file. With WORKER_WEIGHTS=nfs, the worker mounts the head's cache as a read-only NFS docker volume, without sudo: both ranks come up in ~2.2 min and the worker saves ~166 GiB of disk.
\[ h \;=\; \mathrm{SHA256}\big(\texttt{cat patches/*.patch} \;\|\; \texttt{IMAGE\_EXTRAS}\big)_{[0:12]}, \qquad \text{tag} = \texttt{v0.6.0-}h \]
  • \(\|\): byte concatenation, with the patches in name order
  • \(\texttt{IMAGE\_EXTRAS}\): av==18.1.0 xgrammar>=0.2.8,<0.3; changing a package rebuilds the image just like changing a patch
  • \([0:12]\): the first 12 hexadecimal digits (ae8d1c789b47 in this release)

start.sh in five stages

  1. Setup: prepare.sh, if the marker changed.
  2. Checks: arguments, link, previous server, free port and memory (warning below ~110 GiB).
  3. Launch: rank 1 on the worker over ssh, then rank 0 and the API.
  4. Loading: every 15 s, the elapsed time and the GiB already on each Spark's GPU. If rank 0 dies with largest fitting prompt-plus-reply window: N tokens, the script does the refit: it restarts once with --context N.
  5. Smoke test: a chat completion through both ranks (thinking off, temperature 0, 32 tokens, “Reply with OK.”), then is now LIVE! on port 8888.

Step 3 · The budget that refuses before it freezes

On the GB10, the server's allocations come out of the same host RAM (chapter 27). They do not count toward the container limit (docker run --memory), and “running out tends to freeze the machine rather than fail an allocation”. That is why TensorFold computes the budget before loading weights, from what the system reports as available at that moment, counting reclaimable page cache:

\[ \text{budget} = \text{MemAvailable}_{\text{start}} - \text{reserve}, \qquad \text{reserve}_{\text{TF}} = \max(4\ \text{GiB},\ \text{RAM}/10) \] \[ \text{free}_{\text{idle}} \approx \text{reserve} + \text{leftover} - F, \qquad \text{free}_{\min} \approx \text{reserve} + \text{leftover} - (F + \Delta_{1\text{M}}) \]
  • reserve: what the budget leaves free; the recipe uses MEMORY_RESERVE_GIB=14.5 (the TF default gives ~12.2 GiB). Leftover: what the pool did not use because it hit the KV_POOL_GIB ceiling
  • \(F \approx 8.6\) GiB: what the server uses beyond its own estimate from startup, the “CUDA context, NCCL and workspace” memory the estimate does not count, plus CUDA graphs (inferred: ~10 − 1.4; TensorFold's GLM documentation measured 3.5–4.8 GiB for CUDA context, NCCL and graphs alone)
  • \(\Delta_{1\text{M}} \approx 1.4\) GiB: the increase from a 1M prompt, measured on the head (7.0 → 5.6 GiB free). \(F + \Delta_{1\text{M}} \approx 10\) GiB is the README's “about 10 GiB beyond its own estimate at its peak”
  • \(\text{free}_{\min}\): the lowest free memory under load; ~4.5–5 GiB on the head with a 14.5 reserve (measured: 5.6 GiB)

Inside the budget go rank 0's startup estimate (88.09 GiB: ~80 GiB of weights, the 1M window, the vision tower and friends) and the shared pool beyond the window, which grows into whatever is left up to KV_POOL_GIB=12.5 per Spark. With the TF default (3 GiB), the pool was 1,411,072 tokens. If not even the window fits, the configuration is refused with the largest window that fits, and start.sh does the refit. The size comes from the code of patch 0030:

\[ \text{pool\_rows} = \Big\lfloor \frac{\text{capacity} + \max(0,\ \text{cache\_bytes} - \text{states}) \,/\, \text{per\_token}}{\text{ALIGN}} \Big\rfloor \cdot \text{ALIGN}, \qquad \text{states} = N_{\text{entries}} \cdot \Big(\tfrac{\text{slot\_bytes}(0)}{2} + 22\ \text{MiB}\Big) \]
  • capacity: the per-request window; cache_bytes: the TF_GLM_CACHE_GIB ceiling (= KV_POOL_GIB)
  • states: fixed state of the kept prompts; \(N_{\text{entries}} = 32\) in the recipe, ~45 MiB each by the v1.3.2 estimate (patch 0097 later measured ~91 MiB per state on two Sparks)
  • per_token: bytes per token of the geometry; ALIGN = 2,048 tokens, the alignment of an extent

How much does a token cost? From the code (an inventory calculation, not the README), each DSA layer stores 528 B of FP8 latent and 36 B of grouped indexer key (144 B per pool of 4 tokens). With 11 layers, that is \(11 \times 564 = 6{,}204\) B per token and per rank, because the latent is replicated on both ranks. A 1M window costs ~6.1 GiB. In vLLM, fp8_ds_mla plus the indexer come to 7,579 B. The KDA state stays out of the count because it does not grow with context: it lives in one slot per stream.

Try it. In Figure 49.4, watch the “free now” label while the red pulse beats: it swings between ~6.8 and ~5.4 GiB, the back-and-forth of the measured 7.0 → 5.6. Drop MEMORY_RESERVE_GIB to 8 and raise KV_POOL_GIB to 20: the pool swallows the leftover, the minimum free turns red and it starts to snow. Put the reserve and the ceiling back to their defaults and drop MemAvailable to 101: not even the window fits, refusal and refit.

With 4 streams, the pool is split into extents: “one 1M-token conversation next to one more of 1M, or next to three of ~640k”. Whoever does not fit waits in order, and kept prompts give way first. In the measured v1.3 start: a pool of 2,922,496 tokens; idle MemAvailable of 7.0 GiB (rank 0) and 10.5 GiB (rank 1); a minimum of 5.6 and 9.5 GiB under a 1M prompt. In v1.2, raising the ceiling from 11 to 12.5 GiB took the pool from 2,684,928 to 2,852,864 tokens.

The idle number is the most revealing. Sitting still, with no prompt at all, the head already has only 7.0 GiB free, less than half of the 14.5 GiB reserve. So most of the ~10 GiB the server uses beyond the estimate is there from startup (CUDA context, NCCL, graphs, workspaces), and a 1M prompt adds only ~1.4 GiB (7.0 → 5.6). The reserve is not slack for rare peaks: it gets occupied right at boot, and what is left of it is the real margin.

Analogy: the water tank with the safety line

Think of the Spark's RAM as a water tank with a line painted on the inside. At startup, TensorFold measures the level and promises to fill only up to the line (weights, window, pool); above it sits the reserve. But some inflows are not in the plan: CUDA context, NCCL and friends raise the level by ~8.6 GiB (inferred) as soon as the engine turns on, and a 1M prompt is a wave of another ~1.4. With the line too high (a small reserve), the wave overflows, and in unified memory overflowing locks up the machine.

Do not squeeze the reserve to gain pool

The reserve sets the minimum free memory. Sitting idle, the server already takes ~8.6 GiB of the reserve; a 1M prompt pushes that to ~10. With a reserve of 10 GiB or less and no leftover, the peak eats the entire margin, and in unified memory that tends to lock up the Spark instead of returning an error (an interpretation of the README's rule). If another workload shares the machine, increase MEMORY_RESERVE_GIB.

The two declared losses: DENSE and KV

The checkpoint leaves in BF16 everything that is not a routed expert (attention, shared experts, dense layers, head): ~9.7 GiB per Spark, read at every decode step. DENSE=fp8 (patch 0002) uses e4m3 (chapter 21) with a scale per row and per block of 128 columns and gives ~+33% decode over BF16. The default DENSE=q4 (patch 0005) is a 4-bit affine quantization in groups of 64, with the range chosen by an MSE clipping search:

\[ a_i = 1 - 0.45\,\tfrac{i}{15},\quad lo = a_i \min g,\quad s = \tfrac{a_i (\max g - \min g)}{15},\quad q = \mathrm{clamp}\Big(\mathrm{round}\big(\tfrac{g - lo}{s}\big), 0, 15\Big),\quad i^\star = \arg\min_i \sum (g - s q - lo)^2 \]
  • \(g\): the 64 weights of a group; \(i = 0,\dots,15\): the 16 clippings tested (from 1.0 to 0.55 of the minimum and maximum)
  • \(s, lo\): scale and bias in bf16, that is, \(4 + 32/64 = 4.5\) effective bits per weight
  • in the kernel, \(x \cdot (s q + lo) = s\,(x \cdot q) + lo \sum x\): that is why it receives the activation sum per group

One rare, large weight stretches the 16-step ruler for the other 63, and clipping the tip trades one big error for several small ones (chapter 20). There is no calibration with activations, as in GPTQ/AWQ. The head stays in FP8 and kv_b in BF16. Over fp8: prose 38.9 → 44.4 tok/s, code 44.2 → 48.7, prefill ~1,090 → ~1,260 tok/s. GSM8K gave 98.0% and HumanEval 95.1% on both (bf16: 97.2% and 96.3%; how to read these tests is in chapter 25).

FP8 KV (patch 0038, the idea from chapter 23) stores each 512-value row of the latent as e4m3 codes with a power-of-two scale:

\[ s = 2^{\lceil \log_2 a_{\max} \rceil - 8}, \qquad \frac{a_{\max}}{s} \in [128,\ 256] \;<\; 448, \qquad 512 + 4 + 12 = 528\ \text{B per row} \]
  • \(a_{\max}\): the largest absolute value in the row; 8 is the SHIFT, and nothing saturates below e4m3's 448
  • 528 B: 512 codes + fp32 scale + 12 bytes of alignment (1,024 B in BF16)

Why a power of two? A float's relative precision does not depend on the scale, so a finer scale does not help. It would only make a difference for values smaller than \(2^{-14}\) times the maximum, which fall below e4m3's normal range. On real GLM rows, fp32 scales per token, per block of 128 and fixed per layer all landed within 0.001 of the 2.65% relative error per row. And multiplying by \(2^k\) does not round, so readers apply the scale in the fp32 products with no error. A single helper quantizes the prefill and decode rows: “Lossy (the owner's call), never inexact”. It is the idea behind the per-token UE8M0 scale of DeepSeek-V3.2's indexer.

Try it. In Figure 49.5, turn off the search and drag the clipping \(i\). At \(i = 0\), the 16 steps span from the smallest to the largest weight and are wide; near \(i^\star\), red (clipped) dots appear at the ends and the MSE goes down; then it goes back up, because clipping too much ruins the large weights. In FP8, toggle the scales and ask for new rows: the errors stay within tenths of a point of each other, and the power of two, exact to apply, comes for free.

Prompt: experts and attention (0001, 0004, 0009, 0020, 0024, 0028)

Problem. In a 2,048-row chunk, each expert of the MoE receives dozens of tokens. The weights are in an EXL3 trellis: each tile has to be decoded into registers before the tensor core, and the input goes through a Hadamard rotation with a sign vector. The decode kernel decodes a tile for only 16 rows, so the prompt would repeat the decoding every 16 tokens.

Idea. (1) Launch order (0001): the blocks that read the same rows of an expert run side by side, while the L2, the cache the SMs share (chapter 26), still holds them. (2) Swapped operands (0004): \(Y^\top = W^\top X^\top\) puts the weight on the reused side of the tensor core, and one decoded tile feeds up to 64 tokens; fused epilogues do Hadamard and SiLU without a round trip through memory. (3) One rotation per row (0009): all GLM experts use the same sign vector, and 16 rotations per row (top-8 × gate and up) become one. (4) DRAM/tensor core order (0020): interleaving experts with few tokens (memory-bound) and with many (tensor-core-bound) keeps both resources busy. In attention, the DSA indexer picks 512 pools of 4 tokens, so only rows before 2,051 tokens (= 512 × 4 + 3) go through dense attention (0009); selection goes in blocks of 512 rows (0024); and the estimate stops counting scratch that no kernel allocates (0028), because every byte overcounted was one less KV token.

Number. “the same kernel and arithmetic, 2.3-2.5x faster at 4,096 rows” for the launch order; the README sums up the rest as “faster prefill, less memory at 1M”. Prompt bits differ from decode bits (≠ prompt), but are the same for any chunking, so drafted = serial still holds.

Prompt on both Sparks (0010, 0017, 0022, 0033)

Problem. Between blocks, GLM mixes its four residual streams: this is the hyper-connections glue (24 products over 16,384 columns and one Sinkhorn per row). Small, repeated work: without split, both ranks do the same glue over all rows.

Idea. With SPLIT=1, rank \(r\) owns rows \([rH, rH+H)\), \(H = R/2\): it sends the peer the partials for its rows, sums its own “rank 0 first”, runs the glue only on them and exchanges the normalized rows in BF16. It is sequence parallelism (chapter 38) restricted to the glue: per row, traffic drops from \(4D\) to \(3D\) bytes and the glue is halved. 0033 runs the next block's “front” during the exchanges.

Number. 50k: ~1,270 → ~1,730 tok/s; decode −1.5%; same bits. A lesson in method (chapter 45): the side stream was born high-priority in 0010; 0017 only exposed TF_GLM_OVERLAP_PRIORITY (default still −1, high), and 0022 switched the default to 0 (normal) when two boots with each priority showed the same prefill and, with high priority, decode rounds 0.5–1% slower after a prompt.

KDA on the prompt (0012, 0014, 0039)

Problem. The 34 KDA layers are linear attention with a delta rule (chapter 14): a \(128\times128\) state per head, updated token by token. Row by row, a 50k prompt is 50 thousand steps in series.

Idea. In chunked (WY) form, the recurrence of a 32-row sub-chunk becomes matmuls and a triangular inverse; only the state handoff between sub-chunks stays sequential. The final CUDA kernel (0039) uses 256 threads per head, with the state in registers. The numerics needed care (chapter 4): the cumulative sum of the log-decay reaches −320 over 64 rows, and the difference of two such values carries \(\mathrm{ulp}(320) \approx 3\cdot10^{-5}\) for decays near 1; that is why the final version multiplies the decays in order (running products). In the Triton version (0014), the GB10's 99 KiB of shared memory per block forced a single pipeline stage; the final CUDA kernel (0039) pre-warms the next sub-chunk in L2 and copies with cp.async. A row's bits depend only on its sub-chunk and the incoming state, hence chunks in multiples of 32 and states on a grid of 64.

Number. 50k 29.3 → 26.4 s; 149k 91.1 → 84.5 s. Bits: “close to the serial kernel, not its bits”, because the prompt arithmetic changes; drafted = serial still holds.

Prompt reuse (0008, 0015, 0042)

Problem. In a model with KDA, the prompt state includes the recurrent state of each linear layer, the convolution windows, the drafter's context and the indexer's tail. It only exists at one point: you cannot slice it into blocks like an ordinary KV cache.

Idea. Keep whole prompt states at chosen points: on a grid of 64 (0008), so that fresh and resumed pass through the same state; up to 2 extras where the prompt diverges from a kept one and at the end of the system block, the shared prefix (0015); and the head's logits row together with the final state (0042), so an identical prompt comes out “prefilling nothing”: the replay.

Number. Identical 64k: 34 s → under 0.07 s; 7.9k system: 4.24 → 0.13 s; same replies. vLLM's APC (chapter 33) reuses any aligned prefix, but in a hybrid it only restores at 3,584-token checkpoints and recomputes the tail; TensorFold reuses a few whole states, with no recomputation, the pattern of an agent that resends the conversation and appends. Prompts with images and requests with a grammar do not replay.

Decode (0013, 0016, 0019, 0031, 0043, 0046, 0047)

Problem. Each round reads almost all the weights for a few rows: the bottleneck is memory bandwidth, and every millisecond the GPU waits on the host or the network is lost.

Idea. Windows of up to 16 rows in CUDA graphs, with a round's tokens delivered when the next window is already queued on the GPU (0013). Tiles measured per matrix shape, fused epilogues and decode KDA 4–36% faster (0016); hc_partial rewritten in CUDA copying Triton's reduction tree, to keep the bits (0019). In the indexer, the query is loaded once per row (0031), and scoring stops at the visible pools, \(\min(N_{PS}, \max(\lfloor (P+r+1)/4 \rfloor, K))\), read on the device, and not at the rounded size at which the graph was captured (0043). On the memory side, a side stream brings the next weights into L2 while DRAM waits on all-gathers and recurrence, with the shared expert before the routed ones (0046), and the trellis comes in 16 B loads, one step ahead (0047).

Number. Editing 84 → 119 tok/s with 16-row windows; L2 prefetch + 16 B loads + 512 KiB: prose +2.7%, code +3.3%. Same bits.

Concurrency (0026, 0027, 0029, 0030, 0035, 0040, 0041, 0048, 0049)

Problem. Serve up to 4 requests in a batch (8 since v1.5, patch 0069;chapter 32) without changing a single bit of any of them: KDA has per-sequence state, each stream keeps its cache in its own place in the pool, and kernels such as cuBLAS's or torch.topk can switch algorithms depending on the number of rows.

Idea. Segment tables on the device (each stream runs from its own slot and its own extent, with the solo kernel's arithmetic), whatever depends on the number of rows runs per stream, and one DFlash2 context per stream (0027); Step 6 shows the round. In 0048, the timing used a repeated token, which routed to the same few experts and measured a 16-row window at half its cost: in an MoE, the cost depends on how many distinct experts the batch touches.

Step 6 · A round from the inside: key, drafts and four streams

The decode's unit of time is the round. The engine proposes drafts, runs one forward over the window [pending token, drafts…], samples each row with the key, accepts up to the first disagreement and commits the accepted rows (KV, KDA state, conv, drafter context). The key turns verification into an equality test:

\[ u_{p,v} = \mathrm{mix}(\text{seed},\ p,\ v) \in (0,1), \qquad G_{p,v} = -\log(-\log u_{p,v}), \qquad x_p = \arg\max_{v \in \mathcal{C}_p}\Big(\frac{\ell_{p,v}}{T} + G_{p,v}\Big) \]
  • seed: the request's seed or 8 bytes of the SHA-256 of the prompt ids (“the same request gives the same reply”)
  • \(\mathrm{mix}\): three rounds of splitmix64 over (seed, absolute position \(p\), token \(v\)), an indexable, stateless generator
  • \(\arg\max(\ell/T + G)\): an exact sample from \(\mathrm{softmax}(\ell/T)\), via the Gumbel-max trick
  • \(\mathcal{C}_p\): candidates after top-k → /T → top-p → min-p, in float64 on the host; draft \(d_j\) stays if \(d_j = x_{p+j}\)

The rejection sampling from chapter 35 preserves the distribution. Here the token at each position is decided before any proposal, so no drafter or policy changes the reply: “replies are the same under every policy”. Three things follow from this. You can tune policies offline: patch 0011 writes teacher-forced dumps, and a numpy simulator reproduces exactly the rounds of any policy. You can preempt by recomputation: tokens already sent are checked, not resent. And the drafter can look at the target's noise before verification.

That last one is the case of the noise-aware stop, fnc7:0.3. At each depth, DFlash2 (the block drafter from chapter 37) picks \(\arg\max(\text{score} + 0.7\,g)\), with \(\text{score} = (\text{logits} + 0.6\cdot\text{edge})/T\), and estimates the chance of a hit:

\[ c_j = \mathrm{softmax}\Big(\frac{\text{score}_j + g_j}{\beta}\Big)[\text{pick}_j], \qquad \text{continue while}\ \prod_{i \le j} c_i \ge P, \quad j \le N \]
  • \(g_j\): the target's own keyed Gumbel draws, over the candidates at that position
  • \(\beta = 2.0\): fitted by log loss on 9 teacher-forced dumps from 2026-09-30 (7 of sampled prose, 2 of greedy code)
  • \(N = 7\), \(P = 0.3\); the alternative fcost7:noisy picks the \(k\) that maximizes \(E[\text{tokens}\mid k]/\text{ms}(k)\), with \(E = 1 + \sum_{j\le k}\prod_{i\le j} c_i\)

On the cost side, the simulator's old table gives 29.2, 35.6, 42.6, 48.8, 53.6, 58.9, 64.5 and 66.0 ms for windows of 1 to 8 rows, plus 3.08 ms per DFlash2 block. Verifying 8 rows costs ~2.3× verifying one, and that margin is what speculation exploits. When a copy exists, copy drafts take DFlash2's place: if the last 8 tokens have already appeared, up to 15 following tokens become that round's drafts, and DFlash2 does not even propose. In code, copies from the reply itself kept 23% of the drafts, versus 74% for copies from the prompt; that is why COPY_CODE requires matching 16 tokens before copying from the reply.

Analogy: the echo of a dictation

Someone is dictating a text you have already read. If the last 8 words match a passage in front of you, the best guess is to continue the passage, like an echo: it costs nothing (a lookup in numpy) and, in a quotation, gets everything right in one go. When the echo misses, the key shows where, and the right token comes from the target.

Four streams

With PARALLEL=4, a thread on rank 0 handles admissions and then runs either a prompt chunk from the oldest stream that is filling (up to 1,024 rows while others decode), or a decode round, alternating according to FILL_SHARE=0.5. That is the v1.3.2 policy, and it favours the newcomer's first token: each 1,024-row chunk (~0.65 s) froze the replies already streaming. Since v1.4 the default slices the fill and protects those replies instead (update). Prefill and decode never share a forward, unlike vLLM's mixed chunked prefill. In the round, each stream proposes under its own policy, the combined window is capped at 32 rows (64 by default past 4 requests since v1.5; a draft is trimmed from the longest tail) and one verification runs over all of them. The row-independent parts use the whole batch. KDA uses a segmented chain starting from each stream's slot, and DSA attends within each one's extent. The KDA state has two parities: if the stream accepts fewer rows than it verified, the state is rebuilt from the kept rows (replay), instead of keeping \(k+1\) copies.

A request gets in if the free rows (plus the extents that only hold prompts) cover the prompt with a margin of 2,048 per decoding stream. Otherwise it waits in the queue. In v1.3.2, to make room, the engine evicts kept prompts (LRU), compacts extents or grows in place; since v1.6 it compacts before it evicts (patch 0074), and which kept state goes first follows the policy described in the update.

Analogy: spots in a row, not scattered

Extents are contiguous parking spots: each conversation takes a whole row, in multiples of 2,048 tokens, and not scattered spots like PagedAttention's pages (chapter 31). That way a stream's kernel sees its piece as a tensor of its own, with no page table. The price is fragmentation: when a conversation leaves from the middle, the valet slides the cars along (compaction), and the cars that have gone unclaimed the longest (kept prompts, LRU) get towed first (the v1.3.2 rule).

MULTI_PREFILL goes after TTFT. A short forward takes “~0.12 s on two Sparks, the weights read once a layer whatever the rows”, and four short prompts that arrived together used to wait for eight of them. In a chunk [s1][s2][s3][s4], each expert is read once for all of them, with the policy “fewest remaining rows first”.

Analogy: one bus instead of four taxis

The trip costs almost the same with 30 or 300 passengers, because the bulk of it is reading each layer's weights. Four prompts in taxis pay for eight trips (two chunks each); on the bus, they pay for two. Each passenger gets off at their own stop (KDA and attention run piece by piece, with the bits of a chunk of their own), and whoever has the shortest ride sits up front.

  • What you lose (v1.3.2): the GLM CUDA engine required exactly two ranks (no TP3/TP4, chapter 40) and served at most 4 requests. Since then start-tp3.sh runs three Sparks (v1.4, experimental) and PARALLEL goes to 8 (v1.5); four Sparks exist only on a branch. Long fresh prompts arriving together still wait in a queue.
  • Smaller API: logprobs, top_logprobs and n ≠ 1 get HTTP 400; logit_bias and the penalties are accepted and ignored; no API key. In v1.3.2 there was also no /v1/messages and no abliteration: Anthropic Messages arrived in v1.9 (patch 0084) and ABLIT=1 in v1.7.
  • Maintenance: 53 patches (123 in the current image) against the site-packages of one engine version call for a rebase with every release.

Quality caveats

q4 and French (#18): on short code prompts in French, DENSE=q4 misses the end of turn and runs until max_tokens in 12 of 48 replies, versus 1 of 48 with bf16 or fp8. GSM8K and HumanEval, in English, did not catch this. For non-English prompts, use DENSE=fp8, which costs ~10% of decode. Step 8 · Tune to your workload and reproduce

The defaults were designed for agents on two Sparks. Other scenarios call for another combination. Figure 49.10 builds the .env from your answers, recomputes CONTEXT and PARALLEL with config.sh's logic and points to the vLLM recipe when the request is beyond what the engine can do. The direction of that advice changed upstream: on 2026-10-04 the vLLM recipe's own README was retitled “Use the TensorFold recipe” and says everyone should use it (commit cafea0f). What still favours vLLM is narrower than in v1.3.2: logprobs, n > 1, penalties, an API key on the server itself, a faster boot and a four-Spark launcher (experimental) on its main branch.

Try it. Turn on “commercial use” and “short non-English prompts”: DRAFTER=mtp and DENSE=fp8 come in, and PARALLEL drops to 1 (only DFlash2 drafts in a batch). With only “exactness against the checkpoint”, KV=bf16 doubles the bytes per token and CONTEXT drops to 163,840. With “I need logprobs”, the panel points to the vLLM recipe.

Reproduction checklist

  1. Hardware: ~110 GiB free per Spark, QSFP cable, IPv4 on the same subnet, RoCE v2 GID, ssh with BatchMode=yes, Docker + NVIDIA runtime + rsync, ~205 GB of disk (or NFS).
  2. Before the 1st start: decide DRAFTER (license), DENSE (language), WORKER_WEIGHTS (disk) and VISION, in scripts/local.sh or .env.
  3. Bring it up: ./start.sh (the 1st time downloads, copies and compiles; after that, 2–6 min). Check the LIVE line and the patch hash.
  4. Exactness: the same request with and without "draft": false; four concurrent ones against the same ones alone; a resend. Compare the reply's token_sha.
  5. Correctness: tools/needle.py (needle at ~195k tokens) and tools/toolcheck.py (an array parameter comes back as a JSON array).
  6. Measure: sparkDash from another machine, clocks capped, temperature 0, thinking off. Record the image hash and digest, the revisions and the date. In an A/B, change one variable and do two boots on each side.
  7. Operate and maintain: watch /health (pool_tokens, pool_free_tokens, streams) and /metrics. Modified patches rebuild the image (scripts/publish-image.sh publishes it and prints the values to pin), and a new TensorFold version calls for a rebase and prepare.sh --rebuild.
What to take to your next recipe

The engine is a recipe decision too, just like the flags and overlays from chapter 41. With the same hardware and the same weights, swapping the engine moved decode, TTFT under concurrency, reuse and context, and cost scale, API and maintenance. In the recipe from scratch, ask early: is the architecture exotic enough that a generic engine pays dearly for it? Will you stay within what the engine serves (2 nodes and 4 requests in v1.3.2; 3 nodes and 8 requests by v1.5)? Do you need bit-for-bit reproducibility? If the answer is yes to all three, a per-family engine may be worth the work.

This chapter closes Module 1, which went from the neuron to the cluster and ended with two recipes for the same model. The next chapter opens Module 2: instead of serving frozen weights, we will adjust them after pretraining (SFT, preferences, RL). There you will see why a fast, and sometimes exact, inference engine becomes a central piece of the training loop.

Checkpoint
v1.3.3 made Mia-AiLab/GLM-5.3-Flash-EXL3-4bpw-TensorFold (revision 078455ff) the default: Mia's own EXL3 quantization, Apache-2.0, with the format, size (~176 GB), speed and memory of TR3-4bpw. Against TR3 on the same build, its KL divergence to Z.AI's official FP8 release is 2–18% lower on all six test sets (paired 95% intervals exclude zero on all but chat). GSM8K 98.8%, HumanEval 95.7%, HumanEval+/MBPP+ 86.5% (thinking on); no difference to TR3 is significant. The vLLM recipe switched to the same weights (commit 98cf18f).
Scale
start-tp3.sh (v1.4, experimental) runs three Sparks wired as a triangle, one direct cable per pair. The TP-N engine is patches 0066–0068: heads, expert columns, vocabulary and DFlash2 KV groups are split in whole units, with the remainder on the lowest ranks, so the 64 heads become 22/21/21 (the uneven split from chapter 40). By default every all-gather goes over NCCL there. With sparkDash and the default configuration, going from two to three Sparks took one request's prose from 60.4 to 77.6 tok/s and four at once from 108.8 to 146.2 (separate boots). Four Sparks exist only on the tp4 branch.
Concurrency
Patch 0069 (v1.5) takes PARALLEL from 1–4 to 1–8 (MAX_SEGS 4 → 8) and the shared verify window to 64 rows past four requests. Aggregate decode from 4 to 8 at once: on two Sparks, prose 103.2 → 130.8 tok/s (+27%) and code 126.7 → 167.0 (+32%); on three, +36% and +28%. Replies stay byte-identical to the same requests served alone. The price is memory: the reserve grows ~0.95 GiB per request past four, and the two-Spark pool falls to ~1.5M tokens at 8 (2.0–2.6M at 4). That is why two Sparks keep 4 by default and three default to 8.
Spill tier
SPILL_GIB (patch 0088 in v1.9, block store 0128; off by default) writes kept prompt states to local NVMe in 2,048-token blocks with CRC-32 checks, shared by later turns of the same conversation. A conversation then survives an eviction, a restart or a kill -9: at PARALLEL=8, a 40k-token one resumed after a kill -9 in 1.4 s, against 21.8 s computed fresh, and a 40k state restores in 147 ms (median).
KV sharding
TF_GLM_KV_SHARD=1 (patch 0129, off by default) stores each conversation's MLA latent once, on the Spark that owns it, instead of on every rank (the replicated latent cache of chapter 48): 6,204 → 3,300 B per token per Spark. At PARALLEL=8 the pool holds 1.87× the tokens (1.51M → 2.83M), decode stays within 1% and every reply is byte-equal to the unsharded engine's.
Single-flight prefill
PREFIX_WAIT=1 (patch 0128, off by default): a request whose prompt starts with what another request is still prefilling waits for that state instead of computing it too. Six agents at once on a fresh 12k-token system prompt all answered in 14.7–15.0 s instead of 45.7–47.0 s, with the same replies.
Kept states
No longer plain LRU. A conversation's superseded (shorter) states go first (0063, v1.4); the pool compacts before it evicts (0074, v1.6); shared prefixes go by recency only (0077), and so does a state another conversation forked from (0120); an opt-in byte budget and per-conversation quota (0089) and a count that follows a share of the pool (0097) complete the policy. Measured with 0097 on two Sparks: ~91 MiB per kept state, about twice the earlier ~45 MiB estimate.
Streaming
Sliced fill (0062) and smooth streaming (0061), on by default since v1.4, change whom the scheduler protects. In v1.3.2, each 1,024-row chunk of a new prompt froze every other reply for ~0.65 s. Now the fill runs a few layers at a time (FILL_BUDGET_MS=200) with a drafted decode round between slices, and tokens leave a 400 ms playout buffer at a steady pace. Three replies streaming while a fresh ~25k-token prompt arrives (two boots each): gaps p50 630 → 81 ms, while the newcomer's first token went from 16.1 to 21.1–21.3 s. The default now protects the replies already streaming. Later, FILL_ROWS=2048 gave the fill back 10–14% (three Sparks, a cold ~256k prompt beside a streaming reply: 132.2–132.6 → 113.4–114.0 s).
API
Anthropic Messages (/v1/messages and count_tokens; patch 0084, v1.9, backported from upstream TensorFold v0.6.3), so Claude Code and the Anthropic SDKs talk to the server directly. ABLIT=1 (v1.7) serves the gated abliterated weights (chapter 19), with thinking off by default. Earlier turns' reasoning stays in the prompt (0060, v1.4): a replayed agent session prefilled 16,106 tokens instead of 85,127. Tool calls were hardened (0114–0117): quoted markup stays text, and in 30 live replies that mentioned the tag before a real call, tool_calls went from 15/30 to 30/30. Still refused: logprobs and n ≠ 1; penalties are still ignored, and the recipe still has no API key.
Health
Rank messages carry a sequence number and a checksum, so ranks that fall out of step stop with a named error, and /health reports iteration_s (0065, v1.4); with TF_GLM_MULTI_WATCHDOG_EXIT=1 a stalled server exits after its stack dump. Patch 0118 makes a broken engine visible (/health ok: false with the first error, tensorfold_health:ok in /metrics), and TF_GLM_EXIT_ON_BROKEN=1 exits at once so a supervisor can restart both ranks.
Kernels
Patch 0085 (v1.9) fixed the indexer's split top-k pass, which summed a table sized for the whole pool: on three Sparks (PARALLEL=4), one request at 590k tokens of context went from 66.2 to 184.4 tok/s, with byte-identical replies. Patches 0099–0108, by BadAd84, take host stalls out of the loop (tokenizing without the GIL, the next draft pass launched at a round's end) and port Triton indexer and sparse-attention kernels to CUDA reproducing Triton's own instruction sequence, so the bits do not change: the decode indexer call with 4 streams × 8 rows at 596k went from 1,296 to 647 µs on one GB10 (0107).

NUCLEUS_UNION=1 since v1.9 (same draws, sampled decode at greedy's pace); TF_ROCE_WAIT_S 20 → 300 (v1.6, #54); TENSORFOLD_GLM_REQUEST_IMAGE_TOKENS 16,384 → 102,400, with the vision workspace 768 → 1,440 MiB (rank 0's estimate 88.09 → 88.74 GiB); FILL_ROWS 1,024 → 2,048; at TP=3, PARALLEL=8 and KV_POOL_GIB=32; MEMORY_RESERVE_GIB 14.5 plus ~0.95 GiB per request past 4.

What to take from the pace of change

In 24 days the patch count went from 53 to 123, the default checkpoint changed, two of the costs Step 7 listed (two Sparks, four requests) went away, and a default this chapter explained, the fill policy, now protects the other side. That is the normal pace of a fast-moving serving stack, not an anomaly. Three habits follow for research: pin what you measure (image digest, weight revisions, engine version) and write it next to every number; read the changelog before trusting a README summary, which can lag behind the image it ships; and re-measure on your own workload after an upgrade, because a new default can trade one latency for another, as the sliced fill did.

Beyond the Spark

None of these features is specific to the GB10. The spill tier is a KV offload tier, the role LMCache or NVIDIA Dynamo's KV block manager plays beside engines like vLLM or SGLang on H200 nodes. Owner sharding of the latent is the motive behind decode context parallelism (chapter 38): an MLA cache replicated across tensor-parallel ranks keeps one copy per rank. Single-flight prefill is request coalescing on a shared prefix. Only the scarce resource changes, 128 GB of unified memory here and HBM per GPU there; the levers stay the same: where the KV lives, how many copies of it exist and who computes a shared prefix first (interpretation).
