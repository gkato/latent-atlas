Three numbers describe the machine the recipes run on: 48 multiprocessors, about 125 TFLOPS of dense BF16 and ~273 GB/s of memory bandwidth per node. With them and some back-of-the-envelope math you can estimate Qwen's decode ceiling with MTP=3 (~76–80 tok/s from streaming alone) and understand why the measured number lands at 52.1 tok/s, why GLM's prefill uses only 14% of peak compute and why DeepSeek spends ~80% of a decode step just bringing weights in from memory. In this chapter you open up the GPU: how work is cut into threads and warps, where the data lives, what a tensor core actually computes, why a binary built for a B200 may not even load on a DGX Spark, and how to put it all together into a cost model that predicts tokens per second before you start the server.

A factory with 48 workshops

A CPU is a handful of very clever artisans. There are few cores, each with branch prediction, out-of-order execution and huge caches, and all of that serves to finish one task as fast as possible. The GPU makes the opposite bet: it is a factory with thousands of simple workers doing the same thing at the same time. It does not try to shorten the latency of one calculation. It tries to maximize how many calculations finish per second, the throughput. In an LLM, where almost everything is multiplying huge matrices (revisit Tensors and linear algebra), that trade pays off.

The basic unit of the factory is the SM (streaming multiprocessor), the “workshop”. A GPU is, in essence, a grid of identical SMs that share an L2 cache and the memory controllers. The GB10, the DGX Spark's chip, puts 20 ARM cores and a Blackwell GPU with 48 SMs in the same package, and both read the same 128 GB of LPDDR5X DRAM, of which ~121.69 GiB are visible to CUDA. A datacenter GB300 has 160 SMs. In the DeepSeek recipe audit, the GB10's SM clock held steady at ~2,190 MHz during decode (3,003 MHz max), with ~26 W on the GPU rail. The TensorFold version of the GLM recipe publishes its numbers with the GPU clocks capped at 2,200 MHz, close to that level. The cap cuts off boost and its swings, which takes that variation out of the comparison between runs and between the two ranks, though it does not stop the clock from dropping below it. That matters because, in a TP=2 round, the slowest rank sets the pace (interpretation). (The DeepSeek repository has three runtime lanes, and that changes what applies in each example; the box at the end of this section explains.)

A two-node recipe also has a third road. Between the two Sparks, the ConnectX-7 link has a 200 Gb/s port (confirmed by ethtool in GLM's prefill report, docs/improve-prefill.md), that is, ~25 GB/s at the port's ceiling. But each PCIe function of the card is Gen5 ×4 (≈15.7 GB/s raw), and the vLLM recipes use only one by default: the all-gather measured when GLM boots sits at 12.6 GB/s per rank, some 20× below the ~273 GB/s of the LPDDR5X. The TensorFold version uses both functions as two rails when both have an address on the link's subnet: the 32 MB all-gather of a prompt chunk drops from 3.5 ms to 1.9 ms, or from ≈9 to ≈17 GB/s (our arithmetic, taking the 32 MB as what each rank sends; it is a different measurement, not directly comparable with the 12.6 GB/s from the vLLM boot), still more than an order of magnitude below the DRAM. That is why every collective between the nodes goes into the fixed cost of the step, which shows up in the cost model later on.

Follow the zoom in the figure, from the chip to the SM, from the SM to the warp, from the warp to the thread and, finally, to a whole kernel spread across the workshops.

Notice two things. First: what travels through the figure is bytes. Before computing anything, the GPU has to bring in weights and activations from a DRAM that is far away and that the CPU also uses. Second: inside the SM, everything is split in four. Each sub-partition has its own warp scheduler, a slice of the register file, integer and floating-point units and a tensor core. The recipes' kernels try to keep this design, replicated 48 times, busy at all times.

Analogy: the industrial kitchen

Each SM is a kitchen. The registers are each cook's countertop, the shared memory is the kitchen's shared table, the L2 is the building's pantry and the DRAM is the warehouse across town, connected by a single avenue: the bandwidth. Hiring more cooks does not help if the ingredient truck does not arrive in time. In decode, that is exactly what happens.

Threads, warps and CTAs: how the work is cut

A kernel is a function that runs in thousands of copies at the same time. Whoever writes it decides how to cut the work, on three levels:

  1. Grid. It is the whole launch, a grid of CTAs (thread blocks). Each CTA gets an independent piece of the problem, for example a 128×128 tile of a GEMM's output.
  2. CTA. Up to 1,024 threads that run together on a single SM, share the same shared memory and can wait for each other at a barrier (__syncthreads()). A CTA is never split across SMs.
  3. Warp. The SM executes threads 32 at a time. A warp is a group of 32 lanes that receive the same instruction in the same cycle, each with its own data. This is the SIMT model.

For performance, the unit that matters is the warp. If an if sends half the lanes down one path and half down another, the warp executes both paths in sequence, with half the lanes switched off in each. That is divergence. Because the 32 lanes march together, they can also exchange register values directly, without going through memory, using the shuffle instructions: __shfl_xor_sync(mask, v, m) hands each lane the v of the lane whose index differs from its own by an XOR with m.

The XOR shuffle has the exact shape of a butterfly of the fast Hadamard transform, the same rotation EXL3 applies to activations (Rotations, trellises and EXL3). At stage \(s\), each lane talks to the partner that differs from it in bit \(s\):

\[ p = \ell \oplus 2^{s}, \qquad v_\ell^{(s+1)} = \begin{cases} v_\ell^{(s)} + v_p^{(s)} & \text{if bit } s \text{ of } \ell \text{ is } 0\\[2pt] v_p^{(s)} - v_\ell^{(s)} & \text{if bit } s \text{ of } \ell \text{ is } 1 \end{cases} \qquad y = \tfrac{1}{\sqrt{n}}\; v^{(\log_2 n)} = H_n\, x \]
  • \(\ell\): lane index (0 to 31 in a warp); \(p\): the partner lane; \(\oplus\): bitwise XOR
  • \(v_\ell^{(s)}\): the value lane \(\ell\) holds in a register before stage \(s\)
  • \(n\): vector size (a power of 2). After \(\log_2 n\) stages, the warp has computed \(H_n x\), the normalized Hadamard transform

In the figure, each column is a lane and each row is a stage. Advance the stage and follow the arrows: no lane reads memory, the values pass from register to register.

Notice that the number of stages grows with \(\log_2 n\): 3 for 8 lanes and 5 for a whole warp. With four values per lane, two stages inside the thread itself and five shuffles across lanes, a warp does a 128-point Hadamard (\(4 \times 32\), \(2 + 5 = 7 = \log_2 128\) stages) without touching shared memory. That is the fat_had_ff_128 in the epilogue of GLM's E2 kernel.

In the recipe: how GLM cuts an expert GEMM

First, the vocabulary. In GLM's MoE, an expert is thin when it receives few rows (tokens), up to EXL3_TEMP_ROWS_FUSED (32 with E3 in the current launcher), and it runs in the fused kernel exl3_moe, the same one used in decode. It is fat when it receives more rows than that, which happens in prefill. For fat experts the recipe has three tiers: E1 (EXL3_FAT_BATCHED, which copies the per-expert counts on a side stream), E2 (EXL3_FAT_KERNEL, a direct GEMM over the trellis weights) and E3 (EXL3_FAT_GROUPED, grouped kernels exl3_fat_moe_* with no CPU synchronization). The E2 kernel (exl3_fat_gemm) uses CTAs of 256 threads, or 8 warps, with a 128×128 output tile, and advances along K 16 at a time. Each warp owns a block of 16 columns: it copies the 16×16 tiles of the quantized weight into shared memory, dequantizes them in its own registers and feeds the tensor core. In the epilogue, the per-row 128-point Hadamard combines a butterfly of 4 inside each thread with shuffle_had_f2x32 across lanes, the same pattern as in the figure. E3 (exl3_fat_moe) follows this division of work. The mainloop in detail is in Kernels.

Deep dive: each thread's index has a size too

Each thread computes its own address with index arithmetic (blockIdx.x * blockDim.x + threadIdx.x, block_idx * block_stride…). With a 1M-token context, these products exceed \(2^{31}\) and silently overflow a 32-bit int. DeepSeek's Stage-C overlay (lane B, recipe/overlay/…/common/ops/cache_utils.py) fixes this by promoting to int64 the products block_idx * block_stride (exceeds \(2^{31}\) with ≥ 57 thousand blocks) and batch_idx * out_stride0. The corresponding code in the production image (lane A) is not in the repository, so there is no way to check whether it does the same. The lesson applies to any kernel: the GPU does not complain about a negative index, it just reads or writes in the wrong place.

Where data lives: registers, shared memory, L2 and DRAM

Each level of the memory hierarchy trades capacity for speed. From top to bottom:

Registers
Private to each thread and read at the pace of the instruction itself. The SM has a file of 65,536 32-bit registers (256 KB), split among all resident threads, and each thread can use up to 255. (Public specification of recent compute capabilities.)
Shared memory / L1
Fast memory in each SM, visible to all threads of the CTA and managed by the programmer. This is where GEMM tiles sit “on stage”. On consumer Blackwell (12.x) it reaches ~100 KB per SM; on Hopper and datacenter Blackwell, ~228 KB. (Public compute capability table.)
L2
A single cache, shared by all SMs, in front of the memory controllers.
Global memory (DRAM)
The GB10's 128 GB of LPDDR5X, where weights, KV cache and activations live. It is the slowest and the most distant, with ~273 GB/s theoretical for the whole chip, shared with the CPU.

Getting close to DRAM bandwidth depends on how the kernel reads. Global memory does not deliver loose bytes: it delivers 32 B sectors, grouped into 128 B lines. When the 32 lanes of a warp read 32 consecutive 4-byte words, the request becomes a single 128 B line. That is coalesced access. If the lanes read scattered addresses, each one may pull in a whole sector to use 4 bytes of it, and traffic can grow by as much as 8×. Decode kernels store weights in a layout where each warp reads contiguous chunks, and that is what keeps them close to the effective ~230 GB/s (tile layouts are in Kernels). The L2 also helps less than it seems. In decode, each weight passes through it only once per step, with no reuse, because a step's weight set (gigabytes) is much larger than the cache. What benefits from the L2 is data reused within the step, such as activations, scales and chunks of the KV cache.

In the recipe: choosing what each cache keeps

In the TensorFold version of GLM, two patches change only where the bytes are when the computation needs them, without touching a bit of the result. The first exploits the reuse that prefill has. In the prompt EXL3 expert kernel, the column blocks of the same item reread the same activation rows (an item is up to 16 rows routed to the same expert: 16 × 4,096 × 2 B = 128 KiB in FP16, our arithmetic). With the item in blockIdx.x, the dimension that varies fastest in the launch order, the blocks dispatched together belonged to different items (dispatch roughly follows index order), and in a chunk of thousands of rows an item's rows left the L2 before they were reread. Swapping the dimensions (TF_GLM_EXL3_NFIRST=1) puts an item's blocks side by side: same kernel, same arithmetic, and the kernel got 2.3–2.5× faster at 4,096 rows. The prompt kernels that came later (glm-prompt-kernels, now the default prefill path) are born with this grid: column blocks in x, items in y. The second applies to decode, where each byte of the trellis is read once per window. The expert kernel now reads the trellis in 16 B loads through the read-only path, with ld.global.nc.L1::no_allocate, which does not fill the L1 with data that will not come back, and one k step ahead (TF_GLM_EXL3_LOADS=nc, a non-coherent load). On its own, this took prose from 48.36 to 48.78 tok/s and code from 59.54 to 60.42. The launch-order figure and the load loop are in Kernels.

A DRAM access costs hundreds of cycles, and the GPU does not sit around waiting. When a warp stalls waiting for data, the scheduler switches, at no cost, to another ready warp. This is called latency hiding, and it only works with many resident warps. Little's law says how many bytes need to be “in flight” for the DRAM avenue to run full:

\[ \text{bytes in flight} = B \times L \qquad \text{(illustrative: } 273\ \tfrac{\text{GB}}{\text{s}} \times 500\ \text{ns} \approx 137\ \text{KB} \;\Rightarrow\; \approx 2.8\ \text{KB per SM)} \]
  • \(B\): the bandwidth you want to sustain
  • \(L\): mean latency of a DRAM access. The 500 ns is an illustrative value, not a GB10 measurement
  • The result is how many bytes of pending reads the 48 SMs need to keep outstanding at all times

How many warps fit on an SM is the occupancy, and it is limited by whichever resource runs out first:

\[ n_{\text{CTA/SM}} = \min\left( \left\lfloor \frac{R_{\text{SM}}}{r \cdot T} \right\rfloor,\ \left\lfloor \frac{S_{\text{SM}}}{s} \right\rfloor,\ \left\lfloor \frac{W_{\max}}{T/32} \right\rfloor \right), \qquad \text{occupancy} = \frac{n_{\text{CTA/SM}} \cdot T/32}{W_{\max}} \]
  • \(R_{\text{SM}}\): registers per SM (65,536); \(r\): registers per thread; \(T\): threads per CTA
  • \(S_{\text{SM}}\): shared memory per SM; \(s\): shared memory requested per CTA
  • \(W_{\max}\): resident warps per SM, 48 on 12.x and 64 on 9.0/10.0 according to the public table. There is also a cap on CTAs per SM and allocation granularities, which the formula leaves out

In the calculator, raise the registers per thread until occupancy drops. Then lower the compiler's register cap and see what happens to traffic.

When the compiler cannot keep all of a thread's variables in the allowed registers, it spills: it writes the excess to local memory with STL instructions and reads it back later with LDL. The name is misleading, because “local” means private to the thread, but this memory lives in DRAM, behind the L1 and the L2. In a decode kernel, which already lives and dies by bandwidth, each LDL is one more trip to the warehouse across town.

KernelGLM53_EXL3_MOE_FAST=1

The SASS audit of the stock thin-decode kernel exl3_moe_kernel<4,256> on SM121 found real spilling: 128 registers, an 88 B frame, 37 STL and 39 LDL. The glm53_exl3_moe_fast_kernel version trades pipeline depth in registers for depth in shared memory, with 1 fragment stage instead of 3 and 8 SMEM stages instead of 3. It ends up with 127 registers, a 16 B frame, 6 write-only STL and 0 LDL, the same 1,024 B of SMEM and the same occupancy class. The layer got 8–17% faster, and decode rose +7.71%, +8.88% and +14.59% in three cells of the A/B/A2. Parity passed in 119/119 cases; the sealed numerical study came out INCONCLUSIVE. It is opt-in and applies only to TP2 on SM121.

Occupancy also depends on how many SMs there are. A launch table tuned for the 160 SMs of a GB300 asks for too many CTAs for the GB10's 48. Qwen shows the case: the stock decode profile of the sparse QSA kernel (block_n 16, 64 split-K partitions, 4 warps) launches ~5× more CTAs than the GB10 runs at once and still pays for a merge of 64 partials. The QSA_PROFILE=gb10 profile moves to (32, 16, 4), “≈1.3 waves instead of ≈5”, but it was not benchmarked. The wave math and split-K are in Kernels. On the DeepSeek side, the MoE runs on b12x, a library of kernels written in CuTeDSL for consumer Blackwell (SM120/121). In it, VLLM_B12X_W4A16_FORCE_BLOCKS_PER_SM (default 0, registered in the production image) forces how many CTAs of the W4A16 kernel stay on each SM: it is occupancy exposed as an environment variable, for experiments.

Trap: datacenter shared memory does not exist here

A kernel tuned for the ~228 KB of SMEM of an H100 or B200 may simply fail to launch on the ~100 KB of an SM 12.x, or launch with lower occupancy. GLM ran into this in the sparse indexer's persistent_topk: a chunk of 8,192 tokens with a long history overflows the GB10's SMEM (crash at 300k tokens of context). That is why the recipe never uses MAX_NUM_BATCHED_TOKENS=8192, and the video patch turns off the persistent top-k path for select_k ∈ {512, 1024, 2048}.

Constraint: 99 KiB per blocksm_121 · num_stages = 1

What it is. The ceiling on shared memory that a CTA can request on the GB10 (sm_121): 99 KiB, or 101,376 B, the smem/block (opt-in) field of the snippet at the start. In the TensorFold version of GLM, the patch that adapted the chunked KDA Triton kernels to the GB10 (glm-kda-chunked-gb10) did the arithmetic in a comment: the per-block loops, with pipelined loads, would need up to 154 KiB. It was an intermediate step, but it shows the constraint well.

Mechanism. In Triton, num_stages is the depth of the software pipeline: with S stages, the kernel keeps S input slices in shared memory and loads the next one while it computes on the current one. Each extra stage is one more buffer. With no room for them, the patch's launch table set one stage in every kernel. A block's loads and compute then take turns, and hiding latency is left to the other resident warps (interpretation).

Trade-off. The version the recipe runs today (glm-kda-chunked-kernel) replaced the Triton kernels with a single CUDA kernel: one 256-thread block per head, the 128×128 state in FP32 in registers (64 floats per thread), and the next sub-chunk's rows warmed into the L2 during the current one and copied into shared memory with 16 B cp.async. Against the serial kernel, chunked KDA (the three patches together) took the prefill of 50k tokens from 29.3 to 26.4 s, and that of 149k from 91.1 to 84.5 s (one boot each). You can read it as the dilemma of the vLLM recipe's FAST kernel seen from the other side (interpretation: the patch does not blame the switch on shared memory alone): there, registers ran short (there was spilling), and the pipeline depth moved to shared memory; here, shared memory was tight, and the state moved into registers. Chunked KDA is in Linear attention.

Tensor cores: the SM's matrix calculator

An ordinary floating-point unit does one multiply-add per lane per cycle. The tensor core computes an entire block of a matrix product: one MMA (matrix multiply-accumulate) instruction does

\[ D_{m\times n} = A_{m\times k}\; B_{k\times n} + C_{m\times n}, \qquad \text{FLOPs per instruction} = 2\,m\,n\,k \]
  • \(m, n, k\): the shape of the instruction, written as m16n8k16 (\(m=16\), \(n=8\), \(k=16\): 4,096 FLOPs at once)
  • \(A, B\): low-precision input fragments (FP16, BF16, FP8, FP4…)
  • \(C, D\): the accumulator, usually FP32, the high-precision accumulation from How the computer stores numbers

In mma.sync, the instruction belongs to the whole warp: each of the 32 lanes comes in with a piece of A, of B and of C in its own registers and leaves with a piece of D. No lane has the whole matrix. In the figure, the magnifier at the bottom shows the dot product that produces one cell of D. Turn on “color by lane” to see who holds what, and hover over D.

In NVFP4 mode, notice the scale matrices: 4 scales per row of A, 4 per column of B. This is Blackwell's block-scaled MMA. The instruction receives the FP4 codes and the scales and dequantizes inside the tensor core. On SM12x it is written mma.sync.aligned.kind::mxf4nvf4.block_scale.scale_vec::4X.m16n8k64.row.col.f32.e2m1.e2m1.f32.ue4m3, and the “4X” comes from \(k = 64\) split into blocks of 16.

\[ D_{ij} = \sum_{b=0}^{k/16-1} s^{A}_{i,b}\; s^{B}_{b,j} \sum_{t \,\in\, \text{block } b} a_{it}\, b_{tj} \;+\; C_{ij} \]
  • \(a_{it}, b_{tj}\): E2M1 codes, the 4-bit values from FP8, FP4 and microscaling
  • \(s^{A}_{i,b}, s^{B}_{b,j}\): UE4M3 scales of block \(b\) in row \(i\) of A and in column \(j\) of B
  • The inner 16-term sum runs in hardware; the scales come in before the FP32 accumulation

Each generation, a different calculator

From one generation to the next the speed changes, but so do which formats the calculator accepts and where it reads its operands from. A simplified summary:

Generation (CC)MMA instructionNew formatsOperands
Ampere (8.0)mma.sync, per warpFP16, BF16, TF32, INT8registers
Hopper (9.0)wgmma, group of 4 warps, asynchronousFP8 (Ada, 8.9, already had FP8 in mma.sync)shared memory (A may come from registers)
Blackwell datacenter (10.x)tcgen05.mma, asynchronous, issued by a single threadFP6, FP4, MX and NVFP4 with block scalingshared memory; accumulator in TMEM

The last row explains half the chapter. The GB10 has FP4 tensor cores, but it does not have tcgen05 or TMEM. The datacenter kernels built around them, such as FlashMLA (DeepSeek's MLA attention kernels), DeepGEMM's SM100 paths, MegaMoE and TensorRT-LLM's MoE (TRTLLM), have no way to run here. GLM's kernel lab records that the current CuTe implementation sends SM120/121 kernels to warp-level mma.sync, not to tcgen05. That is why GLM reuses ExLlamaV3's CUDA path instead of writing a new CUTLASS kernel.

GLM · EXL3

  • 4 bpw trellis weights, which is not a hardware format.
  • Dequantizes in registers and feeds mma.sync m16n8k16 FP16→FP32.
  • Uses the 16-bit tensor core: wins on bandwidth, not on FLOPs.
  • TensorFold reads the same EXL3 with its own kernels and the same design: the trellis decoded in registers (decode_tile) becomes mma.sync m16n8k16 fragments.

Qwen · NVFP4

  • NVFP4 experts run as W4A4, with the activation in FP4 as well.
  • FlashInfer's CUTLASS SM120 grouped GEMM, with block-scaled FP4 MMA.
  • Dense projections in BF16, via cuBLAS.

DeepSeek · MXFP4

  • Experts in fp4_e8m0_k32 (MXFP4).
  • b12x's FP4 tensor core path (the CuTeDSL kernel library for SM12x) only accepts a modelopt_nvfp4 source, so it runs W4A16: it dequantizes to BF16 and uses BF16 MMA.
  • In decode that is enough. In prefill it stays in the ~125 TFLOPS BF16 class, not the ~4× of FP4 (an estimated +30–60% with MXFP4×MXFP8).
Why it matters

The checkpoint format decides which calculator you use. With small M (decode), any path that reads 4 bits per weight will do, because the bottleneck is bandwidth. With large M (prefill), only a format the tensor core understands natively reaches the peak. When choosing a checkpoint for your new model, ask: “does this format have native MMA on my SM?”

Compute capability: the GPU's ID card

Every NVIDIA GPU has a compute capability (CC), a major.minor number that says which instruction set and features it offers. The compiler writes the same number as sm_XY. These are the ones that show up in the recipes:

CCTargetFamilyWhere it shows up in the recipes
9.0sm_90Hopper (H100)FlashMLA, FA3 (FlashAttention 3), PDL (Programmatic Dependent Launch: the next kernel starts its prologue before the previous one finishes), red.v4 (16 B atomics)

Going from 10 to 12 is not trading up to “a newer version”. They are two parallel Blackwell lineages. 10.x is the datacenter one, with HBM, tcgen05, TMEM and NVLink. 12.x is the consumer and workstation one, with warp-level mma.sync, smaller SMEM and no MNNVL (the NVLink that connects GPUs in different nodes). The GB10 is 12.1 and shares the consumer ISA with 12.0; DeepSeek's hotfix spells it out: SM120 and SM121 “share the consumer Blackwell ISA”. That is why the GB10 runs many 12.0 binaries and almost none built for 10.0.

The practical problem lies in the gates, the lines of code that ask for the capability and pick a path. A “Blackwell” gate that tests family(100) excludes the GB10. One that tests == (12, 0) misses 12.1 by a tenth. One that tests major >= 9 enables a feature on the GB10 that was only ever validated in the datacenter. Choose the GPU in the figure and see the real gatekeepers of the three recipes.

Read the GB10's pinks and reds as a to-do list, because each one turned into a patch, a fallback or a recipe decision. The subtlest case is Qwen's. The FP8 KV backport to v0.30 brings a launch table tuned on sm_120, but picks that table with _is_sm120(), which compares == (12, 0). The GB10 is (12, 1), so (going by the code) it stays on the default table, tuned on the GB300. Nobody measured the effect; the lesson is to look at the gate before concluding that “the sm_120 patch covers the GB10”.

GateEXL3_FAT_MOE_MIN_CAPABILITY = (9, 0)

The E3 tier for the prefill's “fat” experts sums the output of the down projection with 16-byte vector atomics (atomicAdd on float4, the red.v4 instruction). That way several experts write to the same token without a separate reduction. The instruction exists from sm_90 onward, and the gate tests exactly that: capability ≥ 9.0. Below that, the tier falls back to E2 and logs the reason. The image compiles for sm_121a, and on the GB10 (12.1) the gate passes.

PluginGB10_HYBRID_NVFP4_ALLOW_NON_GB10=0

The optional gb10_hybrid_nvfp4 plugin dispatches NVFP4 by M: below GB10_HYBRID_NVFP4_M_THRESHOLD (128) it uses Marlin W4A16, and from there on, CUTLASS W4A4. By default, _check_device() requires cc == 121 and fails fast on any other GPU, because the threshold was copied “from the community-reported sm_120 crossover” and the code itself asks for the benchmark to be redone on the GB10. Setting the flag to 1 unlocks other GPUs at your own risk. Two important caveats: the plugin does not apply to this recipe's checkpoint, because it serves ModelOpt NVFP4 checkpoints and DSV4 ships native MXFP4 experts; and it is opt-in (ENABLE_VLLM_GB10_PATCH=0 by default). The plugin's README says it was tested “for packaging only”, not on a live GB10. It serves here as an example of a well-written gate, not as a fast path in use.

How to write (and review) a gate

Ask what the code needs, not which GPU it is. If it is an instruction, red.v4 requires 9.0+ and >= (9, 0) is right. If it is an amount of SMEM, query the device attribute. If it is an ISA family, family(120) covers 12.0 and 12.1. Exact equality, such as == (12, 0), is almost always a bug waiting for the next chip.

From code to binary: PTX, SASS, cubin and the ARCH_LISTs

A .cu file goes through two compilers. nvcc translates C++ into PTX, a stable, virtual assembly, similar to bytecode. Then ptxas translates the PTX into SASS, the real machine code of one architecture, packaged in a cubin. A library usually carries several cubins and pieces of PTX in a single fatbin. When the kernel is loaded, the driver chooses:

  1. Compatible SASS. An sm_XY cubin runs on any GPU with the same major and a minor ≥ Y. That is why sm_120 runs on 12.1.
  2. PTX + JIT. With no compatible SASS, the driver compiles the embedded PTX for the GPU at hand. The first use is slower, and only features from that PTX version are available.
  3. Error. With neither SASS nor usable PTX, you get no kernel image is available for execution on the device.

Two suffixes change the rule. The a suffix (sm_121a) unlocks instructions specific to that exact architecture, such as block-scaled MMA. The price is that the binary runs only on that CC, not on a newer one, not on a neighbor. The f suffix (family, as in 12.0f) sits in between: features common to the family and compatibility within it. Build a fatbin and choose the GPU:

The figure shows the price of portability. The generic fatbin runs everywhere, but almost always via JIT and without the new instructions. 12.1a is the fastest possible on the GB10 and is useless anywhere else. The recipes, built for a single piece of hardware, pick the latter without hesitation.

Deep dive: --use_fast_math and rounding

The nvcc fast-math flag swaps expf for __expf, IEEE division for an approximate one, and flushes subnormals to zero. It is faster and changes the last bits. ExLlamaV3 compiles with it. GLM's E3 module (exl3_fat_moe_ext) is deliberately compiled without fast-math, and the epilogue computes the SwiGLU sigmoid with a double-precision exp and __fdiv_rn, which the flag does not affect. The goal is to reproduce the rounding of torch.sigmoid and keep E2's rounding boundaries bit for bit. Compiling is also a numerical decision (Measuring the damage).

Finally, the toolkit. All three images use CUDA 13.0 with cu130 wheels: torch 2.11.0+cu130 in DeepSeek, torch 2.13+cu130 in Qwen, base vllm/vllm-openai:glm53-flash-arm64-cu130 in GLM; the audited Qwen and DeepSeek kits run driver 580.x. The cu130 suffix means “compiled against the CUDA 13.0 runtime”, and an old nvcc does not even know the sm_121 target. In GLM, the toolkit headers live in the pip package nvidia/cu13/include, not in /usr/local/cuda/include. That is why the build exports CPATH/CPLUS_INCLUDE_PATH pointing at them (Dockerfile:429-431). A separate problem: ExLlamaV3 ships AVX2/AVX512 CPU targets (the CPU all-reduce) that do not compile on aarch64, and patch_exl3_ext_aarch64.py replaces them with stubs. The persisted JIT caches (Triton, TileLang, FlashInfer, DeepGEMM) are the subject of CUDA graphs and warmup.

The TensorFold version of GLM starts from a different base, the nvcr.io/nvidia/pytorch:26.07-py3 image, and compiles the engine's CUDA extensions on the first start of each image, which takes a few minutes and leaves the cache in a directory named after the image hash. Because each rank compiles on its own, the two could finish tens of seconds apart, more than the RDMA all-gather's wait tolerates. The cuda-roce-startup patch solves this with an NCCL barrier before each gather until the engine is ready. It is the CUTE_DSL_ARCH lesson again: compiling in the path of a collective holds up the other rank.

Bandwidth: HBM, LPDDR5X and the GB10 roofline

A memory's bandwidth is width times speed: how many bits the bus carries per transfer and how many transfers happen per second. In the DGX Spark, the LPDDR5X has a 256-bit bus at 8,533 MT/s (public specification), which gives

\[ B = \frac{256\ \text{bits}}{8} \times 8.533 \times 10^{9}\ \tfrac{\text{transfers}}{\text{s}} \approx 273\ \text{GB/s} \]
  • 256/8 = 32 bytes per transfer; 8,533 MT/s = 8.533 billion transfers per second
  • The result matches the ~273 GB/s theoretical figure the Qwen recipe report cites (GLM and DeepSeek work only with the effective bandwidth, ~230 and 230–250 GB/s)

LPDDR5X is the memory of phones and laptops: cheap, power-efficient, with lots of capacity (128 GB) and modest bandwidth. Datacenter GPUs use HBM, stacks of DRAM mounted next to the chip in the same package, with 1,024-bit interfaces per stack, reaching terabytes per second (public specification; no recipe runs on HBM). The difference is more than an order of magnitude, and it is what defines the GB10's game. The capacity lets it serve models with hundreds of billions of parameters; the bandwidth limits how fast each one can be read.

And the theoretical number is never the real one. The recipe reports measure or estimate ~230 GB/s effective (GLM), 235–245 GB/s (Qwen) and 230–250 GB/s (DeepSeek). Since CPU and GPU share the same DRAM, whatever the operating system and the page cache do also goes down the same avenue (Unified memory).

The roofline: the ceiling physics imposes

Every kernel reads bytes and does FLOPs. The minimum time is the larger of the two times, and the attainable performance is the smaller of the two ceilings:

\[ t \;\ge\; \max\!\left(\frac{Q}{B},\ \frac{F}{P}\right) \quad\Longleftrightarrow\quad \frac{F}{t} \;\le\; \min\left(P,\ I \cdot B\right), \qquad I = \frac{F}{Q}, \qquad I^{*} = \frac{P}{B} \]
  • \(Q\): bytes brought in from DRAM; \(F\): FLOPs; \(B\): bandwidth; \(P\): peak compute
  • \(I\): arithmetic intensity, in FLOPs per byte
  • \(I^{*}\): the ridge point (the ridge, for short). Below it the kernel is memory-bound; above it, compute-bound

With the GB10's numbers (\(P \approx 125\) dense BF16 TFLOPS, an estimate from the GLM repository, and \(B \approx 273\) GB/s), the ridge sits at \(I^{*} \approx 458\) FLOP/B. Just to break even with compute, a kernel has to do 458 operations for every byte it brings in from DRAM. This is the roofline that the prefill and decode chapter introduced, now with the machine's numbers.

GEMM versus GEMV, revisited

Consider a linear layer \(y = xW\), with \(W\) made of \(K\times N\) weights of \(b\) bits and \(M\) activation rows (tokens). It does \(2MKN\) FLOPs and reads at least \(KN\,b/8\) bytes of weights. With small \(M\), the weights dominate the traffic:

\[ I(M) = \frac{2MKN}{KN\,\frac{b}{8} + 2M(K+N)} \;\approx\; \frac{16\,M}{b} \qquad (M \ll K, N) \]
  • \(M\): rows that share the same read of the weights (tokens in the batch, or the rows an expert receives)
  • \(b\): bits per weight: 16 in BF16, 8 in FP8, ~4.5 in NVFP4 with the scales, 4 in 4 bpw EXL3
  • \(2M(K+N)\): bytes of BF16 activations read and written

With \(M = 1\), a GEMV (the decode of a single sequence), \(I \approx 1\) FLOP/B in BF16, and the GB10 would use 0.2% of its peak. Quantizing to 4 bits multiplies \(I\) by 4 and, more importantly, divides the bytes by 4. That is why quantization speeds up decode almost linearly. Only with hundreds of rows does the GEMM cross the ridge. Move M and the format in the chart:

The “GLM prefill MoE” point is a lesson in itself. With chunks of 1,024 tokens and top-8 among 288 experts, each expert receives ~28 rows on average. With 4 bpw weights, \(I \approx 4 \times 28 = 112\) FLOP/B, well below 458: even in prefill, the experts are memory-bound. The GLM report estimates 75.6 GB touched per GPU per chunk (≥ 330 ms at ~230 GB/s) and measures 947 tok/s of prefill, ≈ 34 TFLOPS summed over the two nodes, ~14% of BF16 peak. The proposed way out is the one the formula suggests: larger chunks (more \(M\) per expert) and grouped kernels (Kernels).

Why decode is bandwidth-bound: the step cost model

Now put it all together in a calculation that predicts tokens per second. In decode, each step runs the whole model once for all active sequences, plus the speculation's verification tokens. The step time is the time to bring the bytes in from DRAM, plus fixed costs that do not depend on bandwidth:

\[ t_{\text{step}} \approx \frac{\sum_i Q_i}{B_{\text{eff}}} + t_{\text{fixed}}, \qquad \text{tok/s per sequence} \approx \frac{\tau}{t_{\text{step}}} \]
  • \(Q_i\): bytes each component (experts, attention, lm_head…) reads per GPU at every step
  • \(B_{\text{eff}}\): the effective bandwidth, not the theoretical one
  • \(t_{\text{fixed}}\): NCCL collectives (which cross the CX7 link between the nodes: ~12–16 GB/s with the default single HCA, 25 GB/s only with both PFs), launches and synchronizations
  • \(\tau\): tokens per step (accepted drafts + 1 from the target): 1 without speculation, more with MTP or DSpark (Speculative decoding)

This step cost model is what the recipes' audit reports worked out, starting from the checkpoints' safetensors headers. Choose the scenario and play with the effective bandwidth and the acceptance.

Qwen is the textbook case. Per GPU and per step (batch 1, MTP=3): the lm_head, read 4 times, adds up to 2.36 GiB (26%); the routed experts, ~2.1 GiB (23%); the GDN projections, 1.95 (21%); the replicated HyperConnections, 1.19 (13%); attention and indexer, 0.60; the MTP, ~0.5; router, shared expert and the PLE projection, 0.40; and the GDN state, 0.1. Total: ≈9.2 GiB. At 273 GB/s that takes 36 ms; at the real 235–245 GB/s, 40–42 ms, or 24–25 steps/s. Each step emits ≈3.2 tokens (2.2 accepted drafts + the bonus token), which would give ~76–80 tok/s from streaming alone. The measured value with MTP=3 is 52.1 tok/s, with steps of ~60 ms (59.3 ms on prose and 60.7 on code, with the full vocabulary): ~1/3 of the step goes to something other than reading weights. The report concluded that batch-1 decode “is already at the bandwidth roofline” because it multiplied only the 2.2 accepted drafts and compared against an old 55.8, measured without MTP (see Benchmarking).

DeepSeek repeats the story with a different cast. There are ≈12 GB of experts (up to 42 distinct ones, out of 256, per layer, × 6.7 MB per rank × 43 layers), ≈2.4 GB of attention, ≈0.9 GB for the drafter, ≈1.06 GB of lm_head and ≈0.2 GB for the Markov head: 16.5–17 GB per rank per step, 68–74 ms at 230–250 GB/s. With τ ≈ 4.15 tokens per step (≈3.15 accepted drafts + the bonus), streaming alone would cap it at ~56–61 tok/s; the measured range was 62–83. The engine counters later saw 14–15 steps/s (67–71 ms) and 76 tok/s on code at 73.3% acceptance — ~5.2 tokens per step on that workload, which accepts more drafts than the probe's prose. (The report attributes the headroom to an effective bandwidth better than assumed; see Benchmarking.) The report's diagnosis: “c=1 is ~80% weight streaming”. The rest, ~10–15 ms according to the same report, is fixed cost; the ≈108 collectives per step alone, at 30–50 µs each, already add up to 3–5 ms (docs/CLAUDE/fable5-1-report.md §2). The report's numbers do not add up perfectly. It cites measured steps of 58–65 ms at c=1, close to what streaming alone would take at the theoretical bandwidth (16.5 GB ÷ 273 GB/s ≈ 60 ms), and adding 10–15 ms of fixed cost to the estimated 68–74 ms would overshoot that (and the counters' 67–71 ms). Interpretation: part of the estimated bytes do not come out of DRAM at every step, or part of the fixed cost overlaps with streaming. The cost model gets the order of magnitude right and points to the bottleneck; it is not a stopwatch.

Why it matters: the lesson of TP=3

With three nodes, each rank reads about 1/3 less (≈11.5 GB, ≈48 ms of streaming), but the measured step came in at ≈61 ms (64 tok/s ÷ 3.9 tokens per step). The ~13 ms of fixed cost (3-rank ring, heads padded from 64 to 72) wiped out the gain. When the bytes per rank shrink, \(t_{\text{fixed}}\) is what decides. That is the subject of Beyond 2 nodes.

The equation also lists the levers, and each one gets a chapter of its own:

  1. Fewer bytes per step. Quantizing the dense paths (Qwen's FP8-dense: 9.2 → 5.7 GiB, ~85–90 tok/s analytical, never measured) and no longer rereading the lm_head (the drafter's reduced vocabulary, in MTP, EAGLE and cheap drafts).
  2. More accepted tokens per step. A larger \(\tau\) comes from better drafters (DFlash2 and DSpark).
  3. More sequences per step. Weights read once serve every sequence in the batch, and aggregate tok/s rises almost for free until the number of distinct experts grows (Scheduler and batching).
  4. Less fixed cost. Collectives, launches and synchronizations: the next section and Communication. In the TensorFold version of GLM , decode's small all-gathers leave NCCL (45 µs for 16 KiB) and become a one-shot RDMA write (11 µs), for +6% decode.

Two queues and a clock: streams, synchronization and pinned memory

What remains is the \(t_{\text{fixed}}\) that happens inside a node. CPU and GPU work asynchronously: the CPU does not execute kernels, it launches them onto a stream, a queue the GPU consumes in order, and moves on. Three rules govern this relationship:

  1. On the same stream, everything happens in series. Kernel 2 only starts when kernel 1 finishes, which guarantees nobody reads a half-written tensor.
  2. Different streams can overlap if there are free SMs. Ordering between them is expressed with events: one stream records an event and the other waits for it, without involving the CPU.
  3. If the CPU needs a value from the GPU, it stops. .item(), .tolist(), .cpu() or an if tensor: force a host-device synchronization. The CPU waits for the queue to drain, reads the number and only then goes back to launching, and in the meantime the GPU sits idle.

In decode the kernels are short: Qwen's whole step lasts ~40 ms for dozens of layers, and a DeepSeek prefill chunk fires ~1,500 launches. A small kernel may also fail to fill the chip, because a decode GEMM with few CTAs leaves a good part of the 48 SMs idle. The figure shows three remedies from the recipes, in an illustrative composition.

Turn each remedy on and off and watch the step shrink. In all three cases, the gain comes from the CPU never having to stop and look at a number.

  • Auxiliary streams. DeepSeek's Stage-C overlay (lane B, recipe/overlay/…/nvidia/model.py:1700-1709) creates 3 CUDA streams for the attention input GEMMs that do not depend on one another: the compressor's kv_score, indexer.weights_proj and the indexer compressor's kv_score. fused_wqa_wkv stays on the default stream, and the streams are turned off on ROCm/XPU because of hangs. The motivation (our interpretation): small GEMMs that on their own do not fill 48 SMs now share the chip, and step latency drops. It is an example of a technique, read in the overlay's code; the model code in the production image (lane A) is not in the repository, so we cannot check whether it does the same.
  • Deciding on the device. In lane A, DeepSeek's hotfix #175 classifies image tokens once per forward, “instead of 43 host-device syncs”. #31 v2 (opt-in, DSPARK_ENABLE_ISSUE31_GPU_HOTFIX=1) keeps the thinking budget in UVA/staged tensors and enforces it with two Triton kernels, with no D2H copy at every step. The overlay (lane B) shows the same idea in two variables: VLLM_DSPARK_GPU_REJECTED_CONTEXT_MASK masks the rejected rows of the drafter's ring buffer on the GPU, without bringing rejection counts to the CPU, and, going the other way, VLLM_DSPARK_COLLECT_CONFIDENCE_DIAGNOSTICS=1 copies confidences to the CPU at every step and “costs a sync”, which is why it is for diagnostics only. Careful: both exist only in the overlay's envs.py. In the production image they are no-ops, and turning them on there changes nothing beyond a warning in the log.
  • Asynchronous copy to pinned memory. A GPU→CPU copy is only truly asynchronous if the destination is pinned memory (page-locked): the copy engine does DMA directly, without the CPU. With ordinary pageable memory, the driver goes through an intermediate buffer, and the copy becomes, in practice, synchronous. The same principle shows up in weight loading: GLM's InstantTensor loader reads the safetensors via O_DIRECT into a ring of pinned buffers, with many reads in flight (Unified memory).

GLM's E1 tier (EXL3_FAT_BATCHED, default 0) is the third remedy in code. Routing produces the per-expert counts; the CPU needs them to dispatch the fat experts, but the thin experts can start right away:

host = torch.empty(n, dtype=counts.dtype, device="cpu", pin_memory=True)  # allocated once
with torch.cuda.stream(side):
    side.wait_stream(torch.cuda.current_stream())   # event: wait for routing
    host.copy_(counts, non_blocking=True)            # DMA in parallel
_exl3_moe_launch(...)                                # thin experts already queued
side.synchronize()                                   # wait only for the small copy
counts_host = host.tolist()

It is the same .tolist(), but after the GPU has already been given work to keep it busy. At the other extreme, the legacy prefill path (apply_exl3_python_loop, used for experts with more rows than EXL3_TEMP_ROWS_FUSED: 128 at the time of the prefill report, now 32 with E3 in the launcher) does a .tolist() per layer before anything else, one of the reasons for E3, with tables computed on the device (Kernels).

On the GB10, host and device are the same RAM

With UVA, CPU and GPU see a single address space, and a kernel can read or write directly into a pinned host buffer. On the GB10, where the physical memory is already the same, this is especially cheap. But not everything is there: the GB10 reports CU_DEVICE_ATTRIBUTE_CAN_USE_STREAM_MEM_OPS = 0, that is, it lacks the stream memory operations (cuStreamWaitValue32/WriteValue32) that would let GPU and CPU synchronize through flags. This broke the offload of Qwen's PLE table, a story told in Unified memory.

In the recipe: GPU, CPU and network card agreeing through flags

Without cuStreamWaitValue32, GPU and CPU can still synchronize through flags in pinned memory, as long as the kernel itself reads and writes those flags in the right order. The TensorFold version's one-shot all-gather (the cuda-roce-allgather patch, on top of b12x's RoCEnante transport) does this in a single kernel call. On the GB10, the GPU addresses pinned memory directly, and the network card registers it for RDMA. Each block copies its part of the shard into a send slot. The last block to arrive (it finds out through a counter with atom.relaxed.gpu) executes fence.sc.sys and writes the sequence number into a doorbell. A proxy thread on the CPU sees the doorbell and has the network card write the shard into the other Spark, followed by a 4-byte flag on the same reliable channel, which is why the flag never becomes visible before the data. On each GPU, one kernel thread per peer (and per rail) waits for the flag from the other side with ld.acquire.sys, and then the blocks copy the shards in rank order. At the end, the last block advances an epoch on the device with st.release.gpu, so that a CUDA graph can replay the exchange. Each instruction's suffix is the scope of the ordering it promises: .gpu holds among threads of the same GPU, which is all the counter and the epoch need; .sys holds for the whole system, CPU included, and costs more. The result is 11 µs per 16 KiB all-gather, against 45 µs for NCCL, which on the GB10 stages through the host for lack of GPUDirect RDMA, and +6% decode. The price is maintaining a transport of your own, with failure modes of its own: a wait that runs too long “poisons” the runtime on purpose. The full protocol is in Communication and in An exact engine.

Deep dive: occupancy and launches add up

A decode step is a sequence of hundreds of short kernels. Each one pays the launch cost on the CPU and, if it has few CTAs, uses only part of the SMs. The recipes attack both. CUDA graphs record the whole step and replay it with a single call (CUDA graphs and warmup). PDL and streams overlap neighboring kernels; GLM turns PDL off on SM12x because it “races” the state kernels of KDA, GLM's linear attention (Linear attention; PDL in detail is in Kernels).

A stream that does not compute: prefetching into the L2

The step cost model adds \(\sum_i Q_i / B_{\text{eff}}\) and \(t_{\text{fixed}}\) as if one waited for the other. In decode that is almost true, and the TensorFold version of GLM shows where the gap is. A layer alternates DRAM-bound matmuls (projections, shared expert, routed experts, the head) with phases in which the DRAM sits idle: the layer's two all-gathers (the wait on the network), the hyper-connection glue, the router and top-k, the KDA recurrence and the latent attention core. In those phases the avenue is empty, and the SMs are busy with something else or waiting for the other Spark.

The glm-l2-prefetch patch, adapted from a third-party project and turned on in the recipe by TF_GLM_L2PF=1, takes advantage of those phases. At three points in each layer, a small kernel on a side stream asks the memory system to bring into the L2 the weights the main stream will read next: this is L2 prefetch. That kernel neither computes nor writes anything. It only issues reads, with one of three instructions: cp.async.bulk.prefetch.L2 (one request per piece of memory, which the TMA unit walks; sm_90+, the recipe's mode), prefetch.global.L2::evict_last (line by line, with a hint to be the last to leave the cache) or ld.global.cg (an ordinary load, which stays in the L2 and not in the L1). When the next matmul starts, part of its bytes are already in the L2. The three points are:

o · during the recurrence or the attention core
The attention's output projection (in DSA, also the value half of kv_b, which is read before it).
a · at the attention all-gather
The FFN's hyper-connection weights and norm, the router, and the shared expert's gate/up and down.
f · at the FFN all-gather
The next layer's input weights; after the last layer, the final norm and the head.

Three details show the L2 becoming a programmed resource, not just a cache. The first is the budget: up to 8 MiB per point (TF_GLM_L2PF_MB), small tensors first (scales, biases, norms), then the leading bytes of the large matrices. The second is the order: with the prefetch on, the MoE runs the shared expert before the routed ones, or else the routed experts' stream of more than ~100 MB would evict from the L2 what was brought in for it. The third is waves. The code notes that 192 programs fit at once on the GB10 (4 CTAs per SM × 48 SMs). When the next 4-bit matmul fits in one wave, the prefetch brings forward the start of each slice a program will read, not just the start of the tensor, because in a wave the time is that of the slowest program. The side stream is forked at the point (side.wait_stream(main)) and joined before the forward ends, so that the branches of a CUDA graph come together. Windows of more than 64 rows and prompt chunks skip the prefetch.

Measured in the recipe, on its own and with 1 request: prose from 48.36 to 49.46 tok/s and code from 59.54 to 61.08 (two boots each), with the same bits. These are development A/Bs noted in config.sh, with a tool and load the repository does not detail, and the baseline (48.36) does not match the 60.4 tok/s the README publishes for sparkDash; read them as each knob's incremental effect, not as terms to add up. Added to the non-coherent loads from the memory section and to RDMA all-gathers of up to 512 KiB (TF_ROCE_MAX_KB=512), it comes to +2.7% on prose and +3.3% on code; with 4 requests, from 74.8 to 76.6 and from 100.0 to 102.7 tok/s.

Why the gain is small, and why it is worth it anyway

The prefetch only fills the phases in which the DRAM would sit idle; in the rest of the layer, the matmuls already read close to the ceiling. A third-party project that runs GLM-5.3-Flash (an abliterated EXL3 checkpoint) on TensorFold 0.3.4 with its own patches (jayleaton/glm53-tensorfold-spark, where the patch was adapted from) measured, on its own engine, the large kernels reading at 205–217 GB/s against a read ceiling of 235 GB/s. It also measured that the transport of one exchange between the Sparks takes 10.8 µs and that the rest of the wait is misalignment between the ranks. Hence the ~2–3% (interpretation). Compare with the remedies in the previous figure: DeepSeek's auxiliary streams split the SMs among small GEMMs, and the E1 copy overlaps DMA with compute. TensorFold's side stream splits the DRAM's time and touches no result at all, which, in an engine that promises identical bits, makes it a risk-free optimization. The cost is engineering: knowing ahead of time which addresses the next kernel will read, reordering the MoE so the L2 does not throw away what was brought in, and staying within budget. Too much prefetch turns into traffic competing for the same avenue.

Roadmap for your new model

  1. Identify the machine. Run the get_device_properties snippet: CC, SMs, registers and SMEM per SM, memory. Write down the effective bandwidth from a simple copy test, not the spec sheet's.
  2. Build the cost model before anything else. Read the safetensors headers (Checkpoints), add up the bytes each GPU reads per step and divide by the effective bandwidth. That is your tok/s ceiling. If the measured value lands far from it, look for fixed cost.
  3. Check the format against the tensor core. Decode with 4-bit weights works through any path. Fast prefill requires a format with native MMA on SM12x (FP8, NVFP4, MXFP4 with kind::mxf8f6f4) or a large enough M.
  4. Hunt for the gates. In the kernels the model uses, grep for get_device_capability, is_device_capability_family, _is_sm1 and major. List the ones that exclude 12.1 and decide between patching, falling back or accepting it.
  5. Pin the compile targets. Use TORCH_CUDA_ARCH_LIST=12.1a, FLASHINFER_CUDA_ARCH_LIST=12.1a and CUTE_DSL_ARCH=sm_121a if there is CuTeDSL. Persist the JIT caches and verify the binaries: cuobjdump --list-elf lists the architectures in a .so, and a self-test on the GPU closes the loop.
  6. Watch registers and SMEM. -Xptxas -v shows registers, spills and SMEM per kernel. Chunk sizes (MAX_NUM_BATCHED_TOKENS) and tile sizes must fit in the ~100 KB of an SM 12.x. GLM's kernel_lab/exl3/benchmark.py shows the method: sweep tile shapes and SM quotas (a quarter, half, all) and decide by measurement.
  7. Get the CPU out of the way. No .item()/.tolist() on the hot path, D2H copies into pinned memory on a side stream, streams for small independent GEMMs. Then, CUDA graphs.

One character has shown up in almost every section: the DRAM the GPU shares with the CPU. On the GB10 it is a single 128 GB pool for both processors, and that changes what gpu_memory_utilization means, how weights are loaded and what happens when memory runs out. That is the topic of Unified memory: CPU and GPU in the same RAM.
