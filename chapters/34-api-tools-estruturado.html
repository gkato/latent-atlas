Tudo o que vimos até aqui (pesos quantizados, KV paginado, scheduler, prefix cache) existe para um momento só: um cliente manda um JSON por HTTP e espera outro JSON de volta. Esse cliente pode ser um chat, um agente de código ou um benchmark. Ele nunca vê tensores, só texto, campos e códigos de status. Este capítulo abre essa porta. Você vai ver como mensagens viram tokens, como tokens voltam a ser texto, como o raciocínio é separado da resposta, como o modelo “chama ferramentas” e como uma gramática consegue garantir um JSON válido. Vai ver também por que as três receitas acumulam tantos patches justamente aqui: é na fronteira da API que um detalhe pequeno (um stop que dispara cedo demais, um token de sintaxe sorteado com temperatura, um lote especulativo que passa do fim da gramática) vira uma falha silenciosa para o usuário. E como a receita do GLM ganhou uma segunda versão sobre outro motor, o TensorFold , você também vai ver como um servidor que promete a mesma resposta com ou sem rascunhos resolve essas fronteiras de outro jeito: tool calls que só saem inteiras, um raciocínio que o servidor devolve quando o cliente o joga fora e uma chamada quebrada no histórico que deixa de travar a conversa.

Um servidor que fala “OpenAI”

Quase todo cliente de LLM fala o mesmo dialeto: a API HTTP que a OpenAI popularizou. Um servidor compatível com OpenAI implementa as mesmas rotas e os mesmos campos JSON, então basta trocar a base_url para que o mesmo SDK, o mesmo agente ou o mesmo benchmark converse com outro modelo. O vllm serve sobe exatamente isso: um servidor FastAPI/uvicorn (o API server que você conheceu em Por dentro do vLLM) na frente do EngineCore.

/v1/models
GET. Lista os nomes que o servidor aceita no campo model, isto é, o que você passou em --served-model-name.
/v1/chat/completions
POST. A rota principal. Recebe messages (papéis system/user/assistant/tool), aplica o template de chat e gera.
/v1/completions
POST. A rota “crua”: recebe um prompt já em texto e não aplica template. É ótima para experimentos causais, porque você controla cada byte do prompt.
/v1/responses
POST. A API mais nova (usada por agentes como o Codex), com itens tipados e estado opcional no servidor. Ela tem uma seção própria mais adiante.
/tokenize
Utilitário montado na raiz, fora de /v1 (assim como /detokenize). Recebe prompt (ou messages) e devolve os IDs.
/health
Prontidão: o launcher faz polling até receber 200. Vizinhos: /metrics (Prometheus), /version e /docs (a documentação interativa do FastAPI, que a receita Qwen lista entre os endpoints do head).

Um fato de design molda tudo o que vem depois: a API de chat é stateless. O servidor não se lembra da conversa. A cada turno o cliente reenvia o histórico inteiro, com system prompt, ferramentas, respostas anteriores e resultados de ferramentas. Pode parecer desperdício, e seria, se não fosse o prefix caching, que reconhece o prefixo repetido e pula o prefill correspondente. Por isso tantas decisões deste capítulo são julgadas pela pergunta “isso muda os bytes do começo do prompt?”.

Na figura abaixo, siga um pedido do começo ao fim. Cada estação é uma peça do API server ou do motor. Repare onde entram as máscaras, os stops e os parsers, porque cada seção do capítulo aprofunda uma dessas estações.

Nome, endereço e porta

Três flags definem “onde” e “como” o modelo aparece. --served-model-name é o id público. O cliente precisa mandar exatamente esse texto em model, senão recebe 404. A flag aceita vários aliases (a receita DeepSeek documenta aliases separados por espaço). A resposta usa o primeiro, e os probes, o warmup e o smoke da receita também. --host é a interface de rede em que o servidor escuta: 127.0.0.1 só aceita conexões da própria máquina, 0.0.0.0 aceita de qualquer interface. --port é a porta TCP (o default do vLLM é 8000; as três receitas usam 8888). Em inferência multi-nó, só o head (rank 0) serve a API. O worker sobe com --headless, sem servidor HTTP.

  • --host 0.0.0.0 --port $PORT, PORT=8888
  • O preflight confere se a porta está livre.

Armadilhas pequenas, efeitos grandes

O launcher DeepSeek normaliza a porta com $((10#$VLLM_PORT)). Em bash, um número com zero à esquerda (“08888”) seria lido como octal e daria erro, e o prefixo 10# força a base decimal. Scripts de benchmark antigos da mesma receita ainda têm deepseek-v4-flash-0731 como nome default e precisam de --model deepseek-v4-flash-vision-exp. Um nome errado não degrada nada: o servidor simplesmente responde 404.

Campos além do padrão: extra_body e vllm_xargs

O vLLM aceita campos que a OpenAI não define: chat_template_kwargs, structured_outputs, bad_words, vllm_xargs, thinking_token_budget… No SDK Python eles vão em extra_body, uma opção do SDK que mescla o conteúdo no nível de cima do JSON. Em HTTP cru, mande esses campos direto no topo. Um objeto literal "extra_body": {…} no corpo é um erro comum que o README do GLM documenta. Já vllm_xargs é um dicionário livre que chega aos parâmetros de amostragem e permite a overlays adicionarem opções por requisição sem quebrar clientes. Um exemplo é o {"skip_writing_prefix_cache": 1} do GLM, que o capítulo anterior explica.

from openai import OpenAI
cli = OpenAI(base_url="http://head:8888/v1", api_key="sk-…")
r = cli.chat.completions.create(
    model="GLM-5.3-Flash-EXL3",
    messages=[{"role": "user", "content": "Quanto é 17 + 25?"}],
    max_tokens=32768,
    extra_body={                                   # o SDK "achata" isto no topo do JSON
        "chat_template_kwargs": {"enable_thinking": True, "reasoning_effort": "low"},
        "vllm_xargs": {"skip_writing_prefix_cache": 1},
    })
print(r.choices[0].message.reasoning, r.choices[0].message.content)

O /tokenize merece nota. No GLM, /v1/tokenize dá 404: a rota vive na raiz e valida prompt, não text. A resposta traz count, tokens e max_model_len. A receita Qwen usa essa rota para calibrar prompts de contexto longo (cerca de 25 tokens por linha no bench/longctx.py), e o warmup da DeepSeek confere cada prompt de tamanho exato com um /tokenize autenticado antes de dispará-lo.

A API também impõe limites por requisição que vêm de flags do servidor, não do modelo. O mais comum é o de mídia: --limit-mm-per-prompt fixa quantas imagens (e vídeos) cabem num único pedido. No Qwen, o default documentado é 1 imagem + 1 vídeo por prompt. Na DeepSeek, LIMIT_MM_PER_PROMPT=image=8 vira {"image":8} (com o teto testado em 32, a 33ª imagem dá HTTP 400). O encoder da DeepSeek também só aceita imagens em mensagens user: uma imagem em system, assistant ou tool dá 400, e esse 400 fica no histórico e envenena a sessão. O caminho da imagem até os tokens está em Multimodal.

Na lane TensorFold: a mesma porta, outro motor atrás

A segunda versão da receita GLM serve o mesmo checkpoint com o TensorFold v0.6.0 mais 53 patches (Um motor exato), e o rank 0 abre a mesma API com --name GLM-5.3-Flash-EXL3 --host 0.0.0.0 --port 8888 (o default do motor é 127.0.0.1:8080). As rotas são quase as mesmas: /v1/chat/completions, /v1/completions, /v1/responses, /v1/models, /health e /metrics, sem /v1/messages na v1.3.2 (desde a v1.9, patch 0084, a receita também fala a API Anthropic Messages, em /v1/messages, /messages e /count_tokens, e o Claude Code e os SDKs da Anthropic conversam direto com o servidor). O patch 0037 acrescenta /tokenize e /detokenize com os campos do vLLM (prompt ou messages, resposta com count, tokens e max_model_len), montados também sob /v1/. O 404 de /v1/tokenize descrito acima não acontece nessa lane, e o /v1/completions passa a aceitar um prompt que já é uma lista de IDs. As mídias seguem outras regras: imagens (image_url) e vídeos (video_url) só em mensagens user, até 50 imagens e 4 vídeos por requisição num corpo de até 96 MiB, e só data URLs por default (VISION_URLS=1 deixa o servidor buscar URLs https:// públicas).

Campos recusados e ignoradoslogprobs · n · logit_bias · penalidades

Um servidor “compatível” nunca é compatível com tudo, e o que importa é saber como ele diverge. O TensorFold recusa com HTTP 400 o que não sabe fazer: logprobs: true e top_logprobs (o motor não devolve probabilidades de tokens) e n diferente de 1. Já logit_bias e as penalidades de presença, frequência e repetição são aceitos e ignorados, sem erro nenhum, e um cliente que conta com uma penalidade contra repetição não recebe aviso. No sentido oposto, a lane acrescenta extensões próprias: "draft": false pede a decodificação serial de referência, e a resposta traz um bloco tensorfold com tempos (prefill_s, decode_s) e um token_sha dos tokens gerados. É com eles que se confere o contrato do motor, “a resposta com rascunhos é idêntica à serial”, comparando hashes em vez de ler textos (amostragem com chave).

Streaming, usage e finish_reason

Com "stream": true, a resposta não vem de uma vez. O servidor abre uma conexão HTTP longa e envia Server-Sent Events: linhas data: {json} separadas por uma linha em branco, terminando com data: [DONE]. Cada evento carrega um delta, só o pedaço novo: um trecho de content, de reasoning ou um fragmento de tool_calls[i].function.arguments. O ganho é de latência percebida: o usuário vê o primeiro token assim que o prefill termina (o TTFT), e um agente pode começar a interpretar antes do fim.

data: {"object":"chat.completion.chunk","choices":[{"index":0,"delta":{"role":"assistant"}}]}

data: {"choices":[{"index":0,"delta":{"reasoning":"Somar 17 e 25…"}}]}

data: {"choices":[{"index":0,"delta":{"content":"42"}}]}

data: {"choices":[{"index":0,"delta":{},"finish_reason":"stop"}]}

data: {"choices":[],"usage":{"prompt_tokens":812,"completion_tokens":57,
       "prompt_tokens_details":{"cached_tokens":768}}}      ← só com include_usage

data: [DONE]

(Números ilustrativos.) Duas propriedades importam para o resto do capítulo. Primeira: o stream é append-only. Uma vez enviado, um pedaço não pode ser desfeito. Um parser que emite cedo demais não tem como voltar atrás, e por isso vários patches deste capítulo seguram texto num buffer antes de decidir. Segunda: o último evento de escolha traz o finish_reason, o motivo da parada:

stop
O modelo emitiu EOS ou casou uma stop string.
length
Esgotou max_tokens (ou o contexto). A resposta está cortada.
tool_calls
O turno terminou com uma chamada de ferramenta completa. O cliente deve executá-la.
abort
A requisição foi cancelada (desconexão, erro interno).

usage e cached_tokens

O objeto usage conta os tokens de prompt e de saída. Com --enable-prompt-tokens-details, ele ganha prompt_tokens_details.cached_tokens, quantos tokens do prompt vieram do prefix cache. É assim que um cliente verifica se o cache está funcionando. Em streaming, o usage só aparece se o cliente pedir "stream_options": {"include_usage": true}: o servidor manda um chunk extra, com choices vazio, antes do [DONE]. O documento de cache da receita Qwen insiste que isso é só metadado: a flag não liga nem reajusta o prefix caching, e as métricas Prometheus em /metrics não dependem dela.

Na lane TensorFold: usage sempre no fim

No TensorFold, o usage vem em toda resposta, no último evento do stream, sem precisar de include_usage. Ele traz prompt_tokens_details.cached_tokens (os tokens do prompt reaproveitados) e também completion_tokens_details.reasoning_tokens, que conta os tokens de pensamento até o </think>. A pergunta “o cache funcionou?” continua respondida, só que sem flag. O mecanismo de reuso, porém, é outro: no lugar de um prefix cache por blocos, o motor guarda estados de prompt inteiros numa grade de 64 tokens (Um motor exato).

Hotfixhotfix-dsv4-issue55-tool-truncation.py

Sempre ligado. Quando finish_reason == length, o final do stream e a escolha não streaming reportam "length" e removem tool calls cujo arguments não é um JSON completo. O stop natural continua tool_calls. No A/B ao vivo, antes do patch toda célula truncada (max_tokens = 300/800/1500/600+high) reportava tool_calls. Depois, todas reportam length, e com max_tokens=3000 (sem corte) o tool_calls continua com argumentos válidos. De quebra, a auditoria achou que FinishReason é um IntEnum: sem o str(…), ABORT/REPETITION chegavam ao cliente como '2'/'4'. Limite honesto: fragmentos inválidos já enviados no stream não podem ser desfeitos (append-only). A proteção é o sinal correto no final.

max_tokens: quem decide quando ninguém decide

max_tokens limita tudo o que o modelo gera: raciocínio, resposta visível e markup de ferramenta. O que acontece quando o cliente o omite? No chat do vLLM fixado pelo GLM, o fallback é “todo o contexto restante” (max_model_len − prompt, limitado por tetos de plataforma). No legado /v1/completions, o protocolo usa 16 por default. Um agente que esquece o campo pode gerar até encher o contexto, e o KV dessa sequência cresce até preemptar outras sessões.

A lane TensorFold resolve o mesmo problema com outro número e outra justificativa. Uma requisição sem max_tokens ganha 32.768 tokens para raciocínio e resposta juntos, cortados ao que sobra da janela e nunca recusados. O default do próprio motor é 4.096, e a receita o subiu na v1.3 porque agentes como o Codex não mandam max_tokens, e 4.096 tokens podiam terminar uma resposta no meio de uma tool call. Já um max_tokens explícito que não cabe na janela é recusado antes de gerar, com um erro que o agente sabe ler (seção Atualização: a fronteira da API no TensorFold).

Do diálogo ao prompt: templates e o modo de pensar

O modelo nunca viu um JSON de messages no treino. Ele viu texto com marcadores especiais de papel. O chat template é a função que traduz uma lista de mensagens (e as ferramentas declaradas) nesse texto. Normalmente é um programa Jinja que vem no checkpoint. Um template errado não dá erro: dá um modelo estranhamente pior, porque ele passa a receber um formato que nunca viu. Os detalhes de tokens especiais estão em Tokens e embeddings. Aqui interessa o que a API controla.

  • O GLM força --chat-template /opt/glm53/chat_template.jinja, porque o Jinja do checkpoint é só de linguagem. Ele monta [gMASK]<sop><|system|>…<|user|>…<|assistant|><think>.
  • O Qwen usa o chat_template.jinja do checkpoint, com <|im_start|> (248045) e <|im_end|> (248046).
  • O DeepSeek não traz Jinja. Com --tokenizer-mode deepseek_v4, o vLLM chama o encoder Python do checkpoint (encoding_dsv4.py, copiado pelo compose para dentro do vLLM), e esse programa é o template.

O turno morto (DeepSeek #52/#120)

Harnesses de agente às vezes reenviam a conversa terminando numa mensagem assistant (um retry, por exemplo). O encoder stock só anexa o gatilho de geração (<｜Assistant｜><think>) quando a última mensagem é user/developer. Com um assistant no fim, o prompt termina num EOS “morto”: o modelo gera 1 ou 2 tokens e para, ou alucina markup, e o erro se autoalimenta. O opt-in DSPARK_ENABLE_ASSISTANT_FINAL_HOTFIX=1 anexa um cabeçalho novo (também quando um latest_reminder segue o assistant). O A/B causal foi feito via /v1/completions, justamente para controlar os bytes: com o turno aberto saíram 183 tokens coerentes, e com o turno fechado por EOS saíram 400 tokens de DSML cru como texto.

O reasoning parser: duas vozes, dois campos

Modelos de raciocínio escrevem primeiro um rascunho de pensamento entre <think> e </think> e depois a resposta (veja Gerando texto). O reasoning parser (--reasoning-parser) separa esse fluxo em dois campos: o pensamento vai para reasoning e a resposta para content. Ele também define a fronteira em que outras peças mudam de comportamento. Tool calls só são extraídas de content, a gramática de saída estruturada só começa depois de </think> e os stops do cliente passam a valer ali (próxima seção).

GLM · glm45

O campo é reasoning. Um cliente que lê reasoning_content não recebe nada e acha que o pensamento vazou para content, o que não aconteceu. O vLLM aceita o nome antigo na entrada e renomeia, mas nunca o emite. A flag também mantém vivo o hook do tool_choice:"none".

Qwen · qwen3

Este build faz streaming em delta["reasoning"], não em reasoning_content, e clientes e benches precisam ler o campo certo. O card oficial ainda traz preserve_thinking (default true), o análogo inverso do clear_thinking.

DeepSeek · deepseek_v4

Vem com --reasoning-config {"reasoning_parser":"deepseek_v4","reasoning_start_str":"<think>","reasoning_end_str":"</think>"}, que declara os marcadores usados pelo orçamento de thinking e pela supressão de stops. A documentação do build fixado fala em reasoning_content. Regra prática: rode jq '.choices[0].message | keys' no seu build antes de escrever o cliente.

Na lane TensorFold, o nome volta a ser reasoning_content

Mesmo modelo, mesmo template, outro servidor: o TensorFold devolve o pensamento em reasoning_content (e em delta.reasoning_content no stream), não em reasoning. Um cliente escrito para a lane vLLM lê o campo vazio e cai na mesma armadilha do card do GLM, só que ao contrário. Na entrada, o patch 0036 aceita os dois nomes e renomeia reasoning para reasoning_content antes de renderizar, porque há clientes (o vLLM mais novo, o OpenRouter) que usam o nome curto. A regra prática do card da DeepSeek vale para as quatro lanes: confira as chaves no seu servidor antes de escrever o cliente.

De volta ao texto: detokenização e stop strings

Na volta, o caminho se inverte: IDs viram texto. Parece trivial, mas não é. Um token é uma sequência de bytes, e um caractere UTF-8 (um acento, um ideograma, um emoji) pode ficar dividido entre dois tokens. O detokenizer incremental mantém offsets do que já foi convertido e só emite texto quando os bytes formam caracteres completos. É também ali que o vLLM confere as condições de parada: EOS (IDs) e stop strings (texto).

Uma stop string pode atravessar tokens. Se o modelo gera " Ques" e depois "tion:", nenhum token sozinho contém Question:. Por isso a busca olha para uma janela que inclui os caracteres novos mais \(|s|-1\) caracteres anteriores, e em streaming o servidor segura até \(|s|-1\) caracteres, para não enviar ao cliente o começo de um stop que ainda pode se completar (mecanismo do vLLM, simplificado):

\[ \text{parar se } s \subseteq \text{texto}\big[\,L_{\text{ant}} - |s| + 1 : L_{\text{novo}}\big) \]
  • \(s\): uma stop string do cliente (ex.: "Question:")
  • \(|s|\): comprimento de \(s\) em caracteres
  • \(L_{\text{ant}}\): tamanho do texto antes deste passo
  • \(L_{\text{novo}}\): tamanho depois de anexar os tokens do passo

O problema: stops que disparam dentro do pensamento

Benchmarks e harnesses usam stops como "Question:" para cortar o modelo quando ele começa a inventar a próxima pergunta. Num modelo de raciocínio, o prompt termina em <think> (o “think-in-prompt”), e o pensamento, que é livre, costuma repetir esses marcadores (“Question: quanto é…?”). O detokenizer v1 casava os stops contra o stream inteiro. A requisição morria no meio do raciocínio com content: null.

A correção é a mesma nas duas receitas que a aplicam, um port do “Patch 5” de tonyd2wild/Capicua25x. O guard só é armado se o último token do prompt for o marcador de início do raciocínio, ou seja, se a requisição realmente pensa. Enquanto o </think> não aparece, os stops do cliente ficam dormentes. Com decodificação especulativa (prévia de Decodificação especulativa), cada passo pode entregar até k+1 tokens de uma vez. Se o </think> chega no meio desse lote, o stop_check_offset avança para depois do marcador, e só o texto da resposta é conferido. EOS e max_tokens não mudam.

Tool calling: o modelo escreve, o parser traduz

“Chamar uma ferramenta” soa como se o modelo executasse algo. Ele não executa nada. Tool calling é um protocolo de texto: o modelo foi treinado para, quando convém, escrever um pedido estruturado num formato próprio. O servidor reconhece esse texto e o converte num objeto JSON. Quem executa a ferramenta é o cliente, e o resultado volta ao modelo como uma mensagem nova.

  1. Declarar O cliente envia tools: nome, descrição e parâmetros em JSON Schema.
  2. Renderizar O template injeta as ferramentas no prompt. No GLM é um bloco <|system|># Tools … You may call one or more functions… seguido da assinatura do formato de chamada.
  3. Gerar O modelo escreve o markup de chamada no seu formato (tabela abaixo).
  4. Traduzir O tool-call parser extrai nome e argumentos e devolve tool_calls: [{id, type:"function", function:{name, arguments:"<string JSON>"}}] com finish_reason:"tool_calls".
  5. Executar O cliente roda a função e responde com {"role":"tool","tool_call_id":…,"content":…}.
  6. Reencodar No turno seguinte, o template precisa re-renderizar a chamada antiga e o resultado. No GLM, o resultado entra após <|observation|>, que também é um dos EOS do modelo.

Com o parser errado, as chamadas chegam como texto em content e o agente quebra sem erro nenhum. Na receita Qwen, a regressão de tool calling passa com o MTP ligado.

O parser em streaming é uma máquina de estados

Em streaming, o parser recebe o texto aos pedaços e precisa decidir, a cada pedaço, se aquilo é conversa ou o começo de uma chamada. Ele é uma máquina de estados: TEXTO → ABERTURA → NOME → ARGUMENTOS → FECHAMENTO. Os argumentos saem como fragmentos de string JSON, e como o stream é append-only, o parser precisa ter certeza antes de mudar de estado. Veja na figura o mesmo pedido nos três formatos, e depois o caso patológico do DSML.

Controlando a chamada: tool_choice, máscaras e temperatura

O cliente pode dizer ao servidor se e qual ferramenta deve ser chamada, pelo campo tool_choice:

"auto"
O modelo decide (exige --enable-auto-tool-choice). A chamada é extraída do texto, e os argumentos podem sair malformados, a menos que a ferramenta tenha strict: true.
"none"
O cliente não quer chamada, mesmo com ferramentas declaradas. O que o servidor de fato garante é outra história (logo abaixo).
"required"
Precisa chamar pelo menos uma.
nomeada
{"type":"function","function":{"name":"x"}}: precisa chamar exatamente x.

Dois campos refinam o contrato. parallel_tool_calls diz se várias chamadas no mesmo turno são permitidas. strict, na definição da função, exige que os argumentos obedeçam ao schema. No vLLM, required e a forma nomeada são impostas com saídas estruturadas (a próxima seção): em geral, guided JSON sobre o schema dos parâmetros; no build da DeepSeek, uma structural tag DSML. Já none não restringe a geração. Ele só impede que o parser devolva tool_calls, e com --exclude-tools-when-tool-choice-none tira as ferramentas do prompt. É essa lacuna que o overlay #13 do GLM fecha com bad_words, logo abaixo. Em tudo o que restringe a saída, a ferramenta por baixo é a mesma: mexer nos logits antes do sorteio.

Mascaramento de logits

Na última camada o modelo produz um logit \(z_i\) por token do vocabulário, e o sampler transforma isso em probabilidades. Mascarar é multiplicar por um vetor de 0/1 antes da normalização, o que equivale a pôr \(-\infty\) nos logits proibidos:

\[ p_i \;=\; \frac{m_i\, e^{z_i/T}}{\sum_{j} m_j\, e^{z_j/T}} \]
  • \(z_i\): logit do token \(i\)
  • \(T\): temperatura
  • \(m_i\): máscara (1 = permitido, 0 = proibido)
  • \(p_i\): probabilidade final; com \(m_i=0\), \(p_i=0\) para qualquer \(T\)

O vLLM expõe a forma mais simples disso como bad_words: uma lista de strings que são tokenizadas e bloqueadas. Uma palavra de um token só é mascarada em toda posição. Uma palavra de vários tokens só tem o último token bloqueado quando os anteriores já saíram, o que é bem menos robusto.

tool_choice na lane TensorFold: a escolha oposta

A documentação do TensorFold descreve duas decisões que contrastam com o overlay #13. A primeira: tool_choice:"none" tira as ferramentas do template, justamente o caminho que a lane vLLM rejeitou para não quebrar o prefixo comum. O custo reaparece aqui (interpretação nossa): as ferramentas moram no bloco de sistema do GLM, e o fim desse bloco é um dos pontos em que o TensorFold guarda um estado reaproveitável entre conversas. Um pedido none renderiza outro bloco de sistema e não compartilha esse estado com os pedidos que declaram ferramentas. Em troca, a garantia é estrutural: sem ferramentas no prompt, o modelo não tem o que chamar. A segunda: required e a forma nomeada não usam gramática. O servidor troca o primeiro token não-branco da resposta pelo opener <tool_call> mais o texto do template antes do nome, e então segura o nome dentro das ferramentas oferecidas: um token que sai delas é trocado pelo resto do primeiro nome compatível. Cada correção depende só dos tokens anteriores, então o rascunhado, o serial e o concorrente escrevem a mesma chamada. Os argumentos ficam por conta do modelo, e uma chamada malformada volta como texto em content, não como erro. Mandar uma gramática junto de required dá HTTP 400.

Temperatura nos tokens de sintaxe

Há um efeito mais sutil. O vLLM sorteia todo token com a temperatura da requisição, os de sintaxe (tags, cabeçalhos invoke, chaves, aspas) e os de payload (os valores dos argumentos). No DSML, um único token estrutural errado basta para o parser não reconhecer a chamada. O motor ds4, usado noutra receita da Mia, força \(T=0\) nos tokens de sintaxe e só sorteia os de payload com a temperatura pedida. Com o mesmo modelo (e pesos até melhores no vLLM: FP8, contra experts GGUF de ~2 bits com atenção Q8 no ds4), a \(T=1{,}0\) e thinking ligado, o vLLM pontua menos no tool-eval-bench. O benchmark lê só message.tool_calls, então uma chamada malformada conta como “nenhuma chamada” (missing_step). O documento da receita descarta o KV quantizado, o MTP e os pesos como causas. O argumento dos pesos é o mais forte: se eles dominassem, o vLLM venceria. É um artefato mecânico de serving, e não um sinal de qualidade do modelo.

\[ \begin{aligned} P_{\text{chamada ok}}(T) &\approx \prod_{s=1}^{K} p_{\text{ok},s}(T) \\ p_{\text{ok}}(T) &= \frac{1}{1 + M\,e^{-\Delta/T}} \end{aligned} \]
  • \(K\): número de tokens de sintaxe numa chamada
  • \(p_{\text{ok},s}\): chance do token certo na posição \(s\)
  • \(\Delta\): margem de logit do token certo sobre os alternativos (modelo de brinquedo)
  • \(M\): quantas alternativas plausíveis existem

As mitigações do lado do vLLM, da mais barata para a mais cara, segundo a receita: (1) rodar o benchmark a \(T=0\), o que torna a sintaxe à prova de temperatura, mas também deixa o payload guloso. Como diagnóstico, isso separa “sintaxe corrompida” de “lacuna real de capacidade”. (2) Saídas estruturadas com structural tags do XGrammar: a máscara deixa as posições de sintaxe com exatamente um token válido, e o resultado é determinístico a qualquer temperatura. Não existe gramática DSML pronta no vLLM, e function calling por structural tag ainda é um RFC aberto (vllm#32142). (Para tool_choice nomeado ou required, o build da DeepSeek já aplica uma structural tag DSML estrita, como mostra a seção seguinte. O que falta é uma gramática para auto, o modo em que o benchmark roda: ali, a \(T>0\), nenhuma gramática protege a sintaxe.) (3) Um logits processor próprio que rastreie o estado do DSML e force argmax nas regiões de sintaxe, na prática um port da lógica do ds4.

Saídas estruturadas: a gramática segura a caneta

Às vezes você não quer “um texto que parece JSON”. Você quer garantia de JSON válido contra um schema. Saídas estruturadas (ou guided decoding) fazem isso restringindo o sorteio a cada passo. O cliente pede com response_format: {"type":"json_schema","json_schema":{…}}, ou com o campo do vLLM structured_outputs, que aceita json, regex, choice, grammar ou structural_tag. O backend padrão é o XGrammar (há também guidance, outlines e lm-format-enforcer). Nenhuma das três receitas passa --structured-outputs-config: todas usam os defaults.

  1. Compilar O schema vira uma gramática livre de contexto, e a gramática vira um autômato com pilha (JSON aninha, então uma FSM pura não basta). O XGrammar pré-computa, para cada estado, quais tokens são decididos sem contexto, o que torna o passo barato.
  2. Mascarar A cada passo, o matcher no estado atual preenche um bitmask, 1 bit por token do vocabulário: pode ou não pode.
  3. Sortear O sampler aplica a máscara (a equação da seção anterior) e sorteia entre os permitidos.
  4. Avançar O token escolhido é aceito pelo matcher, que muda de estado. No fim da gramática, só o EOS é permitido e o matcher “termina”.

O custo em memória do bitmask é fácil de calcular, porque o XGrammar empacota os bits em inteiros de 32 bits:

\[ \text{bytes por linha} = 4\,\Big\lceil \tfrac{V}{32} \Big\rceil \]
  • \(V\): tamanho do vocabulário
  • GLM: \(V=154.880\) → 4.840 palavras → 19.360 B
  • Qwen: \(V=248.320\) → 7.760 palavras → 31.040 B
  • DeepSeek: \(V=129.280\) → 4.040 palavras → 16.160 B

É uma linha por sequência a cada passo e, com decodificação especulativa, uma linha por posição de rascunho. É pouca memória. O ponto delicado é sobre o quê cada linha é montada. Com async scheduling, o passo N+1 é agendado antes de os rascunhos do passo N existirem, e o scheduler reserva as posições com placeholders (-1). As linhas de máscara dessas posições são montadas sobre os placeholders, não sobre rascunhos reais, e é por aí que a máscara pode “falhar aberta” (a família vLLM #49694/#54437 do #191, seção anterior). Desligar o async (DSPARK_ASYNC_SCHEDULING=0) faz as linhas virem de rascunhos reais, a ~4% de custo em single-stream.

Raciocínio e structural tags

Com um reasoning parser ativo, a gramática só começa depois do </think> (a menos de enable_in_reasoning). O pensamento é livre e a resposta é restrita, então o motor precisa saber exatamente em que token o raciocínio terminou. Guarde essa frase para a próxima seção. Uma structural tag é uma gramática que só se ativa dentro de uma região marcada por um gatilho, perfeita para tool calls. No DeepSeek, a tag de tool_choice nomeado ou required é uma sequência estrita, \n\n<｜DSML｜tool_calls>\n … </｜DSML｜tool_calls>, que o XGrammar 0.2.3 aplica.

Por que isso importa para quem escreve receitas

Saída estruturada é o recurso que um agente de produção mais usa, e o que menos aparece nos benchmarks de tokens/s. Ela toca em quatro peças ao mesmo tempo: o parser de raciocínio (onde começa), o scheduler (quando a máscara é calculada), o sampler (onde é aplicada) e a especulação (várias posições por passo). Nas receitas, os bugs moram exatamente nessas junções.

Gramática × especulação: quando o lote passa do ponto

Uma prévia do que a Parte VII detalha: na decodificação especulativa, um rascunhador barato propõe k tokens, o modelo grande verifica todos num único forward e aceita um prefixo deles, mais um token “bônus”. Cada passo entrega até k+1 tokens de uma vez. Para a gramática, isso muda tudo. O matcher precisa de uma linha de máscara para cada posição de rascunho, avança provisoriamente por eles (validate_tokens), desfaz os rejeitados e aceita os confirmados (accept_tokens). Duas fronteiras podem cair no meio de um lote: o fim da gramática e o fim do raciocínio.

Na lane TensorFold: cortar antes de verificar

O TensorFold também usa o XGrammar (com os mesmos pedidos: response_format json_object/json_schema, guided_json, guided_regex, guided_choice, guided_grammar e structured_outputs), também só depois do </think>, e mantém os rascunhos ligados. O que muda é a ordem das operações. Antes de cada forward de verificação, o motor corta a cadeia de rascunhos no primeiro que a gramática rejeita, e só então mascara os logits de cada linha restante com os tokens que a gramática permite depois do caminho daquela linha. Como a amostragem é chaveada e a verificação é um teste de igualdade, uma resposta restrita sai idêntica à versão "draft": false e à execução sozinha. Os dois Sparks compilam a mesma gramática, e cada um mascara as suas colunas do vocabulário. Como nenhum rascunho rejeitado chega à verificação, a pergunta “o lote passou do fim da gramática?” desta seção não chega ao matcher (interpretação nossa). Três detalhes de contrato: a gramática só libera o token de fim quando o valor está completo (um corte por max_tokens sai incompleto, com length); uma gramática JSON aceita no máximo 32 caracteres em branco entre dois tokens, para o modelo não encher a resposta de espaços; e uma gramática que falha no meio da decodificação encerra só aquela resposta, com HTTP 500 (um evento de erro no stream), enquanto as outras seguem. Na receita, o modo estruturado mediu 114,7 tok/s com 1 requisição e 227,9 agregados com 4 (sparkDash, temperatura 0, thinking off, clocks da GPU limitados a 2.200 MHz). O README da lane vLLM dá 83,0 tok/s com 1 requisição, medidos com outra ferramenta e em outra data: é ordem de grandeza, não um A/B controlado.

Como testar isso numa receita nova

Teste saída estruturada com a especulação ligada e com thinking ligado, usando schemas curtos (o fim chega rápido e cai no meio do lote com frequência). Combine com concorrência > 1 e async scheduling. Rode tool_choice auto, required e nomeado, com e sem streaming. Um bug de fronteira não aparece em teste de uma requisição por vez.

Responses API: quando o servidor guarda a conversa

A Responses API (POST /v1/responses) é a sucessora do chat na família OpenAI e é a que o Codex e vários agentes usam. Em vez de messages, ela trabalha com itens tipados de entrada e saída (message com partes input_text/output_text, function_call, function_call_output, reasoning) e eventos SSE nomeados (response.created, response.output_text.delta, response.completed…). A diferença conceitual está no estado. Ela suporta dois estilos de continuação:

Stateless: replay do histórico

store: false. O cliente reenvia todos os itens, inclusive as saídas anteriores exatamente como vieram (type=message/id/status/output_text+annotations). É como o chat: o servidor não guarda nada, reinícios não quebram a conversa, e o prefix cache cuida do custo.

Stateful: previous_response_id

store: true guarda a resposta no servidor, e o turno seguinte manda só o novo item com previous_response_id. O cliente fica simples e o tráfego diminui, mas o estado vive na memória do processo: um restart perde tudo, e a continuação passa a dar 404.

Stateful não significa mais barato para a GPU. O servidor reconstrói o histórico e o modelo processa o prompt inteiro de qualquer jeito, e quem economiza prefill continua sendo o prefix cache. O store economiza bytes de rede e complexidade de cliente, e troca isso por memória no servidor e fragilidade a reinícios.

Recriar, não reiniciar

Esses opt-ins são patches aplicados na camada gravável do container no boot. Um docker restart reaproveita essa camada: desligar a flag não desfaz os bytes já patchados. Para mudar o modo ou o teto, faça stop + start (recriar os containers) em todos os ranks. O capítulo Engenharia de receita generaliza essa regra.

Responses na lane TensorFold: store ligado, com teto duplo

O TensorFold executa /v1/responses como a chat completion equivalente, pelo mesmo handler e pelo mesmo caminho do motor: os mesmos tokens (o token_sha bate), os mesmos rascunhos e a mesma igualdade com "draft": false. As escolhas de estado são quase o espelho das da DeepSeek. O store é true por default: uma resposta terminada fica na memória antes de o último evento sair, e o armário guarda as 1.024 mais recentes, até 256 MiB. O teto conta entradas e bytes, enquanto o LRU da DeepSeek conta só entradas. GET e DELETE /v1/responses/{id} leem e apagam uma resposta guardada. previous_response_id reconstrói as mensagens que um cliente de chat mandaria, e por isso o reuso de prompt retoma o prefixo como no chat. A fragilidade é a mesma: um restart esquece tudo, e um previous_response_id que não está guardado dá HTTP 400. O servidor também recusa com 400 o que não executa, como as ferramentas embutidas (web search, file search, computer use), background e o raciocínio criptografado.

Atualização: a fronteira da API no TensorFold

Tudo até aqui foi o vLLM. A receita GLM agora tem uma segunda versão , que serve o mesmo checkpoint EXL3 nos mesmos dois Sparks com outro motor: o TensorFold v0.6.0 mais 53 patches. O TensorFold é escrito por família de modelo e tem um contrato raro. Com a amostragem chaveada, a resposta com rascunhos é idêntica, token a token, à decodificação serial, e quatro requisições servidas juntas dão as mesmas respostas que cada uma sozinha (Um motor exato). A receita completa está em A receita GLM em TensorFold. Nove dos 53 patches mexem justamente na fronteira deste capítulo: visão e mídias (0003, 0050), tool calls (0036, 0051, 0053), /tokenize (0037), reasoning_effort: "max" (0023), erros de contexto (0044) e métricas (0045).

O contrato de exatidão muda o jeito de consertar uma fronteira. No vLLM, as correções deste capítulo atuam onde o bug aparece: uma máscara a mais, um stop que dorme, um finish_reason corrigido no fim. No TensorFold, toda regra que mexe nos tokens precisa depender só dos tokens anteriores, para que o rascunhado, o serial e o concorrente escrevam a mesma coisa. O resto do trabalho fica com o servidor, que pode segurar, reordenar e reconstruir texto à vontade, porque isso não muda token nenhum. Três problemas de agentes mostram o padrão.

Uma tool call inteira, ou nenhuma

Um agente de código que pede write_file com um arquivo de centenas de linhas faz o modelo passar minutos escrevendo os argumentos. O stream SSE pode tratar isso de três jeitos, e a receita passou pelos três. O TensorFold v0.6.0 só entregava a chamada do GLM no fim, pelo parser final. Durante a escrita não saía byte nenhum, e clientes que derrubam conexões ociosas (o LiteLLM, o fetch do Node) desistiam. O patch 0036 passou a transmitir a chamada enquanto ela é escrita: um cabeçalho com índice, id call_<24 hex> e nome assim que o nome fecha, e depois o JSON dos argumentos aos pedaços. É o mesmo desenho do parser em streaming do vLLM, e herda o mesmo defeito. O stream é append-only, então uma resposta cortada por max_tokens no meio da chamada já entregou argumentos pela metade, que um cliente pode guardar ou até executar. O hotfix #55 da DeepSeek corrige o finish_reason, mas não consegue recolher o que já foi enviado.

O patch 0053 fecha o ciclo com a regra da call inteira. O streamer continua acompanhando a chamada enquanto ela é escrita, mas só a envia quando chega o </tool_call>, com cabeçalho e argumentos num único delta. Uma chamada dentro da qual a resposta termina nunca é enviada, em streaming ou não, e a resposta termina com finish_reason: "length". O parser final também tira do content um <tool_call> não fechado. Para não repetir o silêncio do v0.6.0, entra um keepalive: enquanto uma chamada está segurada, sai um delta vazio a cada 2,0 s (CALL_KEEPALIVE_S). Na figura, compare as três estratégias nos dois cenários. A faixa de cima é o que o modelo escreve, a do meio é o que atravessa o fio e o painel de baixo é o que o cliente tem nas mãos.

O preço da atomicidade é a visibilidade. Com fragmentos, uma interface pode mostrar o arquivo sendo escrito em tempo real; com a chamada inteira, só vê o resultado no fim. Para agentes, que executam a chamada em vez de exibi-la, a troca compensa: tudo o que chega ao cliente é um JSON completo e parseável. A regra também combina com o contrato do motor, porque o que vai para o fio depende só de tokens já gerados.

Chamadas escritas dentro do pensamento

O GLM às vezes escreve a tool call dentro do bloco <think>, sem fechá-lo. O split original do TensorFold lia qualquer chamada num bloco não fechado como resposta, e assim confundia uma chamada apenas mencionada no raciocínio com uma chamada de verdade. O patch 0036 adota a regra “D5”, adaptada do patch 0620 do jayleaton/glm53-tensorfold-spark: uma chamada escrita no pensamento só é chamada se termina a resposta, sem nada depois além de espaço e do fechamento do bloco. Até decidir, o servidor segura esse texto fora do raciocínio. Se vier mais texto depois, ele volta a ser raciocínio; se a resposta acabar nele, vira tool_calls. Uma chamada segurada com mais de 1.024 caracteres (THINK_CALL_HOLD) é tomada como chamada na hora, para que a escrita de um arquivo longo possa ser transmitida, e a partir daí nada a transforma de volta em raciocínio. É um compromisso explícito entre esperar para classificar certo e não segurar o cliente para sempre.

O histórico que volta: raciocínio devolvido e chamadas quebradas

Os outros dois problemas vêm do histórico que o agente reenvia a cada turno. O primeiro é o raciocínio intercalado. O template do GLM-5.3 renderiza o raciocínio de cada passo do assistente depois da última mensagem do usuário: dentro de um laço de ferramentas, o modelo relê o que pensou em cada passo. Muitos clientes de agente (o spark-bench e vários frameworks) não devolvem esse raciocínio, e o template renderiza <think></think> no lugar. O patch 0036 aponta dois prejuízos. O modelo passa a ver um contexto que nunca escreveu, e o prompt deixa de casar com o anterior naquele passo, então o cache de prefixo relê o resto. A correção é um LRU no servidor, o KeptReasoning, que guarda o raciocínio das respostas que fizeram tool calls. A chave é dupla: os ids das chamadas que o próprio servidor gerou e, para clientes que renumeram ids, uma assinatura SHA-256 da conversa inteira antes das chamadas (papéis, texto e chamadas sem ids) mais as chamadas. Antes de renderizar, o servidor recoloca o raciocínio nos passos que vieram sem ele. Um passo que já traz o próprio raciocínio nunca é tocado, e um "" conta como ausente. A assinatura cobre a conversa inteira, e não só a última mensagem do usuário como no patch de origem, para que um raciocínio só volte à conversa para a qual foi escrito. O LRU guarda até 1.024 respostas e 32 MiB de texto (TF_GLM_KEEP_REASONING, em que 0 desliga, e TF_GLM_KEEP_REASONING_MB).

O segundo problema é uma chamada antiga quebrada (issue #2). Se uma tool call do histórico tem argumentos que não são um objeto JSON (uma string cortada ou corrompida pelo modelo, pelo cliente ou por um proxy), o servidor respondia HTTP 400. Como o agente reenvia o histórico em todo turno, o 400 voltava para sempre e a conversa ficava travada. O patch 0051 deixa essa chamada fora do prompt, junto com o resultado dela (casado pelo id ou, sem ids, pela posição, quando o número de resultados é igual ao de chamadas), e registra o fato no log. O resto da mensagem fica: as outras chamadas, o texto e o raciocínio. O 0036 já saneava o caso mais leve, trocando argumentos "" ou null por {}.

Fail-closed na saída, fail-open no histórico

Compare com o #191 da DeepSeek, que prefere um HTTP 500 a um 200 errado. As duas escolhas parecem opostas, mas seguem o mesmo critério: quem paga pelo erro. Na saída, um 200 errado é executado pelo agente, e falhar alto protege o mundo lá fora. No histórico, um erro recusado volta em todo turno e mata a conversa, enquanto omitir a chamada quebrada (e registrar no log) só tira do modelo um passo que ele já não conseguia ler. O mesmo critério explica a call inteira: uma chamada cortada não sai, porque o cliente a executaria.

Depois da v1.3.2: a marcação lida nos tokens, não no texto

Patches posteriores atacam um defeito comum a quase todo servidor. O GLM escreve <think>, </think> e <tool_call> como tokens únicos (tokens adicionados), mas o servidor procurava a marcação no texto. Na entrada, o HF tokenizers extrai de uma string o texto de todo token adicionado, especial ou não, então um pedido que só citava </think> (um agente lendo a saída crua de outro modelo, um log, um template) virava o próprio token. O patch 0116 mascara o texto do pedido antes de renderizar o template e o codifica como texto, em volta dos tokens do próprio template. Na saída, o patch 0117 faz a leitura da marcação pelos ids: anota cada token marcador que o modelo gerou e neutraliza, antes dos parsers, toda outra ocorrência do mesmo texto (o cliente recebe o texto de volta). Um </think> citado no raciocínio não o encerra mais, e uma chamada de exemplo escrita como texto não vira tool_calls. Medido com 10 respostas amostradas por caso: respostas que escreviam como token um </think> citado, 7 → 0 (dois Sparks, 0116); ecoar <think>hello</think> world certo, 0 → 5 (quatro Sparks, 0117). Já uma chamada a uma ferramenta que o pedido não ofereceu continua texto e nunca roda, como antes; o patch 0115 só passa a registrá-la no log (tool call rejected: unknown_tool_name), sem mudar um token, para que um gateway saiba por que a resposta parou.

No fio, o patch 0111 estende a ideia do keepalive: um stream que passou SSE_KEEPALIVE_S (15 s) sem enviar nada, esperando uma vaga ou preenchendo um prompt longo, escreve um comentário SSE, : keepalive, que os clientes ignoram. Atrás de um Cloudflare Tunnel, esses streams eram cortados por ociosidade em ~125 s. Em qualquer servidor, vLLM ou SGLang num H200 incluídos, os dois testes baratos são os mesmos: um prompt que cita a própria marcação do modelo e um stream que passa minutos sem token atrás do seu proxy.

Erros que um agente sabe ler, e a mesma porta com outro contrato

Um agente de contexto longo precisa de um sinal específico para saber quando compactar a conversa. Quando o prompt mais o max_tokens não cabem na janela, o TensorFold responde HTTP 400 no texto da OpenAI, com o código context_length_exceeded, e o patch 0044 acrescenta param com o nome do campo (messages ou prompt). A regra vale também para prompts com imagens que passam da janela, e falta de capacidade vira 503. Clientes que compactam a conversa ao ver esse código passam a funcionar sem configuração extra. Na observabilidade, o patch 0045 copia para o /metrics (Prometheus) os números do /health, como métricas tensorfold_health:. São contadores (requests_total, completion_tokens_total, cached_tokens_total, rounds_total, prefill_seconds_total, decode_seconds_total) e gauges (pool_tokens, pool_free_tokens, kept_prompts, streams{state=decoding|filling|paused}). Para quem opera, esses são os sinais de capacidade: quanto do pool está livre e quantos fluxos estão em cada estado (Benchmarking).

Nas receitas: portas, chaves e clientes

Uma API de inferência na rede é uma máquina de gastar GPU à disposição de quem a alcança. As receitas tratam isso em três camadas: quem pode falar (bind e chave), que portas existem (rotas) e onde o segredo aparece (logs, argv).

--api-key e o prefixo guardado

--api-key (ou a variável VLLM_API_KEY) liga a autenticação Bearer: o cliente precisa mandar Authorization: Bearer <chave>. O middleware do vLLM só confere as rotas sob o prefixo guardado: /v1, /v2 e /inference (o GLM cita também /cohere). Todo o resto responde sem chave. No runtime fixado da DeepSeek isso inclui POST /invocations e POST /generative_scoring, que rodam inferência sem autenticação, além de /tokenize, /detokenize, /health, /metrics, /version e /ping. Por isso a chave sozinha não basta: é preciso controlar o acesso à porta na camada de rede.

  • chatTemplateKwargs: thinking ← thinking.enabled; reasoning_effort ← thinking.effort (omitWhenOff)
  • supportsThinkingTokenBudget: false. Declarar true com o flag de boot #31 em 0 faz todo pedido falhar (“thinking_token_budget is not yet supported by the V2 model runner”). O pi mapeia minimal 1024 / low 2048 / medium 8192 / high 16384.

Daí sai uma regra de dimensionamento (interpretação nossa, coerente com os números): (1) contextWindow ≤ --max-model-len, com folga para a saída. O GLM declara 500 mil e reserva 65.536 tokens na compactação. (2) maxTokens compatível com o modo de pensar: 8.192 bastam com thinking off (GLM), e 32.768 são o mínimo razoável com thinking on (DeepSeek). (3) Subagentes simultâneos ≤ --max-num-seqs. O maxConcurrent 2 do GLM cabe no seu MAX_NUM_SEQS de 4, deixando lugar para o agente principal. (4) Timeout ocioso longo (600 s), porque um prefill de centenas de milhares de tokens não devolve nada por minutos. Por fim, o que é portátil entre servidores (cluster Spark, Mac local, nuvem): base_url, api_key, model, mensagens, tools, tool_choice, stream, max_tokens, temperature. O que não é: os chat_template_kwargs de cada família, vllm_xargs de overlays, thinking_token_budget e os nomes de modelo.

A mesma regra, outros números

Na lane TensorFold a regra de dimensionamento dá outros valores: janela de 1.048.576 tokens por requisição (CONTEXT), no máximo 4 requisições decodificando juntas na v1.3.2 (PARALLEL=4; até 8 desde a v1.5) e saída default de 32.768 tokens. A lista do que não é portátil também cresce: o nome do campo de raciocínio, o efeito de medium, o "draft": false e as penalidades, que essa lane aceita e ignora. E o erro context_length_exceeded com param é o que permite a um cliente compactar a conversa sozinho quando ela passa da janela.
