To serve Llama-3.1-8B in BF16 you need only 16.1 GB of weights, and a DGX Spark still has plenty left over for the KV cache. To fine-tune all of it with AdamW in mixed precision, you need 128.5 GB of state alone, before storing a single activation. The Spark exposes 121.69 GiB to the GPU (130.7 GB), and in practice the training process gets about 100–110 GiB (interpretation). It does not fit. Same numbers, same architecture, taking up 8× more memory. This chapter explains where every byte comes from: gradients, optimizer moments, FP32 master weights, activations saved for the backward. Then it shows the four levers the community invented to make it fit: recompute instead of storing, split the state across machines (ZeRO/FSDP), train only a low-rank correction (LoRA), and freeze the base in 4 bits (QLoRA). By the end you will be able to do the math for any model and say, before hitting train, whether it fits on 2× DGX Spark or on a 24 GB Mac M4.

Inference keeps weights; training carries a backpack

In Module 1, a server’s memory had two owners: the weights, read at every decode step, and the KV cache, which grows with the context (chapter 27). The activations of an inference forward are temporary: layer 12 uses the output of layer 11, and layer 11’s output can then be forgotten. None of that changes with post-training, which is ordinary learning (chapter 1) applied to an already-trained model. What changes is the question the training step asks. To turn each knob in the right direction, training needs to know how much the loss changes if that knob changes, and that creates a little baggage for every parameter.

  1. Forward. The batch goes through the model and each layer saves the inputs the backward will need (the chain rule from chapter 2 multiplies local derivatives, and each local derivative depends on the operation’s input).
  2. Loss. The logits become cross-entropy against the target tokens.
  3. Backward. The gradient flows down layer by layer and leaves a number \(\partial L/\partial w\) next to each parameter: a gradient tensor the size of the model.
  4. Optimizer step. AdamW reads the gradient, updates two moving averages per parameter (the moments \(m\) and \(v\)), computes the update, and applies it to a high-precision copy of the weight, the master weight, which is then rounded back to BF16.

Add it all up and you get the per-parameter training state. The classic accounting comes from the ZeRO paper (Rajbhandari et al.), which calls the number of parameters \(\Psi\):

\[ M_{\text{state}} \;=\; \underbrace{2\Psi}_{\text{BF16 weights}} \;+\; \underbrace{2\Psi}_{\text{BF16 gradients}} \;+\; \underbrace{K\Psi}_{\text{optimizer}}, \qquad K \;=\; \underbrace{4}_{\text{FP32 master}} + \underbrace{4}_{m\ \text{FP32}} + \underbrace{4}_{v\ \text{FP32}} \;=\; 12 \]
  • \(\Psi\): number of trainable parameters (in an MoE, the total ones, not the active ones)
  • \(2\Psi\): the BF16 copy used in the forward and backward (2 bytes per number)
  • \(K\): optimizer bytes per parameter; 12 for AdamW in mixed precision
  • total: \(16\Psi\) bytes, the famous 16 B/parameter; activations, logits, and communication buffers come on top

In the figure, each parameter is a character with a backpack. In inference the backpack holds only the weight itself; in full fine-tuning, it gains one compartment per state. Switch the regime and watch the bytes appear and disappear; the animated cycle shows who writes to each compartment during a step.

The regime A′ trap

TRL’s SFTTrainer loads the model in FP32 if you do not pass dtype (“If dtype is not specified … it defaults to float32”). In full FT this gives the same 16 B/param with a different split. In a LoRA, however, it doubles the memory of the frozen weights, which go from 2 to 4 B/param. Always pass --dtype bfloat16.

In an MoE, you pay for the total

In the full FT of an MoE, every expert has a gradient and optimizer state, even if each token visits only a few of them. Memory scales with the total parameters; compute per token, with the active ones. Qwen3-30B-A3B (30.5 B total, 3.35 B active) needs 488 GB of state for a model that computes like a ~3.3 B one. And there is a subtlety: an expert can go through an entire microbatch without receiving a single token. Its gradient is zero on that step, but Adam keeps decaying the moments. MiMo-V2-Flash uses the count of parameters with zero gradient (num-zeros) as a thermometer for MoE SFT: if it rises, expert load balancing is getting worse; if it falls, the model is overfitting.

Why this matters for the rest of the module

Classic RLHF with PPO keeps four models in memory: a trainable policy and critic (16 B/param each), plus a frozen reference model and reward model (2 B/param each). That is \(36N\) bytes: with four 8 B models, 288 GB before the activations and before the inference engine that generates the rollouts. This math is what pushes LLM RL toward LoRA (the reference becomes “the same network with the adapter turned off”), toward smaller critics, or toward critic-free methods such as GRPO. The math in this chapter is the yardstick for every method on the post-training map.

Mixed precision: the master weight and the BF16 step

Why spend 4 bytes on an FP32 master weight if the forward uses BF16? The answer is in chapter 4. BF16 has 8 exponent bits (the range of FP32) and only 7 explicit mantissa bits. Between two neighboring BF16 numbers there is a step, the ulp, and round-to-nearest-even throws away any addition smaller than half a step:

\[ \mathrm{ulp}(w) = 2^{\lfloor \log_2 |w| \rfloor - 7}, \qquad \mathrm{bf16}(w + \Delta) = w \quad\text{if}\quad |\Delta| < \tfrac12\,\mathrm{ulp}(w) \]
  • \(w\): the weight, already in BF16
  • \(\lfloor \log_2|w|\rfloor\): the exponent, that is, the binade where \(w\) lives
  • \(-7\): the 7 mantissa bits split each binade into \(2^7 = 128\) steps
  • \(\Delta\): the optimizer update on this step

Now plug in the typical size of an update. AdamW divides the first moment by the square root of the second moment, so each coordinate moves by something on the order of the learning rate \(\eta\) per step. A typical SFT uses \(\eta \approx\) 1e-5 to 2e-5 (TRL’s default is 2e-5). On a weight of magnitude 0.02, the ulp is 1.22e-4 and half an ulp is 6.1e-5. Steps of 1e-5 are all rounded to zero. Weight decay is even worse: \(\eta\lambda w = 10^{-5}\times 0.1\times 0.02 = 2\times10^{-8}\) always vanishes. The table comes from a simulation with real BF16 rounding:

\(w\)ulp½ ulp\(w\) + 1e-6\(w\) + 1e-5\(w\) + 1e-4

Notice the perverse effect: small weights move, and in steps larger than requested; large ones stay stuck. Pure BF16 training does not fail with a bang; it just learns less than you told it to. There are three remedies. The first is the FP32 master weight (regime A): the additions happen with 23 mantissa bits and only the copy used in the forward is rounded. The second is Kahan compensated summation, which keeps aside the remainder lost in each addition and gives it back in the next one. The third is stochastic rounding, which rounds up or down with probability proportional to the distance, and therefore gets it right on average:

\[ \mathrm{SR}(x) = \begin{cases} \lceil x \rceil & \text{with prob. } p = \dfrac{x - \lfloor x\rfloor}{\mathrm{ulp}} \\[4pt] \lfloor x \rfloor & \text{with prob. } 1-p \end{cases} \qquad\Longrightarrow\qquad \mathbb{E}\big[\mathrm{SR}(x)\big] = x \]
  • \(\lfloor x\rfloor, \lceil x\rceil\): the two BF16 neighbors of \(x\)
  • \(p\): the fraction of the step that \(x\) has already covered
  • the expected value is exact: many small steps add up to what they should, with noise

What about FP8? And NVFP4?

Training “in FP8” means doing the GEMMs in FP8, and sometimes storing activations in FP8. The optimizer state and the master weights stay in high precision. DeepSeek-V3 is the reference: FP8 GEMMs with fine-grained quantization (1×128 blocks for activations and 128×128 for weights), accumulation promoted to FP32, master weights and weight gradients in high precision, AdamW moments in BF16, and the embedding, head, MoE gating, normalizations, and attention kept out of FP8. MiMo-V2-Flash follows the same design and keeps FP32 in the router parameters. Low precision in training buys speed, not state memory. NVIDIA’s nvfp4-pretraining playbook measured, on a GB300 (not on the Spark), Llama 3.1 8B with the bf16_with_nvfp4_mixed recipe: 9.05 s/step and a 221.6 GB peak in BF16 versus 5.39 s/step and 207.8 GB in NVFP4. That was 1.68× faster with only ~6% less memory. For the GB10 (sm_121), support for the FP8/NVFP4 training paths was not confirmed in this module’s research; Module 1 already showed that several “Blackwell” kernels in vLLM are sm_100 only (chapter 28).

Activations and logits: the memory that grows with the text

The 16 B/param do not depend on the text. The saved activations do, and a lot. Korthikanti et al. counted, for a Transformer block with 16-bit activations, how many bytes stay saved per layer waiting for the backward:

\[ A_{\text{layer}} = s\,b\,h\left(34 + \frac{5\,a\,s}{h}\right)\ \text{bytes} \quad\xrightarrow{\ \text{FlashAttention}\ }\quad A_{\text{layer}} \approx 34\,s\,b\,h \]
  • \(s\): sequence length; \(b\): microbatch (sequences per forward step)
  • \(h\): hidden size; \(a\): number of attention heads
  • \(34\): the sum, in bytes per unit of \(sbh\), of every tensor the backward rereads (QKV, attention, projections, MLP, norms, and dropout masks); the table right below breaks it down
  • \(5as/h\): the \(s\times s\) attention matrix, which FlashAttention does not materialize

The rule for any other architecture is the same: list every tensor the backward rereads and add up the bytes. In an MoE, the MLP row becomes the \(k\) active experts of each token, with each expert’s intermediate, plus the router logits. In a model with a widened residual stream, such as the 4 mHC streams of GLM-5.3-Flash (4 × 4,096 numbers per token), the mixes between streams and the norms reread inputs of that width, and the KDA layers have their own accounting. That is why the calculator at the end of the chapter does not estimate GLM activations (interpretation).

For Llama-3.1-8B (\(h = 4096\), 32 layers) with a 2,048-token sequence, this comes to 9.13 GB, and it grows linearly with \(s\): 146 GB at 32K tokens. The way out is gradient checkpointing. Instead of saving everything, you save only the input of each layer (\(2sbh\) bytes) and, in the backward, each layer is recomputed from it, one at a time:

\[ A_{\text{peak}}^{\text{ckpt}} \;\approx\; \underbrace{2\,s\,b\,h\,L}_{\text{saved inputs}} \;+\; \underbrace{34\,s\,b\,h}_{\text{the layer being recomputed}}, \qquad \text{FLOPs per token: } 6N \;\to\; 8N \]
  • \(L\): number of layers
  • \(6N\): forward (\(2N\)) + backward (\(4N\): gradients of the activations and of the weights), with \(N\) = active parameters
  • \(8N\): the recompute costs one more forward, that is, ~33% more math

There is a third giant, the logits tensor \([b, s, V]\). In FP32 it takes \(s\cdot V\cdot 4\) bytes per sequence: with vocabularies of 128–152K tokens, ~1 GB per 2K tokens. In the backward, the logits gradient is the same size, so the real peak is ~2× \(s\cdot V\cdot 4\). With short sequences, the logits become the largest thing in memory. TRL uses loss_type="chunked_nll" by default: it drops the positions with labels == -100 before the lm_head and computes the cross-entropy in chunks, without materializing either the logits or their gradient all at once. The documentation reports ~30% less peak memory on Qwen3-1.7B, and up to ~50% with FSDP2 on 4 GPUs. The option is not compatible with Liger, PEFT, or VLM, so in a LoRA run check the log to see which loss was chosen. There is also selective checkpointing (gradient_checkpointing_kwargs={"selective": True} in TRL), which saves the attention output so it does not have to be recomputed at long context.

Analogy: the trail and the breadcrumbs

Without checkpointing, you climb the mountain taking a photo of every step so you can retrace the path on the way down: the backpack fills up with photos. With checkpointing, you only drop a breadcrumb at each camp and, on the way down, you redo the stretch between two breadcrumbs by looking around again. You walk more (one extra forward), but you carry almost nothing.

Offload on a unified-memory machine

On a discrete GPU, sending activations (activation_offloading=True in TRL), optimizer states (ZeRO-Offload), or optimizer pages to host RAM frees up VRAM. On the GB10 and on Apple Silicon, host RAM is GPU memory (chapter 27). Offloading to the “CPU” creates no new capacity: at most it changes fragmentation or pinning. Only offloading to NVMe (ZeRO-Infinity) adds capacity. And the Module 1 tip that the Spark playbooks repeat still applies: if training fails “within capacity,” free the page cache with sudo sh -c 'sync; echo 3 > /proc/sys/vm/drop_caches' before starting.

Optimizers, learning rate, and batches

Chapter 1 showed how momentum, AdamW, and Muon move across the loss landscape. Here the question is different: what each one carries, and how much that costs in memory and in bandwidth.

  • Plain SGD stores nothing. With momentum, it stores one buffer the size of the weights.
  • AdamW stores two: \(m\) (mean of the gradient) and \(v\) (mean of the squared gradient), coordinate by coordinate. TRL SFTConfig defaults: adam_beta1 0.9, adam_beta2 0.999, adam_epsilon 1e-8, weight_decay 0.0, optim "adamw_torch_fused", max_grad_norm 1.0. LLM pretraining runs usually use \(\beta_2 = 0.95\) (MiMo-V2-Flash used \(\beta_1\) 0.9, \(\beta_2\) 0.95, weight decay 0.1, and clipping at 1.0).
  • 8-bit AdamW (bitsandbytes) quantizes \(m\) and \(v\) in blocks, as in chapter 20; Axolotl’s examples use optimizer: adamw_8bit. That is ~2 B/param of state, with a quality risk that still has to be measured.
  • Adafactor does not store the full \(v\) matrix: it stores row and column means and reconstructs the second moment as an outer product. Memory becomes sublinear (available in mlx_lm.lora --optimizer adafactor).
  • Muon stores one momentum buffer and orthogonalizes the update via Newton–Schulz, using the quintic iteration with coefficients \((a,b,c) = (3.4445,\,-4.7750,\,2.0315)\) for 5 steps (MLX uses exactly this, with momentum 0.95, Nesterov, weight_decay 0.01, ns_steps 5). It applies only to hidden 2D matrices; embeddings, head, norms, and biases stay on AdamW. The extra cost in FLOPs is \(\approx T m/B\) (\(T\) Newton–Schulz steps, \(m\) the model dimension, \(B\) the tokens in the batch): 0.7% in the NanoGPT speedrun and ~0.5% for a hypothetical “Llama 405B”.

AdamW’s defaults are not arbitrary numbers. Each one answers a question about the gradient: how much of the past to remember, how much to trust the estimated scale, how much to pull back. The values from SFTConfig and from MiMo-V2-Flash pretraining, side by side:

Muon in pretraining, and the mismatch in SFT

To scale Muon, Moonlight matched the RMS of the update to AdamW’s and added weight decay: \(W \leftarrow W - \eta\,(0.2\cdot O\cdot\sqrt{\max(A,B)} + \lambda W)\), where \(A\times B\) is the matrix shape. With that, it reported ~2× compute efficiency versus AdamW in the compute-optimal regime (3B/16B MoE, 5.7T tokens). Two Module 1 models were pretrained this way. Qwen3.8 uses Muon with 8 Newton–Schulz iterations on the “linear” matrices and AdamW on the embeddings, the router, and the low-rank GR projections. At 4× the optimal learning rate, AdamW with the Qwen3.5 architecture had 183 spikes per 10,000 steps, while Muon with GR had zero. DeepSeek-V4 uses a hybrid 10-iteration Muon: 8 with \((3.4445, -4.7750, 2.0315)\) and 2 with \((2, -1.5, 0.5)\). Moonlight’s practical finding for post-training is that the best result came from using Muon in pretraining and in SFT; switching optimizers between the two erased Muon’s advantage in SFT. Interpretation: in a full FT of Qwen3.8 or DeepSeek-V4, Muon is the coherent choice; in LoRA, where the \(A\) and \(B\) matrices are thin, the evidence is weak and AdamW remains the default. Muon is available as torch.optim.Muon starting with PyTorch 2.9 (2D parameters only and, in that version, without distributed support), as optim.Muon in MLX, and as mlx_lm.lora --optimizer muon.

The bandwidth of the optimizer step

A mixed-precision AdamW step reads the gradient, master, \(m\), and \(v\), and writes the master, \(m\), \(v\), and the BF16 copy: ~28 bytes per parameter. For 8 B parameters, that is ~225 GB; at ~230 GB/s effective on the GB10, ~1 s per step for the optimizer alone. With LoRA r=16 (41.9 M trainable parameters), ~1.2 GB, ~5 ms. On LPDDR5x memory, frequent optimizer steps are expensive in full FT. Accumulating gradients, that is, running several microbatches per step, amortizes that second.

The learning-rate clock

The learning rate \(\eta\) is almost never constant. Warmup ramps \(\eta\) up gradually at the start; the usual explanation is that Adam’s \(v\) estimates are still raw in the first steps, and large steps there destabilize training. Then comes the decay: linear (Tülu 3), cosine (Axolotl, LLaMA-Factory, MiMo’s SFT), or WSD (warmup-stable-decay). MiMo-V2-Flash pretraining warmed up to 3.2e-4 over 50 B tokens, stayed constant for 12T, and decayed along a cosine to 1e-4 over 10T. In short LoRA runs it is common to stay constant after warmup. Batches, packing, and sequence length

The effective batch is microbatch × gradient accumulation steps × data-parallel replicas. The number that matters is tokens per optimizer step. LoRA tolerates very large batches worse than full FT does, and raising the rank does not fix it: it is a property of the \(BA\) parametrization. Another detail that changes the LR is loss normalization. Tülu 3 switched from the mean to the sum to avoid the accumulation bias (with a per-microbatch mean, samples with few tokens get too much weight), “which requires adjusting the LR”; TRL normalizes by the total number of tokens in the accumulated batch (average_tokens_across_devices=True).

Packing puts short examples together in the same max_length row so positions are not wasted on padding. SFTTrainer packs with best-fit decreasing ("bfd", the default; it drops the overflow of long examples), "bfd_split" (cuts long examples into pieces), or "wrapped" (concatenates everything and cuts it into blocks, mixing examples; the Qwen3-Coder-Next report says this hurts). With "bfd", padding_free turns on by itself: the batch becomes a single sequence, with position_ids reset per example, and variable-length FlashAttention keeps one example from attending to another. Without FlashAttention 2/3 there is a risk of “contamination” between examples, and its availability on sm_121 was not confirmed. The length \(s\) weighs in three times: activations \(\propto s\), attention FLOPs \(\propto s^2\), logits \(\propto sV\). For reasoning models there is no escaping it: the MOPD examples use 32,768 tokens (math/instructions) and 65,536 (SWE). The SFT chapter comes back to packing and the loss mask in detail.

Divide to fit: data parallel, ZeRO, FSDP, and friends

In chapter 38 the problem was serving a model that does not fit on one GPU. In training, the extra problem is the state. Classic data parallel (DDP) replicates everything in each process: each one runs its own microbatch, and an all-reduce sums the gradients before the step. It is simple, but wasteful: \(N_d\) processes keep \(N_d\) identical copies of the optimizer. ZeRO (Zero Redundancy Optimizer) partitions that state instead of replicating it:

StageWhat is partitionedMemory per process (\(K\) = 12)
DDPnothing\((2 + 2 + K)\,\Psi\)
ZeRO-1 (\(P_{os}\))optimizer\((2 + 2)\,\Psi + K\Psi/N_d\)
ZeRO-2 (\(P_{os+g}\))+ gradients\(2\Psi + (2 + K)\,\Psi/N_d\)
ZeRO-3 (\(P_{os+g+p}\)) ≈ FSDP FULL_SHARD+ parameters\((2 + 2 + K)\,\Psi/N_d\)

The paper’s example (7.5 B parameters, \(N_d = 64\)) goes from 120 GB to 31.4, 16.6, and 1.9 GB per process. The example we care about is Llama-3.1-8B (8.03 B) on two Sparks, one process per node: DDP needs 128.5 GB per node and does not fit; ZeRO-1, 80.3; ZeRO-2, 72.3; ZeRO-3, 64.2 GB per node, and then it fits along with the activations.

ZeRO is not free on the network. DDP, ZeRO-1, and ZeRO-2 move \(2\Psi\) elements per step. An all-reduce is a reduce-scatter (each process ends up with the sum of one shard) followed by an all-gather (everyone receives all the shards), and each half moves ~\(\Psi\), hence \(2\Psi\). ZeRO-1/2 does the same two halves with the optimizer step in the middle: reduce-scatter of the gradients, each process updates its shard, all-gather of the updated parameters. ZeRO-3 moves \(3\Psi\), 1.5× as much, because it gathers the parameters in the forward and again in the backward. Between two Sparks, the 200 Gb/s cable gives 25 GB/s in theory, served by two PCIe Gen5 ×4 functions of ~126 Gb/s each (chapter 39); at ~20 GB/s effective (research-note assumption), the all-reduce of an 8B’s 16.1 GB of gradients takes ~0.8 s per step (~1.2 s with ZeRO-3). The compute for a step with a global batch of 64 × 2,048 = 131,072 tokens is \(6 \times 8.03\times10^{9}\times 131{,}072 \approx 6.3\times10^{15}\) FLOPs, ~63 s on the two Sparks at 50 TFLOPS effective each (assumption: ~40% MFU of the estimated 125 TFLOPS peak). The network stays at 1–2% even without overlap. It is the opposite of decode with TP over the same cable, where each token waits on ~100 collectives: in training, the compute/communication ratio per step is huge.

FSDP is PyTorch’s native ZeRO-3; version 2 (fully_shard) shards per parameter on top of DTensor. The Spark multi-node playbook uses Accelerate with this configuration:

TP, PP, EP, and CP when there is a backward

The other parallelisms from chapter 38 come back, now with twice the collectives, because the backward communicates too.

  • TP (Megatron): the same column→row pair as in inference. Per layer, 2 all-reduces in the forward and 2 in the backward, each of \(s\cdot b\cdot h\cdot 2\) bytes. An 8B with TP = 2 across the Sparks and a microbatch of 8 × 2,048 moves 134 MB per all-reduce, × 4 × 32 layers ≈ 17.2 GB per microbatch: ~0.86 s at 20 GB/s versus ~7.9 s of compute per node at 50 TFLOPS, ~11% without overlap. Megatron’s sequence parallel splits the norm and dropout activations across the TP ranks.
  • PP: layers in stages. In the 1F1B schedule, the bubble costs \((p-1)/m\) of the ideal time, with \(p\) stages and \(m\) microbatches: 12.5% with 2 stages and 8 microbatches.
  • EP: whole experts on different nodes; two all-to-all operations per MoE layer in the forward (dispatch and return) and two in the backward. It is the natural way to train MoE across several nodes (Megatron-Core, DeepEP); Axolotl gained EP in 2026/06.
  • CP (ring attention, Ulysses): splits the sequence across ranks for long context. TRL 1.13 documented 1,048,576 tokens per step on Qwen3-8B on an 8×H100 node (~380 s/step), with chunked_nll, checkpointing offload, and YaRN, without packing.

Interpretation for the Spark: for SFT of dense models up to ~8B, FSDP/ZeRO-3 on 2 nodes is the simplest path, and it is the playbook’s. TP across nodes is only justified when a node cannot hold even one layer with its activations. For large MoE, EP would be mandatory, but full FT of those models is already out of reach, as section 8 shows.

LoRA: train only the difference, in low rank

All the levers so far trim the \(16\Psi\) state from the outside. LoRA (Hu et al., 2021) goes after \(\Psi\) itself. The observation is that the change post-training makes to a weight matrix has a low “intrinsic dimension.” So, instead of learning the full correction \(\Delta W\), with \(d_{out}\times d_{in}\) numbers, you learn a low-rank factorization, \(\Delta W = BA\), and the original \(W_0\) stays frozen:

\[ h \;=\; W_0\,x \;+\; \frac{\alpha}{r}\,B\,A\,x, \qquad A\in\mathbb R^{r\times d_{in}},\quad B\in\mathbb R^{d_{out}\times r},\quad r \ll \min(d_{in}, d_{out}) \]
  • \(W_0\): the pretrained matrix, frozen (no gradient, no optimizer)
  • \(A\): projects the input down to \(r\) dimensions; \(B\): projects back up to \(d_{out}\)
  • \(r\): the adapter’s rank, typically 8–64
  • \(\alpha/r\): the scale that multiplies the correction
  • trainable per matrix: \(r\,(d_{in} + d_{out})\) instead of \(d_{in}\,d_{out}\)

It is the same idea as q_lora_rank and kv_lora_rank in MLA, applied somewhere else: there, the low-rank bottleneck is part of the architecture; here, it sits in the update. In a 4096×4096 q_proj of Llama-3.1-8B, with \(r = 16\), that is \(16\times(4096+4096) = 131{,}072\) trainable numbers versus 16.8 million: 0.78%. In the original paper, on the 175B GPT-3, LoRA cut trainable parameters by 10,000× and GPU memory by 3× relative to full FT with Adam, and the adapter checkpoint (\(r = 4\), only on q and v) shrank from 350 GB to ~35 MB.

Initialization: B starts at zero

Matrix \(A\) is born random (in PEFT, Kaiming-uniform; in MLX, uniform in \(\pm 1/\sqrt{d_{in}}\)) and \(B\) is born zeroed. At step 0, \(\Delta W = 0\) and the model is exactly the base, which guarantees that the fine-tune starts from known behavior. Why not zero both? The gradients are \(\partial L/\partial B \propto (\ldots)\,A^\top\) and \(\partial L/\partial A \propto B^\top(\ldots)\). With both zeroed, both gradients would be zero forever. With a random \(A\), \(B\) receives gradient from the very first step, and \(A\) “wakes up” as soon as \(B\) stops being zero. The figure trains a real LoRA, with Adam, to reproduce a rank-3 target correction.

Play with the rank. With \(r=1\) the error stops at ~55%, which is exactly \(\sqrt{1.2^2+0.5^2}/\sqrt{2^2+1.2^2+0.5^2}\): the best a rank-1 matrix can do is the dominant singular component (the Eckart–Young theorem). With \(r = 3\), the error goes to zero. The toy has a hard floor because the target is a single fixed matrix and the loss is the Frobenius error: Eckart–Young gives the best possible rank-\(r\) approximation. A real LLM has no fixed target \(\Delta W\). There are dozens of matrices in series, with nonlinearities, fitting a loss over tokens. What LoRA Without Regret observed is that an adapter too small for the dataset does not get stuck on a visible plateau; its loss curve just goes down more slowly than full FT’s. That is what “capacity-limited” means in practice.

The α/r scale and the target modules

With the \(1/r\) prefactor, the initial contribution of \(\frac{1}{r}\sum_{i=1}^{r} b_i a_i^\top\) does not grow with the number of terms, which is why the optimal LR barely changes with the rank: it varies by less than 2× between \(r = 4\) and \(r = 512\), according to LoRA Without Regret (Thinking Machines). rsLoRA changes the scale to \(\alpha/\sqrt r\) to stabilize high ranks (use_rslora=True). Conventions vary: Thinking Machines uses a fixed α = 32; Unsloth, α = 2r; Axolotl, r16/α32 for LoRA and r32/α16 for QLoRA; NVIDIA’s playbook, r8/α16. In mlx-lm, the parameter scale = 20 is not PEFT’s α: it multiplies \(BA\) directly, which is equivalent to \(\alpha/r = 20\) (α = 160 with r = 8). The code warns you if you pass alpha.

Where to put the adapters is the most important decision. The practical results from LoRA Without Regret:

  • LoRA on all matrices, especially MLP/MoE. Attention-only is clearly worse even with the same number of parameters: attention with r = 256 loses to MLP with r = 128 on Llama-3.1-8B, and the same holds for Qwen3-30B-A3B.
  • LoRA matches full FT in sample efficiency when it is on all layers and is not capacity-limited.
  • In RL, it matches full FT even at rank 1. The argument is information-theoretic: a policy-gradient episode carries O(1) bits (the advantage), while an SFT example carries O(number of tokens) bits.
  • LoRA’s optimal LR is ≈ 10× that of full FT (≈ 15× in runs with fewer than ~100 steps).

QLoRA, DoRA, LoRA on experts, and merging

LoRA cut the state, but the frozen base still takes 2 B/param: 141 GB for a 70B. QLoRA (Dettmers et al., 2023) freezes the base in 4 bits and trains the adapters on top of it, with the promise to “fine-tune a 65B parameter model on a single 48GB GPU” without losing the performance of 16-bit fine-tuning. There are three ingredients.

  1. NF4 (4-bit NormalFloat). Pretrained weights are approximately Gaussian. Instead of 16 uniform levels, NF4 places the levels at the quantiles of an \(\mathcal N(0,1)\) normalized to \([-1, 1]\): more levels near zero, where there are more weights. They are asymmetric (8 positive, 7 negative, and an exact zero), with an absmax scale per block of 64 weights. It is the “codebook + per-block scale” family from chapter 20, but without tensor cores: the kernel dequantizes to BF16 before the GEMM.
  2. Double quantization. Each block of 64 weights has an FP32 scale, which costs 32/64 = 0.5 bit per parameter. QLoRA quantizes those scales to 8 bits, in blocks of 256 scales with one FP32 scale per block.
  3. Paged optimizers. They use NVIDIA unified memory to page state between CPU and GPU at the peaks. Interpretation: on the GB10, this does not create memory (CPU and GPU share the same LPDDR5x); it only avoids OOM at peaks if there are pages to free.
\[ \text{bits/param} \;=\; \underbrace{4}_{\text{NF4 code}} \;+\; \underbrace{\frac{8}{64}}_{\text{8-bit scale}} \;+\; \underbrace{\frac{32}{64\cdot 256}}_{\text{scale of the scale}} \;=\; 4.127 \;\;(0.516\ \text{B/param}) \]
  • 64: weights per first-level block
  • 256: scales per second-level block
  • without double quantization it would be \(4 + 32/64 = 4.5\) bits: the savings are 0.373 bit/param, ~3 GB on a 65B

DoRA: separating size from direction

DoRA (Liu et al., ICML 2024) decomposes each weight column into magnitude and direction. LoRA acts only on the direction, and the magnitude becomes a trainable vector of its own:

\[ W' \;=\; m \cdot \frac{W_0 + BA}{\lVert W_0 + BA\rVert_c}, \qquad m^{(0)} = \lVert W_0 \rVert_c \]
  • \(\lVert\cdot\rVert_c\): the norm of each column
  • \(m\): trainable magnitude vector, one number per column
  • at the start, \(BA = 0\) and \(m = \lVert W_0\rVert_c\), so \(W' = W_0\)

DoRA closes part of the gap to full FT, especially at low rank, and it is also mergeable, with zero cost after the merge. The price is more memory and time during training because of the norm. You turn it on with LoraConfig(use_dora=True) in PEFT or --fine-tune-type dora in mlx-lm, which does not support DoRA on expert layers (SwitchLinear). Other variants you will run into in configs: LoRA+ (LR of \(B\) = λ × LR of \(A\), λ ≈ 16, via loraplus_lr_ratio), PiSSA (initializes \(A\) and \(B\) with the principal singular components of \(W_0\)), OLoRA, EVA, and CorDA (other initializations), LoRA-FA (freezes \(A\) and reduces activation memory), and rank_pattern/alpha_pattern (rank and α per module, by regex).

LoRA in an MoE

There are four places to put the adapter in an MoE. (1) Only on the attention and the shared expert: cheap, but that is precisely where LoRA pays off least. (2) One LoRA per expert, with 3D adapters \([E, r, d_{in}]\) and \([E, d_{out}, r]\): this is what MLX does in LoRASwitchLinear (two gather_mm calls indexed by the routing) and what PEFT does with target_parameters=["mlp.experts.gate_up_proj","mlp.experts.down_proj"]. Thinking Machines used, per expert, rank = total rank ÷ active experts (8 in Qwen3 MoE), which keeps the LoRA/full ratio equal to that of the dense layers. (3) Factors shared across experts (“shared-outer”), which vLLM loads with --enable-moe-shared-loras. (4) The router stays frozen. In Unsloth’s words, “it's not a good idea to fine-tune the router layer”, and MiMo-V2.6-Pro (384 experts per layer) showed why: in RL with a trainable router, the expert load collapsed within 20 steps (coefficient of variation from 0.78 to 2.0, “cold” experts from 0.5% to 22%), and restoring only the router recovered the balance without changing the benchmarks.

Merging the adapter, and the QLoRA problem

The merge is the LoRA equation added in one go: \(W = W_0 + \frac{\alpha}{r}BA\). Once merged, the inference cost is zero. The tools: PeftModel.from_pretrained(base, id).merge_and_unload() (and add_weighted_adapter to combine adapters by linear, svd, ties, dare_ties…), mlx_lm.fuse, axolotl merge-lora, and llamafactory-cli export, whose example warns: “DO NOT use quantized model or quantization_bit when merging lora adapters”. The reason is subtle (interpretation). A QLoRA adapter learned to correct \(\mathrm{deq}(W_{NF4})\), not \(W_{BF16}\). Merging into \(W_{BF16}\) gives \(W_{BF16} + BA \ne \mathrm{deq}(W_{NF4}) + BA\), and the difference is the quantization error the adapter may have been compensating for. Merging into \(\mathrm{deq}(W_{NF4})\) preserves the trained function, but “bakes” the NF4 error into the model. Either way, measure the KLD against the trained model, as in chapter 25.

You can also skip the merge and serve several adapters on top of the same base (multi-LoRA). In vLLM: --enable-lora, --lora-modules name=path, --max-loras (default 1, distinct adapters in a batch), and --max-lora-rank (default 16; choices 1, 8, 16, 32, 64, 128, 256, 320, 512; it sizes the memory, so use the largest rank you will serve). The prefix caching hash includes the LoRA ID, and CUDA graph dispatch separates batches with and without LoRA (has_lora in the BatchDescriptor).

How long it takes

Memory tells you whether it fits; FLOPs tell you how long it takes. With \(N\) = active parameters, one training token costs ≈ \(6N\) in full FT, \(8N\) with checkpointing, \(4N\) in LoRA, and \(6N\) in LoRA with checkpointing. A Spark’s ceiling is \(F/(kN)\) tokens per second:

\[ t \;=\; \frac{\text{tokens}\times k\times N}{\text{MFU}\times F\times \text{nodes}} \]

  • \(F\): hardware peak (~125 TFLOPS of dense BF16 on the GB10, Module 1 estimate)
  • MFU: the fraction of the peak that training actually uses (the 40% below is an assumption; the GB10’s real training MFU has not been measured)

The recipe’s model has 125.7 B main parameters, plus the 51.2 B PLE table and the vision and MTP parts. Full FT and BF16 LoRA are out of reach (≥ 250 GB for the base alone). A QLoRA on 2 nodes would fit in theory (4-bit main weights ~65–71 GB + FP8 PLE ~51 GB, more than one node holds), but it requires support for GR, PLE, QSA, and GDN in the training stack, which has not been verified. Module 1’s serving checkpoints do not work as a training base either: the recipes’ packed formats have no backward kernel, so you would have to start from the official BF16. The viable path (interpretation) is to use the recipe as a teacher: serve Qwen3.8 with Module 1’s vLLM and distill a small student (4–14B) from the same tokenizer family (248,320-token vocabulary; check the tokenizer.json). And if you ever merge an adapter into it, remember that Qwen3.8 was pretrained with Muon and that the MTP head used as a drafter was trained against the original model: re-measure the speculative decoding acceptance rate (chapter 35) before celebrating.

Minimal roadmap

(1) Do the math: state + activations + logits per node, against ~105 GiB on the Spark or ~19 GB on the Mac. (2) Pick the method from the column that gives ✅, not 🟡. (3) Turn on --dtype bfloat16, checkpointing, and LoRA on all linear layers, with an LR ~10× that of full FT. (4) On 2 nodes, use FSDP/ZeRO-3 and test the network first. (5) After training, merge in BF16, requantize to the recipe’s format, and measure the KLD and the task metric: the effect of the fine-tune has to survive quantization.
