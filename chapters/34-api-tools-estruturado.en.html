Everything we have seen so far (quantized weights, paged KV, the scheduler, the prefix cache) exists for one single moment: a client sends a JSON payload over HTTP and expects another one back. That client may be a chat app, a coding agent or a benchmark. It never sees tensors, only text, fields and status codes. This chapter opens that door. You will see how messages become tokens, how tokens turn back into text, how reasoning is separated from the answer, how the model “calls tools” and how a grammar can guarantee valid JSON. You will also see why all three recipes pile up so many patches right here: the API boundary is where a small detail (a stop that fires too early, a syntax token sampled with temperature, a speculative batch that runs past the end of the grammar) turns into a silent failure for the user. And since the GLM recipe gained a second version on another engine, TensorFold , you will also see how a server that promises the same reply with or without drafts solves these boundaries differently: tool calls that only go out whole, reasoning that the server puts back when the client throws it away, and a broken call in the history that no longer locks up the conversation.

A server that speaks “OpenAI”

Almost every LLM client speaks the same dialect: the HTTP API that OpenAI popularized. An OpenAI-compatible server implements the same routes and the same JSON fields, so changing the base_url is enough for the same SDK, the same agent or the same benchmark to talk to a different model. vllm serve brings up exactly that: a FastAPI/uvicorn server (the API server you met in Inside vLLM) sitting in front of the EngineCore.

/v1/models
GET. Lists the names the server accepts in the model field, that is, whatever you passed in --served-model-name.
/v1/chat/completions
POST. The main route. It receives messages (roles system/user/assistant/tool), applies the chat template and generates.
/v1/completions
POST. The “raw” route: it receives a prompt that is already text and does not apply a template. It is great for causal experiments, because you control every byte of the prompt.
/v1/responses
POST. The newest API (used by agents such as Codex), with typed items and optional server-side state. It gets its own section further ahead.
/tokenize
A utility mounted at the root, outside /v1 (as is /detokenize). It receives a prompt (or messages) and returns the IDs.
/health
Readiness: the launcher polls it until it gets a 200. Its neighbors: /metrics (Prometheus), /version and /docs (FastAPI's interactive documentation, which the Qwen recipe lists among the head's endpoints).

One design fact shapes everything that follows: the chat API is stateless. The server does not remember the conversation. On every turn the client resends the whole history, with the system prompt, the tools, previous answers and tool results. That may look wasteful, and it would be, were it not for prefix caching, which recognizes the repeated prefix and skips the corresponding prefill. That is why so many decisions in this chapter are judged by the question “does this change the bytes at the start of the prompt?”.

In the figure below, follow a request from start to finish. Each station is a piece of the API server or of the engine. Notice where the masks, the stops and the parsers come in, because each section of the chapter digs into one of these stations.

Name, address and port

Three flags define “where” and “how” the model shows up. --served-model-name is the public id. The client must send exactly that text in model, or it gets a 404. The flag accepts several aliases (the DeepSeek recipe documents space-separated aliases). The response uses the first one, and so do the recipe's probes, warmup and smoke test. --host is the network interface the server listens on: 127.0.0.1 only accepts connections from the machine itself, 0.0.0.0 accepts them from any interface. --port is the TCP port (vLLM's default is 8000; all three recipes use 8888). In multi-node inference, only the head (rank 0) serves the API. The worker comes up with --headless, with no HTTP server.

GLM

  • --served-model-name GLM-5.3-Flash-EXL3
  • --host 0.0.0.0 --port $PORT, PORT=8888
  • The preflight checks that the port is free.

Qwen

  • qwen3.8-flash-next (FP8 lane: qwen3.8-flash-next-fp8)
  • --host 0.0.0.0, port 8888 on the head only
  • On TP1, comfy-h3.service also listens on 8888 and the script refuses to launch.

DeepSeek

  • deepseek-v4-flash-vision-exp (accepts aliases)
  • VLLM_HOST: the compose fallback is 127.0.0.1, but the example .env opens 0.0.0.0
  • VLLM_PORT=8888, validated between 1 and 65535
Small traps, big effects

The DeepSeek launcher normalizes the port with $((10#$VLLM_PORT)). In bash, a number with a leading zero (“08888”) would be read as octal and fail, and the 10# prefix forces base 10. Older benchmark scripts in the same recipe still have deepseek-v4-flash-0731 as the default name and need --model deepseek-v4-flash-vision-exp. A wrong name degrades nothing: the server simply answers 404.

Fields beyond the standard: extra_body and vllm_xargs

vLLM accepts fields that OpenAI does not define: chat_template_kwargs, structured_outputs, bad_words, vllm_xargs, thinking_token_budget… In the Python SDK they go in extra_body, an option of the SDK that merges its contents into the top level of the JSON. In raw HTTP, send these fields directly at the top level. A literal "extra_body": {…} object in the body is a common mistake that the GLM README documents. vllm_xargs, in turn, is a free-form dictionary that reaches the sampling parameters and lets overlays add per-request options without breaking clients. One example is GLM's {"skip_writing_prefix_cache": 1}, which the previous chapter explains.

from openai import OpenAI
cli = OpenAI(base_url="http://head:8888/v1", api_key="sk-…")
r = cli.chat.completions.create(
    model="GLM-5.3-Flash-EXL3",
    messages=[{"role": "user", "content": "What is 17 + 25?"}],
    max_tokens=32768,
    extra_body={                                   # the SDK "flattens" this into the top of the JSON
        "chat_template_kwargs": {"enable_thinking": True, "reasoning_effort": "low"},
        "vllm_xargs": {"skip_writing_prefix_cache": 1},
    })
print(r.choices[0].message.reasoning, r.choices[0].message.content)

/tokenize deserves a note. On GLM, /v1/tokenize returns 404: the route lives at the root and validates prompt, not text. The response carries count, tokens and max_model_len. The Qwen recipe uses this route to calibrate long-context prompts (about 25 tokens per line in bench/longctx.py), and the DeepSeek warmup checks each exact-length prompt with an authenticated /tokenize before firing it.

The API also enforces per-request limits that come from server flags, not from the model. The most common one concerns media: --limit-mm-per-prompt sets how many images (and videos) fit in a single request. On Qwen, the documented default is 1 image + 1 video per prompt. On DeepSeek, LIMIT_MM_PER_PROMPT=image=8 becomes {"image":8} (with the ceiling tested at 32, the 33rd image gets HTTP 400). The DeepSeek encoder also only accepts images in user messages: an image in system, assistant or tool gets a 400, and that 400 stays in the history and poisons the session. The path from an image to tokens is in Multimodal.

In the TensorFold lane: the same door, a different engine behind it

The second version of the GLM recipe serves the same checkpoint with TensorFold v0.6.0 plus 53 patches (An exact engine), and rank 0 opens the same API with --name GLM-5.3-Flash-EXL3 --host 0.0.0.0 --port 8888 (the engine's default is 127.0.0.1:8080). The routes are almost the same: /v1/chat/completions, /v1/completions, /v1/responses, /v1/models, /health and /metrics, with no /v1/messages in v1.3.2 (since v1.9, patch 0084, the recipe also speaks the Anthropic Messages API, at /v1/messages, /messages and /count_tokens, and Claude Code and the Anthropic SDKs talk to the server directly). Patch 0037 adds /tokenize and /detokenize with vLLM's fields (prompt or messages, answered with count, tokens and max_model_len), mounted also under /v1/. The /v1/tokenize 404 described above does not happen in this lane, and /v1/completions starts accepting a prompt that is already a list of IDs. Media follow other rules: images (image_url) and videos (video_url) only in user messages, up to 50 images and 4 videos per request in a body of up to 96 MiB, and only data URLs by default (VISION_URLS=1 lets the server fetch public https:// URLs).

Refused and ignored fieldslogprobs · n · logit_bias · penalties

A “compatible” server is never compatible with everything, and what matters is knowing how it diverges. TensorFold refuses with HTTP 400 what it cannot do: logprobs: true and top_logprobs (the engine returns no token probabilities) and an n other than 1. logit_bias and the presence, frequency and repetition penalties, on the other hand, are accepted and ignored, with no error at all, and a client that relies on a penalty against repetition gets no warning. In the opposite direction, the lane adds its own extensions: "draft": false asks for the serial reference decoding, and the response carries a tensorfold block with timings (prefill_s, decode_s) and a token_sha of the generated tokens. They are how you check the engine's contract, “the reply with drafts is identical to the serial one”, by comparing hashes instead of reading texts (keyed sampling).

Streaming, usage and finish_reason

With "stream": true, the response does not arrive all at once. The server opens a long-lived HTTP connection and sends Server-Sent Events: data: {json} lines separated by a blank line, ending with data: [DONE]. Each event carries a delta, only the new piece: a chunk of content, of reasoning, or a fragment of tool_calls[i].function.arguments. The gain is in perceived latency: the user sees the first token as soon as prefill finishes (the TTFT), and an agent can start interpreting before the end.

data: {"object":"chat.completion.chunk","choices":[{"index":0,"delta":{"role":"assistant"}}]}

data: {"choices":[{"index":0,"delta":{"reasoning":"Add 17 and 25…"}}]}

data: {"choices":[{"index":0,"delta":{"content":"42"}}]}

data: {"choices":[{"index":0,"delta":{},"finish_reason":"stop"}]}

data: {"choices":[],"usage":{"prompt_tokens":812,"completion_tokens":57,
       "prompt_tokens_details":{"cached_tokens":768}}}      ← only with include_usage

data: [DONE]

(Illustrative numbers.) Two properties matter for the rest of the chapter. First: the stream is append-only. Once sent, a piece cannot be taken back. A parser that emits too early has no way to backtrack, which is why several patches in this chapter hold text in a buffer before deciding. Second: the last choice event carries the finish_reason, the reason generation stopped:

stop
The model emitted EOS or matched a stop string.
length
It ran out of max_tokens (or of context). The answer is truncated.
tool_calls
The turn ended with a complete tool call. The client should execute it.
abort
The request was canceled (disconnect, internal error).

usage and cached_tokens

The usage object counts prompt and output tokens. With --enable-prompt-tokens-details, it gains prompt_tokens_details.cached_tokens, the number of prompt tokens that came from the prefix cache. That is how a client checks whether the cache is working. When streaming, usage only appears if the client asks for "stream_options": {"include_usage": true}: the server sends an extra chunk, with an empty choices, before [DONE]. The Qwen recipe's cache document insists that this is metadata only: the flag neither turns on nor retunes prefix caching, and the Prometheus metrics at /metrics do not depend on it.

In the TensorFold lane: usage always at the end

In TensorFold, usage comes with every reply, in the stream's last event, with no need for include_usage. It carries prompt_tokens_details.cached_tokens (the reused prompt tokens) and also completion_tokens_details.reasoning_tokens, which counts the thinking tokens through </think>. The question “did the cache work?” is still answered, just without a flag. The reuse mechanism, however, is different: instead of a block-based prefix cache, the engine keeps whole prompt states on a 64-token grid (An exact engine).

Hotfixhotfix-dsv4-issue55-tool-truncation.py

Always on. When finish_reason == length, the end of the stream and the non-streaming choice report "length" and remove tool calls whose arguments is not complete JSON. A natural stop remains tool_calls. In the live A/B, before the patch every truncated cell (max_tokens = 300/800/1500/600+high) reported tool_calls. After it, all of them report length, and with max_tokens=3000 (no truncation) tool_calls still carries valid arguments. As a bonus, the audit found that FinishReason is an IntEnum: without the str(…), ABORT/REPETITION reached the client as '2'/'4'. Honest limit: invalid fragments already sent in the stream cannot be undone (append-only). The protection is the correct signal at the end.

max_tokens: who decides when nobody decides

max_tokens caps everything the model generates: reasoning, visible answer and tool markup. What happens when the client omits it? In the chat route of the vLLM version that GLM pins, the fallback is “all the remaining context” (max_model_len − prompt, bounded by platform ceilings). In the legacy /v1/completions, the protocol defaults to 16. An agent that forgets the field can generate until it fills the context, and that sequence's KV grows until it preempts other sessions.

Overlay #22DEFAULT_MAX_NEW_TOKENS=65536

patch_default_max_new_tokens.py changes only the fallback of get_max_tokens() when the request omits the field. Explicit values (including an explicit null, which keeps the native behavior) and the server ceilings still apply. To tell “omitted” apart from “explicit 16” on /v1/completions, the patch preserves the omission in a Pydantic before-validator. Valid range: 1 to 1,000,000. Empty keeps stock. Only in the two-node start.sh. The .env itself warns that it is not an admission gate (“admission is chunk-based”): what limits long-context concurrency is the KV pool. The knob is decode hygiene against endless generations (issue #43).

Output defaultMAX_TOKENS=32768 → --max-tokens

The TensorFold lane solves the same problem with another number and another rationale. A request without max_tokens gets 32,768 tokens for reasoning and answer together, cut to what is left of the window and never refused. The engine's own default is 4,096, and the recipe raised it in v1.3 because agents such as Codex send no max_tokens, and 4,096 tokens could end a reply in the middle of a tool call. An explicit max_tokens that does not fit the window, on the other hand, is refused before generating, with an error the agent knows how to read (section Update: the API boundary in TensorFold).

From dialogue to prompt: templates and thinking mode

The model never saw a JSON of messages during training. It saw text with special role markers. The chat template is the function that translates a list of messages (and the declared tools) into that text. It is usually a Jinja program that ships with the checkpoint. A wrong template raises no error: it gives you a strangely worse model, because the model now receives a format it has never seen. The details of special tokens are in Tokens and embeddings. Here we care about what the API controls.

  • GLM forces --chat-template /opt/glm53/chat_template.jinja, because the checkpoint's Jinja is language-only. It builds [gMASK]<sop><|system|>…<|user|>…<|assistant|><think>.
  • Qwen uses the checkpoint's chat_template.jinja, with <|im_start|> (248045) and <|im_end|> (248046).
  • DeepSeek ships no Jinja. With --tokenizer-mode deepseek_v4, vLLM calls the checkpoint's Python encoder (encoding_dsv4.py, copied into vLLM by the compose file), and that program is the template.

chat_template_kwargs: variables the template reads

chat_template_kwargs is a dictionary that the client sends and that becomes variables inside the template. It is how you turn reasoning on or off and choose the effort. Each family uses different names and values, and getting this wrong is the most common cause of “works on one model, breaks on another”. The dead turn (DeepSeek #52/#120)

Agent harnesses sometimes resend the conversation ending in an assistant message (on a retry, for example). The stock encoder only appends the generation trigger (<｜Assistant｜><think>) when the last message is user/developer. With an assistant at the end, the prompt ends in a “dead” EOS: the model generates 1 or 2 tokens and stops, or hallucinates markup, and the error feeds on itself. The opt-in DSPARK_ENABLE_ASSISTANT_FINAL_HOTFIX=1 appends a fresh header (also when a latest_reminder follows the assistant). The causal A/B was done through /v1/completions, precisely to control the bytes: with the turn left open, 183 coherent tokens came out, and with the turn closed by EOS, out came 400 tokens of raw DSML as text.

The reasoning parser: two voices, two fields

Reasoning models first write out their thinking between <think> and </think> and only then the answer (see Generating text). The reasoning parser (--reasoning-parser) splits that stream into two fields: the thinking goes to reasoning and the answer to content. It also defines the boundary at which other pieces change behavior. Tool calls are only extracted from content, the structured-output grammar only starts after </think>, and the client's stops take effect there (next section).

GLM · glm45

The field is reasoning. A client that reads reasoning_content gets nothing and concludes that the thinking leaked into content, which did not happen. vLLM accepts the old name on input and renames it, but never emits it. The flag also keeps the tool_choice:"none" hook alive.

Qwen · qwen3

This build streams in delta["reasoning"], not in reasoning_content, and clients and benches must read the right field. The official card also includes preserve_thinking (default true), the inverse analog of clear_thinking.

DeepSeek · deepseek_v4

It comes with --reasoning-config {"reasoning_parser":"deepseek_v4","reasoning_start_str":"<think>","reasoning_end_str":"</think>"}, which declares the markers used by the thinking budget and by stop suppression. The pinned build's documentation talks about reasoning_content. Rule of thumb: run jq '.choices[0].message | keys' against your build before writing the client.

In the TensorFold lane, the name goes back to reasoning_content

Same model, same template, different server: TensorFold returns the thinking in reasoning_content (and in delta.reasoning_content in the stream), not in reasoning. A client written for the vLLM lane reads an empty field and falls into the same trap as in the GLM card, only in reverse. On input, patch 0036 accepts both names and renames reasoning to reasoning_content before rendering, because some clients (newer vLLM, OpenRouter) use the short name. The rule of thumb from the DeepSeek card holds for all four lanes: check the keys on your server before writing the client.

Back to text: detokenization and stop strings

On the way back, the path reverses: IDs become text. It looks trivial, but it is not. A token is a sequence of bytes, and a UTF-8 character (an accented letter, an ideogram, an emoji) can be split across two tokens. The incremental detokenizer keeps offsets of what has already been converted and only emits text once the bytes form complete characters. It is also where vLLM checks the stop conditions: EOS (IDs) and stop strings (text).

A stop string can span tokens. If the model generates " Ques" and then "tion:", no single token contains Question:. That is why the search looks at a window that includes the new characters plus the \(|s|-1\) characters before them, and, when streaming, the server holds back up to \(|s|-1\) characters, so that it does not send the client the beginning of a stop that may still complete (vLLM's mechanism, simplified):

\[ \text{stop if } s \subseteq \text{text}\big[\,L_{\text{prev}} - |s| + 1 : L_{\text{new}}\big) \]
  • \(s\): a stop string from the client (e.g., "Question:")
  • \(|s|\): length of \(s\) in characters
  • \(L_{\text{prev}}\): length of the text before this step
  • \(L_{\text{new}}\): length after appending this step's tokens

The problem: stops that fire inside the thinking

Benchmarks and harnesses use stops such as "Question:" to cut the model off when it starts inventing the next question. In a reasoning model, the prompt ends in <think> (“think-in-prompt”), and the thinking, which is free-form, tends to repeat those markers (“Question: what is…?”). The v1 detokenizer matched stops against the whole stream. The request died in the middle of the reasoning with content: null.

The fix is the same in both recipes that apply it, a port of “Patch 5” by tonyd2wild/Capicua25x. The guard is only armed if the last token of the prompt is the reasoning start marker, that is, if the request really thinks. Until </think> shows up, the client's stops stay dormant. With speculative decoding (a preview of Speculative decoding), each step can deliver up to k+1 tokens at once. If </think> arrives in the middle of that batch, stop_check_offset moves past the marker, and only the answer text is checked. EOS and max_tokens do not change.

In the TensorFold lane, stops do not sleep

None of the 53 patches ports this section's guard. On CUDA, TensorFold's documentation says stop strings are checked after every token against the generated text, reasoning included. The reason is the engine's contract: the reply with drafts and the serial one must stop at the same token, and a rule that looks only at the text generated so far guarantees that. The cost is the scenario of the figure without the patch. A harness that sends stop: ["Question:"] to a thinking GLM may get the reply cut while it is still thinking (interpretation from the documented rule; the recipe publishes no such test). There is one more detail: after a match, the GLM engine keeps decoding until an end token or the limit, and the server only returns the reply up to the stop. In this lane, with thinking on, it is safer to bound the reply with max_tokens or a grammar than with stops (our suggestion).

max_tokens versus thinking

Reasoning consumes max_tokens first. If the budget runs out before </think>, the response comes back with empty content and finish_reason: "length", and it looks as if the model “did not answer”. The recipes document this with numbers: at effort max, DeepSeek produced about 50,000 characters (~12.5k tokens) of reasoning on a moderate prompt, and harness caps of 256/512/800 return content: null. GLM recommends max_tokens ≥ 32,768 with thinking on. Qwen suggests 2k to 4k for questions about images and warns that chat_template_kwargs.thinking_budget is not honored by this build. Thinking budgets enforced on the GPU (DeepSeek's hotfix #31, which forces a </think> at the exact limit) are in Generating text.

Tool calling: the model writes, the parser translates

“Calling a tool” sounds as if the model executes something. It executes nothing. Tool calling is a text protocol: the model was trained to write, when appropriate, a structured request in a format of its own. The server recognizes that text and converts it into a JSON object. The client is the one that runs the tool, and the result goes back to the model as a new message.

  1. Declare The client sends tools: name, description and parameters in JSON Schema.
  2. Render The template injects the tools into the prompt. On GLM it is a <|system|># Tools … You may call one or more functions… block followed by the signature of the call format.
  3. Generate The model writes the call markup in its own format (listing below).
  4. Translate The tool-call parser extracts the name and arguments and returns tool_calls: [{id, type:"function", function:{name, arguments:"<JSON string>"}}] with finish_reason:"tool_calls".
  5. Execute The client runs the function and replies with {"role":"tool","tool_call_id":…,"content":…}.
  6. Re-encode On the next turn, the template must re-render the old call and its result. On GLM, the result goes after <|observation|>, which is also one of the model's EOS tokens.
GLM (glm47)      <tool_call>get_weather<arg_key>city</arg_key><arg_value>Paris</arg_value></tool_call>
Qwen (qwen3_coder) <tool_call><function=get_weather><parameter=city>Paris</parameter></function></tool_call>
DeepSeek (DSML)  <｜DSML｜tool_calls>
                   <｜DSML｜invoke name="get_weather">
                     <｜DSML｜parameter name="city" string="true">Paris</｜DSML｜parameter>
                   </｜DSML｜invoke>
                 </｜DSML｜tool_calls>

(The GLM format comes from the recipe's template and the DSML one from a parser fixture. The Qwen format is the one used by the upstream qwen3_coder parser, with line breaks omitted.) In two of these formats the opening marker is a single vocabulary token, an added token: <tool_call> is id 154843 on GLM (registered as non-special, in the 154838–154855 range alongside <think> and <arg_key>) and 248058 on Qwen. This will matter in the next section: GLM's fix for tool_choice:"none" only works if the text <tool_call> keeps turning into exactly that id, and that is what gate C of the preflight checks. The recipes turn the mechanism on with two flags: --enable-auto-tool-choice lets the model decide on its own whether to call (tool_choice:"auto", which agents require), and --tool-call-parser picks the translator (glm47, qwen3_coder, deepseek_v4). With the wrong parser, calls arrive as text in content and the agent breaks without any error at all. In the Qwen recipe, the tool-calling regression passes with MTP on.

The streaming parser is a state machine

When streaming, the parser receives the text in pieces and has to decide, for each piece, whether it is conversation or the start of a call. It is a state machine: TEXT → OPENING → NAME → ARGUMENTS → CLOSING. The arguments come out as fragments of a JSON string, and since the stream is append-only, the parser has to be sure before changing state. In the figure, see the same request in the three formats, and then the pathological DSML case.

Opt-inDSPARK_ENABLE_DSML_RECOVERY=1 → hotfix-vllm-dsml-recovery.py

A port of vllm#52645 to the pinned build's API, over 6 parser files, each pinned by identity. The model sometimes emits a complete <invoke name="…"> without the tool_calls wrapper, or with the malformed variant toolcalls (vllm#51914). The call then leaks as text or as reasoning. The patch makes provisional transitions into the invoke state from CONTENT or REASONING, buffers events, validates the name against the request's tools (nothing is recovered with tool_choice="none") and only commits at the end of the invoke. Any other outcome returns the original raw text, so correct DSML stays byte-identical. Names longer than 256 characters or containing a line break abort. Status: 34 tests on CPU. The live gate compares tool-call acceptance parity against the 42.3% baseline (C1) and is still pending, which is why the default is 0.

The model imitates its own history (DeepSeek #21)

The parser takes care of the output, but the input matters just as much. OpenAI clients resend old calls in the history, and some send arguments as a JSON string, others as a dictionary. The encoder's encode_arguments_to_dsml always did json.loads(arguments). With a dict, the exception was handled by wrapping everything as {"arguments": <dict>}, and the model, seeing that odd format in its history, started to imitate it in the following calls. hotfix-encoding-dsv4-issue21.py (always on) uses the dict directly and only wraps strings that are not JSON. The lesson applies to any recipe: an encoding error in the history becomes a behavioral error that propagates, not an exception.

Same format, a different sending policy

In the TensorFold lane the markup is the same as glm47's (<tool_call>, <arg_key>, <arg_value>), and the server also follows it with a state machine. The difference is what it does with what it has already recognized: instead of emitting the arguments piece by piece, it holds the call until </tool_call> and sends it in a single delta, with empty deltas every 2 s while it waits. The arguments come out typed by the tool's JSON Schema (an array as a JSON array, null and const as such). On the way back, the parser does not convert values Python-style (such as True or 2.0), so that the resent history renders the same tokens the model wrote, the same lesson as #21 above. The section Update: the API boundary in TensorFold animates this choice and its cost.

Controlling the call: tool_choice, masks and temperature

The client can tell the server whether a tool should be called, and which one, through the tool_choice field:

"auto"
The model decides (requires --enable-auto-tool-choice). The call is extracted from the text, and the arguments can come out malformed, unless the tool has strict: true.
"none"
The client wants no call, even with tools declared. What the server actually guarantees is another story (just below).
"required"
It must call at least one.
named
{"type":"function","function":{"name":"x"}}: it must call exactly x.

Two fields refine the contract. parallel_tool_calls says whether several calls in the same turn are allowed. strict, in the function definition, requires the arguments to obey the schema. In vLLM, required and the named form are enforced with structured outputs (the next section): in general, guided JSON over the parameters schema; in the DeepSeek build, a DSML structural tag. none, on the other hand, does not constrain generation. It only keeps the parser from returning tool_calls, and with --exclude-tools-when-tool-choice-none it removes the tools from the prompt. That is the gap GLM's overlay #13 closes with bad_words, just below. In everything that constrains the output, the underlying tool is the same: acting on the logits before sampling.

Logit masking

At the last layer the model produces one logit \(z_i\) per vocabulary token, and the sampler turns them into probabilities. Masking means multiplying by a 0/1 vector before normalization, which is equivalent to putting \(-\infty\) on the forbidden logits:

\[ p_i \;=\; \frac{m_i\, e^{z_i/T}}{\sum_{j} m_j\, e^{z_j/T}} \]
  • \(z_i\): logit of token \(i\)
  • \(T\): temperature
  • \(m_i\): mask (1 = allowed, 0 = forbidden)
  • \(p_i\): final probability; with \(m_i=0\), \(p_i=0\) for any \(T\)

vLLM exposes the simplest form of this as bad_words: a list of strings that are tokenized and blocked. A single-token word is masked at every position. A multi-token word only has its last token blocked once the previous ones have come out, which is far less robust.

Overlay #13patch_tool_choice_none.py

Symptom: with tool_choice:"none" and tools declared, the model opened a <tool_call> anyway. The API layer already suppressed structured tool_calls under none, and the engine stripped the tool snippet from the content. The result was “complete call, no answer text”. Nothing prevented the generation of the opener. Fix: the Glm47MoeParser.adjust_request hook adds the parser's own TOOL_CALL_START to request.bad_words when tool_choice == "none" and there are tools. The sampler masks that token at every position, including the draft positions of speculative verification (a drafted opener is rejected, at the cost of one acceptance). The hook runs because --reasoning-parser glm45 is set. If that flag goes away, the fix becomes inert. Why not --exclude-tools-when-tool-choice-none? That upstream flag removes the tools block from the prompt and destroys the prefix cache's shared prefix (the doc mentions a difference on the order of 168 vs 17 prompt tokens), so it was rejected. Status: verified on CPU against the image's parser bytes, not yet validated live.

GLM's scripts/tool-choice-none-preflight.py checks three gates before any live test. B, sources: the sha256 of the 13 files in the bad_words chain. C, tokenizer: encode("<tool_call>") == [one id]. Gate C is the most instructive. If the opener ever stopped being a single token, the mask would silently have no effect.

tool_choice in the TensorFold lane: the opposite choice

TensorFold's documentation describes two decisions that contrast with overlay #13. The first: tool_choice:"none" removes the tools from the template, precisely the path the vLLM lane rejected so as not to break the shared prefix. The cost shows up here too (our interpretation): the tools live in GLM's system block, and the end of that block is one of the points where TensorFold keeps a state that can be reused across conversations. A none request renders a different system block and does not share that state with the requests that declare tools. In exchange, the guarantee is structural: with no tools in the prompt, the model has nothing to call. The second: required and the named form use no grammar. The server replaces the reply's first non-whitespace token with the <tool_call> opener plus the template's text before the name, and then holds the name within the offered tools: a token that leaves them is replaced by the rest of the first matching name. Each fix depends only on the previous tokens, so drafted, serial and concurrent decoding write the same call. The arguments are up to the model, and a malformed call comes back as text in content, not as an error. Sending a grammar along with required gets HTTP 400.

Temperature on syntax tokens

There is a subtler effect. vLLM samples every token with the request's temperature, both the syntax ones (tags, invoke headers, braces, quotes) and the payload ones (the argument values). In DSML, a single wrong structural token is enough for the parser not to recognize the call. The ds4 engine, used in another of Mia's recipes, forces \(T=0\) on syntax tokens and only samples the payload ones with the requested temperature. With the same model (and weights that are even better on vLLM: FP8, versus ~2-bit GGUF experts with Q8 attention on ds4), at \(T=1.0\) and with thinking on, vLLM scores lower on tool-eval-bench. The benchmark only reads message.tool_calls, so a malformed call counts as “no call” (missing_step). The recipe's document rules out quantized KV, MTP and the weights as causes. The weights argument is the strongest one: if they dominated, vLLM would win. It is a mechanical serving artifact, not a signal of model quality.

\[ \begin{aligned} P_{\text{call ok}}(T) &\approx \prod_{s=1}^{K} p_{\text{ok},s}(T) \\ p_{\text{ok}}(T) &= \frac{1}{1 + M\,e^{-\Delta/T}} \end{aligned} \]
  • \(K\): number of syntax tokens in a call
  • \(p_{\text{ok},s}\): chance of the right token at position \(s\)
  • \(\Delta\): logit margin of the right token over the alternatives (toy model)
  • \(M\): how many plausible alternatives there are

The mitigations on the vLLM side, from cheapest to most expensive, according to the recipe: (1) run the benchmark at \(T=0\), which makes the syntax temperature-proof, but also makes the payload greedy. As a diagnostic, this separates “corrupted syntax” from “a real capability gap”. (2) Structured outputs with XGrammar structural tags: the mask leaves the syntax positions with exactly one valid token, and the result is deterministic at any temperature. There is no ready-made DSML grammar in vLLM, and function calling through structural tags is still an open RFC (vllm#32142). (For named or required tool_choice, the DeepSeek build already applies a strict DSML structural tag, as the next section shows. What is missing is a grammar for auto, the mode the benchmark runs in: there, at \(T>0\), no grammar protects the syntax.) (3) A custom logits processor that tracks the DSML state and forces argmax in the syntax regions, in practice a port of ds4's logic.

Fail-closed contract: better a 500 than a wrong 200

Even with a grammar, the DeepSeek recipe measured that named or required tool_choice sometimes returned HTTP 200 with zero tool_calls, or with arguments outside the strict schema. The 145-case gate scored 142/145 twice at c=4, with different failing cases on each run. There are two causes, and it is worth separating them. The root in the engine: the structural tag's bitmask can “fail open” under spec decode + async scheduling (vLLM family #49694/#54437), and no API patch fixes that. The measured residual failure: the token budget (step 3 below), which the final no-thinking attempt solves. hotfix-vllm-issue191-toolcall-failclosed.py (opt-in) is a fail-closed contract layer that does not touch the root, but checks the result:

  1. Check after generating Enabled by DSPARK_ENABLE_ISSUE191_TOOLCALL_FAILCLOSED=1 (default 0). Only in non-streaming Chat, with named or required tool_choice: the cardinality (exactly one call if parallel_tool_calls=false), the name, whether the arguments are a JSON object and, with strict, validation against the schema (jsonschema 4.26.0).
  2. Regenerate In failclosed mode, each violation triggers a new generation with a fresh engine id (<id>-issue191r<n>), up to DSPARK_ISSUE191_TOOLCALL_RETRIES times (default 2, range 0–5).
  3. Last attempt without thinking With DSPARK_ISSUE191_TOOLCALL_THINKOFF_FALLBACK=1 (default), the last attempt swaps the prompt's final <think> for </think>, byte-identical to the render with thinking=false, and passes reasoning_ended=True. The call comes out constrained by the grammar from token 0. The measured cause of the residual failure was the budget: with thinking=true, reasoning_effort=low, some requests reasoned for 300–500 tokens and max_tokens=512 cut them off before or inside the DSML call.
  4. Fail loudly Once the attempts are exhausted, the client receives HTTP 500, an explicit error instead of a silently wrong answer. With DSPARK_ISSUE191_TOOLCALL_MODE=log, the patch only logs warnings, which is useful for measuring the violation rate before enabling it.

Its A/B companion is DSPARK_ASYNC_SCHEDULING=0, which removes --async-scheduling from both ranks. The bitmask rows then come from real drafts, at a cost of ~4% in single-stream. Streaming was left out of the patch's scope.

Structured outputs: the grammar holds the pen

Sometimes you do not want “text that looks like JSON”. You want a guarantee of valid JSON against a schema. Structured outputs (or guided decoding) achieve that by constraining sampling at every step. The client asks for it with response_format: {"type":"json_schema","json_schema":{…}}, or with vLLM's structured_outputs field, which accepts json, regex, choice, grammar or structural_tag. The default backend is XGrammar (there are also guidance, outlines and lm-format-enforcer). None of the three recipes passes --structured-outputs-config: they all use the defaults.

  1. Compile The schema becomes a context-free grammar, and the grammar becomes a pushdown automaton (JSON nests, so a plain FSM is not enough). XGrammar precomputes, for each state, which tokens can be decided without context, which makes each step cheap.
  2. Mask At every step, the matcher in its current state fills in a bitmask, 1 bit per vocabulary token: allowed or not.
  3. Sample The sampler applies the mask (the equation from the previous section) and samples among the allowed tokens.
  4. Advance The chosen token is accepted by the matcher, which changes state. At the end of the grammar, only EOS is allowed and the matcher “terminates”.

The memory cost of the bitmask is easy to compute, because XGrammar packs the bits into 32-bit integers:

\[ \text{bytes per row} = 4\,\Big\lceil \tfrac{V}{32} \Big\rceil \]
  • \(V\): vocabulary size
  • GLM: \(V=154{,}880\) → 4,840 words → 19,360 B
  • Qwen: \(V=248{,}320\) → 7,760 words → 31,040 B
  • DeepSeek: \(V=129{,}280\) → 4,040 words → 16,160 B

That is one row per sequence per step and, with speculative decoding, one row per draft position. It is very little memory. The delicate point is what each row is built on. With async scheduling, step N+1 is scheduled before step N's drafts exist, and the scheduler reserves their positions with placeholders (-1). The mask rows for those positions are built on the placeholders, not on real drafts, and that is how the mask can “fail open” (the vLLM family #49694/#54437 behind #191, previous section). Turning async off (DSPARK_ASYNC_SCHEDULING=0) makes the rows come from real drafts, at a ~4% cost in single-stream.

Reasoning and structural tags

With a reasoning parser active, the grammar only starts after </think> (unless enable_in_reasoning is set). The thinking is free and the answer is constrained, so the engine needs to know exactly at which token the reasoning ended. Keep that sentence in mind for the next section. A structural tag is a grammar that only activates inside a region marked by a trigger, which makes it perfect for tool calls. On DeepSeek, the tag for named or required tool_choice is a strict sequence, \n\n<｜DSML｜tool_calls>\n … </｜DSML｜tool_calls>, which XGrammar 0.2.3 enforces.

Why this matters for recipe authors

Structured output is the feature a production agent uses the most, and the one that shows up the least in tokens/s benchmarks. It touches four pieces at once: the reasoning parser (where it starts), the scheduler (when the mask is computed), the sampler (where it is applied) and speculation (several positions per step). In the recipes, the bugs live exactly at these junctions.

Grammar × speculation: when the batch overshoots

A preview of what Part VII covers in detail: in speculative decoding, a cheap drafter proposes k tokens, the big model verifies them all in a single forward pass and accepts a prefix of them, plus one “bonus” token. Each step delivers up to k+1 tokens at once. For the grammar, that changes everything. The matcher needs one mask row per draft position, advances tentatively through them (validate_tokens), rolls back the rejected ones and accepts the confirmed ones (accept_tokens). Two boundaries can land in the middle of a batch: the end of the grammar and the end of the reasoning.

There are three bugs, all from the same family (boundary × batch):

vLLM #52805
Termination. An accepted batch can contain the terminal token followed by speculative tokens. The terminated matcher received tokens (“The matcher has terminated … but is trying to accept new token”, or “Failed to advance FSM”). In the DeepSeek recipe, with DSpark + structural_tag + async + TP=2, the request could stall until the 1,800 s timeout of sample_tokens. Fix: accept_tokens stops at the terminal token, counts it, ignores the rest and treats later acceptances as no-ops. validate_tokens stops at termination and returns [] afterward. reset clears the flag.
vLLM #53046
Post-reasoning drafts. When the end of the reasoning lands in the middle of the speculative window, the drafts produced after it must be validated against the new grammar before they are accepted.
vLLM #44993
Advance. should_advance returned False for JSON/regex/choice when the reasoning ended in the middle of a step. With spec decode, the draft right after </think> never entered the FSM, and output with json_schema + thinking duplicated the prefix: {"city":"Paris{"city":"Paris"}. Fix: should_advance(request, new_token_ids=…) uses the tokens appended in the step as the exact window (placeholder-based counting goes wrong under async + spec with rejections) and records reasoning_end_token_index for every constraint type.

In the TensorFold lane: cut before verifying

TensorFold also uses XGrammar (with the same requests: response_format json_object/json_schema, guided_json, guided_regex, guided_choice, guided_grammar and structured_outputs), also only after </think>, and keeps drafting on. What changes is the order of operations. Before each verification forward, the engine cuts the draft chain at the first draft the grammar rejects, and only then masks the logits of each remaining row with the tokens the grammar allows after that row's path. Since sampling is keyed and verification is an equality test, a constrained reply comes out identical to its "draft": false version and to its solo run. The two Sparks compile the same grammar, and each masks its own vocabulary columns. Since no rejected draft ever reaches verification, this section's question “did the batch run past the end of the grammar?” never reaches the matcher (our interpretation). Three contract details: the grammar only allows the end token once the value is complete (a cut at max_tokens comes out incomplete, with length); a JSON grammar allows at most 32 blank characters between two tokens, so the model cannot fill the reply with whitespace; and a grammar that fails mid-decode ends only that reply, with HTTP 500 (an error event in the stream), while the others go on. In the recipe, structured mode measured 114.7 tok/s with 1 request and 227.9 aggregate with 4 (sparkDash, temperature 0, thinking off, GPU clocks capped at 2,200 MHz). The vLLM lane's README gives 83.0 tok/s with 1 request, measured with another tool on another date: an order of magnitude, not a controlled A/B.

How to test this in a new recipe

Test structured output with speculation on and with thinking on, using short schemas (the end comes quickly and often lands in the middle of a batch). Combine this with concurrency > 1 and async scheduling. Run tool_choice auto, required and named, with and without streaming. A boundary bug does not show up when you test one request at a time.

Responses API: when the server keeps the conversation

The Responses API (POST /v1/responses) is the successor to chat in the OpenAI family, and it is the one Codex and several agents use. Instead of messages, it works with typed items for input and output (message with input_text/output_text parts, function_call, function_call_output, reasoning) and named SSE events (response.created, response.output_text.delta, response.completed…). The conceptual difference lies in the state. It supports two continuation styles:

Stateless: history replay

store: false. The client resends all items, including previous outputs exactly as they came (type=message/id/status/output_text+annotations). It works like chat: the server keeps nothing, restarts do not break the conversation, and the prefix cache takes care of the cost.

Stateful: previous_response_id

store: true keeps the response on the server, and the next turn sends only the new item with previous_response_id. The client stays simple and traffic shrinks, but the state lives in process memory: a restart loses everything, and the continuation starts returning 404.

Stateful does not mean cheaper for the GPU. The server rebuilds the history and the model processes the whole prompt anyway, and what saves prefill is still the prefix cache. The store saves network bytes and client complexity, and pays for that with server memory and fragility across restarts.

Recreate, don't restart

These opt-ins are patches applied to the container's writable layer at boot. A docker restart reuses that layer: turning the flag off does not undo the bytes that were already patched. To change the mode or the cap, do stop + start (recreating the containers) on all ranks. The Recipe engineering chapter generalizes this rule.

Responses in the TensorFold lane: store on, with a double cap

TensorFold runs /v1/responses as the equivalent chat completion, through the same handler and the same engine path: the same tokens (the token_sha matches), the same drafts and the same equality with "draft": false. Its state choices almost mirror DeepSeek's. store is true by default: a finished response is kept in memory before its last event goes out, and the locker keeps the newest 1,024, up to 256 MiB. The cap counts entries and bytes, while DeepSeek's LRU counts entries only. GET and DELETE /v1/responses/{id} read and remove a stored response. previous_response_id rebuilds the messages a chat client would send, which is why prompt reuse resumes the prefix just as in chat. The fragility is the same: a restart forgets everything, and a previous_response_id that is not stored gets HTTP 400. The server also refuses with 400 what it does not run, such as the built-in tools (web search, file search, computer use), background and encrypted reasoning.

Update: the API boundary in TensorFold

Everything so far has been vLLM. The GLM recipe now has a second version , which serves the same EXL3 checkpoint on the same two Sparks with another engine: TensorFold v0.6.0 plus 53 patches. TensorFold is written per model family and has an unusual contract. With keyed sampling, the reply with drafts is identical, token for token, to serial decoding, and four requests served together give the same replies as each one alone (An exact engine). The full recipe is in The GLM recipe on TensorFold. Nine of the 53 patches touch exactly this chapter's boundary: vision and media (0003, 0050), tool calls (0036, 0051, 0053), /tokenize (0037), reasoning_effort: "max" (0023), context errors (0044) and metrics (0045).

The exactness contract changes how you fix a boundary. In vLLM, this chapter's fixes act where the bug shows up: one more mask, a stop that sleeps, a finish_reason corrected at the end. In TensorFold, every rule that touches the tokens must depend only on the previous tokens, so that drafted, serial and concurrent decoding write the same thing. The rest of the work goes to the server, which can hold, reorder and rebuild text at will, because that changes no token. Three agent problems show the pattern.

A whole tool call, or none

A coding agent that asks for write_file with a file of hundreds of lines makes the model spend minutes writing the arguments. The SSE stream can handle that in three ways, and the recipe went through all three. TensorFold v0.6.0 only delivered GLM's call at the end, through the end parser. Not a single byte went out while it was being written, and clients that drop idle connections (LiteLLM, Node's fetch) gave up. Patch 0036 started streaming the call as it is written: a header with the index, the id call_<24 hex> and the name as soon as the name is complete, then the arguments' JSON piece by piece. It is the same design as vLLM's streaming parser, and it inherits the same flaw. The stream is append-only, so a reply cut by max_tokens in the middle of the call has already delivered half-written arguments, which a client may store or even execute. DeepSeek's hotfix #55 fixes the finish_reason, but it cannot take back what was already sent.

Patch 0053 closes the loop with the whole call rule. The streamer keeps following the call while it is written, but only sends it when </tool_call> arrives, with header and arguments in a single delta. A call the reply ends inside is never sent, streamed or not, and the reply ends with finish_reason: "length". The end parser also strips an unclosed <tool_call> from content. To avoid repeating v0.6.0's silence, a keepalive comes in: while a call is held, an empty delta goes out every 2.0 s (CALL_KEEPALIVE_S). In the figure, compare the three strategies in the two scenarios. The top strip is what the model writes, the middle one is what crosses the wire and the bottom panel is what the client holds.

The price of atomicity is visibility. With fragments, a UI can show the file being written in real time; with the whole call, it only sees the result at the end. For agents, which execute the call rather than display it, the trade pays off: everything that reaches the client is a complete, parseable JSON. The rule also fits the engine's contract, because what goes on the wire depends only on tokens already generated.

Calls written inside the thinking

GLM sometimes writes the tool call inside the <think> block, without closing it. TensorFold's original split read any call in an unclosed block as the answer, and so it mistook a call that was merely mentioned in the reasoning for a real call. Patch 0036 adopts the “D5” rule, adapted from patch 0620 of jayleaton/glm53-tensorfold-spark: a call written in the thinking is a call only if it ends the reply, with nothing after it but whitespace and the block's close. Until it decides, the server holds that text out of the reasoning. If more text follows, it goes back to being reasoning; if the reply ends on it, it becomes tool_calls. A held call longer than 1,024 characters (THINK_CALL_HOLD) is taken as a call at once, so that writing a long file can be streamed, and from then on nothing turns it back into reasoning. It is an explicit compromise between waiting to classify correctly and not holding the client forever.

The history that comes back: returned reasoning and broken calls

The other two problems come from the history the agent resends every turn. The first is interleaved thinking. GLM-5.3's template renders the reasoning of every assistant step after the last user message: inside a tool loop, the model rereads what it thought at each step. Many agent clients (spark-bench and several frameworks) do not send that reasoning back, and the template renders <think></think> in its place. Patch 0036 points out two harms. The model starts seeing a context it never wrote, and the prompt stops matching the previous one at that step, so the prefix cache re-reads the rest. The fix is an LRU on the server, KeptReasoning, that keeps the reasoning of replies that made tool calls. The key is twofold: the ids of the calls the server itself generated and, for clients that renumber ids, a SHA-256 signature of the whole conversation before the calls (roles, text and calls without ids) plus the calls. Before rendering, the server puts the reasoning back into the steps that came without it. A step that already carries its own reasoning is never touched, and a "" counts as missing. The signature covers the whole conversation, not only the last user message as in the source patch, so that a piece of reasoning only goes back into the conversation it was written for. The LRU keeps up to 1,024 replies and 32 MiB of text (TF_GLM_KEEP_REASONING, where 0 turns it off, and TF_GLM_KEEP_REASONING_MB).

The second problem is a broken old call (issue #2). If a tool call in the history has arguments that are not a JSON object (a string cut or corrupted by the model, the client or a proxy), the server answered HTTP 400. Since the agent resends the history every turn, the 400 came back forever and the conversation was stuck. Patch 0051 leaves that call out of the prompt, together with its result (matched by id or, without ids, by position, when the number of results equals the number of calls), and records it in the log. The rest of the message stays: the other calls, the text and the reasoning. Patch 0036 already sanitized the milder case, turning "" or null arguments into {}.

Fail-closed on the output, fail-open in the history

Compare with DeepSeek's #191, which prefers an HTTP 500 to a wrong 200. The two choices look opposite, but they follow the same criterion: who pays for the error. On the output, a wrong 200 gets executed by the agent, and failing loudly protects the world outside. In the history, a refused error comes back every turn and kills the conversation, while leaving the broken call out (and logging it) only takes from the model a step it could no longer read anyway. The same criterion explains the whole call: a cut call does not go out, because the client would execute it.

After v1.3.2: markup read in the tokens, not in the text

Later patches go after a defect common to almost every server. GLM writes <think>, </think> and <tool_call> as single tokens (added tokens), but the server looked for the markup in the text. On the way in, HF tokenizers pulls the text of every added token out of a string, special or not, so a request that merely quoted </think> (an agent reading another model's raw output, a log, a template) became the token itself. Patch 0116 masks the request's text before the template renders and encodes it as text, around the template's own tokens. On the way out, patch 0117 does markup reading by id: it records each marker token the model generated and makes every other occurrence of the same text inert before the parsers run (the client gets the text back). A </think> quoted in the reasoning no longer ends it, and an example call written as text no longer becomes tool_calls. Measured with 10 sampled replies per case: replies that wrote a quoted </think> as the token, 7 → 0 (two Sparks, 0116); echoing <think>hello</think> world correctly, 0 → 5 (four Sparks, 0117). A call to a tool the request did not offer still stays text and never runs, as before; patch 0115 only starts logging it (tool call rejected: unknown_tool_name), without changing a token, so a gateway can tell why the reply stopped.

On the wire, patch 0111 extends the keepalive idea: a stream that has sent nothing for SSE_KEEPALIVE_S (15 s), waiting for a slot or filling a long prompt, writes an SSE comment, : keepalive, which clients skip. Behind a Cloudflare Tunnel, such streams used to be cut as idle at ~125 s. On any server, vLLM or SGLang on an H200 included, the two cheap tests are the same: a prompt that quotes the model's own markup and a stream that goes minutes without a token behind your proxy.

Errors an agent can read, and the same door with another contract

A long-context agent needs a specific signal to know when to compact the conversation. When the prompt plus max_tokens does not fit the window, TensorFold answers HTTP 400 in OpenAI's wording, with the code context_length_exceeded, and patch 0044 adds param with the field's name (messages or prompt). The rule also covers prompts with images that run past the window, and a lack of capacity becomes 503. Clients that compact the conversation on seeing that code start working with no extra configuration. On observability, patch 0045 copies the /health figures into /metrics (Prometheus) as tensorfold_health: metrics. There are counters (requests_total, completion_tokens_total, cached_tokens_total, rounds_total, prefill_seconds_total, decode_seconds_total) and gauges (pool_tokens, pool_free_tokens, kept_prompts, streams{state=decoding|filling|paused}). For whoever operates the server, these are the capacity signals: how much of the pool is free and how many streams are in each state (Benchmarking).

In the recipes: doors, keys and clients

An inference API on the network is a GPU-burning machine at the disposal of anyone who can reach it. The recipes handle this in three layers: who can talk (bind and key), which doors exist (routes) and where the secret shows up (logs, argv).

--api-key and the guarded prefix

--api-key (or the VLLM_API_KEY variable) turns on Bearer authentication: the client must send Authorization: Bearer <key>. vLLM's middleware only checks the routes under the guarded prefix: /v1, /v2 and /inference (GLM also mentions /cohere). Everything else answers without a key. In DeepSeek's pinned runtime, that includes POST /invocations and POST /generative_scoring, which run inference without authentication, plus /tokenize, /detokenize, /health, /metrics, /version and /ping. That is why the key alone is not enough: access to the port must be controlled at the network layer.

A naming correction

The DeepSeek recipe's patches/keys-concurrency.patch file has nothing to do with API keys. “Keys” is the nickname of the author (drowzeys) of a DSpark concurrency patch: a stable KV slot per request and ragged context. That topic is covered in DFlash2 and DSpark. Multi-key authentication is the DSPARK_API_KEYS described above.

The other end of the wire: configuring the client

The recipe does not end at the server: a poorly sized client wastes what the server offers, or breaks against it. The two recipes that publish configs for the “pi” agent show the decisions to be made.

GLM · examples/pi/*.json

  • api: openai-completions, baseUrl http://127.0.0.1:8888/v1
  • contextWindow 500000, maxTokens 8192
  • chatTemplateKwargs {"enable_thinking": false}; supportsReasoningEffort false, supportsStore false, maxTokensField max_tokens
  • httpIdleTimeoutMs 600000; compaction reserveTokens 65536, keepRecentTokens 24000
  • subagents: maxConcurrent 2, maxConcurrentForeground 1, defaultMaxTurns 20, maxSubagentDepth 1

DeepSeek · pi-models.dspark.example.json

  • thinkingLevelMap low/high/max; input: ["text","image"]
  • contextWindow 1048576, maxTokens 32768
  • chatTemplateKwargs: thinking ← thinking.enabled; reasoning_effort ← thinking.effort (omitWhenOff)
  • supportsThinkingTokenBudget: false. Declaring true with boot flag #31 at 0 makes every request fail (“thinking_token_budget is not yet supported by the V2 model runner”). pi maps minimal 1024 / low 2048 / medium 8192 / high 16384.

A sizing rule follows from this (our interpretation, consistent with the numbers): (1) contextWindow ≤ --max-model-len, with headroom for the output. GLM declares 500k and reserves 65,536 tokens for compaction. (2) maxTokens compatible with the thinking mode: 8,192 is enough with thinking off (GLM), and 32,768 is the reasonable minimum with thinking on (DeepSeek). (3) Concurrent subagents ≤ --max-num-seqs. GLM's maxConcurrent 2 fits within its MAX_NUM_SEQS of 4, leaving room for the main agent. (4) A long idle timeout (600 s), because a prefill of hundreds of thousands of tokens returns nothing for minutes. Finally, what is portable across servers (Spark cluster, local Mac, cloud): base_url, api_key, model, messages, tools, tool_choice, stream, max_tokens, temperature. What is not: each family's chat_template_kwargs, overlays' vllm_xargs, thinking_token_budget and the model names.

The same rule, other numbers

In the TensorFold lane the sizing rule yields other values: a window of 1,048,576 tokens per request (CONTEXT), at most 4 requests decoding together in v1.3.2 (PARALLEL=4; up to 8 since v1.5) and a default output of 32,768 tokens. The list of what is not portable also grows: the name of the reasoning field, the effect of medium, "draft": false and the penalties, which this lane accepts and ignores. And the context_length_exceeded error with param is what lets a client compact the conversation on its own when it outgrows the window.
