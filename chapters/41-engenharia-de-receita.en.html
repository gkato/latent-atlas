None of the three recipes runs vLLM “out of the box.” GLM reapplies 25 overlays on every boot on top of a fork (487ecf187); since 2026-09-30 there are 26, with patch_indexer_warmup_range.py (#203). DeepSeek runs a chain of ~21 hotfix steps before exec vllm serve. Qwen mounts about ten patched files on top of an image that is never rebuilt. And all of it twice, once per node, because a single rank running different bytes from the other is enough for NCCL to hang without an error message. This chapter covers the engineering that makes this sustainable: images identified by their content, patches that would rather refuse than be wrong, ordering and parity across ranks, a .env that doesn't betray you, launchers that check before they act, and canaries that distrust /health. The recipes that follow use this craft on every line. The new version of the GLM recipe, which swaps vLLM for TensorFold, practices the same craft with different answers: diffs baked into the image, an image named after the hash of its patches, and an engine that checks on its own whether both ranks got the same settings.

A recipe is software that patches software

You don't own the engine. The vLLM image was built by someone else, model support arrived on “day zero,” the kernels were written for datacenter GPUs and not for the GB10 (sm_121), and bugs show up under real load, with an issue number: #22, #27, #141, #249… That leaves three paths. You can wait for upstream (weeks). You can maintain a fork (and inherit the maintenance). Or you can patch the engine with engineering discipline. All three recipes chose the third, and the discipline boils down to four principles:

📌

Pin by content

Ideally, the image by digest, vLLM and ExLlamaV3 by commit, weights by revision. Moving names (tags, main) change without warning, and wherever the recipe still uses a tag, another lock has to cover the gap.

⛔

Fail closed

If the source isn't the expected one, the patch refuses and the boot aborts (fail-closed). A service that doesn't come up beats a service that comes up wrong.

🧪

Prove it first

CPU tests against copies of the original files, CI, verification at build time, a canary after boot. GPU time is expensive and scarce; CPU time is cheap.

⚖️

Same bytes on both ranks

Same image, same patches in the same order, same arguments. Tensor parallel is a single program running on two machines.

Analogy: the restaurant chain

Picture two branches that serve the same dish, each one cooking half of it. The recipe demands the exact brand and lot of every ingredient (digest), not “our usual supplier” (tag). An inspector sends back any box from a different lot instead of improvising (fail-closed). Both kitchens follow the steps in the same order (parity). And someone tastes the dish before opening the doors (canary), because “the stove is on” (/health 200) doesn't mean the food is good.

Images: layers, tags, digests and the same image on both nodes

Layers and content addressing

A Docker (OCI) image isn't a single file. It's an ordered stack of layers, each one a tar holding the filesystem differences produced by one Dockerfile instruction. On top sit a config (environment variables, entrypoint, labels and the rootfs.diff_ids list) and a manifest that lists the layer and config blobs. Every piece is identified by the SHA-256 of its own bytes: that's content addressing. At run time, the overlay2 driver stacks the read-only layers and puts a writable layer on top. We'll get to that one later, in “Where a change lives.”

\[ \text{DiffID}_i = H(\text{tar}_i), \qquad \text{ChainID}_1 = \text{DiffID}_1, \qquad \text{ChainID}_i = H\big(\text{ChainID}_{i-1} \,\|\, \text{“ ”} \,\|\, \text{DiffID}_i\big) \]
  • \(H\): SHA-256; \(\|\) is text concatenation
  • \(\text{tar}_i\): uncompressed contents of layer \(i\) (the RootFS.Layers list is exactly \(\text{DiffID}_1,\dots,\text{DiffID}_n\))
  • \(\text{ChainID}_i\): identity of the stack up to layer \(i\). Changing one byte in layer \(k\) changes every ChainID from \(k\) upward, and with them the config and the manifest

The practical consequence is powerful: the manifest digest is a fingerprint of the entire image. If two nodes run the same image by digest, they have the same bytes, guaranteed by math and not by anyone's goodwill.

A tag is a nickname, a digest is an identity

A tag (:0.1.1, :latest) is a mutable pointer in the registry, like a git branch. Anyone with permission can republish it pointing at a different image. The digest (@sha256:…) is like a commit hash: immutable. Across the three recipes, only two images are pinned by digest. One is the GLM base (ARG BASE=vllm/vllm-openai:glm53-flash-arm64-cu130@sha256:905c0293…, Dockerfile:88). The other is DeepSeek's lane A image, which .env.dspark.example pins as ghcr.io/anemll/dspark-vllm-gx10:0.1.1@sha256:a83948492cf1…. DeepSeek's hotfixes are source-exact against that build, so a different image under the same name would make every one of them refuse.

The other images use tags and rely on a different lock. GLM's serving image is the :exl3-instanttensor tag, protected by the recipe stamp (below): a pull is only adopted if its label matches the repository. Qwen uses the tags vllm/vllm-openai:qwen38-flash-next and …:v0.30.0 (lane 0.30). The README records the digest of the first one (sha256:d464f3b4…, ~20.6 GB), but .env.sample doesn't pin it. If that tag were republished, the patches' exact anchors would catch the change, or, worse, it would slip by unnoticed, because the .orig extracted from the image is cached (start.sh:568-575; see the warning in the section on where a change lives). DeepSeek's lane B also starts from a tag (unholy-fusion-prod-ready).

Multi-arch and the trip to the worker

An image name can point to a multi-arch index: a manifest of manifests, one per platform. The GB10 is linux/arm64 (Grace CPU). When the worker can't pull (no internet, or GHCR rate limiting), the recipes carry the image over SSH: docker save --platform linux/arm64 | ssh worker docker load. The --platform matters: without it, load of a multi-arch index breaks (the GLM launcher discovers the platform via inspect and falls back to linux/arm64).

Then comes a question that looks trivial: does the worker have the same image as the head? No obvious field answers it. .Id differs between the overlay2 and containerd stores (one uses the config digest, the other the index digest). And docker save | load loses the RepoDigests, so a shipped image never “matches” its source tag, and the old launcher resent the whole image on every start. GLM solved it with an image key, a short hash of RootFS.Layers (the DiffIDs). Those DiffIDs are identical on both sides along every path, because they describe the uncompressed content, not the registry.

The same question, with more fields

The TensorFold version of the GLM recipe fell into the same hole (issue #8): prepare.sh compared the images' .Id and failed on every run when one Spark used the containerd store and the other overlay2. The fix compares by content, like the image key, but the SHA-256 covers RootFS.Layers and the image's runtime configuration (Env, Entrypoint, Cmd, WorkingDir). Interpretation: two images with the same layers and a different ENV (the JIT cache paths live there) would run differently, and this identity tells them apart too.

Build cache: layer order is an engineering decision

The build cache reuses a layer as long as the instruction, the copied files and every layer below it are unchanged. Change something in layer \(k\) and everything from \(k\) upward is rebuilt. That's why GLM's Dockerfile compiles the ExLlamaV3 CUDA extension before copying overlay/exl3.py. The file's comment says the Python overlay comes after the compilation “so edits don't recompile exllamav3_ext.” And LABEL glm53.recipe.stamp sits on the last line, so a stamp-only rebuild stays cheap. LABEL doesn't even create a file layer: it's config metadata.

In the “naive” order, editing one line of exl3.py recompiles the entire CUDA extension; in the recipe's order, only the light layers on top. The recipe stamp

The GLM launcher computes a recipe stamp: the SHA-256 of the sorted list of hashes of everything the Dockerfile copies (Dockerfile, overlay/, files/, tests/, ablit/, excluding the transplant and the NFS server). It then compares that with the local image's label. A git pull that changes an overlay produces a mismatched stamp and an automatic rebuild (SKIP_BUILD=1 prevents it). An image pulled from GHCR is only adopted if its published stamp matches too. Otherwise, the launcher restores the local tag, so it never serves an image that lacks the artifacts the repository expects.

Build: compiling for the right machine and testing before it leaves the factory

Native extensions: two architectures at once

Part of the code the recipes run isn't Python: it's a native extension, a C++/CUDA .so library that Python imports. GLM's exllamav3_ext runs the EXL3-quantized MoE (see trellises and EXL3). Compiling an extension like that means targeting two architectures at once: the host CPU's (aarch64 on the GB10) for the C++ part, and the GPU's for the kernels. Get either one wrong and the build breaks or, worse, the first request does.

The honest stub: patch_exl3_ext_aarch64.py

ExLlamaV3 ships CPU targets with AVX2/AVX-512 intrinsics, vector instructions that only exist on x86. On a Grace (ARM), the compiler rejects those files. The recipe doesn't try to port them. It replaces them with stubs: is_avx2_supported() and is_avx512_supported() return false, enable_fast_fp*() becomes a no-op and the CPU all-reduce (perform_cpu_reduce*) calls std::abort(). The stub is honest: it says “not supported” where the library asks and, on the all-reduce paths, blows up loudly if anyone reaches code the recipe never uses (all-reduce here is NCCL's job, on the GPU). Not every stub aborts, though. bf16_add_inplace_avx512 becomes a silent no-op, and that's only safe because is_avx512_supported() returns false and keeps anyone from getting there. A silent stub depends on that gate. The Dockerfile warns that this patch “must stay in this layer,” the same one as the RUN that compiles.

Compiling for sm_121a

CUDA kernels become cubins, binaries for a specific compute capability. The GB10 is 12.1. With TORCH_CUDA_ARCH_LIST=12.1a, nvcc generates native sm_121a cubins when building the extension. FLASHINFER_CUDA_ARCH_LIST=12.1a and, in DeepSeek, CUTE_DSL_ARCH=sm_121a play the same role at a different moment: for the kernels that FlashInfer and CuTeDSL JIT-compile at runtime, with the engine already running. Without them, the JIT may pick a slower path. DeepSeek's compose notes that, without CUTE_DSL_ARCH, b12x/CuTeDSL could compile a slower W4A16 MoE in the middle of inference instead of the GB10's native kernels. The a suffix enables architecture-specific instructions that aren't portable: an sm_121a cubin only runs on 12.1. sm_120 cubins without the a run on 12.1 thanks to binary compatibility within the family (Qwen runs some of the image's kernels this way). sm_100 cubins, built for the datacenter, don't run on a 12.x. The Inside the GPU chapter explains capabilities and PTX in detail. Here the rule is enough: compile for the machine that will run it.

Dependencies that run over dependencies

An innocent pip install can swap a critical library out from under you. GLM installs instanttensor==0.2.0 with --no-deps because the normal install pulls nvidia-nccl-cu13==2.29.7 over the image's NCCL 2.30.7. It's the same care behind USE_HOST_NCCL (default 0): with 1, the recipe LD_PRELOADs an NCCL from the host. Two different NCCLs on the two ranks is asking for the collectives to diverge (NCCL and RDMA).

Knowing where the change lives also explains DeepSeek's lanes. In lane A (Anemll, the default), the hotfixes edit the vLLM installed inside the container, at boot. In lane B (Stage-C), whole files ship in the image. In lane C (official-main), the official main gets a Python patch with a sanity test. The VLLM_DSPARK_* and VLLM_DSV4_* variables are only registered in lane B's envs.py. In lane A, they trigger the Unknown vLLM environment variable warning and do nothing. Restarting is not recreating

A container is a read-only image with a writable layer on top, plus a configuration fixed at creation: environment variables, mounts and command. docker restart (or docker compose restart) restarts the same container, with the same writable layer and the same environment it was created with. A hotfix applied on the previous boot is still there, byte for byte, and a gate changed in .env never even reaches the container. Only recreating (./stop + ./start: remove and create again) starts from a clean writable layer, with the image's stock bytes and the new environment. That's why DeepSeek's CHANGELOG repeats, fix after fix: “Recreate both containers after pull (./stop then ./start); restart keeps the old overlay bytes.”

With “boot hotfix”: bring it up, turn the gate off and run docker restart. The file stays patched. Recreate it and it goes back to stock. Swap the base image and the patcher aborts on the unknown SHA-256, as it should.

The flip side: what has to survive recreation

Recreating throws away the entire writable layer, JIT caches included. DeepSeek moves TRITON_CACHE_DIR, TILELANG_CACHE_DIR and B12X_CUTE_COMPILE_CACHE_DIR to the HF cache volume. The documented reason: the cache inside the image “dies on recreation,” known shapes get compiled again mid-service, and a compiling rank can hold the pair past NCCL's 600 s watchdog (CUDA graphs and warmup). The rule: patched code lives in the writable layer and is redone on every creation; state that is expensive to rebuild goes to a volume.

The patch contract: source-exact, fail-closed, idempotent and atomic

A patcher is a program that edits another, already installed program. To be safe, it has to keep four promises at once. Source-exact: it only touches bytes it knows exactly. Fail-closed: faced with the unknown, it refuses. Idempotent: running it twice has the same effect as running it once. Atomic: whoever reads the file sees either the whole old version or the whole new one, never half. DeepSeek's hotfix-vllm-rope-swa-fix.py (a port of upstream vllm#54815) keeps all four in textbook fashion.

Before the mechanism, here's what it fixes in the model. DeepSeek V4 mixes layers with a KV compressor (CSA/HCA) and sparse-attention layers with a sliding window (SWA, 128 tokens in the served checkpoint). RoPE encodes position by rotating pairs of dimensions, and YaRN stretches those rotations for long contexts. According to the reference implementation, that stretching belongs only to the compressor layers, which see the long context through the compressed KV. The pinned build promoted the RoPE type to deepseek_yarn in every layer, so the SWA layers (0, 1 and the three in the DSpark drafter) got factor-16 YaRN over a 128-token window. The patch only promotes YaRN when compress_ratio > 1 and gives the other layers factor=1.0, the identity scale: plain RoPE in the same kernel. The compressor layers keep, byte for byte, the parameters they had before. In the recipe, this hotfix is opt-in: a compose gate runs it before vllm serve. The change is small, but it alters the geometry of the positions attention sees, and so it deserves the full contract:

  1. Version. Requires vllm == 0.25.2.dev0+g752a3a504.d20260714. Any other version is already a refusal.
  2. Type. The target must be a regular file (lstat), never a symlink.
  3. Identity. Reads the bytes and computes SHA-256 and size. Accepts two states: stock 0074271a… (1,242 B) or patched 6452ce2e… (2,111 B). If it's already patched, it exits 0 with already-patched: that's idempotency.
  4. In-memory transformation. The old region must appear exactly once and the # [dspark-rope-swa] marker must not exist. It swaps the region and runs compile() on the post-image.
  5. Pinned post-image. The result must have the expected patched SHA-256 and size. The patch proves what it's about to write before it writes.
  6. Atomic publication. Temporary file in the same directory, write, flush, fsync, chmod matching the original and os.replace(tmp, target). On an exception, it deletes the temporary file.
  7. Re-verification. Re-reads the target, which must be in the patched state. Any failure prints FAIL-CLOSED: … and exits 1. --check and --status only inspect, without writing.
\[ P(x) = \begin{cases} p & \text{if } H(x) = h_s \\ p & \text{if } H(x) = h_p \\ \bot & \text{otherwise} \end{cases} \qquad\Rightarrow\qquad P(P(s)) = P(s) = p \]
  • \(x\): current bytes of the target file; \(s\) and \(p\): the known stock and patched versions
  • \(h_s = H(s)\), \(h_p = H(p)\): the two SHA-256 pins in the patcher
  • \(\bot\): refusal (exit 1). The patch is a partial function: outside \(\{s, p\}\) there is no answer, and “no answer” becomes “doesn't come up”
  • The chance that a different file happens to have a pin's SHA-256 is on the order of \(2^{-256}\): zero, in practice

Why so much care with the write? Because open(target, "w") truncates the file before writing. If the process dies midway (OOM, power loss, docker kill), you're left with half a .py, and vLLM no longer imports. os.replace, on the other hand, is a POSIX rename: atomic, as long as source and destination are on the same filesystem. Hence the temporary file in the same directory. The fsync before the rename guarantees the bytes reached the disk before the name starts pointing at them (atomic publication). Three lessons come out of the figure. Running twice is harmless. A file from another version is refused before any write. And power loss is the ultimate test: with the atomic write, the file stays stock and the next boot applies the patch normally; with the naive one, you're left with a corrupted file that the patcher refuses (thankfully), but that also keeps vLLM from importing.

Whole-file hash or anchor?

There are two ways to make sure you're editing the right file, and the recipes use both:

Whole-file SHA-256 pin

  • Strict: any different byte anywhere becomes a refusal.
  • Requires re-porting and re-pinning for every new image. Pairs naturally with an image pinned by digest.
  • DeepSeek lane A: every modern patcher, with fixtures from source 752a3a504.
  • Also in GLM, for critical-geometry patches: TP=4's opt-in patch_sparse_mla_slice.py pins both pre-image and result by SHA-256.

Exact anchor (1 occurrence)

  • Tolerates changes in other parts of the file.
  • Risk: the semantics may have changed outside the anchor. Mitigation: ast.parse/compile, tests with fixtures, idempotency markers.
  • Qwen and most GLM patches: each anchor exactly 1×; if it doesn't match, abort without writing anything.

Upstream diff hunks

  • Embeds the PR's diff and applies it hunk by hunk.
  • Detects “already applied” and writes atomically.
  • Qwen's patch_qsa_fp8_kv_v030.py (backport of vllm#55557): parse_diff / find / apply + os.replace.

Unified diff applied by patch

  • The anchor is the hunk's context plus the lines it removes.
  • Tolerant: accepts a hunk a few lines off and, by default, ignores up to 2 mismatched context lines at each end (fuzz).
  • --forward refuses a hunk that looks already applied; || exit 1 turns any refusal into a failed build.
  • TensorFold: 53 diffs at build time, always on top of the version pip just installed.

When the fix touches several files, atomicity has to become a transaction. DeepSeek's .sh backports validate every target and anchor before writing any of them, and on failure perform a byte-exact rollback of everything already published (scripts/test-hotfix-atomic-transaction.py tests this). Qwen's patch_block_drop.py follows the same logic: “Patch all files before writing any, so a failed anchor leaves no partial set.” GLM adds a guard on the launcher side. Every mounted overlay must contain its identity string, end on the expected last line and pass Python's parser, which catches a truncated or swapped copy before boot.

Order and parity: composing patches on both ranks

With a single patch, the contract is enough. With 25, algebra enters the picture: the file vLLM executes is the composition of all the patches, in the order they run.

\[ F = P_n \circ \cdots \circ P_2 \circ P_1(\text{stock}), \qquad P_a \circ P_b = P_b \circ P_a \ \ \text{if}\ \ R_a \cap \big(R_b \cup A_b\big) = \varnothing \ \ \text{and}\ \ R_b \cap \big(R_a \cup A_a\big) = \varnothing \]
  • \(P_i\): the i-th patch (a partial function, as in the previous section)
  • \(R_i\): the byte region that \(P_i\) rewrites; \(A_i\): the stretch that \(P_i\)'s anchor needs to find intact
  • The condition is sufficient: if neither one rewrites what the other reads (the anchor) or writes (the region), they commute and order doesn't matter. Two anchors that only overlap for reading (\(A_a \cap A_b \neq \varnothing\)) don't get in each other's way, because each patch finds the stretch intact in the other's post-image
  • If one rewrites the other's region or anchor, the order becomes part of the recipe

That's exactly what the comments in GLM's start.sh, next to GLM53_OVERLAY_ORDER, record. patch_hybrid_prefix_hit.py comes before patch_apc_per_group_retention.py “because they share the coordinator helper's insertion point.” patch_apc_no_store.py comes after the retention patch, but it only edits sampling_params.py, request.py and block_pool.py, with no anchors in common with the coordinator overlays. patch_kv_capacity_log.py follows patch_glm5_drafter_group.py, the other one that edits kv_cache_utils.py. On TP=3, the comment in start-tp3.sh's internal script notes that patch_exl3_ep_shard.py must come after patch_dense_fp8.py, which reinstalls the whole exl3.py and would erase the earlier edit. In DeepSeek, the order is simply the compose's command: chain. scripts/test-python-hotfix-failclosed.py checks the order and the || exit 1 of each Python patcher, and the #136 backport was proven in both orders against #44993: the regions are disjoint, and each one's anchor stays intact in the other's post-image.

Idempotency and a fixed order together enable a GLM trick: apply the overlays at build time (the image comes out coherent and the tests run on patched code) and again at start, from the files mounted at /opt/glm53/*.py:ro. That way, fixing a patch doesn't require a rebuild. On reapplication, each patch recognizes its own marker and becomes a no-op.

Parity: one program, two machines

Tensor parallel is SPMD: the same program runs on each rank, and each collective (all-reduce, all-gather) only completes when every rank reaches it (parallelism). If one rank runs different code, it may launch a different sequence of collectives, and the other one waits forever, or until the watchdog kills the process. The recipes have measured this: ranks with different FP8, adaptive-k or capture sizes hang NCCL after PIECEWISE capture (CUDA graphs recorded per segment, with attention running outside them; see CUDA graphs and warmup), and divergent autotune caches have already hung Qwen's TP2. Hence parity as a rule. GLM generates the overlay block from a function (emit_overlay_block), “same bytes for both ranks,” and passes exactly the same GLM53_*/EXL3_* knobs to each container. DeepSeek uses env -u to clear the knobs that vary per rank (MASTER_ADDR/MASTER_PORT, NODE_RANK, HEADLESS). On the worker's compose line, it injects only what needs to differ (NODE_RANK=1, HEADLESS=1, VLLM_HOST_IP) and repeats the other, already resolved values (GPU_MEMORY_UTILIZATION, DSPARK_MODEL, DSPARK_REVISION, the HF cache…), taken from the same normalized .env snapshot. Qwen builds the vllm serve arguments once (VLLM_ARGS) and shares them between the head and worker scripts.

Three outcomes to remember. The recipe's order and the order with C moved give the same hash, because C commutes: it doesn't even open A and B's file. Swapping A and B makes one anchor disappear, and the boot aborts on both ranks: safe. The TP=3 case is the treacherous one. The reinstall erases the edit with no error at patch time, and the symptom only shows up when the weights load (dim 0 size 2048 is not divisible by tp=3). And a worker with one patch missing produces different hashes on the two ranks: the group comes up, but can hang on the first collective that diverges.

In TensorFold, the engine itself checks parity

The vLLM recipes guarantee parity from the outside: the launcher generates the same bytes and the same knobs for both ranks, and any divergence that slips through becomes a hang on the first collective. TensorFold's GLM engine adds a check from the inside. At startup, each rank packs into a list of integers the settings that change the sequence of calls (drafter, capacity, rows per chunk, prompt grid, copy drafts, the hyper-connection split, concurrency, window widths…), the two all-gather these lists and, if they differ, the engine refuses to start with the two ranks were started with different settings, printing both. The silent hang becomes an error with an address. The update section shows the check at work, and also that the order of the 53 patches matters for the same reason as in this section: several rewrite the same line.

.env, precedence and shell pitfalls

A recipe's configuration comes from several sources: defaults in the script, the .env file, variables exported by the caller, wrappers (start-fp8.sh), command-line flags. Precedence is the rule that picks among them when they disagree:

\[ v = s_{k^*}, \qquad k^* = \min\{\,k : s_k \text{ is defined}\,\} \]
  • \(s_1, s_2, \dots\): the sources, from strongest to weakest
  • \(k^*\): the first source that defines the key; it wins and every source below it is ignored
  • “Defined” has a nuance: X= (empty) is defined. GLM treats an empty export as an override, and DeepSeek unsets empty NCCL variables, because an NCCL_IB_GID_INDEX="" becomes index 0 and masks /etc/nccl.conf

The formula is the same in all three recipes, but the order of the sources isn't:

GLM: the caller wins

  • The launcher snapshots every exported variable (empty ones included) before source .env and re-exports them afterwards.
  • Identity variables (HF_HOME MODEL MODEL_REVISION IMAGE PORT TP NNODES) print a warning when overridden.
  • ABLIT is reset after .env: only ABLIT=1 ./start.sh turns it on.

Qwen: the .env wins

  • source .env after reading the environment: KV_CACHE_DTYPE=auto ./start.sh is ignored if .env defines the key (a gotcha that cost an entire launch cycle).
  • Exceptions: ABLIT and HF_TOKEN (_CLI_ABLIT, _CLI_HF_TOKEN).
  • OVERRIDE_* are read after .env. That's how start-fp8.sh and start-v030.sh reuse the same start.sh.

DeepSeek: normalized .env + CLI

  • --host/--port on the command line beat .env.dspark.
  • The .env beats the environment, except for the ablation knobs, which are preserved.
  • A DSPARK_API_KEYS in the environment that differs from .env isn't resolved by precedence: it's an error (exit 2).

Look at Qwen with “you export”: the value you typed only counts if .env does not have the key. And at GLM with ABLIT: .env never wins, by an explicit safety decision. Every recipe needs to choose a rule, document it and make the launcher print the effective value (Qwen tells you to check the KV dtype: line in the launch summary).

The .env is shell code

In all three recipes, .env is read with source: bash executes it line by line. In GLM and DeepSeek, the source sits between set -a and set +a, which exports everything to child processes. In Qwen, without set -a, the variables stay only in the launcher's shell, which uses them to build the container command. That brings pitfalls a configuration parser wouldn't have:

  • Quotes vanish. SPEC={"method":"dspark"} becomes {method:dspark}, and the JSON dies.
  • CRLF. A file saved on Windows ends its lines in \r\n. Bash keeps the \r inside the value ($'fp8\r'), invisible in the log.
  • BOM. Some editors write EF BB BF at the start. The first line stops being an assignment and becomes a nonexistent command, and the variable ends up empty.
  • Octal and overflow. In $(( )), 08 is an error (“value too great for base”) and 010 equals 8. A giant number wraps around 64 bits: 18446744073709551622 becomes 6 and passes any range check.

DeepSeek defends itself in layers. First, it normalizes a private copy (0600) of .env with sed (stripping BOM and CRLF) and sources that copy; the operator's file stays byte-identical. Then dspark_validate_numeric_knobs rejects non-integers and values longer than 10 digits before any arithmetic, by length alone, without evaluating the number. It's a conservative limit (the real maximums have at most 7 digits) that never lets a giant number reach the 64-bit math. Next, it normalizes with 10# (always decimal) and checks the ranges (MAX_NUM_SEQS 1–4096, MTP_NUM_TOKENS 0–64, MAX_NUM_BATCHED_TOKENS 1–8,388,608). Finally, it rewrites the snapshot so the worker, which receives the file via docker compose --env-file, sees the same decimal as the head. The numbers matter because they're forwarded to the container's own arithmetic: --max-cudagraph-capture-size $(( (6·(6+1)+7)/8·8 )) = 48. GLM validates the numeric knobs before stopping the healthy pair (MAX_MODEL_LEN ≤ 10⁶, MAX_NUM_SEQS ≤ 4096, MAX_NUM_BATCHED_TOKENS ≤ 8,388,608): a typo doesn't take down the service that was working fine.

A .env that is read, never run

The TensorFold version of the GLM recipe cuts the problem at the root: its config.sh doesn't source the .env. It reads the file line by line and only accepts the KEY=value form (with an optional export in front), checked by a regular expression. A value in single or double quotes loses the quotes and the comment after them; an unquoted value loses whatever follows the # and its trailing whitespace. Precedence is environment > scripts/local.sh (this one is sourced, because it's the operator's own code) > .env > defaults, and the .env never overrides a key that is already set. We checked the parser in a bash: the \r of a CRLF file goes away with the trailing whitespace; {"method":"dspark"} arrives with its quotes; $(touch PWNED) becomes text, and nothing runs. The BOM is still treacherous in another way: the first line no longer matches the pattern and is silently ignored, so the key stays at its default. Numbers still go through regular expressions in start.sh (PARALLEL from 1 to 4, COPY_MAX from 1 to 15) and then through the engine's own parser.

Build the JSON inside the container

The lesson of the “JSON in .env” case becomes a design pattern: in .env, only simple atoms (words and validated numbers). Complex structures are assembled where the syntax is under control. DeepSeek's compose also has two interpolation phases: ${VLLM_PORT:-8888} is resolved by Compose on the host, while a reference written with a doubled dollar sign (two $ in a row before HEADLESS) reaches the container as $HEADLESS and is only evaluated by the container's shell, at runtime. The file itself warns against deferring VLLM_HOST this way: that variable only exists for Compose and isn't in the container's environment.

Entrypointassembling --speculative-config (docker-compose.dspark.yml:475-479)

.env holds only MTP_NUM_TOKENS=6 and DRAFT_SAMPLE_METHOD=probabilistic. Inside the container, a case accepts only probabilistic|greedy (any other value: a message and exit 2), and only then is the JSON assembled with escaped quotes:

case "${DRAFT_SAMPLE_METHOD:-probabilistic}" in
  probabilistic|greedy) DRAFT_SAMPLE_METHOD="${DRAFT_SAMPLE_METHOD:-probabilistic}" ;;
  *) echo "DRAFT_SAMPLE_METHOD must be one of: probabilistic, greedy" >&2; exit 2 ;;
esac;

Why: the raw .env value would lose its quotes on source and could inject arbitrary JSON (a value containing " and , would add keys). With the allowlist, the string can only take known shapes. The same pattern shows up in DEFAULT_THINKING (off|low|high|max → DEFAULT_CHAT_TEMPLATE_KWARGS) and in LIMIT_MM_PER_PROMPT: the friendly form image=8 is validated as an integer and converted to {"image":8}, because the Anemll image's argparse runs json.loads and rejected a raw image=8. The DSpark details are in DFlash2 and DSpark.

Secrets and exposed surface

A launcher handles API keys, HF tokens and network addresses, and every channel a value passes through is a place where it can leak. The recipes close those channels one by one. GLM passes -e VLLM_API_KEY without a value on the docker run line: the key doesn't show up in argv and doesn't travel to the worker. DeepSeek applies hotfix-vllm-redact-api-key-log.sh, which replaces the key with <redacted:N value(s)> in the log's non-default args line. It also warns if the API binds to 0.0.0.0 without a key or if the .env holding secrets is readable by group or others, and it copies the env to the worker as a 0600 temporary file + mv -f (atomic). Qwen writes the rendered command to .last_head_launch.sh with mode 0600 (it may contain --api-key) and sends the worker script over stdin (ssh "bash -s" < script): no file sits at a fixed path waiting to leak. And remember that GLM and Qwen serve on --host 0.0.0.0 by default, open to the network. Even with a key, /health, /metrics and /tokenize stay unguarded (API and tools).

The launcher and supervision: from start.sh to the canary

A launcher like start.sh is a small distributed program: it coordinates two machines over SSH, and each step can fail in its own way. The three recipes converge on the same backbone: a gate at each step up to READY and, after that, a known way to observe the pair:

  1. Lock and configuration. GLM serializes start, restart and stop with flock on logs/cluster.lock. Next comes the normalized .env with its validated numbers. Invalid configuration: exit 2, before touching any container.
  2. Preflight. HEAD_IP must be assigned locally, and SSH runs in BatchMode with ConnectTimeout=10. The RoCEv2 GIDs are checked per HCA (a wrong GID kills the rank with errno 61 in ~60 s). Memory must pass MemAvailable ≥ util × total + 2 GiB. Qwen also requires idle GPUs (REQUIRE_IDLE_GPU), and GLM drops the page cache (drop_caches) on both nodes (unified memory).
  3. Image on both nodes. pull or save | ssh load, with the image key compared between head and worker.
  4. Weights. Download on the head, verification of shards and sizes, and copy to the worker via rsync or NFS (nconnect=8 over the CX7; mounting over the management network is refused). Details in checkpoints.
  5. Sync artifacts. Compose, .env (0600, atomic), patchers and proposer go to the worker. In DeepSeek, the --check preflight of each sensitive patcher runs on the worker and then on the head, via docker compose run --rm --no-deps --entrypoint python3 … --check, before any rank comes up.
  6. Worker first, head second. The worker (rank 1, headless) comes up and waits for the rendezvous, the initial meeting where the ranks exchange addresses. The head (rank 0) comes up with the TCPStore (the key-value store that hosts that meeting), the scheduler and the API. By the time the API appears, the whole group already exists (NCCL and RDMA).
  7. Wait with a deadline. The launcher polls /health or /v1/models (DeepSeek: WAIT_ATTEMPTS=100 × WAIT_SECONDS=15 ≈ 25 min). GLM does fail-fast: if the worker container dies (3 consecutive checks, ~30 s), it aborts the wait instead of sitting out the whole timeout.
  8. Warm up and prove. Warmup of the shapes the traffic will use, then the canary. Only then does the READY banner appear.
  9. Observe. After READY, the operator needs to know where to look. GLM writes everything to logs/ ($LOGDIR): build-sm121.log from the build, overlay-verify.log from the GPU self-check and, when the canary or the wait fails, head.log and worker.log (the latter pulled over SSH) before exiting. With TAIL=1, the launcher follows the head log after the banner (Ctrl-C only detaches; the server keeps running). DeepSeek splits observation into dedicated scripts. status-deepseek-v4-flash-dspark.sh counts the failing probes and returns that in its exit code, so a supervisor can rely on it. logs-deepseek-v4-flash-dspark.sh gathers the logs from the head and from each worker (over SSH, 160 lines by default, TAIL). Qwen follows docker logs -f vllm-fn while waiting for /health, prints a summary with the KV dtype: line (the effective value) and saves the rendered command in .last_head_launch.sh (on TP1, .last_launch.sh).

Qwen makes the stages selectable (DO_DOWNLOAD, DO_SYNC, DO_LAUNCH; --no-download, --launch, --nfs). DeepSeek's validate-dspark-config.sh prints the rendered line without bringing anything up. On stop, GLM kills both containers directly and in parallel (kill-first, ~15 s faster; there's no state to flush). DeepSeek uses a 10 s stop_grace_period. Boot measurements: GLM's ./start.sh restart dropped from 259 to 122 s (/health at 99 s, 2026-09-19), and Qwen's cold start takes ≈ 10 min 55 s.

Supervision: who restarts what

The restart policy splits the recipes. DeepSeek uses unless-stopped (issues #38/#39: bring back a worker that crashed, and restore the ranks after a reboot). Qwen leaves out --restart on purpose: a rank restarted on its own can hang in NCCL init (interpretation: the partner stays stuck in the old group and doesn't do a new rendezvous). DeepSeek's own CHANGELOG admits the risk: independent Docker restarts can split the TP=2 pair, and the way out is DSPARK_RESTART_POLICY=no with ./stop/./start together.

Supervision also requires an exit code contract. In DeepSeek: 0 ok, 1 failure, 2 invalid configuration, 3 already running. After a reboot, dockerd restores the ranks and a ./start triggered by systemd finds everything up. Exiting 1 would cause a retry storm; exiting 3 with SuccessExitStatus=3 in the unit solves it. A remote probe distinguishes “the rank exists” (sentinel 42) from “SSH failed” (255). The documentation (docs/ENVS.md) cautions that exit 3 does not prove the group is healthy, because a head-only reboot can leave a stale worker behind. In GLM, the same number 3 means something else: DEGENERATE ENGINE, coming from the canary. Exit codes are local contracts, so document yours.

Launcher./start.sh in 5 steps · FOREGROUND=1

The TensorFold version's start.sh follows the same backbone (setup, checks, worker → head launch, loading, smoke test) and brings four ideas worth copying. 1. Validate with the engine's own parser. Before stopping anything, the arguments go through build_parser().parse_args(...) from tensorfold.cli, in a throwaway container without a GPU. A typo fails there, with the old server still up, and the launcher doesn't need to keep a second copy of the engine's rules. 2. A setup marker. One line with model@revision, drafter@revision, the image ids on both Sparks, the patches hash, the worker and the weights mode; prepare.sh runs again whenever the current line differs from the stored one. 3. A measured second chance. If rank 0 exits naming the largest window that fits in that start's memory, the launcher starts once more with --context set to it, and says so. 4. The pair as the unit. There is no Docker restart policy. With FOREGROUND=1, the script stays attached to rank 0's log and exits with its code, for a systemd unit with Restart=on-failure, and a watcher stops rank 0 if rank 1 ends, because a lone rank would wait for its peer forever. In that mode there is no window retry and no smoke test. In normal mode, the smoke test is the same “Reply with OK.” as GLM's (temperature 0, no reasoning, 32 tokens), but it only requires text in the reply: the exactness of the drafts is proved by other tests (GLM recipe on TensorFold).

The canary: distrust /health

/health 200 proves the HTTP process responds, not that the model gets things right. GLM's canary (GLM53_WARMUP_CANARY=1) runs after warmup: a temperature-0 request with reasoning off (“Reply with OK.”) must come back OK, and DFlash must accept at least 1 out of at least 64 drafted tokens. If it fails, the script exits 3 with DEGENERATE ENGINE, the launcher collects logs, tries to take the engine off the port and finishes without READY. Before, the #249 signature (garbage with ~0 acceptance) only showed up as a slow warmup and went into service. spec-accept-gate.sh hunts a different signature: the vllm#53030 bug (a BatchDescriptor collision in PIECEWISE graphs) pins position-0 acceptance at ~1.00, and the gate requires pos0 < 0.999 with ≥ 100 drafts. Update: baked diffs and an image named by hash, in TensorFold

Everything so far patches vLLM. The GLM recipe now has a second version , which serves the same EXL3 checkpoint on the same two Sparks with a different engine: TensorFold v0.6.0 plus 53 patches. TensorFold is written per model family and arrives as a Python package, installed with pip from a git tag, with its own kernels that compile by JIT on the first start. The engine's design is in the exact engine chapter, and the whole recipe, step by step, in the GLM recipe on TensorFold. What matters here is recipe engineering. The problem is the same as in this chapter: you don't own the engine, you need the same bytes on both nodes, and you'd rather not come up than come up wrong. The answers change in three places: where the change lives, how the image is identified and who checks parity.

Unified diffs against site-packages, baked at build time

The 53 patches are unified diffs, the format diff -u and git diff produce, written against the TensorFold v0.6.0 files installed in the container's site-packages. Nothing is applied at boot. prepare.sh builds the image with a Dockerfile embedded in the script itself, in five steps:

  1. Base. FROM nvcr.io/nvidia/pytorch:26.07-py3, NVIDIA's PyTorch container, with CUDA, PyTorch, Triton and the extension compiler.
  2. Engine. pip install git+https://github.com/ashhart/TensorFold.git@v0.6.0, plus the extras av==18.1.0 (video) and xgrammar>=0.2.8,<0.3 (structured outputs), and a tensorfold --version.
  3. Patches. A COPY of the patches/ folder and, in the directory that holds the tensorfold package, a loop that applies each *.patch in name order: patch -p0 --forward < "$p" || exit 1.
  4. Proof. A python -c "import …" of the patched modules (the CUDA server, the GLM family's engine, vision) and of the extras. A module that no longer imports brings the build down.
  5. Stamp. LABEL tf.patches=<hash> and an ENV that points the JIT caches (TORCH_EXTENSIONS_DIR, TRITON_CACHE_DIR) to /cache, mounted from outside by the launcher.

A unified diff is an anchor patch with a different accent. Each hunk carries the lines it removes (-), the ones it adds (+) and a few lines of context around them, and patch looks in the file for the context plus the removed lines. There are two differences from the vLLM recipe's exact anchors. The first is tolerance: GNU patch accepts a hunk a few lines above or below where it's expected and, by default, ignores up to 2 mismatched context lines at each end of the hunk (fuzz); the removed lines, however, must match. The second is --forward, which makes patch refuse a hunk that looks already applied instead of offering to reverse it. With || exit 1, any refused hunk brings the build down. Interpretation: tolerance would be a risk on a moving target, but here the target is always the same code, the v0.6.0 tag the diffs were written for and that pip just installed. Whatever the context lets through, the proof import and the recipe's exactness tests (a drafted reply equal to serial decoding, four requests together equal to each one alone) catch later.

This changes the answer of the section on where a change lives. It lives in an image layer, always. There is no writable layer patched at boot and no bind-mount: the code the container runs is the image's code, and a docker restart has no way to keep a hotfix that never existed. Changing a patch costs a rebuild, but a cheap one. The pip install layer comes before COPY patches and stays in the build cache, and the comment in prepare.sh says the rebuild takes seconds. It's the layer-order rule again: what changes little (the engine) at the bottom, what changes a lot (the patches) on top, the stamp last.

Order: each patch is written on top of the previous one

The patches go in in file-name order, and the number in front of the name (0001 … 0053) is the order. Nothing guarantees they commute, and many don't, because several rewrite the same line. The best example is the list of settings the engine checks at startup (below): mine = [...], in the GLM family's engine.py. In v0.6.0 it has 8 items. Patch 0007 adds the copy-draft parameters; 0008, the prompt grid; 0010, the hyper-connection split; and so on up to 0035: nine patches rewrite this same list, which leaves 0035 with 35 integers in the recipe's configuration. (0040 adds one more from inside the function that produces the multi-stream policy's part, without touching that line: the final image checks 36.) Each one carries in its diff, as removed lines, the version of the list the previous one left. In the language of the section on order and parity, the region \(P_k\) writes is the anchor of \(P_{k+1}\), and the order is part of the recipe.

In the figure, the list is a row of tiles and each patch is a stamp carrying its hunk. Pick the set of patches and watch what prepare.sh does with it: the hash, where the image comes from and where the build stops.

Three lessons. Swapping two neighbors already breaks things: 0011 was written against the list 0010 left. Deleting a patch from the middle is the same thing seen from another angle. And both failures happen at build time, inside prepare.sh, which start.sh runs before stopping the server that is up: a broken set of patches never takes down a healthy service. That was the work of v1.3 when it moved to TensorFold v0.6.0: rebase every diff, delete the ones upstream absorbed and renumber the rest.

The image's name is the hash of its inputs

The image has a tag that comes from the hash of what defines it:

\[ h = \operatorname{SHA256}\big(P_{0001} \,\|\, P_{0002} \,\|\, \cdots \,\|\, P_{0053} \,\|\, E\big)_{[1..12]}, \qquad \text{tag} = \texttt{v0.6.0-}h \]
  • \(P_i\): the bytes of each patches/*.patch file, concatenated in name order (it's the cat patches/*.patch in config.sh); \(\|\) is concatenation
  • \(E\): the IMAGE_EXTRAS line (av==18.1.0 xgrammar>=0.2.8,<0.3). Changing an extra package changes the image just like changing a patch
  • \([1..12]\): the first 12 hex digits, 48 bits. By the birthday paradox, an accidental collision only becomes likely around \(2^{24} \approx 1.7 \times 10^{7}\) different patch sets
  • In release v1.3.2, \(h = \texttt{ae8d1c789b47}\) and the tag is v0.6.0-ae8d1c789b47

prepare.sh computes \(h\) and decides where the image comes from. If the local image already has tf.patches equal to \(h\), there's nothing to do. If \(h\) is the release's hash, it pulls the published image by digest (…@sha256:22789f0c…), because a tag can be moved and a digest can't. If \(h\) is something else (you touched a patch), it tries the tag v0.6.0-\(h\) in the registry and, if it doesn't exist, or with PULL=0, it builds, writing \(h\) into the label. A pulled image is only adopted if its tf.patches label equals the computed \(h\), and the worker's image only passes if its content identity matches the head's. It's the vLLM recipe's stamp with one difference: there the tag is fixed (:exl3-instanttensor) and the stamp decides; here every set of patches has its own tag, with the hash in the name itself.

Why pin the digest if the name is already a hash? Because the hash covers the inputs, not the result. The base is a tag (26.07-py3), the engine comes from a git tag and xgrammar is a version range, so two builds with the same \(h\), on different days, can produce different bytes (interpretation). The label says “built from these patches”; only the digest says “these bytes”. Publishing has its own care too. publish-image.sh checks that the label survived the re-tagging with the OCI labels (with them, the GHCR package inherits the repository's visibility), logs in with a temporary DOCKER_CONFIG, deleted at the end, so that no credential stays in ~/.docker, pushes :v0.6.0-\(h\) and :latest, and prints the IMAGE_TAG/IMAGE_DIGEST pair to pin in config.sh. The weights follow the same logic: MODEL_REVISION and DFLASH2_REVISION are Hugging Face commits, the containers run with HF_HUB_OFFLINE=1, and a new commit on the Hub changes nothing until the pin does.

Parity checked by the engine itself

What remains is making sure both ranks run with the same settings. That starts in the launcher. Every TENSORFOLD_*, TF_GLM_* and TF_ROCE_* variable present in the environment goes with -e to both containers, because rank 1's command runs over ssh, where the head's environment doesn't reach (none of them is a secret). Extra arguments to ./start.sh restart … go to both ranks after the defaults, and argparse keeps the last value. And it continues in the engine, with the settings check. At startup, each rank builds the mine list (36 integers in the recipe's configuration), appends at the end how much memory is left for kept prompts, in MiB, and the two run an all-gather. The lists must be identical; the spare memory may differ, and both adopt the smaller one. If anything differs, both stop with a message that shows both lists and asks for the same drafter and the same flags on both ranks.

In the figure, change a knob, turn off forwarding to the worker, as a naive launcher would, and then turn off the check to see what it prevents.

The gain is in the kind of error. Without the check, a divergent configuration becomes the worst kind of failure in this chapter: the group comes up, answers, and hangs on the first collective that falls out of step. With it, the same divergence becomes a refusal at startup, on both ranks, with both lists printed. It's fail-closed applied to parity. The check doesn't replace the launcher's forwarding, which is still what makes the lists match; it only guarantees that, when they don't, nobody serves.

Why everything can be baked at build time

Our interpretation. The vLLM recipe reapplies its overlays on every start because its image is expensive to rebuild: the EXL3 extension compiles at build time, and a git pull that changes an overlay shouldn't cost a recompilation. In TensorFold, the expensive layer (the engine) is stable and the kernels don't even live in the image: they compile on the GB10 on the first start. A per-patch rebuild takes seconds, and baking everything becomes the simplest path. The price shows up elsewhere: every set of patches is a new image to send to the worker (only the layers that changed), each image's first start compiles again, and 53 diffs tied to one engine version need a rebase for every new upstream version.

In the recipes: prove on CPU, version, and retire hacks

CPU tests with upstream fixtures

The Spark pair is expensive and almost always serving. CI runners have no GPU. The way out is to test the patches as text transformations, on CPU, against fixtures: frozen copies of the exact files from the pinned image. In GLM they live in tests/fixtures/*-487ecf187.py.txt; in DeepSeek, in scripts/fixtures/*/…-752a3a504-stock.py (ten families). A good patch test proves six things: the pinned identities match, the transformation is the expected one, applying twice is a no-op, drift is refused, rollback is byte-exact, and the patch is actually wired into the compose or launcher. When the code has to be executed, stubs come in. Qwen's test_draft_vocab.py runs the patched functions with a fake vocab-parallel lm_head and a stubbed collective, and compares against the argmax over the full vocabulary. There are even simulators: DeepSeek's test_issue43_scheduler_sim.py shows that no active decode is skipped in the six cold cells (32K/62K × 2/4/8). In GLM, TRITON_INTERPRET=1 runs Triton kernels in the CPU interpreter.

CI: the gate before merge

DeepSeek's CI (.github/workflows/validate.yml → scripts/ci-validate.sh, ubuntu-24.04, 10 min timeout) runs entirely on CPU. It runs bash -n on every script, py_compile on the patches, ~60 unit tests against the fixtures and regression guards. The retired #31 patch, which scanned tokens on the CPU, must not exist again. The #31 GPU patch must not contain .cpu(, .tolist( or .detach( (syncs on the hot path). The applied #26 must be v2. The build script must pass the #173 self-test. Speed (tok/s) still requires the real pair: CI proves the patch is correct, not that it's fast. After the snapshots, both GLM lanes went the same way. The TensorFold recipe gained a CPU workflow (2026-10-10, bbf7e4b) that applies every patch to the pinned v0.6.0 source, checks that the image tag is the hash of the patch set and runs the tools' tests. In the vLLM lane, fixes such as 4709bc5 (the reasoning effort in the TP4 launcher) come with a test shown to fail on the code before the fix (14 failures on the old launcher): a cheap form of mutation testing, in which the mutant is the old code (our interpretation). And decode-floor v7 (b94fdfd, #283) carries the contract into the installer: pristine, v1, v2, v5 and v5+priority installs migrate to the fresh-install v7 bytes, and v3/v4, drifted, duplicated, marker-only and unmarked helpers are refused unwritten, a versioned, fail-closed migration. In a fleet of patched images, on an H200 cluster too, these three habits (a CPU gate, a test that fails without the fix, a migration that refuses what it does not recognize) are what keep drift out.

CHANGELOG and versions

The CHANGELOG is the operational logbook. Qwen follows Keep a Changelog by date. GLM retroactively labeled its history with SemVer (1.0.0–1.5.0; 1.6.0, from 2026-09-17, is the current cut). DeepSeek organizes by date. In all three, entries carry what an operator needs: the measured number, the issue and the practical instruction (“recreate both containers after the pull”). The CHANGELOG also records what was removed, and why, so no one reintroduces it.

Retiring hacks and the limits of backporting

Every patch is a debt: one day upstream fixes the problem, and the patch has to leave the stage. The recipes show five ways to retire well:

  • Detect and become a no-op. Qwen's patch_block_drop.py (backport of vllm#53388) looks for disable_eagle_block_drop in the image's source. If it's already there, it deletes the old outputs and mounts nothing. patch_determinism.py does the same with use_fused_finalize (it mounts the stock file).
  • A death note in the file itself. patch_qsa_fp8_kv_v030.py says: delete this file, its test and its overlay once the image is vLLM 0.31 or later, which ships #55557 natively.
  • Refuse a half fix. GLM's patch_kpool_tail_seed_stride.py (backport of vLLM #57477) only considers the file fixed upstream if every seed call passes the real strides. A half-fixed file fails the boot.
  • Follow the revert. DeepSeek removed the #50004 backport on 2026-08-22, when upstream reverted it (#51318: intermittent corruption under FULL graphs). Upstream later reintroduced a capture-safe version (#52823), but the pinned base predates #50004 and there's no safe variant to port on top of it.
  • Forbid the comeback. The CPU path of thinking_token_budget (#31/#34) cost a ~4.7× decode cliff and was removed. CI makes sure it doesn't come back.
A sixth way: hand it to upstream

The TensorFold version shows the happiest ending for a patch. In v1.3 of the recipe, which moved from TensorFold v0.5.0 to v0.6.0, three of Mia's patches became part of the engine itself and were deleted: the doorbell on which an idle rank 1 waits without spinning, the TENSORFOLD_MEMORY_RESERVE_GIB memory reserve and TF_GLM_MTP. The rest were rebased onto the new version and renumbered (0024 → 0023 … 0053 → 0050), three new ones came in, and the total stayed at 53. Two habits complete the cycle. Many patches come in switched off, with upstream behavior as the default (TF_GLM_COPY_DRAFTS=0, TF_GLM_HC_SPLIT=0, TF_GLM_COMM=nccl…), and it's the recipe's config.sh that turns each one on, with the measured effect written next to it: every gain becomes a switch that can be measured on its own. And a default that doesn't pay is reverted with measurements. The side stream that overlaps the prefill exchanges was born with high priority (0010); 0017 turned the priority into a knob, still high by default, and 0022 switched the default to normal when two boots with each priority showed the same prefill and, with the high one, decode rounds ~0.5–1% slower after a prompt.

Checklist for your recipe

1. Pin the base by digest and the engine by commit, and keep the digests in the example .env. That's best practice, but of the three recipes only DeepSeek (lane A) does it in the .env; if you use a tag, put another lock in front of it, like GLM's stamp. 2. In the Dockerfile, put what rarely changes at the bottom (compilation) and what changes often on top (Python, label). 3. Write every patch as a partial function: source pin, verified post-image, os.replace, --check. 4. Declare the patch order in a single place and generate the same bytes for every rank. 5. In .env, only atoms; validate numbers, normalize BOM/CRLF, build JSON inside the container. 6. Launcher: lock, validate before stopping, preflight, worker → head, wait with a deadline, fail-fast, canary, and logs from both nodes in a known place. 7. Document exit codes and the restart policy. 8. Test on CPU against fixtures, run it in CI, record it in the CHANGELOG with the “recreate” instruction. 9. Give every hack a way to die: upstream detection or a removal note.
