# Latent Atlas — internationalization (PT → EN) guide

The platform ships in **English (default)** and **Brazilian Portuguese (the authoring source)**. Visitors
always start in English; Portuguese is opt-in, through the PT button in the top bar (the choice is stored in
`localStorage` under `la:lang.choice`) or with `?lang=pt` (`?lang=en` forces English). The browser language is
not used. Each language has its own chapter bundle, catalog and glossary:

| What | Portuguese (source) | English |
|---|---|---|
| Chapter body | `chapters/NN-slug.html` | `chapters/NN-slug.en.html` |
| Chapter metadata + figures | `chapters/NN-slug.js` | `chapters/NN-slug.en.js` |
| Chapter glossary | `chapters/NN-slug.glossary.json` | `chapters/NN-slug.en.glossary.json` |
| UI strings | `assets/js/i18n.js` (`pt`) | `assets/js/i18n.js` (`en`) |
| Parts of the trail | `data/manifest.js` (`title`, `short`, `desc`) | same file (`title_en`, `short_en`, `desc_en`) |
| Catalog | `data/catalog.js` | `data/catalog.en.js` |
| Curated glossary | `data/glossary.js` | `data/glossary.en.js` |
| Bundle | `dist/chapters.bundle.js` | `dist/chapters.en.bundle.js` |

If an English chapter file is missing, the English bundle falls back to the Portuguese chapter and
shows a notice. `node build.js` builds both bundles.

## How to translate a chapter

1. Copy the three files to their `.en` names and translate **only what a reader sees**.
2. `node build.js --lang en --check`
3. `node tools/i18n-check.js <id>` — structure must match the Portuguese version exactly and no
   Portuguese may leak into visible text, figure strings or the glossary.
4. `node tools/qa.js --lang en --shots <id>` and `--mobile` — open the PNGs in `$QA_OUT/<id>.en/`.

### Never change
- Chapter `id`, `part`, `order`, `prereqs`, `recipes`, `tags` values that are ids.
- Every HTML `id`, `class`, `data-*` attribute (`data-term` keys, `data-ch`, `data-sec`, `data-recipe`,
  `data-title` **is translated** — it is the visible figure title), inline `style`.
- Code: `<pre>`/`<code>` content, commands, file paths, env vars, flags, config keys, tensor names,
  JSON keys, regexes. Comments inside code blocks may be translated, and so may the **natural-language
  content of example data** (the prompt/response/message strings inside an example JSON/JSONL or chat
  transcript) — keep the keys, structure, numbers and identifiers exactly as they are.
- The structure: same sections, headings, figures, tables, callouts, equations, quiz questions in the
  same order, with the same correct answer index `a`.
- JavaScript logic. In `.en.js` translate only string literals shown to the reader: `title`, `navTitle`,
  `subtitle`, `goals`, `summary`, `quiz` (`q`, `o`, `e`), stepper steps (`t`, `d`), canvas labels
  (`LA.viz.text(...)`, `box({label})`), control labels (`slider/seg/toggle/select/readout/legend`),
  alerts, tooltips, generated captions, table cells built in JS.
- Numbers and units. **Formatting changes**: in English prose use a decimal point and comma
  thousands (`0,835` → `0.835`, `1.340.476` → `1,340,476`, `≈ 5,15` → `≈ 5.15`). In JS, switch
  `toLocaleString('pt-BR')` to `'en-US'` and remove helpers that swap `.` for `,`.
- Glossary keys: `.en.glossary.json` has exactly the same keys; translate `t` and `d` only.

### Style
Natural, precise US technical English with the same playful, didactic tone. Keep every analogy,
example and callout; translate meaning, not word by word. Keep terms that the community uses in
English (KV cache, prefill, decode, top-k, all-reduce…). Recipe and model names never change.
